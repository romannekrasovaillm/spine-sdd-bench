# Spec Delta

## Purpose

Рекуррентные C2B-списания по согласию плательщика («подписки СБП»): выдача и жизненный цикл согласия, инициация списаний по инициативе ТСП без QR и без действия клиента в момент платежа, контроль лимитов и немедленная остановка списаний при отзыве согласия — с сохранением обратной совместимости существующего API ТСП и инвариантов принятого решения.

## ADDED Requirements

### Requirement: Жизненный цикл согласия плательщика (mandate)

Шлюз MUST поддерживать агрегат «согласие плательщика» (мандат/подписка) со статусами `CREATED`, `PENDING_CONSENT`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`. Согласие переходит в `ACTIVE` **только** по подтверждению от ОПКЦ (воля плательщика), полученному через адаптер; локально «активировать» согласие в обход подтверждения MUST быть невозможно. `REVOKED` и `EXPIRED` — терминальные: новые списания по ним невозможны. Агрегат MUST хранить лимиты (сумма за одно списание, совокупный лимит, срок действия) и непрозрачную ссылку на согласие в ОПКЦ.

#### Scenario: Успешная выдача согласия

- **WHEN** ТСП запрашивает создание согласия и плательщик подтверждает его в приложении своего банка
- **THEN** шлюз фиксирует `PENDING_CONSENT`, по подтверждению от ОПКЦ переводит согласие в `ACTIVE`, сохраняет срок действия и лимиты и уведомляет ТСП событием

#### Scenario: Плательщик не подтвердил согласие

- **WHEN** подтверждение от ОПКЦ не поступило в течение установленного срока
- **THEN** согласие остаётся неактивным (или `EXPIRED`) и ни одно списание по нему не инициируется

#### Scenario: Истечение срока согласия

- **WHEN** наступает срок действия активного согласия
- **THEN** согласие переходит в `EXPIRED`, новые списания блокируются, ТСП получает уведомление

### Requirement: Инициация списания по согласию без QR

Шлюз MUST позволять ТСП инициировать списание по активному согласию. Такое списание создаёт платёж в существующей статусной машине платежа **без выпуска QR** (внутренний путь `CREATED → PAID`), с тем же инвариантом зачисления. Списание MUST быть отклонено без обращения к ОПКЦ, если согласие на момент инициации не в статусе `ACTIVE` или если сумма превышает лимиты. Внешние значения статуса платежа в API ТСП MUST оставаться неизменными (см. Requirement: Обратная совместимость API ТСП).

#### Scenario: Успешное списание по согласию

- **WHEN** ТСП инициирует списание по активному согласию в пределах лимитов
- **THEN** создаётся платёж, шлюз запрашивает списание у ОПКЦ через адаптер, по подтверждению статус становится `PAID`, далее выполняется существующий поток зачисления

#### Scenario: Списание по неактивному согласию

- **WHEN** ТСП инициирует списание по согласию в статусе `PENDING_CONSENT`, `SUSPENDED`, `REVOKED` или `EXPIRED`
- **THEN** шлюз возвращает ошибку `MANDATE_NOT_ACTIVE`, не создаёт платёж и не обращается к ОПКЦ

#### Scenario: Отказ ОПКЦ по списанию

- **WHEN** ОПКЦ отклоняет запрос списания
- **THEN** платёж завершается неуспешно, зачисление не выполняется, ТСП получает уведомление с нормализованной причиной

### Requirement: Лимиты согласия

Шлюз MUST проверять сумму каждого списания против лимитов согласия (предел суммы за одно списание и совокупный/периодический лимит) **до** обращения к ОПКЦ. Превышение лимита MUST приводить к отказу без изменения финансового состояния и без внешнего вызова.

#### Scenario: Превышение лимита одного списания

- **WHEN** ТСП инициирует списание на сумму больше предела одного списания
- **THEN** шлюз возвращает `MANDATE_LIMIT_EXCEEDED`, не обращается к ОПКЦ и не меняет состояние

#### Scenario: Исчерпание совокупного лимита

- **WHEN** суммарные списания по согласию достигли совокупного лимита
- **THEN** дальнейшие списания отклоняются по лимиту до изменения условий согласия

### Requirement: Отзыв согласия — немедленная граница для новых списаний

Отзыв согласия (плательщиком через ОПКЦ или ТСП через API) MUST обрабатываться с приоритетом. После фиксации отзыва шлюз MUST NOT инициировать ни одного нового списания по этому согласию, независимо от конкуренции с параллельными запросами. Уже инициированные списания MUST завершаться по правилам протокола (подтверждение либо компенсация); отзыв MUST NOT приводить к «зависшим» зачислениям. Проверка «согласие активно» и переход/обработка отзыва MUST быть согласованы так, чтобы исключить списание после отзыва.

#### Scenario: Отзыв плательщиком через ОПКЦ

- **WHEN** поступает нотификация ОПКЦ об отзыве согласия
- **THEN** согласие переходит в `REVOKED`, ТСП получает уведомление, все последующие запросы списания отклоняются

#### Scenario: Гонка отзыва и списания

- **WHEN** запрос списания и отзыв согласия происходят одновременно
- **THEN** ни одно списание не остаётся инициированным после фиксации отзыва (fitness-проверка «0 списаний после отзыва»)

#### Scenario: Отзыв при недоступном ОПКЦ

- **WHEN** отзыв инициирован ТСП через API, а канал к ОПКЦ недоступен
- **THEN** шлюз немедленно блокирует новые списания локально (согласие не `ACTIVE`), доводит отзыв до ОПКЦ ретраями и не теряет его

### Requirement: Идемпотентность мандата и списания

Создание согласия, отзыв и инициация списания MUST быть идемпотентными. Повторная доставка любого запроса MUST NOT создавать второй мандат, второе списание или второе зачисление. Для списаний, помимо `Idempotency-Key`, шлюз MUST поддерживать долговременный ключ списания, задаваемый ТСП (например, идентификатор биллингового периода), чтобы повтор за пределами 24-часового окна `Idempotency-Key` не приводил к повторному списанию.

#### Scenario: Повтор запроса списания

- **WHEN** ТСП повторяет запрос списания с тем же ключом и теми же параметрами
- **THEN** возвращается ранее созданное списание (тот же идентификатор), новое списание и зачисление не создаются

#### Scenario: Биллинговый повтор спустя сутки

- **WHEN** повторный запрос списания с тем же долговременным ключом поступает позже 24 часов
- **THEN** шлюз распознаёт повтор и не выполняет второе списание

#### Scenario: Конфликт ключа и тела

- **WHEN** приходит запрос с уже использованным ключом, но другим телом
- **THEN** шлюз возвращает `IDEMPOTENCY_CONFLICT` и не выполняет действий

### Requirement: Зачисление только из подтверждённого статуса (распространение на списания)

Зачисление средств по списанию по согласию MUST быть возможно только из состояния `PAID` (подтверждённый ОПКЦ статус) — как и для разовых платежей. Зачисление из `CREATED` и любого состояния до подтверждения MUST быть недостижимо.

#### Scenario: Попытка зачисления до подтверждения

- **WHEN** платёж по списанию находится в состоянии до `PAID`
- **THEN** вызов зачисления в АБС недостижим (fitness-проверка инварианта)

### Requirement: Обратная совместимость API ТСП

Изменения контракта API ТСП MUST быть аддитивными. Существующие ресурсы, методы, поля и значения перечисления статуса платежа MUST NOT изменяться или удаляться. Новые поля в существующих схемах MUST быть опциональными; новые значения перечислений в существующих полях MUST NOT вводиться. Существующие вебхуки MUST сохранять формат; новые типы событий — дополнение, а потребители MUST игнорировать неизвестные типы. Существующие потребители MUST продолжать работать без изменений.

#### Scenario: Существующий QR-поток не затронут

- **WHEN** существующий ТСП продолжает создавать разовые платежи по QR и получать статусы
- **THEN** формат запросов и ответов, перечисление статусов и набор вебхуков не меняются

#### Scenario: Новый функционал без новой версии API

- **WHEN** ТСП не использует мандаты и не знает о новых полях
- **THEN** ответы остаются для него валидными (новые поля опциональны), перевод на `/v2` не требуется

### Requirement: Расширение контракта адаптера ОПКЦ

Внутренний контракт «ядро ↔ транспортный адаптер» MUST быть расширен аддитивно операциями регистрации/статуса/отзыва согласия и инициации/статуса списания, а также событиями по согласиям. Ядро MUST оставаться контрактно-независимым от протокола НСПК (единственная зависимость — этот контракт). Мутирующие вызовы MUST быть идемпотентны по `reference`; повторный вызов MUST NOT создавать дубль в ОПКЦ. Протокол НСПК MUST знать только адаптер.

#### Scenario: Идемпотентность мандатной операции

- **WHEN** ядро повторно вызывает мандатную операцию с тем же `reference`
- **THEN** адаптер возвращает тот же результат и не создаёт дубль в ОПКЦ

#### Scenario: Отсутствие поддержки у транспорта

- **WHEN** транспортный адаптер не поддерживает мандатные операции
- **THEN** функционал подписок не активируется (fail-closed), базовый C2B-приём продолжает работать без изменений

### Requirement: Нотификации ТСП по согласиям

События по согласиям (активация, отзыв, истечение, результат списания) MUST доставляться ТСП по тем же правилам, что существующие нотификации: at-least-once, подпись HMAC, ретраи с экспоненциальной задержкой, DLQ, дедупликация потребителем по идентификатору события. Недоставленное событие MUST NOT терять операцию: состояние остаётся доступным через API и сверку.

#### Scenario: Недоставка события по согласию

- **WHEN** ТСП не подтверждает получение события
- **THEN** шлюз повторяет доставку, затем помещает событие в DLQ; состояние согласия остаётся доступным через API

#### Scenario: Дедупликация у потребителя

- **WHEN** событие доставлено повторно
- **THEN** ТСП может дедуплицировать по идентификатору события, а состояние в шлюзе не меняется

### Requirement: Аудит, AML/антифрод и минимизация ПДн

Выдача, приостановка, отзыв и истечение согласия, а также каждое списание MUST фиксироваться в неизменяемом аудит-логе. Списания по согласию MUST проходить проверки антифрода/AML в соответствии с действующим контуром банка. Согласие MUST хранить только непрозрачную ссылку на плательщика; персональные данные плательщика сверх необходимого MUST NOT персистироваться, ПДн в логах MUST маскироваться.

#### Scenario: Аудит выдачи и отзыва согласия

- **WHEN** согласие выдано или отозвано
- **THEN** событие с реквизитами операции попадает в неизменяемый аудит-лог

#### Scenario: Подозрительная серия списаний

- **WHEN** серия списаний по согласию попадает под пороги AML/антифрода
- **THEN** операции передаются в AML-контур, решение принимает AML-контур, а не шлюз

#### Scenario: Минимизация ПДн

- **WHEN** шлюз хранит согласие
- **THEN** в хранилище нет персональных данных плательщика сверх непрозрачной ссылки, а в логах нет открытых ПДн

### Requirement: Сверка по согласиям и списаниям

Согласия и списания MUST включаться в сверку с ОПКЦ. Расхождения (в том числе «у ОПКЦ согласие отозвано/не активно, у шлюза активно») MUST попадать в отчёт незавершённых операций и приводить к эскалации; расхождение «у ОПКЦ списание есть, у шлюза нет» MUST компенсироваться дозапросом статуса.

#### Scenario: Расхождение статуса согласия

- **WHEN** сверка обнаруживает расхождение статуса согласия между шлюзом и ОПКЦ
- **THEN** согласие блокируется для новых списаний, инцидент попадает в отчёт и на эскалацию

#### Scenario: Пропущенное списание

- **WHEN** сверка обнаруживает подтверждённое ОПКЦ списание, отсутствующее в шлюзе
- **THEN** шлюз дозапрашивает статус и обрабатывает операцию как нотификацию (идемпотентно)

### Requirement: Измеримые NFR рекуррентных списаний

Новый функционал MUST соответствовать измеримым целям: инициация списания — p95 < 500 мс / p99 < 1 с (без учёта времени ОПКЦ); чтение статуса — p95 < 300 мс; обработка отзыва согласия — 100 % в течение ≤ 60 с от нотификации ОПКЦ и 0 новых списаний после фиксации отзыва; 0 двойных списаний при повторах; 100 % списаний в пределах лимитов; доставка нотификации — p95 < 5 с; доступность мандатного API ≥ 99,95 %; RPO=0 для согласий и списаний; существующие NFR базового C2B-приёма MUST NOT деградировать выше согласованного порога.

#### Scenario: Нагрузочный профиль подписок

- **WHEN** проводится нагрузочный тест биллингового пика (массовые списания)
- **THEN** замеренные лаги, пропускная способность и доля отказов соответствуют целям, а базовый QR-профиль не деградирует выше порога

#### Scenario: Проверка остановки после отзыва

- **WHEN** выполняется тест отзыва согласия под нагрузкой
- **THEN** после фиксации отзыва не зафиксировано ни одного нового списания, а обработка отзыва уложилась в целевое время
