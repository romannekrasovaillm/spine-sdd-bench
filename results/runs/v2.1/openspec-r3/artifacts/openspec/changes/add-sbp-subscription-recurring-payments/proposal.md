# Proposal

## Why

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** («подписки СБП»): одно подтверждённое согласие — далее списания по инициативе ТСП без QR и без действия клиента в момент каждого платежа. Текущее принятое решение (`docs/solutioning.md`, ADR-001..007) обслуживает только разовые оплаты (QR/ссылка), а «автоплатежи» явно отнесены к roadmap **вне scope**. Требуется оформленное расширение scope: это не новая разновидность существующего платежа, а новый финансовый примитив — списание без участия клиента, с отдельным правовым основанием (согласие), новым агрегатом состояния и новой регуляторной поверхностью.

## Significance and route

Оценка значимости — **≈ 12/15, маршрут Critical** (шкала сопоставима с оценкой исходной задачи: 11/15, README.md). Разбивка (суждение архитектора, подтверждается на гейте):

| Измерение | Балл | Обоснование |
|---|---|---|
| Финансовое влияние и регуляторный риск | 3/3 | Списание без действия клиента: выше риск мошенничества/диспутов; согласие — отдельное правовое основание (161-ФЗ, 152-ФЗ, правила НСПК) |
| Глубина изменения принятой архитектуры | 3/3 | Затрагивает статусную машину (AD-002), идемпотентность (AD-003), контракт адаптера ОПКЦ (AD-004), API ТСП, NFR, аудит/AML (AD-007) |
| Новые внешние зависимости и контракты | 2/3 | Новые операции/события протокола НСПК; расширение требований к вендору транспорта (ADR-007/AD-008) |
| Обратимость/сложность отката | 2/3 | До боевых списаний — reversible; после реальных списаний/отзывов — costly (деньги и обязательства уже возникли) |
| Неопределённость внешних входов | 2/3 | Поддержка рекуррентного режима в протоколе ОПКЦ и его форма — `[ТРЕБУЕТ ПРОВЕРКИ]` |

**Почему глубокое проектирование обязательно:** изменение кросс-секущее (статусная машина + идемпотентность + адаптер + контракты + NFR + AML/аудит), вводит необратимое финансовое действие и зависит от внешнего протокола. Поэтому маршрут — полный Solutioning: proposal + delta-спека + design + ADR (Proposed) + задачи, с **отдельным человеческим решением (аналог A3) до начала реализации** и **gate «протокол НСПК подтверждён»**.

## What Changes

- **Новый агрегат «Согласие плательщика» (mandate/подписка)** со своей статусной машиной (`CREATED → PENDING_CONSENT → ACTIVE → REVOKED | EXPIRED`, плюс `SUSPENDED`) и лимитами (сумма за списание, совокупный/периодический лимит, срок действия, периодичность).
- **Новый API ТСП** (аддитивно): создание согласия (инициируется у ОПКЦ/через подтверждение плательщика), чтение статуса, отзыв, **инициация списания по согласию**, чтение статуса списания.
- **Расширение статусной машины платежа**: путь списания по мандату **без QR** (`CREATED → PAID` через внутреннее подсостояние «списание запрошено»). Внешний `Payment.status` (enum) **не меняется** — обратная совместимость сохраняется.
- **Расширение внутреннего контракта адаптера ОПКЦ** (ядро ↔ транспорт): операции `registerMandate`/`getMandateStatus`/`revokeMandate`/`createMandateCharge`/`getMandateChargeStatus` и события `mandate.*` (аддитивно, AD-004/AD-008 сохраняются).
- **Новые вебхуки ТСП** (`mandate.activated`, `mandate.revoked`, `mandate.expired`, событие по списанию) — аддитивно; существующие события не изменяются.
- **Новые инварианты spine (Proposed):** AD-009 «отзыв/недействительность согласия — жёсткая граница для новых списаний», AD-010 «лимиты согласия — потолок списания». Ратифицируются ADR-008 через человеческое решение.
- **Антифрод/AML, лимиты и аудит** на каждое списание по согласию; события выдачи/отзыва согласия — в неизменяемый аудит-лог (AD-007).

**BREAKING:** нет. Все изменения контракта ТСП — аддитивные (новые ресурсы, опциональные поля, новые коды ошибок/события); существующие потребители не затрагиваются. Ломающих изменений в принятых решениях не требуется (см. Impact).

## Impact on Accepted Architecture

| Инвариант | Статус | Что меняется |
|---|---|---|
| AD-001 Изоляция платёжного контура | Не затронут | Новые операции НСПК идут через существующие адаптеры; прямых обращений мимо шлюза не добавляется |
| AD-002 Статусная машина — единый источник истины | **Затронут** | Новый путь перехода для списания по мандату + внутреннее подсостояние; атомарность «статус + outbox + аудит» сохраняется. Новый агрегат (согласие) — отдельная машина состояний |
| AD-003 Идемпотентность финансовых операций | **Затронут (расширение)** | Новые ключи идемпотентности для мандата и списания; 24-часового `Idempotency-Key` недостаточно для биллинговых повторов — нужен долговременный ключ списания |
| AD-004 Единственный адаптер ОПКЦ | **Затронут (аддитивно)** | Адаптер получает mandate-операции; единственность и контрактная независимость ядра (AD-008) сохраняются |
| AD-005 Зачисление только из подтверждённого статуса | Не затронут | Списание по мандату, как и разовый платёж, зачисляется **только из `PAID`**; инвариант перепроверяется fitness-тестом для нового пути |
| AD-006 Trust-зоны и сегментация | Не затронут | Новых зон нет; согласие хранит только непрозрачный идентификатор плательщика (минимизация ПДн) |
| AD-007 НПС/КИИ/ПДн, аудит | **Затронут (расширение)** | Новые аудируемые действия (выдача/отзыв согласия), новая точка AML/антифрода на каждое списание, новая регуляторная поверхность (согласие) |
| AD-008 Стратегия реализации — гибрид [ADOPTED] | **Затронут (ограничения)** | Требования к вендору транспорта расширяются поддержкой рекуррентного режима; контрактная независимость ядра от транспорта сохраняется |

## Capabilities

### New Capabilities

- `sbp-recurring-payments`: рекуррентные C2B-списания по согласию плательщика — жизненный цикл согласия (выдача, активация, лимиты, приостановка, отзыв, истечение), инициация и обработка списаний по согласию, обратная совместимость API ТСП, аудит и сверка согласий.

### Modified Capabilities

Отсутствуют: `openspec/specs/` пока пуст, baseline-поведение описано в `docs/` (state-machine, контракты, NFR, spine). Изменения baseline-требований (статусная машина платежа, контракт адаптера ОПКЦ, контракт API ТСП, NFR, spine) зафиксированы в `design.md` и ADR-008 и применяются на гейтах A1/A3 **способом, принятым в репозитории** (delta-спека + ADR; принятые файлы вручную не переписываются).

## Impact

- **Контракты/документы решения (изменяются на гейте A1, не в этом изменении):** `openapi/tsp-api.yaml` → 0.2.0 (аддитивно), `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`, `docs/spec/state-machine.md`, `docs/nfr.md`.
- **Пакет вендора:** `docs/rfp/vendor-rfp.md` — критерии дополняются поддержкой mandate-протокола ОПКЦ (влияет на ADR-007/AD-008).
- **Spine:** предложение AD-009/AD-010 (ратифицируются ADR-008 через человеческое решение); `ARCHITECTURE-SPINE.md` вручную не правится.
- **Новое решение:** `docs/adr/ADR-008-...md` (Status: Proposed).
- **Handoff:** `.arch-handoff/` регенерируется харнессом после одобрения; ручная правка не производится.
- **Код:** не пишется в этом изменении (planning boundary); задачи для исполнителей — в `tasks.md`.

## Human Decisions (указатель)

Полный перечень — в `design.md` (раздел Human Decisions). Ключевое: (1) регуляторная допустимость и правовая форма согласия; (2) подтверждение поддержки рекуррентного режима протоколом НСПК и его формы — **gate до реализации**; (3) расширение scope roadmap («автоплатежи» были вне scope) и ратификация AD-009/AD-010; (4) требования к вендору транспорта; (5) продуктовая политика лимитов/периодичности/дефолтов (dunning).
