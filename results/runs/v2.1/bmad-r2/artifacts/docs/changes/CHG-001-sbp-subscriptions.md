# CHG-001. Рекуррентные C2B-списания (подписки СБП) — архитектурный пакет изменения

- Status: Proposed — выносится на архитектурное решение (человеческий гейт A3′, см. §7); до ратификации реализация транспортной части запрещена (AD-008/ADR-008 п.2)
- Инициатор: бизнес (ТСП сегментов «онлайн-кинотеатры», «ЖКХ», «связь»)
- Owner: solution-architect (платёжный контур)
- Базовая линия: `docs/solutioning.md`, `ARCHITECTURE-SPINE.md` (AD-001…AD-008), ADR-001…ADR-007, `docs/contracts/tsp-api.md` v0.1, `docs/nfr.md`, `openapi/tsp-api.yaml` v0.1
- Решение: `docs/adr/ADR-008-sbp-podpiski-mandaty-rekurrentnye-spisaniya.md`; спецификация: `docs/spec/mandate-state-machine.md`
- Изменяемые артефакты линии: `ARCHITECTURE-SPINE.md` (AD-003, AD-009, AD-010), `docs/contracts/tsp-api.md` (v0.2), `openapi/tsp-api.yaml` (v0.2.0), `docs/nfr.md` (§7), `docs/solutioning.md` (дельты)

## 0. Суть изменения

Принятое решение принимает только разовые C2B-платежи: плательщик каждый раз сканирует QR и подтверждает платёж. Требуется **рекуррентное списание по согласию плательщика** (подписка СБП / автоплатёж): плательщик один раз оформляет мандат (согласие) в своём банке, далее ТСП инициирует списания без участия клиента; плательщик может отозвать согласие.

Изменение **не создаёт новый денежный путь**: дебет — это платёж в той же статусной машине, том же outbox, с тем же зачислением из `PAID` и той же сагой возврата. Добавляются: сущность «мандат», её жизненный цикл, расширение контракта адаптера ОПКЦ и API ТСП (обратно совместимо).

**Вывод: маршрут — Critical.** Изменение не ниже критичности базового решения (11/15) и требует полного проектного дельта-цикла.

### 1.2. Маршрут и глубина проектирования

**Требуется полное проектирование (полный solutioning-дельта), а не облегчённое**, потому что изменение:
1. меняет **модель авторизации** (кто и на каком основании вправе инициировать списание) — это не косметика контракта, а новый класс финансового риска;
2. вводит **автономное массовое движение денег** — цена ошибки растёт, требуется новый fitness-инвариант и негативные сценарии;
3. **расширяет поверхность контракта** для существующих потребителей-ТСП, где важна обратная совместимость;
4. несёт **регуляторный** слой (согласие/отзыв/уведомление), который нельзя оставить на потом.

Объём дельта-цикла (гейты базового решения A0–A5):
- **A1′ (Spec):** ADR-008, `docs/spec/mandate-state-machine.md`, `docs/contracts/tsp-api.md` v0.2, `openapi/tsp-api.yaml` v0.2.0, расширение контракта адаптера ОПКЦ, `docs/nfr.md` §7.
- **A3′ (человеческое решение, обязательно до транспортной части):** ратификация ADR-008 и §7 настоящего пакета (локус инициации дебета, лимиты, политика уведомления). Без него транспортные работы запрещены (AD-008).
- **A4 (conformance):** новые fitness-тесты (мандат-гейт, идемпотентность дебета), нагрузочный профиль «горячего часа» подписок, ИБ-аудит согласий.
- **A5 (drift):** сверка мандатов/дебетов с ОПКЦ и АБС в проде.

Что **не** требует пересмотра: транспортная стратегия (ADR-007), trust-зоны (ADR-006), денежный путь (ADR-001/002/005), единственный адаптер ОПКЦ (ADR-003). Изменение ложится поверх без локального переопределения родительского spine.

## 2. Влияние на принятую архитектуру

### 2.1. Влияние на инварианты spine (AD-001…AD-008)

| Инвариант | Влияние | Что меняется / что сохраняется |
|---|---|---|
| AD-001 (изоляция платёжного контура) | Не меняется | Мандат и дебет живут в том же платёжном контуре; обращений к АБС/ОПКЦ мимо адаптеров не появляется |
| AD-002 (единый источник истины — статусная машина) | Не меняется | Дебет — платёж в той же машине; переходы «статус + outbox + аудит» атомарны |
| AD-003 (идемпотентность) | **Уточняется** | Rule дополняется ключом дебета `(mandateId, billingRef)`; сама гарантия не ослабляется (spine, AD-003) |
| AD-004 (единственный адаптер ОПКЦ) | **Расширяется** | Контракт адаптера получает операции/события мандата и дебета; граница «ядро ↔ транспорт» сохраняется |
| AD-005 (зачисление только из `PAID`) | Не меняется | Инвариант распространяется на дебеты без исключений; зачисление подписок — тот же гейт |
| AD-006 (trust-зоны и сегментация) | Не меняется | Новых каналов между зонами не появляется |
| AD-007 (соответствие НПС/КИИ/ПДн) | **Усиливается требованиями** | Каждое списание обязано ссылаться на мандат и версию согласия в неизменяемом аудит-логе; согласие/отзыв — регуляторно значимые события |
| AD-008 (гибрид, ядро контрактно-независимо) [ADOPTED] | Не меняется | Расширение протокола НСПК (подписки) полностью укрывается внутренним контрактом адаптера; ограничение «не начинать транспорт до документации НСПК» действует |

### 2.2. Новые инварианты (spine)

- **AD-009** — мандат (согласие) как единственный источник авторизации рекуррентных списаний; гейт `ACTIVE` + лимиты на инициации; немедленная блокировка при отзыве.
- **AD-010** — единый денежный путь: дебет — это платёж в той же машине/outbox; отдельного канала зачисления подписок нет.

### 2.3. Влияние на компоненты и потоки

| Компонент / аспект | Влияние |
|---|---|
| Сервис мандатов (новый) | Жизненный цикл согласия, лимиты, отзыв, сверка мандатов |
| Статусная машина платежа | Новый вход создания дебета без `QR_ISSUED`; переходы D1–D7; AD-005 не меняется |
| Outbox / нотификатор ТСП | Новые события `mandate.*`; результат дебета — существующие `payment.*` |
| Адаптер ОПКЦ | + операции/события мандата и дебета (расширение контракта, не ломающее базовые) |
| Адаптер АБС | Без изменений: зачисление по `paymentId`, списание по `refundId` |
| API ТСП | + ресурсы `/v1/mandates*`, опциональные поля `mandateId`/`billingRef` |
| Сверка | + сверка мандатов (ежечасно), дебеты в общей сверке |
| RFP вендора | + обязательные критерии поддержки подписок (POC-сценарии, идемпотентность дебета) |

### 2.4. Что явно не меняется

- Денежный путь и правило «зачисление только из `PAID`» (AD-005).
- Транспортная стратегия «гибрид» и граница ядро↔адаптер (ADR-007, AD-008).
- Trust-зоны, криптография, аудит-контур (ADR-003, ADR-006, AD-007).
- Семантика существующих ошибок и **значения статусов `Payment.status`** (контракт расширяется аддитивно, §4).

## 3. Архитектурное решение

Полный текст: **`docs/adr/ADR-008-sbp-podpiski-mandaty-rekurrentnye-spisaniya.md`**. Кратко:

1. Мандат — отдельный ресурс и единственный источник авторизации; согласие подтверждается в ОПКЦ (`ACTIVE` только по событию оператора).
2. Дебет — платёж в существующей статусной машине и outbox; `QR_ISSUED` в сценарии отсутствует; зачисление только из `PAID`; возврат — та же сага.
3. Идемпотентность дебета — `(mandateId, billingRef)` + `Idempotency-Key`.
4. Лимиты и состояние мандата проверяются до вызова ОПКЦ; отзыв необратим и блокирует дебеты немедленно.
5. Контракт адаптера ОПКЦ расширяется; ядро остаётся контрактно-независимым (AD-008).
6. API ТСП расширяется обратно совместимо (v0.1 → v0.2).
7. Локус инициации дебета (ТСП vs планировщик шлюза) — решение человека-архитектора (§7); baseline — инициатива ТСП.

**Рассмотренные альтернативы** (детально в ADR-008): мандат в ОПКЦ + дебет как платёж (выбрано); расписание только у ТСП с QR на каждое списание (не выполняет требование); биллинговый движок с расписанием в шлюзе (расширяет границы и риск, отложено); отдельная денежная модель подписок (ломает AD-002/AD-005); вендорский модуль подписок «под ключ» (смешивает транспорт и финансовую логику банка).

**Последствия:** переиспользование денежного пути и сертифицированного транспорта, прозрачная авторизация; при этом — новый класс риска автономных списаний, внешняя зависимость от документации НСПК, новая эксплуатационная нагрузка (сверка мандатов, разбор отзывов и in-flight дебетов), необходимость юридической проработки уведомления плательщика.

**Обратимость:** `reversible` до ратификации и до появления активной базы мандатов; `costly` после (отключение затрагивает действующих подписчиков), но управляемая за счёт неизменности денежного пути (stop-new + drain). Необратимой миграции данных нет.

## 4. Изменения контрактов (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`) без поломки потребителей

### 4.1. Правило совместимости

Изменение — **строго аддитивное** (версия `0.1 → 0.2`, путь `/v1` сохраняется). Запрещено: удалять/переименовывать поля, менять типы, добавлять обязательные поля в существующие запросы, удалять значения перечислений, менять семантику существующих статусов. Ни один существующий потребитель v0.1 не должен требовать изменений.

### 4.2. Что добавляется

| Тип изменения | Элемент | Совместимость |
|---|---|---|
| Новый путь | `POST /v1/mandates` — регистрация согласия (Idempotency-Key) | Аддитивно |
| Новый путь | `GET /v1/mandates/{mandateId}` — статус согласия | Аддитивно |
| Новый путь | `POST /v1/mandates/{mandateId}/revoke` — прекращение подписки (ТСП) | Аддитивно |
| Новый путь | `POST /v1/mandates/{mandateId}/debits` — рекуррентное списание (Idempotency-Key) | Аддитивно |
| Новая схема | `MandateRequest`, `Mandate`, `MandateStatus`, `DebitRequest` | Аддитивно |
| Опциональное поле запроса | `PaymentRequest.mandateId` | Аддитивно (не обязательное) |
| Опциональные поля ответа | `Payment.mandateId`, `Payment.billingRef` | Аддитивно |
| Новое перечисление | `MandateStatus = CREATED | CONSENT_PENDING | ACTIVE | SUSPENDED | REVOKED | EXPIRED | REJECTED` | Отдельная схема; **`Payment.status` не меняется** |
| Новые коды ошибок | `MANDATE_NOT_FOUND` (404), `MANDATE_NOT_ACTIVE` (409), `MANDATE_LIMIT_EXCEEDED` (422), `DEBIT_CONFLICT` (409) | Аддитивно к Problem Details; `MANDATE_NOT_ACTIVE` покрывает все не-`ACTIVE` состояния, включая `EXPIRED` (отдельный код `MANDATE_EXPIRED` не вводится) |
| Новые вебхуки | `mandate.activated`, `mandate.suspended`, `mandate.revoked`, `mandate.expired`, `mandate.rejected`; результат дебета — существующие `payment.*` с `mandateId`/`billingRef` | Потребитель обязан игнорировать неизвестные типы событий (правило фиксируется в контракте) |

### 4.3. Ключевые решения по контракту

- **Статусы платежа не расширяются.** Дебет укладывается в существующее множество `CREATED → PAID → CREDITED → COMPLETED` / `FAILED`; `QR_ISSUED` для дебета недостижим. Это исключает поломку потребителей, разбирающих `Payment.status` исчерпывающе.
- **`MandateStatus` — отдельное перечисление**, а не значения `Payment.status`.
- **Идемпотентность дебета** — `Idempotency-Key` + уникальность `(mandateId, billingRef)`; повтор с другой суммой → `409 DEBIT_CONFLICT`. Ключ `(mandateId, billingRef)` уникален на всё время жизни мандата (не ограничен 24-часовым окном `Idempotency-Key`); приоритет конфликтов и семантика лимитов — `docs/spec/mandate-state-machine.md` §5/§5.1. Не более одного `ACTIVE`-мандата на пару `(tspId, payerRef)`.
- **Версия согласия** — `consentVersion` фиксируется при активации мандата и попадает в каждый дебет и аудит-лог (требование AD-009); изменение лимитов = новый мандат.
- **Расширение контракта адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md` §10) — операции `registerMandate`/`getMandateStatus`/`revokeMandate`/`createDebit`/сверка согласий и события `mandate.*`; существующие методы/события и их семантика не изменяются. Обязательное требование к вендору (RFP §8 п.7).
- Обратная совместимость проверяется на A4: diff-проверка схем (отсутствие удалённых/изменённых обязательных элементов) + тест «клиент v0.1 работает без изменений».

## 6. Критерии приёмки и план отката

### 6.1. Критерии приёмки (проверяемые на моках, до боевого транспорта)

| ID | Критерий | Проверка |
|---|---|---|
| AC-CHG1-01 | Сквозной сценарий: регистрация мандата → согласие → `ACTIVE` → дебет → `PAID` → `CREDITED` → `COMPLETED` → вебхук; отзыв → новые дебеты отклоняются | E2E-тест на моках НСПК/АБС |
| AC-CHG1-02 | Повтор `POST .../debits` с тем же `(mandateId, billingRef)`/`Idempotency-Key` → один `paymentId`, одна проводка, одно событие | Тест идемпотентности (негативный) |
| AC-CHG1-03 | Дебет при мандате `CONSENT_PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED` → отказ `MANDATE_NOT_ACTIVE`, вызов ОПКЦ не выполняется | Fitness AD-009 |
| AC-CHG1-04 | Превышение лимитов (сумма/период/число списаний) → `422 MANDATE_LIMIT_EXCEEDED`, проводки нет | Тест границ |
| AC-CHG1-05 | Зачисление только из `PAID`; из `CREATED` недостижимо — для дебета тоже | Fitness AD-005 (расширенный на дебет) |
| AC-CHG1-06 | Повторная доставка входящих событий ОПКЦ (`payment.paid`, `mandate.activated`, `mandate.revoked`) по `eventId` не меняет состояние; наружу ТСП уходят `payment.completed`/`mandate.*` | Тест идемпотентности событий |
| AC-CHG1-07 | `billingRef` повтор с другой суммой → `409 DEBIT_CONFLICT` | Негативный тест |
| AC-CHG1-08 | Совместимость: клиент v0.1 без изменений; diff схем не содержит удалённых/обязательных изменений | Contract-тест/дифф |
| AC-CHG1-09 | Отзыв мандата блокирует новые дебеты ≤ 5 с; in-flight разбирается по runbook | Тест отзыва + runbook |
| AC-CHG1-10 | NFR §7 выполнимы на моках: лаги, идемпотентность, отсутствие двойных списаний | Нагрузочный/интеграционный прогон |
| AC-CHG1-11 | Аудит: 100 % дебетов содержат `mandateId` и `consentVersion` | Проверка аудит-лога |
| AC-CHG1-12 | Лимит резервируется атомарно (единственная точка — сервис мандатов) и освобождается при `FAILED`/`EXPIRED`; повтор дебета не расходует лимит дважды | Тест лимитов/повторов |
| AC-CHG1-13 | Дебет `CREATED` без ответа ОПКЦ дольше TTL → `EXPIRED`, лимит освобождён | Тест TTL |
| AC-CHG1-14 | Гонка: `payment.paid` после `REVOKED` → дебет зачислен (`CREDITED`/`COMPLETED`) и затем возвращён по саге; подтверждённый платёж не «теряется» | Негативный тест гонки |
| AC-CHG1-15 | Не более одного `ACTIVE`-мандата на `(tspId, payerRef)`; повтор `registerMandate` не создаёт второй согласия | Тест уникальности |

### 6.2. План отката

**До боевой эксплуатации:** откат = не включать. Все работы обратимы, данные не мигрируются, фиче-флаг `subscriptions.enabled` выключен по умолчанию.

**Сигналы-триггеры отката (после включения):**
- двойное списание или расхождение дебет/проводка (AC-CHG1-02/05 нарушены);
- дебет при не-`ACTIVE` мандате или списание после отзыва (AC-CHG1-03/09 нарушены);
- несоблюдение уведомления плательщика/лимитов (регуляторный риск);
- рост отказов/жалоб плательщиков по подпискам сверх согласованного порога;
- расхождение сверки мандатов с ОПКЦ > 0 по `REVOKED`.

**Шаги отката:**
1. `stop-new` — запрет новых мандатов и новых дебетов (фиче-флаг на уровне шлюза и по ТСП); приём существующих операций продолжается.
2. `drain` — дождаться/завершить in-flight дебеты; зачисление уже подтверждённых (`PAID`) доводится по общим правилам (AD-005, сверка).
3. Отзыв — обеспечить обработку отзывов согласий (не блокировать `mandate.revoked`), уведомить ТСП и, при необходимости, плательщиков по регламенту.
4. Откат релиза — rolling; **данные мандатов не удаляются** (нужны для аудита и сверки); денежный путь остаётся источником истины до полной сверки с АБС/НСПК.
5. Аварийный сценарий — DLQ → дежурная смена по runbook; RTO ≤ 1 ч (как в базовом плане).

**Владелец решения об откате:** дежурный архитектурный/продуктовый дежурный по платёжному контуру; для регуляторно значимого отзыва — комплаенс/ИБ. Критерий успешного отката: новых дебетов не создаётся, все `PAID`-дебеты доведены до зачисления, сверка мандатов и дебетов сходится, аудит полон.

## 7. Что остаётся на решение человека-архитектора и почему

| ID | Вопрос | Почему на человека (а не на агента) | Владелец | Гейт |
|---|---|---|---|---|
| H1 | **Локус инициации дебета:** только ТСП (baseline), планировщик в шлюзе или гибрид | Меняет границы продукта, эксплуатационную нагрузку и класс риска (шлюз как биллинговая система); trade-off «автономность ТСП ↔ контроль и сложность» | solution-architect + продукт | A3′ |
| H2 | **Точный протокол подписок НСПК** (поля согласия, подтверждение, уведомление, отзыв, in-flight) | Внешний вход; не раскрыт публично `[ТРЕБУЕТ ПРОВЕРКИ]`; до него транспорт реализовать нельзя (AD-008) | проектный офис / НСПК | до A2′ |
| H3 | **Политика уведомления плательщика перед списанием** (нужно ли, срок, канал) | Юридически значимо (161-ФЗ/правила НСПК), не техническое решение | комплаенс/юристы + ИБ | A3′ |
| H4 | **Дефолтные лимиты мандата** (кап суммы, частота, срок) и их конфигурируемость по ТСП | Баланс «удобство ТСП ↔ защита плательщика/антифрод»; влияет на AML | продукт + риск/AML | A3′ |
| H5 | **Допустимость частичных/разовых сумм в рамках мандата** и правил изменения лимитов | Влияет на модель согласия (изменение лимитов = новое согласие?) и контракт | solution-architect + комплаенс | A1′ |
| H6 | **Состав первой волны** (сегменты ТСП, статический QR/подписка, приоритеты) | Бизнес-приоритезация и объём пилота | продукт/бизнес | A3′ |

| H8 | **Хранение идентификаторов плательщика** (токен ОПКЦ vs ПДн) | Минимизация ПДн (ADR-006) против эксплуатационных нужд | ИБ/ДПО | A3′ |

| H10 | **Подтверждение маршрута и значимости** (Critical, 12/15) архитектурным органом | Формальное решение о глубине проектирования и приоритете | архитектурный орган | A3′ |

## 8. Готовность к передаче исполнителям (handoff delta)

После ратификации ADR-008 и закрытия §7 пакет передаётся кодовому харнессу. Дельта к `.arch-handoff/` (базовый пакет walking skeleton не затрагивается):

- **epic-context:** ADR-008 + AD-009/AD-010 + `docs/spec/mandate-state-machine.md` + NFR §7 (дистиллят 800–1500 токенов; подготовлен предварительно — `.arch-handoff/changes/CHG-001-subscriptions/`).
- **CONSTRAINTS.yaml:** новые fitness-правила — мандат-гейт (`ACTIVE` + лимиты), идемпотентность `(mandateId, billingRef)`, отсутствие новых значений `Payment.status`, аддитивность контракта.
- **TASK.md:** сценарии мандата/дебета на моках + негативные сценарии (повтор, отзыв, лимит, отказ соседа).
- **RUBRIC.yaml:** без изменений (оценивает качество пакета, а не предметную область).
- **RFP:** в критерии допуска и POC добавляются сценарии подписок (создание/активация/отзыв мандата, идемпотентность дебета) — после H2.

Передача исполнителям **транспортной части** запрещена до закрытия H2 (нет документации НСПК) — ограничение AD-008/ADR-007. Исполнителям можно передавать ядро (мандат, статусная машина дебета, контракты, NFR, тесты на моках).
