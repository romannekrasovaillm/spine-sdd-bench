# ADR-009. Рекуррентные списания по мандату: тихие списания в лимитах, подтверждение сверх порога, отдельный ресурс `Charge`

- Date: 2026-09-29
- Status: Proposed (выносится на архитектурный гейт A3)
- Owner: solution-architect (платёжный контур) + бизнес-владелец
- Related: ADR-002, ADR-004, ADR-005, ADR-008 (new), AD-002, AD-003, AD-005, AD-010 (new)
- Change: `openspec/changes/sbp-recurring-payments`

## Context

После активации мандата (ADR-008) списания инициирует ТСП. Нужно решить: (1) в каких случаях списание проходит без действия плательщика, а в каких требует его подтверждения; (2) как обеспечить, чтобы ретраи и повторные запуски планировщика ТСП не приводили к двойному списанию; (3) как учитывать лимиты мандата под конкуренцией; (4) как расширить контракт, не сломав существующих потребителей. Бизнес-решение по развилкам: списание — **тихое в пределах лимитов мандата, с подтверждением плательщика сверх порога**.

Ограничения: зачисление возможно только из подтверждённого НСПК статуса (AD-005); существующее перечисление `Payment.status` менять нельзя без поломки потребителей; путь зачисления и сагу возвратов следует переиспользовать.

## Decision

1. **Инициирование списания — ТСП, по действующему мандату.** Списание принимается только по мандату в состоянии `ACTIVE`; иначе — `MANDATE_NOT_ACTIVE`.
2. **Тихие списания в пределах лимита.** Если сумма ≤ доступного остатка лимитов и ≤ порога подтверждения, списание проводится без действия плательщика.
3. **Подтверждение сверх порога.** Если сумма > порога подтверждения (но ≤ жёсткого максимума мандата), списание переходит в `AWAITING_CONFIRMATION`; до подтверждения плательщиком зачисление невозможно; при отсутствии подтверждения в течение TTL списание завершается без списания средств (`EXPIRED`).
4. **Зачисление — только из `PAID`.** `AWAITING_CONFIRMATION` не является подтверждением; вызов АБС идемпотентен (AD-005, AD-010).
5. **Идемпотентность списания — детерминированный ключ** (`mandateId` + итерация подписки) плюс `Idempotency-Key` ТСП, с уникальным ограничением в БД; повторная инициация возвращает существующий `chargeId`.
6. **Учёт лимитов транзакционный:** резерв суммы при инициации и освобождение при `FAILED`/`EXPIRED` выполняются в одной транзакции с переходом состояния (AD-002).
7. **Рекуррентное списание — отдельный ресурс `Charge`** с собственным перечислением статусов (`CREATED`, `AWAITING_CONFIRMATION`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`, `REFUNDED`). Существующее перечисление `Payment.status` **не расширяется**; изменение контракта ТСП — только аддитивное в `/v1`.
8. **Возвраты** по списаниям выполняются существующей сагой (`refundId`) без изменения инварианта AD-005.

## Alternatives Considered

| Развилка | Вариант | Плюсы | Минусы | Выбор |
|---|---|---|---|---|
| Режим списания | Всегда тихо | Максимальная ценность подписки | Высокий клиентский/регуляторный риск, дорогие диспуты | нет |
| Режим списания | Всегда подтверждение | Близко к текущей модели QR | Обесценивает подписку, не решает задачу бизнеса | нет |
| Режим списания | Тихо в лимитах, подтверждение сверх порога | Баланс ценности и защиты | Нужен порог, конфигурируемый по регламенту НСПК | **да** |
| Идемпотентность | Только `Idempotency-Key` ТСП | Просто | Новый ключ при ретрае у ТСП → дубль | нет |
| Идемпотентность | Только автогенерируемый ключ | Просто | Не отсекает повтор инициации | нет |
| Идемпотентность | Детерминированный ключ + ключ ТСП | Отсекает дубли на уровне БД | Нужен уникальный индекс | **да** |
| Модель контракта | Добавить `AWAITING_CONFIRMATION` в `Payment.status` | Единый ресурс | **BREAKING** для строгих потребителей | нет |
| Модель контракта | Флаг `paymentType` в `Payment` без новых состояний | Не ломает перечисление | Не выражает ожидание подтверждения | нет |
| Модель контракта | Отдельный ресурс `Charge` | Нулевая поломка, явная модель | Дублирование представления | **да** |

## Consequences

### Positive

- Задача бизнеса решена: подписки работают без действий плательщика в типичном случае, с защитой плательщика — на крупных суммах.
- Нулевое влияние на существующих потребителей API: только аддитивные изменения.
- Двойные списания и превышение лимитов исключены конструктивно (уникальный индекс, транзакционный резерв).
- Зачисление по-прежнему только из подтверждённого статуса — регуляторное соответствие сохраняется.

### Negative

- Появляется фаза `AWAITING_CONFIRMATION` и её TTL — дополнительная сложность статусной машины и клиентского опыта.
- Порог подтверждения — продуктовый/регуляторный параметр, требующий фиксации с бизнесом и ОПКЦ.
- Дублирование модели `Charge`/`Payment` (смягчено ссылкой списания на итоговый платёж и общим путём зачисления/возврата).

## Reversibility

**reversible.** Режим списания (порог, тихо/подтверждение) — конфигурируемая политика; ресурсная модель `Charge` обратима до боевой эксплуатации. После боевой эксплуатации смена модели контракта — **costly** (затронет потребителей), но не необратима: контракт версионируется через `/v2`.
