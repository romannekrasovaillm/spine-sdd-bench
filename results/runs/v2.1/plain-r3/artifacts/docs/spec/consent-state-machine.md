# Статусная машина согласия плательщика (подписка) — спецификация переходов

- Status: Draft (для ревью на гейте A1′)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, AD-003, AD-009, AD-010, `docs/spec/state-machine.md`

Согласие плательщика (мандат) — **отдельный агрегат** ядра (ADR-008), единственный источник истины по подписке. Платежи, создаваемые списаниями по согласию, используют автомат платежа без изменений (`docs/spec/state-machine.md`); настоящее согласие его не заменяет и не расширяет. Каждый переход согласия — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002/AD-009).

## 1. Состояния

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | согласие зарегистрировано в шлюзе, регистрация в ОПКЦ в процессе | да |
| `PENDING_ACTIVATION` | ожидает подтверждения плательщика / регистрации в ОПКЦ | да |
| `ACTIVE` | мандат активен, списания разрешены | да |
| `SUSPENDED` | приостановлено (исчерпан лимит периода, ручная пауза) | да |
| `REJECTED` | отклонено ОПКЦ/плательщиком при активации (терминальное) | да |
| `REVOKED` | отозвано плательщиком или ТСП (терминальное) | да |
| `EXPIRED` | истёк срок действия `validUntil` (терминальное) | да |

Технические подсостояния (наружу не выставляются): `REGISTRATION_PENDING` (вызов ОПКЦ в процессе), `SYNC_STALE` (нет свежего статуса от ОПКЦ, требуется сверка).

## 2. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| C1 | — | `CREATED` | `POST /v1/consents` (новый `consentId`) | валидные реквизиты мандата, ТСП активен | запись согласия + outbox-событие «регистрация в ОПКЦ» |
| C2 | `CREATED` | `PENDING_ACTIVATION` | ответ адаптера ОПКЦ: регистрация принята | ссылка/идентификатор согласия получены | сохранить `opkcConsentRef`, outbox-уведомление ТСП |
| C3 | `PENDING_ACTIVATION` | `ACTIVE` | событие `consent.activated` (или подтверждение сверкой) | реквизиты активированного мандата совпадают с заявленными | фиксация параметров мандата (иммутабельны), outbox, вебхук `consent.activated` |
| C4 | `CREATED`/`PENDING_ACTIVATION` | `REJECTED` | событие `consent.rejected` / отказ плательщика | — | `reasonCode`, outbox, вебхук `consent.rejected` |
| C5 | `ACTIVE` | `SUSPENDED` | исчерпан лимит периода или ручная приостановка | новых списаний в текущем периоде нет | зафиксировать причину, аудит |
| C6 | `SUSPENDED` | `ACTIVE` | начало нового периода / снятие паузы | согласие не отозвано и не истекло | сброс счётчика периода, аудит |
| C7 | `ACTIVE`/`SUSPENDED` | `REVOKED` | `consent.revoked` от ОПКЦ **или** `DELETE /v1/consents/{consentId}` | — | **немедленный запрет новых списаний**, outbox, вебхук `consent.revoked`, аудит |
| C8 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | таймер `validUntil` | новых списаний не требуется | закрытие согласия в ОПКЦ (по протоколу), вебхук `consent.expired` |

## 3. Запрещённые переходы (инварианты)

- **Списание возможно только из `ACTIVE`.** Из `CREATED`/`PENDING_ACTIVATION`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`REJECTED` инициация списания недостижима (AD-009). Проверяется fitness-тестом.
- `REVOKED`, `EXPIRED`, `REJECTED` — терминальные: переходов из них нет; повторные триггеры идемпотентны.
- **Отзыв необратим**: `REVOKED` не может вернуться в `ACTIVE`; возобновление подписки — только новым согласием.
- Реквизиты мандата (лимит, период, срок, ТСП, назначение) иммутабельны после `ACTIVE`; изменение — новым согласием.
- **Согласие не является основанием для зачисления** (AD-010): зачисление по списанию возможно только из `PAID` платежа.
- Отзыв/истечение согласия не меняет статус уже созданных платежей; их корректировка — возврат (сага, ADR-005).

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| API ТСП `POST /v1/consents` | `Idempotency-Key` | возврат того же `consentId`, состояние не меняется |
| API ТСП `POST /v1/consents/{consentId}/payments` | `(consentId, billingPeriod / attemptId)` | возврат существующего `paymentId`, дубль списания не создаётся |
| Событие ОПКЦ `consent.activated/revoked/expired` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| API ТСП `DELETE /v1/consents/{consentId}` | `consentId` | повторный отзыв возвращает `REVOKED` без побочных эффектов |

## 5. Сверка и восстановление

- Согласия — кандидаты для сверки с НСПК (целевая — ежечасная, как открытые платежи): состояние, лимиты, периоды, отзывы.
- «У НСПК отозвано, у нас `ACTIVE`» → немедленный переход в `REVOKED`, стоп списаний, алерт (риск неверного списания).
- «У нас отозвано, у НСПК `ACTIVE`» → эскалация; гарантировать отсутствие списаний на стороне шлюза.
- Расхождение лимитов/периодов → стоп списаний по согласию до выяснения.
- Согласие в `ACTIVE` при недоступном НСПК — остаётся `ACTIVE`, но списания, требующие подтверждения, уходят в ретраи/DLQ и видны в отчёте незавершённых операций.

## 6. Согласованность с API ТСП и с автоматом платежа

- Маппинг статусов наружу (`docs/contracts/tsp-api.md` §3.6–3.8): `CREATED`, `PENDING_ACTIVATION`, `ACTIVE`, `SUSPENDED`, `REJECTED`, `REVOKED`, `EXPIRED` — без технических подсостояний.
- Платёж, созданный списанием по согласию, отражается в API ТСП существующими статусами платежа; поле `consentId` связывает его с согласием.
- Зачисление по такому платежу — только из `PAID` (AD-005/AD-010).
