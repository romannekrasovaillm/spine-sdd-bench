# Архитектурный контекст инкремента (epic-context) — Подписки СБП

Собран: 2026-09-29. Источники: `ARCHITECTURE-SPINE.md`, `docs/adr/ADR-008-*.md`, `docs/solutioning-subscriptions.md`, `docs/spec/subscription-lifecycle.md`, `docs/contracts/tsp-api-subscriptions.md`, `docs/nfr-subscriptions.md`.

## Цель

Дать ТСП рекуррентные C2B-списания по согласию плательщика поверх уже построенного шлюза. Денежный путь зачисления не меняется; новая сложность — в двух местах: жизненный цикл согласия и идемпотентный планировщик плановых списаний.

## Стыки (контракты, по которым режется работа)

- **ТСП ↔ шлюз**: REST `/v1/subscriptions…` (аддитивно к v0.1), `Idempotency-Key`, вебхуки с `X-SBP-Event-Id`/HMAC. Контракт: `docs/contracts/tsp-api-subscriptions.md` + `openapi/tsp-api.yaml` (0.2.0-draft).
- **Ядро ↔ ОПКЦ**: единственный адаптер (AD-004); новые операции автоплатежа (согласие/списание/отмена) с идемпотентностью по `reference`; события at-least-once с `eventId`. Протокол НСПК ядру неизвестен.
- **Ядро ↔ АБС**: только зачисление из `PAID` (существующий контракт, без изменений).
- **Внутри ядра**: `Charge` (occurrence) → `Payment` (денежный FSM) → АБС/вебхук; состояние и outbox — в одной транзакции.

## Запреты (что менять нельзя)

- Зачисление — только из `PAID`; распространяется на списания по подписке без исключений.
- Списание — только при `Consent=ACTIVE` и `Subscription=ACTIVE` и в пределах лимитов согласия.
- Одна `occurrence` — не более одного `Payment`.
- Внутренние состояния наружу не выставляются: `DEBIT_REQUESTED` → `CREATED`; enum `Payment.status` и обязательные поля v0.1 неизменны.
- Знание протокола НСПК — только в адаптере; операции автоплатежа входят в контракт адаптера.
- Конфликт с любым AD — остановка и эскалация.

## Инварианты (дословные Rule)

**AD-001.** Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза (проверка: сетевые правила и код — единая точка вызова; fitness: отсутствие исходящих вызовов НСПК/АБС вне адаптеров).

**AD-002.** Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера (ревью + fitness-тест на каждый переход).

**AD-003.** Повторная доставка любого сообщения не изменяет уже завершённое состояние. Fitness: тест «повторная нотификация/повторный запрос → состояние не меняется, результат идемпотентен».

**AD-004.** Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.

**AD-005.** Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Fitness: проверка недостижимости зачисления из `CREATED`/`QR_ISSUED`.

**AD-006.** Сеть между зонами — только через межсетевые экраны по белому списку; ключевой материал — в сертифицированном СКЗИ/HSM; доступ операторов — привилегированный контур с 4-eyes для ручных операций.

**AD-007.** Каждый финансовый переход и административное действие — в неизменяемом аудит-логе; все каналы к ОПКЦ — на сертифицированных СКЗИ. Проверка — ИБ-аудит и fitness.

**AD-008.** Ядро шлюза проектируется контрактно-независимым от транспорта (внутренний контракт адаптера ОПКЦ — единственная зависимость). Вендор транспорта обязан предоставить сертификаты ФСТЭК/соответствие требованиям НСПК, тестовый контур, SLA. Реализация транспортного слоя начинается только после подписания контракта и получения документации НСПК.

**AD-009.** Рекуррентное списание — отдельный `Payment` в существующей статусной машине; переходы и инварианты AD-002/AD-005 не изменяются. Согласие плательщика (`Consent`) — отдельный агрегат с собственным жизненным циклом, локально хранится как зеркало ОПКЦ и сверяется регламентно. Списание допускается только при `Consent=ACTIVE` и `Subscription=ACTIVE` и в пределах лимитов согласия. Источник истины по согласию — СБП/ОПКЦ; при расхождении «локально `ACTIVE`, в ОПКЦ `REVOKED`» списание запрещено (fail-safe).

**AD-010.** Каждая плановая попытка списания имеет идентичность `occurrence = (subscriptionId, plannedAt)`; повторный запуск или реплей планировщика не создаёт второго `Payment`. Создание occurrence и связанного `Payment` — в одной локальной транзакции с outbox и аудитом (AD-002). Каждая occurrence имеет ровно один исход (`INITIATED`/`SKIPPED`/`FAILED`) и видна в сверке; occurrence без исхода — 0.

## Приёмка (проверяемое)

Позитив: П1 сквозной путь «подписка → согласие → плановое списание → `PAID→CREDITED→COMPLETED` → вебхук»; П2 отмена подписки прекращает будущие списания; П3 история списаний — ровно один исход на occurrence. Негатив: Н1 реплей планировщика → одно списание; Н2 отказ списания → `Charge=FAILED`, подписка `ACTIVE`; Н3 отзыв согласия → 0 новых списаний; Н4 превышение лимита → отклонено, деньги не двигаются; Н5 недоступность ОПКЦ в `plannedAt` → попытка не потеряна; Н6 повтор нотификации → без второго зачисления; Н7 расхождение сверки согласий → стоп (fail-safe); Н8 потребитель v0.1 не ломается. Пороги — `docs/nfr-subscriptions.md`.

## Откат

Stop-new (фиче-флаг) → остановка планировщика, идущие списания доводятся → управляемое сворачивание активных подписок → сверка (0 occurrence без исхода, 0 списаний после стоп). Сигналы, шаги и владелец решения — `docs/solutioning-subscriptions.md` §9. Владелец решения об откате — архитектор платёжного контура + бизнес/CIO + ИБ.

## Открытые внешние входы (не догадываться, останавливаться и эскалировать)

- Протокол автоплатежа НСПК (окна уведомления, тайминги отзыва, лимиты, кардинальность согласие↔подписки) — `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Поддержка автоплатежа вендором транспорта (расширение RFP).
- Бизнес-политики: ретраи/dunning отказанного списания, пропущенное окно, гонка «отзыв ↔ инициированное списание».
