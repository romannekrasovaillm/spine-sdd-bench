# ADR-008. Подписки СБП: рекуррентные C2B-списания по согласию плательщика

- Date: 2026-09-29
- Status: Proposed (требует человеческого решения на гейте A3 изменения)
- Owner: solution-architect (платёжный контур) + бизнес/CIO + ИБ
- Related: ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-006, ADR-007, AD-002, AD-003, AD-004, AD-005, AD-006, AD-009, AD-010

## Context

**Бизнес-задача.** ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика — «подписки СБП». Сейчас каждый платёж в принятом решении требует регистрации QR и активного действия клиента: для регулярных платежей с постоянной суммой это неприемлемо по клиентскому пути и по стоимости транзакции.

**Границы.** В принятом решении (`docs/solutioning.md` §1) автоплатежи явно вынесены в roadmap вне scope. Перевод их в scope — **смена границ на уровне родительской инициативы** «Подключение банка к СБП (эквайринг C2B)»: spine данного уровня переопределять родительские ограничения не вправе, конфликт эскалируется наверх.

**Что даёт СБП.** Механизм автоплатежа/подписки: согласие плательщика оформляется в СБП (на стороне банка плательщика), списание инициирует ТСП/шлюз, плательщик уведомляется о списании и вправе отозвать согласие. Точные поля, тайминги и правила уведомления — документация НСПК [ТРЕБУЕТ ПРОВЕРКИ].

**Силы, формирующие решение.**

1. Платёж инициируется не плательщиком, а **расписанием**: переходы состояния возникают из времени, а не только из внешних событий. Это новый класс источника переходов для статусной машины (ADR-002).
2. Согласие плательщика — объект с **собственным жизненным циклом** (выдача, приостановка, отзыв, истечение) и юридически значимое доказательство воли плательщика; хранит ПДн (152-ФЗ).
3. **Денежный путь уже решён** и не должен меняться: `PAID → CREDITED → COMPLETED`, зачисление только из подтверждённого статуса (AD-005).
4. Отказ отдельного списания (например, недостаток средств) — **норма, а не терминальный сбой**: подписка продолжает действовать, каждая попытка имеет свой исход.
5. **Отзыв согласия** должен прекращать будущие списания в регламентном окне; расхождение «локально активно, в СБП отозвано» обязано трактоваться в пользу запрета списания (fail-safe).
6. Транспорт к ОПКЦ остаётся единственным адаптером (AD-004), но получает новые операции; это расширяет требования к вендору (ADR-007, RFP).

## A3 Decision (машинно-читаемый пакет для человеческого решения)

- **choice**: `consent-aggregate-plus-scheduler` — согласие плательщика выносится в отдельный агрегат `Consent` (зеркало СБП), подписка `Subscription` описывает расписание и лимиты, каждое плановое списание — обычный `Payment` в существующей статусной машине, а планировщик рекуррентных списаний становится новым компонентом ядра.
- **rationale**: сохраняет неизменным проверенный денежный путь и все финансовые инварианты (AD-002, AD-005), локализует новую сложность в двух местах (жизненный цикл согласия и идемпотентность плановых попыток), не расширяет поверхность доверия (AD-004, AD-006) и остаётся в рамках стратегии гибрида (AD-008).
- **constraints**: (1) зачисление — только из `PAID`, без исключений для списаний по подписке; (2) согласие и подписка не смешиваются с платежом — раздельные агрегаты и раздельные ключи идемпотентности; (3) каждая плановая попытка идемпотентна по `occurrence = (subscriptionId, plannedAt)`; (4) списание допустимо только при действующих согласии и подписке и в пределах лимитов согласия; (5) контракт API ТСП расширяется аддитивно, без ломающих изменений для существующих потребителей; (6) источник истины по согласию — СБП/ОПКЦ, локально — зеркало со сверкой; (7) операции автоплатежа входят в контракт адаптера ОПКЦ (AD-008) и в требования RFP к вендору.
- **rejected options**: `subscription-as-long-payment` (единый «длинный» платёж с дочерними списаниями — ломает семантику атомарного платежа и аудит); `merchant-side-only-scheduling` (ТСП сам вызывает обычный QR API — не решает задачу, нет согласия плательщика); `vendor-subscription-engine` (движок подписок у вендора — противоречит ADR-007, vendor lock-in в финансовой логике); `opkc-only-consent` (согласие только в ОПКЦ без локального зеркала — лишает шлюз идемпотентности, аудита и RPO=0, повторяет ошибку «тонкого прокси» из ADR-001).
- **expiry**: пересмотр при (а) отсутствии у вендора транспорта поддержки автоплатежа СБП; (б) отсутствии в документации НСПК требуемой идемпотентности инициирования списания; (в) ином регулировании уведомления/отзыва согласия, несовместимом с моделью. Плановая ревизия — через 12 месяцев боевой эксплуатации.

## Decision

1. **Согласие плательщика (`Consent`) — отдельный агрегат** с собственным жизненным циклом (`PENDING → ACTIVE → SUSPENDED → REVOKED | EXPIRED | DECLINED`). Одна шаблонная единица согласия может обслуживать несколько подписок одного ТСП в пределах лимитов; отзыв согласия прекращает все связанные подписки. Детализация — `docs/spec/subscription-lifecycle.md`.
2. **Подписка (`Subscription`) — отдельный агрегат**: расписание, сумма/лимиты, ссылка на ТСП и согласие, статус (`PENDING_CONSENT → ACTIVE → SUSPENDED → CANCELLED | REVOKED | EXPIRED`).
3. **Каждое плановое списание — обычный `Payment`** в существующей статусной машине (ADR-002). Изменяется только фаза до `PAID`: вместо `CREATED → QR_ISSUED` списание идёт `CREATED → DEBIT_REQUESTED → PAID`. Канонический список состояний расширяется одним состоянием `DEBIT_REQUESTED` (расширение допустимо по Reversibility ADR-002). Переходы `PAID → CREDITED → COMPLETED` и все запреты AD-005 — **без изменений**.
4. **Планировщик рекуррентных списаний** — новый компонент ядра (в платёжном контуре, AD-006). Переходы атомарны: «создание occurrence + `Payment(CREATED)` + outbox + аудит» в одной локальной транзакции (AD-002). Каждая плановая попытка идемпотентна по `occurrence` (AD-010).
5. **Идемпотентность (расширение AD-003)**: `Idempotency-Key` — для запросов API подписок; `occurrence = (subscriptionId, plannedAt)` — для плановых попыток; `eventId` — для нотификаций о согласии; `reference = paymentId`/`refundId` — для вызовов адаптера (без изменений, `docs/contracts/opkc-adapter.md` §5).
6. **Отказ списания не завершает подписку**: попытка получает исход `FAILED` на уровне платежа; политика ретраев/dunning и порог авто-приостановки — бизнес-решение (см. §10 пакета изменения).
7. **Отзыв согласия — fail-safe**: по нотификации ОПКЦ `consent.revoked` (или по данным сверки) согласие переводится в `REVOKED`, все связанные подписки — в `CANCELLED`, будущие occurrence не инициируются. Политика по уже инициированному списанию (довести vs компенсировать возвратом) — за бизнесом и юристами.
8. **Транспорт — тот же единственный адаптер ОПКЦ** (AD-004). Контракт адаптера расширяется операциями автоплатежа (регистрация/статус согласия, инициирование списания, отмена) — `docs/contracts/opkc-adapter.md` (v0.2). Протокол НСПК автоплатежа по-прежнему знает только адаптер. Требование к вендору RFP расширяется.
9. **Локальное зеркало согласий с обязательной сверкой**: источник истины по согласию — СБП/ОПКЦ; локально хранится зеркало (для идемпотентности, аудита и RPO=0). Регламентная сверка согласий с ОПКЦ — ежечасная (по аналогии со сверкой платежей, ADR-004).
10. **Контракт API ТСП расширяется аддитивно** до v0.2-draft: новые методы подписок, новые опциональные поля, новые коды ошибок; существующие методы, обязательные поля и значения `Payment.status` не меняются. Детали — `docs/contracts/tsp-api-subscriptions.md`, машинный контракт — `openapi/tsp-api.yaml`.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Согласие-агрегат + планировщик, списание = обычный платёж (выбран)** | Денежный путь и все финансовые инварианты неизменны; сложность локализована; согласие и платёж аудируются раздельно; вписывается в гибрид (AD-008) | Новый компонент (планировщик) и новый агрегат; расширение контракта адаптера и требования к вендору |
| Подписка как «длинный» платёж с дочерними списаниями в одном агрегате | Меньше сущностей | Ломает семантику атомарного платежа и единого источника истины (AD-002), запутывает сверку и аудит, неизвестная итоговая сумма и число списаний |
| Расписание только на стороне ТСП (ТСП сам вызывает обычный QR API) | Не требует изменений в шлюзе | Не решает задачу: клиент платит вручную каждый раз; нет согласия плательщика и уведомления о списании; нет регуляторной основы |
| Движок подписок у вендора (расширение гибрида в сторону вендора) | Быстрее старт | Финансовая логика уходит вендору, vendor lock-in, дорогая кастомизация под АБС, сложнее аудит ЦБ — противоречит ADR-007 |
| Согласие только в ОПКЦ, без локального зеркала | Меньше хранения ПДн | Нет идемпотентности плановых попыток, нет аудита и RPO=0, сверка невозможна — повторяет ошибку «тонкого прокси» (ADR-001) |

## Consequences

### Positive

- Денежный путь, статусная машина и все финансовые запреты (AD-002, AD-005) переиспользуются без изменений — минимальный финансовый риск.
- Рекуррентные списания дают бизнесу новые сценарии (подписки, ЖКХ, связь) поверх уже построенного шлюза.
- Согласие как отдельный агрегат даёт аудируемое доказательство воли плательщика и естественную точку для сверки и отзыва.
- Отказ отдельного списания не разрушает подписку — клиентский путь устойчив к недостатку средств.

### Negative

- Новый компонент (планировщик) в платёжном контуре: эксплуатация, мониторинг, отказоустойчивость; это ещё одна критичная зависимость для доступности (NFR).
- Новый класс ПДн (реквизиты плательщика по согласию) и требование хранить доказательство согласия — нагрузка на ИБ и 152-ФЗ.
- Расширение контракта адаптера и требований RFP: вендор может не поддерживать автоплатёж — внешний риск сроков (эскалация к НСПК/вендору).
- Появляется класс «пропущенных/отложенных» плановых списаний, который надо видимо обрабатывать (сверка occurrence), иначе подписки «тихо» перестают собирать деньги.
- Отзыв согласия создаёт гонку с уже инициированным списанием — нужна явная бизнес-политика, иначе жалобы и возвраты.

## Reversibility

**costly** после старта боевых подписок; **reversible** до включения. Модель расширяет существующую (не заменяет): выключение фиче-флага останавливает оформление новых подписок, уже оформленные требуют управляемого сворачивания (соблюдение или массовая отмена с уведомлением плательщика). Данные согласий и occurrence остаются в БД шлюза, обратная миграция не требуется. Расширение статусной машины одним состоянием (`DEBIT_REQUESTED`) не затрагивает уже завершённые платежи.
