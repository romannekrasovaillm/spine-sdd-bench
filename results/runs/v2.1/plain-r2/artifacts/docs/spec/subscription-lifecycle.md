# Статусные модели подписок СБП — спецификация переходов

- Status: Draft (для ревью на гейте A1 изменения)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002, ADR-005, ADR-008, AD-003, AD-005, AD-009, AD-010

Спецификация дополняет `docs/spec/state-machine.md` (статусная машина платежа) и **не заменяет её**. Денежный путь зачисления (`PAID → CREDITED → COMPLETED`) и запреты AD-005 остаются без изменений; здесь описаны новые агрегаты и фаза инициирования списания.

## 1. Три сущности и их разграничение

| Сущность | Смысл | Источник истины | Жизненный цикл |
|---|---|---|---|
| `Consent` (согласие плательщика) | Воля плательщика на рекуррентные списания в пользу ТСП с лимитами | **СБП/ОПКЦ** (локально — зеркало) | §2 |
| `Subscription` (подписка) | Расписание и параметры рекуррентных списаний ТСП | БД шлюза | §3 |
| `Charge` (плановая попытка списания) | Одна плановая попытка; связывает `Subscription` и `Payment` | БД шлюза | §4 |

Ключевое разграничение: **согласие и подписка не смешиваются с платежом**. Финансовое следствие даёт только `Payment` (ADR-002); `Charge` — запись оркестрации плановой попытки.

Кардинальность: одна единица `Consent` может обслуживать **несколько** `Subscription` одного ТСП в пределах лимитов согласия; отзыв согласия прекращает все связанные подписки.

## 2. Жизненный цикл согласия (`Consent`)

| Состояние | Смысл |
|---|---|
| `PENDING` | Согласие запрошено, плательщику выдана ссылка/QR на подписание в СБП |
| `ACTIVE` | Согласие подписано плательщиком и подтверждено ОПКЦ |
| `SUSPENDED` | Согласие приостановлено (ТСП, банк или ОПКЦ); списания не выполняются |
| `REVOKED` | Согласие отозвано плательщиком — терминальное |
| `EXPIRED` | Истёк срок действия согласия — терминальное |
| `DECLINED` | Плательщик не подписал / ОПКЦ отказал — терминальное |

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING` | запрос согласия по инициативе ТСП | ТСП активен, лимиты запроса валидны | выпуск ссылки/QR, аудит, outbox |
| C2 | `PENDING` | `ACTIVE` | событие ОПКЦ `consent.activated` | плательщик = заявленный, лимиты совпадают | зеркало активно, аудит, outbox (активация подписок) |
| C3 | `PENDING` | `DECLINED` | событие ОПКЦ `consent.declined` / истечение окна подписания | — | аудит, уведомление ТСП |
| C4 | `ACTIVE` | `SUSPENDED` | событие ОПКЦ `consent.suspended` | — | приостановка списаний, аудит |
| C5 | `SUSPENDED` | `ACTIVE` | событие ОПКЦ `consent.resumed` | — | возобновление, пересчёт расписания |
| C6 | любой активный | `REVOKED` | событие ОПКЦ `consent.revoked` **или** данные сверки | — | **fail-safe**: все `Subscription` этого согласия → `CANCELLED`, будущие occurrence не инициируются, аудит, алерт |
| C7 | `ACTIVE` | `EXPIRED` | срок действия истёк / событие ОПКЦ | — | подписки → `EXPIRED`, аудит |

Запрещено: `REVOKED`/`EXPIRED`/`DECLINED` — терминальные; возврат к активной работе возможен только оформлением **нового** согласия. Локальный переход в `ACTIVE` без подтверждения ОПКЦ невозможен.

## 3. Жизненный цикл подписки (`Subscription`)

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_CONSENT` | Подписка создана, ожидает действующего согласия | да |
| `ACTIVE` | Расписание активно, списания выполняются | да |
| `SUSPENDED` | Приостановлена (согласие приостановлено или пауза ТСП) | да |
| `CANCELLED` | Отменена ТСП (или каскадом от отзыва согласия) | да |
| `REVOKED` | Прекращена из-за отзыва согласия плательщиком | да |
| `EXPIRED` | Истёк срок согласия/подписки | да |

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| B1 | — | `PENDING_CONSENT` | `POST /v1/subscriptions` (новый `subscriptionId`) | ТСП активен, расписание валидно | запись подписки + outbox + аудит |
| B2 | `PENDING_CONSENT` | `ACTIVE` | `Consent=ACTIVE` | согласие относится к тому же ТСП, лимиты покрывают параметры | расчёт `nextChargeAt` (SCHEDULED-occurrence), outbox |
| B3 | `ACTIVE` | `SUSPENDED` | `Consent → SUSPENDED` или пауза ТСП | — | будущие occurrence не инициируются |
| B4 | `SUSPENDED` | `ACTIVE` | `Consent → ACTIVE` / снятие паузы | — | пересчёт расписания (пропущенные occurrence не «догоняются» автоматически) |
| B5 | любой активный | `CANCELLED` | `POST /v1/subscriptions/{id}/cancel` | инициатор — ТСП/банк | стоп будущих occurrence, outbox, аудит |
| B6 | любой активный | `REVOKED` | `Consent → REVOKED` | — | каскад от C6 |
| B7 | любой активный | `EXPIRED` | `Consent → EXPIRED` | — | каскад от C7 |

## 4. Жизненный цикл плановой попытки (`Charge`) и её связь с платежом

`Charge` — оркестрационная запись с идентичностью `occurrence = (subscriptionId, plannedAt)`. Каждая `Charge` ссылается ровно на один `Payment` (`paymentId`).

| Состояние `Charge` | Смысл | Соответствие в `Payment` |
|---|---|---|
| `SCHEDULED` | Плановая попытка зарегистрирована на `plannedAt` | `Payment` ещё не создан |
| `INITIATED` | Списание инициировано в ОПКЦ | `Payment=DEBIT_REQUESTED` |
| `PAID` | Списание подтверждено ОПКЦ | `Payment=PAID` |
| `CREDITED` | Зачислено на счёт ТСП | `Payment=CREDITED` |
| `COMPLETED` | Доведено до ТСП (вебхук) | `Payment=COMPLETED` |
| `FAILED` | Списание отклонено (недостаток средств, отказ банка плательщика) | `Payment=FAILED` |
| `SKIPPED` | Попытка не инициирована осознанно (согласие/подписка не активны, лимит исчерпан, окно пропущено) | `Payment` не создаётся |

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| H1 | — | `SCHEDULED` | расчёт расписания подписки | `Subscription=ACTIVE`, `Consent=ACTIVE` | запись occurrence (идемпотентно по `occurrence`) |
| H2 | `SCHEDULED` | `INITIATED` | наступление `plannedAt` (или окно после него) | `Consent=ACTIVE` **и** `Subscription=ACTIVE` **и** сумма ≤ лимитов согласия | **атомарно**: `Payment(CREATED→DEBIT_REQUESTED)` + вызов адаптера (outbox) + аудит |
| H3 | `SCHEDULED` | `SKIPPED` | наступление `plannedAt` | согласие/подписка не активны **или** лимит исчерпан | аудит, алерт по политике; `Payment` не создаётся |
| H4 | `INITIATED` | `PAID` | нотификация ОПКЦ о списании | сумма и получатель совпадают | как T4 в `state-machine.md` (outbox на зачисление) |
| H5 | `INITIATED` | `FAILED` | нотификация ОПКЦ об отказе / исчерпаны ретраи инициирования | ошибка не транзиентная | `Payment=FAILED`, аудит, вебхук `charge.failed` |
| H6 | `PAID` → `CREDITED` → `COMPLETED` | — | подтверждение АБС, доставка вебхука | как T8–T10 в `state-machine.md` | без изменений |
| H7 | `SCHEDULED`/`INITIATED` | `SKIPPED` | `Consent → REVOKED` до подтверждения | списание ещё не подтверждено | отмена попытки; если `PAID` уже наступил — политика возврата (см. §7) |

## 5. Расширение статусной машины платежа: состояние `DEBIT_REQUESTED`

- Канонический список состояний платежа (ADR-002) расширяется **одним** состоянием `DEBIT_REQUESTED` — «списание инициировано в ОПКЦ, ожидается подтверждение». Оно занимает место `QR_ISSUED` в ветке подписки: `CREATED → DEBIT_REQUESTED → PAID` вместо `CREATED → QR_ISSUED → PAID`.
- `DEBIT_REQUESTED` — переходное состояние; `PAID` достижим только из `DEBIT_REQUESTED` (для списаний) или из `QR_ISSUED` (для обычных платежей). **Зачисление по-прежнему возможно только из `PAID`** (AD-005) — новые пути зачисления не появляются.
- Расширение допустимо по Reversibility ADR-002 («модель можно расширять новыми состояниями»); уже завершённые платежи не затрагиваются.

## 6. Маппинг наружу (совместимость API ТСП)

Технические состояния наружу не выставляются. Для сохранения обратной совместимости `Payment.status` в API v1 **не получает новых значений**:

| Внутреннее состояние | Значение в `GET /v1/payments/{paymentId}` | Причина |
|---|---|---|
| `DEBIT_REQUESTED` | `CREATED` | не ломать существующий enum `Payment.status` у потребителей v0.1 |
| `ABS_PENDING` | `PAID` + `creditingStatus` | как в принятом решении |

Различение источника — через новое **опциональное** поле `source` (`QR` по умолчанию | `SUBSCRIPTION`) и `subscriptionId`/`chargeId`. Детальный статус плановой попытки (включая `DEBIT_REQUESTED`, `SKIPPED`) виден только в API подписок: `GET /v1/subscriptions/{id}/charges`.

## 7. Гонка «отзыв согласия ↔ инициированное списание» и сверка

- **Fail-safe (AD-009)**: при расхождении «локально `ACTIVE`, в ОПКЦ `REVOKED`» списание запрещено; локальное зеркало обновляется по данным сверки, а не ожидается нотификация.
- **Гонка**: если на момент отзыва списание уже `INITIATED`, а тем более `PAID` — отменить его нельзя. Политика (довести зачисление vs инициировать возврат) — **бизнес-решение**, фиксируется до боевого включения (см. `docs/solutioning-subscriptions.md` §10). Технически: `Consent → REVOKED` не откатывает уже подтверждённый `PAID` (согласуется с запретом «`PAID` необратим», `state-machine.md` §3).
- **Сверка occurrence**: каждое `plannedAt` в пределах горизонта планирования обязано иметь ровно один исход (`INITIATED` или `SKIPPED`). «Пропущенных без исхода» — 0 (AD-010); обнаружение — ежечасная сверка, replay идемпотентен по `occurrence`.
- **Сверка согласий**: ежечасная сверка локального зеркала `Consent` с ОПКЦ; расхождения по активным согласиям — 0; «у ОПКЦ `REVOKED`, локально актив`» обрабатывается немедленно (стоп списаний + алерт).

## 8. Идемпотентность (расширение AD-003)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/subscriptions`, `POST .../cancel` | `Idempotency-Key` | возврат того же `subscriptionId`/состояния, действие не повторяется |
| Плановая попытка списания | `occurrence = (subscriptionId, plannedAt)` | второго `Payment` не создаётся; повторный запуск планировщика безопасен |
| События согласия ОПКЦ | `eventId` | дубль игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Инициирование списания в ОПКЦ | `reference = paymentId` | адаптер не создаёт дубль (opkc-adapter §5, без изменений) |
| Подтверждение/отказ списания | `eventId` | дедупликация (ADR-004, без изменений) |
| Сага возврата по списанию | `refundId` | повтор возвращает существующий `refundId` (без изменений) |

## 9. Запрещённые переходы (инварианты)

- Зачисление в АБС — только из `PAID` (AD-005); для списаний по подписке исключений нет.
- Списание невозможно при `Consent ≠ ACTIVE` или `Subscription ≠ ACTIVE` (AD-009); проверяется fitness-тестом.
- Одна плановая попытка (`occurrence`) — не более одного `Payment` (AD-010).
- `Payment` для списания не может миновать `DEBIT_REQUESTED` (нельзя `CREATED → PAID` в ветке подписки).
- Терминальные состояния согласия (`REVOKED`, `EXPIRED`, `DECLINED`) и производные статусы подписки — необратимы; возобновление — только через новое согласие.
- Сумма и реквизиты планового списания иммутабельны после `INITIATED`.

## 10. Открытые вопросы (для A1)

1. Точные правила уведомления плательщика о списании и окно «до списания» — по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ]; может добавить обязательный шаг «предварительное уведомление» в H2.
2. Модель расписания (фиксированный день месяца / интервал от даты оформления / произвольное) — продукт; влияет на расчёт `occurrence`.
3. Поведение при пропущенном окне (например, АБС/ОПКЦ недоступны в `plannedAt`): «догнать позже» vs `SKIPPED` — бизнес-решение (влияет на H2/H3).
4. Кардинальность «согласие ↔ подписки» (одна единица на N подписок vs 1:1) — финализируется по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ].
5. Необходимость метода паузы/возобновления подписки для ТСП — продукт (в v0.2 осознанно не входит).
