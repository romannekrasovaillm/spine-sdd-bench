# Контракт API ТСП — дополнение v0.2 (подписки СБП / рекуррентные C2B-списания)

- Status: Draft (для ревью на гейте A1 изменения)
- Версия контракта: 0.2-draft (аддитивное расширение v0.1; ломающих изменений нет)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002 (идемпотентность), ADR-004 (нотификации), AD-003, AD-009, AD-010
- Машинный контракт: `openapi/tsp-api.yaml` (`info.version: 0.2.0-draft`)

Дополнение расширяет `docs/contracts/tsp-api.md` (v0.1). Все общие правила (транспорт, кодировка, суммы в копейках, mTLS, rate limiting, корреляция `X-Trace-Id`, формат ошибок RFC 9457) действуют **без изменений**.

## 1. Гарантии совместимости с v0.1

Изменения **аддитивны**; существующие потребители v0.1 не обязаны меняться:

- Существующие методы (`POST /v1/tsp`, `POST /v1/payments`, `GET /v1/payments/{paymentId}`, `POST /v1/payments/{paymentId}/refunds`, `GET .../refunds/{refundId}`) сохраняют сигнатуры, обязательные поля и семантику.
- **`Payment.status` не получает новых значений.** Внутреннее состояние `DEBIT_REQUESTED` (см. `docs/spec/subscription-lifecycle.md` §5) наружу в `GET /v1/payments/{paymentId}` отдаётся как `CREATED`. Это осознанное решение ради совместимости: потребители, разбирающие enum `status` исчерпывающе, не ломаются.
- Новые поля в существующих схемах — только **опциональные** (`Payment.source`, `Payment.subscriptionId`, `Payment.chargeId`). Отсутствие поля = поведение v0.1 (`source = QR`).
- Новые коды ошибок и новые типы вебхуков — расширяемые справочники; потребитель обязан игнорировать неизвестные события и коды (это требование к потребителю, а не ломающее изменение).
- Ломающие изменения, если когда-либо понадобятся, — только через `/v2` с периодом поддержки ≥ 6 мес. (как в v0.1 §6). Введение `/v2` для этого изменения **не требуется**.

## 2. Идемпотентность

- `Idempotency-Key` обязателен для всех `POST` (в том числе новых), правила v0.1 §2 действуют без изменений: тот же ключ + то же тело → тот же ресурс; тот же ключ + другое тело → `409 IDEMPOTENCY_CONFLICT`.
- Для новых `POST` ключ защищает от дублей подписок и отмен: повтор возвращает ранее созданный `subscriptionId`/состояние.

## 3. Новые методы

### 3.1 Создание подписки

`POST /v1/subscriptions`

Назначение: оформить подписку (расписание рекуррентных списаний). Если действующего согласия плательщика нет, ответ содержит ссылку/QR на подписание согласия; активация подписки произойдёт после подтверждения согласия ОПКЦ.

Запрос:
```json
{
  "tspId": "tsp_9f3c2a1b",
  "amount": 29900,                 // копейки, int; сумма одного списания
  "currency": "RUB",
  "schedule": {
    "frequency": "MONTHLY",        // DAILY | WEEKLY | MONTHLY
    "dayOfMonth": 15,              // для MONTHLY
    "anchorDate": "2026-09-29",    // опц.; начало расписания
    "maxCharges": 12               // опц.; ограничение числа списаний
  },
  "consentId": null,               // опц.; если согласие уже оформлено
  "paymentPurpose": "Подписка «Кино+», 1 месяц",
  "merchantOrderId": "sub-100500", // опц., сквозной для ТСП
  "redirectUrl": "https://merchant.example.com/subscription/done" // опц.
}
```

Ответ `201`:
```json
{
  "subscriptionId": "sub_7c2f9a10",
  "tspId": "tsp_9f3c2a1b",
  "status": "PENDING_CONSENT",     // PENDING_CONSENT | ACTIVE | SUSPENDED | CANCELLED | REVOKED | EXPIRED
  "amount": 29900,
  "currency": "RUB",
  "consentId": "cns_3b8e11",
  "consentUrl": "https://qr.nspk.ru/…", // опц.; ссылка/QR на подписание согласия
  "nextChargeAt": null,            // появится после ACTIVE
  "createdAt": "2026-09-29T10:00:00.000Z"
}
```

Правила: `amount` > 0; лимиты — по согласию и лимитам НСПК [ТРЕБУЕТ ПРОВЕРКИ]; расписание иммутабельно после активации (изменение — отмена + новая подписка).

### 3.2 Список подписок

`GET /v1/subscriptions?tspId=…&status=…&cursor=…` → `200` массив `Subscription` (пагинация курсором).

### 3.3 Состояние подписки

`GET /v1/subscriptions/{subscriptionId}` → `200 { subscriptionId, tspId, status, amount, currency, consentId, schedule, nextChargeAt, createdAt, cancelledAt }`

Состояние согласия видно как поле `consent: { consentId, status }` (расширение ответа, опциональное для старых клиентов).

### 3.4 Отмена подписки

`POST /v1/subscriptions/{subscriptionId}/cancel` (обязателен `Idempotency-Key`)

Семантика: прекратить будущие плановые списания. Уже завершённые списания не отменяются (возврат — отдельный метод v0.1 §3.4). Ответ `200 { subscriptionId, status: "CANCELLED", cancelledAt }`.

### 3.5 История списаний подписки

`GET /v1/subscriptions/{subscriptionId}/charges?from=…&to=…&cursor=…`

Ответ `200`:
```json
{
  "items": [
    {
      "chargeId": "chg_1a2b3c",
      "subscriptionId": "sub_7c2f9a10",
      "paymentId": "pay_8d1e4f5a",     // null, если попытка SKIPPED
      "amount": 29900,
      "status": "COMPLETED",           // SCHEDULED|INITIATED|PAID|CREDITED|COMPLETED|FAILED|SKIPPED
      "scheduledAt": "2026-10-15T10:00:00.000Z",
      "attemptedAt": "2026-10-15T10:00:03.000Z",
      "errorCode": null
    }
  ],
  "nextCursor": null
}
```

Примечание: детальный статус попытки (включая `INITIATED`, `SKIPPED`) выставляется **только** здесь; в `GET /v1/payments/{paymentId}` фаза до `PAID` показывается как `CREATED` (совместимость, §1).

## 4. Расширение существующих схем (опционально)

`Payment` (в `GET /v1/payments/{paymentId}`) получает опциональные поля:

```json
{
  "paymentId": "pay_8d1e4f5a",
  "status": "COMPLETED",
  "source": "SUBSCRIPTION",        // опц.; QR (по умолчанию) | SUBSCRIPTION
  "subscriptionId": "sub_7c2f9a10",// опц.; для списаний по подписке
  "chargeId": "chg_1a2b3c"         // опц.
}
```

Остальные поля и значения `status` — без изменений (v0.1 §3.3).

## 5. Новые коды ошибок (расширение справочника v0.1 §4)

| Код | HTTP | Смысл |
|---|---|---|
| `CONSENT_NOT_FOUND` | 404 | Согласие не найдено в СБП |
| `CONSENT_NOT_ACTIVE` | 422 | Согласие не активно (не подписано / приостановлено / отозвано) |
| `CONSENT_REVOKED` | 422 | Согласие отозвано плательщиком — подписка прекращена |
| `SUBSCRIPTION_NOT_ACTIVE` | 422 | Подписка не активна (ожидает согласия / приостановлена / отменена) |
| `AMOUNT_EXCEEDS_CONSENT_LIMIT` | 422 | Сумма превышает лимит согласия |
| `SCHEDULE_INVALID` | 400 | Некорректное расписание |
| `CONSENT_CARDINALITY_CONFLICT` | 409 | Согласие уже связано с подписками несовместимым образом |

Формат ошибки — RFC 9457 (v0.1 §4) без изменений.

## 6. Новые события вебхуков (расширение справочника v0.1 §5)

Подпись, заголовки (`X-SBP-Event-Id`, `X-SBP-Signature`) и механика доставки (at-least-once, ретраи, DLQ) — без изменений.

| Событие | Смысл |
|---|---|
| `subscription.activated` | Подписка активирована (согласие подтверждено) |
| `subscription.cancelled` | Подписка отменена |
| `subscription.revoked` | Подписка прекращена из-за отзыва согласия плательщиком |
| `charge.failed` | Плановое списание отклонено (например, недостаток средств) |
| `consent.expired` | Согласие истекло |

Тело (`charge.failed`):
```json
{
  "eventId": "evt_…",
  "type": "charge.failed",
  "subscriptionId": "sub_7c2f9a10",
  "chargeId": "chg_1a2b3c",
  "paymentId": "pay_8d1e4f5a",
  "amount": 29900,
  "status": "FAILED",
  "errorCode": "INSUFFICIENT_FUNDS",  // нормализованный код [ТРЕБУЕТ ПРОВЕРКИ]
  "timestamp": "2026-10-15T10:00:05.000Z"
}
```

Требование к потребителю: неизвестные типы событий игнорируются (прямая совместимость при добавлении новых).

## 7. Открытые вопросы (для A1)

1. Модель расписания и её выразительность (интервал vs календарный день; часовой пояс списания) — продукт + документация НСПК [ТРЕБУЕТ ПРОВЕРКИ].
2. Нужен ли метод паузы/возобновления подписки для ТСП — продукт (в v0.2 не входит).
3. Набор нормализованных `errorCode` для отказов списания — по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ].
4. Может ли один `consentId` обслуживать несколько подписок одного ТСП — финализируется по документации НСПК (влияет на §3.1/`CONSENT_CARDINALITY_CONFLICT`).
5. Правила уведомления плательщика о списании: влияет ли на публичный API (видимое ТСП предварительное уведомление) — уточняется.
