# Design

## Context

Мотивация — в `proposal.md` (Why). Ниже — только состояние и ограничения, определяющие подход.

Принятое решение «Платёжный шлюз СБП (C2B-приём)» зафиксировано в `ARCHITECTURE-SPINE.md` (инварианты AD-001…AD-008), `docs/solutioning.md`, `docs/adr/ADR-001…007`, контрактах `docs/contracts/{tsp-api,opkc-adapter}.md`, статусной машине `docs/spec/state-machine.md`, NFR `docs/nfr.md` и черновике `openapi/tsp-api.yaml` (v0.1).

Ограничения, формирующие подход:

- **Внешний вход.** Протокол ОПКЦ СБП по согласиям/автоплатежам (поля, тайминги, лимиты, сроки нотификаций) публично не раскрыт; получается по договору через Портал поддержки НСПК. Все протокольные детали помечаются `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **AD-008 [ADOPTED].** Ядро шлюза контрактно-независимо от транспорта; единственная зависимость — внутренний контракт адаптера ОПКЦ. Реальная реализация транспорта — вендорская, начинается после контракта и получения документации НСПК.
- **Инварианты.** Зачисление только из подтверждённого статуса (AD-005), атомарность «статус + outbox + аудит» (AD-002), идемпотентность (AD-003), единственный адаптер (AD-004), trust-зоны (AD-006), НПС/КИИ/ПДн (AD-007). Локальное переопределение родительских ограничений запрещено.
- **Механизм изменения решения.** Правки принятых артефактов (`ARCHITECTURE-SPINE.md`, `docs/`, `openapi/`) вносятся только после ратификации на архитектурном гейте; данный пакет — предложение (OpenSpec change), а не факт изменения принятых файлов.
- **Терминология.** «Согласие плательщика» = mandate; «инициируемое списание» = debit; «подписка» — пользовательское имя сценария регулярных списаний.

## Goals / Non-Goals

**Goals:**

- Добавить рекуррентные C2B-списания по согласию плательщика **без QR и без участия клиента на каждое списание**, сохранив все инварианты принятого решения.
- Ввести согласие как отдельный управляемый ресурс с лимитами, сроком, периодичностью, изменением и отзывом.
- Расширить контракты **аддитивно** — без поломки существующих потребителей API ТСП и без новой мажорной версии.
- Дать измеримые NFR, критерии приёмки (включая негативные сценарии) и план отката.

**Non-Goals:**

- Диспуты/оспаривание списаний — остаются в Deferred (roadmap), вне этой волны.
- Изменение топологии шлюза, trust-зон, стратегии реализации (AD-008) — не пересматриваются.
- Реализация реального протокола НСПК — вне scope (внутренний контракт + мок-адаптер на этом этапе).
- C2C-переводы и выплаты B2C/B2B — не затрагиваются.
- Код в этом пакете не пишется.

## Оценка значимости изменения и маршрута

Изменение оценивается по пяти осям, шкала 1–3 (максимум 15); порог маршрута **Critical ≥ 11**, **High 7–10**, **Standard ≤ 6**.

| Ось | Оценка | Обоснование |
|---|---|---|
| Финансовое влияние | 3 | Рекуррентное списание без участия клиента: несанкционированное или двойное списание — финансовый инцидент и репутационный риск. |
| Регуляторика / ПДн / КИИ | 3 | Согласие — правовое основание по 152-ФЗ; лимиты и мониторинг по 115-ФЗ; операции в контуре КИИ (161-ФЗ, 187-ФЗ, AD-007). |
| Новизна внешней интеграции | 3 | Новый внешний протокол (согласия/автоплатежи) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`, новые регламенты НСПК. |
| Глубина изменения ядра | 3 | Затрагивает статусную модель, API ТСП, внутренний контракт адаптера, БД, сверку, нотификатор, аудит; новые инварианты. |
| Обратимость | 2 | До боевой эксплуатации — reversible (фиче-флаг); после включения и накопления согласий — costly. |

**Итог: 14/15 → маршрут Critical.** Глубокое проектирование обязательно, потому что изменение: (1) финансово значимо и рекуррентно (новый класс ошибок — массовое несанкционированное списание), (2) регуляторно нагружено (согласие = ПДн), (3) опирается на неполученный внешний протокол, (4) меняет ядро и инварианты, (5) требует нового ADR и дельты spine, (6) эволюционирует публичный контракт.

**Маршрут гейтов:** A1 (спект/контракты) → A2 (план) → **A3 (человеческое решение: ратификация нового AD и дельты AD-002/003/005, политика лимитов)** → A4 (конформанс: fitness, нагрузка, ИБ-аудит) → A5 (post-deploy drift). Данный пакет находится **до A3**: он готовит предложение, а не изменяет принятые файлы.

## Влияние на принятую архитектуру

| Инвариант | Статус | Что происходит |
|---|---|---|
| AD-001 Изоляция платёжного контура | Не меняется | Новый поток остаётся внутри шлюза; АБС/ОПКЦ — по-прежнему только через адаптеры. Расширяется состав операций, не границы. |
| AD-002 Единый источник истины | **Расширяется** | Вводятся отдельный автомат согласия и поток инициируемого списания с теми же атомарными переходами «статус + outbox + аудит». Канонические состояния существующего платежа (`CREATED→QR_ISSUED→PAID→CREDITED→COMPLETED`) **не меняются**. |
| AD-003 Идемпотентность | **Расширяется** | Новые ключи: `Idempotency-Key` для `/v1/mandates`, `/v1/debits`; `eventId` для событий ОПКЦ; `mandateId`/`debitId`/`refundId` для вызовов АБС. Правило «повтор не меняет завершённое состояние» сохраняется. |
| AD-004 Единственный адаптер ОПКЦ | Не меняется | Операции согласий/списаний идут через тот же адаптер; протокол НСПК знает только он. Расширяется внутренний контракт и требования к вендору. |
| AD-005 Зачисление только из подтверждённого статуса | **Расширяется** | Для debit — зачисление только из `CONFIRMED`; дополнительный guard «согласие `ACTIVE` и в пределах лимитов». Инвариант не ослабляется. |
| AD-006 Trust-зоны и сегментация | Не меняется | Новые данные (ПДн согласия, реквизиты) обрабатываются в том же защищённом контуре; ключевой материал — в СКЗИ/HSM. |
| AD-007 НПС / КИИ / ПДн | **Расширяется** | Согласие как правовое основание и объект ПДн; лимиты/мониторинг 115-ФЗ; аудит новых переходов. Требования не ослабляются. |
| AD-008 Стратегия (гибрид) [ADOPTED] | Не меняется | Ядро остаётся контрактно-независимым от транспорта; операции согласий добавляются во внутренний контракт адаптера. Родительские ограничения не переопределяются. |
| Deferred (автоплатежи) | **Изменяется формально** | Пункт «автоплатежи» перемещается из Deferred в scope **после** ратификации (решение A-gate). |

**Предлагаемый новый инвариант (к ратификации, рабочий номер AD-009):** «Инициируемое списание допустимо только по согласию в состоянии `ACTIVE` и в пределах его лимитов; подтверждённый отзыв согласия блокирует новые списания, а подтверждённые — завершаются». Fitness-проверки — в разделе приёмки.

**Что меняется:** состав состояний/агрегатов, API ТСП (аддитивно), внутренний контракт адаптера, требования к вендору (RFP), сверка, NFR, типология аудита ПДн.

**Что не меняется:** топология шлюза и AD-001, trust-зоны и AD-006, выбор гибрида и AD-008, семантика существующего потока QR и возвратов для несогласий, канонические состояния существующего платежа, внешний протокол НСПК для QR-приёма.

## Decisions

### D1. Согласие — отдельный агрегат, а не модификация существующего платежа

Решение: вводится отдельный агрегат **mandate** со своим жизненным циклом и отдельный поток **debit**; существующий `Payment` не перегружается.

Альтернативы:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Отдельный агрегат mandate + debit (выбран) | Чистые границы, отдельные автоматы, существующий поток не затрагивается, проще fitness и сверка | Новые таблицы/сервисы, дублирование части кода postановки/статусов |
| Переиспользовать `Payment` с `mandateId` и `qrType=recurrent` | Минимум новых сущностей | Семантика `QR_ISSUED`/QR бессмысленна; размывает автомат и fitness; риск регрессий в существующем приёме |
| Модель «статический QR» как согласие | Переиспользование | У QR нет лимитов, срока, периода, приостановки и отзыва — не покрывает согласие |

**Последствия:** новые агрегаты и состояния; существующий поток платежа остаётся неизменным; требуется новая таблица лимитов/истории версий согласия.

### D2. Два автомата с едиными транзакционными правилами

Решение: согласие — автомат `PENDING → ACTIVE ⇄ SUSPENDED → REVOKED | EXPIRED | REJECTED`; списание — автомат `INITIATED → CONFIRMED → CREDITED → COMPLETED` с терминальными `FAILED | REJECTED | EXPIRED | REVERSED | REFUNDED`. Оба используют AD-002 (атомарная транзакция «статус + outbox + аудит»).

Обоснование: жизненный цикл согласия (дни/месяцы) и жизненный цикл списания (секунды/минуты) имеют разную динамику; смешение усложняет сверку и аудит. Состояния списания сознательно зеркалят состояния платежа для единообразия сверки и отчётности.

### D3. Инициируемое списание проходит те же финансовые гейты

Решение: зачисление — только из `CONFIRMED` (расширение AD-005); идемпотентность — по `Idempotency-Key`, `eventId`, `debitId` (AD-003); зачисление в АБС — через ту же очередь/outbox и идемпотентный адаптер (ADR-005); возврат — та же сага.

Обоснование: финансовый инвариант не зависит от способа инициирования платежа (QR или согласие).

### D4. Enforcement лимитов и статуса — в шлюзе, до ОПКЦ

Решение: проверки «согласие `ACTIVE`», «сумма ≤ maxAmount», «остаток суммарного лимита» выполняются в шлюзе **до** обращения в ОПКЦ, с атомарным резервированием лимита в транзакции. Нарушение — локальный отказ `MANDATE_NOT_ACTIVE`/`MANDATE_REVOKED`/`MANDATE_LIMIT_EXCEEDED`.

Обоснование: защита от гонок (одновременные списания) и от лишних обращений к внешнему оператору; снижает риск несанкционированного списания. Альтернатива «полагаться на ОПКЦ» отвергнута: лимиты согласия должны соблюдаться банком независимо от внешней системы.

### D5. Расширение API ТСП — аддитивное в `/v1`

Решение: добавляются пути `/v1/mandates`, `/v1/mandates/{mandateId}`, `/v1/mandates/{mandateId}/revoke`, `/v1/debits`, `/v1/debits/{debitId}` и новые схемы; существующие пути, поля, коды и семантика не изменяются. Новая мажорная версия не вводится. Детали и YAML-дельта — в разделе «Изменения контрактов».

### D6. Расширение внутреннего контракта адаптера ОПКЦ

Решение: в `docs/contracts/opkc-adapter.md` добавляются операции (регистрация/изменение/отзыв согласия, инициируемое списание, статусы согласий/списаний) и события (`mandate.*`, `debit.*`), нормализованные адаптером. Протокол НСПК остаётся внутри адаптера (AD-004/AD-008). Требования к вендору (идемпотентность по `reference`, тестовый контур, метрики) расширяются на новые операции.

### D7. Отзыв и приостановка — «согласованное в конечном счёте» блокирование

Решение: подтверждённый отзыв/приостановка блокируют новые списания в пределах p99 ≤ 5 с; уже подтверждённые ОПКЦ списания завершаются по своей модели. При задержке события страхует периодический опрос статуса согласия (ADR-004).

### D8. Политика деградации транспорта — как в существующем дизайне

Решение: при `transport.unavailable` регистрация новых согласий/списаний ведёт себя по той же утверждаемой политике, что и регистрация QR (очередь или отклонение по политике, утверждается на A2, `docs/contracts/opkc-adapter.md` §9).

### Последствия решения

**Positive:** согласие и списания изолированы в понятных агрегатах; существующий приём не деградирует; инварианты AD-005/AD-002/AD-003 сохранены в строгой форме; контракт эволюционирует без ломки потребителей.

**Negative:** растёт число состояний и объём сверки; enforcement лимитов требует аккуратной транзакционной работы (гонки); растёт внешняя зависимость (новые регламенты НСПК); повышается эксплуатационная нагрузка (массовые отзывы, DLQ списаний).

**Обратимость:** **reversible** до боевой эксплуатации — функциональность отключается фиче-флагом, контракт аддитивен и не навязывается потребителям, изменения обратимы без миграции. **costly** после включения и накопления согласий — отключение требует массового отзыва согласий и согласованного сворачивания с ТСП/ОПКЦ; но не является необратимым (границы контракта сохраняются, как в ADR-001/ADR-002).

## Изменения контрактов (`openapi/tsp-api.yaml`) без поломки потребителей

**Принцип аддитивности.** Меняются только новые элементы; существующие пути, схемы, поля, коды и семантика не трогаются. Новые поля в ответах — опциональны и могут игнорироваться старыми потребителями. Ломающие изменения возможны только в будущей мажорной версии (≥ 6 мес. поддержки) — существующий принцип `docs/contracts/tsp-api.md` §6 сохраняется.

**Дельта (применяется на этапе apply/после ратификации):** новые пути `/v1/mandates`, `/v1/mandates/{mandateId}`, `/v1/mandates/{mandateId}/revoke`, `/v1/debits`, `/v1/debits/{debitId}`; новые схемы `MandateRequest`, `Mandate`, `DebitRequest`, `Debit`; расширение справочника ошибок (`MANDATE_NOT_FOUND`, `MANDATE_NOT_ACTIVE`, `MANDATE_REVOKED`, `MANDATE_LIMIT_EXCEEDED`) и типов вебхуков (`mandate.*`, `debit.*`). Предлагаемый YAML приведён в Приложении A — он готов к переносу в `openapi/tsp-api.yaml`.

**Гарантия совместимости:** проверяется контрактным тестом — JSON-схемы и пути существующих операций до/после должны совпадать (diff OpenAPI), существующие потребители — проходить без изменений. Соответствие зафиксировано как требование в `specs/tsp-api/spec.md`.

**Также (дельта к `docs/`, после ратификации):** `docs/contracts/tsp-api.md` — новые разделы/ресурсы; `docs/contracts/opkc-adapter.md` — новые операции/события; `docs/spec/state-machine.md` — автомат согласия и поток debit; `docs/nfr.md` — новые метрики; `docs/solutioning.md` и `ARCHITECTURE-SPINE.md` — новый AD и дельта AD-002/003/005.

## Измеримые NFR нового функционала

Базовые значения согласуются с бизнесом и регламентами НСПК (которые могут быть строже); выполнимы на моках и в нагрузочном контуре.

| Метрика | Цель | Метод проверки |
|---|---|---|
| Регистрация/изменение/отзыв согласия (без времени ОПКЦ) | p95 < 600 мс | Нагрузочный тест, APM |
| Инициирование списания (без времени ОПКЦ) | p95 < 500 мс | Нагрузочный тест |
| Блокировка новых списаний после подтверждённого отзыва | p99 ≤ 5 с | Тест отзыва под нагрузкой |
| Зачисление в АБС от подтверждения ОПКЦ | p95 < 60 с (согласовано с SLA АБС) | Метрика процесса |
| Доставка нотификации ТСП | p95 < 5 с | Метрика лага очереди |
| Суммарная нагрузка (QR + списания) | 200 TPS sustained, 500 TPS пик (burst 1000 TPS/мин) | Нагрузочный тест смешанного профиля |
| Доступность | ≥ 99,95 % | SLO-отчёт |
| RPO / RTO | 0 / ≤ 1 ч | Chaos-тест, DR-учения |
| Двойные списания/зачисления при повторах | 0 | Тест повторных доставок |
| Списания по не-`ACTIVE` согласию или сверх лимита | 0 | Fitness + тест enforcement |
| Сверка согласий/списаний с ОПКЦ и АБС | ежечасная/суточная, расхождений 0 | Reconciliation-отчёт |
| Лимит резервируется атомарно при параллельных списаниях | 0 «перерасхода» лимита | Конкурентный тест |

## Risks / Trade-offs

- **[Протокол НСПК по согласиям не получен]** → абстрагировать за внутренним контрактом (AD-008), реализовать мок-адаптер, все протокольные детали помечать `[ТРЕБУЕТ ПРОВЕРКИ]`, начать транспорт только после документации (как ADR-007/ADR-003).
- **[Гонка при параллельных списаниях исчерпывает лимит]** → атомарное резервирование лимита в одной транзакции со сменой состояния; конкурентный fitness-тест.
- **[Двойное списание из-за повторов]** → идемпотентность на всех ключах + fitness-тест «повтор не меняет состояние».
- **[Задержка блокировки после отзыва]** → p99 ≤ 5 с + периодический опрос статуса согласия; алерт на превышение.
- **[Расползание сложности статусной модели]** → единый канонический список состояний в spine/state-machine; запрещённые переходы — fitness.
- **[Незаметная поломка совместимости контракта]** → контрактный тест-diff OpenAPI в CI как критерий приёмки.
- **[Юридический/продуктовый риск «тихого» списания]** → аудит, уведомления плательщику через банк-эмитент (по протоколу ОПКЦ), политика лимитов — на решение A3.

## Migration Plan

1. **Фаза 0 (решение).** Ратификация нового AD и дельты AD-002/003/005, снятие «автоплатежей» из Deferred; получение документации НСПК по согласиям.
2. **Фаза 1 (контракты).** Аддитивное расширение `openapi/tsp-api.yaml` и `docs/contracts/*` — без изменения существующих элементов.
3. **Фаза 2 (ядро).** Агрегат согласия, поток debit, enforcement лимитов, автоматы, outbox/аудит, сверка — на мок-адаптерах.
4. **Фаза 3 (транспорт).** Расширение вендорского адаптера ОПКЦ на новые операции — после контракта с вендором и документации.
5. **Фаза 4 (конформанс и пилот).** Fitness/нагрузка/ИБ-аудит; пилот на ограниченном круге ТСП за фиче-флагом, затем расширение.

**Откат:**

- **До боевой эксплуатации:** функциональность не включается — откат = оставить фиче-флаг выключенным; контракт аддитивен, потребители не затронуты.
- **После включения:** kill-switch на инициируемые списания и фиче-флаг по ТСП (`stop-new-debits`) — новые списания запрещаются без остановки обработки уже открытых; откат релиза — rolling; данные согласий/списаний сохраняются и остаются источником истины до полной сверки с АБС/ОПКЦ; при необходимости — массовый отзыв согласий по согласованной с ТСП процедуре.
- **Сигналы отката:** любое двойное списание/зачисление; списание по не-`ACTIVE` или сверх лимита; превышение p99 блокировки отзыва; деградация доступности ниже 99,95 %; рост DLQ списаний; расхождения сверки, не устранимые за ≤ 4 ч.
- **Владелец решения:** архитектор платёжного контура (владелец ADR) совместно с дежурной сменой и владельцем продукта (фиче-флаг). RTO ≤ 1 ч.

## Критерии приёмки

Функциональные (позитивные):

1. Согласие регистрируется, подтверждается ОПКЦ и переходит `PENDING → ACTIVE`; списание по `ACTIVE`-согласию проходит `INITIATED → CONFIRMED → CREDITED → COMPLETED`, ТСП получает `debit.completed`.
2. Полный/частичный возврат зачисленного списания завершает сагу; полный возврат → `REFUNDED`.
3. События согласия/списания доставляются ТСП с HMAC-подписью и `X-SBP-Event-Id`; при недоставке — DLQ и видимость в отчёте незавершённых операций.

Негативные и граничные (обязательны):

4. Зачисление по debit недостижимо из `INITIATED` (fitness-тест недостижимости).
5. Списание по согласию в `PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`REJECTED` отклоняется локально (`MANDATE_*`), в ОПКЦ не уходит.
6. Списание сверх `maxAmount` или остатка суммарного лимита отклоняется; при параллельных списаниях лимит не превышается (конкурентный тест).
7. Повторный `POST /v1/debits` с тем же `Idempotency-Key` возвращает тот же `debitId`; повторное событие `eventId` не меняет состояние; повторное подтверждение АБС не создаёт вторую проводку.
8. Отзыв согласия: новые списания блокируются (p99 ≤ 5 с), подтверждённое в процессе списания — завершается.
9. Двойных зачислений при повторах — 0.
10. Контрактная совместимость: diff OpenAPI показывает отсутствие изменений в существующих путях/схемах; тесты существующих потребителей проходят без изменений.
11. ИБ/аудит: 100 % новых переходов в неизменяемом аудит-логе; ПДн маскируются в логах; доступ операторов — 4-eyes.
12. Нагрузка: смешанный профиль QR + списания на 500 TPS удерживает целевые p95; RPO=0, RTO ≤ 1 ч на chaos-тесте.

Каждый критерий проверяем тестом или командой; критерии 4–9 — обязательные fitness-правила нового инварианта.

## Open Questions

- Точный набор атрибутов согласия и нормализованных `reasonCode` — после получения протокола НСПК (не меняет выбранный подход; отражается в контракте адаптера аддитивно).
- Нужен ли отдельный метод API для изменения согласия в волне 1 или достаточно версионирования на стороне ОПКЦ — добавляется аддитивно при необходимости (спект-требование уже допускает расширение).
- Формат выписки сверки по согласиям/списаниям (`getReconciliationReport`) — решается с вендором на RFP (как в `docs/contracts/opkc-adapter.md` §9).
- Поведение шлюза при `transport.unavailable` для новых операций — та же политика, что для QR, утверждается на A2.

## Что остаётся на решение человека-архитектора

1. **Ратификация инвариантов:** новый AD (инициируемое списание по согласию) и дельта AD-002/AD-003/AD-005 в `ARCHITECTURE-SPINE.md`; новый ADR в `docs/adr/`; формальное снятие «автоплатежей» из списка Deferred. Без этой ратификации пакет остаётся предложением.
2. **Продуктово-юридическая модель согласия:** состав параметров (периодичность, лимиты, срок), правила «тихих» периодов и уведомления плательщику, соответствие Правилам ОПКЦ СБП и позиция юристов по 152-ФЗ.
3. **Политика лимитов и AML:** пороги 115-ФЗ, максимальные значения, поведение при исчерпании лимита — с владельцем AML/комплаенсом.
4. **Границы волны 1:** диспуты сознательно вне scope (Deferred); подтвердить, нужны ли в волне 1 интерфейсы управления согласием в ЛК банка/ТСП.
5. **Политика деградации транспорта** для новых операций (очередь vs отклонение) — утверждение на A2.
6. **Расширение критериев RFP/выбора вендора** на операции согласий (идемпотентность, тестовый контур, метрики, SLA) — закупки/проектный офис.
7. **Финальные значения NFR** — согласование с бизнесом и регламентами НСПК.
8. **Точная модель изменения согласия** (кто и как инициирует, подтверждение плательщиком) — после документации НСПК.

## Приложение A. Предлагаемая YAML-дельта для `openapi/tsp-api.yaml`

Аддитивный фрагмент; существующие пути/схемы не изменяются. Применяется на этапе apply.

```yaml
paths:
  /v1/mandates:
    post:
      operationId: createMandate
      parameters:
        - in: header
          name: Idempotency-Key
          required: true
          schema: {type: string}
      requestBody:
        required: true
        content:
          application/json:
            schema: {$ref: '#/components/schemas/MandateRequest'}
      responses:
        '201':
          description: Согласие зарегистрировано
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Mandate'}
  /v1/mandates/{mandateId}:
    get:
      operationId: getMandate
      parameters:
        - {in: path, name: mandateId, required: true, schema: {type: string}}
      responses:
        '200':
          description: Статус согласия
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Mandate'}
  /v1/mandates/{mandateId}/revoke:
    post:
      operationId: revokeMandate
      parameters:
        - {in: path, name: mandateId, required: true, schema: {type: string}}
        - in: header
          name: Idempotency-Key
          required: true
          schema: {type: string}
      responses:
        '200':
          description: Отзыв инициирован
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Mandate'}
  /v1/debits:
    post:
      operationId: createDebit
      parameters:
        - in: header
          name: Idempotency-Key
          required: true
          schema: {type: string}
      requestBody:
        required: true
        content:
          application/json:
            schema: {$ref: '#/components/schemas/DebitRequest'}
      responses:
        '201':
          description: Списание инициировано
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Debit'}
  /v1/debits/{debitId}:
    get:
      operationId: getDebit
      parameters:
        - {in: path, name: debitId, required: true, schema: {type: string}}
      responses:
        '200':
          description: Статус списания
          content:
            application/json:
              schema: {$ref: '#/components/schemas/Debit'}
components:
  schemas:
    MandateRequest:
      type: object
      required: [tspId, maxAmount, currency]
      properties:
        tspId: {type: string}
        maxAmount: {type: integer, description: Максимальная сумма одного списания, копейки}
        totalLimit: {type: integer, description: Суммарный лимит, копейки}
        currency: {type: string, enum: [RUB]}
        period: {type: string, enum: [DAY, WEEK, MONTH]}
        expiresAt: {type: string, format: date-time}
        purpose: {type: string}

    Mandate:
      type: object
      required: [mandateId, tspId, status]
      properties:
        mandateId: {type: string}
        tspId: {type: string}
        status:
          type: string
          enum: [PENDING, ACTIVE, SUSPENDED, REVOKED, EXPIRED, REJECTED]
        maxAmount: {type: integer}
        totalLimit: {type: integer}
        remainingLimit: {type: integer}
        currency: {type: string, enum: [RUB]}
        period: {type: string, enum: [DAY, WEEK, MONTH]}
        expiresAt: {type: string, format: date-time}
        merchantOrderId: {type: string}
    DebitRequest:
      type: object
      required: [mandateId, amount]
      properties:
        mandateId: {type: string}
        amount: {type: integer, description: Сумма в копейках}
        paymentPurpose: {type: string}
        merchantOrderId: {type: string}
    Debit:
      type: object
      required: [debitId, mandateId, amount, status]
      properties:
        debitId: {type: string}
        mandateId: {type: string}
        amount: {type: integer}
        status:
          type: string
          enum: [INITIATED, CONFIRMED, CREDITED, COMPLETED, FAILED, REJECTED, EXPIRED, REVERSED, REFUNDED]
        creditingStatus: {type: string}
        createdAt: {type: string, format: date-time}
        merchantOrderId: {type: string}
```
