# 06. Критерии приёмки и план отката

- Status: Draft (для рассмотрения на архитектурном решении)
- Owner: solution-architect (платёжный контур) + владелец продукта
- Связано: ADR-008, `docs/nfr.md` §7, `docs/spec/state-machine.md` §7

## 1. Критерии приёмки

Каждый критерий проверяем тестом/командой. Негативные сценарии обязательны (рубрика handoff: критерии без негативных сценариев и отката не считаются полными).

### 1.1 Позитивные сценарии

| # | Дано / когда | Тогда (проверяемо) |
|---|---|---|
| A1 | Создание мандата (`POST /v1/subscriptions`) с `Idempotency-Key` | `201` + `subscriptionId`; статус `PENDING_OPKC`; запись согласия и outbox — в одной транзакции |
| A2 | ОПКЦ подтверждает мандат (`mandate.registered`) | Мандат `ACTIVE`; вебхук `subscription.activated` доставлен; аудит-запись |
| A3 | Наступает плановое время цикла | Создан цикл-платёж с `(subscriptionId, cycleNumber)`, `DEBIT_PENDING`; вызов `debitMandate` идемпотентен по `paymentId` |
| A4 | ОПКЦ подтверждает списание (`mandate.debit.succeeded`) | Переход в `PAID` → зачисление в АБС из подтверждённого статуса → `CREDITED` → `COMPLETED`; вебхук `payment.completed` с `subscriptionId` |
| A5 | Отмена подписки (`POST /v1/subscriptions/{id}/cancel`) | Мандат `CANCELLED`; новые циклы не создаются; вебхук `subscription.cancelled` |
| A6 | Отзыв согласия плательщиком | Новые циклы блокируются; мандат переводится в терминальное состояние; событие в ОПКЦ |

### 1.2 Негативные сценарии (обязательны)

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| N1 | Повторный запуск цикла (тот же `subscriptionId` + `cycleNumber`) | Ровно одна проводка; повтор не создаёт второй платёж/списание (идемпотентность AD-003). Тест: 2 запуска → 1 зачисление |
| N2 | Повторная доставка события мандата (`eventId`) | Обработанный `eventId` игнорируется; состояние не меняется (AD-003, ADR-004) |
| N3 | «Неизвестный исход» вызова `debitMandate` (таймаут) | Ретрай с идемпотентностью; двойного списания нет; при исчерпании попыток — DLQ, платёж виден в сверке |
| N4 | Отказ плательщика (`mandate.debit.failed`) | Цикл `FAILED`; политика по мандату (SUSPENDED/остаётся ACTIVE) применяется; алерт; отсутствие зачисления |
| N5 | Попытка списания по отозванному/истёкшему мандату | Списание запрещено (guard); зачисление невозможно (AD-005) |
| N6 | **Гонка «отзыв согласия ↔ запуск цикла»** | Побеждает отзыв: цикл не отправляется в ОПКЦ; проверка мандата и создание цикла — в одной транзакции |
| N7 | ОПКЦ недоступен в момент цикла | Цикл не теряется (очередь/ретраи); статус не «перескакивает» в `PAID`; API ТСП деградирует по политике, без потери данных (RPO=0) |
| N8 | `debitMandate` вне подтверждённого статуса | Недостижимо: fitness-тест «зачисление только из подтверждённого статуса» (AD-005) |
| N9 | Создание цикла при недоступной АБС | Платёж остаётся `PAID`/`DEBIT_PENDING`→`PAID`, виден в отчёте незавершённых операций; зачисление гарантируется сверкой (ADR-005) |

### 1.3 Совместимость и нефункциональные

| # | Критерий | Проверка |
|---|---|---|
| C1 | Потребитель v0.1 не ломается | Контрактный тест: неизменность `required` и существующих enum; новые поля игнорируются; новые события не приводят к ошибкам |
| C2 | NFR подписок | Нагрузочные/интеграционные тесты по `docs/nfr.md` §7 |
| C3 | Аудит и ПДн | 100 % циклов и операций с согласием в неизменяемом логе; маскирование ПДн в логах; ИБ-ревью |
| C4 | Сверка мандатов | Ежечасная сверка с ОПКЦ; расхождений по завершённым операциям — 0 |

## 2. План отката

### 2.1 Сигналы отката (триггеры)

- Любое **двойное списание** по одному циклу.
- Любое **списание без действующего согласия**.
- Рост DLQ по циклам выше порога (по мониторингу) или расхождения сверки мандатов.
- Инцидент ИБ, связанный с ПДн/согласиями.
- Деградация базового сервиса разовых платежей из-за нового функционала (нарушение NFR §1–3).

### 2.2 Шаги отката

1. **До боевой активации (GA):** отключить фиче-флаг подписок; контракт v0.2 аддитивен — откат к v0.1 без изменения потребителей; мандаты не создаются. Полностью обратимо.
2. **После GA, при инциденте:**
   - **stop-new**: запрет создания/активации новых мандатов и запуска новых циклов;
   - **honor existing**: обслуживание уже выданных согласий — обработка отзывов и (в пределах обязательств) ранее согласованных списаний; данные мандатов **не удаляются** (нужны для отзыва/сверки);
   - **заморозка планировщика** циклов при критическом дефекте идемпотентности; ручной разбор через DLQ/runbook;
   - **откат релиза** — rolling (система без downtime-деплоя, NFR §1); статусная машина и БД шлюза остаются источником истины, обратной миграции данных нет.
3. **Владелец решения об откате:** архитектор (A3) + владелец продукта; при инциденте ИБ/ПДн — с обязательным участием ИБ.
4. **Критерий успешного отката:** новые циклы не создаются; существующие согласия отзываемы; ни один незавершённый цикл не «потерян» (виден в сверке); нет открытых расхождений с ОПКЦ/АБС.

### 2.3 Согласование с обратимостью ADR-008

План отката соответствует трёхуровневой оценке ADR-008: reversible (до GA) → costly (после появления мандатов; обязанность обслуживать согласия) → irreversible (по факту собранных согласий: прекращается приём новых, но не обработка уже принятых). Правовая интерпретация «honor existing» — на юристов (см. `07-human-decisions.md`).
