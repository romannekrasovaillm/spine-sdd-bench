# Change package: Подписки СБП (рекуррентные C2B-списания)

Архитектурный пакет изменения **поверх принятого решения** «Платёжный шлюз СБП (C2B-приём)». Назначение — вынести изменение на архитектурное решение (A3) и, после ратификации, передать исполнителям.

- Маршрут изменения: **Critical — 13/15** (см. `01-significance-and-route.md`).
- Ключевое решение: **ADR-008** (`docs/adr/ADR-008-podpiski-sbp-rekurrentnye-c2b-spisaniya.md`), статус `Proposed`.
- Изменение аддитивно: корневые инварианты AD-001…AD-008 **не пересматриваются**.

## Как изменялись принятые артефакты (дисциплина репозитория)

- `[ADOPTED]`-блок **AD-008** и **ADR-007 (Accepted)** — **не редактировались**; изменение, затрагивающее стратегию, проведено как новый `Proposed` ADR-008 и `Proposed`-инварианты.
- Новые инварианты в spine добавлены **только** в статусе `Proposed` — действуют после ратификации ADR-008 (принятый в репозитории механизм).
- Расширения контрактов — **аддитивные** (опциональные поля, новые пути/события); существующие обязательные поля и enum не изменялись.
- `.arch-handoff/` **не перегенерирован**: он отражает принятое решение и обновляется харнессом после ратификации (см. `07-human-decisions.md` §4).

## Порядок ревью (рекомендуемый)

1. `01` — согласиться с маршрутом и объёмом проектирования.
2. `02` — подтвердить, что инварианты не ослаблены (главный вопрос архитектора).
3. `ADR-008` — рассмотреть альтернативы и обратимость; принять решение A3.
4. `04`–`06` — контракты, NFR, приёмка/откат.
5. `07` — закрыть решения человека; только затем — передача исполнителям.

## Handoff-дельта (дистиллят для будущей передачи исполнителям)

Заготовка epic-context для инкремента (полный пакет `.arch-handoff/` генерируется харнессом после ратификации; этот блок — смысловое ядро, которое обязано туда попасть).

**Цель.** Добавить рекуррентные C2B-списания по согласию плательщика (подписки СБП) для ТСП, переиспользуя принятое ядро.

**Связывающие инварианты (передавать дословно Rule).**
- AD-001: любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза.
- AD-002: изменение финансового статуса платежа и запись исходящего события (outbox) — в одной локальной транзакции.
- AD-003: повторная доставка любого сообщения не изменяет уже завершённое состояние.
- AD-004: протокол НСПК знает только адаптер ОПКЦ.
- AD-005: вызов АБС на зачисление возможен только из состояния `PAID`.
- AD-006/AD-007: trust-зоны; сертифицированные СКЗИ/ГОСТ; неизменяемый аудит каждого финансового перехода.
- AD-008 [ADOPTED]: ядро контрактно-независимо от транспорта; реализация транспорта — только вендором после контракта и документации НСПК.
- AD-009 (Proposed): подписка — отдельный агрегат над неизменным ядром; каждый цикл — отдельный платёж, подчиняется AD-002/AD-003/AD-005.
- AD-010 (Proposed): согласие плательщика — неизменяемый аудируемый артефакт; списание без действующего согласия запрещено.

**Запрещено менять при реализации.** Финансовый enum статусов платежа; правило зачисления только из подтверждённого статуса; единственный адаптер ОПКЦ; модель идемпотентности; существующие обязательные поля/enum контракта ТСП. Конфликт с любым AD — остановка работы и эскалация.

**Стыки и контракты.** API ТСП v0.2 (`openapi/tsp-api.yaml`); контракт адаптера (`docs/contracts/opkc-adapter.md`, мандаты); планировщик циклов; хранилище мандатов; сверка.

**Критерии приёмки.** Позитивные A1–A6, негативные N1–N9 (включая N1 дубль цикла, N6 гонку «отзыв ↔ цикл»), совместимость C1, NFR C2, аудит/ПДн C3, сверка C4 (`06`).

**Критерий успешного отката.** Новые циклы не создаются; существующие согласия отзываемы; ни один незавершённый цикл не потерян; нет открытых расхождений с ОПКЦ/АБС (`06` §2).

**Контракт результата прогона.** JSON `{status: complete|partial|blocked, assumptions, open_questions, conflicts_with_prior_decisions}`; при конфликте со spine/ADR — `conflicts_with_prior_decisions` + остановка.
