# Контракт API ТСП (мерчант-API) — v0.2 draft

- Status: Draft (для ревью на гейте A1)
- Версия контракта: 0.2 (нестабильная; до A1 фиксируется v1.0-draft). Относительно 0.1 — **аддитивная дельта подписок СБП** (ADR-008, ADR-009): новые пути, схемы, опциональные поля и типы вебхуков; существующие поля и enum `status` не изменяются (совместимость — §8).
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002 (идемпотентность), ADR-004 (нотификации), ADR-008 (подписки), AD-003, AD-009 (spine)

Назначение: контракт между **ТСП/мерчантом** и **СБП-шлюзом банка** (ядро, собственная разработка). Контракт **не зависит** от протокола ОПКЦ СБП (AD-008): адаптер НСПК скрыт за внутренним интерфейсом шлюза.

## 1. Общие положения

- Транспорт: **HTTPS, REST/JSON**, версия пути `/v1`.
- Кодировка: UTF-8. Числа сумм — **целые, в копейках** (minor units), валюта — `RUB` (ISO 4217: 643).
- Временные метки — ISO 8601 (UTC), формат `YYYY-MM-DDTHH:MM:SS.sssZ`.
- Авторизация ТСП: **mTLS** (сертификат ТСП, выпущенный УЦ банка) + `X-API-Key`. Детали финализирует ИБ на A4; для v0.1 — mTLS обязателен.
- **Идентичность и владение (v0.2):** аутентифицированная личность ТСП (mTLS) — авторитетна; `tspId`, если передан в теле, должен ей соответствовать. Для путей `/v1/subscriptions*` `tspId` в теле не передаётся вовсе: владелец выводится из mTLS. Любое чтение/изменение согласия и любая инициация списания авторизуются по владельцу (`consent.tspId` = аутентифицированный ТСП); иначе `403 CONSENT_FORBIDDEN`. Это исключает межмерчантный доступ (IDOR). Для существующих потребителей QR-потока, передающих собственный корректный `tspId`, поведение не меняется.
- Rate limiting: по умолчанию 50 req/s на ТСП (конфигурируемо); превышение — `429` + заголовок `Retry-After`.
- Корреляция: каждый ответ содержит `X-Trace-Id` (генерируется шлюзом, прокидывается в логи/SIEM).

## 2. Идемпотентность

- Заголовок `Idempotency-Key` **обязателен** для всех `POST`.
- Ключ генерирует ТСП (UUID); шлюз хранит маппинг ключ → ресурс **24 часа**.
- Повторный `POST` с тем же ключом и тем же телом → возвращается **тот же ресурс** (тот же `paymentId`/`refundId`), статус 200/201 без повторного действия.
- Повторный `POST` с тем же ключом, но **другим телом** → `409 IDEMPOTENCY_CONFLICT`.
- GET-запросы идемпотентны по своей природе, ключ не требуется.
- Для подписок (v0.2): ключ на `POST /v1/subscriptions` идентифицирует согласие, ключ на `POST /v1/subscriptions/{id}/debits` — отдельное списание (`paymentId`). Повтор с тем же ключом и телом возвращает тот же ресурс и **не создаёт второе списание**.

## 3. Методы

### 3.1 Регистрация ТСП (онбординг)

`POST /v1/tsp`

Запрос:
```json
{
  "inn": "7701234567",
  "ogrn": "1027700132195",
  "name": "ООО «Ромашка»",
  "merchantType": "LE",            // LE | IE | SELF_EMPLOYED
  "mcc": "5411",
  "settlementAccount": "40702810900000000001",
  "pointsOfSale": [
    { "name": "Магазин на Тверской", "address": "Москва, ул. Тверская, 1", "phone": "+74950000000" }
  ],
  "webhookUrl": "https://merchant.example.com/hooks/sbp",
  "webhookSecret": "…"             // секрет для HMAC-подписи вебхуков (см. §5)
}
```

Ответ `201`:
```json
{
  "tspId": "tsp_9f3c2a1b",
  "status": "ACTIVE"
}
```

Примечания: регистрация ТСП в ОПКЦ выполняется асинхронно через адаптер; если ОПКЦ не подтвердил — ТСП получает статус `PENDING_OPKC`, приём платежей недоступен до подтверждения. Критерии отказа (ПОД/ФТ) — на этапе A4.

### 3.2 Создание платежа (динамический QR / ссылка)

`POST /v1/payments`

Запрос:
```json
{
  "tspId": "tsp_9f3c2a1b",
  "amount": 149990,                // копейки, int
  "currency": "RUB",
  "qrType": "dynamic",             // dynamic | static | link
  "paymentPurpose": "Заказ № 12345",
  "ttlSeconds": 900,               // опц.; лимит — по НСПК [ТРЕБУЕТ ПРОВЕРКИ]
  "redirectUrl": "https://merchant.example.com/order/12345/return",
  "merchantOrderId": "order-12345" // опц., сквозной для ТСП
}
```

Ответ `201`:
```json
{
  "paymentId": "pay_8d1e4f5a",
  "qrId": "QR-…",                  // id в ОПКЦ (сквозной для сверки)
  "qrUrl": "https://qr.nspk.ru/AS100001ORTF4GAF80KPJ53K186D9A3G?type=02&bank=…&crc=…",
  "qrImage": "data:image/png;base64,…", // опц., если ТСП не рендерит сам
  "status": "QR_ISSUED",
  "amount": 149990,
  "expiresAt": "2026-08-15T18:00:00.000Z"
}
```

Правила: `amount` > 0; для `qrType=static` сумма может отсутствовать (`amount` опц.); после создания **сумма и реквизиты иммутабельны** (ADR-002). Максимальная сумма — по лимитам НСПК [ТРЕБУЕТ ПРОВЕРКИ].

### 3.3 Запрос статуса платежа

`GET /v1/payments/{paymentId}`

Ответ `200`:
```json
{
  "paymentId": "pay_8d1e4f5a",
  "origin": "qr",                  // v0.2: qr | subscription (опц., по умолчанию qr — обратная совместимость)
  "consentId": null,               // v0.2: subscriptionId согласия, если origin=subscription; иначе null
  "status": "COMPLETED",           // CREATED | QR_ISSUED | PAID | CREDITED | COMPLETED | FAILED | EXPIRED | REFUNDED
  "amount": 149990,
  "paidAt": "2026-08-15T17:31:02.000Z",
  "creditingStatus": "CREDITED",   // технический статус зачисления (для ТСП)
  "refunds": [
    { "refundId": "ref_1a2b3c", "amount": 149990, "status": "COMPLETED" }
  ],
  "errorCode": null,               // код отклонения НСПК, если статус FAILED
  "merchantOrderId": "order-12345"
}
```

`origin` и `consentId` добавлены в v0.2 аддитивно: для QR-платежей `origin` может отсутствовать (трактуется как `qr`), `consentId` — `null`. Enum `status` не расширялся: внутреннее подсостояние списания `DEBIT_ISSUED` наружу отображается как `CREATED` (см. `docs/spec/subscription-state-machine.md` §4).

### 3.4 Возврат (полный/частичный)

`POST /v1/payments/{paymentId}/refunds`

Запрос:
```json
{
  "amount": 149990,                // <= оплаченная сумма; опц. (по умолчанию — полный)
  "reason": "Возврат по заявлению клиента"
}
```

Ответ `201`:
```json
{ "refundId": "ref_1a2b3c", "paymentId": "pay_8d1e4f5a", "amount": 149990, "status": "PENDING" }
```

Правила: возврат возможен только если платёж в состоянии `CREDITED`/`COMPLETED` (ADR-005, сага). Полный возврат переводит платёж в `REFUNDED`; частичные — платёж остаётся `COMPLETED`, возврат виден в `refunds[]`. Статус возврата: `PENDING → COMPLETED | FAILED`. Правила одинаковы для платежей `origin=qr` и `origin=subscription`: возврат по списанию идёт той же сагой (ADR-005) и не зависит от текущего статуса согласия.

### 3.5 Статус возврата

`GET /v1/payments/{paymentId}/refunds/{refundId}` → `200 { refundId, paymentId, amount, status, completedAt }`

### 3.6 Создание подписки (согласия плательщика) — v0.2

`POST /v1/subscriptions`

Создаёт согласие плательщика на рекуррентные списания в пользу ТСП. **`tspId` в теле отсутствует**: владелец согласия выводится из аутентифицированной личности ТСП (mTLS-сертификат); запрос с чужим `tspId` невозможен. Запрос:

```json
{
  "payerRef": "tok_…",              // токен/деплинк плательщика; полный MSISDN не принимается и не хранится (ADR-006 §4)
  "amountLimit": 99900,             // лимит суммы одной операции, копейки — обязателен
  "periodLimit": 299900,            // лимит суммы за период, копейки — обязателен для периодических режимов
  "period": "MONTHLY",              // MONTHLY | WEEKLY | ON_DEMAND (по требованиям НСПК [ТРЕБУЕТ ПРОВЕРКИ])
  "paymentPurpose": "Подписка «Кинопоиск»",
  "expiresAt": "2027-08-15T00:00:00.000Z", // срок действия согласия; лимит — по НСПК [ТРЕБУЕТ ПРОВЕРКИ]
  "redirectUrl": "https://merchant.example.com/subscription/return",
  "merchantConsentId": "sub-order-777"     // опц., сквозной идентификатор ТСП
}
```

Ответ `201` (`SubscriptionCreated` — расширенная схема только для ответа на создание):

```json
{
  "subscriptionId": "sub_3c9a1f",
  "status": "PENDING_PAYER",        // при синхронной регистрации в ОПКЦ; CREATED — если ответа ОПКЦ ещё нет
  "consentUrl": "https://…",        // форма согласия/деплинк плательщика — возвращается ТОЛЬКО здесь, инициатору
  "amountLimit": 99900,
  "periodLimit": 299900,
  "period": "MONTHLY",
  "expiresAt": "2027-08-15T00:00:00.000Z",
  "merchantConsentId": "sub-order-777"
}
```

Правила: `Idempotency-Key` обязателен; лимит обязателен (согласие без лимита не создаётся); согласие активируется только после авторизации плательщиком и подтверждения ОПКЦ (вебхук `subscription.activated`); до `ACTIVE` списания запрещены. `consentUrl` возвращается только в ответе на создание и не выдаётся в `GET` (защита от IDOR). Точный состав полей и лимитов — по документации НСПК **[ТРЕБУЕТ ПРОВЕРКИ]**.

### 3.7 Статус подписки

`GET /v1/subscriptions/{subscriptionId}` → `200 { subscriptionId, status, amountLimit, periodLimit, period, expiresAt, activatedAt, revokedAt, merchantConsentId }` (без `consentUrl`). Владелец проверяется: `consent.tspId` = аутентифицированный ТСП, иначе `403 CONSENT_FORBIDDEN`. Enum `status`: `CREATED | PENDING_PAYER | ACTIVE | SUSPENDED | REJECTED | REVOKED | EXPIRED`.

### 3.8 Отзыв подписки (со стороны ТСП/банка)

`POST /v1/subscriptions/{subscriptionId}/revoke`

Запрос: `{ "reason": "Отзыв мерчантом" }`. Ответ `200 { subscriptionId, status: "REVOKED", revokedAt }`. **Семантика fail-closed:** отзыв фиксируется локально (техническое подсостояние `REVOKE_PENDING`, наружу — `REVOKED`), новые списания запрещаются немедленно, включая отмену ещё не отправленных debit-outbox строк; подтверждение ОПКЦ — асинхронное. Если ОПКЦ отклоняет отзыв (протокол **[ТРЕБУЕТ ПРОВЕРКИ]**) — инцидент по runbook, без автоматического возврата в `ACTIVE`. Идемпотентно (`Idempotency-Key`): повтор → тот же результат. Отзыв со стороны плательщика приходит по протоколу ОПКЦ и отражается статусом `REVOKED`; вебхук `subscription.revoked`.

### 3.9 Инициация списания по подписке

`POST /v1/subscriptions/{subscriptionId}/debits`

Запрос:

```json
{
  "amount": 49900,                  // копейки; в пределах лимитов согласия
  "paymentPurpose": "Подписка за сентябрь 2026",
  "merchantOrderId": "order-2026-09" // рекомендуется: бизнес-ключ дедупликации (tspId, consentId, merchantOrderId)
}
```

Ответ `201` — ресурс **платежа** (та же схема, что §3.3), что позволяет без изменений использовать статус платежа (§3.3) и возвраты (§3.4):

```json
{
  "paymentId": "pay_5f7a2b",
  "origin": "subscription",
  "consentId": "sub_3c9a1f",
  "status": "CREATED",              // затем PAID → CREDITED → COMPLETED либо FAILED
  "amount": 49900,
  "merchantOrderId": "order-2026-09"
}
```

Правила: `Idempotency-Key` обязателен (повтор → тот же `paymentId`, второго списания нет); дополнительно действует бизнес-ключ `(tspId, consentId, merchantOrderId)` — повтор намерения с новым ключом идемпотентности не создаёт второе списание; списание допустимо только при согласии `ACTIVE`, у владельца согласия (= аутентифицированный ТСП), в пределах лимита и при положительном решении антифрод/AML — иначе `403 CONSENT_FORBIDDEN` / `422 SUBSCRIPTION_NOT_ACTIVE` / `422 CONSENT_LIMIT_EXCEEDED` без обращения к НСПК; зачисление — только после подтверждения НСПК (`PAID`), AD-005. Событие результата — `payment.completed`/`payment.failed` с корреляцией по `paymentId` (не по `qrId`).

### 3.10 Список списаний по подписке (опционально)

`GET /v1/subscriptions/{subscriptionId}/debits?from&to&cursor` → постраничный список платежей (`paymentId`, `amount`, `status`, `createdAt`). Назначение — сверка на стороне ТСП; необходимость финализируется на A1 (см. §7, п.6).

## 4. Ошибки (RFC 9457, Problem Details)

```json
{
  "type": "https://api.bank.ru/sbp/errors/amount-exceeds-paid",
  "title": "Сумма возврата превышает оплаченную",
  "status": 422,
  "detail": "Доступная к возврату сумма: 149990",
  "code": "AMOUNT_EXCEEDS_PAID",
  "traceId": "…",
  "idempotencyKey": "…"
}
```

Канонические коды: `INVALID_REQUEST` (400), `UNAUTHORIZED` (401), `TSP_NOT_ACTIVE` (403), `NOT_FOUND` (404), `IDEMPOTENCY_CONFLICT` (409), `PAYMENT_NOT_REFUNDABLE` (422), `AMOUNT_EXCEEDS_PAID` (422), `RATE_LIMITED` (429), `INTERNAL` (500). Идемпотентный повтор успешного запроса возвращает ресурс со статусом 200, а не ошибку.

Коды, добавленные в v0.2 (аддитивно, для подписок): `SUBSCRIPTION_NOT_FOUND` (404), `CONSENT_FORBIDDEN` (403) — согласие принадлежит другому ТСП, `SUBSCRIPTION_NOT_ACTIVE` (422) — согласие не в `ACTIVE` (отозвано, истекло, приостановлено, не активировано), `CONSENT_LIMIT_EXCEEDED` (422) — превышен лимит операции или периода. Смысл кодов — только для подписок; существующие коды не меняются.

## 5. Вебхуки (нотификации ТСП)

Шлюз доставляет события на `webhookUrl` ТСП (ADR-004: at-least-once, ретраи, DLQ).

Заголовки: `X-SBP-Event-Id` (uuid события — для дедупликации у ТСП), `X-SBP-Signature` (HMAC-SHA256 тела, ключ — `webhookSecret`), `Content-Type: application/json`.

События:
- `payment.completed` — платёж зачислен (`status: COMPLETED`)
- `payment.failed` — платёж отклонён/ошибка
- `payment.expired` — истёк TTL
- `refund.completed` / `refund.failed`

События подписок (v0.2, аддитивно):
- `subscription.pending` — согласие зарегистрировано в ОПКЦ, плательщику предъявлена форма (используется, когда регистрация завершилась асинхронно)
- `subscription.activated` — согласие активировано плательщиком (списания разрешены)
- `subscription.rejected` — плательщик отказал или ОПКЦ отклонил согласие
- `subscription.suspended` — списания заморожены (расхождение сверки, сигнал AML/антифрод, административное удержание)
- `subscription.revoked` — согласие отозвано (плательщиком, банком плательщика или ТСП); новые списания запрещены
- `subscription.expired` — истёк срок действия согласия

Результат списания доставляется существующими событиями `payment.completed` / `payment.failed` (списание — это платёж с `origin=subscription`); отдельные события для списаний не вводятся.

Тело (`payment.completed`):
```json
{
  "eventId": "evt_…",
  "type": "payment.completed",
  "paymentId": "pay_8d1e4f5a",
  "status": "COMPLETED",
  "amount": 149990,
  "timestamp": "2026-08-15T17:32:00.000Z"
}
```

Тело (`subscription.activated`):
```json
{
  "eventId": "evt_…",
  "type": "subscription.activated",
  "subscriptionId": "sub_3c9a1f",
  "tspId": "tsp_9f3c2a1b",
  "status": "ACTIVE",
  "timestamp": "2026-09-29T10:00:00.000Z"
}
```

Доставка: ответ ТСП `2xx` = успех; иначе ретрай (экспоненциальная задержка + джиттер), после исчерпания — DLQ. ТСП обязан отвечать идемпотентно по `eventId`. ТСП, не использующий подписки, события `subscription.*` не получает; при получении неизвестного типа ТСП обязан его игнорировать (обратная совместимость, §6).

## 6. Версионирование и совместимость

- Путь `/v1`; изменения, ломающие контракт, — только в `/v2` с периодом поддержки обеих версий ≥ 6 мес.
- Добавление опциональных полей — обратно совместимо, не требует новой версии.
- Deprecation: заголовок `Deprecation` + `Sunset` в ответах старой версии.
- Дельта 0.1 → 0.2 (подписки): только аддитивные изменения (новые пути, схемы, опциональные поля, коды ошибок, типы вебхуков); enum `status` платежа и существующие поля не изменяются — новая версия пути не требуется. Детали — §8.

## 7. Открытые вопросы (для A1)

1. Необходимость отдельного метода «отмена QR до оплаты» (`POST /v1/payments/{paymentId}/cancel`) — roadmap, ждёт подтверждения от бизнеса.
2. Лимиты сумм и TTL — по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ].
3. Модель подписи запросов ТСП (mTLS + подпись тела) — финализирует ИБ на A4.
4. Формат `qrImage` (PNG base64) и необходимость — на усмотрение продукта.
5. Подписки: точные режимы/лимиты согласия, сроки предъявления и отзыва, состав полей — по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ].
6. Подписки: нужен ли `GET /v1/subscriptions/{id}/debits` (§3.10) или достаточно существующего статуса/вебхуков.
7. Подписки: достаточно ли неявного `origin` (по умолчанию `qr`) или требуется явное требование в запросе; как ТСП узнаёт о поддержке подписок (онбординг/feature-флаг).
8. Подписки: политика уведомления плательщика перед списанием (за сколько дней, каким каналом) — бизнес/юрист, влияет на состав событий.

## 8. Совместимость v0.1 → v0.2 (дельта подписок)

Проверка «ничего не сломано» для существующих потребителей контракта v0.1:

| Изменение | Тип | Влияние на потребителя v0.1 |
|---|---|---|
| Новые пути `/v1/subscriptions*` | аддитивно | нет (потребитель их не вызывает) |
| Поля `origin`, `consentId` в ответе платежа | опционально | нет (неизвестные поля игнорируются; при отсутствии `origin` трактуется как `qr`) |
