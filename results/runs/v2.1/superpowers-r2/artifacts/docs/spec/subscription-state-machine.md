# Статусная модель мандата и рекуррентного списания — спецификация переходов

- Status: Draft (для ревью на гейтах A3/A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, ADR-002, ADR-005, AD-002, AD-003, AD-005, AD-009, AD-010, AD-011

Расширяет `docs/spec/state-machine.md` (статусная машина платежа) без изменения её существующих состояний. Списание — платёж типа `RECURRING`; мандат — отдельный агрегат со своей машиной. Каждый переход — атомарная транзакция «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003).

## 1. Состояния мандата

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_CONSENT` | Мандат зарегистрирован, ожидается согласие плательщика в банке плательщика | да |
| `ACTIVE` | Согласие получено; списания в рамках лимитов и срока разрешены | да |
| `REJECTED` | Плательщик отказал или ОПКЦ отклонил оформление | да |
| `REVOKED` | Согласие отозвано плательщиком | да |
| `EXPIRED` | Истёк срок действия (`validUntil`) | да |
| `SUSPENDED` | Приостановлен (антифрод/регулятор/операционное решение); списания запрещены, отзыв возможен | да |

Терминальные: `REJECTED`, `REVOKED`, `EXPIRED`. `SUSPENDED` — обратимое (возврат в `ACTIVE` по решению, с аудитом).

## 2. Переходы мандата

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `PENDING_CONSENT` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен, лимиты валидны | запись мандата + outbox «регистрация в ОПКЦ», аудит |
| M2 | `PENDING_CONSENT` | `ACTIVE` | нотификация `mandate.activated` (или подтверждение сверкой) | `mandateRef` получен | аудит факта согласия, outbox-нотификация ТСП |
| M3 | `PENDING_CONSENT` | `REJECTED` | нотификация `mandate.rejected` (отказ плательщика/ОПКЦ) | — | `reasonCode`, outbox, вебхук |
| M4 | `PENDING_CONSENT` | `EXPIRED` | таймер: согласие не получено в срок | `mandateRef` не активирован | закрытие в ОПКЦ, outbox, вебхук |
| M5 | `ACTIVE` | `REVOKED` | нотификация `mandate.revoked` (или `POST /revoke` по инициативе ТСП) | — | аудит, outbox, вебхук; **новые списания запрещены** (AD-011) |
| M6 | `ACTIVE` | `EXPIRED` | наступил `validUntil` / нотификация `mandate.expired` | — | аудит, outbox, вебхук |
| M7 | `ACTIVE` | `SUSPENDED` | решение антифрод/регулятора/оператора | 4-eyes для ручного действия | аудит, outbox, вебхук; новые списания запрещены |
| M8 | `SUSPENDED` | `ACTIVE` | снятие приостановки | 4-eyes | аудит, outbox |

## 3. Состояния списания (= платёж типа `RECURRING`)

Списание использует состояния платежа и добавляет `SENT`:

`CREATED → SENT → PAID → CREDITED → COMPLETED`, терминальные `FAILED`, `EXPIRED`.

- `CREATED` — списание зарегистрировано в шлюзе, проверки пройдены, запрос в ОПКЦ не подтверждён.
- `SENT` — списание инициировано в ОПКЦ (аналог `QR_ISSUED` для QR-ветви).
- `PAID` — подтверждённый НСПК статус списания; **только отсюда** разрешено зачисление (AD-005/AD-010).
- `CREDITED` / `COMPLETED` — зачислено в АБС / доведено до ТСП.
- `FAILED` / `EXPIRED` — отклонено (нет средств, лимит, мандат неактивен, отказ банка плательщика) / не состоялось по TTL.

Технические подсостояния (`ABS_PENDING`, `NOTIFY_PENDING`) — как в базовой машине.

## 4. Переходы списания

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `CREATED` | `POST /v1/mandates/{id}/charges` (новый `chargeId`) | мандат `ACTIVE`; срок валиден; `amount ≤ maxAmountPerCharge`; сумма за период ≤ `maxAmountPerPeriod` | запись списания + outbox «инициация в ОПКЦ», аудит |
| C2 | `CREATED` | `SENT` | ответ адаптера: списание принято ОПКЦ | `ACCEPTED` | сохранение ссылки ОПКЦ, outbox |
| C3 | `CREATED` | `FAILED` | отказ инициации (не транзиентный; исчерпаны ретраи/DLQ) | — | `reasonCode`, outbox, вебхук `charge.failed` |
| C4 | `SENT` | `PAID` | нотификация `charge.paid` (или подтверждение сверкой) | сумма/получатель/мандат совпадают | outbox «зачисление в АБС» |
| C5 | `SENT` | `FAILED` | нотификация `charge.rejected` | — | `reasonCode`, outbox, вебхук `charge.failed` |
| C6 | `SENT` | `EXPIRED` | TTL списания истёк | `PAID` не наступил | закрытие в ОПКЦ (по протоколу), outbox, вебхук |
| C7 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`), идемпотентно по `paymentId` | — | сохранение `absDocId`, outbox «доставка ТСП» |
| C8 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен/поставлен в очередь | — | outbox, аудит; вебхук `charge.completed` |
| C9 | `COMPLETED` | `REFUNDED` | сага возврата завершена | полный возврат | outbox, вебхук `refund.completed` |

## 5. Запрещённые переходы (инварианты)

- **Списание невозможно, если мандат не в `ACTIVE`** (AD-009/AD-011): из `PENDING_CONSENT`, `REVOKED`, `EXPIRED`, `REJECTED`, `SUSPENDED` — недостижимо; проверяется fitness-тестом.
- **Зачисление невозможно из любого состояния, кроме `PAID`** (AD-005/AD-010): автосписание не ослабляет правило.
- `FAILED`/`EXPIRED` — терминальные для списания; `REJECTED`/`REVOKED`/`EXPIRED` — терминальные для мандата (кроме `SUSPENDED ↔ ACTIVE`).
- Сумма и получатель списания иммутабельны после `CREATED`; лимиты мандата иммутабельны после `ACTIVE` (изменение — новый мандат).
- Отзыв мандата не «откатывает» уже подтверждённые (`PAID`+) списания; корректировки — только возвратом (сага).

## 6. Гонка «отзыв мандата против инициированного списания»

- Если списание уже в `SENT` на момент `mandate.revoked`: шлюз **не инициирует новое** списание; исход уже отправленного определяет банк плательщика/ОПКЦ.
- Если приходит `charge.paid` после отзыва — списание доводится до `CREDITED/COMPLETED` (деньги плательщика уже списаны; не оставлять их «зависшими»), с аудитом и, при необходимости, предложением возврата ТСП.
- Если приходит `charge.rejected` — списание в `FAILED`.
- Двойного движения средств быть не может: зачисление только из `PAID`, идемпотентность по `chargeId`.

## 7. Идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| API ТСП `POST /v1/mandates` | `Idempotency-Key` | тот же `mandateId`, состояние не меняется |
| API ТСП `POST /v1/mandates/{id}/charges` | `Idempotency-Key` (+ `periodKey` при шедулере) | тот же `chargeId`, второго списания нет |
| API ТСП `POST /v1/mandates/{id}/revoke` | `Idempotency-Key` | идемпотентно: мандат уже `REVOKED` |
| Нотификация `mandate.*`/`charge.*` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт |
| Подтверждение АБС | `paymentId` (= `chargeId`) | повтор не создаёт вторую проводку |
| Сверка мандатов/списаний | `mandateRef` / ссылка ОПКЦ | повторный дозапрос не меняет завершённые состояния |

## 8. Сверка и восстановление

- Открытые мандаты (`PENDING_CONSENT`, `ACTIVE`, `SUSPENDED`) и открытые списания (`CREATED`, `SENT`, `PAID`, `ABS_PENDING`) — кандидаты сверки.
- Сверка статусов мандатов с НСПК — ежечасная (по регламенту `[ТРЕБУЕТ ПРОВЕРКИ]`); расхождение «у НСПК отозван, у нас активен» → немедленная блокировка списаний, эскалация.
- «У НСПК списание `PAID`, у нас нет» → дозапрос статуса → C4.
- Списание в `PAID` с недоступной АБС — остаётся `PAID`, видно в отчёте незавершённых, зачисление гарантируется сверкой.

## 9. Согласованность с API ТСП

Наружу выставляются статусы мандата (`PENDING_CONSENT`, `ACTIVE`, `REVOKED`, `EXPIRED`, `REJECTED`, `SUSPENDED`) и списания (`CREATED`, `SENT`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`); технические подсостояния (`ABS_PENDING`, `NOTIFY_PENDING`) наружу не выставляются. Существующие статусы платежа (`QR_ISSUED` и др.) не меняются — обратная совместимость (см. `docs/contracts/tsp-api.md` §8).
