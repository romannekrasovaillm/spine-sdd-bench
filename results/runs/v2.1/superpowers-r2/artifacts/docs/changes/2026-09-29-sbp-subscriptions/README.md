# Пакет архитектурного изменения: СБП-подписки (рекуррентные C2B-списания)

- Status: **Draft — выносится на архитектурное решение (гейт A3)**. До ратификации ADR-008/ADR-009 транспортный слой подписок не реализуется.
- Date: 2026-09-29
- База: принятое решение «Платёжный шлюз СБП (C2B-приём)» (git tag `accepted`)
- Owner: solution-architect (платёжный контур)
- Related: `ARCHITECTURE-SPINE.md` (AD-001…AD-008), `docs/adr/ADR-008`, `docs/adr/ADR-009`, `docs/spec/subscription-state-machine.md`, `docs/solutioning.md`

Настоящий пакет — **изменение поверх принятого решения**, а не новое решение. Он оформлен по принятому в репозитории способу: решения добавляются как ADR в статусе `Proposed`, инварианты — блоками `Proposed` в spine, контракты и NFR расширяются **аддитивно** (без потери совместимости), изменение статуса `Adopted` возможно только человеческим решением A3.

## 1. Что и зачем (бизнес-задача)

Ключевые ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** (подписки СБП). Сегодня каждый платёж требует QR/ссылки и действия клиента при каждой оплате, что неприемлемо для подписочных и регулярных платежей (продление подписки, абонплата, квартплата).

Целевой результат: ТСП один раз получает согласие плательщика (мандат), далее инициирует списания в его рамках **без повторного действия клиента**; каждое списание проходит тот же платёжный контур банка (зачисление на счёт ТСП в АБС, возвраты, сверка, аудит).

## 2. Оценка значимости и маршрут

Оценка по пяти осям методики решения (максимум 3 балла на ось, сумма 15 — та же шкала, по которой исходное решение получило 11/15 и маршрут Critical; разложение исходных 11 баллов — реконструкция и требует подтверждения владельцем метода).

| Ось | Балл | Обоснование |
|---|---|---|
| Новизна модели и протокола | 3 | Новый агрегат «мандат», новый протокол НСПК (подписки/периодические списания), новое состояние списания |
| Финансовое влияние | 3 | Списание без действия клиента; ошибка = незаконное или двойное списание, репутационный/регуляторный риск |
| Регуляторика / КИИ / ПДн | 3 | Юридически значимое согласие плательщика (152-ФЗ), НПС/161-ФЗ, аудит, минимизация ПДн |
| Интеграционная поверхность | 3 | НСПК (новый протокол) + АБС-зачисление + API ТСП + (возможно) планировщик шлюза |
| Обратимость | 2 | До боевых согласий — reversible; после массовых мандатов откат costly (нужно закрывать согласия у плательщиков) |
| **Итого** | **14/15** | |

**Маршрут: Critical.** Следствие для процесса:
- обязательны ADR на каждое решение и **человеческое решение A3** до реализации транспортного слоя подписок (по образцу ADR-007);
- полный цикл гейтов A0–A5 над изменением;
- финальный комплект — spec (статусная модель), аддитивный контракт, измеримые NFR, критерии приёмки и план отката, handoff исполнителям.

**Почему требуется глубокое проектирование, а не «доработка под QR»:** меняется природа триггера платежа (не клиент, а ТСП/расписание по ранее выданному согласию), появляется юридически значимый артефакт согласия и лимиты, добавляется новый протокол НСПК — то есть затрагиваются одновременно модель данных, статусная машина, идемпотентность, интеграции и комплаенс.

## 3. Влияние на принятую архитектуру

| Инвариант | Затронут | Что происходит |
|---|---|---|
| AD-001 Изоляция платёжного контура | Нет | Взаимодействие с НСПК/АБС остаётся только через адаптеры шлюза |
| AD-002 Единый источник истины (статусная машина) | Да, расширение | Появляется агрегат «мандат» со своим автоматом; списание — платёж в существующей машине; переходы остаются атомарными (статус + outbox + аудит) |
| AD-003 Идемпотентность финансовых операций | Да, расширение | Новые ключи: `mandateId`, `chargeId`, `periodKey`; нотификации по `eventId`; повторные триггеры не меняют состояние |
| AD-004 Единственный адаптер ОПКЦ | Да, расширение контракта | Протокол подписок знает только адаптер ОПКЦ; внутренний контракт расширяется аддитивно |
| AD-005 Зачисление только из подтверждённого статуса | Да, подтверждение действия | Инвариант распространяется на **каждое** списание: автосписание ≠ авто-зачисление; зачисление только из `PAID` |
| AD-006 Trust-зоны и сегментация | Нет | Новых зон доверия нет; мандаты/списания обслуживаются в существующих контурах |
| AD-007 НПС/КИИ/ПДн | Да, расширение | Согласие — новый юридически значимый ПДн-артефакт: неизменяемый аудит, минимизация, правовое основание |
| AD-008 Стратегия реализации (гибрид) `[ADOPTED]` | Нет | Ядро по-прежнему контрактно-независимо от транспорта; вендорский транспорт обязан поддержать протокол подписок |

**Что меняется:** модель данных (мандат), статусная машина (состояние `SENT` и тип платежа `RECURRING`), контракт ТСП (аддитивно), контракт адаптера ОПКЦ (аддитивно), NFR (новые цели), отчётность/сверка (мандаты), RFP (критерии по подпискам).

**Что не меняется (запрещено менять в рамках изменения):** существующие состояния и семантика платежа `CREATED/QR_ISSUED/PAID/CREDITED/COMPLETED/FAILED/EXPIRED/REFUNDED`; контрактные поля, используемые текущими потребителями (обратная совместимость); принцип «зачисление только из `PAID`»; единственный адаптер ОПКЦ; границы trust-зон; номер версии существующих методов (ломающие изменения — только через новую версию).

**Вне-scope изменения:** C2C-переводы, выплаты B2C/B2B, диспуты, мультивалютность, изменение платёжной модели существующих C2B-платежей.

## 5. Решения, выносимые на A3 (человеческий архитектор)

1. **Модель инициации списаний** (ADR-009): ТСП-инициируемая / планировщик шлюза / гибрид.
2. **Источник истины по мандату**: ОПКЦ (авторитет) + проекция в шлюзе vs полное зеркалирование и объём хранимых ПДн плательщика.
3. **Правовое основание и форма согласия** (152-ФЗ/161-ФЗ), хранение доказательства согласия, требования к аудиту.
4. **Объём первой волны**: все три вертикали или пилот (например, кинотеатры), нужны ли повторные попытки списания (dunning).
5. **Форма закупки**: включает ли действующий контракт/ RFP с вендором транспорта протокол подписок или это отдельная процедура (ограничения ADR-007/AD-008).
6. **Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`**: точный протокол НСПК по подпискам (поля мандата, лимиты, семантика отзыва, жизненный цикл списания, тайминги) — из документации НСПК по договору.

## 6. Гейты и следующий шаг

- **A3 (человеческое решение)**: ратификация ADR-008 и выбор по ADR-009; фиксация ответов по п.5. **До этого** — только проектирование и мок-реализация.
- **A1 (Spec)**: после A3 — финализация статусной модели, контрактов v0.2 и NFR подписок.
- **A2 (Plan)**: инкремент walking skeleton на моках (`handoff/TASK.md`).
- **A4 (conformance)**: fitness-тесты инвариантов (нет списаний без мандата, нет двойных зачислений, зачисление только из `PAID`), нагрузочные тесты, ИБ-аудит.
- **A5 (post-deploy)**: сверка мандатов/списаний, SLO-отчёт, проверка отсутствия дрейфа.

**Примечание о handoff-пакете.** `.arch-handoff/` в корне — производный (генерируемый методикой) epic-context принятого решения (этап walking skeleton) и **вручную не редактируется**: после ратификации A3 он перегенерируется с учётом новых ADR-008/ADR-009 и контрактов v0.2. Handoff инкремента подписок для исполнителей — `docs/changes/2026-09-29-sbp-subscriptions/handoff/TASK.md`.
