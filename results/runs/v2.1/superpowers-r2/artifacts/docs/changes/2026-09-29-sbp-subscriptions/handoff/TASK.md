# Задача для кодового харнесса (инкремент: СБП-подписки)

Расширить walking skeleton платёжного шлюза СБП (C2B-приём) рекуррентными списаниями по согласию плательщика поверх принятого решения (`docs/solutioning.md`, ADR-001..007) и решений изменения (`docs/changes/2026-09-29-sbp-subscriptions/`, ADR-008, ADR-009): (1) агрегат **мандат** — регистрация согласия, статусная модель `PENDING_CONSENT→ACTIVE→(REVOKED|EXPIRED|REJECTED|SUSPENDED)`, аудит факта согласия; (2) **списание как платёж** типа `RECURRING` с состоянием `SENT`, переиспользующее существующую статусную машину, outbox и аудит (не создавать вторую платёжную машину); (3) мок-расширение адаптера ОПКЦ (имитация НСПК: `registerMandate`, `getMandateStatus`, `revokeMandate`, `createCharge`, `getChargeStatus`; нотификации `mandate.activated/rejected/revoked/expired`, `charge.paid/charge.rejected`) — ядро контрактно-независимо, реальный протокол НСПК НЕ реализуется (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`); (4) идемпотентные зачисления по списаниям через существующий мок-адаптер АБС (ключ `paymentId=chargeId`); (5) нотификатор вебхуков ТСП по событиям мандата/списания (ретраи, DLQ). Spine-инварианты обязательны: зачисление только из `PAID` (AD-005/AD-010), атомарные переходы «статус+outbox+аудит» (AD-002), идемпотентность повторных доставок (AD-003), списание без активного мандата невозможно (AD-009). Критерии приёмки — `docs/changes/2026-09-29-sbp-subscriptions/acceptance-and-rollback.md` и NFR §7 `docs/nfr.md` (выполнимыми на моках). Технологический стек — по выбору команды с обоснованием в ADR; приоритет — доказать архитектуру сквозным сценарием, а не полнотой продукта.

## Обязательные инварианты (дословно из spine)

- AD-002: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции».
- AD-003: «Повторная доставка любого сообщения не изменяет уже завершённое состояние».
- AD-005: «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус)».
- AD-008 `[ADOPTED]`: ядро контрактно-независимо от транспорта; единственная зависимость — внутренний контракт адаптера ОПКЦ.
- AD-009 (Proposed): списание без активного мандата запрещено; мандат — единственное правовое основание списания.
- AD-010 (Proposed): каждое рекуррентное списание — отдельный платёж с собственной идемпотентностью; автосписание не отменяет требования зачисления только из `PAID`.
- AD-011 (Proposed): отзыв/истечение мандата немедленно блокирует новые списания.

## Запрещено менять в рамках инкремента

- Существующие состояния и семантику платежа; контрактные поля, используемые текущими потребителями (обратная совместимость).
- Единственный адаптер ОПКЦ (AD-004) и границы trust-зон (AD-006).
- Принцип «зачисление только из `PAID`» и правило «одна сумма, один плательщик, один ТСП».

Конфликт с spine или принятыми ADR обязан **останавливать работу и эскалироваться**, а не разрешаться «на месте».

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine).

Архитектурный контекст — `docs/changes/2026-09-29-sbp-subscriptions/README.md` и `solutioning.md`, инварианты — `ARCHITECTURE-SPINE.md`, критерии приёмки — `acceptance-and-rollback.md`, NFR — `docs/nfr.md` §7.
