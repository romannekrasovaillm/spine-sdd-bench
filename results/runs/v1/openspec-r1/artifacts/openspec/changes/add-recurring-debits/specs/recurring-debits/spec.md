# Spec Delta

## Purpose

Обеспечивает рекуррентные C2B-списания (дебиты) по активному согласию плательщика: инициацию без QR и действия клиента, зачисление в пользу ТСП, возвраты и сверку, с гарантией «дебетование только при активном согласии».

## ADDED Requirements

### Requirement: Инициация дебита по согласию

Система SHALL позволять ТСП инициировать дебит через `POST /v1/payments` с `paymentType: RECURRING`, `consentId` и обязательным `Idempotency-Key`, без полей QR. Дебит переиспользует статусную машину платежа, минуя состояние `QR_ISSUED`.

#### Scenario: Инициация дебита по активному согласию

- **WHEN** ТСП отправляет `POST /v1/payments` с `paymentType=RECURRING` и `consentId` активного согласия
- **THEN** система создаёт дебит в статусе `CREATED`, возвращает `paymentId` и `201`

#### Scenario: Повторная инициация дебита

- **WHEN** ТСП повторяет запрос с тем же `Idempotency-Key`
- **THEN** система возвращает тот же `paymentId`, списание не дублируется

### Requirement: Дебетование только по активному согласию

Система SHALL отклонять инициацию дебита, если согласие не в статусе `ACTIVE`, истекло, отозвано или сумма/период превышают пределы согласия. Данный переход SHALL быть недостижим при любом другом состоянии согласия.

#### Scenario: Дебит по отозванному согласию

- **WHEN** ТСП инициирует дебит по согласию в статусе `REVOKED`
- **THEN** система возвращает ошибку `CONSENT_NOT_ACTIVE` (403/422), дебит не создаётся

#### Scenario: Дебит сверх лимита согласия

- **WHEN** сумма дебита превышает `maxAmount` или частоту, заданную в согласии
- **THEN** система отклоняет дебит с ошибкой `CONSENT_LIMIT_EXCEEDED`

#### Scenario: Дебит по истёкшему согласию

- **WHEN** ТСП инициирует дебит по согласию в статусе `EXPIRED`
- **THEN** система отклоняет дебит, зачисление невозможно

### Requirement: Зачисление только из подтверждённого статуса дебита

Зачисление в АБС по дебиту SHALL выполняться только из состояния `PAID` (подтверждённый НСПК статус), аналогично C2B-QR. Переход `PAID → CREDITED → COMPLETED` SHALL быть атомарным (статус + outbox + аудит).

#### Scenario: Подтверждение дебита НСПК

- **WHEN** адаптер ОПКЦ доставляет событие `payment.paid` по дебиту с корректными суммой и реквизитами
- **THEN** дебит переходит в `PAID`, инициируется зачисление в АБС

#### Scenario: Расхождение суммы в подтверждении

- **WHEN** сумма в событии `payment.paid` не совпадает с суммой дебита
- **THEN** зачисление запрещено, дебит переводится в `FAILED`, генерируется алерт

### Requirement: Возврат дебита

Система SHALL поддерживать полный и частичный возврат дебита через существующую сагу возвратов (`POST /v1/payments/{paymentId}/refunds`), применимую только после зачисления (`CREDITED`/`COMPLETED`).

#### Scenario: Полный возврат дебита

- **WHEN** ТСП инициирует полный возврат зачисленного дебита
- **THEN** возврат проходит сагу (списание АБС + подтверждение НСПК), дебит переходит в `REFUNDED`

#### Scenario: Возврат незачисленного дебита

- **WHEN** ТСП инициирует возврат дебита не в `CREDITED`/`COMPLETED`
- **THEN** система возвращает `PAYMENT_NOT_REFUNDABLE`

### Requirement: Сверка рекуррентных дебитов

Система SHALL включать рекуррентные дебиты и согласия в сверку с НСПК (ежечасную) и с АБС (суточную), с нулевыми расхождениями по завершённым операциям.

#### Scenario: Дебит подтверждён у НСПК, но не у шлюза

- **WHEN** сверка находит у НСПК `PAID` по дебиту, которого нет у шлюза
- **THEN** система дозапрашивает статус и обрабатывает как нотификацию, зачисление гарантируется

### Requirement: Нотификация плательщика о списании

Система SHALL обеспечивать уведомление плательщика о каждом рекуррентном списании в соответствии с требованиями регулятора и правилами НСПК (канал и тайминг — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`).

#### Scenario: Уведомление о списании

- **WHEN** дебит переходит в `COMPLETED`
- **THEN** в outbox формируется событие уведомления плательщика о списании
