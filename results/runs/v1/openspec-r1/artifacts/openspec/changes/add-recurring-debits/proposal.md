# Proposal

## Why

ТСП с повторяющимися платежами (онлайн-кинотеатры, ЖКХ, связь) требуют рекуррентных C2B-списаний по заранее оформленному согласию плательщика — подписок СБП. Сейчас каждый платёж требует QR и действия клиента, что делает подписочную модель нереализуемой. Это выводит в scope ранее отложенную возможность «автоплатежи» (см. `docs/solutioning.md`, раздел Deferred).

Значимость изменения — **высокая, маршрут «глубокое проектирование»**: новая финансовая сущность (`Согласие`), новая финансовая операция (дебетование без QR), новые регуляторные обязательства (право плательщика на отзыв согласия, уведомления, лимиты), расширение контрактов API ТСП и адаптера ОПКЦ, расширение RFP вендора. Изменение требует нового ADR (списание только по активному согласию) и нового spine-инварианта — это не «малое изменение», а отдельная архитектурная развилка. Детальный анализ маршрута — в `design.md`.

## What Changes

- **Новая сущность «Согласие плательщика» (consent)** с собственным жизненным циклом и статусной машиной: создание → подтверждение плательщиком → `ACTIVE` → `REVOKED`/`EXPIRED`. Согласие хранится в той же БД шлюза (единый источник истины, AD-002) и пишется в outbox-транзакциях.
- **Новый тип операции — рекуррентное списание (debit)** по активному согласию: дебетование средств плательщика в пользу ТСП **без QR и без действия плательщика в каждом платеже**. Реализуется как `Payment` с `paymentType: RECURRING` и ссылкой `consentId` (переиспользование статусной машины, зачисления, возвратов-саги).
- **Расширение API ТСП** (`/v1/consents`, поля `paymentType`/`consentId` в платеже) — только аддитивно, без поломки существующих потребителей C2B-QR.
- **Расширение контракта адаптера ОПКЦ** (методы/события согласия и рекуррентного списания) и, соответственно, **RFP вендора** (вендор обязан поддерживать сервис рекуррентных списаний НСПК).
- **Новый spine-инвариант** «дебетование только по активному согласию» (аналог AD-005) — требует ратификации на архитектурном решении.
- **Новые NFR** (латентность активации согласия, эффективность отзыва, массовые волновые списания, нулевые дубли).

Ничего из существующего C2B-QR сценария не ломается: изменения аддитивны и изолированы фиче-флагом.

## Capabilities

### New Capabilities

- `consents`: жизненный цикл согласия плательщика — создание, подтверждение, активация, отзыв, истечение; идемпотентность; нотификации об изменении статуса согласия.
- `recurring-debits`: рекуррентные C2B-списания по активному согласию — инициация дебета, подтверждение зачисления, возвраты дебетов, сверка; гарантия «дебетование только при активном согласии».

## Impact

- **Код/компоненты**: ядро СБП-шлюза — статусная машина (новая машина согласия + ветка `paymentType=RECURRING` в машине платежа), API ТСП, сверка, нотификатор вебхуков; адаптер ОПКЦ (контракт) и адаптер АБС (без изменений — зачисление/списание как для C2B).
- **API**: `openapi/tsp-api.yaml` — новые ресурсы `/v1/consents` и поля `paymentType`/`consentId`; `docs/contracts/tsp-api.md` — новый раздел. **Без BREAKING** (аддитивно, поддержка `/v1` сохраняется).
- **Контракты**: `docs/contracts/opkc-adapter.md` — новые методы/события согласия и рекуррентного списания; `docs/rfp/vendor-rfp.md` — критерии поддержки рекуррентных списаний.
- **Спецификации**: `docs/spec/state-machine.md` — машина согласия + запрещённые переходы для дебетов.
- **Зависимости/внешние входы**: протокол НСПК по согласию и рекуррентным списаниям (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`), поддержка вендором ОПКЦ, регуляторные требования (161-ФЗ/НПС, 152-ФЗ, 115-ФЗ).
- **Инварианты spine**: затронуты AD-002 (расширение), AD-003 (расширение), AD-005 (аналог для дебетов), AD-007 (расширение compliance); добавляется новый инвариант «дебетование только по активному согласию». AD-001, AD-004, AD-006, AD-008 — без изменения принципа.
