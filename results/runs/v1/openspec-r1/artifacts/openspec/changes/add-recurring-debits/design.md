# Design

## Context

См. `proposal.md` — Why. Здесь — оценка значимости/маршрута, влияние на инварианты принятой архитектуры и технические решения.

### Маршрут и значимость (оценка)

- **Значимость: высокая (≈ 10/15)** — не новый initiative, а глубокая фича поверх принятого Critical-решения (11/15). Новый финансовый объект (`Согласие`), новая финансовая операция (дебетование без QR), регуляторные обязательства (право отзыва, уведомления, лимиты), расширение контрактов API ТСП и адаптера ОПКЦ, расширение RFP вендора.
- **Маршрут: полное проектирование под-домена** по той же схеме, что и родительский Solutioning (гейты A1–A5), но на уровне feature: новый ADR (списание только по активному согласию), spec-дельта, дельта контрактов, дельта NFR, дельта RFP. Требуется **человеческое архитектурное решение** до реализации (аналог A3): регуляторная модель рекуррентных списаний, подтверждение поддержки вендором, продуктовые лимиты. Причина «глубокого» маршрута: финансовое влияние ошибки (двойное списание / списание после отзыва согласия) и необратимость некоторых решений (формат согласия, канал подтверждения).

### Влияние на инварианты spine (AD-001…AD-008)

| Инвариант | Статус | Что меняется / не меняется |
|---|---|---|
| **AD-001** Изоляция платёжного контура | не затронут | Согласия и дебиты живут в том же контуре; обращения к АБС/ОПКЦ — только через адаптеры. |
| **AD-002** Единый источник истины — статусная машина | **расширен** | Добавляется вторая статусная машина `Согласие` в той же БД шлюза; переходы согласия и дебита — атомарные транзакции «статус + outbox + аудит». |
| **AD-003** Идемпотентность финансовых операций | **расширен** | Новые ключи: `consentId` (создание согласия), `paymentId` дебита, `eventId` для событий согласия/дебита. Правило «повтор не меняет завершённое состояние» распространяется на согласия. |
| **AD-004** Единственный адаптер ОПКЦ | не затронут в принципе | Контракт адаптера расширяется методами/событиями согласия и дебита; транспорт остаётся единственным. |
| **AD-005** Зачисление только из подтверждённого статуса | **получает аналог** | Для дебита зачисление в АБС — по-прежнему только из `PAID`. Добавляется **новый инвариант** (см. AD-009 ниже): дебетование — только по активному согласию. |
| **AD-006** Trust-зоны и сегментация | не затронут | Те же зоны; ключевой материал — в СКЗИ/HSM. |
| **AD-007** Соответствие НПС/КИИ/ПДн | **расширен** | ПДн согласия (плательщик, лимиты) — минимизация и шифрование; неизменяемый аудит жизненного цикла согласия; обязательства по уведомлению плательщика. |
| **AD-008** Стратегия реализации (гибрид) | не затронут в принципе | Ядро остаётся контрактно-независимым; вендорский адаптер обязан реализовать рекуррентный сервис НСПК → расширение RFP. |

**Что меняется**: появляется сущность `Согласие` и ветка `paymentType=RECURRING` в машине платежа (переход `CREATED → PAID` без `QR_ISSUED`); расширяются контракты и RFP. **Что не меняется**: родительский spine (по-прежнему C2B-приём; C2C/выплаты/диспуты — вне scope), trust-зоны, outbox-механизм, сверка, гибридная стратегия, C2B-QR сценарий.

## Goals / Non-Goals

**Goals:**
- Ввести `Согласие` как отдельную сущность с жизненным циклом и гарантией отзыва.
- Реализовать дебит как переиспользование машины платежа (`paymentType=RECURRING`), без дублирования зачисления/возвратов/сверки.
- Расширить API ТСП и контракт адаптера ОПКЦ аддитивно, без поломки существующих потребителей.
- Зафиксировать новый spine-инвариант «дебетование только по активному согласию».

**Non-Goals:**
- C2C-переводы, B2C/B2B-выплаты, диспуты — вне scope (не трогаются).
- Реализация реального протокола НСПК — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`, остаётся в вендорском адаптере.
- Собственный UI/канал подтверждения согласия плательщиком — канал диктует НСПК; шлюз канально-независим.

## Decisions

### D1. `Согласие` — отдельная сущность; дебит — `Payment` с `paymentType=RECURRING`

**Решение.** Вводим сущность `Согласие` (consent) с собственной статусной машиной `PENDING → ACTIVE → REVOKED|EXPIRED|FAILED`. Дебит реализуем как `Payment` с `paymentType: RECURRING` и ссылкой `consentId`, переиспользуя машину платежа, зачисление (AD-005), возврат-сагу (ADR-005) и сверку. Ветка `RECURRING` минует `QR_ISSUED`/`EXPIRED`.

Альтернативы:

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **Согласие отдельно + дебит как Payment (выбран)** | Минимальный новый код; переиспользование зачисления/возврата/сверки; единая модель денег | Смешение семантик QR и согласия в одном ресурсе (снимается дискриминатором `paymentType`) | принят |
| Отдельный домен «Дебит» (своя машина, таблицы, API) | Чистая изоляция | Дублирование зачисления/возврата/сверки/идемпотентности, рост стоимости | отклонён — дублирует AD-001/002/005 |
| Делегировать рекуррент целиком вендору/НСПК | Меньше работы | Нарушает AD-001/AD-002 (финлогика в шлюзе), vendor lock-in, сложный аудит | отклонён |
| Согласие как флаг на ТСП без per-payer согласия | Просто | Не соответствует регуляторному требованию (согласие персонально и отзывно) | отклонён |

**Последствия.** Положительные: переиспользование проверенной механики, аддитивность, заменяемость. Отрицательные: две машины состояний в одной БД, усложнение сверки (согласия + дебиты).

**Обратимость.** `reversible`: ветка `RECURRING` — аддитивный переход в существующей машине; сущность `Согласие` добавлена, не мигрирует существующие данные. Откат — отключить флаг `recurring.enabled`, C2B-QR не затронут.

### D2. Новый spine-инвариант (проект AD-009): «Дебетование только по активному согласию»

**Решение.** Ввести инвариант: списание средств плательщика в рекуррентном режиме SHALL выполняться только при согласии в `ACTIVE`, в пределах лимитов согласия (`maxAmount`, период), до `expiresAt`. Проверка в ядре (не доверяя адаптеру/НСПК). Fitness-тест: переход в `PAID`/зачисление недостижимы при `PENDING`/`REVOKED`/`EXPIRED` согласии.

Альтернативы: проверять согласие только в НСПК (отклонено — ядро теряет контроль, нарушает AD-002); не вводить инвариант, считать согласие «пожеланием» (отклонено — регуляторный риск).

**Обратимость.** Инвариант обратим до ратификации; после ратификации — costly (аналог AD-005).

### D3. Канал подтверждения согласия — канально-независимое ядро

**Решение.** Подтверждение плательщиком происходит в канале НСПК (push/QR-подтверждение в приложении банка плательщика) — ядро не реализует UI. Ядро получает результат только как событие адаптера `consent.activated`/`consent.rejected` и не зависит от конкретного канала.

Альтернативы: собственный канал подтверждения (отклонено — вне зоны банка-эквайера, канал диктует НСПК); синхронный опрос статуса согласия вместо событий (дополнение — сверка/опрос статуса страхует потерю события).

**Обратимость.** reversible — конкретный канал скрыт за адаптером.

### D4. Лимиты согласия — обязательны и проверяются ядром

**Решение.** Согласие SHALL содержать `maxAmount` (на одно списание), период/частоту (`period`), срок действия (`expiresAt`); ядро отклоняет дебит, нарушающий лимиты.

Альтернативы: лимиты только на стороне ТСП/НСПК (отклонено — контроль в ядре обязателен); без лимитов (отклонено — регуляторный риск).

**Обратимость.** reversible — структура лимитов аддитивна.

## Изменения контрактов (без поломки существующих потребителей)

Все изменения — **аддитивные** под `/v1`, без версии `/v2`. Существующие C2B-QR потребители не затрагиваются.

### API ТСП (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`)

Новые ресурсы:

```yaml
  /v1/consents:
    post:
      operationId: createConsent
      parameters:
        - {in: header, name: Idempotency-Key, required: true, schema: {type: string}}
      requestBody:
        required: true
        content:
          application/json:
            schema: {$ref: '#/components/schemas/ConsentRequest'}
      responses:
        '201': {description: Согласие создано, content: {application/json: {schema: {$ref: '#/components/schemas/Consent'}}}}
  /v1/consents/{consentId}:
    get:
      operationId: getConsent
      parameters:
        - {in: path, name: consentId, required: true, schema: {type: string}}
      responses:
        '200': {description: Статус согласия, content: {application/json: {schema: {$ref: '#/components/schemas/Consent'}}}}
  /v1/consents/{consentId}/revoke:
    post:
      operationId: revokeConsent
      parameters:
        - {in: path, name: consentId, required: true, schema: {type: string}}
        - {in: header, name: Idempotency-Key, required: true, schema: {type: string}}
      responses:
        '200': {description: Согласие отозвано, content: {application/json: {schema: {$ref: '#/components/schemas/Consent'}}}}
```

Новые схемы:

```yaml
    ConsentRequest:
      type: object
      required: [tspId, payerIdentifier, maxAmount, period, expiresAt, purpose]
      properties:
        tspId: {type: string}
        payerIdentifier: {type: string, description: Идентификатор плательщика по правилам НСПК [ТРЕБУЕТ ПРОВЕРКИ]}
        maxAmount: {type: integer, description: Максимум на одно списание, копейки}
        period: {type: string, enum: [DAY, WEEK, MONTH]}
        expiresAt: {type: string, format: date-time}
        purpose: {type: string}
        merchantConsentId: {type: string, description: Опц., сквозной id ТСП}
    Consent:
      type: object
      required: [consentId, status, maxAmount, period, expiresAt]
      properties:
        consentId: {type: string}
        status: {type: string, enum: [PENDING, ACTIVE, REVOKED, EXPIRED, FAILED]}
        maxAmount: {type: integer}
        period: {type: string, enum: [DAY, WEEK, MONTH]}
        expiresAt: {type: string, format: date-time}
        createdAt: {type: string, format: date-time}
        activatedAt: {type: string, format: date-time}
        revokedAt: {type: string, format: date-time}
```

Расширение `PaymentRequest` (обратно совместимо — новые поля опциональны):

```yaml
    PaymentRequest:
      type: object
      required: [amount, merchantOrderId]
      properties:
        amount: {type: integer, description: Сумма в копейках}
        merchantOrderId: {type: string}
        paymentType: {type: string, enum: [QR, RECURRING], default: QR}
        consentId: {type: string, description: Обязателен при paymentType=RECURRING}
        qrType: {type: string, description: Только при paymentType=QR}
        ttlSeconds: {type: integer}
        redirectUrl: {type: string}
```

Расширение `Payment` (добавляются `paymentType`, `consentId`):

```yaml
    Payment:
      type: object
      required: [paymentId, amount, status]
      properties:
        paymentId: {type: string}
        amount: {type: integer}
        status: {type: string, enum: [CREATED, QR_ISSUED, PAID, CREDITED, COMPLETED, FAILED, EXPIRED, REFUNDED]}
        paymentType: {type: string, enum: [QR, RECURRING], default: QR}
        consentId: {type: string}
```

Новые коды ошибок: `CONSENT_NOT_FOUND` (404), `CONSENT_NOT_ACTIVE` (403), `CONSENT_LIMIT_EXCEEDED` (422), `CONSENT_CONFLICT` (409).

Новые вебхуки: `consent.activated`, `consent.revoked`, `consent.expired`, `consent.failed`; для дебитов переиспользуются `payment.completed`/`payment.failed`/`refund.completed` с полем `paymentType`.

### Контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md`) и RFP

Новые синхронные методы (ядро → адаптер): `registerConsent` (reference=consentId, payerIdentifier, limits, purpose → ACCEPTED), `revokeConsent` (reference=consentId, reason → ACCEPTED), `createDebit` (reference=paymentId, consentRef=consentId, amount → ACCEPTED), `getConsentStatus` (consentRef → ACTIVE/REVOKED/EXPIRED/PENDING/UNKNOWN). События (адаптер → ядро): `consent.activated`, `consent.rejected`, `consent.revoked`, `consent.expired`, `debit.paid`, `debit.rejected` — все с `eventId`, at-least-once. Идемпотентность мутирующих вызовов по `reference` — **обязательное требование RFP** (G3), распространяется на `registerConsent`/`createDebit`.

RFP-критерии добавляются: поддержка сервиса рекуррентных списаний НСПК (согласие + дебит), нормализация статусов согласия, тестовый контур с POC-сценариями `consent.activated`/`consent.revoked`/`debit.paid`/повторы.

## NFR (измеримые, новые)

| Метрика | Цель | Метод проверки |
|---|---|---|
| Латентность создания согласия (`POST /v1/consents`) | p95 < 500 мс | Нагрузочный тест, APM |
| Латентность активации согласия (от события НСПК до `ACTIVE` + вебхук) | p95 < 5 с | Метрика лага |
| Латентность инициации дебита | p95 < 500 мс | Нагрузочный тест |
| Зачисление по дебиту от подтверждения НСПК | p95 < 60 с | Метрика процесса |
| **Эффективность отзыва**: дебит после `REVOKED` | 0 (отклоняется за ≤ 1 с) | Fitness-тест + интеграционный тест |
| Дубли списаний при ретраях | 0 | Тест на повторную доставку |
| Дубли согласий | 0 | Тест на повторное создание |
| Throughput рекуррентных дебитов | 200 TPS sustained, **волна 1000 TPS на 1 мин** (ЖКХ/связь — массовые списания) | Нагрузочный тест |
| Сверка согласий/дебитов с НСПК | ежечасная, расхождений 0 | Reconciliation-отчёт |
| Уведомление плательщика о списании | 100 % (канал/тайминг — `[ТРЕБУЕТ ПРОВЕРКИ]`) | Тест-кейсы |
| Аудит жизненного цикла согласия | 100 % переходов в неизменяемом логе | ИБ-аудит |

Базовые NFR шлюза (доступность ≥ 99,95 %, RPO=0, RTO ≤ 1 ч) наследуются без изменений.

## Risks / Trade-offs

- [Регуляторная модель рекуррентных списаний НСПК не подтверждена] → блокировать реализацию протокола до документации НСПК; ядро проектировать канально-независимо (AD-008).
- [Вендор ОПКЦ не поддерживает рекуррентный сервис] → отдельный раунд RFP/пересмотр вендора; зафиксировать как человеческое решение.
- [Списание после отзыва согласия из-за гонки (дебит в полёте, согласие отозвано)] → проверка согласия в той же транзакции инициации дебита; отзыв фиксирует «точку невозврата»; расхождение — сверка + runbook.
- [Массовые волновые списания создают пиковую нагрузку на АБС] → приоритизация очереди, плавный ramp, отдельное окно для волн.
- [ПДн согласия] → минимизация полей, шифрование в покое, маскирование в логах (AD-007).

## Migration Plan

1. Внедрение аддитивно: новые эндпоинты/поля под флагом `recurring.enabled` (по умолчанию off).
2. Расширение контрактов (API ТСП, адаптер ОПКЦ) и RFP — до реализации.
3. Walking skeleton: `создать согласие → подтвердить (мок НСПК) → дебит → зачисление (мок АБС) → вебхук`, плюс негатив «дебит по отозванному согласию».

**План отката.**
- **До боевой эксплуатации**: не включать; все изменения обратимы.
- **После включения**: kill-switch `recurring.stopNew` (запрет новых согласий и дебитов) без влияния на C2B-QR и уже активные согласия; откат релиза — rolling; данные согласий не мигрируются обратно (шлюз остаётся источником истины до сверки).
- **Сигналы отката**: двойное списание, списание после отзыва, расхождение сверки > 0 по завершённым дебитам, SLO-нарушение по отзыву.
- **Владелец решения об откате**: solution-architect (платёжный контур) + дежурная смена.

## Acceptance criteria (для гейта A4)

Каждый критерий проверяется тестом/командой:

1. Согласие проходит `PENDING → ACTIVE → REVOKED/EXPIRED`; повторные события идемпотентны.
2. Дебит создаётся только по `ACTIVE` согласию; `REVOKED`/`EXPIRED`/`PENDING` → отклонение (fitness).
3. Сумма/период сверх лимитов согласия → `CONSENT_LIMIT_EXCEEDED`.
4. Зачисление по дебиту — только из `PAID`; двойное списание — 0.
5. Существующий C2B-QR сценарий не регрессировал (регресс-тест полного набора C2B).
6. NFR (латентность, throughput, эффективность отзыва) — в допусках.
7. Сверка покрывает согласия и дебиты; уведомление плательщика — 100 %.

## Open Questions (требуют решения человека-архитектора)

Эти пункты меняют спецификацию/подход и не могут быть сняты автором пакета — требуют решения архитектора, ИБ/комплаенса, бизнеса или вендора:

1. **Семантика сервиса рекуррентных списаний НСПК** (формат согласия, канал подтверждения, поля плательщика, тайминги) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`, подтверждается документацией НСПК. *Почему человек: единственный источник истины по протоколу.*
2. **Регуляторная модель**: право отзыва, обязательность и канал уведомления плательщика, лимиты/период, окно бесспорного возврата. *Почему человек: ИБ/комплаенс, не техника.*
3. **Поддержка вендором ОПКЦ рекуррентного сервиса** (или новый раунд RFP). *Почему человек: закупки + подтверждение capability.*
4. **Ратификация нового spine-инварианта «дебетование только по активному согласию»** (аналог AD-005). *Почему человек: изменение набора инвариантов.*
5. **Продуктовые лимиты** по сегментам (кинотеатры/ЖКХ/связь) и окно возврата дебитов. *Почему человек: бизнес-решение.*
