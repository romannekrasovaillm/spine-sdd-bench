# Solutioning — Рекуррентные C2B-списания (подписки СБП)

Изменение поверх принятого решения «Платёжный шлюз СБП (C2B-приём)» (`docs/solutioning.md`, ADR-001..007, `ARCHITECTURE-SPINE.md` AD-001..AD-008). Настоящий документ — пакет для архитектурного решения (A3) и последующего handoff исполнителям. Код не пишется.

## 1. Оценка значимости и маршрут

Инструмент `significance_score` (15 триггеров): **score = 8, маршрут Critical**.

Сработавшие триггеры:

| # | Триггер | Обоснование |
|---|---|---|
| 1 | `new_component` | менеджер согласий + планировщик (scheduler) — новая ответственность в платёжном контуре |
| 2 | `new_datastore` | реестр согласий, токены расчётных инструментов, расписание списаний |
| 3 | `cross_domain_integration` | жизненный цикл согласия пересекает банк плательщика через НСПК (новый pull-поток) |
| 4 | `api_contract_change` | новые endpoints `/v1/subscriptions/*` + расширение модели платежа (`paymentType`) |
| 5 | `data_contract_change` | новые сущности: согласие, расписание, рекуррентное списание |
| 6 | `consistency_model_change` | две новые статусные машины (согласие, рекуррентное списание) + гонка «отзыв vs списание» |
| 7 | `significant_nfr` | точность планировщика, лаг распространения отзыва, пакетный профиль нагрузки |
| 8 | `financial_impact` | двойное/неавторизованное списание — финансовый и регуляторный риск |

**Почему глубокое проектирование обязательно:** 8 ≥ 5 и финансовое влияние → полный Solutioning (spine + ADR + NFR), обязательная человеческая точка A3, walking skeleton до массовой реализации, evidence-гейты (A4/A5). Дельта-спека (`delta-spec`) недостаточна — Critical Path исключён из её области применимости.

## 2. Влияние на принятую архитектуру (инварианты)

| Инвариант | Что меняется | Что НЕ меняется |
|---|---|---|
| **AD-001** Изоляция платёжного контура | В scope контура добавляются менеджер согласий и планировщик | Принцип: АБС/ОПКЦ — только через адаптеры шлюза; единая точка вызова сохраняется |
| **AD-002** Единый источник истины (статусная машина) | Добавляются машины согласия и рекуррентного списания | Атомарность «статус + outbox + аудит»; платёж остаётся единым источником истины |
| **AD-003** Идемпотентность финансовых операций | Новые ключи: детерминированный `{subscriptionId}:{periodKey}`, идемпотентность создания согласия | Принцип «повтор не меняет завершённое состояние» |
| **AD-004** Единственный адаптер ОПКЦ | Контракт `opkc-adapter.md` расширяется методами/событиями рекуррентности | Протокол НСПК знает только адаптер; ядро контрактно-независимо |
| **AD-005** Зачисление только из подтверждённого статуса | Ничего в правиле; появляется **новый** предусловие-гейт (активное согласие — вынесено в AD-009) | `PAID` остаётся единственным состоянием зачисления; сага возвратов не меняется |
| **AD-006** Trust-зоны и сегментация | Ничего | Новых зон нет; согласие/токен — чувствительные данные внутри существующего контура |
| **AD-007** Соответствие НПС/КИИ/ПДн | Новая ПДн-поверхность (согласие, токен) и аудит-журнал отзыва; AML по рекуррентному потоку | Регуляторный каркас, СКЗИ/ГОСТ, неизменяемый аудит-лог |
| **AD-008** Стратегия гибрид [ADOPTED] | Scope RFP и контракта адаптера растёт (рекуррентные операции НСПК) | Сам выбор «ядро in-house + вендорский транспорт» неизменен |

**Новый инвариант** — **AD-009** (см. `ARCHITECTURE-SPINE.md`): рекуррентное списание только из активного согласия в пределах лимитов; отзыв блокирует новые списания, гонка разрешается детерминированно. Это именно то, в чём независимые исполнители могут разойтись несовместимо (одни проверят «согласие существует», другие — «активно и в лимитах»).

## 3. Архитектурное решение

Полный текст — `docs/adr/ADR-008-*.md` (статус Proposed, ждёт A3). Кратко: согласие — сущность первого класса со своей машиной; рекуррентное списание — платёж `paymentType: recurring` поверх существующей машины (без `QR_ISSUED`); инициация pull/планировщиком; протокол НСПК — только в адаптере. Альтернативы и последствия — в ADR.

## 5. Измеримые NFR (новый функционал)

| NFR | Цель | Метод проверки |
|---|---|---|
| Активация согласия от нотификации НСПК | p95 < 2 с | APM, синтетика |
| Распространение отзыва согласия (блокировка новых списаний) | ≤ 1 с после REVOKED/EXPIRED | Тест гонки |
| Инициация рекуррентного списания (pull ТСП) | p95 < 500 мс (как разовый `createPayment`) | Нагрузочный тест |
| Своевременность планировщика | ≥ 99,9 % окон срабатывают в ±5 мин от планового времени | Метрика scheduler |
| Двойной запуск окна планировщиком | 0 (детерминированный ключ) | Тест повторного запуска/ребалансировки |
| Неавторизованное списание (согласие неактивно/сверх лимита) | 0 — блокируется на входе | Fitness-тест AD-009 |
| Пропускная способность рекуррентного потока | sustained 200 TPS агрегат; пакетная обработка 10k списаний/час без деградации интерактивной латентности | Нагрузочный стенд |
| Доступность реестра согласий | ≥ 99,95 % (в составе шлюза) | SLO-отчёт |
| RPO / RTO | RPO=0; RTO ≤ 1 ч (наследуются) | DR-учения |
| ПДн: шифрование согласия/токена в покое, минимизация | 100 % | ИБ-ревью, тесты |
| AML по рекуррентному потоку | 100 % списаний выше порога передаются в AML | Тест-кейсы |
| Двойное списание при повторах | 0 | Тест повторной доставки |

Противоречия NFR: точность планировщика (±5 мин) против простоты пакетной обработки — разрешено допущением «окно списания, а не секундная точность» (подписки не требуют секундного тайминга); зафиксировано в ADR-008.

## 6. Критерии приёмки (EARS) и план отката

### 6.1 Критерии приёмки (readiness-гейт)

- `When` ТСП создаёт согласие с корректными лимитами, `the шлюз shall` зарегистрировать его в `PENDING_ACTIVATION` и вернуть `subscriptionId`.
- `When` НСПК подтверждает согласие (`consent.confirmed`), `the шлюз shall` перевести согласие в `ACTIVE` идемпотентно по `eventId`.
- `When` плательщик отзывает согласие, `the шлюз shall` перевести его в `REVOKED` и заблокировать новые списания за ≤ 1 с.
- `When` ТСП инициирует списание по активному согласию в пределах лимитов, `the шлюз shall` создать платёж `paymentType: recurring` и провести его по машине платежа.
- `While` согласие не `ACTIVE` или лимит превышен, `the шлюз shall` отклонить списание (403/422) без обращения к ОПКЦ (AD-009).
- `When` планировщик повторно запускает то же окно, `the шлюз shall` вернуть существующий `paymentId` без создания дубля (`{subscriptionId}:{periodKey}`).
- `When` рекуррентное списание подтверждено НСПК, `the шлюз shall` зачислить средства ТСП только из `PAID` (AD-005).
- `When` отзыв согласия конкурирует со списанием в полёте, `the шлюз shall` довести подтверждённое списание до конца, а неподтверждённое — отменить (детерминированное правило AD-009).

Негативные сценарии: двойная доставка нотификации; отзыв в момент списания; недостаточно средств у плательщика; недоступность НСПК/АБС в окно списания; повторный запуск планировщика после ребалансировки.

### 6.2 План отката

- **До боевой эксплуатации**: откат = не включать feature-flag; всё обратимо (ADR-008 reversible).
- **После включения**: feature-flag отключает создание новых согласий и новых рекуррентных списаний; уже открытые списания доводятся по саге/сверке; разовые платежи не затрагиваются (изолированы по `paymentType`).
- **Сигналы отката (триггеры)**: доля отклонённых рекуррентных списаний по вине шлюза > порога (согласовать с бизнесом); любое двойное списание; рассогласование сверки с НСПК по рекуррентным операциям > 0; рост DLQ рекуррентного потока.
- **Владелец решения об откате**: человек-архитектор + бизнес (A3/A5).

## 7. Что остаётся на решение человека-архитектора (A3) и почему

| # | Вопрос | Почему не решается сейчас |
|---|---|---|
| 1 | **Протокол и канал захвата согласия НСПК** (подтверждение плательщика через банк/ОПКЦ) | Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`: точный протокол рекуррентных операций НСПК публично не раскрыт. Решить: ждать документацию (как ADR-007 для транспорта) или строить по допущению |
| 2 | **Параметры модели согласия** (фиксированная/переменная сумма, max-сумма, период, открытый/срочный срок) | Продуктовое и риск-решение бизнеса; влияет на лимиты и потолки в AD-009 |
| 3 | **Состав первой волны** (какие вертикали; только pull или сразу планировщик) | Бизнес-приоритизация; влияет на NFR пакетной обработки и сроки |
| 4 | **Диспуты/претензии по рекуррентным списаниям** | В базовом решении диспуты deferred; рекуррентность повышает риск споров. Решить: оставить deferred или включить в первую волну |
| 5 | **Расширение фича-spine (AD-009) vs выделение нового инициативного spine** | Вопрос владения/границ: рекуррентность — расширение этого spine (выбрано в ADR-008) или новый initiative с родительским spine |
| 6 | **Пороги AML/комплаенс на уровне согласия** (мониторинг не только списаний, но и создания/отзыва согласий) | Требует позиции комплаенс/ИБ по 115-ФЗ |
