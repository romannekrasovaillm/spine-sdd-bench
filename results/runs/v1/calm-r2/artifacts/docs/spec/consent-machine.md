# Статусная машина согласия (consent) — спецификация переходов

- Status: Draft (для ревью на гейте A1 фичи подписок)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002 (обобщён), AD-002 (расширен), AD-003, AD-009 (новый)

Согласие — first-class сущность шлюза; единственный источник истины его жизненного цикла — БД шлюза. Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (обобщение AD-002). Повторные события идемпотентны (AD-003).

## 1. Состояния согласия

| Состояние | Смысл | Спискания разрешены |
|---|---|---|
| `PENDING` | Согласие зарегистрировано в шлюзе, запрос на подтверждение ушёл в НСПК/банк плательщика | нет |
| `ACTIVE` | Плательщик подтвердил согласие; списания разрешены в пределах лимитов | да |
| `PAUSED` | Приостановлено (ТСП или банк); возобновляемо | нет (возобновляемо) |
| `CANCELLED` | Отменено ТСП | нет |
| `EXPIRED` | Истёк срок действия (`validTo`) | нет |
| `REVOKED` | Отозвано плательщиком (или банком плательщика) | нет |
| `DECLINED` | Плательщик отклонил первоначальное подтверждение | нет |
| `FAILED` | Регистрация в ОПКЦ не удалась (исчерпаны ретраи) | нет |

Терминальные: `CANCELLED`, `EXPIRED`, `REVOKED`, `DECLINED`, `FAILED` — из них переходов нет.

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен, лимиты валидны | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `PENDING` | `ACTIVE` | событие `consent.confirmed` | `eventId` новый; лимиты в силе | outbox «согласие активно», вебхук `consent.activated` |
| C3 | `PENDING` | `DECLINED` | событие `consent.declined` | — | вебхук `consent.declined` |
| C4 | `PENDING` | `FAILED` | ошибка регистрации в ОПКЦ (ретраи исчерпаны) | ошибка не транзиентная | outbox, вебхук `consent.failed` |
| C5 | `ACTIVE` | `REVOKED` | событие `consent.revoked` | — | **немедленная блокировка новых списаний**; outbox, вебхук `consent.revoked` |
| C6 | `ACTIVE` | `PAUSED` | `POST /v1/consents/{consentId}/pause` (или событие от НСПК) | фича `PAUSED` включена | outbox; новые списания блокируются |
| C7 | `PAUSED` | `ACTIVE` | `POST /v1/consents/{consentId}/resume` (или событие от НСПК) | срок не истёк | outbox; списания возобновлены |
| C8 | `ACTIVE`/`PAUSED` | `CANCELLED` | `POST /v1/consents/{consentId}/cancel` (ТСП) | — | outbox, вебхук `consent.cancelled` |
| C9 | `ACTIVE`/`PAUSED` | `EXPIRED` | таймер `validTo` | `validTo` наступил, `ACTIVE`/`PAUSED` | outbox, вебхук `consent.expired` |

## 3. Лимиты согласия (проверяются в шлюзе до инициации списания)

- `amountLimitPerDebit` — максимум одного списания;
- `amountLimitPeriod` + период — суммарный потолок за период (день/месяц);
- `minIntervalSeconds` — минимальный интервал между списаниями;
- `validFrom`/`validTo` — срок действия.

Проверка перед `initiateDebit`: согласие `ACTIVE`; `validFrom ≤ now ≤ validTo`; сумма списания ≤ `amountLimitPerDebit`; накопленная сумма за период + сумма ≤ `amountLimitPeriod`; интервал от последнего списания ≥ `minIntervalSeconds`. Нарушение — отказ до обращения к НСПК.

## 4. Связь с рекуррентным списанием (debit)

Debit — это платёж `paymentType = subscription`, создаваемый `POST /v1/consents/{consentId}/debits`. Он переиспользует статусную машину платежа (`docs/spec/state-machine.md`) с отличиями:

- стартует из `CREATED`; `QR_ISSUED` недостижимо (QR не выпускается);
- триггер `PAID` — нотификация НСПК о списании по согласию (а не по QR);
- guard T4 (сумма/получатель совпадают) действует без изменений;
- зачисление в АБС — только из `PAID` (AD-005).

## 5. Идемпотентность

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | тот же `consentId`, состояние не меняется |
| `POST /v1/consents/{consentId}/debits` | `Idempotency-Key` (или сквозной `merchantDebitId`) | тот же `paymentId`, состояние не меняется |
| События согласия | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| `consent.confirmed` после `REVOKED` | `eventId` + статус | игнорируется с алертом (нельзя активировать отозванное) |

## 6. Сверка и восстановление

- Ежечасная сверка статусов согласий с НСПК: «у НСПК `ACTIVE`, у шлюза нет» → дозапрос статуса; «у шлюза `ACTIVE`, у НСПК нет/отозвано» → перевод в `REVOKED`/стоп-сигнал с эскалацией.
- Debit-ы сверяются по существующему контуру сверки платежей (ADR-004/AD-005).
- Согласие в `PENDING` дольше регламентного срока — опрос статуса у НСПК (не зависеть только от push).

## 7. Согласованность с API ТСП

Маппинг статусов наружу (`tsp-api.md` §4, `Consent.status`): `PENDING`, `ACTIVE`, `PAUSED`, `CANCELLED`, `EXPIRED`, `REVOKED`, `DECLINED`, `FAILED` — без технических подсостояний. Списание наружу отражается как обычный платёж (`Payment`) с `paymentType: subscription` и ссылкой `consentId`.
