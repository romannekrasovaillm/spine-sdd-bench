# Solutioning — Рекуррентные C2B-списания по согласию (подписки СБП)

Настоящий документ — архитектурный пакет изменения поверх принятого решения «Платёжный шлюз СБП (C2B-приём)». Он переводит roadmap-пункт «автоплатежи» (`docs/solutioning.md` §1) в scope. Принятый baseline (ADR-001..007, spine AD-001..008) не переписывается — изменение оформляется аддитивно (ADR-008, AD-009, расширения контрактов/NFR).

## 1. Оценка значимости и маршрут

**Маршрут: High (значимость 8/15)** — feature-уровень, не новый initiative.

- **Почему не Critical (11/15), как у базового C2B-приёма**: платформа уже принята — статусная машина платежа (AD-002), транзакционный outbox (AD-001), адаптер ОПКЦ (AD-004), зачисление из `PAID` (AD-005), trust-зоны и ГОСТ (AD-006), гибридная стратегия (AD-008). Рекуррентные списания **переиспользуют** эту платформу, а не создают новую.
- **Почему не Medium/Low**: появляется новый финансово-значимый объект (согласие) с собственным жизненным циклом; списание происходит **без действия клиента** в момент операции — повышенный фрод-риск; расширяется compliance-поверхность (161-ФЗ по распоряжениям с заранее данным акцептом, 152-ФЗ — ПДн плательщика, 115-ФЗ — AML).

**Глубина проектирования**: полный feature-уровень — один ADR (ADR-008), один spine-инвариант (AD-009), спецификация статусной машины согласия, аддитивные изменения контрактов (API ТСП + адаптер ОПКЦ), измеримые NFR, критерии приёмки и план отката. Гейты A0–A5 базового решения не пересоздаются; для этой фичи достаточно **одного человеческого решения** (утверждение ADR-008, аналог A3) до начала реализации транспорта согласий.

## 3. Доменная модель и потоки

Новые сущности:

- **Согласие (consent)** — durable-соглашение плательщика с ТСП: `consentId`, ТСП, идентификатор плательщика (маскированный), лимиты (макс. сумма/списание, периодный потолок, мин. интервал, срок действия), статус, `Idempotency-Key`.
- **Рекуррентное списание (debit)** — платёж, инициированный ТСП по `consentId`; повторно использует сущность «платёж» и её статусную машину (с пропуском `QR_ISSUED`), `paymentType = subscription`.

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant P as Банк плательщика
    participant A as АБС

    T->>G: POST /v1/consents (Idempotency-Key, ТСП, плательщик, лимиты)
    G->>G: consent PENDING, outbox
    G->>N: registerConsent (адаптер ОПКЦ)
    N->>P: маршрутизация на подтверждение
    P-->>N: плательщик подтверждает (однократно)
    N-->>G: событие consent.confirmed
    G->>G: consent ACTIVE, outbox
    G-->>T: вебхук consent.activated

    Note over T,G: далее — списания без действия плательщика
    T->>G: POST /v1/consents/{consentId}/debits (Idempotency-Key, сумма)
    G->>G: проверка ACTIVE + лимиты; платёж CREATED (type=subscription)
    G->>N: initiateDebit (адаптер ОПКЦ)
    N-->>G: подтверждение PAID (eventId)
    G->>A: зачисление (paymentId)
    A-->>G: absDocId
    G->>G: CREDITED → COMPLETED, outbox
    G-->>T: вебхук payment.completed
```

Отзыв плательщиком (в банке плательщика) приходит событием `consent.revoked` → согласие `REVOKED` → новые `POST /debits` отклоняются `422 CONSENT_NOT_ACTIVE`.

## 5. NFR

Измеримые цели нового функционала — `docs/nfr.md` §7. Ключевое: регистрация/инициация списания p95 < 500 мс; распространение отзыва согласия до блокировки новых списаний ≤ 30 с; двойных списаний за один период по одному согласию — 0; 100 % списаний с действующим согласием на момент инициации.

## 6. Критерии приёмки

Функциональные:

1. Создание согласия `POST /v1/consents` возвращает `consentId`, статус `PENDING`; повторный вызов с тем же `Idempotency-Key` возвращает тот же `consentId` без дубля.
2. Событие `consent.confirmed` переводит согласие `PENDING → ACTIVE`; событие `consent.declined`/`consent.revoked` — в терминальное состояние; повторная доставка события с тем же `eventId` не меняет состояние.
3. `POST /v1/consents/{consentId}/debits` при `ACTIVE` и сумме в пределах лимитов создаёт платёж `paymentType=subscription`, проходящий `CREATED → PAID → CREDITED → COMPLETED` (зачисление только из `PAID`).
4. Списание при согласии `REVOKED`/`EXPIRED`/`CANCELLED`/`DECLINED`/`FAILED` отклоняется `422 CONSENT_NOT_ACTIVE`; превышение лимита — `422 CONSENT_LIMIT_EXCEEDED`.
5. Сумма/получатель debit-а иммутабельны после создания; расхождение в нотификации НСПК → `FAILED` + алерт, зачисление запрещено.

Негативные (обязательные тесты):

- Повторная нотификация `PAID` (тот же `eventId`) → состояние не меняется, вторая проводка в АБС не создаётся.
- Отзыв согласия между «валидацией» и «инициацией» списания → списание не исполняется (гонка «отзыв vs списание»).
- АБС недоступна на шаге зачисления → платёж остаётся `PAID`, виден в сверке, зачисление гарантируется (не теряется).
- Сбой после регистрации debit в НСПК до подтверждения → сверка находит операцию, зачисление доводится.

Критерий успешного отката — см. §7.

## 7. План отката

- **До боевой эксплуатации**: фича за feature-флагом; откат = выключение флага. Все изменения аддитивны (ADR-008 reversible); QR-поток не затрагивается.
- **После включения**: `stop-new` — запрет регистрации новых согласий и новых списаний мгновенно, без остановки обработки уже инициированных операций; откат релиза — rolling. Данные согласий не мигрируются обратно; открытые списания завершаются по статусной машине и закрываются сверкой.
- **Сигнал отката**: доля отклонённых списаний из-за ошибок согласия > порога (см. NFR), расхождение «у шлюза ACTIVE, у НСПК нет» в сверке, рост DLQ.
- **Владелец решения об откате**: product-owner подписки + solution-architect; аварийная остановка — дежурная смена по runbook.
- **Аварийный сценарий**: DLQ → дежурная смена; сверка компенсирует потерянные нотификации; RTO ≤ 1 ч (унаследовано из базового NFR).

## 8. Gaps и внешние входы

| Gap | Что закроет | Владелец |
|---|---|---|
| Протокол НСПК по согласиям и списаниям (поля, тайминги, форматы) `[ТРЕБУЕТ ПРОВЕРКИ]` | Документация НСПК по договору | Проектный офис / НСПК |
| Нормализованные `reasonCode` согласия/списания | Документация НСПК; справочник | Архитектор + вендор |
| Регламент НСПК по срокам подтверждения согласия | Документация НСПК | Проектный офис |
| Идентификатор плательщика для согласия (какие ПДн минимально) | ИБ + юристы (152-ФЗ) | ИБ/комплаенс |
| Модель лимитов и дефолты | Бизнес/продукт | Product-owner |

## 9. Что остаётся на решение человека-архитектора (и почему)

1. **Утверждение ADR-008 (выбранная модель «согласие как first-class»)** — финансово-значимое решение уровня A3; определяет состав работ и границу с вендором. Без него реализация транспорта согласий не начинается (как ADR-007 для базового C2B).
2. **Модель лимитов** (кто задаёт — банк/ТСП/плательщик; дефолты и верхние границы) — продуктовое решение, вне компетенции архитектора; влияет на API и фрод-политику.
3. **Поддержка `PAUSED` (приостановка)** vs только отмена/отзыв — продуктовый объём; влияет на статусную машину согласия.
4. **Диспуты/chargeback по рекуррентным списаниям** — сейчас Deferred (как в baseline), но фрод-риск по рекурренту выше; требуется решение о сроках возврата в scope.
5. **Минимальный состав ПДн плательщика в согласии** — правовое решение (152-ФЗ), фиксируется с ИБ/юристами до реализации хранения.
6. **Требования НСПК по согласиям** `[ТРЕБУЕТ ПРОВЕРКИ]` — внешний вход; до получения контракт не реализуется, но проектирование на уровне внутреннего контракта выполнимо уже сейчас.
