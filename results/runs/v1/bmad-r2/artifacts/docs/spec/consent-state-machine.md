# Статусная машина согласия (consent) — спецификация переходов

- Status: Draft (для ревью на гейте A1 рекуррентного изменения)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, AD-002, AD-003, AD-009

Согласие плательщика — **сущность первого класса** (ADR-008). Источник истины жизненного цикла для API ТСП — БД шлюза (проекция реестра СБП; мастер-согласие юридически принадлежит плательщику и хранится в СБП — см. ADR-008 §11). Каждый переход — **атомарная транзакция** «смена статуса + outbox + аудит» (AD-002). Повторные события дедуплицируются по `eventId` (AD-003).

## 1. Состояния

| Состояние | Смысл | Спиcания разрешены |
|---|---|---|
| `CONSENT_PENDING` | Регистрация согласия в СБП инициирована, подтверждение от НСПК не получено | нет |
| `CONSENT_ACTIVE` | Согласие активно, подтверждено СБП | **да** |
| `CONSENT_SUSPENDED` | Приостановлено (временная блокировка — по событию НСПК или ТСП) | нет |
| `CONSENT_REVOKED` | Отозвано плательщиком (или ТСП) — терминальное | нет |
| `CONSENT_EXPIRED` | Истёк срок действия — терминальное | нет |

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `CONSENT_PENDING` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `CONSENT_PENDING` | `CONSENT_ACTIVE` | событие `consent.registered` (адаптер ОПКЦ) | согласие подтверждено СБП | сохранить параметры согласия, outbox-вебхук `consent.activated` |
| C3 | `CONSENT_PENDING` | `CONSENT_REVOKED` | событие `consent.rejected` / отказ регистрации | — | `reasonCode`, вебхук `consent.failed` |
| C4 | `CONSENT_ACTIVE` | `CONSENT_REVOKED` | событие `consent.revoked` (плательщик/ТСП) | — | **закрыть приём новых списаний** (AD-009), вебхук `consent.revoked` |
| C5 | `CONSENT_ACTIVE` | `CONSENT_EXPIRED` | таймер срока действия | `REVOKED` не наступил | закрыть приём списаний, вебхук `consent.expired` |
| C6 | `CONSENT_ACTIVE` | `CONSENT_SUSPENDED` | событие `consent.suspended` (НСПК) | — | закрыть приём списаний, вебхук `consent.suspended` |
| C7 | `CONSENT_SUSPENDED` | `CONSENT_ACTIVE` | событие `consent.resumed` (НСПК) | срок не истёк | возобновить приём списаний, вебхук `consent.activated` |
| C8 | `CONSENT_SUSPENDED` | `CONSENT_REVOKED` / `CONSENT_EXPIRED` | события отзыва/таймер | — | как C4/C5 |

## 3. Инварианты (запрещённые переходы)

- **Списание инициируется только из `CONSENT_ACTIVE`** (AD-009): из `CONSENT_PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED` — недостижимо, проверяется fitness-тестом.
- `CONSENT_REVOKED` и `CONSENT_EXPIRED` — терминальные: из них переходов нет; повторные события идемпотентны (AD-003).
- `CONSENT_ACTIVE` не может «вернуться» из `REVOKED`/`EXPIRED` — отзыв/истечение необратимы; возобновление возможно только из `SUSPENDED`.
- Параметры согласия (макс. сумма/списание, срок, частота) иммутабельны после `CONSENT_ACTIVE`; изменение параметров = новое согласие (не мутация старого).

## 4. Идемпотентность

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | тот же `consentId`, состояние не меняется |
| События `consent.*` (НСПК) | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| `POST /v1/consents/{consentId}/revoke` (ТСП) | `Idempotency-Key` / `consentId` | повторный отзыв — idempotent no-op |

## 5. Сверка и восстановление

- Открытые состояния (`CONSENT_PENDING`) — кандидаты на сверку с НСПК (`getConsentStatus`); суточная сверка согласий.
- «У НСПК `REVOKED`, у нас `ACTIVE`» → авто-запрос статуса → C4 (закрыть приём списаний немедленно).
- «У нас `ACTIVE`, у НСПК нет» → стоп-сигнал, эскалация (риск списания без согласия в СБП).

## 6. Согласованность с API ТСП

Маппинг статусов наружу (`tsp-api` §3.6): `CONSENT_PENDING`, `CONSENT_ACTIVE`, `CONSENT_SUSPENDED`, `CONSENT_REVOKED`, `CONSENT_EXPIRED` — без технических подсостояний. Внутренние поля (`consentRef` НСПК, `reasonCode`) наружу не выставляются.
