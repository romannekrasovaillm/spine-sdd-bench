# Solutioning — Платёжный шлюз СБП (C2B-приём)

Маршрут: **Critical** (значимость 11/15). Настоящий документ — полный Solutioning: контекст, компоненты, потоки, разбиение на ADR, NFR, план гейтов A0–A5, план отката, gaps.

## 1. Контекст и границы

Банк — участник СБП (эквайер/агент ТСП) принимает C2B-платежи от ТСП. Внешние системы: **ОПКЦ СБП (АО «НСПК»)** — операционный/клиринговый центр, **Банк России** — расчёты по корсчетам. Внутренние: **АБС** (счета ТСП), **антифрод/AML**, **SIEM**, **отчётность** (ЦБ/НСПК).

Подключение банка — по порядку ЦБ РФ (cbr.ru/PSystem/payment_system/actions/): договор с ПБР + СКЗИ → присоединение к Правилам ОПКЦ СБП → доработка ПО по документации Портала поддержки НСПК → тестовые испытания → активация. **Документация НСПК — внешний вход**: точный протокол получается по договору, публично не раскрыт (все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]` до получения).

Сценарии C2B в scope: динамический QR, статический QR/наклейка, кассовые ссылки, оплата по ссылке в e-commerce, возвраты, **рекуррентные списания по согласию (подписки СБП, ADR-008)**. Roadmap (вне scope): C2C, выплаты B2C/B2B, диспуты.

## 3. Статусная модель платежа

```
CREATED ──► QR_ISSUED ──► PAID ──► CREDITED ──► COMPLETED
   │            │          │            │
   ▼            ▼          ▼            ▼
 FAILED      EXPIRED    FAILED      REFUNDED (через сагу возврата)
```

- `PAID` — подтверждённый НСПК статус; **только из него** разрешено зачисление (AD-005).
- Переходы — атомарные транзакции «статус + outbox + аудит» (AD-002).
- Повторные нотификации идемпотентны (AD-003).

## 4. Ключевые потоки

### 4.1 Оплата динамическим QR (счастливый путь)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant A as АБС

    T->>G: POST /payments (Idempotency-Key, сумма, реквизиты ТСП)
    G->>G: создать CREATED, outbox
    G->>N: регистрация QR (адаптер ОПКЦ)
    N-->>G: qrId + ссылка qr.nspk.ru/...
    G->>G: статус QR_ISSUED, outbox
    G-->>T: 201 {paymentId, qrId, qrUrl, qrImage}
    Note over N: плательщик сканирует QR и платит в своём банке
    N-->>G: нотификация PAID (eventId)
    G->>G: дедупликация по eventId, статус PAID, outbox
    G->>A: зачисление (paymentId, сумма, счёт ТСП)
    A-->>G: absDocId / подтверждение
    G->>G: статус CREDITED → COMPLETED, outbox
    G-->>T: вебхук COMPLETED
```

### 4.2 Возврат (сага)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant A as АБС
    participant N as ОПКЦ СБП (НСПК)

    T->>G: POST /refunds (refundId, paymentId, сумма)
    G->>G: проверка: платёж CREDITED/COMPLETED
    G->>A: списание со счёта ТСП (refundId)
    A-->>G: подтверждение
    G->>N: регистрация возврата (refundId)
    N-->>G: подтверждение возврата
    G->>G: статус REFUNDED, outbox
    G-->>T: вебхук REFUNDED
    Note over G: сбой на шаге → компенсация (отмена АБС-списания / повтор регистрации в НСПК / DLQ + runbook)
```

### 4.3 Создание и активация согласия (подписка)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant P as Банк плательщика

    T->>G: POST /v1/consents (Idempotency-Key, лимиты, срок)
    G->>G: согласие CREATED, outbox
    G->>N: createConsent (reference=consentId)
    N-->>P: запрос на подтверждение плательщика
    P-->>N: плательщик подтверждает в своём приложении
    N-->>G: нотификация consent.activated (eventId)
    G->>G: дедупликация по eventId, согласие ACTIVE, outbox
    G-->>T: вебхук consent.activated
```

### 4.4 Рекуррентное списание (без QR)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant A as АБС

    T->>G: POST /v1/payments (consentId, amount, billingPeriodKey)
    G->>G: guard: согласие ACTIVE, лимиты, billingPeriodKey не дублируется → CREATED, outbox
    G->>N: debitByConsent (reference=paymentId)
    N-->>G: нотификация payment.paid (eventId)
    G->>G: дедуп по eventId, статус PAID, outbox
    G->>A: зачисление (paymentId, сумма, счёт ТСП) — только из PAID (AD-005)
    A-->>G: absDocId
    G->>G: CREDITED → COMPLETED, outbox
    G-->>T: вебхук payment.completed
    Note over G: отзыв согласия (revoke) → согласие REVOKED, любые последующие списания блокируются до вызова НСПК
```

## 5. Разбиение на решения (ADR)

| Решение | ADR | Spine |
|---|---|---|
| Топология: выделенный компонент + outbox | ADR-001 | AD-001, AD-002 |
| Статусная машина + идемпотентность | ADR-002 | AD-002, AD-003 |
| Транспорт к ОПКЦ: изолированный адаптер, mTLS/ГОСТ, СКЗИ | ADR-003 | AD-004 |
| Нотификации: at-least-once, дедуп, DLQ, сверка | ADR-004 | AD-003 |
| АБС: зачисление из PAID, возвраты-сага | ADR-005 | AD-005 |
| НПС/КИИ/ПДн: trust-зоны, ГОСТ | ADR-006 | AD-006, AD-007 |
| Стратегия реализации (гибрид) — **A3 принято 2026-08-15** | ADR-007 (Accepted) | AD-008 [ADOPTED] |
| Рекуррентные списания: согласие + рекуррентный путь платежа | ADR-008 (Proposed) | AD-009 (Proposed) |

## 6. NFR

Полный набор с измеримыми целями — `docs/nfr.md`. Ключевое: доступность ≥ 99,95 %; RPO=0; RTO ≤ 1 ч; регистрация QR p95 < 500 мс; sustained 200 TPS / пик 500 TPS; сверка с НСПК ежечасная, с АБС суточная; двойных зачислений — 0.

## 7. Гейты и критерии приёмки

- **A0 (readiness)**: ADR-001..008 заполнены, spine пролинтован, gaps зафиксированы. Критерий: PASS.
- **A1 (Spec)**: контракт API ТСП (v0.2 — `docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`), таблица переходов статусной машины (`docs/spec/state-machine.md` — платежи и согласия), контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md` — ядро↔транспорт, основа RFP), RFP-пакет по вендору (`docs/rfp/vendor-rfp.md`), NFR финализированы (вкл. §7 рекуррентные).
- **A2 (Plan)**: разбивка на задачи, walking skeleton определён (сквозные пути: QR и рекуррентное списание: ТСП → шлюз → мок НСПК → АБС-мок → нотификация).
- **A3 (человеческое решение)**: стратегия реализации (ADR-007) — **обязательно до реализации транспорта**; ADR-008 — решение по рекуррентным списаниям до реализации согласий.
- **A4 (conformance)**: fitness-проверки spine-инвариантов, нагрузочные тесты (NFR), тесты идемпотентности, ИБ-аудит.
- **A5 (post-deploy drift)**: сверка с НСПК/АБС в проде, SLO-отчёт через 30 дней, проверка отсутствия дрейфа от spine.

**Критерии приёмки рекуррентных списаний (A4, проверяемые тестом):**

- Счастливый путь: согласие → активация (мок НСПК) → рекуррентное списание → `PAID` → `CREDITED` → вебхук `payment.completed`.
- Списание после `REVOKED`/`EXPIRED` → `422`, вызов ОПКЦ не выполняется (0 списаний после отзыва).
- Списание сверх лимита (`maxAmountPerDebit`/`maxFrequency`) → `422 CONSENT_LIMIT_EXCEEDED` до вызова ОПКЦ.
- Повторная инициация за тот же `billingPeriodKey` → тот же `paymentId`, второй дебет не создаётся (0 двойных списаний).
- Недоступность ОПКЦ при списании → платёж остаётся в `CREATED`, идемпотентный ретрай, сверка дозапрашивает статус.
- Fitness: зачисление рекуррентного платежа только из `PAID` (AD-005); переходы из терминальных согласий недостижимы (AD-009).

## 8. План отката

- **До боевой эксплуатации**: откат = не включать. Все работы обратимы (ADR-007 reversible).
- **После включения**: фиче-флаг на приём новых ТСП; мгновенный stop-new (запрет регистрации новых QR) без остановки обработки уже открытых операций; откат релиза — rolling; данные не мигрируются обратно (шлюз остаётся источником истины до полной сверки с АБС).
- **Рекуррентные списания (ADR-008)**: фиче-флаг на эндпоинты согласий и рекуррентных списаний (off по умолчанию); stop-new = запрет `POST /v1/consents` и рекуррентных `POST /v1/payments`, дренаж уже открытых списаний; QR-поток не затрагивается; данные согласий остаются как аудит (обратная миграция не требуется).
- **Аварийный сценарий**: DLQ → дежурная смена по runbook; сверка компенсирует потерянные нотификации; RTO ≤ 1 ч.

## 9. Gaps и внешние входы

| Gap | Что закроет | Владелец |
|---|---|---|
| Точный протокол НСПК (поля, тайминги, TLS-профили) | Документация НСПК по договору (Портал поддержки) | Проектный офис / НСПК |
| **Протокол НСПК для подписок/согласий (создание, активация, отзыв, списание по согласию, лимиты)** | Документация НСПК по подпискам СБП | Проектный офис / НСПК |
| Регламенты НСПК (таймауты, сроки уведомлений, доступность) | Документация НСПК, правила ОПКЦ СБП | Проектный офис |
| Номер/редакция Положения ЦБ о защите информации при переводах | ИБ/комплаенс банка | ИБ |
| Контракт АБС на зачисление/списание (идемпотентность, SLA) | Интервью с владельцем АБС | Архитектор + АБС |
| Категория объекта КИИ, состав мер ФСТЭК | ИБ/КИИ банка | ИБ |
| Выбор конкретного вендора транспорта ОПКЦ | RFP по критериям ADR-007 (сертификаты ФСТЭК, тестовый контур, SLA, референсы) | Проектный офис / закупки |
| Ретенция согласий и связанных ПДн после отзыва/истечения (152-ФЗ) | ИБ/комплаенс | ИБ |

## 10. Открытые вопросы

1. Объём первой волны: только C2B-приём или сразу C2C/выплаты? (влияет на состав адаптеров, но не на ядро).
2. Требования бизнеса к комиссиям и тарифам ТСП (влияет на модель отчётности).
3. Лимиты/пороги для AML-интеграции.
4. Доступность АБС в ночные окна (влияет на SLA зачисления).
5. Источник истины лимитов согласия (шлюз/НСПК/оба) — по документации НСПК подписок [ТРЕБУЕТ ПРОВЕРКИ].
6. Возвраты/диспуты по рекуррентным списаниям — применимость саги возврата (ADR-005) или отдельный сценарий.
7. Модель планировщика выставления и ёмкость под batch-пик (1-е число месяца).
