# Solutioning — Рекуррентные C2B-списания по согласию (подписки СБП)

- Status: Proposed (архитектурный пакет изменения поверх принятого решения)
- Owner: solution-architect (платёжный контур)
- Базовое решение: «Платёжный шлюз СБП (C2B-приём)» (`docs/solutioning.md`, ADR-001..007, `ARCHITECTURE-SPINE.md`)
- Связано: ADR-008 (решение), AD-009 (новый инвариант spine)

Настоящий документ — **пакет изменения**, который можно вынести на архитектурное решение и затем передать исполнителям. Он отвечает на семь обязательных вопросов: значимость/маршрут, влияние на принятую архитектуру, решение (отсылка к ADR-008), изменения контрактов, NFR, приёмка/откат, решения человека.

---

## 1. Оценка значимости и маршрута

| Аспект | Оценка |
|---|---|
| Тип изменения | **Новая финансовая возможность** на существующей Critical-системе: новый юридически значимый объект (согласие) + новый внешний поток (pull-дебит без действия клиента) |
| Значимость | **High** (в рамках Critical-системы). Причины: (а) финансовые последствия ошибок — списание без согласия, сверх лимита, двойное списание; (б) новый объект регулирования 161-ФЗ/152-ФЗ; (в) внешний канал и гонка «отзыв vs дебит»; (г) пиковый нагрузочный профиль («день списания») |
| Глубина проектирования | **Полное проектирование ядра изменения**: конечный автомат согласия, инвариант «дебит только из ACTIVE», идемпотентность новых поверхностей, расширение внутреннего контракта адаптера и API ТСП, новые NFR. **Без перепроектирования** топологии, trust-зон, транспорта и стратегии гибрида — они инвариантны |
| Маршрут | Тот же **Critical**, что и у базового решения (11/15); изменение не понижает и не повышает категорию системы |
| Почему так глубоко | Согласие — это **второй источник истины** и **новый инвариант** (AD-009), а не «ещё один endpoint». Ошибка в модели согласия транслируется в финансовые инциденты и нарушения НПС. Поверхностное проектирование здесь — неприемлемый риск |

**Вывод по маршруту:** изменение оформляется как полный ADR (ADR-008) + спецификация автомата согласия + расширение контрактов, но **не** как новый initiative и **не** как лёгкая правка. Родительский spine (инициатива «Подключение банка к СБП») не меняется.

## 2. Влияние на принятую архитектуру

### 2.1 Что меняется (по инвариантам spine)

| Инвариант | Характер влияния | Что именно |
|---|---|---|
| AD-001 (изоляция контура) | **Не меняется** | Рекуррентность живёт в том же платёжном контуре шлюза; взаимодействие с АБС/ОПКЦ — по-прежнему только через адаптеры |
| AD-002 (единый источник истины — статусная машина) | **Расширяется** | Появляется **вторая** статусная машина — согласия — с той же дисциплиной (атомарный переход + outbox + аудит). Правило не меняется, расширяется область его применения |
| AD-003 (идемпотентность финансовых операций) | **Расширяется** | Новые поверхности идемпотентности: создание/отзыв согласия (`Idempotency-Key`), события согласия (`eventId`), инициация дебита (`Idempotency-Key`), подтверждение дебита (`eventId`) |
| AD-004 (единственный адаптер ОПКЦ) | **Расширяется** | Внутренний контракт адаптера получает новые операции (`registerConsent`, `revokeConsent`, `initiateRecurringPayment`…) и события согласия. Протокол НСПК по-прежнему знает только адаптер |
| AD-005 (зачисление только из подтверждённого статуса) | **Уточняется, не меняется** | Зачисление по-прежнему только из `PAID`. Для рекуррентного дебита `PAID` — это подтверждённый ОПКЦ статус pull-списания, а не QR-оплаты. Путь к `PAID` короче (без `QR_ISSUED`), правило то же |
| AD-006 (trust-зоны) | **Не меняется** | Подписание согласия плательщиком происходит в банке плательщика (вне шлюза); зоны шлюза не меняются |
| AD-007 (НПС/КИИ/ПДн) | **Расширяется** | Согласие — новый объект ПДн/финансово-значимых данных: минимизация хранения, аудит-трейл жизненного цикла, согласие плательщика как правовое основание |
| AD-008 (гибрид, ядро контрактно-независимо от транспорта) | **Не меняется** | Рекуррентность — логика ядра; вендорский адаптер лишь расширяется контрактом. Стратегия и граница контракта прежние |

### 2.2 Что не меняется

- Топология (C4-контейнеры): те же DMZ/API, платёжный контур, контур АБС, антифрод, SIEM, отчётность.
- Механизмы: транзакционный outbox, DLQ, сверка с НСПК/АБС, нотификатор вебхуков — реюзаются.
- Существующие разовые платежи и их статусная модель — **не трогаются** (обратная совместимость, §4).
- Стратегия гибрида (ADR-007) и критерии RFP вендора — прежние; добавляется только требование к вендору реализовать новые операции контракта.

### 2.3 Новый инвариант spine

Предлагается добавить **AD-009** (Proposed, ратифицируется вместе с ADR-008):

> **AD-009. Рекуррентное списание только по активному согласию в пределах лимитов.** Рекуррентный дебит инициируется только если согласие `ACTIVE`, сумма дебита ≤ остаточного лимита, в пределах срока действия. Согласие — отдельный конечный автомат с атомарными переходами (AD-002) и идемпотентностью (AD-003). Fitness: недостижимость дебита из `REVOKED`/`EXPIRED`/`DECLINED`; 0 превышений лимита.

## 3. Архитектурное решение

Полное решение с альтернативами, последствиями и обратимостью — **ADR-008** (`docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-po-soglasiyu-platelshchika.md`). Суть:

1. Согласие — сущность первого класса со своим автоматом.
2. Рекуррентный дебит — вариант платежа (`paymentType=RECURRING`, `consentId`), реюз статусной машины платежа без `QR_ISSUED`/`EXPIRED`.
3. Двухрубежный контроль: локальный guard шлюза + авторитетный контроль ОПКЦ/банка плательщика.
4. Идемпотентность на всех новых поверхностях.
5. Расширение контракта адаптера (ядро ↔ транспорт) и API ТСП — обратно совместимо.

CALM-модель изменения — `docs/calm/recurring-c2b-consent.architecture.json` (узлы, интерфейсы, связи, потоки, контроли; провалидирована).

## 4. Изменения контрактов (без поломки потребителей)

### 4.1 Принцип совместимости

- Все добавления — **новые пути** и **опциональные поля**; существующие пути, схемы и статусная модель разовых платежей неизменны.
- Версия контракта API ТСП: `0.1.0 → 0.2.0` (минорная, аддитивная). Путь `/v1` не меняется.
- ТСП, не использующие рекуррентность, не обязаны обновляться; их запросы/ответы побайтово совместимы (новые поля — `optional`, не входят в `required`).

### 4.2 `openapi/tsp-api.yaml` (детали — в самом файле)

Новые пути:
- `POST /v1/consents` — создать запрос согласия (`Idempotency-Key` обязателен) → `201 Consent`.
- `GET /v1/consents/{consentId}` — статус согласия → `200 Consent`.
- `POST /v1/consents/{consentId}/revoke` — отзыв согласия (`Idempotency-Key`) → `200 Consent` (REVOKED/REVOKING).

Новые/изменённые схемы (аддитивно):
- `PaymentRequest` += `paymentType` (`ONE_TIME`|`RECURRING`, default `ONE_TIME`), `consentId` (обязателен только при `paymentType=RECURRING`).
- `Payment` += `paymentType`, `consentId`.
- Новые `ConsentRequest`, `Consent`.

### 4.3 `docs/contracts/tsp-api.md` (§8)

- Документированы методы согласий, семантика `paymentType`, новые коды ошибок (`CONSENT_NOT_ACTIVE`, `CONSENT_LIMIT_EXCEEDED`, `CONSENT_EXPIRED`, `CONSENT_NOT_FOUND`).
- Новые вебхуки: `consent.signed`, `consent.declined`, `consent.revoked`, `consent.expired` (рядом с существующими `payment.*`, `refund.*`).

### 4.4 `docs/contracts/opkc-adapter.md` (§10)

- Новые операции ядро→адаптер: `registerConsent`, `getConsentStatus`, `revokeConsent`, `initiateRecurringPayment`.
- Новые события адаптер→ядро: `consent.signed`, `consent.declined`, `consent.revoked`, `consent.expired`.
- Требование идемпотентности по `reference` распространяется на новые операции (пункт для RFP вендора).

## 5. Измеримые NFR нового функционала

Целевые значения — **критерии приёмки** (гейт A4/A5), проверяемы на тестовом контуре НСПК и моках.

| Метрика | Цель | Метод проверки |
|---|---|---|
| Latency создания согласия (`POST /v1/consents`) | p95 < 500 мс, p99 < 1 с (без учёта ОПКЦ) | Нагрузочный тест, APM |
| Latency инициации рекуррентного дебита | p95 < 1 с (без учёта ОПКЦ) | Нагрузочный тест |
| Переход согласия в `ACTIVE` от события ОПКЦ `consent.signed` | p95 < 5 с | Метрика лага очереди |
| Превышение лимита согласия дебитом | **0** (guard отклоняет до ОПКЦ) | Тест-кейсы + аудит; fitness AD-009 |
| Дебит по не-ACTIVE согласию (`REVOKED`/`EXPIRED`/`DECLINED`) | **0** | Fitness-тест на переходы |
| Двойное списание при повторах (ретраи/дубли событий) | **0** | Тест повторной доставки, идемпотентность |
| Распространение отзыва согласия (ревок → запрет новых дебитов) | p95 < 5 с; новых дебитов после отзыва — 0 | Тест отзыва + попытка дебита |
| Пиковая волна «день списания» (массовый дебит) | sustained 200 TPS, burst 500 TPS; очередь с бэкпрешшуром без потерь | Нагрузочный тест на 400 TPS + burst |
| Сверка согласий с ОПКЦ | ежедневная; расхождений по завершённым согласиям — 0 | Reconciliation-отчёт |
| Доступность контура согласий | ≥ 99,95 % (в составе шлюза) | SLO-отчёт |
| Аудит жизненного цикла согласия | 100 % переходов в неизменяемом логе | Аудит, SIEM |
| Минимизация ПДн согласия | хранится только необходимое для сверки; маскирование в логах | ИБ-ревью |

Базовые NFR шлюза (`docs/nfr.md`): доступность, RPO=0, RTO≤1 ч, сверка — **остаются в силе** и распространяются на согласия.

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (позитивные)

- [ ] Создание согласия → `PENDING_SIGN` → подписание плательщиком → событие `consent.signed` → `ACTIVE` → вебхук `consent.signed` ТСП.
- [ ] Рекуррентный дебит по `ACTIVE`-согласию в пределах лимита → `PAID` → `CREDITED` → `COMPLETED` → вебхук `payment.completed`.
- [ ] Повторный `POST /v1/consents` с тем же `Idempotency-Key` возвращает тот же `consentId` (не создаёт дубль).
- [ ] Повторный дебит с тем же `Idempotency-Key` возвращает тот же `paymentId`.
- [ ] Отзыв согласия → статус `REVOKED`, вебхук `consent.revoked`.

### 6.2 Критерии приёмки (негативные)

- [ ] Дебит по `REVOKED`/`EXPIRED`/`DECLINED` согласию → `409 CONSENT_NOT_ACTIVE` / `422 CONSENT_EXPIRED`, зачисление недостижимо.
- [ ] Дебит сверх остаточного лимита → `422 CONSENT_LIMIT_EXCEEDED` (до вызова ОПКЦ).
- [ ] Дублирование `eventId` (`consent.signed`, `payment.paid`) → состояние не меняется.
- [ ] ОПКЦ недоступен → дебит/согласие в очереди, не теряются, дозахватываются сверкой.
- [ ] Отзыв во время in-flight дебита → поведение детерминировано (см. §7, решение человека).

### 6.3 План отката

- **До боевой эксплуатации**: фича не включена — откат = не включать (решение reversible).
- **После включения**:
  1. Фиче-флаг `recurring.enabled=false` → **stop-new**: новые согласия и новые дебиты отклоняются (`403 RECURRING_DISABLED`), **разовые QR-платежи продолжают работать**.
  2. Откат релиза — rolling; ядро разовых платежей не затрагивается (изменения аддитивны).
  3. Данные не мигрируются обратно: записи согласий сохраняются для аудита и отчётности (юридическая значимость). «Откат» = запрет новых операций, а не удаление данных.
- **Сигналы триггера отката**: (а) частота превышений лимита > 0 (сбой guard); (б) расхождение сверки согласий с ОПКЦ > 0 по завершённым; (в) несоответствие модели согласия документации НСПК.
- **Владелец решения об откате**: solution-architect + владелец платёжного контура; эскалация на A3/архкомитет.

## 7. Что остаётся на решение человека-архитектора (и почему)

| # | Открытое решение | Почему не решается здесь |
|---|---|---|
| 1 | **Точная модель согласия по документации НСПК** (форма согласия, порядок подписания, где хранится оригинал, формат sign-ссылки/QR) | Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]` — получается по договору с НСПК; без него точные поля/тайминги неизвестны |
| 2 | **Семантика лимитов согласия** (максимум за дебит, суммарный лимит, частота) и кто их авторитетно считает | Продуктовое/регуляторное решение, зависит от НСПК и тарифной модели ТСП |
| 3 | **Каналы отзыва согласия**: только плательщик через свой банк, или также ТСП; нужно ли отдельное согласие на отзыв ТСП | Юридический вопрос прав плательщика/ТСП (161-ФЗ, правила НСПК) |
| 4 | **Поведение in-flight дебитов при отзыве/истечении** (довести начатый дебит до конца vs остановить) | Регуляторная грань; влияет на финансовую модель и диспуты |
| 5 | **Юридическая форма согласия и сроки хранения ПДн** (152-ФЗ) | Компетенция юристов + ИБ, не архитектора |
| 6 | **AML/антифрод-пороги для рекуррентных списаний** | Регуляторные лимиты (115-ФЗ), владелец — комплаенс |
| 7 | **UX подписания согласия плательщиком** (QR vs deep-link в приложение банка) | Продукт + НСПК; влияет на конверсию, не на ядро |
| 8 | **Изменение лимита согласия без повторного подписания** | Продуктовое решение о балансе UX и юридической силы |

Пункты 1–5 — **блокеры точного контракта**, но не блокеры проектирования ядра: модель согласия как сущности, guard, идемпотентность и расширение адаптера проектируются уже сейчас, а протокольные/юридические детали дозаполняются после получения документации НСПК (тот же паттерн, что и в базовом решении — контракт помечен `[ТРЕБУЕТ ПРОВЕРКИ]`).
