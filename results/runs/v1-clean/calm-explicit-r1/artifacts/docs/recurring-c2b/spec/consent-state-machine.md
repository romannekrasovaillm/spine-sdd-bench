# Статусная машина согласия (consent) — спецификация переходов

- Status: Draft (для ревью на гейте A1 пакета изменения)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, AD-002, AD-003, AD-009

Согласие плательщика на рекуррентные C2B-списания — **второй** (после платежа) единый источник истины шлюза. Дисциплина переходов — та же, что у платежа (ADR-002): **атомарная транзакция «смена статуса + outbox + аудит»**, повторные триггеры идемпотентны (AD-003).

## 1. Состояния

### Финансовые/видимые ТСП

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `REQUESTED` | Запрос согласия создан в шлюзе, регистрация в ОПКЦ в процессе | да |
| `PENDING_SIGN` | ОПКЦ принял запрос, выдана ссылка/QR на подписание; ждём подпись плательщика | да |
| `ACTIVE` | Плательщик подписал, согласие действует | да |
| `REVOKED` | Согласие отозвано (плательщиком или ТСП) | да (терминальное) |
| `EXPIRED` | Истёк срок действия / исчерпан суммарный лимит | да (терминальное) |
| `DECLINED` | Плательщик отказался подписывать | да (терминальное) |
| `SUSPENDED` | Приостановлено банком/AML (не терминальное) | да |

### Технические (наружу не выставляются)

| Состояние | Смысл |
|---|---|
| `OPKC_REGISTERING` | Регистрация в ОПКЦ инициирована, ждём `consentRef` (ретраи) |
| `REVOKING` | Отзыв инициирован, ждём подтверждения ОПКЦ |

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `REQUESTED` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `REQUESTED` | `PENDING_SIGN` | ответ адаптера ОПКЦ: `consentRef` + `signUrl/signQr` получены | `consentRef` непустой | сохранить `consentRef`, outbox-нотификация «создан» |
| C3 | `REQUESTED` | `DECLINED` | ошибка регистрации в ОПКЦ (не транзиентная) | — | `reasonCode`, outbox, вебхук `consent.declined` |
| C4 | `PENDING_SIGN` | `ACTIVE` | событие ОПКЦ `consent.signed` (или сверка) | подпись плательщика подтверждена | outbox-событие «согласие активно», вебхук `consent.signed` |
| C5 | `PENDING_SIGN` | `DECLINED` | событие ОПКЦ `consent.declined` | — | `reasonCode`, вебхук `consent.declined` |
| C6 | `PENDING_SIGN` | `EXPIRED` | таймер TTL подписания | `ACTIVE` не наступил | вебхук `consent.expired` |
| C7 | `ACTIVE` | `REVOKED` | `POST /v1/consents/{id}/revoke` или событие ОПКЦ `consent.revoked` | отзыв подтверждён ОПКЦ | outbox, вебхук `consent.revoked`; **запрет новых дебитов** |
| C8 | `ACTIVE` | `EXPIRED` | таймер срока действия / исчерпан суммарный лимит | — | вебхук `consent.expired` |
| C9 | `ACTIVE` | `SUSPENDED` | событие ОПКЦ/AML о приостановке | — | вебхук `consent.suspended`; дебиты отклоняются |
| C10 | `SUSPENDED` | `ACTIVE` | снятие приостановки (ОПКЦ/AML) | — | вебхук `consent.active` |
| C11 | `SUSPENDED` | `REVOKED` | отзыв во время приостановки | — | вебхук `consent.revoked` |

## 3. Запрещённые переходы (инварианты)

- **Рекуррентный дебит достижим только из `ACTIVE`** (AD-009). Из `REQUESTED`/`PENDING_SIGN`/`REVOKED`/`EXPIRED`/`DECLINED`/`SUSPENDED` — недостижим; fitness-тест.
- `REVOKED`/`EXPIRED`/`DECLINED` — терминальные: из них переходов нет (повторные триггеры идемпотентны).
- `ACTIVE` не может «откатиться» в `PENDING_SIGN` — подписанное согласие необратимо; корректировки — только отзыв и новое согласие.
- `ACTIVE → REVOKED` не отменяет уже инициированные (in-flight) дебиты: их судьба определяется политикой (см. открытый вопрос §4 решения человека).

## 4. Идемпотентность

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | тот же `consentId`, состояние не меняется |
| `POST /v1/consents/{id}/revoke` | `Idempotency-Key` | тот же результат, повторный отзыв — no-op |
| События ОПКЦ (`consent.signed` и др.) | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт |
| `initiateRecurringPayment` | `Idempotency-Key` / `paymentId` | повторный дебит с тем же ключом возвращает тот же `paymentId`, второго списания нет |

## 5. Связь «согласие → дебит» (guard)

- Перед `initiateRecurringPayment` шлюз проверяет: `consent.status == ACTIVE`, `amount <= remainingLimit`, дебит в пределах срока.
- `remainingLimit` пересчитывается атомарно при каждом дебите (в той же транзакции, что и создание дебита) — защита от гонки двух параллельных дебитов.
- Авторитетный контроль лимита — у ОПКЦ/банка плательщика; шлюз — первый рубеж + алерт при расхождении.

## 6. Сверка и восстановление

- Открытые состояния (`REQUESTED`, `PENDING_SIGN`, `REVOKING`) — кандидаты для сверки с ОПКЦ (ежедневная сверка согласий): «у ОПКЦ `ACTIVE`, у нас нет» → дозапрос статуса → C4; «у нас `ACTIVE`, у ОПКЦ нет/отозвано» → стоп-сигнал, эскалация.
- `REVOKING` без подтверждения — ретраи, затем DLQ + runbook; согласие видно в отчёте незавершённых операций.
