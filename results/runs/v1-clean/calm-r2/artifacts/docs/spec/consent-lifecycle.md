# Жизненный цикл согласия плательщика (consent) — спецификация

- Status: Draft (для ревью на гейте A1; ратифицируется вместе с ADR-008)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-004; AD-002, AD-009 (spine)

Согласие плательщика — **единый источник истины** для рекуррентных списаний (аналог AD-002 для платежа). Каждый переход — атомарная транзакция «смена статуса + outbox + аудит» (AD-002). Повторные триггеры идемпотентны (AD-003).

## 1. Состояния

| Состояние | Смысл | Списания разрешены | Виден ТСП |
|---|---|---|---|
| `PENDING` | Согласие запрошено, QR первого платежа выдан, ожидается подтверждение плательщика + первый платёж | нет | да |
| `ACTIVE` | Согласие подтверждено НСПК; плательщик согласился, первый платёж прошёл | **да** | да |
| `REVOKED` | Отозвано плательщиком (в банке) или ТСП | нет (терминальное) | да |
| `EXPIRED` | Истёк срок действия (`expiresAt`) | нет (терминальное) | да |
| `SUSPENDED` | Временно приостановлено (риск/AML/лимит) | нет (обратимо) | да |
| `FAILED` | Плательщик отклонил согласие / первый платёж не прошёл | нет (терминальное) | да |

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING` | `POST /v1/consents` (новый `consentId`) | ТСП активен, валидный запрос | запись согласия + outbox → адаптер `registerConsent` + QR первого платежа |
| C2 | `PENDING` | `ACTIVE` | событие `consent.activated` + первый платёж `PAID` | `consentId`/`eventId` не обработан | сохранить `firstPaymentId`, `consentOpcId`, outbox-вебхук `consent.activated` |
| C3 | `PENDING` | `FAILED` | событие `consent.rejected` (или первый платёж `FAILED`) | — | `reasonCode`, вебхук `consent.failed` |
| C4 | `ACTIVE` | `REVOKED` | `consent.revoked` (банк плательщика) или `POST /v1/consents/{id}/revoke` (ТСП) | — | outbox → адаптер `revokeConsent`, вебхук `consent.revoked`; блокировка списаний мгновенно |
| C5 | `ACTIVE` | `EXPIRED` | таймер `expiresAt` | — | закрытие согласия, вебхук `consent.expired` |
| C6 | `ACTIVE` | `SUSPENDED` | риск/AML/превышение лимитов | — | блокировка списаний, вебхук `consent.suspended`, алерт |
| C7 | `SUSPENDED` | `ACTIVE` | снятие риска/AML (решение) | — | восстановление, вебхук `consent.activated` |
| C8 | `SUSPENDED` | `REVOKED` | отзыв/эскалация | — | как C4 |

## 3. Инварианты (списания)

- **AD-009 (spine)**: рекуррентное списание возможно **только из `ACTIVE`**, с неистёкшим сроком, в пределах `maxAmountPerCharge` и лимита периода. `REVOKED`/`EXPIRED`/`FAILED` необратимо блокируют списания; `SUSPENDED` — временно.
- Инкремент лимитного счётчика периода — **в той же транзакции**, что и создание charge (AD-002); гонка двух списаний не даёт перерасхода.
- Отзыв вступает в силу **мгновенно внутри шлюза** (проверка статуса при валидации charge), до НСПК — ≤ 60 с.
- Повторная инициация согласия с тем же `consentId` — идемпотентна; повторный `POST /v1/consents` с тем же `Idempotency-Key` возвращает тот же `consentId`.

## 4. Сверка и восстановление

- `PENDING`/`ACTIVE`/`SUSPENDED` — кандидаты для сверки с НСПК (ADR-004): «у НСПК `ACTIVE`, у нас `PENDING`» → дозапрос статуса согласия (`getConsentStatus`) → C2.
- «У нас `ACTIVE`, у НСПК отозвано» → переход C4 (стоп-сигнал: расхождение источников).
- `ACTIVE`-согласие с недоступной НСПК: списание валидируется шлюзом локально, но исполняется только после доступности адаптера (очередь/DLQ); согласие не «забывается».

## 5. ПДн и аудит

- `payerRef` — токенизированная/маскированная ссылка на плательщика, минимизация (ADR-007); хранение — шифрование в покое, маскирование в логах.
- Каждый переход и каждое списание — в неизменяемом аудит-логе (AD-007); экспорт в SIEM.
- Доступ к согласиям — RBAC, доступ операторов — 4-eyes.
