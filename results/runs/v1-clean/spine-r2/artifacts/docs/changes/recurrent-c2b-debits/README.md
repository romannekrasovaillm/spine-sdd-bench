# Изменение: рекуррентные C2B-списания (автоплатежи/подписки СБП)

Пакет изменения поверх принятого решения «Платёжный шлюз СБП (C2B-приём)». Собран для вынесения на архитектурное решение (A3) и последующей передачи исполнителям.

- Артефакты решения: `docs/adr/ADR-008-…`, `ARCHITECTURE-SPINE.md` (AD-009), `docs/spec/mandate-state-machine.md`, `docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`, `docs/nfr.md` (§7).
- Статус: **Proposed** — ждёт решения A3 (ADR-008) и внешних входов НСПК/комплаенс.

## 1. Суть изменения

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят списывать с плательщика рекуррентно по предварительному согласию — подписки СБП. Сейчас каждый платёж требует QR и действия клиента. Вводим **согласие (consent/мандат)** как сущность первого класса и **рекуррентный платёж** как вариант существующего платежа, переиспользующий статусную машину без QR-состояний.

## 2. Оценка значимости и маршрут

Инструмент `significance_score`: **score = 7 → маршрут Critical**.

Сработавшие триггеры:

| Триггер | Почему |
|---|---|
| `financial_impact` | списание денег без действия плательщика в момент платежа |
| `api_contract_change` | новые эндпоинты `/v1/consents/*`, расширение `POST /v1/payments` |
| `data_contract_change` | новая сущность `consent`, поле `paymentType` |
| `consistency_model_change` | новая статусная машина согласия + инвариант «согласие ACTIVE ↔ списание» |
| `security_boundary_change` | согласие = новые ПДн (152-ФЗ) + канал отзыва согласия |
| `significant_nfr` | пики дат биллинга, дедупликация списаний за период |
| `cross_domain_integration` | отзыв согласия из НСПК/банка плательщика, AML |

**Почему Critical, а не Standard**: рекуррентное списание — самый рискованный класс C2B (несанкционированное/задвоенное списание). Требуется полный Solutioning: ADR + spine + NFR + обязательная человеческая точка A3 + walking skeleton до массовой генерации. Дельта-спеки (`delta-spec`) недостаточно.

## 3. Влияние на принятую архитектуру

| Инвариант | Статус | Что происходит |
|---|---|---|
| AD-001 (изоляция контура) | не меняется | согласие живёт в контуре шлюза — усиливает инвариант |
| AD-002 (источник истины — машина) | **расширяется** | добавляется машина согласия; атомарность «статус+outbox+аудит» распространяется на неё |
| AD-003 (идемпотентность) | **расширяется** | новые ключи: `(consentId, billingReference)`, `Idempotency-Key` для согласий |
| AD-004 (единственный адаптер ОПКЦ) | не меняется | адаптер получает аддитивные операции `registerMandate`/`createRecurringDebit`/`revokeMandate` |
| AD-005 (зачисление только из PAID) | **не меняется** | рекуррентное списание зачисляется так же, только из `PAID`; меняется триггер перехода в `PAID` |
| AD-006 (trust-зоны) | не меняется | согласие — новые ПДн, зоны прежние |
| AD-007 (НПС/КИИ/ПДн) | не меняется | расширяется поверхность ПДн (согласия), меры прежние |
| AD-008 (гибрид) | не меняется | ядро остаётся контрактно-независимым |
| **AD-009** | **новый** | «рекуррентное списание — только по активному согласию» |

**Не меняется**: модель зачисления (AD-005), outbox, сверка, АБС-адаптер, гибридная стратегия (AD-008), trust-зоны, одноразовый C2B-поток и его потребители.

## 4. Архитектурное решение (резюме ADR-008)

Согласие как сущность + рекуррентный платёж как `paymentType=recurring`. Полный текст с альтернативами, последствиями и обратимостью — `docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-soglasie-i-mandat.md`. Ключевые решения: охрана лимитов в той же транзакции, дедупликация `(consentId, billingReference)`, отзыв = немедленная блокировка, инициация списаний — со стороны ТСП (pull).

**A3-пакет (для человеческого решения):**

- **choice**: `consent-entity + payment-variant` — согласие первого класса + рекуррентный платёж как вариант платежа (переиспользование AD-002/AD-005).
- **rationale**: не ломает инвариант зачисления, минимальное новое состояние, согласие в контуре банка даёт гарантию «только по активному согласию».
- **constraints**: (1) списание только из `ACTIVE` (AD-009); (2) проверка лимитов атомарна с созданием платежа; (3) дедупликация по `(consentId, billingReference)`; (4) отзыв блокирует новые списания немедленно; (5) ядро контрактно-независимо от протокола НСПК (AD-008).
- **rejected options**: отдельный сервис «Подписки» (дорого, дублирует машину/сверку/АБС), расширение машины платежа (смешивает жизненные циклы), согласие на стороне ТСП (нарушает AD-001, невозможно гарантировать инвариант).
- **expiry**: пересмотр при получении документации НСПК (если мандат хранится только у НСПК и отзыв не приходит push) или изменении регулирования; плановая ревизия — через 12 мес.

## 5. Изменения контрактов (без поломки потребителей)

`docs/contracts/tsp-api.md` + `openapi/tsp-api.yaml` — **аддитивно**, версия остаётся `0.1.0`:

- `POST /v1/payments`: добавлены опциональные `paymentType` (default `one_time`), `consentId`, `billingReference`. Существующие запросы без этих полей работают как раньше → **не ломает**.
- Новые пути `/v1/consents`, `/v1/consents/{consentId}`, `/v1/consents/{consentId}/cancel` — новые, не затрагивают существующие.
- Новые события вебхуков `consent.*` и коды ошибок `CONSENT_*` — аддитивные.

Проверка: `openapi_lint` (см. §9). Breaking-изменений нет (удалённых путей/полей, сужений типов, новых обязательных полей в существующих запросах — нет).

## 6. NFR (резюме)

Полная таблица — `docs/nfr.md` §7. Ключевое: проверка лимитов p95 < 100 мс; 0 двойных списаний за период; 0 списаний по неактивному согласию; блокировка новых списаний ≤ 1 с от отзыва; пик биллинга 1000 TPS 1 мин без деградации одноразовых; ежесуточная сверка согласий с ОПКЦ.

## 7. Критерии приёмки (EARS)

- **When** ТСП инициирует рекуррентное списание с `consentId` и `billingReference`, **the шлюз shall** создать платёж `CREATED` только если согласие `ACTIVE` и сумма в лимитах.
- **When** согласие в `REVOKED/CANCELLED/EXPIRED/SUSPENDED`, **the шлюз shall** отклонить создание списания с `CONSENT_NOT_ACTIVE` (недостижимость — fitness-тест AD-009).
- **When** ТСП повторяет списание с тем же `(consentId, billingReference)`, **the шлюз shall** вернуть существующий `paymentId`, не создавая второе списание.
- **When** приходит событие `consent.revoked`, **the шлюз shall** перевести согласие в `REVOKED` и блокировать новые списания ≤ 1 с.
- **When** НСПК подтверждает списание (`debit.confirmed`), **the шлюз shall** перевести платёж в `PAID` и зачислить в АБС только из `PAID` (AD-005).
- **While** приём одноразовых платежей работает, **the изменение shall** не менять поведение существующих запросов `POST /v1/payments` без `paymentType` (обратная совместимость).
- **If** приходит повторная нотификация `debit.confirmed`, **then** переход идемпотентен по `eventId` (AD-003).

## 8. План отката

- **До боевой эксплуатации**: откат = не включать. Фиче-флаг `recurring_debits_enabled` (per TSP) — `off`.
- **После включения**: мгновенный `stop-new` — запрет создания новых согласий и списаний без остановки обработки уже созданных операций; откат релиза — rolling; данные не мигрируются обратно (согласия сохраняются, сверка доводит уже инициированные списания).
- **Аварийный сценарий**: DLQ → runbook; сверка согласий принудительно гасит списания по мандатам, отозванным в ОПКЦ, но `ACTIVE` в шлюзе.
- **Сигнал отката**: задвоенное списание; списание по отозванному согласию; расхождение сверки; превышение NFR по пику; AML/антифрод-алерт.
- **Владелец решения об откате**: платёжный контур (владелец) + дежурная смена (исполнение).

## 9. Readiness-вердикт

**VERDICT: CONCERNS** — можно в проектирование и walking skeleton (на моках НСПК/АБС), но НЕ в реализацию транспорта до снятия пробелов.

Пробелы (внешние входы, не блокируют дизайн ядра):

1. `[CONCERN]` Протокол рекуррентных списаний НСПК (формат мандата, идентификация плательщика, порядок отзыва) — `[ТРЕБУЕТ ПРОВЕРКИ]` → документация НСПК.
2. `[CONCERN]` Юридическая форма согласия и право отзыва (ГК, 161-ФЗ) → комплаенс/юристы.
3. `[CONCERN]` Пороги AML/антифрод для серийных списаний → риск-подразделение.
4. `[CONCERN]` UX отзыва согласия плательщиком (банковское приложение vs ТСП) → продукт.

## 10. Что остаётся на решение человека-архитектора и почему

1. **A3-выбор ADR-008** — подтвердить `choice`/`constraints`/`rejected options`/`expiry` (машинно-читаемо). Архитектор фиксирует, что рекуррентные списания не меняют AD-005 и живут на общем ядре.
2. **Юридическая форма согласия и отзыв** — не архитектурный вопрос (ГК/161-ФЗ/152-ФЗ), но влияет на контракт (`payerRef`, канал отзыва). Решает комплаенс.
3. **Порядок отзыва из НСПК (push vs опрос)** — определяется документацией НСПК; от этого зависит, нужна ли ежечасная сверка мандатов как основной механизм отзыва.
4. **Волна запуска** (рекуррент сразу или после стабилизации одноразовых) — приоритет бизнеса; влияет на walking skeleton, но не на архитектуру.
5. **Тарифы/комиссии** — влияют на отчётность, не на архитектуру ядра.
6. **AML-пороги** — серия списаний = риск, решает риск-подразделение.

Почему это остаётся человеку: это регуляторные/бизнес-решения с правовыми и финансовыми последствиями, которые архитектор не уполномочен принимать и которые нельзя вывести из инвариантов.
