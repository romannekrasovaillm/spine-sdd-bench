# Статусные машины согласия и рекуррентного списания — спецификация переходов

- Status: Draft (для ревью на гейте A1; связано с ADR-008)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002, ADR-008, AD-002, AD-003, AD-005, AD-009

Рекуррентные C2B-списания добавляют **две** конечные машины: машину согласия (жизненный цикл права списывать) и машину рекуррентного списания (переиспользует машину платежа ADR-002, пропуская QR-состояния). Обе — в БД шлюза; переходы атомарны «смена статуса + outbox + аудит» (AD-002).

## 1. Машина согласия (consent/мандат)

Источник истины права на рекуррентное списание. `consentId` — id шлюза; мандат в ОПКЦ регистрируется через адаптер (сквозной `reference`).

### 1.1 Состояния

| Состояние | Смысл | Списание разрешено |
|---|---|---|
| `PENDING` | Согласие создано, ожидает подтверждения (ОПКЦ/плательщик) | нет |
| `ACTIVE` | Согласие действует, лимиты установлены | **да** |
| `SUSPENDED` | Временно приостановлено (AML-hold, серия неудачных списаний) | нет |
| `EXPIRED` | Истёк `expiresAt` | нет (терминальное) |
| `CANCELLED` | Отменено ТСП (подписка завершена) | нет (терминальное) |
| `REVOKED` | Отозвано плательщиком / НСПК | нет (терминальное) |

### 1.2 Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен, лимиты заданы | запись согласия + outbox «регистрация мандата в ОПКЦ» |
| C2 | `PENDING` | `ACTIVE` | событие адаптера ОПКЦ `mandate.registered` | мандат подтверждён | outbox-нотификация ТСП `consent.activated` |
| C3 | `PENDING` | `CANCELLED` | отказ ОПКЦ / отмена ТСП до активации | — | `reasonCode`, outbox |
| C4 | `ACTIVE` | `SUSPENDED` | AML-hold / N последовательных неудачных списаний | политика риска | outbox; списания блокируются |
| C5 | `SUSPENDED` | `ACTIVE` | снятие hold | — | outbox |
| C6 | `ACTIVE` | `EXPIRED` | таймер `expiresAt` | — | outbox, вебхук `consent.expired` |
| C7 | `ACTIVE` | `CANCELLED` | ТСП: `POST /v1/consents/{id}/cancel` | — | outbox + отзыв мандата в ОПКЦ, вебхук `consent.cancelled` |
| C8 | `ACTIVE` → `REVOKED` | `REVOKED` | событие `consent.revoked` (плательщик/НСПК) или банк | — | **немедленная блокировка новых списаний**, outbox, вебхук `consent.revoked` |

### 1.3 Инварианты

- Рекуррентное списание достижимо **только из `ACTIVE`** (AD-009). Из `PENDING/SUSPENDED/EXPIRED/CANCELLED/REVOKED` — недостижимо (fitness-тест).
- `EXPIRED/CANCELLED/REVOKED` — терминальные: реактивация невозможна (новое согласие — новая сущность).
- `SUSPENDED → ACTIVE` — единственный обратимый переход.
- Лимиты (`maxAmount`, `maxAmountPerPeriod`, `period`, `expiresAt`) иммутабельны после `ACTIVE`; изменение лимитов = новое согласие (юридически чисто, избегает «тихого расширения права списывать»).

## 2. Машина рекуррентного списания (переиспользует машину платежа)

Рекуррентное списание — платёж с `paymentType=recurring` и ссылкой `consentId`. Проходит тот же путь `CREATED → PAID → CREDITED → COMPLETED`, **без** `QR_ISSUED`/`EXPIRED`.

### 2.1 Дополненные переходы (к таблице платежа ADR-002/`docs/spec/state-machine.md`)

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| R1 | — | `CREATED` | `POST /v1/payments` (`paymentType=recurring`, `consentId`) | согласие `ACTIVE`; сумма ≤ `maxAmount`; лимит за период не исчерпан; `billingReference` не дублируется | проверка лимитов **в той же транзакции** + запись платежа + outbox «списание в ОПКЦ» |
| R2 | `CREATED` | `PAID` | событие адаптера ОПКЦ `debit.confirmed` | сумма списания = сумме запроса | outbox «зачисление в АБС» (AD-005) |
| R3 | `CREATED` | `FAILED` | событие `debit.rejected` (недостаточно средств / согласие не найдено в ОПКЦ / лимит ОПКЦ) | — | `errorCode`, вебхук `payment.failed` |
| R4 | `PAID` → `CREDITED` → `COMPLETED` | — | как в базовой машине (T8/T10) | зачисление только из `PAID` | без изменений |

### 2.2 Отличия от одноразового платежа

- Нет `QR_ISSUED` и `EXPIRED` (нет QR и окна ожидания оплаты).
- Триггер `PAID` — подтверждение списания НСПК (`debit.confirmed`), а не нотификация оплаты QR.
- Обязательные поля: `consentId`, `billingReference`, `paymentType=recurring`.
- Зачисление в АБС — по-прежнему только из `PAID` (AD-005, ADR-005). Инвариант не меняется.

### 2.3 Идемпотентность (AD-003)

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/payments` (recurring) | `Idempotency-Key` **и** `(consentId, billingReference)` | повтор с тем же `billingReference` возвращает существующий `paymentId`, не создаёт новое списание |
| `POST /v1/consents` | `Idempotency-Key` | возвращает существующий `consentId` |
| `debit.confirmed` | `eventId` | повторная нотификация игнорируется (AD-004) |
| `consent.revoked` | `eventId` | повторный отзыв идемпотентен |

## 3. Сверка

- Сверка **согласий** с ОПКЦ: периодическая выверка мандатов (`ACTIVE` в шлюзе ↔ мандат в ОПКЦ); «у ОПКЦ отозван, у нас ACTIVE» → принудительный `REVOKED` + алерт (защита от списаний по отозванному в ОПКЦ мандату).
- Сверка **списаний** — как в базовой машине (ADR-004/005): `PAID` в шлюзе vs подтверждение ОПКЦ vs зачисление в АБС.
- Отчёт незавершённых операций включает рекуррентные платежи и согласия в нефинальных состояниях.

## 4. Согласованность с API ТСП

Наружу не выставляются технические подсостояния. Согласие видно ТСП как `PENDING | ACTIVE | SUSPENDED | EXPIRED | CANCELLED | REVOKED`; рекуррентный платёж — как `CREATED | PAID | CREDITED | COMPLETED | FAILED` (без `QR_ISSUED`/`EXPIRED`; они не применимы к recurring-ветке).
