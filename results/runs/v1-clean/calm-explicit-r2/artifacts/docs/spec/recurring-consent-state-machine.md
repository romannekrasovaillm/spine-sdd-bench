# Статусные машины согласия и рекуррентного списания — спецификация переходов

- Status: Draft (для ревью на гейте A1 рекуррентного инкремента)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-005; AD-002, AD-003, AD-005, AD-009

Дополняет `docs/spec/state-machine.md` (статусная машина платежа). Сущности `Consent` (согласие) и `Debit` (списание по согласию) — отдельные конечные автоматы в БД шлюза. Каждый переход — **атомарная транзакция** «смена статуса + outbox + аудит-лог» (AD-002); повторные триггеры идемпотентны (AD-003). Дебит переиспользует инвариант зачисления AD-005.

## 1. Согласие (Consent)

### 1.1 Состояния

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Согласие зарегистрировано в шлюзе, отправка в ОПКЦ в процессе | да |
| `PENDING_CONFIRMATION` | Отправлено в ОПКЦ, ждёт подтверждения плательщика в его банке | да |
| `ACTIVE` | Плательщик подтвердил; списания разрешены | да |
| `SUSPENDED` | Временно приостановлено (лимит исчерпан, пауза ТСП, риск-менеджмент) — обратимо | да |
| `REVOKED` | Отозвано плательщиком или ТСП — терминальное | да |
| `EXPIRED` | Истёк срок действия — терминальное | да |
| `REJECTED` | Плательщик отклонил согласие — терминальное | да |

### 1.2 Переходы

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `CREATED` | `POST /v1/consents` | валидный запрос, ТСП активен, лимиты заданы корректно | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `CREATED` | `PENDING_CONFIRMATION` | ответ адаптера ОПКЦ: согласие принято | — | outbox-событие «ожидание подтверждения» |
| C3 | `CREATED` | `FAILED` (→`REJECTED`) | ошибка регистрации в ОПКЦ (исчерпаны ретраи) | ошибка не транзиентная | `errorCode`, вебхук `consent.rejected` |
| C4 | `PENDING_CONFIRMATION` | `ACTIVE` | событие `consent.activated` | — | outbox-вебхук `consent.activated` |
| C5 | `PENDING_CONFIRMATION` | `REJECTED` | событие `consent.rejected` / таймаут подтверждения | — | вебхук `consent.rejected` |
| C6 | `ACTIVE` | `SUSPENDED` | лимит периода исчерпан / пауза ТСП / риск-флаг | — | вебхук `consent.suspended` (опц.), блок списаний |
| C7 | `SUSPENDED` | `ACTIVE` | снятие паузы / новый период лимита | — | вебхук `consent.activated` (возобновление) |
| C8 | `ACTIVE`/`SUSPENDED` | `REVOKED` | `POST /v1/consents/{id}/revoke` или событие `consent.revoked` (плательщик отозвал в своём банке) | — | вебхук `consent.revoked`, блок списаний |
| C9 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | таймер `expiresAt` | — | вебхук `consent.expired`, блок списаний |

### 1.3 Инварианты

- Списание возможно **только** из `ACTIVE` (AD-009). Из `CREATED`/`PENDING_CONFIRMATION`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`REJECTED` — недостижимо; fitness-тест.
- `REVOKED`/`EXPIRED`/`REJECTED` — терминальные: из них переходов нет; повторный `revoke` идемпотентен.
- Лимиты согласия иммутабельны после активации (изменение лимитов = новое согласие; `PATCH`-изменение лимитов — вне scope v0.2, см. открытые вопросы).
- Отзыв плательщиком (событие НСПК) и отзыв ТСП (API) сходятся в одно состояние `REVOKED` — гонка разрешается идемпотентностью по `consentId`.

## 2. Списание по согласию (Debit)

### 2.1 Состояния

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Списание зарегистрировано, проверка лимитов/согласия выполнена | да |
| `SUBMITTED` | Передано в ОПКЦ, ожидается исполнение | да |
| `PAID` | **Подтверждённый НСПК статус** исполнения списания | да |
| `CREDITED` | Зачисление на счёт ТСП в АБС выполнено | да |
| `COMPLETED` | Доведено до ТСП (вебхук) | да |
| `FAILED` | Отклонено ОПКЦ (недостаточно средств, согласие отозвано, сверх лимита) / таймаут | да |
| `REFUNDED` | Полный возврат по списанию завершён | да |

### 2.2 Переходы

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| D1 | — | `CREATED` | `POST /v1/consents/{consentId}/debits` | согласие `ACTIVE`, сумма ≤ `amountLimitPerDebit`, сумма успешных списаний периода + эта ≤ `amountLimitPerPeriod` | **атомарная** запись списания + резервирование лимита + outbox «submit в ОПКЦ» |
| D2 | `CREATED` | `SUBMITTED` | ответ адаптера ОПКЦ: списание принято | — | outbox, дебит ждёт исполнения |
| D3 | `CREATED` | `FAILED` | ошибка submit (ретраи исчерпаны) / нарушение лимита на момент submit | ошибка не транзиентная | `errorCode`, вебхук `debit.failed`, **освобождение резерва лимита** |
| D4 | `SUBMITTED` | `PAID` | событие `debit.paid` (или сверка) | сумма и получатель совпадают с согласием (иначе D6) | outbox-событие «зачисление в АБС» |
| D5 | `SUBMITTED` | `FAILED` | событие `debit.rejected` / таймаут без подтверждения | — | `errorCode`, вебхук `debit.failed`, освобождение резерва лимита |
| D6 | `SUBMITTED` | `FAILED` | расхождение суммы/получателя в событии `debit.paid` | ещё не `PAID` | **зачисление запрещено** (AD-005), алерт + runbook |
| D7 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`) | вызов АБС идемпотентен по `debitId` | сохранить `absDocId`, outbox «доставка ТСП» |
| D8 | `PAID` | (остаётся `PAID`) | АБС недоступна / ретраи | — | подсостояние `ABS_PENDING`, сверка; финансовый статус не меняется |
| D9 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен | — | вебхук `debit.completed` |
| D10 | `COMPLETED` | `REFUNDED` | сага возврата по списанию (АБС + НСПК) | полный возврат | вебхук `debit.refunded` |

### 2.3 Инварианты

- **Зачисление дебита — только из `PAID`** (расширение AD-005). Из `CREATED`/`SUBMITTED` недостижимо; fitness-тест.
- **Списание вне согласия/лимитов невозможно** (AD-009): guard D1 выполняется в той же транзакции, что и создание списания (оптимистичная блокировка строки согласия), иначе — гонка двух списаний превысит периодный лимит.
- `FAILED`/`REFUNDED` — терминальные; повторные события `debit.paid`/`debit.rejected` по завершённому дебиту идемпотентны (dedup по `eventId`/`reference`).
- Резерв лимита периода освобождается на `FAILED`/`REFUNDED`, чтобы не «съедать» лимит отклонёнными списаниями.

## 3. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | возврат того же `consentId`, состояние не меняется |
| `POST .../debits` | `Idempotency-Key` | возврат того же `debitId`, состояние не меняется |
| Событие `consent.activated`/`consent.revoked` | `eventId` | обработанный `eventId` игнорируется; новый по завершённому переходу — алерт |
| Событие `debit.paid`/`debit.rejected` | `eventId` + `reference` (`debitId`) | повтор игнорируется; состояние не меняется |
| Подтверждение АБС | `debitId` | повторное подтверждение не создаёт вторую проводку |

## 4. Сверка и восстановление

- Открытые состояния (`PENDING_CONFIRMATION`, `SUBMITTED`, `PAID`) — кандидаты сверки с НСПК (ежечасная) и АБС (суточная).
- «У НСПК согласие ACTIVE, у нас нет» → дозапрос `getConsentStatus` → C4.
- «У нас ACTIVE, у НСПК REVOKED» → C8 (стоп-сигнал, если расхождение не разрешается сверкой).
- «У НСПК debit PAID, у нас нет» → дозапрос `getDebitStatus` → D4.
- Списание в `PAID` с недоступной АБС остаётся `PAID`, видно в отчёте незавершённых операций, зачисление гарантируется сверкой.

## 5. Согласованность с API ТСП

Маппинг наружу (`docs/contracts/tsp-api-recurring.md`): `Consent.status` — `CREATED, PENDING_CONFIRMATION, ACTIVE, SUSPENDED, REVOKED, EXPIRED, REJECTED`; `Debit.status` — `CREATED, SUBMITTED, PAID, CREDITED, COMPLETED, FAILED, REFUNDED`. Технические подсостояния (`ABS_PENDING`) наружу не выставляются (аналог `state-machine.md` §6).
