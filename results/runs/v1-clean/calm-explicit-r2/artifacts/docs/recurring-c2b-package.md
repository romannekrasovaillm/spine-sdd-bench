# Архитектурный пакет: рекуррентные C2B-списания по согласию плательщика (подписки СБП)

- Status: Draft — на архитектурное решение (A3) и затем передачу исполнителям
- Date: 2026-09-28
- Owner: solution-architect (платёжный контур)
- Базовое решение: `docs/solutioning.md`, ADR-001…007, spine AD-001…008

Настоящий документ — сводный пакет изменения «подписки СБП» поверх принятого решения. Артефакты пакета перечислены в §8.

## 1. Оценка значимости и маршрут

**Значимость: Critical (11/15)** — та же категория, что у базового решения.

Почему:
- **Финансовое влияние**: неавторизованное или двойное списание, списание сверх лимита согласия — прямой денежный ущерб и регуляторный инцидент (161-ФЗ, НПС).
- **Новый долгоживущий объект с ПДн** (идентификатор плательщика): новое правовое основание обработки (152-ФЗ), расширение поверхности соответствия.
- **Затрагивает spine-инварианты**: расширяет AD-002/AD-003/AD-004/AD-005 и вводит новый AD-009 — а это принятая «реальность», которую нельзя менять неявно.
- **Затрагивает вендорский контракт** (RFP-скоп адаптера ОПКЦ) — влияет на закупку и сроки.

**Маршрут: полный Solutioning-трек** (новый ADR + спецификация автоматов + контракт + NFR + CALM), но **внутри существующего initiative** (не новый родительский spine). Глубина проектирования — высокая, потому что меняется модель состояний и контракты на границах (ТСП, АБС, ОПКЦ), а не только внутренняя реализация. При этом топология (ADR-001) и стратегия реализации (ADR-007/AD-008) **не пересматриваются** — дизайн ограничен дельтой.

### 2.2 Новый инвариант

**AD-009 (Proposed)** — «Рекуррентные списания только в рамках активного согласия с лимитами»: списание возможно только при `ACTIVE` и в пределах `amountLimitPerDebit`/`amountLimitPerPeriod`, проверка атомарна с созданием; зачисление дебита — только из `PAID`. Добавляется в `ARCHITECTURE-SPINE.md`.

### 2.3 Что остаётся без изменений

- Топология выделенного шлюза (ADR-001), транспорт/СКЗИ (ADR-003), стратегия гибрида (ADR-007/AD-008), trust-зоны (ADR-006).
- Платёжный путь с QR: `/v1/payments`, схема `Payment`, статусная машина платежа — не трогаются.
- Модель сверки (ежечасная НСПК / суточная АБС) — расширяется на consent/debit, но принцип и механизм прежние.

## 3. Архитектурное решение

Полное описание с альтернативами, последствиями и обратимостью — **ADR-008** (`docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-po-soglasiyu-platelshchika.md`). Кратко:

- **Две новые сущности** `Consent` + `Debit` (не переиспользование `Payment`), переиспользование outbox/идемпотентности/зачисления-из-PAID.
- **Merchant-initiated** инициация дебитов (ТСП), банковский планировщик — deferred.
- **Аддитивное расширение** API ТСП и вендорского контракта.
- **Reversibility: reversible** (фиче-флаг, изолированные таблицы).

## 5. Измеримые NFR

Добавлены в `docs/nfr.md` §7 «Подписки и рекуррентные списания». Ключевое: доступность ≥ 99,95 %, RPO=0, RTO ≤ 1 ч; создание согласия и списания p95 < 500 мс; «событие НСПК → статус» p95 < 5 с; «подтверждение списания → зачисление в АБС» p95 < 60 с; **0 списаний сверх лимитов**, **0 двойных списаний**; burst до 1000 TPS на 1 мин в пик биллинга.

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (проверяемы тестом/командой)

Позитивные:
- AC-1 (сквозной счастливый путь): `POST /consents` → `PENDING_CONFIRMATION` → (событие `consent.activated`) → `ACTIVE` → `POST .../debits` → `SUBMITTED` → `PAID` → `CREDITED` → `COMPLETED` → вебхук `debit.completed`. Проверка: E2E-тест на мок-адаптере ОПКЦ/АБС.
- AC-2 (лимиты): списание ≤ `amountLimitPerDebit` и в пределах `amountLimitPerPeriod` проходит; сверх лимита — `422 CONSENT_LIMIT_EXCEEDED`. Проверка: тест границ лимита.

Негативные:
- AC-3 (списание вне согласия): `POST .../debits` при согласии `PENDING_CONFIRMATION`/`REVOKED`/`EXPIRED`/`SUSPENDED` → `422 CONSENT_NOT_ACTIVE`/`CONSENT_REVOKED`/`CONSENT_EXPIRED`; списание не создаётся.
- AC-4 (двойное списание): повторный `POST .../debits` с тем же `Idempotency-Key` → тот же `debitId`, вторая операция не создаётся; повтор события `debit.paid` с тем же `eventId` → состояние не меняется. Цель: **0 двойных списаний**.
- AC-5 (гонка лимита): два параллельных списания, суммарно превышающих `amountLimitPerPeriod` → проходит только одно, второе `422` (атомарный guard AD-009). Проверка: конкурентный тест.
- AC-6 (отказ ОПКЦ): недоступность адаптера → дебит не теряется (outbox + сверка `getDebitStatus` находит `PAID`); зачисление гарантируется после восстановления. Проверка: chaos-тест.
- AC-7 (зачисление только из PAID): fitness-тест недостижимости `CREDITED` из `CREATED`/`SUBMITTED`.
- AC-8 (ПДн): наружу только `payerRefMasked`; `payerRef` не логируется в открытом виде. Проверка: ИБ-ревью + тест маскирования.

### 6.2 План отката

- **До боевой эксплуатации**: откат = не включать фиче-флаг; все работы обратимы.
- **После включения**: фиче-флаг на приём новых согласий и списаний; `stop-new` — запрет регистрации новых согласий и новых дебитов **без** остановки обработки уже созданных списаний (дозавершаются по сверке). Откат релиза — rolling, без даунтайма.
- **Данные**: новые таблицы `consents`/`debits` не мигрируются обратно; при откате флага данные сохраняются для сверки/аудита (шлюз остаётся источником истины до полной сверки с АБС).
- **Сигнал отката**: рост двойных списаний > 0, превышение лимитов > 0, сверхлимитное расхождение сверки, алерт DLQ. Владелец решения — solution-architect + риск-менеджер платёжного контура.
- **Аварийный сценарий**: DLQ → дежурная смена по runbook; сверка компенсирует потерянные нотификации; RTO ≤ 1 ч.

## 7. Что остаётся на решение человека-архитектора (и почему)

1. **Состав первой волны**: только `subscription` (рекуррент) или сразу `on_demand` (one-click/разовое списание без QR). *Почему*: разные регуляторные и продуктовые сценарии, влияет на скоуп АБС/НСПК и сроки.
2. **Политика лимитов согласия по умолчанию** (максимумы, периоды) и их привязка к антифрод/AML-порогам. *Почему*: рекуррентные списания — повышенный риск неавторизованных списаний; требует решения риск-менеджмента, не архитектуры.
3. **Идентификатор плательщика** (`payerRef`: телефон vs маскированный счёт) и правовое основание обработки. *Почему*: ПДн + 152-ФЗ, решает комплаенс/юристы.
4. **Вендорский скоп по consent/debit** в RFP (подтвердить, что выбранный вендор реализует согласие на списание). *Почему*: внешняя зависимость сроков и G3/G4-критериев; решает проектный офис/закупки.
5. **Точный протокол НСПК по согласию** (поля, тайминги, подтверждение) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`. *Почему*: без документации НСПК контракт нельзя финализировать.
6. **Merchant-initiated vs банковский планировщик** как долгосрочная продуктовая опция. *Почему*: ответственность за биллинговый цикл — бизнес-решение, архитектурно оба варианта совместимы (планировщик — аддитивно).
