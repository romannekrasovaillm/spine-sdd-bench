# ADR-008. Рекуррентные C2B-списания по согласию плательщика (подписки СБП)

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + продукт (подписки)
- Related: ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-006, ADR-007; AD-001…AD-009 (spine); `docs/contracts/tsp-api-recurring.md`, `docs/spec/recurring-consent-state-machine.md`, `docs/nfr.md`

## Context

Бизнес-запрос: ТСП (онлайн-кинотеатры, ЖКХ, операторы связи) просят **рекуррентные C2B-списания** — подписки СБП, когда плательщик один раз даёт согласие, а дальше списания происходят без QR и без действия клиента на каждый платёж. Сейчас в scope только C2B-приём с QR (см. `docs/solutioning.md` §1: «автоплатежи — вне scope», roadmap).

Механизм СБП: **согласие на списание** (consent / автоплатёж). Плательщик в своём банковском приложении подтверждает согласие ТСП на списания с лимитами (максимум одного списания, максимум за период, срок действия). После активации согласия ТСП инициирует списания в рамках лимитов без повторного подтверждения плательщика. Точные поля и тайминги протокола НСПК по согласию — **внешний вход, помечено `[ТРЕБУЕТ ПРОВЕРКИ]`** до получения документации НСПК.

Силы: финансовое влияние (двойное/неавторизованное списание недопустимо); согласие — долгоживущий объект с ПДн (идентификатор плательщика), новое правовое основание обработки (152-ФЗ, 161-ФЗ); риск «списаний из воздуха» без согласия или сверх лимитов; необходимость сохранить все spine-инварианты принятого решения.

## Decision

Расширяем принятый СБП-шлюз (ADR-001) **новой бизнес-способностью поверх существующей архитектуры**, не меняя топологию и стратегию реализации:

1. **Две новые сущности в ядре шлюза**:
   - **Consent (Согласие)** — долгоживущий объект согласия плательщика: лимиты (`amountLimitPerDebit`, `amountLimitPerPeriod`, `period`), тип (`subscription` — рекуррентный / `on_demand` — разовое списание без QR), срок действия, статус. Жизненный цикл: `CREATED → PENDING_CONFIRMATION → ACTIVE → (REVOKED | EXPIRED)`, с `ACTIVE ⇄ SUSPENDED` (обратимо) и `PENDING_CONFIRMATION → REJECTED`.
   - **Debit (Списание по согласию)** — каждый отдельный платёж под согласием. Жизненный цикл: `CREATED → SUBMITTED → PAID → CREDITED → COMPLETED`, терминальные `FAILED`, `REFUNDED`. **Зачисление дебита — только из `PAID`** (подтверждённый НСПК статус списания), что буквально расширяет AD-005 на новую сущность.
2. **Новый инвариант AD-009 (spine)**: списание по согласию возможно только при статусе согласия `ACTIVE` и в пределах лимитов; проверка **атомарна** с созданием списания (оптимистичная блокировка/ограничение БД) — исключает гонку «два параллельных списания превысили периодный лимит».
3. **Переиспользуем без изменений**: транзакционный outbox (ADR-001/AD-002), идемпотентность (AD-003, новые ключи `consentId`/debit `reference`), единственный адаптер ОПКЦ (AD-004), зачисление только из подтверждённого статуса (AD-005), trust-зоны и соответствие (AD-006/AD-007), стратегию гибрида (AD-008).
4. **Расширение внутреннего контракта адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`): новые синхронные методы `registerConsent`, `revokeConsent`, `createDebit`, `getConsentStatus`, `getDebitStatus` и события `consent.activated/rejected/revoked/expired`, `debit.paid/rejected`. Протокол НСПК по-прежнему знает только адаптер; ядро оперирует нормализованными статусами.
5. **Модель инициации — merchant-initiated**: дебиты инициирует ТСП по своему биллинговому циклу (`POST /v1/consents/{consentId}/debits`). Банковский планировщик (шлюз сам шлёт дебиты по расписанию) — отложен как отдельная опция (см. Alternatives).
6. **Контракт API ТСП расширяется аддитивно** (`/v1`, без ломающих изменений): согласия и дебиты — отдельные ресурсы, существующие `/v1/payments` и схема `Payment` не меняются (см. `docs/contracts/tsp-api-recurring.md` и `openapi/tsp-api.yaml` v0.2.0).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Отдельные сущности Consent + Debit (выбран)** | Чистая граница лимитов/жизненного цикла согласия; дебит переиспользует зачисление из PAID; ноль изменений существующего `Payment` и его API | Две новые таблицы и два автомата; сверка покрывает два типа операций |
| Переиспользовать `Payment` с дискриминатором `paymentType=consent_debit` (без отдельной сущности) | Один автомат, одна таблица, одна сверка | Нужно менять enum `Payment.status` (риск для существующих потребителей); лимиты согласия «прилипают» к платежу; `QR_ISSUED`/`EXPIRED` нерелевантны дебиту |
| Планировщик на стороне шлюза (банк шлёт дебиты по расписанию) | ТСП не нужен собственный планировщик; банк контролирует списания | Дублирует биллинг ТСП; ответственность за «когда списывать» у банка; конфликт расписаний; выше операционный риск. **Deferred**: как опция продукта после стабилизации merchant-initiated |
| Списывать «без согласия» (просто платёж без QR по сохранённым реквизитам) | Минимум новых сущностей | Нет лимитов и отзыва — регуляторный и репутационный риск; НСПК требует согласие как правовую основу автоплатежа |
| Хранить согласия в АБС | Один источник для расчётов | АБС не имеет понятия «согласие СБП»; нарушение AD-001 (изоляция финансовой логики); ПДн в legacy-системе |

## Consequences

### Positive

- Регуляторно корректно: списание только по активному согласию, в лимитах, с полным аудитом каждого перехода (161-ФЗ, 152-ФЗ).
- Ноль изменений существующего платёжного пути и API ТСП — подписки включаются независимо, фиче-флагом.
- Зачисление дебита переиспользует инвариант AD-005 — «платежей/списаний из воздуха» нет.
- Merchant-initiated снимает с банка ответственность за биллинговый цикл ТСП.

### Negative

- Две новые сущности и два конечных автомата — рост сложности статусной модели и сверки (сверка теперь по payments, consents, debits).
- Согласие — долгоживущие ПДн плательщика: минимизация, маскирование, шифрование в покое, retention по 152-ФЗ (расширение поверхности AD-006/AD-007).
- Расширение вендорского контракта адаптера: RFP-критерии (G3 идемпотентность, G4 полнота методов) должны охватить consent/debit-операции — потенциальное удорожание/задержка закупки (но граница гибрида AD-008 не меняется).
- Рекуррентные списания создают пики нагрузки в даты массового биллинга (1-е число месяца) — нужен запас burst-производительности (см. NFR §7).

## Reversibility

**reversible.** Подписки — аддитивная способность на отдельных сущностях и отдельных endpoint'ах:
- До боевой эксплуатации — не включается, все работы обратимы.
- После включения — фиче-флаг отключает приём новых согласий/списаний; уже активные согласия доживают до отзыва/истечения либо закрываются ручной компенсацией (4-eyes).
- Новые таблицы (consents, debits) не мигрируются обратно в существующие (payments) — они изолированы; откат = отключение флага + остановка обработки дебитов, данные сохраняются для сверки/аудита.
- Замена merchant-initiated на банковский планировщик — отдельное аддитивное решение, не ломает текущее.
