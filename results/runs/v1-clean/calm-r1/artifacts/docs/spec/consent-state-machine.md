# Статусная машина согласия (consent) — спецификация переходов

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-005, AD-009 (spine), AD-002, AD-003

Согласие — второй источник истины в БД шлюза (наряду с платёжной машиной). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003). Рекуррентное списание (дебет) повторно использует платёжную машину (`docs/spec/state-machine.md`) с `paymentType=RECURRENT` и **не входит** в `QR_ISSUED`.

## 1. Состояния согласия

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CONSENT_CREATED` | Согласие зарегистрировано, ожидает подтверждения плательщика | да |
| `CONSENT_ACTIVE` | Плательщик подтвердил; списания разрешены | да |
| `CONSENT_SUSPENDED` | Техническая приостановка (лимит/политика/временный запрет); обратима | да |
| `CONSENT_REVOKED` | Отозван плательщиком или ТСП — терминальный | да |
| `CONSENT_EXPIRED` | Истёк срок действия — терминальный | да |
| `CONSENT_FAILED` | Регистрация отклонена ОПКЦ/банком плательщика — терминальный | да |

## 2. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| C1 | — | `CONSENT_CREATED` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен, лимиты заданы | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `CONSENT_CREATED` | `CONSENT_ACTIVE` | событие адаптера `consent.activated` | плательщик подтвердил (у ОПКЦ/банка плательщика) | outbox-нотификация `consent.activated` ТСП |
| C3 | `CONSENT_CREATED` | `CONSENT_FAILED` | событие `consent.rejected` / ошибка регистрации (исчерпаны ретраи) | отказ не транзиентный | `reasonCode`, вебхук `consent.failed` |
| C4 | `CONSENT_ACTIVE` | `CONSENT_REVOKED` | отзыв плательщиком (событие `consent.revoked`) или `POST /v1/consents/{id}/revoke` (ТСП) | — | **стоп для всех открытых списаний**, вебхук `consent.revoked` |
| C5 | `CONSENT_ACTIVE` | `CONSENT_EXPIRED` | достигнут `validUntil` (таймер) | нет открытых списаний | вебхук `consent.expired` |
| C6 | `CONSENT_ACTIVE` | `CONSENT_SUSPENDED` | технический сигнал (лимит, недоступность канала) | — | приостановка новых списаний; вебхук `consent.suspended` |
| C7 | `CONSENT_SUSPENDED` | `CONSENT_ACTIVE` | восстановление (технический сигнал) | `validUntil` не наступил | возобновление списаний; вебхук `consent.activated` |
| C8 | `CONSENT_SUSPENDED` | `CONSENT_REVOKED` / `CONSENT_EXPIRED` | как C4/C5 | — | как C4/C5 |

## 3. Запрещённые переходы (инварианты)

- **Списание недостижимо из любого состояния, кроме `CONSENT_ACTIVE`** (AD-009). Из `CONSENT_REVOKED`/`CONSENT_EXPIRED`/`CONSENT_SUSPENDED`/`CONSENT_FAILED` — недостижимо; проверяется fitness-тестом.
- `CONSENT_REVOKED`/`CONSENT_EXPIRED`/`CONSENT_FAILED` — терминальные: из них переходов нет.
- Сумма и реквизиты согласия (лимиты, период, `validUntil`) **иммутабельны** после `CONSENT_ACTIVE`; изменение условий — только новое согласие (новый `consentId`), не мутация существующего.
- `CONSENT_ACTIVE` не может «откатиться» в `CONSENT_CREATED`.
- Отзыв плательщика имеет приоритет над любым последующим сигналом: повторная нотификация о списании после `CONSENT_REVOKED` игнорируется и алертит (аналог ADR-004).

## 4. Взаимодействие с платёжной машиной (дебет)

- Дебет создаётся только из `CONSENT_ACTIVE`: `POST /v1/consents/{consentId}/debits` → платёж `CREATED` (`paymentType=RECURRENT`, `consentId`), шаг регистрации QR **заменяется** на инициацию списания в ОПКЦ.
- Guard при инициации: `amount ≤ maxPerDebit`, суммарно по активному согласию `sum(debits) + amount ≤ maxTotal` (если задан), `now ∈ [validFrom, validUntil)`.
- Дебет далее идёт по платёжной машине: `CREATED → PAID (подтверждён ОПКЦ) → CREDITED (АБС) → COMPLETED`; зачисление — **только из `PAID`** (AD-005 неизменен).
- Отказ списания (`debit.rejected`) → платёж `FAILED`; согласие при этом остаётся `CONSENT_ACTIVE` (отказ разового списания ≠ отзыв согласия), если не исчерпан лимит/политика → тогда `CONSENT_SUSPENDED`.

## 5. Идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | возврат того же `consentId`, состояние не меняется |
| `POST /v1/consents/{id}/debits` | `Idempotency-Key` | возврат того же `paymentId`, повторное списание не создаётся |
| Событие `consent.*` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт |
| Операция адаптера `registerConsent`/`initiateDebit` | `reference` | повторный вызов не создаёт дубль в ОПКЦ (обязанность адаптера, ADR-003) |

## 6. Сверка и восстановление

- Открытые состояния (`CONSENT_CREATED`, `CONSENT_ACTIVE`, `CONSENT_SUSPENDED`) — кандидаты для сверки с НСПК (ежедневно, по запросу).
- «У НСПК `REVOKED`, у нас `ACTIVE`» → стоп-сигнал, немедленный переход в `CONSENT_REVOKED`, эскалация (списание после отзыва недопустимо).
- «У нас `ACTIVE`, у НСПК нет согласия» → дозапрос статуса; при расхождении — алерт.
- Открытое списание при переходе согласия в `CONSENT_REVOKED`/`CONSENT_EXPIRED` → списание отменяется/не исполняется; если уже `PAID` — завершается зачислением (уже подтверждённый финансовый факт не отменяется, корректировка — возвратом).

## 7. Согласованность с API ТСП

Маппинг статусов наружу: `CONSENT_CREATED`, `CONSENT_ACTIVE`, `CONSENT_SUSPENDED`, `CONSENT_REVOKED`, `CONSENT_EXPIRED`, `CONSENT_FAILED` — без внутренних подсостояний. Поле `consentUrl` присутствует только пока `CONSENT_CREATED` (ссылка на подтверждение в банке плательщика).
