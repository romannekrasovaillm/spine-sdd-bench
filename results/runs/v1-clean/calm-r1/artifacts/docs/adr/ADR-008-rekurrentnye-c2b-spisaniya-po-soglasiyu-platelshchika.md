# ADR-008. Рекуррентные C2B-списания по согласию плательщика (СБП-подписки)

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + бизнес (продукт «подписки»)
- Related: ADR-002, ADR-003, ADR-004, ADR-005, ADR-007, AD-009 (spine, новый)

## Оценка значимости и маршрута

Значимость изменения: **высокая (9/15), маршрут Critical-feature** поверх родительской инициативы C2B-приёма (Critical, 11/15).

Почему это не «мелкая фича», а полноценное архитектурное решение:

1. **Новая финансовая сущность — согласие (consent/mandate).** У шлюза появляется второй источник истины со своим жизненным циклом, отличным от платёжного. Это не новый статус платежа, а новый тип объекта с собственными инвариантами (нельзя списывать после отзыва).
2. **Новый вид отказа с прямым финансовым и регуляторным ущербом.** Двойное списание абонента или списание после отзыва согласия — это возврат средств, диспут и нарушение прав плательщика (152-ФЗ, 161-ФЗ). Требует идемпотентности и guard-условий уровня AD-005.
3. **Сквозное влияние на контракты.** Меняется контракт API ТСП (`openapi/tsp-api.yaml`) и внутренний контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md`), а значит и RFP-пакет вендора транспорта (ADR-007 — гибрид).
4. **Внешний вход не закрыт.** Точный протокол рекуррентных операций НСПК публично не раскрыт — `[ТРЕБУЕТ ПРОВЕРКИ]` (документация по договору). Проектируем на уровне шлюза/контракта, протокол скрыт за адаптером (AD-008).
5. **Смена профиля нагрузки.** Подписки дают batch-волны (ЖКХ/связь — начало месяца), а не равномерный поток QR. Влияет на NFR производительности.

Маршрут: **полное решение (ADR + solutioning + расширение spine + расширение контрактов + NFR)**, гейт A3 (человеческое решение по модели согласия) — **обязательно до реализации транспорта**, как в ADR-007.

## Context

ТСП (онлайн-кинотеатры, ЖКХ, операторы связи) требуют рекуррентных C2B-списаний: плательщик один раз даёт согласие на периодические списания, дальше платежи идут без QR и без действия клиента. Сейчас каждый платёж требует генерации QR и активного подтверждения плательщика — это блокирует подписочную бизнес-модель.

Механизм в СБП: согласие регистрируется один раз с явным подтверждением плательщика в приложении его банка; затем ТСП через банк-эквайер (наш шлюз) инициирует списания под этим согласием, а банк плательщика исполняет их без повторного подтверждения в рамках лимитов и срока действия согласия. Точный протокол НСПК (роли, токены, поля лимитов, тайминги) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.

Ограничения и силы:

- Списание — финансовое действие; дубли и списание после отзыва недопустимы (AD-003, AD-005).
- Согласие — ПДн + волеизъявление плательщика: хранение, отзыв, сроки регулируются (152-ФЗ, 161-ФЗ, AD-007).
- Ядро шлюза контрактно-независимо от транспорта (AD-008); транспорт — вендорский адаптер (ADR-007).
- Существующие потребители API ТСП (v0.1) не должны ломаться — расширение обратно совместимо (контракт §6).

## Decision

1. **Вводим сущность «Согласие» (Consent)** — второй источник истины в БД шлюза, со своей статусной машиной (см. `docs/spec/consent-state-machine.md`):
   `CONSENT_CREATED → CONSENT_ACTIVE`, терминальные `CONSENT_REVOKED` (отозван плательщиком/ТСП), `CONSENT_EXPIRED` (истёк срок), `CONSENT_FAILED` (отказ при регистрации), плюс `CONSENT_SUSPENDED` (техническая приостановка, обратимая).
2. **Рекуррентное списание — тот же платёж, а не отдельная сущность.** Расширяем платёжную модель дискриминатором `paymentType` (`ONE_OFF | RECURRENT`) и опциональной ссылкой `consentId`. Рекуррентное списание повторно использует статусную машину платежа (`CREATED → PAID → CREDITED → COMPLETED`, терминальные `FAILED`), но **не входит** в состояние `QR_ISSUED`: шаг «регистрация QR» заменяется на «инициация списания под согласием». Это сохраняет AD-002 (единая машина) и AD-005 (зачисление только из `PAID`) без изменений.
3. **Новый spine-инвариант AD-009**: списание инициируется/исполняется **только** из `CONSENT_ACTIVE`, сумма — в пределах лимитов согласия; повторная доставка запроса/нотификации не создаёт второго списания.
4. **Идемпотентность расширяется на согласия и списания**: `Idempotency-Key` на `POST /v1/consents` и `POST /v1/consents/{consentId}/debits`; `eventId` — на события согласия; `reference` — на операции адаптера ОПКЦ. Повторная инициация списания возвращает тот же `paymentId` (AD-003).
5. **Согласованность и сверка**: переходы согласия атомарны (статус + outbox + аудит, AD-002); отзыв/истечение согласия — стоп-событие для всех открытых списаний; ежедневная сверка согласий и списаний с НСПК (AD-004).
6. **Контракты** расширяются обратно совместимо: API ТСП (новые методы `/v1/consents/*` + опциональные поля платежа) и адаптер ОПКЦ (операции `registerConsent`/`revokeConsent`/`initiateDebit`/`getConsentStatus`, события `consent.*`/`debit.*`). Вендорский адаптер (ADR-007) обязан поддержать рекуррентные операции — это расширяет RFP (см. `docs/rfp/vendor-rfp.md`).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Расширить платёжную машину `paymentType` (выбран)** | Одна статусная машина, AD-005/AD-002 без изменений; повторное использование сверки/нотификатора/аудита; минимальный дифф | Нужен guard «рекуррентный платёж не входит в `QR_ISSUED`»; оплата и списание смешаны в одном API |
| Отдельная сущность «списание» со своей машиной | Чистое разделение семантики | Дублирует AD-002/AD-003/AD-005 (зачисление, идемпотентность, сверка); удваивает поверхность кода и тестов; два платёжных источника истины — риск расхождений |
| Хранить согласия только в НСПК, в шлюзе — кэш | Нет второго источника истины в шлюзе | Шлюз теряет локальную гарантию RPO=0 и идемпотентность; каждая проверка лимита — внешний вызов (латентность, доступность); противоречит AD-001/AD-002 |
| «Подписка как очередь отложенных QR» | Переиспользование QR-потока без нового API | QR требует действия плательщика каждый раз — не решает задачу; не является подпиской |

## Consequences

### Positive

- Платёжная подписка достигается без изменения ядра статусной модели платежа и без правки уже ратифицированных AD-002/AD-005.
- Обратная совместимость: существующие ТСП (one-off) продолжают работать без изменений.
- Идемпотентность и сверка распространяются на согласия по уже построенным механизмам (outbox, DLQ, eventId).

### Negative

- Второй источник истины (согласие) — рост сложности эксплуатации и сверки (два набора состояний и два набора неоконченных операций).
- Guard «списание только из `CONSENT_ACTIVE`» — новый инвариант, обязателен к fitness-тесту (как AD-005), иначе — финансовый/регуляторный инцидент.
- Зависимость от внешнего протокола НСПК по рекуррентным операциям (не закрыт до документации) и от поддержки вендорским адаптером (расширение RFP/контракта).
- Batch-волны списаний меняют профиль нагрузки (нужен отдельный NFR на burst).

### Positive/negative for compliance

- Согласие = волеизъявление + ПДн: обязательны явная фиксация согласия, отзыв в один шаг, срок хранения, аудит (152-ФЗ, 161-ФЗ). Это укладывается в AD-007, но требует отдельного ИБ-ревью на A4.

## Reversibility

**reversible на уровне фичи, costly после боевых списаний.**

- До боевой эксплуатации: фича изолирована feature-флагом, отключается без влияния на one-off платежи.
- После старта: stop-new (запрет новых списаний и новых согласий) — мгновенный; уже исполненные списания — обычные платежи, откатываются только возвратом (сага ADR-005). Записи согласий — ПДн с обязательствами по хранению, «просто удалить» нельзя (требуется политика хранения/обезличивания). Смена модели «расширение платёжной машины» на «отдельная сущность» — costly, как и смена модели согласия после ратификации.
