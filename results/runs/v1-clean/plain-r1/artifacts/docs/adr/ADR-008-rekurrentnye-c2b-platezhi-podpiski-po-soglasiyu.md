# ADR-008. Рекуррентные C2B-платежи СБП: подписки по согласию плательщика

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур)
- Related: ADR-001, ADR-002, ADR-004, ADR-005, ADR-007; spine AD-001..AD-008, AD-009..AD-011

## Context

### Бизнес-потребность

ТСП — онлайн-кинотеатры (ежемесячные подписки), ЖКХ (регулярные коммунальные платежи), операторы связи (абонентская плата) — просят **рекуррентные C2B-списания по согласию плательщика** («подписки СБП»). Сейчас каждый платёж требует генерации QR и активного действия клиента в своём банке; для периодических платежей это неприемлемо: высокий отток при продлении, ручные напоминания, невозможность автоматического списания.

Рекуррентный платёж в СБП устроен иначе, чем разовый C2B: плательщик **однократно** даёт согласие на серию списаний (с ограничениями по сумме и частоте), после чего ТСП инициирует списания без участия плательщика в каждой операции. Плательщик может отозвать согласие в любой момент. Точный протокол НСПК для автоплатежей — внешний вход, публично не раскрыт; все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]` (как и базовый C2B-протокол, ADR-003).

### Значимость и маршрут

- **Маршрут: Major — значимость 10/15** (в шкале базового решения «Critical 11/15»). Обоснование:
  - новый финансовый продукт и новая доменная сущность **согласие (consent/mandate)** — не переиспользуется из базового решения;
  - повышенная регуляторная чувствительность: неавторизованное либо превышающее лимит списание = прямой имущественный вред плательщику; затрагивает 161-ФЗ, Положение ЦБ о защите информации при переводах, 152-ФЗ (ПДн согласия, безусловное право отзыва), правила НСПК по автоплатежам;
  - расширяет три контракта одновременно (API ТСП, внутренний контракт адаптера ОПКЦ, RFP вендора транспорта);
  - **но** базовые инварианты AD-001..AD-008 сохраняются — это **инкремент поверх принятого решения, а не перепроектирование**. Отдельного полного Solutioning не требуется.
- **Глубина проектирования**: полноценный ADR + расширение spine (новые инварианты) + расширение статусной машины + добавление методов в контракты + новый раздел NFR. Обязательное **A3-решение человека** (см. §9): регуляторная валидация модели согласия и расширение scope RFP вендора.

### Что меняется, что нет

**Добавляется:**
1. Новая сущность **согласие (consent)** с собственной статусной машиной и аудитом (первый «гражданин» шлюза наравне с платежом).
2. Новый тип платежа `paymentType=RECURRING`: рекуррентное списание по активному согласию, без QR (переход `CREATED → PAID` минуя `QR_ISSUED`).
3. Новые методы API ТСП (согласия, рекуррентные списания), новые события вебхуков, новые методы/события контракта адаптера ОПКЦ.
4. Новые NFR для подписок (латентность, пропускная способность, время отзыва, контроль лимитов).

**Не меняется:**
- Инварианты AD-001..AD-008 (расширяются, не отменяются — см. §2).
- Существующие методы и семантика API ТСП (обратная совместимость контракта — §4 контракта tsp-api).
- Модель зачисления (только из `PAID`, AD-005) и сага возвратов (рекуррентные списания возвращаются тем же механизмом ADR-005, без изменений).

## A3 Decision (машинно-читаемый пакет)

- **choice**: `consent-first-class` — согласие как самостоятельный агрегат шлюза с собственной статусной машиной; рекуррентное списание переиспользует существующую статусную машину платежа (`paymentType=RECURRING` + ссылка `consentId`).
- **rationale**: сохраняет AD-002 (локальный источник истины для согласия и лимитов), AD-005 (зачисление только из PAID), AD-003 (идемпотентность); минимизирует новую финансовую логику (не дублируется статусная машина платежа); лимиты проверяются локально (defense in depth с НСПК); отзыв — немедленный и аудируемый.
- **constraints**: (1) рекуррентное списание — только из `ACTIVE` согласия в пределах `maxAmount`/частоты/срока (AD-009); (2) отзыв — немедленный, необратимый, идемпотентный по `eventId` (AD-010); (3) согласие — отдельный агрегат с атомарными переходами и неизменяемым аудитом (AD-011); (4) ядро контрактно-независимо от транспорта — методы согласий добавляются во внутренний контракт адаптера ОПКЦ, не в ядро (AD-008); (5) ПДн согласия минимизированы, право отзыва доступно всегда (152-ФЗ).
- **rejected options**: `delegate-to-opkc` (шлюз — тонкий прокси, согласие хранится только в НСПК — теряется локальный источник истины и локальный контроль лимитов, нарушение духа AD-002); `full-vendor-subscription` (вендорский модуль подписок целиком — vendor lock-in, противоречит ADR-007 гибриду); `separate-engine` (отдельный параллельный движок подписок со своей статусной машиной — дублирование финансовой логики и риска расхождения с платежами).
- **expiry**: пересмотр при (а) изменении правил НСПК по автоплатежам, требующих отдельного продукта; (б) появлении у бизнеса требований к агрегированным/батчевым списаниям, не укладывающимся в модель «один consent → серия платежей». Плановая ревизия — через 12 месяцев боевой эксплуатации.

## Decision

1. **Согласие — самостоятельный агрегат шлюза.** Жизненный цикл: `PENDING → ACTIVE → REVOKED | EXPIRED | REJECTED` (терминальные: `REVOKED`, `EXPIRED`, `REJECTED`). Атрибуты: `consentId` (шлюз), `tspId`, `maxAmount` (лимит одного списания), `maxDebitsPerPeriod` + `period` (лимит частоты), `validUntil` (срок), `purpose`, `merchantConsentRef` (сквозной id ТСП). Каждый переход — атомарная транзакция «статус + outbox + аудит» (AD-002, AD-011).
2. **Рекуррентное списание переиспользует статусную машину платежа.** Новый `paymentType=RECURRING` + `consentId`; создание — `CREATED`, минуя `QR_ISSUED` (QR нет); далее `PAID → CREDITED → COMPLETED` как обычно. Возврат по рекуррентному списанию — существующей сагой ADR-005 без изменений. ТСП видит то же поле `status`, без новых значений в перечислении.
3. **Лимиты проверяются локально (authoritative) и дублируются НСПК (defense in depth).** Шлюз — источник истины для `maxAmount`/частоты/срока (AD-002); НСПК — финальный арбитр на своей стороне. Расхождение → отказ списания + сверка.
4. **Отзыв — немедленный, необратимый, идемпотентный.** Отзыв возможен плательщиком (через банк плательщика/НСПК → нотификация `consent.revoked` → шлюз) и ТСП (через API → шлюз → адаптер ОПКЦ). Переход в `REVOKED` атомарно блокирует все последующие списания (AD-010); in-flight списания доотрабатываются по статусной машине платежа и сверке.
5. **Контракты расширяются аддитивно** (без поломки существующих потребителей): API ТСП — новые методы согласий и рекуррентных списаний + опциональные поля в `Payment` (§5); адаптер ОПКЦ — новые методы/события согласий (§6); вебхуки — новые события `consent.*` + поле `paymentType` в событиях платежа.
6. **NFR** — отдельный раздел `docs/nfr.md` §7 (§7).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Согласие — агрегат шлюза, списание переиспользует машину платежа (выбран)** | Локальный источник истины и контроль лимитов (AD-002); не дублируется финансовая логика; отзыв немедленный и аудируемый | Новый агрегат и статусная машина; расширение контрактов |
| Согласие хранить только в НСПК, шлюз — прокси | Меньше кода в ядре | Теряется локальный источник истины (нарушение AD-002); лимиты не контролируются локально; зависимость от НСПК на каждую проверку |
| Отдельный движок подписок со своей статусной машиной | Чистое разделение доменов | Дублирование статусной машины платежа, риск расхождения, двойная поддержка |
| Согласие как «флаг» на ТСП без жизненного цикла | Максимально просто | Нет аудита жизненного цикла, гарантий отзыва и лимитов — не проходит 161-ФЗ/152-ФЗ/НСПК |
| Батчевое/агрегированное списание (один вызов НСПК на много операций) | Ниже нагрузка на НСПК | Усложнение идемпотентности и сверки; преждевременно для первой волны |

## Consequences

### Positive

- Подписки без QR: разовый consent → серия списаний, рост конверсии продления для ТСП.
- Локальный контроль лимитов и немедленный отзыв — соответствие 161-ФЗ/152-ФЗ и снижение риска неавторизованных списаний.
- Переиспользование проверенной статусной машины, outbox, сверки и саги возвратов — минимальный прирост финансовой логики.
- Аддитивные контракты — существующие ТСП и методы не затронуты.

### Negative

- Новый агрегат и статусная машина согласия — рост сложности и тестов (каждый переход + гонка «списание vs отзыв»).
- Два источника истины по лимитам (шлюз и НСПК) — нужна сверка и дисциплина расхождений.
- Расширение scope RFP вендора транспорта (методы/события согласий) — риск задержки вендора, POC-сценарии усложняются.
- Точный протокол НСПК по автоплатежам — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`, блокирует финальные сигнатуры контракта адаптера.

### Гонки и негативные сценарии (обязательны к тестам)

- **Списание vs отзыв**: отзыв в момент создания списания → списание отклоняется (`CONSENT_REVOKED`), состояние согласия — источник истины.
- **Превышение лимита**: сумма > `maxAmount` или частота > `maxDebitsPerPeriod` → `CONSENT_LIMIT_EXCEEDED`.
- **Истечение срока**: `validUntil` в прошлом → `CONSENT_EXPIRED`.
- **Повторная нотификация отзыва** → идемпотентно по `eventId`.
- **НСПК отклонил согласие после принятия шлюзом** → `PENDING → REJECTED`, вебхук ТСП.
- **Сбой АБС при зачислении по списанию** → платёж остаётся `PAID`, сверка гарантирует зачисление (как в базовом решении).

## Reversibility

**reversible.** Согласие — аддитивная сущность; рекуррентные списания — подмножество платежей (`paymentType`). Откат = отключение новых методов фиче-флагом и остановка приёма новых согласий без влияния на уже обработанные платежи. Данные согласий не мигрируются обратно. Полное удаление функционала после накопления боевых согласий — costly (как и любой финансовый домен), но локальное хранилище и контрактная граница это допускают. Обратимость на старте (до боевых подписок) — полная.

## Критерии приёмки (проверяются тестом/командой на A4)

1. **Создание согласия**: `POST /v1/consents` с новым `Idempotency-Key` → `201` + `consentId`, статус `PENDING`; повтор с тем же ключом → тот же `consentId` без дубля (AD-003).
2. **Активация**: нотификация НСПК `consent.activated` → `PENDING → ACTIVE`; повтор `eventId` игнорируется.
3. **Списание по активному согласию**: `POST /v1/recurring-payments` с `consentId` → платёж `paymentType=RECURRING`, `CREATED → PAID → CREDITED → COMPLETED`; зачисление в АБС — только из `PAID` (fitness, AD-005).
4. **Негатив — неактивное согласие**: списание при `PENDING`/`REVOKED`/`EXPIRED`/`REJECTED` → `422 CONSENT_NOT_ACTIVE`.
5. **Негатив — лимиты**: сумма > `maxAmount` → `422 CONSENT_LIMIT_EXCEEDED`; превышение `maxDebitsPerPeriod` за `period` → `422 CONSENT_LIMIT_EXCEEDED`.
6. **Отзыв**: `POST /v1/consents/{id}/revoke` (ТСП) и нотификация `consent.revoked` (НСПК) → `ACTIVE → REVOKED`; последующее списание отклоняется (AD-010).
7. **Обратная совместимость**: существующие `POST /v1/payments` и `GET /v1/payments/{id}` работают без изменений; `Payment` без `paymentType` трактуется как `QR`.
8. **Возврат по списанию**: полный возврат по рекуррентному списанию переводит платёж в `REFUNDED` существующей сагой (ADR-005), без нового кода.
9. **NFR**: метрики из `docs/nfr.md` §7 выполнены на моках/нагрузочном тесте.

## План отката

- **До боевой эксплуатации**: откат = не включать фиче-флаг рекуррентных списаний; все работы обратимы (ADR-008 reversible).
- **После включения**: (1) фиче-флаг на приём новых согласий и новых рекуррентных списаний — мгновенный `stop-new`; (2) уже активные согласия и in-flight списания доотрабатываются штатно (сверка + DLQ runbook); (3) откат релиза — rolling, без downtime (как в базовом NFR «плановая недоступность = 0»).
- **Сигнал отката**: рост доли `CONSENT_*` ошибок сверх порога, расхождения сверки по согласиям/списаниям > 0, инцидент неавторизованного списания.
- **Владелец решения об откате**: владелец платёжного контура + дежурная смена (SRE) по runbook; критерий успешного отката — после `stop-new` и отката релиза новых списаний не создаётся, открытые операции завершены или корректно сверены.

## Что остаётся на решение человека-архитектора (и почему)

1. **Регуляторно-правовая валидация модели согласия** (161-ФЗ, Положение ЦБ о защите информации при переводах, 152-ФЗ, правила НСПК по автоплатежам): состав полей согласия, порядок и безусловность отзыва, сроки хранения ПДн согласия. *Почему человек:* это юридико-комплаенс решение, не выводимое из кода; ошибка = регуляторный риск.
2. **Точный протокол НСПК для автоплатежей** — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; определяет финальные сигнатуры методов/событий адаптера ОПКЦ и семантику лимитов. *Почему человек:* зависит от документации НСПК по договору.
3. **Расширение scope RFP вендора транспорта**: подтверждение, что вендор реализует методы/события согласий и рекуррентных списаний (расширение критериев G3/G4 RFP) — выбор вендора и POC. *Почему человек:* A3-решение о закупке, за рамками архитектурного ADR.
4. **Продуктовая модель подписок**: какие сегменты ТСП в первой волне, конкретные значения лимитов/периодов/тарифов. *Почему человек:* бизнес-параметры, влияют на конфигурацию, но не на архитектуру.
5. **UX и канал отзыва согласия**: доступен ли отзыв только через банк плательщика/НСПК или также через ТСП-API (влияет на обязанности ТСП и аутентификацию отзыва). *Почему человек:* продуктовое/регуляторное решение.
6. **Ратификация новых инвариантов AD-009..AD-011** (spine) и самого ADR-008 на A3. *Почему человек:* гейт принятия решения, как для ADR-007.
