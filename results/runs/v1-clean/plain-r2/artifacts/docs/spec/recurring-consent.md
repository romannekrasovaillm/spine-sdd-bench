# Рекуррентные C2B-списания (СБП-подписки) — спецификация машин состояний

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-004, ADR-005, AD-009, AD-010

Расширение `docs/spec/state-machine.md`: добавляется вторая статусная машина — **согласие плательщика (consent/mandate)** — и аддитивный переход в машине платежа для рекуррентного списания. Базовые C2B-переходы (T1–T12) не меняются.

## 1. Сущности

### 1.1 Согласие плательщика (consent)

| Поле | Смысл | Примечание |
|---|---|---|
| `consentId` | id согласия в шлюзе (сквозной для ТСП и сверки) | генерирует шлюз |
| `tspId` | ТСП-владелец согласия | дебит возможен только от того же ТСП |
| `perDebitLimit` | макс. сумма одного списания (копейки) | обязателен |
| `maxTotal` | макс. накопительная сумма за срок (копейки) | опционально |
| `validFrom` / `validTo` | срок действия | за пределами — списание запрещено |
| `status` | состояние машины согласия | см. §2 |
| `opkcConsentRef` | ссылка на согласие в ОПКЦ (сквозной id) | заполняется адаптером ОПКЦ |
| `payerMasked` | маскированный идентификатор плательщика (для сверки/ПДн) | минимизация по AD-007 |

### 1.2 Рекуррентное списание

Это платёж с атрибутами `paymentType = RECURRING` и `consentId`. Всё остальное (сумма, `paymentId`, статусы `PAID/CREDITED/COMPLETED`, `Idempotency-Key`, `eventId`) — из базовой машины платежа (ADR-002).

## 2. Машина состояний согласия

```
CREATED ──► PENDING_CONFIRMATION ──► ACTIVE ──► EXPIRED
   │              │                     │
   ▼              ▼                     ├──► REVOKED
 FAILED         FAILED                  └──► PAUSED ──► ACTIVE (resume)
```

Состояния:

| Состояние | Смысл | Списание разрешено |
|---|---|---|
| `CREATED` | заявка на согласие создана в шлюзе, запрос к ОПКЦ в процессе | нет |
| `PENDING_CONFIRMATION` | согласие зарегистрировано в ОПКЦ, ждём подтверждения плательщиком | нет |
| `ACTIVE` | плательщик подтвердил; списания разрешены | **да** |
| `PAUSED` | временно приостановлено (пауза подписки) | нет |
| `REVOKED` | отозвано плательщиком или ТСП; терминальное | нет |
| `EXPIRED` | срок истёк или достигнут `maxTotal`; терминальное | нет |
| `FAILED` | ОПКЦ отклонил согласие (напр., AML); терминальное | нет |

Переходы:

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `CREATED` | `POST /v1/consents` | валидный запрос, ТСП активен, `perDebitLimit` > 0 | запись согласия + outbox «создание в ОПКЦ» |
| C2 | `CREATED` | `PENDING_CONFIRMATION` | ОПКЦ принял регистрацию (`createConsent` → ACCEPTED) | `opkcConsentRef` непустой | сохранить `opkcConsentRef`, outbox |
| C3 | `CREATED` | `FAILED` | ОПКЦ отклонил регистрацию | — | `errorCode`, outbox, вебхук `consent.rejected` |
| C4 | `PENDING_CONFIRMATION` | `ACTIVE` | событие `consent.activated` (подтверждение плательщиком) | событие от ОПКЦ, `consentId` совпадает | outbox, вебхук `consent.activated` |
| C5 | `PENDING_CONFIRMATION` | `FAILED` | плательщик отклонил / таймаут подтверждения | — | outbox, вебхук `consent.rejected` |
| C6 | `ACTIVE` | `PAUSED` | `POST /v1/consents/{id}/pause` | — | outbox, вебхук `consent.paused` |
| C7 | `PAUSED` | `ACTIVE` | `POST /v1/consents/{id}/resume` | в пределах срока | outbox, вебхук `consent.resumed` |
| C8 | `ACTIVE`/`PAUSED` | `REVOKED` | отзыв плательщиком (событие ОПКЦ) или `POST /v1/consents/{id}/revoke` | — | outbox, вебхук `consent.revoked` |
| C9 | `ACTIVE` | `EXPIRED` | истёк `validTo` или накоплено ≥ `maxTotal` | — | outbox, вебхук `consent.expired` |

Терминальные `REVOKED`/`EXPIRED`/`FAILED` — переходов наружу нет; повторные триггеры идемпотентны (AD-003).

## 3. Рекуррентное списание в машине платежа

Аддитивный переход к `docs/spec/state-machine.md`:

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| T13 | — | `CREATED` | `POST /v1/consents/{consentId}/payments` | согласие `ACTIVE` и принадлежит ТСП; `amount ≤ perDebitLimit`; накопление ≤ `maxTotal`; в сроке | запись платежа (`paymentType=RECURRING`, `consentId`) + outbox «рекуррентное списание в ОПКЦ» |
| T14 | `CREATED` | `PAID` | нотификация НСПК `PAID` (или сверка) | **сумма и согласие совпадают**; иначе → `FAILED` | outbox «зачисление в АБС» (далее T8–T10, как обычно) |
| T15 | `CREATED` | `FAILED` | НСПК отклонил списание (`payment.rejected`) | — | `errorCode`, вебхук `payment.failed` |

Ключевое отличие от одноразового: **нет `QR_ISSUED`** — `CREATED → PAID` напрямую. Зачисление по-прежнему только из `PAID` (AD-005); `PAID → CREDITED → COMPLETED` — без изменений (T8–T10). Повторные `POST /v1/consents/{id}/payments` идемпотентны по `Idempotency-Key` + `paymentId`.

## 4. Запрещённые переходы (инварианты)

- Создание рекуррентного списания из любого состояния согласия, кроме `ACTIVE`, — недостижимо (AD-009).
- Создание списания сверх `perDebitLimit`/`maxTotal`/срока — недостижимо (AD-009).
- Создание списания ТСП, не совпадающим с владельцем согласия, — недостижимо (AD-009).
- После `REVOKED`/`EXPIRED` новые списания недостижимы; уже `PAID`-списания доводятся до завершения и не отменяются (AD-010).
- `PAID` не откатывается в `CREATED`/`QR_ISSUED` — подтверждённый статус необратим (как в базовой машине).
- Зачисление в АБС невозможно из `CREATED` — только из `PAID` (AD-005).

## 5. Идемпотентность и гонки

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/consents` | `Idempotency-Key` | тот же `consentId`, состояние не меняется |
| `POST /v1/consents/{id}/payments` | `Idempotency-Key` | тот же `paymentId` |
| Событие `consent.*` от ОПКЦ | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по терминальному переходу — алерт |
| Нотификация `PAID` по списанию | `eventId` | как в базовой машине (ADR-004) |

**Гонка «отзыв параллельно со списанием»**: проверка `consent.status == ACTIVE` и создание списания выполняются в одной транзакции с переходом согласия (AD-010). Исход ровно один из двух:

- отзыв выиграл → `consent.status = REVOKED`, списание не создаётся (`422 CONSENT_NOT_ACTIVE`);
- списание выиграло → списание `CREATED`, отзыв фиксируется, но списание не отменяется задним числом.

Политика in-flight (дефолт, ADR-008 §7 п.4): `PAID` доводится до `COMPLETED`; `CREATED` без подтверждения НСПК — отменяется/закрывается, если согласие отозвано до `PAID`.

## 6. Сверка и восстановление

- Согласие — новый объект сверки с ОПКЦ: ежесуточная сверка статусов согласий (дополняет часовую/суточную сверку платежей из ADR-004).
- «У ОПКЦ `ACTIVE`, у нас нет» → дозапрос `getConsentStatus` → C4.
- «У нас `ACTIVE`, у ОПКЦ `REVOKED`» → стоп-сигнал, эскалация (не списывать).
- Открытые состояния (`CREATED`, `PENDING_CONFIRMATION`, `ACTIVE`) — кандидаты для сверки.
