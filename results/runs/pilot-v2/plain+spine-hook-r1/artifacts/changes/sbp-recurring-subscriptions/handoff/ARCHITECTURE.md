# Архитектурный контекст: инкремент «Подписки СБП» (epic-context)

Компиляция по смыслу (не по источнику). Источники: `ARCHITECTURE-SPINE.md` (AD-002, AD-003, AD-005,
AD-009, AD-010), `docs/adr/ADR-008-*.md`, `docs/solutioning-subscriptions.md`,
`docs/spec/subscriptions.md`, `openapi/tsp-api.yaml` v0.2.0, `docs/nfr.md` §7.

## Цель

Добавить к разовому C2B-приёму **рекуррентные списания по согласию плательщика** без разрыва
принятых инвариантов. Согласие плательщика (mandate) — первоклассная сущность со своей статусной
машиной в БД шлюза; списание — обычный платёж, инициируемый шлюзом против активного согласия.

## Жёсткие инварианты (дословно; менять запрещено)

- **AD-002.** Изменение финансового статуса и запись исходящего события (outbox) — в одной локальной
  транзакции. Согласие — второй агрегат с тем же правилом.
- **AD-003.** Повторная доставка любого сообщения не изменяет уже завершённое состояние.
  Ключи: `Idempotency-Key` (создание согласия/списания), `eventId` (consent-события), `reference`
  (отзыв), `paymentId`/`refundId` (АБС).
- **AD-005.** Вызов АБС на зачисление возможен только из состояния `PAID`. **Согласие `ACTIVE` не
  подменяет подтверждение НСПК** — зачисление по списанию только из `PAID`.
- **AD-009 (новый).** Инициировать списание можно **только при согласии в состоянии `ACTIVE`** и в
  пределах его параметров (получатель, лимит на списание, суммарный лимит, период). Отзыв согласия
  запрещает новые списания.
- **AD-010 (новый).** Создание/изменение/отзыв согласия фиксируются в **неизменяемом аудит-логе**;
  ПДн плательщика минимизируются (хранится референс согласия, не полные реквизиты); статус согласия
  сверяется с НСПК не реже ежедневно.
- **AD-001, AD-004.** Взаимодействие с АБС/ОПКЦ — только через адаптеры шлюза; протокол НСПК знает
  только адаптер ОПКЦ (consent-операции — во внутреннем контракте `opkc-adapter.md`).

## Статусная машина согласия (`docs/spec/subscriptions.md`)

`INITIATED → PENDING_PAYER → ACTIVE`; нетерминальное `SUSPENDED`; терминальные `REVOKED`, `EXPIRED`,
`REJECTED`. `ACTIVE` не возвращается в `PENDING_PAYER`; отозванное согласие не реактивируется
(нужно новое согласие). Точные переходы M1–M11 и запреты — в спеке.

## Контракт ТСП (аддитивный, v0.2.0)

- `POST /v1/subscriptions` (`Idempotency-Key`) → `201 Subscription` (`PENDING_PAYER`, `consentUrl`).
- `GET /v1/subscriptions/{id}` → `200 Subscription`.
- `POST /v1/subscriptions/{id}/charges` (`Idempotency-Key`, `amount`) → `201 SubscriptionCharge`;
  отказ `SUBSCRIPTION_NOT_ACTIVE` / `SUBSCRIPTION_LIMIT_EXCEEDED` / `SUBSCRIPTION_REVOKED`, платёж не
  создаётся.
- `POST /v1/subscriptions/{id}/revoke` (`Idempotency-Key`) → `202`.
- `Payment.subscriptionId` — опциональная связь; статус списания — через `GET /v1/payments/{paymentId}`.
- Вебхуки: `subscription.activated`, `subscription.revoked`, `charge.completed`.
- Существующие пути `/v1/payments*` **не изменены** (ломающих изменений нет: `contract_diff` = 0).

## Запрещено

- Менять существующие пути/поля/обязательность контракта ТСП (только аддитивно).
- Выносить протокол НСПК за пределы адаптера ОПКЦ.
- Зачислять по списанию вне `PAID`; инициировать списание при не-`ACTIVE` согласии или вне лимитов.
- Хранить полные реквизиты плательщика; писать финансовые/consent-переходы вне аудита.
- Изменять инварианты AD-002/AD-003/AD-005/AD-009/AD-010: расхождение — **стоп и эскалация**.

## Критерии приёмки (сжато)

NFR §7 (активация согласия p95 ≤ 30 с; инициирование списания p95 ≤ 500 мс; блокировка новых
списаний после отзыва ≤ 60 с, сквозное ≤ 5 мин; двойных списаний — 0; аудит 100 %) + негативные
сценарии (не-`ACTIVE`, превышение лимитов, дубль события, гонка отзыва/списания, недоступность НСПК).
