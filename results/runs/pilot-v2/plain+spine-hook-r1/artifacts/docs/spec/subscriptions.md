# Согласие плательщика (подписка) — статусная машина

- Status: Draft (для ревью на гейте A1; ожидает A3 по ADR-008)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-004, AD-002, AD-003, AD-009, AD-010

Единый источник истины состояния согласия — БД шлюза (AD-002). Каждый переход — **атомарная
транзакция** «смена статуса + запись в outbox + аудит-лог». Повторные триггеры идемпотентны
(AD-003). Согласие **не** ведёт деньги: списание — это платёж, доводимый по `docs/spec/state-machine.md`,
и зачисляется только из `PAID` (AD-005).

## Проблема

Разовые C2B-платежи требуют сканирования QR и действия клиента на каждый платёж, что не подходит
подпискам (кинотеатры, ЖКХ, связь). Нужен способ повторяющихся списаний **по ранее данному согласию
плательщика**, доказуемый, ограниченный параметрами согласия и мгновенно останавливаемый при отзыве —
при сохранении действующих инвариантов платёжного контура (зачисление только из `PAID`, атомарные
переходы, идемпотентность, изоляция протокола НСПК).

## 1. Состояния

| Состояние | Смысл | Видно ТСП |
|---|---|---|
| `INITIATED` | Согласие зарегистрировано в шлюзе, запрос к ОПКЦ в процессе | да |
| `PENDING_PAYER` | Ожидает подтверждения плательщика в банке плательщика | да |
| `ACTIVE` | Согласие действует; списания в пределах параметров разрешены | да |
| `SUSPENDED` | Временно приостановлено (не терминально); списания запрещены | да |
| `REVOKED` | Отозвано плательщиком/банком; списания запрещены | да |
| `EXPIRED` | Истёк срок согласия; списания запрещены | да |
| `REJECTED` | Отклонено банком плательщика/НСПК при оформлении | да |

Терминальные: `REVOKED`, `EXPIRED`, `REJECTED`. `SUSPENDED` — нетерминальное.

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `INITIATED` | `POST /v1/subscriptions` (новый `subscriptionId`) | валидный запрос, ТСП активен | запись согласия + параметры + outbox + аудит |
| M2 | `INITIATED` | `PENDING_PAYER` | адаптер ОПКЦ вернул `consentRef`/`consentUrl` | `consentRef` непустой | сохранить `consentRef`, outbox-нотификация ТСП |
| M3 | `INITIATED` | `REJECTED` | ошибка регистрации в ОПКЦ (не транзиентная, ретраи исчерпаны) | — | `errorCode`, аудит, вебхук |
| M4 | `PENDING_PAYER` | `ACTIVE` | событие `consent.activated` (или подтверждение сверкой) | `eventId` новый | outbox, аудит, вебхук `subscription.activated` |
| M5 | `PENDING_PAYER` | `REJECTED` | событие `consent.rejected` | — | `errorCode`, аудит, вебхук |
| M6 | `PENDING_PAYER` | `EXPIRED` | TTL ожидания подтверждения истёк | подтверждение не наступило | закрытие в ОПКЦ (по протоколу), аудит |
| M7 | `ACTIVE` | `SUSPENDED` | запрос ТСП/банка на приостановку | — | аудит; списания запрещены |
| M8 | `SUSPENDED` | `ACTIVE` | возобновление (запрос/подтверждение) | согласие не отозвано/не истекло | аудит; списания разрешены |
| M9 | `ACTIVE` | `REVOKED` | событие `consent.revoked` / требование плательщика | `eventId` новый | аудит, вебхук `subscription.revoked`; **блок новых списаний** |
| M10 | `SUSPENDED` | `REVOKED` | событие `consent.revoked` / требование плательщика | — | аудит; блок новых списаний |
| M11 | `ACTIVE` | `EXPIRED` | истёк срок согласия | — | аудит; блок новых списаний |

## 3. Запрещённые переходы (инварианты)

- **Инициирование списания возможно только из `ACTIVE`** (AD-009). Из `INITIATED`/`PENDING_PAYER`/
  `SUSPENDED`/`REVOKED`/`EXPIRED`/`REJECTED` — недостижимо. Fitness: негативный тест.
- **Списание обязано укладываться в параметры согласия** (получатель, лимит на списание, суммарный
  лимит, период, назначение) — AD-009. Превышение → отказ, платёж не создаётся.
- `REVOKED`/`EXPIRED`/`REJECTED` — терминальные: переходов из них нет (повторные триггеры
  идемпотентны, AD-003).
- `ACTIVE` не может вернуться в `PENDING_PAYER`; отозванное согласие не «реактивируется» — при
  необходимости оформляется новое согласие (новый `subscriptionId`).
- **Зачисление по списанию — только из `PAID`** (AD-005): согласие `ACTIVE` не подменяет
  подтверждение НСПК.

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/subscriptions` | `Idempotency-Key` | тот же `subscriptionId`, состояние не меняется |
| `POST /v1/subscriptions/{id}/charges` | `Idempotency-Key` | тот же `chargeId`/`paymentId`, второе списание не создаётся |
| Событие `consent.activated`/`consent.revoked` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Отзыв согласия | `reference`/`subscriptionId` | повторный отзыв идемпотентен |

### 4.1 Порядок проверок при инициировании списания (конкурентность)

Порядок guard'ов критичен для корректности под нагрузкой и при гонке с отзывом:

1. **Идемпотентность сначала.** Повтор с тем же `Idempotency-Key` возвращает ранее созданный
   `chargeId` **независимо от текущего статуса согласия**. Иначе ретрай «после отзыва» вернул бы
   ошибку вместо результата уже созданного списания (потеря результата для ТСП).
2. **Guard согласия.** Для **нового** запроса — согласие строго в `ACTIVE`; иначе
   `SUBSCRIPTION_NOT_ACTIVE` (`SUSPENDED`/`PENDING_PAYER`/`EXPIRED`/`REJECTED`) или
   `SUBSCRIPTION_REVOKED` (`REVOKED`). Платёж не создаётся.
3. **Guard лимитов и периода.** Сумма ≤ лимита на списание; накопленный кумулятив + сумма ≤
   суммарного лимита; период согласия соблюдён.
4. **Атомарность.** Проверка лимитов, создание платежа-списания и учёт кумулятива — **в одной
   транзакции** (в духе AD-002): иначе две параллельные заявки превысят суммарный лимит.

Идемпотентность `Idempotency-Key` (п.1) и идемпотентность события `eventId` (§4) — разные ключи:
первая защищает от повторов ТСП, вторая — от повторов нотификаций НСПК.

## 5. Конкурентность отзыва и списания

- Списание, **подтверждённое НСПК как `PAID`** до вступления отзыва в силу, доводится до
  зачисления (авторизовано согласием на момент инициирования).
- Списание, инициированное **после** `REVOKED`, отклоняется (`SUBSCRIPTION_REVOKED`), платёж не
  создаётся.
- Неопределённый исход (запрос отправлен, ответа нет) разрешается **сверкой** с НСПК, не догадкой;
  операция остаётся видимой в отчёте незавершённых операций.
- Момент «вступления отзыва в силу» (по событию НСПК / по требованию плательщика) — предмет
  решения A3 п.8 `docs/solutioning-subscriptions.md` §8 (регламент НСПК).

## 6. Сверка и восстановление

- Открытые состояния (`PENDING_PAYER`, `ACTIVE`, `SUSPENDED`) — кандидаты сверки с НСПК: не реже
  ежедневно (NFR §7).
- «У НСПК согласие активно, у нас нет» → дозапрос статуса → обработка как событие `consent.activated`.
- «У нас `ACTIVE`, у НСПК нет/отозвано» → стоп-сигнал: блок новых списаний + эскалация.
- Согласие в `ACTIVE` с недоступной НСПК: новые списания не инициируются (fail-closed), уже начатые
  операции доводятся по сверке.

## Критерии приёмки

- When ТСП инициирует списание по согласию не в состоянии `ACTIVE`, the шлюз shall отклонить запрос
  и не создавать платёж (AD-009).
- When параметры списания выходят за лимиты согласия, the шлюз shall отклонить запрос с
  `SUBSCRIPTION_LIMIT_EXCEEDED`.
- When приходит повторное событие согласия с тем же `eventId`, the сервис согласий shall не изменять
  состояние (AD-003).
- When плательщик отзывает согласие, the сервис согласий shall перевести согласие в `REVOKED` и
  заблокировать новые списания в пределах NFR §7.
- If согласие отозвано, then подтверждённое до отзыва списание shall быть доведено до зачисления.
- When изменяется состояние согласия, the сервис согласий shall записать неизменяемую аудит-запись
  (AD-010).
- While согласие в `ACTIVE`, the сверка shall не реже раза в сутки подтверждать статус у НСПК.

## Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Списание без действующего согласия (дефект guard) | Финансовый/регуляторный инцидент | AD-009 + негативные fitness-тесты + сверка; блок новых списаний |
| Двойное списание при повторе | Прямой ущерб плательщику | Идемпотентность по ключу/`eventId`; тесты повторной доставки |
| **Два списания за один период с разными `Idempotency-Key`** | Двукратное списание за период | Суммарный лимит ограничивает ущерб; вопрос «одно списание на период» — решение A3 (`docs/solutioning-subscriptions.md` §8 п.9) |
| Гонка параллельных заявок на суммарный лимит | Превышение согласия | Проверка лимитов и учёт кумулятива в одной транзакции (§4.1) |
| Отзыв не блокирует списание вовремя | Списание после отзыва | NFR §7 (≤ 60 с); мониторинг лага; fail-closed |
| Расхождение статуса согласия с НСПК | Недоказуемость/ошибочные списания | Ежедневная сверка; алерт на расхождение |
| Избыточные ПДн плательщика | Нарушение 152-ФЗ | AD-010: хранить референс, не реквизиты; ревью ИБ |
| Иная модель согласия в протоколе НСПК | Пересмотр решения | Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; expiry ADR-008 |
