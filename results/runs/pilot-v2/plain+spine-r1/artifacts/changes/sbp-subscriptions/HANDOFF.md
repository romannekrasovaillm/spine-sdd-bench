# HANDOFF — дельта «подписки СБП» кодовому харнессу

- Status: Draft (готов после A3; до A3 использовать как A2-заготовку walking skeleton)
- Дата: 2026-09-28
- Источники: ADR-008, ADR-009, `docs/spec/mandate-lifecycle.md`, `docs/nfr-sbp-subscriptions.md`, `openapi/tsp-api.yaml` (v0.2.0), `.arch-handoff/CONSTRAINTS.yaml`

## Задача (epic-context, по смыслу)

Реализовать в существующем СБП-шлюзе **подписки**: согласие плательщика (mandate) и **рекуррентные C2B-списания** по нему. Уже реализуемый разовый приём (QR/ссылка, платёж, зачисление, возврат) **не меняется** — подписки добавляются рядом и переиспользуют те же механизмы: статусную машину, транзакционный outbox, дедупликацию, нотификации, сверку.

**Границы и стыки.**

- Вход ТСП (ядро, собственная разработка): новые пути `/v1/mandates` (создать согласие), `/v1/mandates/{id}` (статус), `/v1/mandates/{id}/revoke` (отзыв), `/v1/mandates/{id}/debits` (инициация списания). Идемпотентность — по `Idempotency-Key`; для списаний **дополнительно** по (`mandateId`, `billingPeriod`).
- Транспорт к НСПК: операции согласий/списаний идут **только** через существующий единственный адаптер ОПКЦ (AD-004), в мок-виде (реальный протокол СБП-подписок НЕ реализуется — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`).
- АБС: зачисление/списание — существующим идемпотентным контрактом по `paymentId`/`refundId`; контракт АБС не меняется.
- Нотификации ТСП: новые события `mandate.activated`, `mandate.rejected`, `mandate.revoked` (доставка включается флагом ТСП — opt-in); отказ по списанию — существующее `payment.failed` с `errorCode=PAYER_REJECTED`.

**Модель инициации (ADR-008):** списания инициирует **ТСП** на дату обязательства; шлюз **не хранит биллинговый календарь** и не запускает списания сам. Шлюз хранит состояние согласия и исполняет списание.

## Инварианты (обязательны, дословно из spine)

- **AD-009:** «Рекуррентное списание инициируется ТОЛЬКО при статусе согласия `ACTIVE`, в пределах лимитов согласия (сумма списания и сумма за период), при выполненном требовании предварительного уведомления плательщика; ключ дедупликации обязательства — (`mandateId`, `billingPeriod`), повтор не создаёт второе списание; после события отзыва согласия новые списания запрещены немедленно. Зачисление — по-прежнему только из `PAID` (AD-005).»
- **AD-005:** «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус).»
- **AD-002:** изменение финансового статуса и запись исходящего события (outbox) — в одной локальной транзакции.
- **AD-003:** повторная доставка любого сообщения не изменяет уже завершённое состояние.
- **AD-004:** протокол НСПК знает только адаптер ОПКЦ; операторы согласий — через него же.
- **AD-008:** ядро контрактно-независимо от транспорта; вендор обязан поддержать операции подписок.

## Что запрещено менять

- Существующие пути/схемы/статусы `Payment` (v0.1) и enum `Payment.status`.
- Правило «зачисление только из `PAID`» (AD-005).
- Границу ядро↔транспорт: протокольные детали НСПК вне адаптера не появляются.
- Контракт АБС.
- Любой конфликт с spine обязан **останавливать** работу и эскалироваться, а не обходиться.

## Критерии приёмки (см. `ACCEPTANCE.md` — EARS)

Ключевое: `ACTIVE`-only; лимиты; предуведомление; «(mandateId, billingPeriod) → одно списание»; «отзыв → 0 новых списаний»; отказ плательщика → `FAILED` (согласие `ACTIVE`); зачисление только из `PAID`; `contract_diff` = 0 breaking; `openapi_lint` PASS; регресс разового приёма отсутствует.

Проверка — property-тесты на фейках ОПКЦ/АБС (со счётчиком, без сети и сна), с обязательной **нарушающей реализацией** (тест обязан падать на нарушении).

## Контракт результата (headless JSON)

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено; `partial` — частично; `blocked` — заблокировано внешним входом (документация НСПК, подтверждение вендора).
- `conflicts_with_prior_decisions` — любое расхождение с ADR-008/009 или spine **останавливает** работу и эскалируется.

## Ограничения окружения

- Реальный протокол НСПК по подпискам недоступен — работаем на моке; всё протокольное помечено `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Технологический стек — по выбору команды с обоснованием в ADR; приоритет — доказать архитектуру сквозным сценарием, а не полноту продукта.
