# Impact — дельта «подписки СБП»: влияние на принятую архитектуру

- Status: Draft (вход на A3)
- Дата: 2026-09-28
- Связано: `changes/sbp-subscriptions/DELTA.md`, ADR-008, ADR-009, `docs/spec/mandate-lifecycle.md`, `docs/nfr-sbp-subscriptions.md`
- Базовое решение: `docs/solutioning.md`, `ARCHITECTURE-SPINE.md` (AD-001..AD-008)

## 0. Сводка

Добавляется **подписка**: согласие плательщика (mandate) + рекуррентное C2B-списание по нему. Изменение **аддитивно**: существующий разовый приём (QR/ссылка) не меняется. Ядро шлюза остаётся контрактно-независимым от транспорта; протокол СБП-подписок НСПК уходит в единственный адаптер.

## 1. Оценка значимости и маршрут

- **Машинный вердикт:** `significance_score` → **Critical, score 11** (11 триггеров).
- **Триггеры:** `new_component`, `new_datastore`, `domain_ownership_change`, `cross_domain_integration`, `api_contract_change`, `data_contract_change`, `security_boundary_change`, `consistency_model_change`, `significant_nfr`, `financial_impact`, `criticality_or_exception`.
- **Не сработали:** `new_vendor`, `trust_zone_change`, `rto_rpo_targets`, `irreversible_migration`.
- **Почему Critical, а не дельта:** движение денег **без активного действия плательщика** на каждый платёж + новый аспект security boundary (согласие как основание списания). Для Critical дельты недостаточно — нужен полный Solutioning, ADR с альтернативами, обязательная точка **A3**, evidence-гейты.
- **Маршрут и гейты:** A0 fit (аддитивность, ядро независимо от транспорта) → A1 Spec (mandate-lifecycle, NFR, контракты) → A2 Plan (walking skeleton на моках) → **A3 human** (`A3-PACKAGE.md`) → A4 conformance (fitness + property-тесты + `contract_diff`) → A5 drift (сверка согласий, «списание после отзыва = 0»).

> **Примечание о маршруте.** Композитный `architect_review` печатает маршрут из git-диффа; для пакета, состоящего из документов, он даёт `Fast` (score 1, только `api_contract_change`). Это не противоречие: дифф-детектор видит изменение контракта, но не семантику «деньги без активного действия плательщика». **Авторитетна** оценка по триггерам — `significance_score` → **Critical/11**; при появлении кода и транспортных изменений дифф-маршрут поднимется.

## 2. Влияние на инварианты spine

| Инвариант | Затронут? | Как именно |
|---|---|---|
| **AD-001** Изоляция платёжного контура | Да (усиление) | Сервис согласий — внутри платёжного контура; обращения к ОПКЦ и АБС остаются только через адаптеры |
| **AD-002** Единый источник истины (статусная машина) | Да (расширение) | Согласие — второй конечный автомат под тем же принципом: атомарные переходы «статус + outbox + аудит» |
| **AD-003** Идемпотентность | Да (расширение) | Добавляется дедупликация обязательства (`mandateId`, `billingPeriod`) с окном ≥ срока жизни согласия; сохраняются `Idempotency-Key` и дедуп нотификаций по `eventId` |
| **AD-004** Единственный адаптер ОПКЦ | Да (расширение) | Новые операции согласий идут через тот же адаптер; протокол НСПК не протекает в ядро. `Binds` расширен дельтой |
| **AD-005** Зачисление только из `PAID` | **Нет** (подтверждён) | Рекуррентное списание зачисляется по тому же правилу; исключений нет |
| **AD-006** Trust-зоны и сегментация | Да (без новых зон) | Новых trust-зон нет; усиливаются требования к хранению согласий и артефактов подтверждения (ПДн) |
| **AD-007** НПС/КИИ/ПДн | Да (расширение) | Согласие — правовое основание списания; неизменяемый аудит согласий; минимизация ПДн плательщика |
| **AD-008** Стратегия реализации (гибрид, ADOPTED) | Да (уточнение) | Сохраняется; вендор обязан поддержать операции подписок; реализация транспорта подписок — после документации НСПК и подтверждения вендора |
| **AD-009** Списание только при действующем согласии | **НОВЫЙ** | Добавлен дельтой (Proposed (ADR-008)) — см. `DELTA.md` ADDED A1 |

Итог: ни один действующий инвариант не ослаблен; AD-005 подтверждён; добавлен AD-009, продолжающий AD-003/AD-005.

## 3. Влияние на компоненты

**Новые:**
- **Сервис согласий (mandate store)** — регистрация/статус/отзыв согласия, лимиты, guard-проверки инициации, дедупликация обязательства, аудит.
- **Справочник/ключи дедупликации обязательств** (`mandateId`, `billingPeriod`).

**Изменяемые:**
- **API ТСП (ядро)** — новые пути `/v1/mandates*`; без изменения существующих.
- **Статусная машина** — новый триггер создания платежа по согласию без стадии `QR_ISSUED` (`docs/spec/state-machine.md` §7).
- **Нотификатор ТСП** — новые типы событий `mandate.*` (opt-in).
- **Сверка (reconciliation)** — согласия как объект сверки с ОПКЦ (отзыв/приостановка).
- **Аудит-лог** — жизненный цикл согласия.

**Не изменяемые:** адаптер АБС (зачисление/возврат по `paymentId`/`refundId` без изменений), граница ядро↔транспорт по форме (ADR-008), транспортная криптография.

## 5. Влияние на данные и ПДн

- Новый объект — **согласие** (атрибуты: ТСП, `payerRef`, период, лимиты, ссылка на артефакт подтверждения, статусы/переходы).
- ПДн плательщика минимизированы, шифрование в покое, маскирование в логах (AD-006/AD-007).
- Согласия и их переходы — в неизменяемом аудит-логе; RPO=0.
- Миграция обратно не требуется (см. Reversibility ADR-008).

## 6. Влияние на NFR

- Базовые SLO сохраняются (доступность ≥ 99,95 %, RPO=0, RTO ≤ 1 ч, 200/500 TPS).
- Новое: **синхронные пики биллинга** (массовые списания 1-го числа) — требуют rate limit по ТСП и проверки на профиле «1-е число»; латентность инициации списания p95 < 500 мс; запрет списания после отзыва ≤ 60 с; «двойное списание за период = 0». Детали — `docs/nfr-sbp-subscriptions.md`.

## 7. Риски изменения (кратко)

| Риск | Влияние | Митигация |
|---|---|---|
| Двойное списание за период при ретраях | Финансовый инцидент | Дедуп (`mandateId`,`billingPeriod`) + property-тест (AD-009) |
| Списание после отзыва согласия | Нарушение прав плательщика, регуляторный риск | Немедленный `REVOKED`, дозапрос для «в полёте», алерт, сверка |
| Недоступность ОПКЦ/вендора для операций подписок | Срыв списаний | DLQ + сверка; не теряем операции; политика при `transport.unavailable` (A2) |
| Неопределённость протокола НСПК по подпискам | Ошибки модели согласия | Пометки `[ТРЕБУЕТ ПРОВЕРКИ]`; ADR-008 expiry; старт транспорта подписок только после документации |
| Пик «1-е число» перегружает шлюз | Деградация базового приёма | Rate limit по ТСП, нагрузочный профиль пика, изоляция (bulkhead) |

## 8. Что явно НЕ меняется

- Разовый приём (`/v1/payments`, возвраты, вебхуки) — контракт и поведение.
- AD-005: зачисление только из `PAID`.
- Стратегия реализации (гибрид) и граница с вендорским транспортом.
- Trust-зоны (AD-006) по составу.
- Ответственность АБС и её контракт.
