# Приёмка и план отката — дельта «подписки СБП»

- Status: Draft (вход на A1/A3)
- Дата: 2026-09-28
- Связано: ADR-008, ADR-009, AD-009, `docs/nfr-sbp-subscriptions.md`, `docs/spec/mandate-lifecycle.md`

Критерии приёмки — в нотации **EARS** (формально проверяемы). Проверка — на гейте **A4** на моках ОПКЦ/АБС (walking skeleton), затем в проде (A5). Каждый критерий имеет метод проверки и не содержит «работает корректно».

## 1. Критерии приёмки (EARS)

### 1.1 Позитивные

- When ТСП создаёт согласие (`POST /v1/mandates`), the СБП-шлюз shall вернуть `mandateId` со статусом `PENDING_CONSENT` за p95 < 1 с (без учёта ОПКЦ).
- When плательщик подтверждает согласие, the СБП-шлюз shall перевести согласие в `ACTIVE` и поставить событие `mandate.activated` в очередь нотификаций.
- While согласие `ACTIVE`, when ТСП инициирует списание в пределах лимитов и с выполненным предуведомлением, the СБП-шлюз shall создать платёж, вернуть `paymentId` за p95 < 500 мс и перевести платёж по общему пути `PAID → CREDITED → COMPLETED`.
- When нотификация ОПКЦ подтверждает рекуррентное списание, the СБП-шлюз shall выполнить переход `CREATED → PAID` и инициировать зачисление в АБС **только** из `PAID` (AD-005).
- When ТСП запрашивает статус согласия (`GET /v1/mandates/{id}`), the СБП-шлюз shall вернуть актуальный статус согласия за p95 < 300 мс.

### 1.2 Негативные и граничные

- If согласие не в статусе `ACTIVE` (`PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`REJECTED`/`EXPIRED`), then the СБП-шлюз shall отклонить списание кодом `MANDATE_NOT_ACTIVE` **без вызова ОПКЦ**.
- If сумма списания превышает `maxAmountPerDebit` или сумма за период превышает `maxAmountPerPeriod`, then the СБП-шлюз shall отклонить списание кодом `MANDATE_LIMIT_EXCEEDED`.
- If требование предварительного уведомления не выполнено (нарушен lead time), then the СБП-шлюз shall отклонить инициацию кодом `PRE_NOTIFICATION_REQUIRED`.
- When ТСП повторяет списание с тем же (`mandateId`, `billingPeriod`), the СБП-шлюз shall вернуть ранее созданный `paymentId` и **не создавать второе списание** (property: «две инициации с одним периодом → ровно одно списание»).
- If тот же (`mandateId`, `billingPeriod`) приходит с другим телом, then the СБП-шлюз shall вернуть `409 DUPLICATE_BILLING_PERIOD`.
- When приходит событие отзыва согласия, the СБП-шлюз shall немедленно запретить новые списания и зафиксировать отзыв в аудит-логе; после отзыва число новых списаний = **0**.
- If списание находится «в полёте» на момент отзыва, then the СБП-шлюз shall не выполнять слепой повтор, а дозапросить статус у ОПКЦ (исход `UNKNOWN` разрешается в `PAID`/`FAILED`).
- When плательщик отклоняет конкретное списание, the СБП-шлюз shall перевести платёж в `FAILED` с `errorCode=PAYER_REJECTED`, при этом согласие остаётся `ACTIVE`.
- While согласие `ACTIVE`, if ОПКЦ недоступен, then the СБП-шлюз shall не терять операцию (DLQ + сверка), а двойное списание за период остаётся = 0.
- When ТСП создаёт разовый платёж без `mandateId`, the СБП-шлюз shall обработать его как прежде (регрессия базовых NFR и статусов без изменений).

## 2. Критерии совместимости контрактов (машинные)

- When выполняется `contract_diff` v0.1.0 → v0.2.0, then breaking-изменений (`CD-001..CD-010`) shall быть **0**.
- When выполняется `openapi_lint` на `openapi/tsp-api.yaml` v0.2.0, then итог shall быть PASS.
- If потребитель не разбирает неизвестные типы вебхуков, then доставка событий `mandate.*` shall быть выключена (opt-in) и разовый приём shall не ломаться.

## 3. Property-тесты (исполняемые, на фейках внешних систем)

| Свойство | Фейк | Ожидание | Нарушающая реализация обязана упасть |
|---|---|---|---|
| Дедупликация обязательства | Фейк ОПКЦ со счётчиком | Повтор (`mandateId`,`billingPeriod`) → ровно 1 вызов ОПКЦ | Да |
| Отзыв запрещает списания | Фейк с событиями | После `mandate.revoked` → 0 вызовов списания | Да |
| Лимиты согласия | Фейк ОПКЦ | Списание сверх лимита → вызов ОПКЦ не сделан | Да |
| Зачисление только из `PAID` | Фейк АБС со счётчиком | Зачисление недостижимо из `CREATED`/`QR_ISSUED` | Да |

Проверка «зубов» правил: `arch-be rules template verify` / `verify --dir <кейс>` — тест, зелёный при любом поведении, не принимается.

## 5. План отката

**Сигналы отката (триггеры):**
1. Зафиксировано **двойное списание** за один (`mandateId`, `billingPeriod`) в проде.
2. Зафиксировано списание **после отзыва** согласия (алерт «списание после отзыва»).
3. Доля отказов инициации/активации согласий выше согласованного порога, или деградация базового разового приёма (латентность/ошибки) от подписок.
4. Вендор/ОПКЦ не подтвердил корректность операций подписок на тестовом контуре.

**Шаги отката (по возрастанию жёсткости):**
1. **Stop-new** — выключить флаг подписок для новых ТСП: новые согласия и списания не принимаются; **уже открытые операции дорабатываются** (не бросаем «в полёте»).
2. **Freeze debits** — запретить инициацию новых списаний по всем согласиям; существующие согласия переводятся в `SUSPENDED`/`REVOKED` по решению владельца.
3. **Rollback релиза** — rolling-откат сервиса согласий и API-расширения; **разовый приём не затрагивается** (аддитивность).
4. **Данные** — согласия не удаляются (нужны для аудита 152-ФЗ); миграция обратно не требуется. Разовый контур продолжает работу на v0.1-контракте.

**Владелец решения об откате:** solution-architect + владелец продукта (совместно); исполнение — SRE/дежурная смена по runbook.

**Критерий успешного отката:** базовый разовый приём соответствует исходным NFR; по подпискам нет новых списаний; данные согласий сохранены и доступны для аудита; отчёт «списание после отзыва = 0» зелёный.

## 6. Definition of Done (гейты)

- **A1:** `docs/spec/mandate-lifecycle.md`, `docs/nfr-sbp-subscriptions.md`, контракты v0.2 согласованы.
- **A2:** walking skeleton «согласие → активация → списание → зачисление» на моках.
- **A3:** принято человеческое решение (`A3-PACKAGE.md`), ADR-008/009 переведены в Accepted, AD-009 ратифицирован.
- **A4:** fitness PASS, property-тесты (с проверкой зубов) PASS, `contract_diff` = 0 breaking, `openapi_lint` PASS.
- **A5:** прод-наблюдение; «двойное списание за период = 0», «списание после отзыва = 0», сверка согласий с ОПКЦ — без расхождений 30 дней.
