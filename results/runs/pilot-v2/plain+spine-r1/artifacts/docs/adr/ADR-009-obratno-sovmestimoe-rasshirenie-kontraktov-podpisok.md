# ADR-009. Обратно совместимое расширение контрактов (API ТСП и адаптер ОПКЦ) для подписок

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур)
- Related: ADR-004, ADR-007, ADR-008, AD-004, AD-008
- Supersedes: —

## Context

ADR-008 добавляет согласия и рекуррентные списания. Это затрагивает два контракта: **API ТСП** (`openapi/tsp-api.yaml`, v0.1 draft) и **внутренний контракт адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md` — граница с вендорским транспортом, AD-008). API ТСП уже имеют потребители (ТСП), а контракт адаптера — основа RFP; оба нельзя ломать произвольно.

Силы: расширение должно быть **аддитивным** (существующие ТСП не переписывают интеграцию); enum-поля в уже отдаваемых ответах нельзя расширять незаметно для строгих потребителей; контракт адаптера обязан остаться единственной зависимостью ядра от транспорта (AD-004); проверяемость — ломающие изменения должны ловиться машиной до релиза (`contract_diff`).

## Decision

1. **API ТСП остаётся в `/v1`; существующие операции и схемы не изменяются.** Новые возможности добавляются как новые ресурсы/пути: `/v1/mandates`, `/v1/mandates/{mandateId}`, `/v1/mandates/{mandateId}/revoke`, `/v1/mandates/{mandateId}/debits`.
2. **Инициация рекуррентного списания — отдельный endpoint** `POST /v1/mandates/{mandateId}/debits`, который создаёт обычный платёж и возвращает `paymentId`. Существующий `POST /v1/payments` не перегружается условной семантикой подписки.
3. **Enum `Payment.status` не расширяется.** Отказ плательщика по конкретному списанию — это `FAILED` + `errorCode = PAYER_REJECTED`; жизненный цикл согласия вынесен в отдельный ресурс `Mandate` со своим enum. Это исключает ломающее изменение для потребителей с исчерпывающим разбором `status`.
4. **В `Payment` добавляются только опциональные поля** (`mandateId`, `billingPeriod`, `paymentType`); в запросы существующих операций — ничего обязательного.
5. **Новые типы вебхуков** (`mandate.activated`, `mandate.rejected`, `mandate.revoked`) — аддитивны; потребители обязаны игнорировать неизвестные типы. Доставка событий подписок **включается флагом ТСП (opt-in)**, чтобы не ломать строгих потребителей, считающих неизвестный тип ошибкой. Отказ по списанию доставляется существующим `payment.failed`.
6. **Новые коды ошибок** (`MANDATE_NOT_ACTIVE`, `MANDATE_LIMIT_EXCEEDED`, `MANDATE_REVOKED`, `DUPLICATE_BILLING_PERIOD`, `PRE_NOTIFICATION_REQUIRED`) — аддитивны, формат RFC 9457 без изменений.
7. **Контракт адаптера ОПКЦ расширяется новыми операциями и событиями согласий** (единственная зависимость ядра от транспорта, AD-004); поддержка операций подписок — обязательное требование RFP (constraints AD-008).
8. **Ломающие изменения — только в `/v2`** с периодом поддержки обеих версий ≥ 6 мес (политика v0.1 сохраняется).
9. **Доказательство совместимости** — машинное: `contract_diff` (старая→новая версия) не должен показывать ни одного `CD-001..CD-010`; `openapi_lint` — PASS. Отчёт прикладывается к evidence-бандлу гейта A4.

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **Отдельный ресурс `mandates` + endpoint списания** (выбран) | Явная семантика; естественная дедупликация по согласию; изоляция нового от старого; возвращает `paymentId` → общий retrieval/вебхуки | Больше путей в контракте | — |
| Добавить подписки в `POST /v1/payments` условными полями | Меньше сущностей | Перегрузка семантики; условная валидация; риск регресса существующих потребителей; лимиты согласия некуда «повесить» | Риск ломать работающую интеграцию |
| Расширить enum `Payment.status` значениями вроде `PENDING_CONSENT` | Всё «в одном поле» | Ломает строгих потребителей (exhaustive switch); смешивает жизненные циклы платежа и согласия | Совместимость важнее удобства |
| Немедленно выпустить `/v2` для всего API | Чистая граница версий | Массовая миграция потребителей без необходимости; изменения аддитивны | Избыточная цена |

## Consequences

### Positive

- Существующие потребители не переписывают интеграцию; регресс разового приёма сведён к нулю.
- Совместимость проверяема механически (`contract_diff`/`openapi_lint`) — не «на глаз».
- Граница ядро↔транспорт сохранена: вся протокольная специфика подписок уходит в адаптер (AD-004).

### Negative

- API растёт числом ресурсов — нужна дисциплина владения (`mandates` — отдельный домен внутри шлюза).
- Opt-in вебхуков усложняет конфигурацию ТСП и матрицу тестов (два режима доставки).
- Расширение контракта адаптера добавляет обязательное требование к вендору — сужает пул вендоров и влияет на сроки (constraint AD-008).

## Reversibility

**reversible.** Контракт расширяется аддитивно: новые пути/поля/события можно не включать (opt-in), существующие — не менялись. Отказ от подписок = выключить флаг и новые ресурсы; версия `/v1` остаётся валидной. Ломающая эволюция (если понадобится) — только через `/v2`, как и было принято.

**Условие/срок пересмотра:** при появлении требования жёсткой изоляции подписок в отдельный API-продукт или при переходе к `/v2` по иным причинам.
