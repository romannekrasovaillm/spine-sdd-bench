# Жизненный цикл согласия плательщика (mandate) — спецификация

- Status: Draft (для ревью на гейте A1 дельты «подписки СБП»)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, ADR-002, AD-002, AD-003, AD-005, AD-009 (spine)

Единый источник истины состояния согласия — БД шлюза (AD-002). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог». Повторные триггеры идемпотентны (AD-003).

## 1. Состояния согласия

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_CONSENT` | Согласие зарегистрировано, плательщик ещё не подтвердил | да |
| `ACTIVE` | Согласие подтверждено плательщиком; списания разрешены в пределах лимитов | да |
| `SUSPENDED` | Временно приостановлено (плательщиком/банком плательщика); новые списания запрещены | да |
| `REVOKED` | Отозвано; списания запрещены навсегда | да |
| `REJECTED` | Плательщик отказал в согласии при подтверждении | да |
| `EXPIRED` | Истёк срок действия согласия | да |

Терминальные: `REVOKED`, `REJECTED`, `EXPIRED`. `SUSPENDED` — не терминальное (возврат в `ACTIVE` возможен).

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие при переходе |
|---|---|---|---|---|---|
| M1 | — | `PENDING_CONSENT` | `POST /v1/mandates` (новый `mandateId`) | ТСП активен; лимиты заданы валидно | запись согласия + outbox «регистрация согласия в ОПКЦ» + аудит |
| M2 | `PENDING_CONSENT` | `ACTIVE` | событие ОПКЦ `mandate.activated` (плательщик подтвердил) | ссылка на подтверждение непуста | сохранить артефакт подтверждения (ссылку/хеш), outbox `mandate.activated`, аудит |
| M3 | `PENDING_CONSENT` | `REJECTED` | событие ОПКЦ `mandate.rejected` | — | `reasonCode`, outbox `mandate.rejected`, аудит |
| M4 | `PENDING_CONSENT` | `EXPIRED` | таймер срока подтверждения | не подтверждено | закрытие в ОПКЦ (по протоколу), аудит |
| M5 | `ACTIVE` | `SUSPENDED` | событие ОПКЦ (приостановка) | — | запрет новых списаний, outbox, аудит |
| M6 | `SUSPENDED` | `ACTIVE` | событие ОПКЦ (возобновление) | — | снятие запрета, outbox, аудит |
| M7 | `ACTIVE`/`SUSPENDED` | `REVOKED` | событие отзыва (плательщик/НСПК) ИЛИ ТСП-отзыв (`POST .../revoke`) | — | **немедленный запрет новых списаний**, outbox `mandate.revoked`, аудит |
| M8 | `ACTIVE` | `EXPIRED` | истёк срок согласия | — | запрет новых списаний, аудит |

## 3. Инварианты (запрещённые состояния/переходы)

- **Рекуррентное списание возможно только из `ACTIVE`** (AD-009). Из `PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`REJECTED`/`EXPIRED` — недостижимо; проверяется fitness-тестом.
- **Отзыв необратим**: `REVOKED` — терминальное, реактивации нет. Возобновление — только новым согласием (M1).
- **Одно списание за (mandateId, billingPeriod)**: повтор с тем же ключом не создаёт второе списание (AD-009).
- **Лимиты согласия непреодолимы**: сумма списания и сумма за период не превышают лимиты согласия.
- **Предуведомление обязательно** при инициации: не выполнено — списание не регистрируется. Проверяемый шлюзом прокси: окно `plannedDebitDate − now ≥ notificationLeadHours` согласия; при `notificationLeadHours > 0` поле `plannedDebitDate` в запросе списания **обязательно**. Доставку уведомления плательщику выполняет банк плательщика/НСПК по регламенту; если регламент возлагает уведомление на мерчанта — это отдельная операция адаптера `[ТРЕБУЕТ ПРОВЕРКИ]`. Согласие нельзя подтвердить без ссылки на подтверждение (M2) — согласие без доказуемого основания недействительно (152-ФЗ).

## 4. Маппинг «списание → платёж»

Рекуррентное списание создаёт платёж в существующей статусной машине (`docs/spec/state-machine.md`): `CREATED → QR_ISSUED? → PAID → CREDITED → COMPLETED`.

- Для рекуррентного списания стадия `QR_ISSUED` не используется: платёж регистрируется сразу в ОПКЦ как рекуррентное списание (через адаптер, AD-004); внешний статус до `PAID` — `CREATED` (ТСП видит как «в обработке»).
- **Зачисление — только из `PAID`** (AD-005, без изменений).
- Отказ плательщика по конкретному списанию → платёж `FAILED` + `errorCode=PAYER_REJECTED`; **согласие остаётся `ACTIVE`** (отказ по одному списанию ≠ отзыв согласия).
- Списание «в полёте» при отзыве → исход `UNKNOWN` → дозапрос статуса у ОПКЦ, без слепого повтора; результат — `PAID`/`FAILED`.

## 5. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| Событие ОПКЦ по согласию | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| `POST .../debits` | `Idempotency-Key` **и** (`mandateId`, `billingPeriod`) | возврат ранее созданного `paymentId`; второе списание за период не создаётся |
| `POST .../revoke` | `Idempotency-Key` | повторный отзыв идемпотентен (уже `REVOKED`) |

Окно хранения ключа (`mandateId`, `billingPeriod`) — **не менее срока жизни согласия** (отличие от 24-часового окна идемпотентности платежа).

## 6. Сверка и восстановление

- Открытые согласия (`PENDING_CONSENT`, `ACTIVE`, `SUSPENDED`) — кандидаты для сверки с ОПКЦ по регламенту: «у НСПК отозвано, у нас `ACTIVE`» → немедленный `REVOKED` + алерт (риск списания после отзыва).
- Расхождения по лимитам/срокам согласия — в отчёт незавершённых операций.
- Согласие в `ACTIVE` при недоступном ОПКЦ — остаётся `ACTIVE`, но инициация списаний не проходит (транзиентный отказ), операции не теряются (DLQ + сверка, ADR-004).

## 7. Открытые вопросы

1. Точный состав атрибутов согласия и обязательный lead time предуведомления — по документации НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`.
2. Возможность нескольких активных согласий на одну пару (плательщик, ТСП, назначение) — уточняется по регламенту НСПК.
3. Хранение артефакта подтверждения согласия: ссылка vs хеш vs подписанный документ — решение ИБ/юриста (152-ФЗ).
