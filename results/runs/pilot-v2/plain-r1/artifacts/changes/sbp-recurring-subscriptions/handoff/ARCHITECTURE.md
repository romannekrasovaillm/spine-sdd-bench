# Архитектурный контекст (epic-context) — «СБП-подписки»

Дистиллят для исполнителя: цель, стыки, инварианты. Источник истины — репозиторий; здесь — только необходимое, чтобы реализовать **без архитектурных изобретений**. Полные тексты: `../../ARCHITECTURE-SPINE.md`, `../../docs/adr/ADR-008-recurring-c2b-subscriptions.md`, `../../docs/spec/mandate-lifecycle.md`, `../../openapi/tsp-api.yaml`.

## Цель и границы

Банк — эквайер C2B СБП. Добавляем **рекуррентные списания по согласию плательщика**: мандат (согласие) → подписка → периодическое списание, инициируемое банком. Базовая топология сохраняется: **ядро шлюза (собственная разработка) + вендорский адаптер ОПКЦ**; протокол НСПК ядро не знает.

**Стыки (контракты, менять только по спецификации):**
- ТСП ↔ ядро: REST/JSON, `openapi/tsp-api.yaml` (аддитивное расширение; `Idempotency-Key` обязателен для `POST`).
- Ядро ↔ адаптер ОПКЦ: `docs/contracts/opkc-adapter.md` (методы `registerMandate/getMandateStatus/revokeMandate/createCharge`; события `mandate.*`, `charge.*`; at-least-once, дедуп по `eventId`).
- Ядро ↔ АБС: идемпотентное списание по `chargeId`, зачисление по `paymentId`.

**Запрещено менять (принятые решения):** AD-008 [ADOPTED] (контрактная независимость транспорта, стратегия hybrid); стратегию ADR-007; значения `Payment.status` и существующие поля контракта; зачисление вне `PAID`.

## Инварианты (Rule — дословно; конфликт с ними = остановка и эскалация)

- **AD-002.** «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера.»
- **AD-003.** «Повторная доставка любого сообщения не изменяет уже завершённое состояние.»
- **AD-005.** «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус).»
- **AD-008 [ADOPTED].** «Ядро шлюза проектируется контрактно-независимым от транспорта (внутренний контракт адаптера ОПКЦ — единственная зависимость).»
- **AD-009 (новая).** «Периодическое списание выполняется только при мандате в состоянии `ACTIVE`; отзыв и истечение блокируют новые списания.»
- **AD-010 (новая).** «Ключ идемпотентности списания — `(mandateId, subscriptionId, billingPeriod)`; повторная инициатива или доставка не создаёт вторую операцию.»
- **AD-011 (новая).** «Событие отзыва (плательщиком или ТСП) переводит мандат в `REVOKED` и запрещает новые списания не позднее 60 с (p99); отзыв фиксируется в неизменяемом аудит-логе.»

## Ключевые переходы

- Мандат: `DRAFT→PENDING_PAYER→ACTIVE→SUSPENDED→REVOKED|EXPIRED` (таблица M1–M9, `docs/spec/mandate-lifecycle.md`).
- Платёж по подписке: `—→CREATED` (ядро, T13) → `CREATED→PAID` (подтверждение списания НСПК, T14) → `PAID→CREDITED→COMPLETED` (общие). `QR_ISSUED` на рекуррентном пути не используется.
- Отзыв мандата: `ACTIVE|SUSPENDED→REVOKED`; связанные подписки → `PAUSED`.

## Негативные сценарии (обязательны к реализации и тестам)

Повтор инициативы за тот же период (нет двойного списания); списание по `REVOKED`/`SUSPENDED` мандату → `MANDATE_NOT_ACTIVE`; превышение `maxAmount` → `MANDATE_LIMIT_EXCEEDED`; АБС недоступна → платёж остаётся `PAID` и зачисляется ровно один раз после восстановления; повтор `eventId` — игнорируется; поздняя нотификация — не откатывает завершённое состояние.

## NFR (критерии приёмки, детали — `../../docs/nfr.md` §7)

Инициация списания p95 < 500 мс; sustained 200 TPS / пик 500 TPS; двойных списаний — 0; лаг запрета после отзыва ≤ 60 с (p99); RPO=0; расхождений сверки с НСПК/АБС — 0.
