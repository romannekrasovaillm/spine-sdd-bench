# Задача для кодового харнесса — рекуррентные C2B-списания («СБП-подписки»)

> **Гейт.** Не начинать реализацию до человеческого решения A3 (ADR-008 переведён в `Accepted`, блоки AD-009…AD-011 ратифицированы в spine). До этого пакет — материал для A3, а не задание в работу.

Реализовать поверх walking skeleton платёжного шлюза СБП (см. `.arch-handoff/TASK.md`) функционал рекуррентных списаний по согласию плательщика:

1. **Мандат (согласие плательщика)** — объект ядра с конечным автоматом `DRAFT → PENDING_PAYER → ACTIVE → SUSPENDED → REVOKED | EXPIRED`, атомарные переходы «статус + outbox + аудит» (AD-002), идемпотентность по `Idempotency-Key` и `eventId`.
2. **Подписка** — связка «мандат ↔ ТСП» (период, фиксированная сумма, лимит `maxAmount`), активируется только при мандате `ACTIVE`.
3. **Периодическое списание** — платёж, **инициируемый ядром** (рекуррентный оркестратор/планировщик или ручной `POST /v1/subscriptions/{id}/charges`); проводится по существующей статусной машине платежа (`CREATED → PAID → CREDITED → COMPLETED`); зачисление — **только из подтверждённого `PAID`** (AD-005 не ослабляется).
4. **Идемпотентность списания** — ключ `(mandateId, subscriptionId, billingPeriod)`: повторная инициатива/доставка не создаёт второй платёж/проводку.
5. **Отзыв мандата** — событие от НСПК или ТСП (`POST /v1/mandates/{id}/revoke`) переводит мандат в `REVOKED` и запрещает новые списания (цель ≤ 60 с, p99); списание в полёте — по саге.
6. **API ТСП** — новые ресурсы `mandates`/`subscriptions`/`charges` строго по `openapi/tsp-api.yaml` (аддитивно; существующие методы и значения `Payment.status` не менять).
7. **Мок-адаптер ОПКЦ** — дополнить методами `registerMandate`, `getMandateStatus`, `revokeMandate`, `createCharge` и событиями `mandate.*`, `charge.*`; реальный протокол НСПК НЕ реализуется (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`), ядро контрактно-независимо от транспорта (AD-008).
8. **АБС-мок** — списание по `chargeId` идемпотентно; зачисление по `paymentId` (как в базовом skeleton).
9. **Вебхуки/нотификации ТСП** — события `mandate.pending/activated/revoked/expired`, `charge.failed`, `payment.completed` с ретраями и DLQ; дедупликация по `eventId`.

Соблюсти spine-инварианты AD-001…AD-011 (AD-009…AD-011 — новые). Критерии приёмки — NFR `docs/nfr.md` §7 (выполнимы на моках) и чек-лист `../DELTA.md` («Критерии приёмки»). Технологический стек — по выбору команды с обоснованием в ADR; приоритет — доказать сквозной сценарий подписки и отсутствие двойных списаний.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми решениями (ADR/spine). **Обязан останавливать работу и эскалировать** — молчаливое отклонение от AD-002/003/005/009/010/011 недопустимо.

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml`.
