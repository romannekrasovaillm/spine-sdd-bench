## Проблема

Сегодня приём C2B в СБП — одноразовый: каждый платёж требует QR/ссылки и действия плательщика. ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные списания по согласию плательщика** (подписки СБП): плательщик один раз оформляет согласие (мандат), далее списания инициирует банк-эквайер по поручению ТСП — без участия плательщика в каждом периоде. Изменение добавляет мандатную модель (`мандат → подписка → периодическое списание`) поверх принятого решения, не меняя базовую топологию и статусную модель платежа.

## ADDED

- **Мандат (согласие плательщика) — объект ядра.** Требование AD-009: `When ТСП запрашивает оформление подписки, the СБП-шлюз shall зарегистрировать мандат и вернуть ссылку/QR на подписание ≤ 500 мс (p95, без времени НСПК).` Жизненный цикл: `DRAFT → PENDING_PAYER → ACTIVE → SUSPENDED → REVOKED|EXPIRED`.
- **Подписка и периодическое списание.** Требование AD-010: `When мандат ACTIVE и наступил расчётный период, the шлюз shall инициировать списание по подписке ровно один раз за период.` Идемпотентность списания: ключ `(mandateId, subscriptionId, billingPeriod)`.
- **Инициация платежа ядром.** `When подписка активна, the шлюз shall создать платёж в состоянии CREATED без входящего запроса ТСП и провести его по существующей статусной машине (без QR_ISSUED).`
- **Отзыв мандата.** Требование AD-011: `When поступает отзыв мандата (плательщик в своём банке или ТСП через API), the шлюз shall запретить новые списания по мандату ≤ 60 с (p99) и отразить отзыв в аудит-логе.`
- **Контрактные сущности** (аддитивно, `openapi/tsp-api.yaml`): `/v1/mandates`, `/v1/mandates/{mandateId}`, `/v1/mandates/{mandateId}/revoke`, `/v1/subscriptions`, `/v1/subscriptions/{subscriptionId}`, `/v1/subscriptions/{subscriptionId}/charges`; схемы `Mandate`, `Subscription`, `Charge`.
- **Расширение внутреннего контракта ОПКЦ** (`docs/contracts/opkc-adapter.md`): регистрация/статус/отзыв мандата, инициация списания, нормализованные события `mandate.*`, `charge.*`; требование к вендору/RFP — дополнение к существующему контракту.
- **NFR рекуррентного контура** (`docs/nfr.md`, §7): латентности оформления/инициации, `двойных списаний — 0`, лаг распространения отзыва.

## План отката

1. Сигнал: рост двойных списаний / отказов зачисления по подпискам, массовый отзыв мандатов без остановки списаний, расхождения сверки с НСПК по `chargeId`.
2. **Stop-new**: выключить приём новых мандатов и новых списаний (фиче-флаг `recurring.enabled=false`); уже открытые подписки — перевести в `SUSPENDED` без списаний.
3. Действующие операции доводятся по существующему контуру (списание в полёте — до `CREDITED`/сага возврата); данные мандатов сохраняются до полной сверки (шлюз — источник истины).
4. Контрактные эндпоинты не удаляются физически: на период отката отвечают `403 RECURRING_DISABLED` (обратимо, без ломающего релиза).
5. Владелец решения об откате — solution-архитектор платёжного контура + бизнес-владелец продукта; аварийные сигналы обрабатываются по runbook (DLQ → дежурная смена).

## Критерии приёмки

- [ ] Позитив: ТСП регистрирует мандат → плательщик подписывает → мандат `ACTIVE` → платёж по подписке проведён `PAID→CREDITED→COMPLETED` (E2E на моках/тестовом контуре НСПК).
- [ ] Негатив (дубль): повторная нотификация `PAID`/повторная инициация списания за тот же период → двойного зачисления/списания нет (идемпотентность).
- [ ] Негатив (отзыв): списание по `REVOKED`/`SUSPENDED` мандату отклоняется с `MANDATE_NOT_ACTIVE`.
- [ ] Негатив (лимит): списание сверх лимита мандата отклоняется с `MANDATE_LIMIT_EXCEEDED`.
- [ ] Негатив (сосед): АБС недоступна → платёж остаётся `PAID`, попадает в сверку, при восстановлении — зачисляется ровно один раз.
- [ ] Сверка: расхождений по завершённым подпискам/списаниям с НСПК и АБС — 0.
- [ ] Откат: `recurring.enabled=false` останавливает новые списания, открытые операции завершаются штатно; критерий успешного отката — 0 незавершённых подписочных операций после сверки.
