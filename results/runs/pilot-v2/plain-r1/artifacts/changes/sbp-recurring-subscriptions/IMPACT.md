# Влияние на принятую архитектуру — «СБП-подписки»

- Дата: 2026-09-28
- База: `ARCHITECTURE-SPINE.md` (AD-001…AD-008), `docs/adr/ADR-001…007`, `docs/solutioning.md`, `docs/spec/state-machine.md`, `docs/contracts/*`.
- Принцип: изменение **аддитивно**; базовая топология и модель одноразового платежа не пересматриваются.

## 1. Сводка по инвариантам spine

| Инвариант | Затронут | Что меняется | Что НЕ меняется |
|---|---|---|---|
| **AD-001** Изоляция платёжного контура | косвенно | Рекуррентный оркестратор и реестр мандатов живут **внутри** платёжного контура шлюза; доступ к АБС/ОПКЦ — по-прежнему только через адаптеры | Правило «единая точка вызова» АБС/ОПКЦ; RPO=0 |
| **AD-002** Единый источник истины, атомарные переходы | **ДА** | Жизненный цикл мандата/подписки — тоже конечный автомат с транзакцией «статус + outbox + аудит»; появляются переходы платежа, инициированные ядром (T13/T14) | Формула перехода (атомарность, outbox+аудит в одной транзакции) |
| **AD-003** Идемпотентность финансовых операций | **ДА** | Новые ключи идемпотентности: списание `(mandateId, subscriptionId, billingPeriod)`, события мандата — по `eventId`, регистрация мандата/подписки — по `Idempotency-Key` | Принцип «повторная доставка не меняет завершённое состояние» |
| **AD-004** Единственный адаптер ОПКЦ | **ДА** | Контракт адаптера расширяется методами/событиями мандатов и списаний; протокол НСПК по-прежнему знает только адаптер | Единственность адаптера; нормализация статусов/ошибок |
| **AD-005** Зачисление только из `PAID` | сохраняется, усиливается | Рекуррентное списание обязано пройти собственный `PAID` перед зачислением; списаний «напрямую по мандату» нет | Инвариант «нет финансового следствия без подтверждения» |
| **AD-006** Trust-зоны и сегментация | косвенно | Мандат содержит согласие + ПДн: минимизация, шифрование в покое, 4-eyes для ручных операций с мандатами | Состав trust-зон и правила межзонного доступа |
| **AD-007** НПС/КИИ/ПДн | **ДА** | Правовое основание согласия, аудит отзыва/изменения мандата, пороги AML для рекуррента | Обязательность соответствия (не обсуждается) |
| **AD-008** Стратегия реализации (hybrid) [ADOPTED] | **НЕ меняется** | Ядро остаётся контрактно-независимым от транспорта; мандатная модель — в ядре, протокол мандатов — в вендорском адаптере | Сам [ADOPTED]-инвариант; переопределение родительских ограничений запрещено |

## 2. Что меняется в компонентах (C4, поверх `docs/solutioning.md` §2)

- **Ядро шлюза**: добавляются логические компоненты «Реестр мандатов» и «Рекуррентный оркестратор/планировщик»; существующая «Статусная машина платежа» переиспользуется для подписочных платежей.
- **API ТСП**: новые ресурсы `mandates`/`subscriptions`/`charges` (аддитивно).
- **Адаптер ОПКЦ**: новые синхронные методы (регистрация/статус/отзыв мандата, инициация списания) и асинхронные события (`mandate.*`, `charge.*`) — расширение `docs/contracts/opkc-adapter.md`; требование к вендору и RFP.
- **АБС-адаптер**: существующее идемпотентное списание/зачисление переиспользуется; для списания по подписке ключ идемпотентности = `chargeId` (шлюза).
- **Сверка**: к сверке с НСПК добавляются мандаты и списания (выписка операций по подпискам).

## 3. Что НЕ меняется (границы изменения)

- Топология (AD-001): те же trust-зоны и адаптеры; новых внешних контуров нет.
- Канонические состояния платежа `CREATED…COMPLETED`, терминальные `FAILED/EXPIRED/REFUNDED` — без изменений; `QR_ISSUED` просто не используется для списаний по подписке.
- Модель возвратов (сага) — без изменений (возврат подписочного платежа — обычный возврат по `paymentId`).
- Стратегия реализации ADR-007 (hybrid) и AD-008 [ADOPTED] — без пересмотра.
- Публичные значения `Payment.status` — без добавления (см. §4 контракта): это защищает строгих потребителей.

## 4. Риски влияния

| Риск | Механизм митигации |
|---|---|
| Разрастание AD-002 на второй автомат (мандат) без общей дисциплины | Общая библиотека переходов «статус+outbox+аудит»; fitness-тесты на переходы мандата. |
| Незаконное списание при рассинхроне состояния мандата с НСПК | Отзыв мандата блокирует новые списания; сверка мандатов; алерт на списание по неактивному мандату. |
| Двойное списание при ретраях планировщика | Идемпотентность `(mandateId, subscriptionId, billingPeriod)` + дедуп событий по `eventId`. |
| Расширение ПДн в контуре | Минимизация, шифрование, маскирование в логах, ИБ-ревью (AD-006/AD-007). |
