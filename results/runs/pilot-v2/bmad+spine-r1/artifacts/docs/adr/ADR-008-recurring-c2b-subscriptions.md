# ADR-008. Рекуррентные C2B-списания (подписки СБП): расширение ядра шлюза согласиями плательщика

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + владелец продукта подписок
- Модель-автор: qwen-code
- Related: ADR-001, ADR-002, ADR-004, ADR-005, ADR-007, AD-002, AD-003, AD-004, AD-005, AD-008, AD-009, AD-010

## Context

Бизнес-задача: ТСП (онлайн-кинотеатры, ЖКХ, операторы связи) просят **рекуррентные C2B-списания по согласию плательщика** (подписки СБП). Сейчас каждый платёж C2B требует QR/ссылки и действия клиента в приложении банка плательщика — модели подписки это не поддерживает.

Сервис подписок СБП вводит новый объект — **согласие плательщика** (mandate): договорённость ТСП и плательщика на периодические списания в заданных пределах, подтверждаемая плательщиком в банке-эмитенте через НСПК. После активации ТСП инициирует списание **без участия клиента** на каждую операцию.

Силы и ограничения:
- **Основание списания** — только действующее согласие. Списание без согласия или сверх его лимитов недопустимо (161-ФЗ, правила ОПКЦ, права плательщика).
- **Согласие — финансовый документ** (авторизация списаний), его доказательство должно быть доказуемо перед плательщиком, ТСП и регулятором; нарушение = правовой и регуляторный риск.
- **Внешний вход**: точный протокол НСПК по подпискам публично не раскрыт — `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **Вендорская зависимость**: транспорт к ОПКЦ — вендорский модуль (ADR-007, AD-008); подписки требуют новых операций протокола, которые вендор обязан поддержать.
- **Наследуемые инварианты**: изоляция платёжного контура (AD-001), единая статусная машина и атомарные переходы (AD-002), идемпотентность (AD-003), единственный адаптер ОПКЦ (AD-004), зачисление только из подтверждённого статуса (AD-005).

## Decision

1. **Согласие плательщика — объект первого класса в БД шлюза** (реестр согласий) внутри изолированного платёжного контура (AD-001). Своя статусная модель `PENDING → ACTIVE → SUSPENDED | REVOKED | EXPIRED`, переходы атомарны (статус + outbox + аудит, AD-002).
2. **Рекуррентное списание — подвид платежа**, переиспользует существующую статусную машину (`CREATED → PAID → CREDITED → COMPLETED`, терминальные `FAILED/EXPIRED/REFUNDED`) и правила зачисления (AD-005). Отдельная денежная модель не вводится.
3. **Обязательный guard согласия**: инициация списания и зачисление возможны только при согласии в статусе `ACTIVE`, покрывающем ТСП, сумму и периодичность (AD-009). Отзыв согласия немедленно и идемпотентно блокирует новые списания.
4. **Новые транспортные операции** (регистрация/активация и отзыв согласия, инициация и статус списания) выполняются **только** через адаптер ОПКЦ (AD-004); ядро остаётся контрактно-независимым (AD-008). Внутренний контракт `docs/contracts/opkc-adapter.md` расширяется аддитивно; поддержка подписок — обязательный критерий RFP вендора. Протокольные детали — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации НСПК.
5. **Контракт ТСП расширяется аддитивно** (0.1.0 → 0.2.0): новые пути `/v1/mandates*`, опциональные поля `paymentMethod`/`mandateId` в платеже, новые события вебхуков (`mandate.*`), новые коды ошибок. Существующие пути, схемы и значения `status` не меняются.
6. **Согласие иммутабельно и аудируемо** (AD-010): условия фиксируются, изменение — новое согласие; доказательство согласия хранится весь срок действия согласия и далее — по требованиям регулятора.

## Alternatives Considered

| Вариант | Плюсы | Минусы / почему отвергнут |
|---------|-------|---------------------------|
| **A. Расширить ядро шлюза** (выбран): согласие — сущность шлюза, списание — подвид платежа | Единый источник истины (AD-002), переиспользование статусной машины, outbox, сверки, идемпотентности; зачисление по AD-005 без изменений; минимум нового кода и эксплуатации | Расширяет модель шлюза и БД; требуется аккуратное расширение контрактов и тестов; новый класс чувствительных данных (согласия) в контуре |
| **B. Отдельный сервис «подписки»** (новый bounded context со своей БД и API) | Изоляция жизненного цикла подписок, независимый релизный цикл, своя команда | Второй источник истины для денег → риск рассинхрона с платежами и АБС; дублирование статусной машины/идемпотентности/сверки; cross-service транзакции; усложнение AD-002/AD-005; выше стоимость владения. Для MVP избыточно |
| **C. Полностью вендорское решение подписок** (согласия и списания ведёт вендор) | Быстрый старт, протокол на стороне вендора | Финансовая логика и доказательства согласий уходят вендору — vendor lock-in, ограниченный контроль, сложный аудит для ЦБ; противоречит принятой стратегии «ядро — собственная разработка» (ADR-007, AD-008) |
| **D. Транзитный прокси без хранения согласия** (шлюз только пробрасывает списание по `mandateId`) | Минимум изменений | Невозможно исполнить AD-009 (проверка покрытия лимитов/статуса до списания), нет локального доказательства согласия, ненадёжный отзыв, нечем сверять согласия → регуляторный и правовой риск. Отвергнут |

## Consequences

### Positive

- Единый источник истины: платежи и списания в одной модели, одна сверка, одна идемпотентность (AD-002/AD-003).
- Зачисление по-прежнему только из подтверждённого НСПК статуса — модель «платежей из воздуха» не расширяется (AD-005 сохраняется).
- Согласие проверяемо и аудируемо (AD-009/AD-010) — основа для защиты перед плательщиком и регулятором.
- Контракт ТСП расширяется аддитивно — существующие потребители (одиночные QR) не затрагиваются.
- Новый функционал не требует нового контура: переиспользуются очередь, DLQ, сверка, мониторинг.

### Negative

- Расширение модели данных и контрактов: рост числа состояний/полей, риск усложнить статусную машину — держим согласие отдельным автоматом.
- Новый класс финансово значимых данных (согласия, доказательства) — ужесточение требований к хранению, шифрованию, аудиту (ADR-006).
- Критическая зависимость от вендора транспорта: без поддержки подписок вендором функционал нереализуем (внешняя блокировка).
- Протокол НСПК по подпискам не подтверждён — часть требований живёт как гипотезы до документации НСПК.
- Эксплуатация: рост объёма данных, новые сценарии пиковой нагрузки (массовые списания в дни биллинга), новые runbook-и (отзыв согласия, расхождения по согласиям).
- Отзыв согласия создаёт разрыв «отзыв ↔ уже подтверждённое списание» — нужна явная политика (см. HUMAN-DECISIONS).

## Reversibility

**costly.** До боевой эксплуатации — **reversible**: фича-флаг, отказ от функционала без последствий. После массовой выдачи согласий — **costly**: согласия являются финансовыми документами и не могут быть «отменены» вместе с кодом; откат = политика «stop-new» (запрет новых списаний и регистраций) при сохранении чтения/отзыва уже выданных согласий. Перенос модели согласий в другой сервис/модель потребует по-мандатной миграции с сохранением доказательств. Необратимой миграции данных нет.

**Триггеры пересмотра (expiry):** (а) документация НСПК делает согласие неотделимым от ядра иначе, чем принято; (б) вендор не подтверждает поддержку подписок; (в) регуляторные требования к хранению/форме согласия меняют модель. Плановая ревизия — через 12 месяцев боевой эксплуатации.
