# ADR-009. Исполнение периодических списаний: детерминированный ключ, единственный писатель, dunning

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + SRE платёжного контура
- Related: ADR-001, ADR-002, ADR-004, ADR-005, ADR-008, AD-002, AD-003, AD-005, AD-010, AD-011
- Модель-автор: qwen3-coder

## Context

Подписки (ADR-008) порождают два потока списаний: **плановые** по расписанию (например, первое число месяца) и **по запросу ТСП** для переменных сумм. Планировщик — источник трёх классических отказов: **дубль** (двойное списание), **пропуск** (не списали вовсе) и **шторм** (все подписки в один момент). Шлюз масштабируется горизонтально (NFR: ×2 без перепроектирования), значит несколько инстансов не должны «выстрелить» одним и тем же списанием.

Силы:
- Канал к ОПКЦ СБП — at-least-once; ответ может прийти позже таймаута, исход вызова неопределён (ADR-002: UNKNOWN — «может прошло, может нет»).
- АБС и НСПК деградируют (ADR-004/ADR-005): списание может быть отложено, но не потеряно.
- Повторное списание необратимо для плательщика → цена ошибки выше цены задержки.
- Пиковые дни (первое число, зарплатные периоды) создают всплески нагрузки на АБС/НСПК.

## Decision

1. **Детерминированный идентификатор charge.** `chargeId = f(subscriptionId, periodKey)`, где `periodKey` — нормализованный период, **вычисляемый шлюзом** из расписания подписки (`period`/`dayOfPeriod`) и даты в MSK (`YYYY-MM`, для `WEEKLY` — `YYYY-Www`). `billingReference` ТСП — необязательная корреляционная ссылка, **не** идентификатор периода (ТСП не может «раздробить» период разными ссылками). Повторное планирование, рестарт или параллельный инстанс дают **тот же** `chargeId`; идемпотентность обеспечивается конструкцией, а не удачей (AD-010). `attemptSeq` — подсостояние попытки, новый charge не создаёт.
2. **Единственный писатель на charge.** Планирование выполняется через **транзакционный outbox** (ADR-001, AD-002) и очередь с задержкой; «тик» планировщика защищён **leader election/lease**, а потребители шардируются по **`hash(tspId)`** (bulkhead по ТСП; порядок внутри шарда — по `subscriptionId`). Конкурирующие инстансы не создают дубль: вставка идемпотентна по `chargeId`. Никаких независимых cron-задач на каждом узле.
3. **Изоляция и сглаживание.** Шардирование по `tspId` изолирует «шумного» ТСП (bulkhead); нагрузка сглаживается (queue-based load leveling), а плановые списания раскладываются по **окну списаний** (baseline — несколько часов, а не минуты) с джиттером слота, чтобы портфель не собирался в одну секунду. Конкурирующие потребители дают масштабирование, DLQ — изоляцию ядовитых сообщений. Пропущенные за простой периоды обрабатываются **ограниченной догоняющей очередью (catch-up) с backpressure** по политике (см. `NFR.md` §3) — без «лавины» задним числом.
4. **Повторные попытки и dunning.** Ограниченное число попыток с экспоненциальной задержкой и джиттером; при исчерпании — статус dunning, уведомление ТСП/плательщика, повтор в следующем окне. Конкретика (число попыток, окна, состав уведомлений) — бизнес-решение на A3, фиксируется в ACCEPTANCE/NFR.
5. **Неопределённый исход не повторяется вслепую.** При таймауте вызов трактуется как UNKNOWN и разрешается запросом статуса/сверкой по `chargeId` (переиспользование ADR-004), затем либо продолжение, либо компенсация. Повторная отправка «на удачу» запрещена (avoiding-fallback / unknown-outcome-no-resend).
6. **Переиспользование финансового ядра.** Charge не вводит новой логики зачисления: он создаёт платёж, далее действуют AD-005 (`PAID` → АБС), ADR-005 (возврат сагой), ADR-004 (нотификации/DLQ/сверка). Сверка расширяется цепочкой «мандат ↔ charge ↔ платёж ↔ АБС».
7. **Наблюдаемость и переключатель остановки.** Метрики: запланировано/создано/успешно/дубли/лаг планировщика/глубина DLQ/доля dunning. Отдельный переключатель **stop-new-charges** для отката (см. `ACCEPTANCE.md`).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Детерминированный ключ + единственный писатель + очередь (выбран)** | Дубли исключены по построению; переживает рестарт и масштабирование; сглаживает пики; переиспользует outbox | Нужны leader election/шардирование и очередь с задержкой; сложнее отладка |
| Cron/планировщик на каждом узле без координации | Просто, привычно | Дубли при нескольких инстансах; «все в 00:00» → шторм; рестарт дублирует или теряет |
| Внешний планировщик (платформа/вендор) | Готовое расписание и ретраи | Закрытая логика, иная семантика; не связан с локальной транзакцией шлюза → рассинхрон; lock-in |
| Синхронный batch «списать всё в момент T» | Просто понять | Thundering herd на НСПК/АБС; нет backpressure; хрупко при деградации |
| Только event-driven без детерминированного ключа | Гибкая композиция | at-least-once → дубли; нет гарантии «один charge на период» |

## Consequences

### Positive

- «Один charge на период» доказуемо (детерминированный ключ) и проверяется тестом на фейке.
- Рестарты и масштабирование не приводят к двойным списаниям.
- Пиковые дни сглажены, сбой одной подписки не задерживает поток остальных.
- Сверка, возвраты и идемпотентность АБС переиспользуются без изменения финансовых инвариантов.

### Negative

- Инфраструктурная сложность: очередь с задержкой, leader election/шардирование, DLQ — дополнительная эксплуатационная нагрузка.
- Списание может происходить в окне ±N относительно «идеального» времени — окно нужно согласовать с бизнесом и ТСП.
- Dunning и повторные попытки — новая бизнес-логика и уведомления (владелец — бизнес).
- UNKNOWN-исход требует дисциплины сверки: без неё операция либо «висит», либо рискует двоиться.

## Reversibility

**reversible.** Механику исполнения (очередь, планировщик, шардирование) можно заменить без смены модели мандата (ADR-008) и финансового ядра; ключ идемпотентности и контракт адаптера сохраняются. Отказ от детерминированного ключа был бы costly, но такой необходимости нет.
