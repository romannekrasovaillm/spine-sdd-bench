# Статусная машина подписки и charge — спецификация переходов (дельта)

- Status: Draft (для ревью на гейте A1 дельты)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, AD-009, AD-010, AD-011; дополняет `docs/spec/state-machine.md` (статусная машина платежа)

Домен подписки **отделён** от статусной машины платежа: переходы подписки и charge — атомарные транзакции «смена состояния + запись в outbox + аудит-лог» (AD-002). Charge переиспользует финансовый путь платежа (`PAID` → АБС, AD-005; возвраты-сага, ADR-005).

## 1. Состояния подписки

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_CONSENT` | Подписка создана, ожидается подтверждение согласия плательщиком | да |
| `ACTIVE` | Согласие подтверждено; автоматические списания разрешены | да |
| `PAUSED` | Приостановлена ТСП; будущие списания не создаются | да |
| `REVOKED` | Согласие отозвано (ТСП или плательщиком); терминальное | да |
| `EXPIRED` | Истёк срок мандата; терминальное | да |
| `FAILED_CONSENT` | Плательщик отказал либо подтверждение не получено; терминальное | да |

| S2 | `PENDING_CONSENT` | `ACTIVE` | событие `mandate.activated` | `eventId` не обработан; **`termsHash` события совпадает** с хэшем зарегистрированного мандата | свидетельство согласия (`append-only`), outbox, вебхук `subscription.activated` |

## 3. Жизненный цикл charge

Charge создаётся только при `ACTIVE`-подписке (S7/S8 делают создание недостижимым, AD-011).

**Charge — проекция финансового состояния.** Финансовую истину хранит **платёж** (AD-002); `charge.status` выводится из состояния платежа и подсостояния попытки в **той же** атомарной транзакции, не может расходиться с ним и не является вторым источником истины. Сверка сверяет цепочку `charge ↔ платёж ↔ ОПКЦ ↔ АБС`; расхождение — дефект.

**Периодный ключ.** `chargeId = f(subscriptionId, periodKey)`, где `periodKey` — период, **вычисляемый шлюзом** из расписания подписки (`period`/`dayOfPeriod`) и даты в MSK (`YYYY-MM`; для `WEEKLY` — `YYYY-Www`). `billingReference` ТСП — необязательная корреляционная ссылка, **не** идентификатор периода: ТСП не может «раздробить» период разными ссылками. Один `periodKey` → ровно один charge: повторный тик или повторный запрос за тот же период возвращает существующий charge, второй дебет не создаётся (AD-010). Окно лимита за период (`maxAmountPerPeriod`) — тот же календарный период `periodKey`. Списание по запросу ТСП разрешено **только для `amountMode=VARIABLE`** (для `FIXED` списания инициирует исключительно движок). Симметрично, плановые списания движка выполняются **только для `FIXED`**; для `VARIABLE` движок лишь формирует напоминание, но не дебетует. Таким образом, у подписки ровно один путь списания, и коллизия «плановый vs по запросу» на один период конструктивно исключена. Мандат несёт per-charge лимит (`maxAmount`) и **лимит за период** (`maxAmountPerPeriod`); оба проверяются при создании charge, превышение → отказ без побочного эффекта.

**Политика in-flight при отзыве/паузе.** Подписка в `PAUSED`/`REVOKED` новых charge не создаёт. Charge в `SCHEDULED` — отменяется без списания (C9); charge в `INITIATED` — доводится до терминального состояния либо отменяется по протоколу и **не инициируется повторно**. **Dunning/повторы после отзыва не выполняются**: инициированный charge, отклонённый после `REVOKED`/`PAUSED`/stop-new-charges, переходит в `FAILED` без новых попыток (в отличие от обычного dunning).

| Состояние charge | Смысл |
|---|---|
| `SCHEDULED` | charge спланирован (детерминированный `chargeId`), вызов ОПКЦ ещё не сделан |
| `INITIATED` | вызов списания отправлен адаптеру/ОПКЦ; исход ожидается |
| `PAID` | ОПКЦ подтвердил списание (зачисление в АБС разрешено) |
| `CREDITED` | зачисление в АБС выполнено (`absDocId`) |
| `COMPLETED` | доведено до ТСП (вебхук поставлен/доставлен) |
| `FAILED` | списание за период завершилось неуспехом (после dunning-политики) |

Технические подсостояния: `DUNNING` (повторы), `UNKNOWN` (неопределённый исход вызова — разрешается сверкой), `ABS_PENDING` (зачисление в АБС в процессе). Наружу не выставляются (кроме агрегированного `dunning`-флага).

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `SCHEDULED` | тик планировщика / `POST /v1/subscriptions/{id}/charges` | мандат `ACTIVE` и покрывает ТСП/сумму/период; для `POST` — `amountMode=VARIABLE`; `periodKey` ещё не заряжен (иначе — возврат существующего charge) | идемпотентная вставка по `chargeId` + outbox |
| C2 | `SCHEDULED` | `INITIATED` | отправка `initiateCharge` адаптеру | **на момент инициации** (перепроверка при де-очереди): подписка `ACTIVE`, мандат не отозван, глобальный stop-new-charges выключен | `attemptSeq += 1` |
| C3 | `INITIATED` | `PAID` | событие `charge.paid` | `eventId` не обработан; сумма/мандат совпадают | outbox «зачисление в АБС» |
| C4 | `INITIATED` | `SCHEDULED`/`DUNNING` | отклонение/неуспех | попытки не исчерпаны | ретрай с задержкой/джиттером, уведомление по политике |
| C5 | `INITIATED`/`DUNNING` | `FAILED` | попытки исчерпаны | — | outbox, вебхук `charge.failed`, отчёт незавершённых |
| C6 | `PAID` | `CREDITED` | подтверждение АБС | вызов идемпотентен по `paymentId` | `absDocId`, outbox |
| C7 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен/в очереди | — | outbox, аудит |
| C8 | `INITIATED` | `UNKNOWN` | таймаут/ошибка канала | — | **без слепого повтора**: дозапрос статуса/сверка |
| C9 | `SCHEDULED` | `FAILED` (отменён) | отзыв/пауза подписки или stop-new-charges **до** инициации | charge ещё не `INITIATED` | закрытие без списания, outbox, отчёт незавершённых |

## 4. Запрещённые переходы (инварианты)

- **Нет `charge` без `ACTIVE`-мандата** (AD-009): из `PENDING_CONSENT`/`PAUSED`/`REVOKED`/`EXPIRED`/`FAILED_CONSENT` создание charge недостижимо.
- **Нет нового `charge` после `REVOKED`/`PAUSED`** (AD-011); зачисленные ранее операции не откатываются — только возврат (сага ADR-005).
- **Один `charge` на `(subscriptionId, periodStart)`** (AD-010): повторный тик/рестарт даёт тот же `chargeId`.
- **Зачисление только из `PAID`** (AD-005) — charge не исключение.
- `REVOKED`/`EXPIRED`/`FAILED_CONSENT` — терминальные; возврат к `ACTIVE` невозможен (нужен новый мандат).
- Условия мандата (лимит, расписание, ТСП) иммутабельны после `ACTIVE`; изменение — новый мандат.
- Сумма charge не может превышать лимит мандата (для переменных сумм — per-charge max).

## 5. Идемпотентность

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/subscriptions` | `Idempotency-Key` | тот же `subscriptionId`, состояние не меняется |
| `mandate.activated` / `mandate.revoked` | `eventId` | обработанный `eventId` игнорируется |
| Тик планировщика | `chargeId = f(subscriptionId, periodKey)` | идемпотентная вставка, второй charge не создаётся |
| `POST /subscriptions/{id}/charges` | `Idempotency-Key` | тот же `chargeId` |
| `charge.paid` | `eventId` | повтор не меняет завершённый переход |
| Подтверждение АБС | `paymentId`/`chargeId` | повтор не создаёт вторую проводку |
| `revoke`/`suspend`/`resume` | `Idempotency-Key` | идемпотентно |

> Повторный `POST charges` с **другим** `Idempotency-Key`, но тем же `billingReference` (период уже заряжен) возвращает существующий charge, а не создаёт второй дебет. Плановое и «по запросу» списания за один нормализованный период используют один `periodKey` и не могут зарядить период дважды.

## 6. Сверка и восстановление

- Сверка с НСПК (ежечасная): мандаты `ACTIVE` ↔ активные подписки; charges за период ↔ выписка ОПКЦ. Расхождение «у НСПК списано, у нас нет» → дозапрос статуса → `PAID`; «у нас есть, у НСПК нет» → стоп-сигнал, эскалация.
- Сверка с АБС (суточная): `PAID`-charges ↔ зачисления. Двойные проводки исключены идемпотентностью.
- `UNKNOWN`-charges — обязательный список в отчёте незавершённых операций; разрешение по runbook ≤ 4 ч.
- **Catch-up после простоя**: пропущенные периоды перепланируются тем же `periodKey` (идемпотентно) через **ограниченную догоняющую очередь с backpressure**. Число автоматически обрабатываемых пропущенных периодов ограничено (baseline ≤ 2); при большем пропуске — `skip`/эскалация в dunning по решению бизнеса, без «лавины» задним числом (NFR §3).

## 7. Согласованность с API ТСП

Маппинг наружу: `PENDING_CONSENT`, `ACTIVE`, `PAUSED`, `REVOKED`, `EXPIRED`, `FAILED_CONSENT`. Для charge наружу выставляются состояния `SCHEDULED`, `INITIATED`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED` (совпадает с `openapi/tsp-api.yaml`); технические подсостояния (`DUNNING`, `UNKNOWN`, `ABS_PENDING`) не выставляются, но отражаются флагом `dunning`. См. `docs/contracts/tsp-api.md` §3.6–3.8.
