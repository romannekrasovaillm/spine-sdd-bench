# EXECUTABLE-CHECKS — исполняемые проверки инвариантов подписок (передаются в реализацию)

- Status: план к A4 (применяется на этапе реализации; репозиторий сейчас в стадии «решение», кода нет)
- Owner: solution-architect (платёжный контур)
- Связано: AD-009, AD-010, AD-011, AD-002, ADR-009, `.arch-handoff/CONSTRAINTS.yaml`, навык `fitness-functions`

## Зачем этот документ

Зелёный `fitness_check` сейчас — **структурный, не поведенческий**: все 14 правил проверяют наличие/запрет текста
(паспорт вердикта `arch-be/verdict-passport/v1`, аттестация `sha256:619fa10aeed16d979f6aaf2652a4efc1469542645ca7277e39b56cf77a0fd0cd`,
блок «Заявлено, но механикой не проверяется»: «правил, судящих по ТЕКСТУ файла, — 14 из 14; исполняемых проверок поведения: 0»).
Код, который спишет без действующего мандата или спишет дважды, останется «зелёным». Для Critical-изменения этого недостаточно:
инварианты **AD-009 / AD-010 / AD-011** обязаны получить исполняемые проверки поведения на гейте A4.

## Что применить (шаблоны исполняемых правил)

Применяются к коду на этапе реализации (создают тест + фейк внешней системы + нарушающую реализацию и включают проверку «зубов»).
Команда: `arch-be rules template apply <id> --ad AD-N --dir <кейс>` (фрагмент правила с `C-NNN` и `verified_by` вносится в `CONSTRAINTS.yaml` дельтой/архитектором — реестр защищён).

| Инвариант | Свойство (что проверяет тест) | Шаблон | Куда применяется |
|---|---|---|---|
| AD-009 | Без записи о действующем согласии (мандате) действие-списание не создаётся | `consent-before-auto-action` | движок списаний + реестр мандатов |
| AD-010 | Повторная доставка/перепланирование с тем же `periodKey` не создаёт второй эффект (тот же `chargeId`) | `idempotency-key` | движок списаний / API `POST charges` |
| AD-011 | После `REVOKED`/`PAUSED` создание charge недостижимо (в т.ч. перепроверка при де-очереди) | `consent-before-auto-action` (вариант guard) | движок списаний |
| AD-002 (проекция charge) | Устаревшее состояние charge не выдаётся за актуальное; charge согласован с платежом | `single-source-of-truth` | статусная машина / проекция charge |
| AD-007/AD-009 (аудит) | Журнал свидетельств согласия — только на дозапись, запись нельзя изменить/удалить | `append-only-journal` | аудит-лог согласий |
| ADR-009 (UNKNOWN) | При неопределённом исходе — UNKNOWN и разрешение сверкой, а не повторная отправка | `unknown-outcome-no-resend` | адаптер/движок списаний |

Три принципа (навык `fitness-functions`): свойство, а не протокол; фейк со счётчиком без сети/сна; **нарушающая реализация обязательна** (иначе `executable_rule_toothless`).

## Как правило попадёт в реестр

`rule_template_apply` **печатает** готовый фрагмент правила (`C-NNN`, тип `command_succeeds`, `verified_by`). Внесение фрагмента в `.arch-handoff/CONSTRAINTS.yaml` и в spine-блок — правка защищённых файлов, выполняется **дельтой** (`arch-be delta new <name>`), а не напрямую. Пока фрагменты не внесены, инварианты AD-009/010/011 покрыты только текстовыми правилами трассировки (см. таблицу `DELTA.md`), и это состояние должно быть закрыто до перехода от walking skeleton к боевой реализации.

## Границы (что эти проверки НЕ заменяют)

- Нагрузочные/chaos-проверки (NFR §2/§3/§5) — отдельный контур, не fitness.
- Независимая оценка ADR (`adr_quality`) и смысловые рубрики (`adr_spine_consistency`, `nfr_mechanism_fit`) — судья/человек.
- NFR-бюджеты на A4 (`arch-be gate` на маршруте Critical с `[gate.required]`, включая `decision_quality`).
