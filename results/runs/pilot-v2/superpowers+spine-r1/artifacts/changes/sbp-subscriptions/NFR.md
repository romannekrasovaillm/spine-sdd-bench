# NFR (дельта) — СБП-подписки: рекуррентные C2B-списания

- Status: Draft (для ревью на A1/A4 дельты)
- Owner: solution-architect (платёжный контур) + владелец продукта C2B + SRE
- Связано: ADR-008, ADR-009; дополняет `docs/nfr.md` (вливается при `archive`)

Целевые значения — **измеримые критерии приёмки** на гейтах A4/A5. Помечены как **baseline**: финальные согласуются с бизнесом и регламентами НСПК (регламенты оператора могут быть строже). Каждая цель имеет метод проверки и следствие нарушения.

## 1. Согласие (мандат)

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Приём запроса на создание подписки | p95 < 500 мс, p99 < 1 с | нагрузочный тест, APM | ТСП не может инициировать подписку, отток |
| Обработка события активации мандата (`mandate.activated` → `ACTIVE`) | p95 < 5 с | метрика обработки событий | плательщик подтвердил, а списания не идут |
| Полнота свидетельства согласия | 100 % подписок `ACTIVE` имеют неизменяемую запись (условия, время, канал, хэш) | аудит + fitness | регуляторный и диспутный риск |
| Доля charges без действующего мандата | 0 | fitness `consent-before-auto-action` + аудит | списание без согласия — недопустимо |

## 2. Планировщик и списание

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Точность расписания: от **назначенного слота** до `INITIATED` | p95 ≤ 60 с, p99 ≤ 5 мин (слот — внутри окна списаний §3, джиттер ±5 мин) | метрика лага планировщика | ЖКХ/связь списывают не в срок; жалобы |
| Приём списания по запросу ТСП | p95 < 500 мс | нагрузочный тест | медленный API для ТСП |
| Лаг планировщика в пиковый день | p95 ≤ 60 с при профиле нагрузки п. 3 | нагрузочный тест пикового дня | «залипшие» списания, dunning по вине шлюза |
| Зачисление в АБС от `PAID` | p95 < 60 с (SLA с АБС) | метрика процесса | задержка денег ТСП |
| Вебхук `charge.completed` от `CREDITED` | p95 < 5 с | метрика лага очереди | ТСП видит устаревший статус |

## 3. Нагрузка и масштабирование

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Окно списаний портфеля (baseline) | плановые списания одного дня раскладываются на окно ≥ 6 ч; при 1 000 000 charges средний темп ≈ 46 charges/s | ёмкостное моделирование + мониторинг лага | «лавина» в одну секунду, перегрузка НСПК/АБС |
| Устойчивая пропускная способность списаний | ≥ 50 charges/s sustained | нагрузочный тест | не успеть в окне списаний |
| Пик списаний (burst) | ≥ 300 charges/s в течение 10 мин (первое число / зарплатный период) | нагрузочный тест | просрочка списаний |
| Портфель подписок (baseline) | ≥ 1 000 000 активных; уточняется бизнесом | ёмкостное моделирование | недооценка инфраструктуры |
| Масштабируемость | ×2 без изменения архитектуры (шардирование по `tspId`, конкурирующие потребители) | load-test на удвоенном профиле | перепроектирование под нагрузкой |
| Изоляция сбоя (bulkhead) | сбой одного **ТСП** не задерживает > 1 % остальных списаний (шардинг по `tspId`) | chaos-тест | «шумный сосед» роняет поток |
| Catch-up после простоя | автоматически ≤ 2 пропущенных периода на подписку; больший простой — эскалация; пик не превышен | chaos-тест простоя | лавина списаний задним числом |

## 4. Корректность и идемпотентность

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Двойные списания на `(subscriptionId, periodStart)` | 0 | fitness `idempotency-key`; тест на рестарте/параллельном тике | финансовый инцидент, возврат |
| Повторное планирование/рестарт планировщика | тот же `chargeId`, состояние не меняется | тест идемпотентности | дубли |
| Повторный `POST` списания с тем же `Idempotency-Key` | тот же `chargeId`, второй дебет не создаётся | контрактный тест | двойное списание |
| Двойное зачисление при повторе АБС | 0 | тест идемпотентности | кассовый разрыв |
| Пропущенный тик | charge перепланируется, не теряется | тест восстановления | недосписанные деньги |
| Один charge на `periodKey` | 0 вторых дебетов на период | тест повторного тика и повторного запроса | двойное списание |
| Соблюдение лимитов мандата (`maxAmount`, `maxAmountPerPeriod`) | 100 % отказов при превышении, без побочного эффекта | тест границ | списание сверх согласия |

## 5. Отзыв и остановка списаний

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Новые charge после `REVOKED`/`PAUSED` | 0 — проверка **на момент инициации** (перепроверка при де-очереди), не только при создании | fitness + тест недостижимости | списание без согласия |
| Charge после stop-new-charges | 0 новых `INITIATED` **после распространения флага** (≤ 1 мин; fail-safe default-deny при недоступности флага); charge в `SCHEDULED` отменяется без списания (C9) | тест kill switch | откат не останавливает списания |
| Обработка отзыва (`revoke`/`mandate.revoked` → `REVOKED`) | p95 < 5 с | метрика обработки событий | запоздалый отзыв → спорный charge |
| Распространение stop-new-charges (kill switch) | ≤ 1 мин до прекращения создания новых charge | учения/тест | откат не останавливает списания |

## 6. Dunning и устойчивость к отказам

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Число попыток списания на период | ≤ 3 (по умолчанию, настраивается) | конфиг + тест | раздражение плательщика, нагрузка |
| Backoff | экспоненциальный + джиттер | тест ретраев | синхронные штормы ретраев |
| UNKNOWN-исход | разрешается сверкой ≤ 4 ч, 100 % видимы в отчёте | runbook + мониторинг | «зависшие» деньги |
| Уведомление о неуспехе | 100 % по политике dunning | тест-кейсы | жалобы/чарджбэки |

## 7. Сверка

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Сверка мандатов/charges с НСПК | ежечасная; расхождений по завершённым — 0 | reconciliation-отчёт | ненайденные расхождения |
| Сверка с АБС | суточная; расхождений — 0 | reconciliation-отчёт | недозакрытые зачисления |
| Отработка расхождений | 100 % по runbook за ≤ 4 ч | KPI дежурной смены | эскалация инцидента |

## 8. Доступность

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Доступность подписочного API (согласие/управление) | ≥ 99,9 % (месяц) | uptime-мониторинг | ТСП не управляет подписками |
| Доступность движка списаний | ≥ 99,95 % | SLO-отчёт | просрочка списаний |
| Плановая недоступность | 0 (rolling-деплой) | CI/CD pipeline | нарушение SLA |

## 9. Безопасность, ПДн, аудит

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Свидетельство согласия | `append-only`, связано с `chargeId`; 100 % | аудит + SIEM | невозможность доказать согласие |
| ПДн плательщика | минимизация, шифрование в покое, маскирование в логах | ИБ-ревью, тесты | нарушение 152-ФЗ |
| Доступ операторов к ручным операциям (dunning, UNKNOWN) | 4-eyes | RBAC-проверка | неаудируемое вмешательство |
| Привязка ресурса к ТСП (payment/subscription/charge/refund) | 0 успешных обращений к чужому ресурсу (`403`) | тест авторизации | IDOR/утечка/несанкционированное списание |
| Каналы к ОПКЦ | 100 % на сертифицированных СКЗИ (ADR-003) | ИБ-аудит | непроходимость испытаний НСПК |

## 10. Наблюдаемость

| Метрика | Цель | Метод проверки | Следствие нарушения |
|---|---|---|---|
| Trace id | 100 % операций (мандат/charge/платёж) | APM | невозможность разбора |
| Метрики планировщика | лаг, запланировано/создано/успешно/дубли | мониторинг | слепое пятно |
| Алерт на DLQ | DLQ > 0 → ≤ 5 мин | мониторинг | потерянные операции |
| Отчёт незавершённых операций (включая UNKNOWN) | актуален всегда | проверка | скрытые «зависшие» списания |

## Внешние входы для NFR

- Регламенты НСПК: сроки/порядок подтверждения согласия, предварительное уведомление плательщика, лимиты, таймауты — `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Портфель подписок и профиль пиков — бизнес-владелец.
- SLA АБС на зачисление/списание (в т. ч. переменные суммы) — владелец АБС.
- Политика dunning (попытки, окна, уведомления) — бизнес-владелец (A3).
