# IMPACT — значимость, маршрут и влияние на принятую архитектуру

Изменение: **рекуррентные C2B-списания по согласию плательщика («СБП-подписки»)** поверх принятого решения «Платёжный шлюз СБП (C2B-приём)».
Артефакт отвечает на вопросы: (1) насколько глубокое проектирование нужно и почему; (2) какие инварианты затронуты, что меняется, а что нет.

## 1. Оценка значимости и маршрут

### 1.1 Триггеры

Инструмент: Architecture Significance Score (`significance_score`, 15 канонических триггеров).

| Триггер | Значение | Обоснование |
|---|---|---|
| `api_contract_change` | да | новые пути/поля в API ТСП (v0.2), новые вебхук-события |
| `data_contract_change` | да | новые сущности мандата/подписки/charge; новый класс данных (согласие, ПДн) |
| `security_boundary_change` | да | согласие плательщика — новая граница авторизации списания; хранение ПДн и свидетельства согласия |
| `consistency_model_change` | да | плановое списание — распределённый планировщик; «один charge на период»; UNKNOWN-исход |
| `significant_nfr` | да | пропускная способность и лаг планировщика в пиковые дни, точность расписания |
| `cross_domain_integration` | да | банк плательщика через ОПКЦ (подтверждение согласия), ТСП (управление подпиской), АБС |
| `financial_impact` | да | автоматические списания денег без участия клиента в момент операции |
| `criticality_or_exception` | да | платёжный контур — значимый объект КИИ; регуляторный контур НПС |
| `new_component` | зависит от решения | движок периодических списаний (логический компонент) — новое проектное решение; может быть выделен или встроен |
| `new_vendor` | зависит от решения | новый вендор не нужен, если текущий транспортный вендор поддержит подписочный протокол; отказ вендора → смена транспорта (условие пересмотра ADR-007) |
| `new_datastore` | нет | переиспользуется БД шлюза (AD-002) |
| `domain_ownership_change` | нет | владелец домена прежний — платёжный контур |
| `trust_zone_change` | нет | новых trust-зон не вводится (ADR-006); расширяется класс данных внутри зоны |
| `rto_rpo_targets` | нет | RPO=0 / RTO ≤ 1 ч сохраняются |
| `irreversible_migration` | нет | миграций данных нет; модель подписки обратима (ADR-008, ADR-009) |

**Итог: 8 подтверждённых триггеров → маршрут `Critical`** (порог 5+; критический триггер `security_boundary_change` присутствует). С проектным решением «новый компонент — движок периодических списаний» — **9 триггеров**. Даже без «зависимых» триггеров маршрут остаётся Critical.

Машинное свидетельство:
- `significance_score` (заявленные триггеры): **Critical, 8/15**; с `new_component=true` — **Critical, 9/15**.
- `control score --from-diff` (механический пол, ADR-034): 1 триггер (`api_contract_change`) → Fast. Пол не занижает и не заменяет заявленный маршрут; объединение (пол ∪ заявленные) даёт **Critical**.

### 1.2 Что влечёт маршрут Critical

- Полный Solutioning: пересмотр spine, ADR с альтернативами, измеримые NFR, план отката — настоящий пакет.
- **Обязательная человеческая точка A3** до реализации (согласие, dunning, коммерция, вендор) — см. `A3-DECISION.md`.
- Walking skeleton до массовой генерации кода: сначала сквозной путь «согласие → плановое списание → зачисление → отзыв», затем масштабирование.
- Evidence-гейты и anti-bypass: `control score --from-diff` (ADR-034) не даёт занизить маршрут.

### 1.3 Обратимость изменения

Обратимо **до боевой эксплуатации** (фиче-флаг, миграций нет). После включения отказ от модели мандата — `costly` (пересмотр согласий с плательщиками/НСПК, перевод данных), но не `irreversible`: финансовые инварианты (зачисление из `PAID`, идемпотентность, аудит) не меняются.

## 2. Влияние на принятую архитектуру

### 2.1 Что НЕ меняется (стабильные основания)

- **Правила AD-001…AD-008 не переписываются.** Изменения — аддитивные (новые AD-009…AD-011) и расширения `Binds`.
- **Финансовое ядро переиспользуется без изменения семантики**: статусная машина платежа (ADR-002), зачисление **только из `PAID`** (AD-005), возвраты сагой (ADR-005), transactional outbox (ADR-001), at-least-once/DLQ/сверка (ADR-004).
- **Единственный адаптер ОПКЦ** (AD-004) и **контрактная независимость ядра от транспорта** (AD-008 [ADOPTED]) — сохраняются; расширяется только внутренний контракт адаптера.
- **Trust-зоны, СКЗИ/ГОСТ, аудит НПС/КИИ/ПДн** (AD-006, AD-007) — модель сохраняется, требования усиливаются.
- **RPO=0, RTO ≤ 1 ч, доступность ≥ 99,95 %, двойных зачислений 0** — сохраняются.

### 2.2 Что меняется

1. **Новый домен `Mandate`/`Subscription`** в платёжном контуре: сущности, таблицы в БД шлюза, собственный конечный автомат (отдельный от платежа).
2. **Новый логический компонент — движок периодических списаний**: планировщик, детерминированные `charge`, ретраи/dunning, шардирование, kill switch (ADR-009).
3. **Charge как разновидность платежа** (`origin=SUBSCRIPTION`, ссылки `subscriptionId`/`mandateId`): новых финансовых состояний не вводится, но расширяется модель данных платежа.
4. **Новый класс данных**: свидетельство согласия и ПДн плательщика — неизменяемая запись, требования 152-ФЗ/НПС, хранение и аудит (расширение ADR-006/AD-007).
5. **Расширение внутреннего контракта адаптера ОПКЦ**: регистрация/отзыв мандата, инициация списания, нормализованные события — **новое обязательство вендора транспорта** (RFP, ADR-007).
6. **API ТСП v0.2** — аддитивные пути и поля (совместимость v0.1 сохраняется).
7. **Новые типы событий аудита и вебхуков** (`subscription.*`, `charge.*`, `mandate.*`).
8. **Расширение NFR**: точность расписания, лаг планировщика, пиковая нагрузка в дни списаний, доля dunning, распространение отзыва (см. `NFR.md`).

### 2.3 Затронутые инварианты

Полная матрица — `DELTA.md`, раздел «Матрица влияния на инварианты». Кратко:

- **Без изменения правила**: AD-001, AD-002, AD-004, AD-005 (критично), AD-008.
- **Усиление**: AD-003 (+AD-010), AD-006, AD-007.
- **Новые**: AD-009 (согласие обязательно), AD-010 (идемпотентность списания), AD-011 (отзыв останавливает списания) — статус `Proposed`, действуют после A3.

### 2.4 Пробелы и допущения (внешние входы)

| Пробел | Влияние | Что закроет |
|---|---|---|
| Протокол подписок/автоплатежей НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` | схема подтверждения согласия, сроки, предуведомление, лимиты | документация НСПК по договору |
| Поддержка подписок вендором транспорта | реализуемость без смены вендора | подтверждение вендора / RFP |
| Контракт АБС для переменных сумм | зачисление/частичные возвраты charge | владелец АБС |
| Отсутствует каталог `model/` | недоступны `trace_check`, `nfr_check`, `change_impact` (проверки по типизированной модели) | решение архитектора: завести модель или принять ADR+spine-дисциплину |
| Отсутствуют активы рубрик (`adr_quality`) | ADR не оценены судьёй механически | независимый судья/человек на A3 |

Допущения, принятые в пакете, вынесены в `A3-DECISION.md` (раздел «Допущения») и явно помечены как требующие подтверждения человеком.
