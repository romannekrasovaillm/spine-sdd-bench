## 1. Критерии приёмки (EARS)

Каждый критерий проверяем тестом, командой или метрикой. Формулировки — по нотации EARS.

| ID | Критерий (EARS) | Как проверяется |
|---|---|---|
| AC-1 | **When** ТСП создаёт подписку, the СБП-шлюз shall создать мандат `PENDING_CONSENT` и вернуть `consentUrl` | контрактный тест `POST /v1/subscriptions`; повтор с тем же `Idempotency-Key` → тот же `subscriptionId` |
| AC-2 | **When** ОПКЦ подтверждает согласие, the СБП-шлюз shall перевести подписку в `ACTIVE` и сохранить неизменяемое свидетельство согласия ≤ 5 с | тест обработки `mandate.activated`; аудит-проверка записи (условия, время, канал, хэш) |
| AC-3 | **When** наступает плановый период, the движок shall создать ровно один `charge` с `chargeId = f(subscriptionId, periodStart)` | тест планировщика; повторный тик → тот же `chargeId`, второй charge не создан |
| AC-4 | **When** ТСП запрашивает списание в пределах мандата, the СБП-шлюз shall принять его идемпотентно и не превысить лимит | контрактный тест; повтор с тем же ключом → тот же `chargeId`; превышение → `422 AMOUNT_EXCEEDS_MANDATE` |
| AC-5 | **If** мандат не `ACTIVE` или не покрывает списание, **then** the СБП-шлюз shall отказать в создании `charge` | fitness `consent-before-auto-action`; негативный тест по каждому неактивному статусу |
| AC-6 | **When** ОПКЦ подтверждает списание (`PAID`), the СБП-шлюз shall зачислить в АБС только из `PAID` и уведомить ТСП | тест недостижимости зачисления из `CREATED`/`QR_ISSUED`/`INITIATED` (AD-005); тест вебхука `charge.completed` |
| AC-7 | **When** ТСП или плательщик отзывает согласие, the СБП-шлюз shall перевести подписку в `REVOKED` и не создавать новые `charge` | контрактный тест `revoke`; тест недостижимости создания charge после `REVOKED` |
| AC-8 | **While** подписка `PAUSED`, the движок shall не создавать плановые `charge` | тест: тик при `PAUSED` не создаёт charge; `resume` возобновляет |
| AC-9 | **If** списание отклонено, **then** the СБП-шлюз shall применить dunning-политику (≤ N попыток, backoff+джиттер, уведомления) и не потерять операцию | тест ретраев на фейке; проверка счётчика попыток; отчёт незавершённых |
| AC-10 | **If** вызов списания вернул UNKNOWN/таймаут, **then** the СБП-шлюз shall разрешить исход сверкой/запросом статуса, не повторяя вслепую | тест: таймаут адаптера → нет слепого повтора, есть дозапрос статуса |
| AC-11 | **While** существует потребитель v0.1, the API ТСП shall не ломать существующие пути и поля | `contract_diff` v0.1→v0.2 → 0 breaking; регрессионный контрактный тест платежа |
| AC-12 | **While** один ТСП/подписка деградирует, the движок shall не задерживать списания остальных | chaos-тест bulkhead: задержка одного шарда не влияет на остальные > 1 % |
| AC-13 | **Where** операция ручная (разбор UNKNOWN, dunning), the система shall требовать 4-eyes | RBAC-тест привилегированного контура |
| AC-14 | **Where** согласие хранится, the система shall минимизировать ПДн и маскировать их в логах | ИБ-ревью, скан логов |
| AC-15 | **If** ТСП обращается к ресурсу другого ТСП, **then** the СБП-шлюз shall вернуть `403` без раскрытия факта существования ресурса | тест авторизации (IDOR) |
| AC-16 | **If** отзыв/пауза/stop-new-charges срабатывает до инициации charge, **then** the СБП-шлюз shall отменить `SCHEDULED`-charge без списания; для `INITIATED` — довести до терминального состояния либо отменить по протоколу, без повторной инициации и без dunning (ноль новых `INITIATED` после распространения флага ≤ 1 мин) | тест гонки «отзыв ↔ списание»; тест kill switch |
| AC-17 | **When** ТСП запрашивает списание, the СБП-шлюз shall вычислить `periodKey` из расписания, вернуть существующий charge при повторе периода и отвергнуть превышение `maxAmount`/`maxAmountPerPeriod` и режим `FIXED` | контрактный тест (повтор периода, границы лимитов, `FIXED`) |
| AC-18 | **If** планировщик пропустил периоды (простой), **then** the СБП-шлюз shall перепланировать не более 2 периодов с backpressure, не превышая пик | chaos-тест простоя |

## 2. Обязательные негативные и граничные сценарии

1. **Дубль планирования**: рестарт планировщика и параллельные инстансы → ровно один `charge` (AC-3).
2. **Дубль запроса ТСП**: повтор `POST charges` с тем же ключом → тот же `chargeId` (AC-4).
3. **Гонка отзыва и списания**: отзыв во время `INITIATED` → исход по правилу (завершить/отменить), новых charge нет (AC-7).
4. **Отказ АБС**: charge остаётся `PAID`, ретраи, сверка; не теряется, не двоится (AC-6/AC-9).
5. **Таймаут/UNKNOWN ОПКЦ**: разрешение сверкой, без слепого повтора (AC-10).
6. **Плательщик отозвал в своём банке**: событие `mandate.revoked` останавливает списания (AC-7).
7. **Превышение лимита мандата** и **истёкший мандат**: отказ без побочного эффекта.
8. **Совместимость**: существующий сценарий динамического QR не затронут (AC-11).
9. **Идемпотентность возврата charge**: полный/частичный возврат по существующей саге.
10. **Простой планировщика**: N пропущенных периодов → ограниченный catch-up, без лавины (AC-18).
11. **Гонка отзыва до инициации**: `SCHEDULED`-charge отменяется, дебет не происходит (AC-16).
12. **Кросс-ТСП доступ**: чужой `subscriptionId`/`chargeId` → `403` (AC-15).
13. **Списание по `FIXED`-подписке через API** → `422 CHARGE_NOT_ALLOWED_FOR_FIXED` (AC-17).

## 5. План отката

### 5.1 До боевой эксплуатации (обратимый откат)

- Подписки — за фиче-флагом `subscriptions.enabled` (по умолчанию `off`).
- Откат = выключить флаг и откатить релиз (rolling). **Миграций данных нет**, существующие платежи не затронуты.
- Критерий: функционал подписок недоступен, приём QR работает штатно.

### 5.2 После включения (операционный откат)

| Шаг | Действие | Ответственный |
|---|---|---|
| 1 | Включить **stop-new-charges** (kill switch): движок не создаёт новые `charge`; уже начатые доводятся/разрешаются сверкой | SRE платёжного контура |
| 2 | Уведомить ТСП о приостановке подписок; плательщикам списания не инициируются | продукт C2B |
| 3 | При полном выводе — отозвать мандаты по протоколу ОПКЦ и сверить | SRE + проектный офис |
| 4 | Сверить in-flight charges и зачисления; незавершённые — в runbook ≤ 4 ч | дежурная смена |
| 5 | Отчёт о откате (что остановлено, сколько операций затронуто) | solution-architect + SRE |

### 5.3 Сигналы-триггеры отката

- метрика **дублей списаний > 0**;
- charged без свидетельства согласия (нарушение AD-009);
- новые `charge` после `REVOKED` (нарушение AD-011) — блокер;
- успешность списаний ниже согласованного порога (базово < 95 %) по вине шлюза;
- устойчивая деградация НСПК/АБС или рост UNKNOWN выше порога.

### 5.4 Что НЕ откатывается

Завершённые и зачисленные списания; данные мандатов/подписок (не удаляются, не мигрируют обратно); существующий функционал QR-платежей. Возвраты — только штатной сагой (ADR-005).

### 5.5 Владелец решения об откате

**solution-architect (платёжный контур) + SRE-лид + бизнес-владелец C2B**; решение фиксируется в инцидентном журнале. Единоличное решение SRE допустимо только при срабатывании блокирующего сигнала (дубли/списание без согласия).

## 6. Handoff-готовность (после A3)

Вход для формирования пакета исполнителям (`arch-be handoff <harness> --repo . --route critical --task …`):

- задача — `changes/sbp-subscriptions/DESIGN.md` (смысловое ядро) + `DELTA.md` (ADDED/MODIFIED);
- инварианты — `ARCHITECTURE-SPINE.md` AD-002, AD-005, AD-009…AD-011 (дословные `Rule`);
- решения — `docs/adr/ADR-008-…`, `ADR-009-…`;
- контракты — `openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`;
- приёмка — этот документ; NFR — `changes/sbp-subscriptions/NFR.md`.

**Пакет не формируется до человеческого решения A3** (`A3-DECISION.md`): сначала утверждается модель мандата, политика dunning и способ инициации списаний.
