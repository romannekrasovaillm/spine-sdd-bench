# Предложение: подписки СБП — рекуррентные C2B-списания по согласию плательщика

## Why

ТСП (онлайн-кинотеатры, ЖКХ, связь) не могут принимать повторные платежи без участия клиента: сейчас каждый C2B-платёж требует QR и действия плательщика. Подписочные модели в СБП сегодня невозможны, и ТСП вынуждены держать второй, карточный канал рекуррентных списаний. Подписки СБП позволяют списывать средства по ранее оформленному согласию плательщика (`мандат`) без QR при каждом платеже, сохраняя расчёты внутри СБП.

## What Changes

- Новое: **реестр мандатов** (согласий плательщика на рекуррентные списания) — проекция состояния, подтверждённого ОПКЦ СБП; хранение в платёжном контуре шлюза.
- Новое: **инициация списания по мандату** (server-to-server, без QR и без действия плательщика) с идемпотентностью «одно списание на период подписки».
- Новое: **отмена/отзыв мандата** — плательщик отзывает согласие в своём банке (приходит событием ОПКЦ); ТСП может инициировать прекращение через шлюз, если это допускает протокол СБП.
- Расширение: платёжный агрегат получает тип инициации (`MANDATE`); статусная машина получает переход `CREATED → PAID` без состояния `QR_ISSUED`. Оплата по QR/ссылке не меняется.
- Расширение API ТСП (**аддитивно**): пути `/v1/mandates*`, новые события вебхуков, новые коды ошибок; версия остаётся `/v1`.
- Не меняется: зачисление только из подтверждённого `PAID` (AD-005), атомарные переходы «статус + outbox + аудит» (AD-002), единственный адаптер ОПКЦ (AD-004), trust-зоны и требования НПС/КИИ/ПДн (AD-006, AD-007), стратегия «гибрид» (AD-008).
- **BREAKING**: нет. Все изменения контракта аддитивны, существующие потребители `/v1/payments` не затронуты (проверено `contract_diff`).

## Capabilities

### New Capabilities

- `sbp-subscriptions` — мандат плательщика и его жизненный цикл, списание по мандату, лимиты, отзыв и уведомления. Спека: `specs/sbp-subscriptions/spec.md`.

### Modified Capabilities

- Нет. Живая истина проекта по существующему поведению находится в `docs/` (`ARCHITECTURE-SPINE.md`, `docs/spec/state-machine.md`, `docs/contracts/tsp-api.md`, `docs/nfr.md`); каталог `openspec/specs/` пуст. Поэтому изменения существующего поведения выражены:
  - дельтой спайна `changes/add-sbp-subscriptions/DELTA.md` (правки защищённых файлов: `ARCHITECTURE-SPINE.md`, `.arch-handoff/CONSTRAINTS.yaml`),
  - аддитивными правками `docs/` и `openapi/tsp-api.yaml`.
  Маршрут изменения — **Critical** (см. `design.md` §1): полный Solutioning, дельта-спеки недостаточно.

## Impact

- **Сервисы**: платёжный контур шлюза — новый модуль «реестр мандатов»; статусная машина платежа; адаптер ОПКЦ (новые операции внутреннего контракта); нотификатор ТСП (новые события); БД шлюза (таблицы: `mandates`, `mandate_charges`, ключи идемпотентности списаний).
- **Контракты**: `openapi/tsp-api.yaml` (аддитивно, 0.1.0 → 0.2.0 draft); `docs/contracts/tsp-api.md`; `docs/contracts/opkc-adapter.md` (новые методы и события — вход для change request к вендору транспорта).
- **Данные**: в платёжный контур добавляются ПДн плательщика (реквизиты согласия) — минимизация, шифрование в покое, маскирование в логах, сроки хранения (AD-007, `[ТРЕБУЕТ ПРОВЕРКИ]`).
- **Процесс**: обязательное человеческое решение A3 до реализации; расширение контракта с вендором транспорта; сверка мандатов добавляется в регламент эксплуатации.
- **Внешний вход**: точная семантика сервиса подписок СБП у ОПКЦ СБП (наличие, поля, тайминги, лимиты, правило первого списания, права ТСП на отмену) — `[ТРЕБУЕТ ПРОВЕРКИ]`, документация НСПК по договору.
