# ADR-008. Рекуррентные C2B-списания по согласию плательщика (подписки СБП)

- Date: 2026-09-28
- Status: Proposed (ожидает человеческого решения A3)
- Owner: solution-architect (платёжный контур) + владелец платёжного продукта
- Author-model: qwen (агент)
- Related: ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-006, ADR-007; AD-002, AD-003, AD-005, AD-007, AD-009

## Context

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят регулярные списания. Сейчас каждый C2B-платёж требует
QR и действия плательщика, поэтому подписки невозможны. Бизнес-запрос вводит **новый класс
финансовых операций**: списание без разового действия плательщика по заранее данному согласию
(поручению). Это меняет границу авторизации, добавляет новые агрегаты (согласие, подписка,
списание) и новый ПДн-чувствительный артефакт.

Силы и ограничения:
- **Авторитетность согласия**: согласие регистрируется и отзывается на стороне ОПКЦ СБП/банка
  плательщика, а не банка-эквайера; для согласия достижима только согласованность в конечном
  счёте со сверкой (аналогично нотификациям, ADR-004).
- **Несущие инварианты ядра**: атомарные переходы «статус + outbox + аудит» (AD-002),
  идемпотентность повторных доставок (AD-003), зачисление только из подтверждённого статуса
  (AD-005), единственный адаптер ОПКЦ и транспортная независимость ядра (AD-004, AD-008).
- **Внешний вход**: точная модель сервиса подписок НСПК и протокол не раскрыты публично —
  `[ТРЕБУЕТ ПРОВЕРКИ]`; их нельзя проектировать «по памяти модели».
- **Маршрут Critical** (значимость 10/15): финансовое влияние, критичность/КИИ, изменение
  границы безопасности, новые контракты и модель консистентности.

## Предлагаемое решение A3 (машинно-читаемый пакет; подписывает человек)

- **choice**: `merchant-initiated-consent` — согласие плательщика как отдельный агрегат
  (авторитетный источник — ОПКЦ, шлюз — проекция), списания инициирует ТСП против действующего
  согласия; зачисление в АБС — только из подтверждённого статуса списания и при действующем
  согласии; контракт адаптера ОПКЦ расширяется аддитивно до `v0.2`.
- **rationale**: переиспользует несущие инварианты ядра без ослабления; не создаёт нового
  single-writer-планировщика; сохраняет заменимость транспорта (AD-008); контракты TSP API
  расширяются без поломки потребителей.
- **constraints**: (1) действующее согласие (1:1 с подпиской) и лимиты — обязательное условие
  списания; согласие проверяется при инициации и перед зачислением (AD-009); (2) зачисление только
  из подтверждённого статуса; при отзыве согласия между инициацией и зачислением — саспенс и
  разворот у ОПКЦ (расширение AD-005); (3) идемпотентность списаний: `Idempotency-Key` (24 ч) +
  уникальный бизнес-ключ `merchantChargeId`; (4) включение через фиче-флаг на ТСП;
  (5) реализация транспорта — после документации НСПК и подтверждения вендором (RFP-гейт G8).
- **rejected options**: `gateway-scheduler` (шлюз хранит расписание и сам инициирует списания),
  `thin-proxy` (не хранить согласие и статус списаний в шлюзе), `credit-on-initiation`
  (зачислять при инициации), `separate-subscription-service` (сервис подписок вне платёжного контура).
- **expiry**: пересмотр через 12 месяцев боевой эксплуатации либо при (а) отсутствии у вендора
  поддержки рекуррентных операций, (б) изменении модели сервиса НСПК, (в) подтверждённом спросе
  на планировщик в шлюзе (тогда — новый ADR).
- **decided_by**: `<человек — подписывает на A3>`

## Decision

Вводим рекуррентные C2B-списания следующим образом: (1) **согласие плательщика** — отдельный
агрегат `Consent` со статусной машиной; авторитетный источник состояния — ОПКЦ СБП, шлюз хранит
проекцию и подтверждает её нотификациями и сверкой; (2) **подписка** ТСП привязана к действующему
согласию и его лимитам; (3) **списание** — отдельный агрегат `Charge` со статусной машиной,
инициируемый ТСП (merchant-initiated), идемпотентный по `Idempotency-Key` (24 ч) и бизнес-ключу
`merchantChargeId`; (4) **согласие проверяется дважды** — при инициации и перед зачислением;
**зачисление** в АБС возможно только из подтверждённого НСПК статуса списания и при действующем
на момент зачисления согласии — атомарно в одной транзакции со сменой статуса, outbox и аудитом;
если согласие отозвано между инициацией и зачислением, средства удерживаются на счёте-саспенс и
разворачиваются у ОПКЦ (`reverseCharge`);
(5) контракт адаптера ОПКЦ расширяется аддитивно до `v0.2` (рекуррентные операции и события) —
ядро остаётся транспортно-независимым; (6) контракт TSP API расширяется аддитивно
(`info.version` 0.2.0, `/v1`, без расширения существующих enum).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| Согласие не хранить, спрашивать ОПКЦ на каждое списание | Нет дублирования | Нет локальной проверки лимитов, RPO и идемпотентности; зависимость от доступности ОПКЦ | Нарушает RPO=0 и AD-009 |
| Считать согласие собственным состоянием шлюза (банк — источник истины) | Проще сверка | Отзыв плательщиком в его банке не будет замечен — неверная модель полномочий | Не соответствует природе сервиса НСПК |
| Планировщик списаний в шлюзе | Независимость от ТСП, точная периодичность | Новый single-writer (выборы лидера), риск двойного списания, дублирование биллинга ТСП | Отложено: нет подтверждённого спроса, растёт риск |
| Зачислять при инициации списания | Быстрый «успех» для ТСП | Зачисление по неподтверждённой операции, откаты | Нарушает AD-005 |
| Зачислять по подтверждённому статусу без перепроверки согласия | Проще | Зачисление после отзыва согласия — несанкционированное списание | Нарушает AD-009 |
| Компенсировать отзыв базовой сагой возврата (ADR-005) | Переиспользование механики | Сага списывает со счёта уже зачисленного ТСП; здесь зачисления ещё не было | Требует саспенс + разворот у ОПКЦ (`reverseCharge`) |
| Отдельный сервис подписок вне платёжного контура | Изоляция нагрузки | Второй источник истины, нарушение AD-001, дублирование адаптеров/АБС-стыка | Нарушает AD-001 |
| Отдельный адаптер подписок к НСПК | Изоляция | Второй адаптер ОПКЦ, второй комплект СКЗИ/сертификатов | Нарушает AD-004 |

## Consequences

### Positive

- Регулярные платежи без разового действия плательщика — новый продукт для ТСП.
- Переиспользование несущих инвариантов ядра (атомарные переходы, outbox, идемпотентность,
  сверка) вместо новой платёжной модели.
- Транспортная независимость и заменимость адаптера сохраняются (AD-008).
- Контракты расширяются аддитивно; существующие потребители не затрагиваются.

### Negative

- Новый класс финансового риска: несанкционированные/ошибочные списания, friendly fraud, диспуты;
  ответственность за корректность лимитов и своевременную блокировку лежит на шлюзе.
- Согласие авторитетно у ОПКЦ → eventual consistency, обязательная сверка, окно гонки
  «списание в момент отзыва» требует компенсации по саге.
- Расширение адаптера зависит от вендора и документации НСПК: внешний риск сроков; при отсутствии
  поддержки — пересмотр ADR-007.
- Рост ПДн-поверхности (данные согласия) и эксплуатационной нагрузки (мониторинг отзывов,
  отказов списаний, DLQ, сверки).

## Reversibility

**reversible** для модели: списания инициирует ТСП, контракты аддитивны, включение — через
фиче-флаг; до боевой эксплуатации откат = не включать. **Costly** для данных согласий: после
регистрации согласий у ОПКЦ их отзыв выполняется у ОПКЦ/банка плательщика и требует процесса
уведомления ТСП, «тихого» отката данных не существует. **Irreversible** для частично исполненных
списаний: их корректная развязка — только через возвраты/сагу.

Условие/срок пересмотра (expiry): через 12 месяцев боевой эксплуатации либо при отсутствии
поддержки вендором, изменении модели сервиса НСПК или подтверждённом спросе на планировщик в шлюзе.
