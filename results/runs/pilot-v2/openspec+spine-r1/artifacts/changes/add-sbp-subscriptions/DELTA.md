## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика
(подписки СБП). Сегодня каждый платёж требует QR и действия клиента, поэтому регулярные
платежи невозможны. Изменение вводит **новый класс финансовых операций** — списание без
разового действия плательщика по предварительно данному согласию (поручению).

## Почему Critical и почему дельты недостаточно

Заявленные триггеры значимости (`significance_score` → 10/15, Critical):
`new_component`, `new_datastore`, `cross_domain_integration`, `api_contract_change`,
`data_contract_change`, `security_boundary_change`, `consistency_model_change`,
`significant_nfr`, `financial_impact`, `criticality_or_exception`.

Причина глубины: меняется **граница авторизации** (списание без действия плательщика),
появляется новый финансово значимый и ПДн-чувствительный артефакт (согласие плательщика,
авторитетный источник — ОПКЦ СБП), новые агрегаты и жизненные циклы, меняются оба контракта
(TSP API и адаптер ОПКЦ). По канону `significance-routing` это полный Solutioning:
spine + ADR + NFR, обязательная человеческая точка A3, walking skeleton до массовой генерации,
evidence-гейты A4/A5. Оговорка: маршрут — функция **заявленных** триггеров; протокольные
детали сервиса подписок НСПК помечены `[ТРЕБУЕТ ПРОВЕРКИ]` и при расхождении могут изменить
состав (например, добавить `trust_zone_change`, если появится новый канал).

## ADDED (спайн)

### AD-009. Рекуррентное списание только при действующем согласии

- Status: Proposed (ADR-008)
- **Binds**: сервис подписок, статусные машины согласия/подписки/списания, адаптер ОПКЦ, АБС-адаптер, аудит-лог, хранилище согласий, счёт-саспенс.
- **Prevents**: списание без действующего согласия плательщика; превышение лимита суммы/числа/периода/срока действия согласия; зачисление по неинициированному или неподтверждённому списанию; зачисление после отзыва согласия; молчаливое продолжение списаний после отзыва; двойное списание по одному ключу.
- **Rule**: Согласие плательщика — 1:1 с подпиской. Любое рекуррентное списание возможно только при действующем согласии и в пределах его лимитов (сумма на списание, сумма и число за период, срок). Согласие проверяется дважды: при инициации и повторно перед зачислением; при отзыве между этими моментами зачисление запрещено, средства удерживаются на счёте-саспенс и разворачиваются у ОПКЦ. Отзыв/приостановка согласия блокирует новые списания по этому согласию. Зачисление в АБС — только из подтверждённого НСПК статуса списания, в одной локальной транзакции со сменой статуса, записью в outbox и аудитом. Fitness: поведенческие тесты «нет списания без активного согласия», «превышение лимита отклонено», «нет зачисления после отзыва», «повтор по одному ключу → одна проводка».

## MODIFIED (спайн)

- **AD-001**: Binds расширяется сервисом подписок, хранилищем согласий и счётом-саспенс (внутри того же платёжного контура; доступ к АБС/ОПКЦ — только через адаптеры). Rule не меняется.
- **AD-002**: Binds расширяется статусными машинами согласия, подписки и списания; Rule «статус + outbox + аудит в одной транзакции» распространяется на финансовые переходы списаний. (Было: только «платёж».)
- **AD-003**: Binds расширяется ключами списания (`Idempotency-Key` — 24 ч; бизнес-ключ `merchantChargeId`) и нотификациями по согласию (`eventId`); идемпотентность повторных доставок распространяется на списания и события согласия. (Было: нотификации платежа и вызовы АБС.)
- **AD-004**: Binds расширяется контрактом адаптера `v0.2` (рекуррентные операции, включая `reverseCharge`, и события); требование «единственный адаптер ОПКЦ» сохраняется.
- **AD-005**: Binds расширяется статусной машиной списания, согласием и счётом-саспенс; Rule усиливается: зачисление возможно только из подтверждённого НСПК статуса **списания** и **при действующем на момент зачисления согласии**. (Было: зачисление только из `PAID` платежа.)
- **AD-007**: Binds расширяется хранилищем согласий плательщика (ПДн) и аудитом рекуррентных списаний; интеграция с антифрод/AML распространяется на рекуррентные операции. Rule (неизменяемость аудита, сертифицированные СКЗИ) не меняется.

## Не изменяется

- **AD-006** (trust-зоны): топология зон и правила сегментации те же; новых зон нет.
- **AD-008** (гибрид [ADOPTED]): стратегия реализации та же; добавляется внешнее требование к вендору — поддержка рекуррентных операций и операции разворота (RFP-гейт G8). При невыполнении — пересмотр ADR-008, а не «тихая» доработка ядра.
- RTO/RPO (RTO ≤ 1 ч, RPO = 0), топология outbox/DLQ, сага возвратов, модель сверки — сохраняются и расширяются.

## План отката

- **До боевой эксплуатации**: откат = не включать. Все работы обратимы (ADR-008 reversible).
- **После включения**: фиче-флаг на возможность и на ТСП; «стоп-новых» (запрет создания подписок
  и новых списаний) с доведением уже открытых операций; данные обратно не мигрируются.
- **Откат выданных согласий** (владелец — solution-architect + платёжная операционная смена):
  пакетный отзыв согласий через адаптер (`cancelSubscription`) с подтверждением опросом
  `getConsentStatus`/сверкой; критерий успеха — 100 % согласий в `REVOKED`/`CANCELLED` и 0 новых
  списаний. Репетиция — часть A4.
- **Сигналы отката**: двойное списание; зачисление без подтверждённого статуса или после отзыва;
  лаг блокировки после нотификации об отзыве > 60 с; рост DLQ; средства в саспенс > 24 ч; всплеск
  фрода/отказов; расхождение сверки.
- **Владелец решения** об откате: solution-architect + владелец платёжного продукта (A3).
- **Репетиция отката** обязательна на A4 (`.arch-handoff/REHEARSAL.json`, PASS).

## Критерии приёмки (сводка)

Полный набор с EARS-сценариями — `specs/sbp-subscriptions/spec.md` и `specs/opkc-adapter/spec.md`.
Ключевое: нет списания без действующего согласия; нет зачисления без подтверждённого статуса или
после отзыва согласия (саспенс + разворот); повторные доставки идемпотентны; отзыв согласия
блокирует новые списания ≤ 60 с после нотификации; расхождения сверки = 0.
