# Solutioning — Платёжный шлюз СБП (C2B-приём)

Маршрут: **Critical** (значимость 11/15). Настоящий документ — полный Solutioning: контекст, компоненты, потоки, разбиение на ADR, NFR, план гейтов A0–A5, план отката, gaps.

## 1. Контекст и границы

Банк — участник СБП (эквайер/агент ТСП) принимает C2B-платежи от ТСП. Внешние системы: **ОПКЦ СБП (АО «НСПК»)** — операционный/клиринговый центр, **Банк России** — расчёты по корсчетам. Внутренние: **АБС** (счета ТСП), **антифрод/AML**, **SIEM**, **отчётность** (ЦБ/НСПК).

Подключение банка — по порядку ЦБ РФ (cbr.ru/PSystem/payment_system/actions/): договор с ПБР + СКЗИ → присоединение к Правилам ОПКЦ СБП → доработка ПО по документации Портала поддержки НСПК → тестовые испытания → активация. **Документация НСПК — внешний вход**: точный протокол получается по договору, публично не раскрыт (все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]` до получения).

Сценарии C2B в scope: динамический QR, статический QR/наклейка, кассовые ссылки, оплата по ссылке в e-commerce, возвраты. Roadmap (вне scope): C2C, выплаты B2C/B2B, диспуты. **Автоплатежи/подписки** выведены из roadmap 2026-09-28 и вошли в scope как рекуррентные C2B-списания по согласию плательщика (AD-008, см. §11).

## 3. Статусная модель платежа

```
CREATED ──► QR_ISSUED ──► PAID ──► CREDITED ──► COMPLETED
   │            │          │            │
   ▼            ▼          ▼            ▼
 FAILED      EXPIRED    FAILED      REFUNDED (через сагу возврата)
```

- `PAID` — подтверждённый НСПК статус; **только из него** разрешено зачисление (AD-005).
- Переходы — атомарные транзакции «статус + outbox + аудит» (AD-002).
- Повторные нотификации идемпотентны (AD-003).

## 4. Ключевые потоки

### 4.1 Оплата динамическим QR (счастливый путь)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant A as АБС

    T->>G: POST /payments (Idempotency-Key, сумма, реквизиты ТСП)
    G->>G: создать CREATED, outbox
    G->>N: регистрация QR (адаптер ОПКЦ)
    N-->>G: qrId + ссылка qr.nspk.ru/...
    G->>G: статус QR_ISSUED, outbox
    G-->>T: 201 {paymentId, qrId, qrUrl, qrImage}
    Note over N: плательщик сканирует QR и платит в своём банке
    N-->>G: нотификация PAID (eventId)
    G->>G: дедупликация по eventId, статус PAID, outbox
    G->>A: зачисление (paymentId, сумма, счёт ТСП)
    A-->>G: absDocId / подтверждение
    G->>G: статус CREDITED → COMPLETED, outbox
    G-->>T: вебхук COMPLETED
```

### 4.2 Возврат (сага)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant A as АБС
    participant N as ОПКЦ СБП (НСПК)

    T->>G: POST /refunds (refundId, paymentId, сумма)
    G->>G: проверка: платёж CREDITED/COMPLETED
    G->>A: списание со счёта ТСП (refundId)
    A-->>G: подтверждение
    G->>N: регистрация возврата (refundId)
    N-->>G: подтверждение возврата
    G->>G: статус REFUNDED, outbox
    G-->>T: вебхук REFUNDED
    Note over G: сбой на шаге → компенсация (отмена АБС-списания / повтор регистрации в НСПК / DLQ + runbook)
```

## 6. NFR

Полный набор с измеримыми целями — `docs/nfr.md`. Ключевое: доступность ≥ 99,95 %; RPO=0; RTO ≤ 1 ч; регистрация QR p95 < 500 мс; sustained 200 TPS / пик 500 TPS; сверка с НСПК ежечасная, с АБС суточная; двойных зачислений — 0. NFR подписок/мандатов — `docs/nfr.md` §7 (списаний после отзыва = 0; двойных списаний по (мандат, период) = 0; списание p95 < 1 с).

## 7. Гейты и критерии приёмки

- **A0 (readiness)**: ADR-001..007 заполнены, spine пролинтован, gaps зафиксированы. Критерий: PASS.
- **A1 (Spec)**: контракт API ТСП (v0.1 — `docs/contracts/tsp-api.md`), таблица переходов статусной машины (`docs/spec/state-machine.md`), контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md` — ядро↔транспорт, основа RFP), RFP-пакет по вендору (`docs/rfp/vendor-rfp.md`), NFR финализированы.
- **A2 (Plan)**: разбивка на задачи, walking skeleton определён (сквозной путь: ТСП → шлюз → мок НСПК → АБС-мок → нотификация).
- **A3 (человеческое решение)**: стратегия реализации (ADR-007) — **обязательно до реализации транспорта**.
- **A4 (conformance)**: fitness-проверки spine-инвариантов, нагрузочные тесты (NFR), тесты идемпотентности, ИБ-аудит.
- **A5 (post-deploy drift)**: сверка с НСПК/АБС в проде, SLO-отчёт через 30 дней, проверка отсутствия дрейфа от spine.

## 8. План отката

- **До боевой эксплуатации**: откат = не включать. Все работы обратимы (ADR-007 reversible).
- **После включения**: фиче-флаг на приём новых ТСП; мгновенный stop-new (запрет регистрации новых QR) без остановки обработки уже открытых операций; откат релиза — rolling; данные не мигрируются обратно (шлюз остаётся источником истины до полной сверки с АБС).
- **Аварийный сценарий**: DLQ → дежурная смена по runbook; сверка компенсирует потерянные нотификации; RTO ≤ 1 ч.

## 9. Gaps и внешние входы

| Gap | Что закроет | Владелец |
|---|---|---|
| Точный протокол НСПК (поля, тайминги, TLS-профили) | Документация НСПК по договору (Портал поддержки) | Проектный офис / НСПК |
| Регламенты НСПК (таймауты, сроки уведомлений, доступность) | Документация НСПК, правила ОПКЦ СБП | Проектный офис |
| Номер/редакция Положения ЦБ о защите информации при переводах | ИБ/комплаенс банка | ИБ |
| Контракт АБС на зачисление/списание (идемпотентность, SLA) | Интервью с владельцем АБС | Архитектор + АБС |
| Категория объекта КИИ, состав мер ФСТЭК | ИБ/КИИ банка | ИБ |
| Выбор конкретного вендора транспорта ОПКЦ | RFP по критериям ADR-007 (сертификаты ФСТЭК, тестовый контур, SLA, референсы) | Проектный офис / закупки |

## 11. Изменение 2026-09-28: подписки СБП — рекуррентные C2B-списания (ADR-008)

**Значимость и маршрут.** Изменение — **Critical (13/15)**: новый домен (согласие/мандат), неизвестная семантика протокола мандатов НСПК (`[ТРЕБУЕТ ПРОВЕРКИ]`), безлюдные финансовые списания (риск двойного/несанкционированного списания), регуляторика защиты плательщика и ПДн, влияние на контракты и статусную машину. Требуется полное проектирование (ADR + spec + контракты + NFR) и **повторное человеческое решение A3** — до реализации транспортных операций мандата.

**Что меняется.** Новый агрегат «мандат» (AD-009); расширение статусной машины платежа переходом `CREATED → PAID` без QR для списаний (AD-010); правило лимитов, сериализации и отзыва (AD-011); отмена незавершённых списаний и банковская компенсация подтверждённых при отзыве (AD-012); единый инициатор зачисления с атомарным claim (AD-013); наблюдаемость списания по ключу списания, не по `qrId` (AD-014); согласие только подтверждённое, с доказательством (AD-015); обязательный антифрод и уведомление до списания, fail-closed (AD-016). **Что не меняется.** AD-001…AD-008 (наследуемые инварианты): зачисление только из `PAID`, единственный адаптер ОПКЦ, outbox/идемпотентность, trust-зоны, стратегия ADR-007. Qr-приём не затрагивается.

**Поток списания.** ТСП `POST /v1/mandates/{id}/charges` → шлюз проверяет `ACTIVE`/лимит/период в одной транзакции → создаёт платёж `paymentOrigin=mandate` → ОПКЦ исполняет списание (без QR) → нотификация `paid` → зачисление в АБС из `PAID` → вебхук ТСП. Отзыв согласия останавливает будущие списания; уже подтверждённое списание возвращается только сагой возврата.

**Контракты.** `docs/contracts/tsp-api.md` v0.2-draft (§3.6–§3.9, аддитивно, `/v1` сохранён), `openapi/tsp-api.yaml` v0.2.0-draft, `docs/contracts/opkc-adapter.md` v0.2-draft (операции/события мандата — допсоглашение с вендором), `docs/rfp/vendor-rfp.md` (G8, P9/P10), `docs/spec/mandate-lifecycle.md` (жизненный цикл мандата).

**NFR.** `docs/nfr.md` §7: списаний после отзыва = 0; двойных списаний по (мандат, период) = 0; списание p95 < 1 с; сверка мандатов ежечасная, расхождений 0; регресс QR-приёма ≤ 5 %.

**Критерии приёмки (негативные — обязательны).** Мандат создаётся/активируется идемпотентно; списание активного мандата проходит полный FSM и доходит до ТСП; списание сверх лимита/вне периода/по неактивному мандату отклоняется без создания платежа; повтор списания за период не создаёт вторую проводку; **после отзыва — 0 списаний**; зачисление невозможно без `PAID`; выключение фиче-флага подписок не влияет на QR-приём.

**План отката.** До включения откат = не включать (все изменения аддитивны). После включения: per-ТСП kill-switch запрещает новые списания; управляемый отзыв активных мандатов через ОПКЦ; rolling-откат релиза; данные не мигрируются обратно (мандаты — история, платежи — источник истины). Сигналы-триггеры: доля отказов списаний выше порога, любой инцидент двойного списания, расхождение сверки мандатов, регуляторное замечание, рост жалоб плательщиков. Владелец решения — владелец продукта + архитектор, исполнение — дежурная смена; RTO ≤ 1 ч.

**Выносится на человека-архитектора (A3):** семантика протокола мандатов НСПК и требования к вендору; юридическая модель согласия и уведомления до списания; включать ли банковский шедулер (сейчас — нет, Deferred); лимиты и риск-политика; категорирование нового агрегата для КИИ/ПДн.
