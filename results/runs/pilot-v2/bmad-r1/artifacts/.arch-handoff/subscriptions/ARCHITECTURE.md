# Архитектурный контекст: подписки СБП (рекуррентные C2B-списания) — epic-context

Собран: 2026-09-28. Источники: `docs/adr/ADR-008-*.md`, `ARCHITECTURE-SPINE.md` (AD-009…AD-011), `docs/spec/mandate-lifecycle.md`, `docs/contracts/tsp-api.md` (v0.2), `docs/contracts/opkc-adapter.md` (v0.2), `docs/nfr.md` §7, `docs/rfp/vendor-rfp.md`.

## Цель изменения

Дать ТСП (кинотеатры, ЖКХ, связь) рекуррентные C2B-списания по **заранее данному согласию плательщика** (мандат), без QR и без действия клиента в момент списания. Подписки ранее были вне scope базового решения; изменение — критическое (13/15), выносится на A3.

## Что строим (в scope исполнителя)

1. **Агрегат «мандат»** в БД шлюза: создание → активация → приостановка/возобновление → отзыв; лимит разового списания, общий лимит, период действия, opaque `opkcMandateRef`.
2. **Списание как обычный платёж**: `POST /v1/mandates/{id}/charges` → тот же FSM, `paymentOrigin=mandate`, без шага QR (`CREATED → PAID`); зачисление в АБС — только из `PAID`.
3. **Валидация в одной транзакции с созданием платежа**: мандат `ACTIVE` ∧ `amount ≤ maxAmountPerCharge` ∧ время в периоде ∧ ТСП — владелец. Иначе — отказ без создания платежа.
4. **Идемпотентность**: `Idempotency-Key` + запрет повтора `merchantOrderId`/периода в рамках мандата (`409`).
5. **Отзыв немедленно запрещает новые списания**; уже подтверждённое (`PAID`) списание возвращается только сагой возврата.
6. **Нотификации ТСП**: `mandate.activated`, `mandate.rejected`, `mandate.revoked`, `mandate.suspended`; исход списания — стандартные `payment.*`.
7. **Сверка мандатов** с ОПКЦ; расхождение «у ОПКЦ отозван — у нас активен» — стоп-сигнал.
8. **Операции транспорта мандата** — через адаптер ОПКЦ (вендорский): `createMandate`, `getMandateStatus`, `revokeMandate`, `executeMandateCharge`, события `mandate.*`. Ядро контрактно-независимо от протокола НСПК; протокольные детали — `[ТРЕБУЕТ ПРОВЕРКИ]`, реализация транспорта — только после контракта с вендором.

## Что НЕ строим

- Банковский шедулер/биллинг-движок (расписание — у ТСП; Deferred).
- Реальный протокол НСПК напрямую — только через адаптер (мок на время walking skeleton).
- Отдельный сервис подписок со своим финансовым контуром — запрещён (второй путь к АБС/ОПКЦ).

## Связывающие инварианты (Rule — дословно, обязующая база)

- **AD-002.** «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции.»
- **AD-003.** «Повторная доставка любого сообщения не изменяет уже завершённое состояние.»
- **AD-005.** «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус).»
- **AD-004.** «Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.»
- **AD-001.** «Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза.»
- **AD-008 [ADOPTED].** «Ядро шлюза проектируется контрактно-независимым от транспорта. Реализация транспортного слоя начинается только после подписания контракта и получения документации НСПК.»
- **AD-009.** «Жизненный цикл согласия плательщика хранится в БД шлюза как отдельный агрегат…; каждый переход выполняется атомарно со сменой статуса, записью в outbox и аудит-логом (по образцу AD-002).»
- **AD-010.** «Рекуррентное списание исполняется как платёж той же статусной машины с признаком `paymentOrigin=mandate`: шаг выпуска QR пропускается (`CREATED → PAID`), зачисление в АБС по-прежнему возможно только из `PAID` (AD-005).»
- **AD-011.** «Условие “мандат `ACTIVE` ∧ `amount ≤ maxAmountPerCharge` ∧ остаток `maxTotalAmount` достаточен ∧ текущее время в периоде действия ∧ `tspId` совпадает с владельцем мандата” проверяется, а суммарный счётчик мандата инкрементируется под блокировкой или версией мандата в одной транзакции с созданием платежа; при невыполнении списание отклоняется без создания платежа. Проверка и создание списания сериализуются с отзывом/приостановкой так, что списание не может быть создано после коммита отзыва.»
- **AD-012.** «Отзыв или приостановка мандата в одной транзакции запрещает инициацию новых списаний и инициирует отмену всех незавершённых (ещё не `PAID`) списаний этого мандата в ОПКЦ. Если списание уже подтверждено (`PAID`/зачислено), оно исполняется до конца, и шлюз (а не ТСП) инициирует компенсацию — возврат по этому списанию через сагу ADR-005.»
- **AD-013.** «Зачисление в АБС инициируется ровно одним владельцем конвейера; переход `PAID → ABS_PENDING` фиксируется атомарным claim по `paymentId` (блокировка/lease) в одной транзакции с outbox. Сверка не вызывает АБС напрямую, а только дозапускает тот же claim.»
- **AD-014.** «Запрос статуса и выписка сверки адресуются по ключу списания (`reference` = `paymentId` ядра / `opkcChargeRef`), а не только по `qrId`. Отсутствие подтверждения трактуется как “не оплачено” (fail-closed): зачисление без подтверждённого статуса запрещено.»
- **AD-015.** «Активация мандата возможна только при получении от ОПКЦ подтверждённых условий согласия (лимиты, период, ТСП) и ссылки-доказательства; до этого мандат остаётся `PENDING_CONSENT` и списания запрещены.»
- **AD-016.** «Контроль антифрода/AML обязателен при создании мандата и на каждое списание; при недоступности контроля списание отклоняется, а не пропускается (fail-closed). Списание не исполняется без подтверждения исполнения требования уведомления плательщика до списания.»

Примечание: приостановка (`SUSPENDED`) — **локальный** обратимый запрет шлюза, в ОПКЦ не передаётся; необратимый отзыв — только `revokeMandate`.

## Запрещено менять

AD-001…AD-008 и принятые ADR-001…ADR-007; контракты QR-приёма и их поведение; коды ошибок/события v0.1; публичный путь `/v1` (версия ломается только через `/v2`); инвариант «зачисление только из `PAID`»; границу «ядро ↔ вендорский транспорт». Конфликт с spine обязан **останавливать** работу и эскалироваться, а не решаться локально.
