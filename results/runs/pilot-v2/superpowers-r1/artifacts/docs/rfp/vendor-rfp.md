# RFP: вендор транспортного адаптера ОПКЦ СБП — чек-лист и пакет закупки

- Status: Draft (для A1; запуск после подписания NDA с вендорами; требования дельты 0.2 — после ратификации ADR-008 на A3)
- Owner: проектный офис / закупки + solution-architect
- Связано: ADR-007 (гибрид), ADR-003, ADR-008, AD-004, AD-008, AD-009, `docs/contracts/opkc-adapter.md`

## 1. Что покупаем (scope)

**Транспортный адаптер ОПКЦ СБП** — сертифицированный компонент, реализующий внутренний контракт `docs/contracts/opkc-adapter.md` поверх протокола участника НСПК, включая:

1. Транспорт к ОПКЦ СБП (mTLS/ГОСТ, сертификаты УЦ НСПК, профили TLS по требованиям НСПК).
2. СКЗИ/HSM для ключевого материала (или интеграция с СКЗИ банка).
3. Нормализацию статусов/ошибок НСПК в канонический контракт.
4. Тестовый контур НСПК (sandbox) для разработки и PVT ядра шлюза.
5. Эксплуатационную документацию, метрики, runbook.
6. Поддержку и SLA.
7. **Операции и события рекуррентных списаний** (дельта 0.2 контракта): `createDebit`, `getDebitStatus`, события `debit.confirmed`, `debit.rejected`, `mandate.activated`, `mandate.revoked` — поверх протокола автоплатежа/подписки СБП; протокольные детали `[ТРЕБУЕТ ПРОВЕРКИ]`.

**Не входит в scope вендора:** ядро шлюза (API ТСП, реестр мандатов, планировщик списаний, статусная машина, сверка, АБС-интеграция) — собственная разработка банка (ADR-008).

## 2. Обязательные критерии допуска (gate — без них предложение отклоняется)

| # | Критерий | Как проверяем |
|---|---|---|
| G1 | Сертификаты ФСТЭК на СКЗИ / соответствие требованиям НСПК и ЦБ | Копии сертификатов, письма НСПК |
| G2 | Референсы: внедрение СБП-транспорта в банках сопоставимого масштаба (≥ N операций/мес) | Список референсов + контакты, проверяем |
| G3 | **Идемпотентность мутирующих операций по `reference`** (opkc-adapter §5) — повторный вызов не создаёт дубль в ОПКЦ | Демо/POC: повторный `createPaymentLink` с тем же `paymentId` → один QR |
| G4 | Реализация полного набора методов/событий контракта opkc-adapter §3–4 | Сверка по чек-листу контракта |
| G5 | Наличие тестового контура НСПК и возможность гонять сценарии paid/rejected/expired/повторы | Демо на тестовом контуре |
| G6 | Финансовая устойчивость и отсутствие конфликта интересов (не конкурент банка по эквайрингу) | Финансовая отчётность, декларация |
| G7 | Передача исходного кода/эскроу на случай прекращения поддержки | Условия эскроу в контракте |
| G8 | **Идемпотентность рекуррентного списания** по `reference = mandateId + periodKey` (opkc-adapter §5) — повторный `createDebit` не создаёт второе списание | Демо/POC (P9): повторный `createDebit` с тем же reference → одно списание |

## 4. Технические требования (детализация)

Вендор обязан подтвердить по каждому пункту контракта `opkc-adapter.md`:

- **Методы** (§3): `registerTsp`, `createPaymentLink`, `getPaymentStatus`, `cancelPaymentLink`, `createRefund`, `getRefundStatus`, `getReconciliationReport`, а также дельта 0.2 — `createDebit`, `getDebitStatus` — сигнатуры, таймауты, нормализованные ответы.
- **События** (§4): все 8 базовых типов плюс события дельты 0.2 (`debit.confirmed`, `debit.rejected`, `mandate.activated`, `mandate.revoked`) — с `eventId`; at-least-once; устойчивость к поздним/повторным событиям.
- **Идемпотентность** (§5): обязательный proof на POC (G3; для списаний — G8/P9).
- **Таймауты/ретраи/circuit breaker** (§6): ретраи внутри адаптера, `503 TRANSPORT_UNAVAILABLE`, событие `transport.unavailable`; политика размыкания конфигурируема.
- **NFR** (§7): нагрузка (включая списания: ≥ 40 TPS sustained, пик 100 TPS), latency, потеря событий = 0, доступность ≥ 99,95 %, Prometheus-метрики, trace id.

## 5. Сценарии POC (обязательный этап перед финальным решением)

На тестовом контуре НСПК вендор демонстрирует:

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| P1 | Счастливый путь: createPaymentLink → payment.paid | qrId/qrUrl корректны; событие с `eventId` |
| P2 | **Повтор createPaymentLink с тем же `reference`** | тот же qrId, дубля QR нет (G3) |
| P3 | Нотификация rejected/expired | нормализованные события, reasonCode |
| P4 | Отказ канала к НСПК (остановка симулятора) | circuit breaker → `503 TRANSPORT_UNAVAILABLE` + `transport.unavailable`, восстановление |
| P5 | Потеря/задержка нотификации | сверка через `getPaymentStatus`/`getReconciliationReport` находит операцию |
| P6 | Нагрузка 200 TPS sustained, пик 500 TPS | latency в допусках, потерь 0 |
| P7 | Ротация ключей/сертификатов без остановки | документированная процедура, без сбоев |
| P8 | Двойная доставка события (повтор `eventId`) | ядро дедуплицирует; вендор подтверждает, что дубль возможен и это норма |
| P9 | **Повтор createDebit с тем же `reference` (`mandateId` + `periodKey`)** | одно списание в ОПКЦ, повтор возвращает тот же результат (G8) |
| P10 | Отзыв мандата после отправки списания | нормализованное событие `debit.rejected`/`mandate.revoked`; отсутствие новых списаний после отзыва |

## 6. Требования к документации и эксплуатации

- Архитектура адаптера, схема размещения в контуре банка (trust-зоны, ADR-006).
- Схема ключей/сертификатов: выпуск, хранение в СКЗИ/HSM, ротация, компрометация.
- Runbook: инциденты (канал вниз, DLQ, расхождения сверки), эскалации к вендору.
- Метрики и алерты: перечень, пороги, интеграция с SIEM/мониторингом банка.
- Обучение: 2 дня эксплуатации + 2 дня разработки (интеграция контракта).

## 7. SLA (целевые, согласуются на переговорах)

| Параметр | Цель |
|---|---|
| Доступность адаптера | ≥ 99,95 % (мес.) |
| Время реакции на инцидент | критичный: ≤ 30 мин; высокий: ≤ 2 ч |
| Время восстановления (RTO вендора) | ≤ 4 ч |
| Обновления протокола НСПК | за ≤ 30 дней до требований НСПК |
| Поддержка | 24×7, русскоязычная |

## 8. Коммерческие условия (запросить)

- Модель лицензирования: perpetual/подписка; привязка к TPS или к числу ТСП.
- Внедрение: фикс + T&M; объём интеграционных работ вендора.
- Сопровождение: годовая стоимость, SLA-уровни.
- Обучение и документация — включено.
- Эскроу исходного кода (G7) — условия.

## 9. Процесс отбора и график

1. RFI (2 нед): квалификация по G1–G7, резюме решения, цены-ориентиры.
2. Демо (1 нед): архитектура, тестовый контур, ответы по чек-листу контракта.
3. **POC на тестовом контуре НСПК (3–4 нед)**: сценарии §5; параллельно ядро шлюза разрабатывается на мок-адаптере.
4. Финальное КП + коммерческие переговоры (2 нед).
5. Контракт и старт внедрения.

**Kill criteria** (стоп в любой момент): не подтверждён G3 (идемпотентность); POC не проходит P2/P4; вендор не может предоставить тестовый контур; стоимость/сроки вне допустимых пределов бизнес-кейса.

## 10. Риски закупки

| Риск | Митигация |
|---|---|
| Вендор затягивает POC | Твёрдый дедлайн; параллельно 2 вендора на POC (если позволяет рынок) |
| Идемпотентность не реализуема из-за протокола НСПК | Эскалация к НСПК; если дубль QR неизбежен — компенсация на ядре (дедупликация по результату + сверка), решение фиксируется ADR |
| Зависимость от единственного вендора | Эскроу кода (G7), контрактная заменимость по контракту opkc-adapter |
| Смена требований НСПК | SLA на обновления (§7), тестовый контур для регресса |
| Конфликт интересов (вендор-конкурент) | G6, декларация |
| Протокол автоплатежа/подписки СБП недоступен банку или ограничен | Ранний запрос регламента НСПК; если протокол недоступен — пересмотр ADR-008 (условие expiry, решение A3) |
| Вендор не подтверждает G8 (идемпотентность списания) | Kill criterion для дельты 0.2: контур подписок не запускается до подтверждения; компенсация — дедупликация на ядре + сверка (решение фиксируется ADR) |
