# NFR — Платёжный шлюз СБП (C2B-приём)

Целевые значения — **измеримые критерии приёмки** на гейтах A4/A5. Значения помечены как baseline; финальные согласуются с бизнесом и НСПК (регламенты оператора могут быть строже).

## 1. Доступность

| Метрика | Цель | Метод проверки |
|---|---|---|
| Доступность шлюза (месяц) | ≥ 99,95 % (плановая); целевая 99,99 % в часы пик | Uptime-мониторинг, синтетика на критичный путь |
| Недоступность регистрации QR (месяц) | ≤ 22 мин суммарно (для 99,95 %) | SLO-отчёт |
| Плановая недоступность | 0 при деплоях (rolling, без downtime) | CI/CD pipeline |

## 2. Производительность

| Метрика | Цель | Метод проверки |
|---|---|---|
| Latency API ТСП «регистрация QR» | p95 < 500 мс, p99 < 1 с (без учёта времени НСПК) | Нагрузочный тест, APM |
| Latency «запрос статуса» | p95 < 300 мс | Нагрузочный тест |
| Доставка нотификации ТСП от события НСПК | p95 < 5 с | Метрика лага очереди |
| Зачисление в АБС от подтверждения НСПК | p95 < 60 с (SLA с АБС) | Метрика процесса |
| Throughput sustained | 200 TPS | Нагрузочный тест |
| Throughput пик (burst) | 500 TPS, допустимый burst 1000 TPS на 1 мин | Нагрузочный тест |
| Масштабируемость | ×2 без изменения архитектуры (горизонтальное масштабирование) | Load-test на 400 TPS |

## 3. Надёжность и восстановление

| Метрика | Цель | Метод проверки |
|---|---|---|
| RPO | 0 (нет потери зарегистрированных операций, статусов, событий outbox) | Тест отключения ноды, сверка |
| RTO (восстановление обработки) | ≤ 1 час | Chaos-тест, DR-учения |
| Потеря нотификации НСПК | 0 (компенсируется сверкой и опросом статусов) | Сверка с НСПК |
| Двойное зачисление при повторах | 0 (идемпотентность) | Тест на повторную доставку |

## 4. Сверка и расхождения

| Метрика | Цель | Метод проверки |
|---|---|---|
| Сверка с НСПК | ежечасная; расхождений по завершённым операциям — 0 | Reconciliation-отчёт |
| Сверка с АБС | суточная; расхождений — 0 | Reconciliation-отчёт |
| Отработка расхождений | 100 % по runbook за ≤ 4 часа | KPI дежурной смены |

| Метрика | Цель | Метод проверки |
|---|---|---|

## 7. Рекуррентные списания (подписки СБП) — изменение ADR-008/ADR-009

Новые бюджеты поверх базовых (§1–§6). Спецификация — `docs/spec/subscriptions.md`.

| Метрика | Цель | Метод проверки |
|---|---|---|
| Двойное списание за один период серии | **0** | тест на повтор ключа (`mandateId`, `occurrenceKey`); сверка с ОПКЦ |
| Списание по согласию не в статусе `ACTIVE` | **0** | тест-свойство `consent-before-auto-action`; аудит согласий |
| Запрет новых списаний после отзыва | 100 %; p95 < 60 с, максимум < 5 мин от события отзыва | метрика процесса, тест, аудит |
| Регистрация согласия (приём запроса, без ОПКЦ) | p95 < 500 мс | нагрузочный тест, APM |
| Списание по согласию (приём запроса до ответа) | p95 < 800 мс, p99 < 1,5 с | нагрузочный тест, APM |
| Подтверждение списания → зачисление в АБС | p95 < 60 с (как для QR, §2) | метрика процесса |
| Неопределённый исход списания приведён к терминальному | 100 % в течение 24 ч (сверкой) | reconciliation-отчёт |
| Throughput «платёжный день» (1–10 число месяца) | 1000 TPS в течение 1 ч без роста DLQ и с удержанием p95 | нагрузочный тест ≥ 1 ч |
| Сверка согласий с ОПКЦ | открытые — ежечасно; полная — суточно; расхождений по `ACTIVE` — 0 | reconciliation-отчёт |
| RPO по согласиям и журналу согласий | 0 | тест отключения ноды, сверка |
| Неизменяемость журнала согласий | 100 % (нет UPDATE/DELETE записей) | проверка append-only, права БД |
| ПДн в логах и метках метрик | 0 | скан логов, тест-свойство `no-pii-in-logs` |
| Хранение согласий | не менее срока по 161-ФЗ/152-ФЗ `[ТРЕБУЕТ ПРОВЕРКИ]` | аудит по политике хранения |

Пояснение к «платёжному дню»: пик массовых списаний ЖКХ и связи приходится на начало месяца и не совпадает с профилем одноразовых платежей. Бюджет 1000 TPS — цель для сглаживания через очередь (`queue-load-leveling`) с приоритетами и shed-политикой; точное значение согласуется с бизнесом (п. A3).

## Зависимости (внешние входы для NFR)

- Регламенты НСПК: таймауты, сроки уведомлений, требования к доступности [ТРЕБУЕТ ПРОВЕРКИ — из документации НСПК].
- SLA АБС на зачисление и списание (согласуется с владельцем АБС).
- Требования ЦБ к защите информации при переводах (номер Положения — уточнить у ИБ) [ТРЕБУЕТ ПРОВЕРКИ].

## Проблема

Нефункциональные цели платёжного контура в исходном виде заданы как «высокая доступность», «быстро» и «надёжно». Без числа, метода измерения и владельца такие цели нельзя ни проверить на гейтах A4/A5, ни предъявить вендору транспорта, ни согласовать с бизнесом — они не создают бюджета, который можно нарушить. Этот документ переводит их в измеримые бюджеты с методом проверки.

## Критерии приёмки

- When документ NFR утверждается, the архитектор shall по каждой метрике указать целевое значение и метод проверки (число + способ измерения), а не качественное прилагательное.
- When целевое значение зависит от внешнего регламента (НСПК, ЦБ, SLA АБС), the NFR shall содержать пометку `[ТРЕБУЕТ ПРОВЕРКИ]` и владельца, который её закроет.
- When NFR нельзя проверить на моках/стенде, the NFR shall иметь указанный метод проверки в проде (SLO-отчёт, reconciliation-отчёт, DR-учения).
- When два NFR противоречат друг другу (согласованность против доступности), the противоречие shall быть разрешено явным trade-off в ADR, а не умолчанием.

## Риски

- **Бумажный DR.** RTO/RPO, не проверенные учениями, остаются декларацией; при реальном сбое цель не будет достигнута.
- **Внешние регламенты строже целей.** Требования НСПК по таймаутам и доступности могут быть жёстче baseline — тогда целевые значения пересматриваются, а часть архитектуры (очереди, ретраи) — тоже.
- **Нереалистичный burst.** Цель «платёжный день» 1000 TPS, не подтверждённая нагрузочным тестом ≥ 1 ч, даст деградацию именно в пик списаний и рост DLQ.
- **NFR выбраны после фиксации инфраструктуры.** Тогда бюджеты подгоняются под выбранную платформу (хвост виляет собакой) и не выполняются.
- **Одинаковые цели для разных критичностей.** Перезаклад стоимости на некритичные направления: отчётность, тест-контуры и приём платежей получат одинаковые бюджеты.
