# Design

## Context

См. `proposal.md` — Why. Принятое решение (baseline) — «Платёжный шлюз СБП (C2B-приём)», маршрут **Critical** (значимость 11/15): `ARCHITECTURE-SPINE.md` (AD-001…AD-008), `docs/solutioning.md`, `docs/nfr.md`, `docs/adr/ADR-001…007`, `docs/spec/state-machine.md`, `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`, `openapi/tsp-api.yaml`.

Ограничивающие факты baseline:
- Единый источник истины о финансовом статусе — конечный автомат платежа в БД шлюза; переходы атомарны с outbox и аудитом (AD-002); зачисление в АБС — только из `PAID` (AD-005).
- Единственный адаптер ОПКЦ знает протокол НСПК; ядро контрактно-независимо от транспорта (AD-004, AD-008).
- Протоколы НСПК — внешний вход: до получения документации все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Возвраты — сага (ADR-005), нотификации — at-least-once с дедупликацией (ADR-004).

Новое требование бизнеса: **рекуррентные C2B-списания по согласию плательщика (подписки СБП)**.

## 1. Значимость и маршрут (deliverable 1)

Оценка `significance_score` (инструмент Spine) по заявленным триггерам:

| Триггер | Значение | Обоснование |
|---|---|---|
| new_component | true | новый модуль «мандаты» + планировщик списаний |
| cross_domain_integration | true | новый домен согласия пересекает ТСП-API, ядро, адаптер ОПКЦ, АБС |
| api_contract_change | true | новые пути/схемы в API ТСП |
| data_contract_change | true | новые сущности mandate/charge-attempt, новые поля платежа |
| consistency_model_change | true | новый жизненный цикл согласия и списания по периоду |
| security_boundary_change | true | новая возможность движения денег без интерактивного действия плательщика |
| trust_zone_change | true | хранение согласия плательщика как нового чувствительного артефакта |
| significant_nfr | true | новые измеримые цели (точность планировщика, окно отзыва) |
| rto_rpo_targets | true | RPO=0 для мандатов и расписаний; RTO планировщика |
| financial_impact | true | финансово значимые операции |
| criticality_or_exception | true | платёжный контур, КИИ |

**Вердикт инструмента: Score 11 → маршрут Critical** (5+ триггеров и критические триггеры `security_boundary_change` / `criticality_or_exception`). Маршрут — функция заявленных триггеров, а не истина о решении; триггеры для нового изменения оценены тем же консервативным порогом, что и baseline.

**Следствие маршрута**: полный Solutioning (этот документ + ADR-008/ADR-009 + spine-дельта AD-009…AD-012), обязательная человеческая точка **A3** по спорным развилкам (§8), walking skeleton до массовой генерации, evidence-гейты A4/A5. Дельта-спека `changes/add-sbp-subscriptions/DELTA.md` используется как **аудиторский след намерения** «что меняется в спайне», а не как замена полному Solutioning.

> **Внимание (расхождение маршрутов).** Инструмент `architect_review` вывел авто-маршрут из git-диффа как **Fast** (score 1, `api_contract_change`): на этом шаге изменения — только документы и контракт, новый компонент ещё не в коде, поэтому дифф недооценивает изменение. Это маршрут «по составу файлов», а не по смыслу: заявленный по триггерам scope (`significance_score`) — **Critical**. **Маршрут изменения — Critical**; для гейта следует зафиксировать `route lock`/провести изменение по Critical-профилю (evidence-бандл 13 артефактов, A3 человеком, состязательное ревью, `decision_quality`). Нельзя понижать маршрут по авто-диффу — это обход анти-обхода (anti-bypass S-1).

## 2. Влияние на принятую архитектуру (deliverable 2)

| Инвариант baseline | Затронут | Что меняется | Что НЕ меняется |
|---|---|---|---|
| **AD-001** Изоляция платёжного контура | Да (расширение) | в `Binds` добавляются «хранилище мандатов» и «планировщик списаний»; они остаются внутри платёжного контура | принцип изоляции; взаимодействие с АБС/ОПКЦ — только через адаптеры |
| **AD-002** Статусная машина — источник истины | Да (расширение) | добавляется состояние **мандата** с той же дисциплиной «статус + outbox + аудит в одной транзакции»; списание — это платёж, а не второй реестр | «финансовый статус + outbox атомарно»; единственный источник истины |
| **AD-003** Идемпотентность | Да (расширение) | в `Binds` добавляется ключ списания `(mandateId, billingPeriodKey)` | «повтор не меняет завершённое состояние» |
| **AD-004** Единственный адаптер ОПКЦ | Да (расширение контракта) | адаптер получает методы/события подписок; протокол НСПК по-прежнему знает только он | единственный адаптер; ядро не знает протокола |
| **AD-005** Зачисление только из `PAID` | Нет (переиспользуется) | списание идёт тем же путём `PAID → CREDITED`; запрет зачисления из `CREATED`/`QR_ISSUED` сохраняется | правило и fitness «недостижимость зачисления вне `PAID`» |
| **AD-006** Trust-зоны и сегментация | Да (без новых зон) | данные согласия размещаются в существующей изолированной зоне; новых зон/каналов нет | топология зон, ключевой материал в СКЗИ/HSM |
| **AD-007** НПС/КИИ/ПДн | Да (расширение) | аудит покрывает переходы мандата; добавляется минимизация данных согласия | неизменяемый аудит, СКЗИ/ГОСТ, 152-ФЗ/161-ФЗ/187-ФЗ |
| **AD-008** Гибридная стратегия [ADOPTED] | Нет (усиливается) | расширение протокола входит в scope вендорского транспорта (RFP-расширение), а не в ядро | ядро контрактно-независимо; граница — внутренний контракт адаптера |

**Вывод**: изменение — **развивающее (additive)**. Оно не опровергает ни один инвариант baseline и не требует пересмотра ADR-001…007. Опасные «искушения», которые изменение могло бы нарушить, и почему они отвергнуты:
- завести **отдельную** статусную машину для списаний → нарушило бы AD-002 (два источника истины) и AD-005 (двойной путь зачисления);
- позволить планировщику зачислять/инициировать платёж вне контура → нарушило бы AD-001/AD-005;
- хранить полные данные плательщика «для удобства» → нарушило бы AD-007 (минимизация ПДн).

## 3. Архитектурное решение (deliverable 3)

Формализованное решение — в `docs/adr/ADR-008-…md` (модель подписки и планировщик) и `docs/adr/ADR-009-…md` (мандат/согласие: хранение, отзыв, граница доверия). Ниже — сводка развилок с альтернативами.

### D1. Модель подписки: мандат как сущность + переиспользование статусной машины платежа

**Решение**: мандат (согласие) — отдельная сущность со своим жизненным циклом; **списание — это обычный платёж** СБП (`Payment`), связанный с мандатом и периодом (`mandateId`, `billingPeriodKey`), проходящий существующий автомат `CREATED → QR_ISSUED/… → PAID → CREDITED → COMPLETED`.

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Мандат отдельно, списание = платёж (выбран)** | единый источник истины (AD-002), зачисление только из `PAID` (AD-005) переиспользуется, сверка/возвраты работают как есть | нужен явный признак «платёж-списание» и проверки условий мандата | — |
| B. Отдельная статусная машина для списаний | «чистая» модель подписок | два источника истины, дублирование идемпотентности/сверки/возвратов, риск расхождения с AD-002/AD-005 | нарушает baseline |
| C. Мандат внутри карточного процессинга | переиспользование инфраструктуры | иная семантика, каскадные сбои, замедление релизов | уже отвергнуто в ADR-001 |
| D. Вендорская «коробка» подписок | быстрый старт | закрытая логика статусов, lock-in, сложный аудит ЦБ | уже отвергнуто в ADR-007 |

### D2. Где живёт мандат и планировщик: модуль в платёжном контуре

**Решение**: мандаты и планировщик списаний — **модули внутри существующего платёжного контура шлюза**, разделяющие БД и outbox ядра (локальная транзакция «создать списание + событие мандата»).

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Модуль в платёжном контуре (выбран)** | атомарность «списание + outbox + аудит» (AD-002), нет распределённой согласованности, минимум новых компонентов | рост кодовой базы ядра шлюза; нужна дисциплина модульных границ | — |
| B. Отдельный сервис подписок со своей БД | изоляция, независимый релиз-цикл | потребует распределённой транзакции/саги между «сервисом подписок» и «платежами», разойдутся источники истины | усложняет то, что baseline делает простым |
| C. Внешний cron/ETL | простота | нет идемпотентности и outbox, потеря/двойное срабатывание при сбоях | нарушает AD-002/AD-003 |
| D. Списания инициирует ОПКЦ (pull от НСПК) | нет собственного планировщика | заявленная модель — инициатор ТСП; зависит от протокола `[ТРЕБУЕТ ПРОВЕРКИ]` | оставлено открытым вопросом §7 |

### D3. Идемпотентность списания: детерминированный ключ периода

**Решение**: ключ списания — детерминированный `(mandateId, billingPeriodKey)` (например `md_123:2026-10`), уникальный индекс в БД; повтор срабатывания планировщика возвращает существующий платёж, а не создаёт новый. Для ретраев внутри одного периода повторно используется тот же платёж-списание.

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Детерминированный ключ периода (выбран)** | доказуемо «одно списание за период», совместимо с retry-at-least-once | нужна политика для повторной попытки после терминального `FAILED` | — |
| B. Случайный `Idempotency-Key` на попытку | простота | повторное срабатывание планировщика даёт второе списание | риск двойного списания — финансовый инцидент |
| C. Дедупликация «по содержимому» | нет ключа | два легитимных списания на равную сумму схлопнутся | ложные дубли (см. anti-pattern `idempotent-consumer`) |

### D4. Согласие/мандат: хранение, отзыв, граница доверия

**Решение**: мандат хранится в БД платёжного контура; хранится только минимум — псевдонимизированный `payerRef` и ссылка согласия `consentRef`; отзыв, полученный от ОПКЦ, немедленно блокирует будущие списания (проверка статуса мандата — в той же транзакции, что и создание списания); переходы мандата — в неизменяемом аудит-логе.

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Локальное хранение минимума + отзыв по событию (выбран)** | локальный источник истины (AD-002), минимизация ПДн (AD-007), управляемая гонка отзыва | нужна дисциплина проверки статуса в транзакции | — |
| B. Не хранить мандат локально, спрашивать у НСПК | нет дублирования данных | нет локальной истины, зависимость каждого списания от НСПК, не выдержит AD-002 | нарушает baseline |
| C. Хранить полные данные плательщика | «больше данных для аналитики» | нарушение 152-ФЗ, рост поверхности атаки | нарушает AD-007 |

### D5. Расширение контракта API ТСП: аддитивно в `/v1`

**Решение**: новые пути/схемы/поля добавляются в `/v1`; `info.version` 0.1.0 → 0.2.0 (minor, draft); ломающие изменения — только в `/v2`. Альтернативы: сразу `/v2` для подписок (лишний форк версий при отсутствии ломающих изменений) и «отдельный сервис подписок со своим API» (два API у одного потребителя, расходится с AD-001/AD-002) — отвергнуты.

### D6. Транспорт подписок: расширение вендорского адаптера

**Решение**: методы/события подписок входят в **внутренний контракт адаптера ОПКЦ** и в scope вендора (расширение RFP); ядро остаётся контрактно-независимым (AD-008). Альтернативы: второй адаптер (дублирование протокола, нарушение AD-004), рекуррент своими силами (сертификация СКЗИ/НСПК — редкие компетенции), фиксировать `full-vendor` для подписок (меняет ADR-007) — не выбраны; см. §8 (решение человека).

## 4. Изменения контрактов без поломки потребителей (deliverable 4)

### 4.1 `openapi/tsp-api.yaml` (аддитивно)

- **Новые пути**: `POST /v1/mandates`, `GET /v1/mandates`, `GET /v1/mandates/{mandateId}`, `POST /v1/mandates/{mandateId}/cancel`, `GET /v1/mandates/{mandateId}/charges`.
- **Новые схемы**: `MandateRequest`, `Mandate`, `MandateList`, `MandateCancelRequest`.
- **Аддитивные поля существующих схем**: `Payment.mandateId` (optional), `Payment.billingPeriodKey` (optional).
- **Новые коды ошибок** (RFC 9457 + канонический `code`): `MANDATE_NOT_FOUND` (404), `MANDATE_NOT_ACTIVE` (409), `MANDATE_CONSENT_PENDING` (409), `MANDATE_LIMIT_EXCEEDED` (422).
- **Идемпотентность**: `Idempotency-Key` обязателен на `POST /v1/mandates` и `POST /v1/mandates/{id}/cancel`; GET — идемпотентны.
- **Вебхуки**: новые типы `mandate.activated`, `mandate.revoked`, `mandate.expired`, `charge.completed`, `charge.failed`; контракт доставки (HMAC, `eventId`, at-least-once) не меняется.

**Аргумент совместимости**: не удалено ни одно поле/операция; новые поля — опциональные; новые пути — изолированы. Проверка: `contract_diff` (old → new) обязан не найти breaking changes; `openapi_lint` — PASS; существующие потребители `POST /v1/payments` и `GET /v1/payments/{id}` работают без изменений.

### 4.2 `docs/contracts/opkc-adapter.md` (аддитивно)

- Новые синхронные методы: `registerMandate`, `getMandateStatus`, `cancelMandate`, `createMandateCharge` (идемпотентность по `reference = paymentId`), `getMandateReconciliationReport`.
- Новые события: `mandate.activated`, `mandate.revoked`, `mandate.expired`, `mandateCharge.paid`, `mandateCharge.rejected`, `mandateCharge.failed`.
- Гарантии, таймауты, ретраи, circuit breaker — как в базовом контракте; нормализация статусов — обязанность адаптера.
- Протокольные детали подписок НСПК — `[ТРЕБУЕТ ПРОВЕРКИ]`; состав методов уточняется после получения документации и подтверждения вендора.

## 5. Измеримые NFR для нового функционала (deliverable 5)

Продолжение `docs/nfr.md`; значения — baseline, финализируются с бизнесом и НСПК (регламенты оператора могут быть строже).

| Метрика | Цель | Метод проверки |
|---|---|---|
| Точность запуска списания | отклонение от расписания p95 ≤ 5 мин, p99 ≤ 15 мин (штатный режим) | мониторинг планировщика |
| Сквозное завершение списания «расписание → COMPLETED» | p95 ≤ 120 с | метрика процесса (поверх базовых: зачисление p95 < 60 с, нотификация p95 < 5 с) |
| Двойные списания на `(mandateId, billingPeriodKey)` | **0** при повторе планировщика и ретраях | тест дублирующего срабатывания, сверка |
| Зачисление вне подтверждённого `PAID` по списанию | **0** | fitness-тест недостижимости |
| Окно отзыва согласия | от `mandate.revoked` до гарантированной блокировки новых списаний ≤ 60 с; отзыв обязан опережать следующий плановый запуск с запасом | тест гонки «отзыв ↔ запуск» |
| Валидация лимита мандата | 100 % попыток проверены; списаний сверх лимита — 0 | тест + сверка |
| Пиковая пропускная способность списаний (границы месяца) | sustained ≥ 300 попыток/мин, рост ×2 без перепроектирования | нагрузочный тест |
| Лаг просроченных списаний | просроченных (> 15 мин) — 0; рост → алерт ≤ 5 мин | мониторинг очереди/метрик |
| Доступность подписок (мандат+планировщик) | ≥ 99,95 % (мес.) | SLO-отчёт |
| RPO/RTO подписок | RPO = 0 (мандаты, расписания, статусы не теряются); RTO ≤ 1 ч | chaos-тест/учения, сверка |
| Наблюдаемость | trace id на 100 % операций; алерты: DLQ, просрочка, ошибка отзыва | APM/мониторинг |
| Аудит мандатов и списаний | 100 % переходов и инициаций в неизменяемом логе | аудит SIEM |
| Латентность API мандатов | `GET /v1/mandates/{id}` p95 < 300 мс; `POST /v1/mandates` p95 < 500 мс (без учёта времени ОПКЦ) | нагрузочный тест, APM |
| Data locality ПДн согласия | данные согласия — только в RU-контуре | fitness: скан маршрутов данных |

## 6. Критерии приёмки и план отката (deliverable 6)

### 6.1 Критерии приёмки (проверяемые, EARS)

- **Позитивные**
  - `When` активный ТСП регистрирует мандат, the шлюз `shall` вернуть `201` с `mandateId` и `PENDING_CONSENT` (тест `POST /v1/mandates`).
  - `When` приходит `mandate.activated`, the шлюз `shall` перевести мандат в `ACTIVE` атомарно с outbox и аудитом (тест перехода + аудит).
  - `When` наступил период по `ACTIVE`-мандату, the планировщик `shall` создать списание-платёж, которое доходит до `COMPLETED` (сквозной тест на моках).
  - `When` платеж-списание в `PAID`, the зачисление `shall` произойти только из `PAID` (fitness-тест недостижимости зачисления вне `PAID`).
- **Негативные**
  - `When` планировщик срабатывает дважды за период, the шлюз `shall` не создать второе списание (тест дубля: эффект ×1).
  - `If` мандат отозван, `then` новые списания `shall not` инициироваться; гонка «отзыв ↔ запуск» не создаёт списание (тест гонки).
  - `When` сумма превышает лимит мандата, the шлюз `shall not` создать списание и `shall` алертить (тест лимита).
  - `When` ОПКЦ отклоняет списание, the платёж `shall` перейти в `FAILED`, а мандат `shall` остаться `ACTIVE` (тест).
  - `When` существующий потребитель вызывает `POST /v1/payments`, поведение и схема ответа `shall not` измениться (регресс-тест контракта).
- **Откат**
  - Успешный откат: фиче-флаг снят; новые списания не инициируются; существующие разовые платежи и их сверка не затронуты; `0` потерянных/двойных зачислений (тест отката).

### 6.2 План отката

- **До боевой эксплуатации**: откат = не включать фичу; работы обратимы (ADR-008: reversible/costly по разделам).
- **Фиче-флаги**: `sbp_subscriptions_enabled` (глобально) + allowlist ТСП. Снятие флага мгновенно прекращает приём новых мандатов и запуск списаний, не затрагивая разовый приём.
- **«Stop-new» без остановки обработки**: запрет регистрации новых мандатов и новых плановых списаний; уже созданные списания доводятся до терминального состояния (зачисление/возврат) — деньги не «зависают».
- **Судьба действующих мандатов при инциденте** — решение человека (§8): (а) продолжить обслуживание существующих мандатов без новых, (б) полный стоп подписок с досрочным обслуживанием незавершённых списаний. По умолчанию — (а).
- **Данные**: обратной миграции нет; таблицы мандатов аддитивны; БД шлюза остаётся источником истины до полной сверки с АБС/НСПК.
- **Сигналы-триггеры откатa**: любое двойное/несанкционированное списание; неотработанный отзыв согласия; превышение лага просроченных списаний; нарушение error budget доступности подписок.
- **Владелец решения об откате**: дежурная смена по runbook (немедленный stop-new) + solution-архитектор (стратегия для действующих мандатов), эскалация на A3-владельца при массовом инциденте.

## 7. Risks / Trade-offs

- [Внешний протокол подписок не получен] → все протокольные детали `[ТРЕБУЕТ ПРОВЕРКИ]`; контракт адаптера проектируется нормализованно, реализация транспорта — после документации (AD-008).
- [Протокол НСПК может требовать подтверждение плательщика на каждое списание] → это меняет UX и статусную модель; вынесено в решения человека (§8) и открытые вопросы.
- [Вендор транспорта не поддерживает рекуррент] → возможен доп. RFP/смена вендора; влияет на сроки, не на ядро (граница контракта).
- [Гонка отзыва и планового списания] → проверка статуса мандата в транзакции создания списания + метрика окна отзыва + тест гонки.
- [Пики в границах месяца] → планировщик с разбросом запусков (jitter), измерение backlog, load-shedding приоритетами (не теряя плановые попытки).
- [Рост ядра шлюза модулями] → модульные границы, отдельные таблицы, fitness-правила на запрет обхода контура.
- [ПДн согласия] → минимизация (`payerRef`), шифрование в покое, маскирование логов, правовое основание (ИБ/комплаенс, §8).

## 8. Human architecture decisions (deliverable 7)

1. **Модель согласия в протоколе НСПК**: поддерживает ли ОПКЦ «тихое» списание по мандату без подтверждения плательщика на каждый период, и как устроен отзыв. *Почему человек*: внешний вход (документация НСПК), определяет UX и статусную модель; нельзя решить по коду.
2. **Модуль vs отдельный сервис** для мандатов и планировщика (D2). *Почему человек*: влияет на границы команд, владение и релиз-цикл; решение уровня A3.
3. **Вендор транспорта подписок**: поддержка рекуррента текущим/новым вендором; при отсутствии — пересмотр объёма RFP и, возможно, уточнение ADR-007. *Почему человек*: закупки/рынок/договор.
4. **Правовое основание и сроки хранения согласия**, доказательство согласия, порядок уведомления плательщика перед списанием. *Почему человек*: ИБ/комплаенс, 152-ФЗ и правила НСПК.
5. **Коммерческие рамки**: максимальная сумма мандата, допустимая периодичность, лимиты числа списаний. *Почему человек*: бизнес + регламент оператора.
6. **Стратегия для действующих мандатов при откате/инциденте** (§6.2). *Почему человек*: риск/бизнес-решение.
7. **Пилот vs полный запуск**: подключать подписки всем ТСП или пилотной когорте. *Почему человек*: риск-аппетит и готовность продаж.

## 10. Open Questions

- Точный набор полей/таймингов протокола подписок НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` — влияет на контракт адаптера, не на ядро.
- Нужен ли `SUSPENDED` как отдельный статус (по запросу ТСП) или достаточно `REVOKED`/паузы планировщика — определяется протоколом и бизнесом.
- Политика повторной попытки списания внутри периода после терминального `FAILED` (одна попытка за период vs ограниченное число попыток) — влияет на `billingPeriodKey`/`attemptSeq`, но не на инвариант «не более одного успешного списания».
- Обязан ли банк-эквайер уведомлять плательщика перед списанием, или это делает банк плательщика — регуляторный вопрос (§8).
- Синхронный `getMandateReconciliationReport` vs сверка событиями/файлами — решается с вендором (аналогично базовому контракту).
