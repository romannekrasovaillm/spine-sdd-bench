# Proposal

## Why

ТСП (онлайн-кинотеатры, ЖКХ, связь) пришли за **рекуррентными C2B-списаниями по согласию плательщика** (подписки СБП): сейчас каждый платёж требует нового QR и действия клиента, из-за чего подписочные модели (продление подписки, ежемесячный платёж ЖКХ, платежи связи) дороги и плохо конвертируются. Нужно включить приём подписок на **уже принятом** платёжном шлюзе, не ломая разовый C2B-приём и не пересматривая базовые инварианты решения.

## What Changes

- Новый домен **«мандат» (согласие плательщика)** с жизненным циклом `PENDING_CONSENT → ACTIVE → (SUSPENDED | REVOKED | EXPIRED)` и единственным источником истины в БД шлюза (развитие AD-002).
- **Планировщик списаний**: периодический запуск списаний по действующим мандатам; списание оформляется **как обычный платёж** (тот же конечный автомат `PAID → CREDITED → COMPLETED`, то же зачисление только из `PAID`) и не заводит второй системы истины.
- **Идемпотентность списания** с детерминированным ключом `(mandateId, billingPeriodKey)`: повтор срабатывания планировщика или ретрай не даёт двойного списания (развитие AD-003).
- **Отзыв согласия**: событие ОПКЦ об отзыве немедленно останавливает будущие списания; гонка «отзыв ↔ запуск списания» разрешается проверкой статуса мандата в той же транзакции, что и создание списания.
- **Расширение контракта API ТСП** `openapi/tsp-api.yaml` — **только аддитивно** в `/v1`: новые пути `/v1/mandates*`, новые схемы `Mandate*`, новые опциональные поля `Payment.mandateId`/`billingPeriodKey`, новые коды ошибок, новые вебхуки `mandate.*`. Ни одно существующее поле/операция не удаляется и не меняет смысл. **BREAKING-изменений нет.**
- **Расширение внутреннего контракта адаптера ОПКЦ** (additive): методы `registerMandate`, `getMandateStatus`, `cancelMandate`, `createMandateCharge`, `getMandateReconciliationReport`; события `mandate.activated|revoked|expired`, `mandateCharge.*`; нормализация статусов — как в базовом контракте. Протокольные детали НСПК остаются `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **Новые инварианты spine** `AD-009…AD-012` (через дельту `changes/add-sbp-subscriptions/DELTA.md`), новые ADR-008/ADR-009, кандидатные fitness-правила.
- **Non-goals**: смена протокола НСПК вне подписок; C2C/выплаты; диспуты; изменение модели возвратов (возврат списания подписки идёт существующей сагой ADR-005); многоразовые «карточные» рекурренты карт — вне scope СБП.

## Capabilities

### New Capabilities

- `sbp-subscriptions`: согласие плательщика (мандат) и рекуррентные C2B-списания — регистрация и активация мандата, отзыв/приостановка, инициирование списания по периоду, идемпотентность периода, обработка неуспешного списания, нотификации ТСП о событиях подписки, аудит и минимизация ПДн согласия, обратная совместимость API ТСП.

## Impact

- **Контракт API ТСП**: `openapi/tsp-api.yaml` (additive, minor-версия 0.1.0 → 0.2.0), `docs/contracts/tsp-api.md`.
- **Внутренний контракт**: `docs/contracts/opkc-adapter.md` (additive методы/события), scope RFP `docs/rfp/vendor-rfp.md` (расширение).
- **Спайн/правила** (через дельту): `ARCHITECTURE-SPINE.md` (+AD-009…AD-012, уточнение Binds существующих AD), `.arch-handoff/CONSTRAINTS.yaml` (новые fitness-правила).
- **Решения**: `docs/adr/ADR-008-…md`, `docs/adr/ADR-009-…md` (Proposed).
- **NFR**: `docs/nfr.md` (дельта: раздел подписок).
- **Компоненты**: ядро шлюза (модуль мандатов), планировщик списаний (модуль в платёжном контуре), БД шлюза (таблицы мандатов и попыток списания), адаптер ОПКЦ (вендорский, расширение), нотификатор ТСП.
- **Внешние входы**: документация НСПК по подпискам `[ТРЕБУЕТ ПРОВЕРКИ]`; подтверждение поддержки рекуррента вендором транспорта; правовое основание хранения согласия (ИБ/комплаенс).
- **Что НЕ меняется**: AD-001 (изоляция контура), AD-004 (единственный адаптер), AD-005 (зачисление только из `PAID`), AD-006/AD-007 (trust-зоны, НПС/КИИ/ПДн), AD-008 (гибридная стратегия). Существующий путь разового платежа не меняется.
