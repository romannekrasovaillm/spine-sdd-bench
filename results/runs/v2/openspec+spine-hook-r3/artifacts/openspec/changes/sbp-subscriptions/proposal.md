# Proposal

## Why

ТСП (онлайн-кинотеатры, ЖКХ, связь) не могут продавать по подписке: сегодня каждый платёж C2B требует динамического QR и действия клиента в приложении его банка, поэтому регулярные списания вручную ведёт либо клиент, либо сам ТСП в обход банка. Рекуррентные списания по одному согласию плательщика («подписки СБП») — отдельная возможность СБП; без неё банк теряет сегмент регулярного эквайринга, а плательщик не получает защиту, которую даёт согласие, зарегистрированное в СБП.

## What Changes

- **Новое:** согласие плательщика (мандат) — регистрация через ОПКЦ по инициативе ТСП, состояние и пределы (сумма, период, срок), отзыв, аудит.
- **Новое:** подписка ТСП поверх действующего мандата — расписание, автоматическое списание за период, обработка отказов и ретраев.
- **Новое:** уведомления плательщика о списании и отзыве (регуляторный контур) и события ТСП по мандатам/подпискам/списаниям.
- **Расширение:** внутренний контракт адаптера ОПКЦ (операции мандата и списания, новые события) — ядро остаётся контрактно-независимым от транспорта.
- **Расширение:** статусная модель — добавляется машина подписки; списание остаётся *платежом* и проходит существующую машину платежа.
- **Расширение (аддитивное):** контракт API ТСП — новые ресурсы и опциональные поля; существующие платежи C2B, их статусы и события не меняются.
- **Новое:** инварианты AD-009…AD-011 (мандат — источник права на списание; ровно одно списание за период; отзыв и уведомления — обязательный контур).
- **НЕ ломающее:** `Payment.status` не получает новых значений — отказ списания выражается существующим `FAILED` + `errorCode`; ломающих изменений в `/v1` нет.

## Capabilities

### New Capabilities
- `mandates`: согласие плательщика на рекуррентные списания — регистрация и подтверждение через ОПКЦ, состояние, пределы (сумма/период/срок), отзыв, аудит и уведомления плательщика.
- `subscriptions`: подписка ТСП поверх мандата — расписание, идемпотентное списание за период, обработка отказов и ретраев, события и API для ТСП.

### Modified Capabilities
Нет: требования существующего C2B-приёма не меняются. Живая истина решения сегодня живёт в `docs/` (а не в `openspec/specs/`), поэтому изменения существующих артефактов описаны дельтой `changes/sbp-subscriptions/DELTA.md` в секции MODIFIED; новые требования — в спеках этого change.

## Impact

- **API ТСП** (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`): +4 метода (мандаты, подписки, списания), +опциональные поля в `Payment`, +типы вебхуков; версия контракта `0.1.0 → 0.2.0` (draft-серия, аддитивно).
- **Внутренний контракт адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`): +`registerMandate`/`getMandateStatus`/`createDebit`, +события `mandate.*`/`debit.*`.
- **Статусная модель** (`docs/spec/subscriptions.md`): машина подписки + триггер списания в существующей машине платежа.
- **Данные:** новые сущности мандат/подписка/списание; персональные данные плательщика (минимизация, шифрование, маскирование — AD-006/AD-007).
- **Внешний вход:** функционал подписок в протоколе НСПК — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации Портала поддержки НСПК; вендор транспорта обязан поддержать операции (RFP, ADR-007).
- **NFR:** пунктуальность расписания, обработка отзыва, уведомления, окна пиковых списаний — `docs/nfr-subscriptions.md`.
- **НЕ затронуто:** топология и изоляция (AD-001), правило зачисления только из `PAID` (AD-005), граница «ядро ↔ транспорт» (AD-008), trust-зоны (AD-006), RTO/RPO.
