# Модель мандата и рекуррентных списаний — спецификация

- Status: Draft (для ревью на гейте A1′)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, AD-009, ADR-002, ADR-003, ADR-005, `docs/spec/state-machine.md`
- Внешний вход: операции мандата и списания НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` (документация НСПК по договору)

## Проблема

Рекуррентное взимание без участия плательщика невозможно без формализованного согласия (мандата), его лимитов и порядка отзыва. Существующая модель платежа описывает только разовый платёж, инициированный плательщиком через QR, и не отвечает на вопросы: кто и когда вправе инициировать списание, чем ограничена сумма и число списаний, что происходит при отзыве согласия, как гарантируется «одно списание на период». Настоящая спецификация закрывает этот пробел, не меняя модель платежа.

## 1. Границы

Мандат (согласие плательщика) — новый агрегат платёжного контура. Рекуррентное списание — это **платёж**, проходящий уже описанную статусную машину (`docs/spec/state-machine.md`) без изменения её переходов T1–T12. В настоящем документе описано только то, что добавляется: жизненный цикл мандата, расписание, лимиты, идемпотентность списания и связь с существующей статусной машиной.

## 2. Мандат: состояния

| Состояние | Смысл | Списания разрешены |
|---|---|---|
| `CREATED` | мандат зарегистрирован в шлюзе, запрос в ОПКЦ в процессе | нет |
| `PENDING_AUTH` | ОПКЦ принял запрос, ожидается подтверждение плательщика в банке плательщика | нет |
| `ACTIVE` | согласие подтверждено | да, в пределах лимитов |
| `SUSPENDED` | приостановлен (ТСП по API, шлюзом по правилам/антифроду/расхождению сверки) | нет |
| `REVOKED` | отозван плательщиком или закрыт; терминальный | нет, безусловно |
| `EXPIRED` | истёк срок действия; терминальный | нет |
| `REJECTED` | ОПКЦ/банк плательщика отклонил согласие; терминальный | нет |

## 3. Мандат: таблица переходов

| № | From | To | Триггер | Guard | Действие при переходе |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/subscriptions` (новый `mandateId`) | валидный запрос, ТСП активен, лимиты и расписание корректны | запись мандата + outbox «регистрация мандата в ОПКЦ» + аудит |
| M2 | `CREATED` | `PENDING_AUTH` | ответ адаптера: `mandateRef` получен | `mandateRef` непустой | сохранить `mandateRef`, outbox, вебхук `subscription.created` |
| M3 | `CREATED` | `REJECTED` | ошибка регистрации мандата у ОПКЦ | ошибка не транзиентная | `reasonCode`, outbox, вебхук `subscription.rejected` |
| M4 | `PENDING_AUTH` | `ACTIVE` | событие ОПКЦ `mandate.activated` (или подтверждение сверкой) | дедупликация по `eventId`; реквизиты и лимиты совпадают с локальными (иначе — стоп-сигнал) | outbox, аудит, вебхук `subscription.activated` |
| M5 | `PENDING_AUTH` | `REJECTED` | событие ОПКЦ `mandate.rejected` / истёк срок подтверждения | — | `reasonCode`, вебхук `subscription.rejected` |
| M6 | `ACTIVE` | `REVOKED` | отзыв плательщиком (событие ОПКЦ `mandate.revoked`) | — | **немедленный запрет новых списаний**, outbox, аудит, вебхук `subscription.revoked` |
| M7 | `ACTIVE` | `SUSPENDED` | приостановка ТСП (`POST …/revoke` с режимом suspend) или правило антифрода/расхождение сверки | — | запрет новых списаний, outbox, вебхук `subscription.suspended` |
| M8 | `SUSPENDED` | `ACTIVE` | возобновление ТСП | мандат действителен у ОПКЦ | outbox, вебхук `subscription.activated` |
| M9 | `SUSPENDED` | `REVOKED` | отзыв плательщиком | — | как M6 |
| M10 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | плановый срок действия мандата истёк | — | outbox, вебхук `subscription.expired` |
| M11 | `ACTIVE` | `EXPIRED`/`REVOKED` | сигнал сверки: у ОПКЦ согласие недействительно | — | **консервативно**: запрет списаний, алерт, эскалация |

Терминальные состояния: `REVOKED`, `EXPIRED`, `REJECTED`. Повторные триггеры идемпотентны (дедупликация по `eventId`, AD-003).

## 4. Расписание и лимиты

Атрибуты расписания: периодичность (например, месяц/неделя/день), день/время, дата начала, дата окончания, число списаний (если задано).

Атрибуты лимитов:

| Лимит | Смысл | Проверка |
|---|---|---|
| Разовая сумма | максимум одного списания | при инициации списания |
| Сумма за период | максимум за период расписания | при инициации; учёт атомарно |
| Совокупный лимит | максимум за весь срок мандата | при инициации; учёт атомарно |
| Число списаний | максимум списаний за срок | при инициации; учёт атомарно |
| Срок действия | дата окончания мандата | до инициации |

Правила:

- Лимит нарушен → списание **не инициируется**, вызов ОПКЦ и АБС не выполняется, ТСП уведомляется (`charge.failed` / ошибка API).
- Учёт израсходованных лимитов изменяется **в одной транзакции** с переходом платежа-списания, чтобы конкурирующие списания одного периода не превысили лимит (AD-002, AD-009).
- Плановое время, пропущенное из-за недоступности (ОПКЦ/АБС), добивается по персистентному расписанию; пропуск периода без явного статуса отказа не допускается (NFR `docs/nfr.md` §7).

## 5. Рекуррентное списание: связь со статусной машиной платежа

Списание создаёт обычный платёж со следующими отличиями от разового:

| Аспект | Разовый C2B (v0.1) | Рекуррентное списание (v0.2) |
|---|---|---|
| Триггер | `POST /v1/payments` от ТСП | планировщик по расписанию мандата |
| Ключ идемпотентности | `Idempotency-Key` | `chargeId` = детерминированная функция от (`mandateId`, период) |
| Предусловие | ТСП активен | мандат `ACTIVE` и лимиты не превышены |
| Состояния | `CREATED → QR_ISSUED → PAID → CREDITED → COMPLETED` | те же состояния, кроме `QR_ISSUED` (QR не выпускается; `CREATED → PAID` по подтверждению ОПКЦ) |
| Зачисление | только из `PAID` (AD-005) | **то же правило**, тот же код |
| Поле платежа | — | `mandateId`, `initiationType = recurring` |

Состояние `QR_ISSUED` для рекуррентного списания недостижимо; этот факт — часть fitness-проверки AD-009. Остальные запрещённые переходы и терминальные состояния — как в `docs/spec/state-machine.md` §3.

## 6. Идемпотентность

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/subscriptions` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| Инициация списания планировщиком | `chargeId` = f(`mandateId`, период) | второго списания и второго зачисления нет |
| Событие ОПКЦ `mandate.activated`/`revoked` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Подтверждение АБС по списанию | `paymentId` | повтор не создаёт вторую проводку |
| Отзыв через API ТСП | `Idempotency-Key` | повтор возвращает текущее состояние |

## 7. Отзыв мандата и списания «в полёте»

- Отзыв переводит мандат в `REVOKED` немедленно (та же транзакция: состояние + outbox + аудит) и запрещает новые списания в пределах целевого времени stop-new (NFR §7).
- Для списания, инициированного до отзыва, но не завершённого, применяется утверждённая человеком политика (`design.md` §3.5, §7): базовый вариант — довести подтверждённое НСПК списание до конца, новые не начинать; спорные случаи — возврат по саге (ADR-005).
- Расхождение «у нас `ACTIVE`, у ОПКЦ отозван» — стоп-сигнал: мандат переводится в `SUSPENDED`/`REVOKED`, алерт, эскалация.

## 8. Сверка

- К существующей сверке платежей (ежечасной с НСПК, суточной с АБС) добавляется сверка мандатов и списаний: статусы мандатов, израсходованные лимиты, список списаний за период.
- «У ОПКЦ списание есть, у нас нет» → дозапрос, обработка как нотификация.
- «У нас списание есть, у ОПКЦ нет» → стоп-сигнал, эскалация, зачисление не выполняется.
- Открытые мандаты и незавершённые списания всегда видны в отчёте незавершённых операций.

## 9. Аудит и ПДн

- Каждое изменение состояния мандата и каждое списание — в неизменяемом аудит-логе (AD-007).
- Идентификатор плательщика хранится в минимизированном/маскированном виде; доказательство согласия — по правилам, утверждаемым юридической службой и ИБ; данные мандата шифруются в покое, маскируются в логах; срок хранения определён.

## 10. Согласованность с API ТСП

Наружу (TSP API §8) выставляются состояния мандата `CREATED`, `PENDING_AUTH`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`, `REJECTED` и состояния списания, соответствующие статусам платежа. Внутренние подсостояния (учёт лимитов, ретраи планировщика) наружу не выставляются.

## Критерии приёмки

- [ ] Списание недостижимо без мандата в состоянии `ACTIVE` и вне его лимитов (AD-009) — проверяется fitness-тестом.
- [ ] Повторный запуск планировщика и повторная доставка события ОПКЦ по одному `chargeId` не создают второго списания (AD-003).
- [ ] Зачисление по списанию возможно только из `PAID` (AD-005).
- [ ] После отзыва мандата новые списания не инициируются в пределах целевого времени stop-new (`docs/nfr.md` §7).
- [ ] Каждое изменение состояния мандата и каждое списание присутствуют в неизменяемом аудит-логе (AD-007).
- [ ] Переходы T1–T12 `docs/spec/state-machine.md` не изменены.

## Риски

| Риск | Митигация |
|---|---|
| Двойное взимание при ретраях | идемпотентность `chargeId` + fitness-тест |
| Взимание после отзыва | приоритетный перевод в `REVOKED`, stop-new, сверка |
| Гонка двух списаний одного периода | атомарный учёт лимитов в транзакции перехода (AD-002) |
| Расхождение статуса мандата с ОПКЦ | ежечасная сверка; консервативная трактовка в пользу плательщика |
| Протокол НСПК отличается от предположений | раздел помечен `[ТРЕБУЕТ ПРОВЕРКИ]`; реализация транспорта — после документации (AD-008) |
