# ADR-010. Расширение контрактов: аддитивный API ТСП и контракт адаптера ОПКЦ для согласий

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур)
- Модель-автор: qwen
- Related: ADR-003, ADR-004, ADR-007, ADR-008, AD-004, AD-008

## Context

Для подписок нужны новые операции на двух стыках: **API ТСП** (создание/чтение/отзыв согласия, инициация/чтение списания) и **внутренний контракт ядро↔адаптер ОПКЦ** (регистрация/отмена согласия, инициация списания, опрос статуса, события жизненного цикла). Действующее правило совместимости (`docs/contracts/tsp-api.md` §6): ломающие изменения — только в `/v2` с поддержкой обеих версий ≥ 6 мес.; добавление опциональных полей совместимо и новой версии не требует. Действующая версия контракта — `0.1.0` (A1-draft); расширение подписок выпускается аддитивно как `0.2.0` в пределах `/v1`. Контракт адаптера ОПКЦ — единственная зависимость ядра от транспорта (AD-008/ADR-007) и основа RFP.

## Decision

1. API ТСП расширяется **аддитивно в пределах `/v1`** (версия `0.2.0`): новые ресурсы `/v1/subscriptions...`, новые схемы (`Subscription*`, `Charge*`, `Problem`) и новые коды ошибок новых методов (`SUBSCRIPTION_NOT_ACTIVE`, `CHARGE_NOT_ALLOWED`, `CHARGE_LIMIT_EXCEEDED`); существующие пути, схемы и коды ошибок не изменяются.
2. Контракт адаптера ОПКЦ расширяется операциями согласий (`createMandate`/`cancelMandate`/`getMandateStatus`), списаний (`createCharge`/`getChargeStatus`/`cancelCharge`) и событиями жизненного цикла; протокол НСПК по-прежнему знает только адаптер (AD-004).
3. Новые типы вебхуков (`subscription.*`, `charge.*`) приходят на тот же `webhookUrl`; контракт фиксирует, что потребитель обязан игнорировать неизвестные типы событий и дедуплицировать по `eventId`.
4. Расширение объёма RFP/контракта вендора транспорта — предмет человеческого решения A3 (объём, стоимость, сроки).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| A. Новая версия `/v2` для подписок | «чистая» граница | обязательная поддержка двух версий ≥ 6 мес., миграция ТСП, удорожание | ломающих изменений нет — `/v2` избыточна |
| B. Отдельный сервис со своим API подписок | изоляция | второй источник истины и распределённая согласованность | противоречит ADR-008 |
| C. Изменить существующие схемы `Payment` (добавить поля рекуррентности) | «всё в одном ресурсе» | расширяет смысл принятого ресурса и риск для существующих потребителей | выбрана аддитивность без изменения `Payment`; связь — через `Charge.paymentId` |
| **D. Аддитивное расширение `/v1` + расширение контракта адаптера (выбрано)** | совместимость, минимум миграций, следует правилам §6 | ресурсов становится больше | — |

## Consequences

### Positive

- Существующие ТСП не меняют интеграцию — нулевая миграция потребителей.
- Расширение контракта адаптера сохраняет контрактную независимость ядра от транспорта.
- Новые вебхуки не ломают существующих потребителей при соблюдении правила «игнорировать неизвестные типы».

### Negative

- Увеличивается число ресурсов и схем в `/v1`.
- Требование «игнорировать неизвестные типы событий» опирается на дисциплину потребителя; наивные потребители могут сломаться — это фиксируется в критериях приёмки.
- Расширение RFP усложняет и удлиняет закупку транспорта.

## Reversibility

**reversible.** Новые ресурсы можно выключить фиче-флагом; контракт адаптера версионируется и расширяется без ломающего изменения.

Условие пересмотра (expiry): получение протокола НСПК — если операции согласий нормализуются иначе, контракт адаптера уточняется (новая версия контракта, ADR-010 не отменяется).
