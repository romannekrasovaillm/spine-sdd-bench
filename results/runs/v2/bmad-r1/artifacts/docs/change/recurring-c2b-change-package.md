## 1. Оценка значимости изменения и маршрут

### 1.1 Что меняется по существу

Новый доменный объект — **мандат плательщика (согласие)** — и новый способ инициации платежа: **рекуррентное списание без QR, инициируемое ТСП** (merchant-initiated) в рамках действующего согласия. Это не косметика: появляется финансовое действие без плательщика онлайн, а значит — новый класс ошибок (списание без согласия, сверх лимита, дубль), новое требование НСПК и новый объект сверки.

### 1.2 Оценка значимости (Architecture Significance Score)

Оценка — формальным инструментом репозитория, 15 канонических триггеров (`arch control score`):

```
arch control score --trigger api_contract_change=true --trigger data_contract_change=true \
  --trigger consistency_model_change=true --trigger significant_nfr=true --trigger financial_impact=true
# → Score: 5 (api_contract_change, consistency_model_change, data_contract_change, financial_impact,
#   significant_nfr) → маршрут Critical
```

`arch control score --from-diff` механически подтверждает `api_contract_change` (изменён/добавлен контракт в каталоге контрактов). Порог маршрута: 0–1 → Fast, 2–4 → Standard, ≥ 5 → Critical.

| Триггер | Значение | Почему |
|---|---|---|
| `api_contract_change` | **true** | API ТСП v0.1→v0.2 и контракт адаптера ОПКЦ расширяются |
| `data_contract_change` | **true** | новый агрегат «мандат» (состояния, лимиты, срок, согласие) |
| `consistency_model_change` | **true** | новый автомат состояний (мандат) + модель согласованности дебета с зачислением |
| `significant_nfr` | **true** | новые измеримые NFR (латентности, корректностные инварианты, throughput биллинговых окон) |
| `financial_impact` | **true** | финансовое действие без плательщика онлайн; риск списания без согласия |
| `new_component` | false | новых развёртываемых компонентов нет — агрегат внутри существующего шлюза |
| `new_datastore` | false | та же БД шлюза (новая таблица) |
| `new_vendor` | false | вендор тот же; расширяется только scope RFP (gate G8) |
| `domain_ownership_change` | false | домен платежей расширяется, владение не меняется |
| `cross_domain_integration` | false | новых внешних систем нет (тот же ОПКЦ) |
| `security_boundary_change`, `trust_zone_change` | false | trust-зоны и границы доверия не меняются (ADR-006) |
| `rto_rpo_targets` | false | целевые RTO/RPO контура не меняются (переиспользуются) |
| `irreversible_migration` | false | мандат — новый объект, обратной миграции данных нет |
| `criticality_or_exception` | false | критичность контура уже учтена исходным решением |

**Итог: 5/15 → маршрут Critical** (полное Solutioning + ADR + архитектурный гейт + дельта-протокол).

### 1.3 Маршрут (глубина проектирования)

| Решение | Обоснование |
|---|---|
| **Полное архитектурное решение — ADR-008** (альтернативы, последствия, обратимость) | Затрагивает финансовый инвариант (`AD-005`) и внешний протокол; цена ошибки — финансовый/регуляторный инцидент |
| **Поправка spine: +AD-009, +AD-010** через дельту `changes/recurring-c2b/DELTA.md` | Прямые правки спайна запрещены; изменения идут дельтой (`arch delta guard`) |
| **Версионирование контрактов** — API ТСП v0.2 (аддитивно), адаптер ОПКЦ v0.2 | Новые потребители; существующие ломать нельзя |
| **NFR, критерии приёмки, план отката** | Финансовый риск требует негативных тестов и управляемого отката |
| **Пересмотр RFP вендора** — мандаты обязательны (gate G8, POC P9–P10) | AD-008 (spine): транспорт реализуется только вендором и только после контракта/документации НСПК |
| **Гейт: человеческое архитектурное решение** до реализации; транспорт — после AD-008-условий | Необратимость и внешняя зависимость |
| **Handoff-инкремент исполнителям** `.arch-handoff/recurring-c2b/` | Передача в кодовый харнесс по принятой схеме |

**Статус архитектурного гейта репозитория (`arch gate`):**
- `arch gate` (маршрут auto, механически выведенный из диффа) — **PASS**;
- `arch gate --route critical` — **INCOMPLETE**: fitness, delta-guard, анти-ослабление правил, линтер спайна и сенсоры спецификаций — PASS; составляющие `trace_check`, `nfr`, `model_validate` (нужен каталог `model/`) и `evidence_verify` (нужен бандл валидации/репетиции отката) не имеют входа в этом репозитории. Это pre-existing инфраструктурный пробел, не связанный с изменением (см. §7, п. 11).

**Почему не меньший маршрут:** изменение проходит через инвариант «зачисление только по подтверждённому статусу» и создаёт финансовые действия без участия плательщика. Это исключает «мелкое» изменение: минимально необходимы решение, инварианты, контракты, негативные критерии приёмки и откат.

## 2. Влияние на принятую архитектуру

### 2.1 Инварианты spine: затрагивание и изменение

| AD | Затронут | Что происходит | Rule меняется |
|---|---|---|---|
| AD-001 Изоляция платёжного контура | Косвенно | Мандат и дебеты живут в БД шлюза; вызовы АБС/ОПКЦ — по-прежнему только через адаптеры | Нет |
| AD-002 Единый источник истины, атомарные переходы | Да | Статусные переходы мандата тоже обязаны быть атомарными (`статус + outbox + аудит`); фиксируется в AD-009 | Нет (распространяется) |
| AD-003 Идемпотентность финансовых операций | Да | Новые ключи идемпотентности: создание мандата, списание, отзыв; расход лимита не двоится | Нет (распространяется) |
| AD-004 Единственный адаптер ОПКЦ | Да | Контракт адаптера расширяется мандатными операциями; единственность сохраняется | Нет |
| AD-005 Зачисление только из подтверждённого статуса | Да, **критично** | Дебет моделируется платём в той же СМ; подтверждение дебета приходит в `PAID` → инвариант сохраняется буквально. Дополнительно закрепляется в AD-010 | **Нет** |
| AD-006 Trust-зоны и сегментация | Косвенно | Новых зон нет; растёт объём ПДн (согласие) → остаётся требование минимизации | Нет |
| AD-007 НПС/КИИ/ПДн | Да | Согласие и его доказательство — новый объект аудита; требование НСПК по рекуррентным списаниям | Нет |
| AD-008 Стратегия — гибрид [ADOPTED] | Да | Мандатный протокол — внутри вендорского адаптера; ядро контрактно-независимо. Расширяет RFP | Нет |

**Новые инварианты:** AD-009 (списание только по действующему мандату и в пределах лимитов), AD-010 (дебет — платёж в единой СМ; зачисление только из подтверждённого `PAID`).

### 2.2 Что меняется

1. **Данные:** новый агрегат «мандат» (состояния, лимиты, срок, доказательство согласия) в БД шлюза.
2. **Статусная модель:** второй автомат (мандат: M1–M9) + новые переходы платежа T13–T15; `QR_ISSUED` для мандатного платежа недостижим.
3. **API ТСП:** новые пути `/v1/mandates*`, новые опциональные поля и схемы; версия 0.2 (аддитивно).
4. **Контракт адаптера ОПКЦ:** мандатные методы/события; обязательный критерий RFP.
5. **NFR:** латентности мандатных операций, корректностные инварианты (0 списаний без согласия/сверх лимитов/дублей), сверка мандатов, аудит согласия.
6. **Сверка и аудит:** мандаты — новый объект сверки с НСПК; согласие — новый объект неизменяемого аудита.
7. **RFP вендора:** gate G8, POC P9–P10, расширенные методы/события.

### 2.3 Что НЕ меняется

- Топология (выделенный шлюз + транзакционный outbox), trust-зоны и сегментация.
- Статусная машина платежа и переходы T1–T12; семантика `PAID`, `CREDITED`, `COMPLETED`.
- Правило «зачисление только из `PAID`» (AD-005) и возвраты-сага (ADR-005).
- Идемпотентность по `eventId` для нотификаций; сверка с НСПК/АБС как механизм гарантий.
- Стратегия реализации (AD-008 [ADOPTED]): ядро — собственная разработка, транспорт — вендорский.
- Существующий QR-контракт `/v1/payments*`, обязательные поля и перечень значений `Payment.status`.

### 2.4 Запреты (что нельзя менять в рамках этого изменения)

- Нельзя вводить второй автомат состояний для денег и второй источник истины для зачисления.
- Нельзя ослаблять AD-005 или переопределять `PAID` иначе как «подтверждённый статус».
- Нельзя выполнять списание без мандата `ACTIVE` или вне его лимитов — в том числе «в обход» на стороне ТСП.
- Нельзя ломать контракт v0.1 (удалять/делать обязательными существующие поля, менять значения `Payment.status`).
- Нельзя начинать реализацию транспорта ОПКЦ до условий AD-008 (контракт вендора + документация НСПК).

### 2.5 Согласованность с принятыми решениями

Проверено: изменение **не противоречит** ни одному ADR-001..007 и ни одному AD-001..AD-008. Ключевая проверка — AD-005: рекуррентный дебет подтверждается в `PAID`, зачисление возможно только из него; QR-сценарий не изменяется. Расхождений, требующих остановки и эскалации, нет.

## 3. Архитектурное решение (ADR-008) — сводка

Полный текст — `docs/adr/ADR-008-recurring-c2b-mandate.md`. Существо:

- **Мандат плательщика — first-class агрегат** в БД шлюза, со своей статусной машиной и лимитами (`maxAmountPerDebit`, `maxTotalAmount` за период, `maxDebitsPerPeriod`, `validUntil`).
- **Дебет — платёж в существующей СМ**: `CREATED → PAID → CREDITED → COMPLETED`, без `QR_ISSUED`; зачисление только из `PAID`.
- **Инициатор списания — ТСП** (`POST /v1/mandates/{mandateId}/payments`); расписание биллинга — у ТСП.
- **Guard-проверки до вызова ОПКЦ**, в одной транзакции с учётом расхода лимита; отзыв немедленно запрещает новые списания.
- **Отзыв/приостановка идемпотентны и приоритетны**; отзыв плательщиком через НСПК переопределяет локальное состояние.
- **Граница транспорта не двигается**: протокол НСПК — только в адаптере; контракт адаптера расширяется.

### 3.1 Рассмотренные альтернативы

| Альтернатива | Вердикт |
|---|---|
| Мандат как first-class агрегат + дебет как платёж | **Выбрана** |
| Мандат как поле платежа (без своей жизни) | Отклонена: нет атомарной проверки согласия/лимитов, согласие не аудируется |
| Отдельный микросервис подписок со своей БД | Отклонена: второй источник истины, распределённые транзакции, дублирование outbox/сверки (нарушает AD-001/AD-002) |
| Согласие только у ТСП, шлюз stateless | Отклонена: нет проверяемого банком согласия и аудита (нарушает AD-007) |
| Merchant-initiated без согласия | Отклонена: недопустимо регуляторно |
| Планировщик биллинга на стороне шлюза | Отложена (Deferred): расширяет scope до биллинговой системы; добавляется позже без смены контракта |

### 3.2 Последствия (кратко)

- **Плюсы:** проверяемое, аудируемое и отзываемое согласие; зачисление невозможно без подтверждённого дебета; максимальное переиспользование принятой архитектуры; аддитивный контракт.
- **Минусы:** новый агрегат и второй автомат состояний (объём тестов); дополнительная регуляторная нагрузка (ПДн/согласие); зависимость от поддержки мандатов НСПК и вендором; новые объекты сверки.
- **Ключевые риски:** НСПК может не поддерживать MIT-списания без подтверждения в каждом списании; гонка «отзыв ∥ списание»; дубль списания при ретрае; дрейф лимитов. Митигации — в ADR-008 (раздел Risks) и в критериях приёмки (§6).

### 3.3 Обратимость

**`costly`, но управляемая.** До включения откат = не включать. После включения фиче-флаг отключает приём новых мандатов/списаний, не затрагивая QR-поток и уже открытые мандаты (обработка/отзыв/сверка продолжаются); данные обратной миграции не требуют. Полный отказ от мандатной модели после боевого использования — costly, но границы контракта (AD-008) и аддитивность API это допускают.

## 5. Измеримые NFR для нового функционала

Полный набор — `docs/nfr.md` §7. Ключевое (baseline; финал — с бизнесом и НСПК):

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (проверяемые; включая негативные и гонки)

| # | Сценарий | Ожидаемый результат | Тип |
|---|---|---|---|
| A1 | Счастливый путь: мандат → согласие (`ACTIVE`) → списание → `PAID` → `CREDITED` → `COMPLETED` → вебхук | сквозной сценарий на моках проходит | позитивный |
| A2 | Списание при мандате `PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`EXPIRED` | `422`, вызова ОПКЦ нет, финансового действия нет | негативный |
| A3 | Списание сверх `maxAmountPerDebit` / `maxTotalAmount` / `maxDebitsPerPeriod` | `422`, лимит не израсходован | негативный |
| A4 | Повтор `POST …/payments` с тем же `Idempotency-Key` | тот же `paymentId`, второе списание и второй расход лимита отсутствуют | негативный |
| A5 | Повтор события дебета (`eventId`) / повтор `debit.confirmed` | состояние не меняется, второго зачисления нет | негативный |
| A6 | Повторный `revoke` / отзыв уже отозванного мандата | текущее состояние, не ошибка | негативный |
| A7 | Гонка «отзыв ∥ списание» | после фиксации `REVOKED` нового списания нет; состояние согласовано | гонка |
| A8 | Отказ банка плательщика по дебету | платёж `FAILED`, `errorCode: DEBIT_DECLINED`, вебхук `payment.failed`, зачисления нет | негативный |
| A9 | Атомарность перехода мандата (сбой между статусом и outbox) | частичного состояния нет; fitness-тест «статус + outbox + аудит в одной транзакции» | fitness |
| A10 | Зачисление по мандатному платежу из `CREATED` | недостижимо (fitness AD-005/AD-010) | fitness |
| A11 | Регресс QR-потока + contract-compat test v0.1→v0.2 | QR-сценарии без изменений; диф контракта без breaking changes | регресс |

### 6.2 План отката

- **До боевого включения:** откат = не включать. Всё изменение обратимо (ADR-008 `costly`), мандат — новый объект, миграции данных нет.
- **Фиче-флаг:** `recurring_c2b` (глобально и по ТСП). Выключение → приём новых мандатов и новых списаний останавливается; существующий QR-поток не затронут.
- **После включения (частичный откат):** «stop-new» — запрет создания мандатов и инициации списаний; обработка уже открытых мандатов/операций, отзывы, вебхуки и сверка продолжаются; при необходимости — массовый отзыв мандатов по runbook (с уведомлением ТСП).
- **Сигналы-триггеры отката:** списание без действующего согласия; двойное списание/зачисление; расхождение статусов мандатов с НСПК выше порога; провал тестовых испытаний НСПК по рекуррентным сценариям; аномальный рост отказов дебетов; предписание ИБ/комплаенс.
- **Владелец решения об откате:** человеческий архитектор совместно с дежурной сменой (SRE) и ИБ; ручные операции — 4-eyes (ADR-006).
- **Критерий успешного отката:** новые списания прекращены ≤ 15 мин; ни одна открытая операция не потеряна; сверка с АБС/НСПК без расхождений; QR-поток работает штатно.
- **RTO:** ≤ 1 ч в терминах восстановления обработки (соответствует NFR §3).

## 7. Что остаётся на решение человека-архитектора

Агент не принимает эти решения: они требуют бизнес-мандата, регуляторной позиции или внешнего входа.

1. **Подтверждение значимости/маршрута** — механика даёт 5/15 → Critical (§1.2); подтвердить состав триггеров (в частности, что `new_component`/`criticality_or_exception` остаются false) и принять маршрут Critical.
2. **Модель мандата по НСПК** — какой протокол/формат рекуррентных списаний доступен банку-эквайеру (собственный формат подписки vs orchestration поверх разовых списаний); зависит от документации НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`. От этого зависит объём логики лимитов/дедупликации в ядре.
3. **Подтверждение выбора «ТСП инициирует списание, расписание — у ТСП»** vs планировщик на стороне шлюза (Deferred в ADR-008): влияет на продукт и ответственность за пропущенные периоды.
4. **Семантика переиспользования `PAID`** для подтверждения дебета — если архитектурный комитет предпочтёт отдельное состояние «подтверждённый дебет», это правка AD-010 и ADR-002 (дороже, но явнее).
5. **Модель лимитов и периодов** — достаточность `maxAmountPerDebit`/`maxTotalAmount`/`maxDebitsPerPeriod`/`period`/`validUntil`; нужны ли дневные окна и уведомления плательщику перед списанием.
6. **Регуляторика и ПДн** — правовое основание и срок хранения доказательства согласия, требования к уведомлению плательщика; позиция НСПК/ЦБ по рекуррентным C2B.
7. **RFP: сделать поддержку мандатов обязательным критерием (G8)** и учесть в POC/стоимости; решение о влиянии на сроки закупки.
8. **Гейт AD-008:** транспорт рекуррентных списаний не реализуется до контракта с вендором и документации НСПК — подтвердить, что это окно соблюдено.
9. **Объём первой волны** — все ТСП или пилот с ограниченным набором мерчантов/лимитами.
10. **Запуск реализации** — ратификация ADR-008 (перевод в Accepted) и снятие статуса «Proposed» с AD-009/AD-010.
11. **Инфраструктура критического гейта** — `arch gate --route critical` даёт INCOMPLETE из-за отсутствия каталога `model/` и бандла evidence (валидация/репетиция отката); это pre-existing пробел репозитория. Решение: завести `model/` и бандл evidence на этапе реализации (A4) либо зафиксировать явное принятие риска.
