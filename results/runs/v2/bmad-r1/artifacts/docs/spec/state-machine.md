# Статусная машина платежа — спецификация переходов

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002, ADR-005, ADR-008, AD-002, AD-003, AD-005, AD-009, AD-010

Единый источник истины состояния платежа — БД шлюза (ADR-002). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003).

## Проблема

Платёж C2B проходит через три системы (шлюз → ОПКЦ → банк плательщика → АБС), и канал к НСПК не даёт доставку «ровно один раз». Без единой канонической таблицы переходов независимые исполнители расходятся в трактовке состояний: когда допустимо зачисление, какие состояния терминальны, как обрабатывать повторные и запоздавшие триггеры. Расхождение здесь — не дефект UX, а финансовый инцидент (двойное зачисление или потерянный платёж). Настоящая спецификация фиксирует переходы платежа и мандата как единый источник истины: из какого состояния возможно финансовое действие и как повтор триггера не меняет завершённое состояние.

## 1. Состояния

### Финансовые (видны ТСП в API)

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Платёж зарегистрирован в шлюзе, запрос к ОПКЦ в процессе | да |
| `QR_ISSUED` | QR/ссылка получена от ОПКЦ, ожидается оплата | да |
| `PAID` | **Подтверждённый НСПК статус** оплаты (нотификация или сверка) | да |
| `CREDITED` | Зачисление в АБС выполнено (получен `absDocId`) | да (как `creditingStatus`) |
| `COMPLETED` | Доведено до ТСП (вебхук доставлен/в очереди) | да |
| `FAILED` | Регистрация QR не удалась / платёж отклонён НСПК | да |
| `EXPIRED` | TTL истёк, оплата не наступила | да |
| `REFUNDED` | **Полный** возврат завершён | да |

### Технические (внутренние, наружу не выставляются)

| Состояние | Смысл |
|---|---|
| `ABS_PENDING` | Зачисление в АБС инициировано, ждём подтверждения (ретраи) |
| `NOTIFY_PENDING` | Вебхук ТСП поставлен в очередь (доставка — outbox/нотификатор) |

## 2. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| T1 | — | `CREATED` | `POST /v1/payments` (новый `paymentId`) | валидный запрос, ТСП активен | запись платежа + outbox-событие «регистрация в ОПКЦ» |
| T2 | `CREATED` | `QR_ISSUED` | ответ адаптера ОПКЦ: `qrId` получен | `qrId` непустой | сохранить `qrId/qrUrl`, outbox-нотификация «создан» |
| T3 | `CREATED` | `FAILED` | ошибка регистрации в ОПКЦ (исчерпаны ретраи/DLQ) | ошибка не транзиентная | `errorCode`, outbox, вебхук `payment.failed` |
| T4 | `QR_ISSUED` | `PAID` | нотификация НСПК `PAID` (или подтверждение сверкой) | **сумма и получатель совпадают** (иначе → T7) | outbox-событие «зачисление в АБС» |
| T5 | `QR_ISSUED` | `EXPIRED` | таймер TTL | `PAID` не наступил | закрытие/отмена в ОПКЦ (по протоколу), вебхук `payment.expired` |
| T6 | `QR_ISSUED` | `FAILED` | нотификация НСПК об отклонении | — | `errorCode`, вебхук `payment.failed` |
| T7 | `QR_ISSUED` | `FAILED` | расхождение суммы/получателя в нотификации | платёж ещё не `PAID` | **зачисление запрещено** (AD-005), алерт + runbook |
| T8 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`) | вызов АБС идемпотентен по `paymentId` | сохранить `absDocId`, outbox-событие «доставка ТСП» |
| T9 | `PAID` | (остаётся `PAID`) | АБС недоступна / ретраи | — | подсостояние `ABS_PENDING`, ретраи, сверка; **финансовый статус не меняется** |
| T10 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен (или поставлен в очередь `NOTIFY_PENDING`) | — | outbox, аудит; вебхук `payment.completed` |
| T11 | `COMPLETED` | `REFUNDED` | сага возврата завершена (АБС списала + НСПК подтвердила) | **полный** возврат, платёж был зачислен | outbox, вебхук `refund.completed` |
| T12 | `COMPLETED` | (остаётся `COMPLETED`) | **частичный** возврат завершён | сумма возврата < суммы платежа | запись в `refunds[]`, вебхук `refund.completed` |

## 3. Запрещённые переходы (инварианты)

- **Зачисление в АБС невозможно из любого состояния, кроме `PAID`** (AD-005). Из `CREATED`/`QR_ISSUED` — недостижимо; проверяется fitness-тестом.
- `FAILED`/`EXPIRED`/`REFUNDED` — терминальные: из них переходов нет (повторные триггеры идемпотентны, AD-003).
- `REFUNDED` достижим **только** из `COMPLETED` (только после зачисления).
- Сумма и реквизиты платежа иммутабельны после `QR_ISSUED` (T2).
- `PAID` не может «откатиться» в `QR_ISSUED` — подтверждённый НСПК статус необратим; корректировки — только возвратом (сага).

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| API ТСП `POST /payments` | `Idempotency-Key` | возврат того же `paymentId`, состояние не меняется |
| Нотификация НСПК `PAID` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Подтверждение АБС | `paymentId` | повторное подтверждение не создаёт вторую проводку (маппинг `paymentId → absDocId`) |
| Сага возврата | `refundId` | повторная инициация возврата возвращает существующий `refundId` |

## 5. Сверка и восстановление

- Открытые состояния (`QR_ISSUED`, `PAID`, `ABS_PENDING`) — кандидаты для сверки с НСПК и АБС (ADR-004, ADR-005): ежечасная сверка с НСПК, суточная с АБС.
- «У НСПК `PAID`, у нас нет» → дозапрос статуса → T4.
- «У нас `PAID`, у НСПК нет» → стоп-сигнал, эскалация.
- Платёж в `PAID` с недоступной АБС — остаётся `PAID`, виден в отчёте незавершённых операций, зачисление гарантируется сверкой (не «забывается»).

## 6. Согласованность с API ТСП

Маппинг статусов наружу (TSP API §3.3): `CREATED`, `QR_ISSUED`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`, `REFUNDED` — без технических подсостояний (`ABS_PENDING`, `NOTIFY_PENDING` наружу не выставляются; `ABS_PENDING` отражается как `PAID` + поле `creditingStatus`).

# Часть II. Рекуррентные C2B-списания (v0.2, ADR-008)

Часть II расширяет часть I, не изменяя её: переходы T1–T12 и инварианты платежа сохраняются. Добавляются новый агрегат «мандат плательщика» и способ инициации платежа без QR.

## 7. Мандат плательщика: состояния

| Состояние | Смысл | Терминальное |
|---|---|---|
| `CREATED` | Мандат зарегистрирован в шлюзе, регистрация в ОПКЦ в процессе | нет |
| `PENDING_CONSENT` | Ожидается подтверждение плательщика в приложении его банка | нет |
| `ACTIVE` | Согласие получено; списания в пределах лимитов разрешены | нет |
| `SUSPENDED` | Приостановлен (ТСП/банк); новые списания запрещены, возобновление возможно | нет |
| `DECLINED` | Плательщик отказал в согласии | да |
| `REVOKED` | Отозван (плательщиком/ТСП/банком); новые списания запрещены | да |
| `EXPIRED` | Истёк `validUntil` | да |

## 8. Таблица переходов мандата

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен, лимиты валидны | запись мандата + outbox «регистрация мандата в ОПКЦ», аудит согласия |
| M2 | `CREATED` | `PENDING_CONSENT` | ответ адаптера ОПКЦ: регистрация принята | — | outbox-нотификация, ожидание согласия |
| M3 | `PENDING_CONSENT` | `ACTIVE` | подтверждение согласия плательщиком (событие ОПКЦ) | согласие подтверждено | фиксация `consentRef`, `activatedAt`; outbox `mandate.activated`; аудит |
| M4 | `PENDING_CONSENT` | `DECLINED` | отказ плательщика (событие ОПКЦ) | — | терминал, аудит, вебхук `mandate.declined` |
| M5 | `ACTIVE` | `SUSPENDED` | приостановка (ТСП/банк) | — | новые списания запрещены (AD-009), аудит |
| M6 | `SUSPENDED` | `ACTIVE` | возобновление | срок не истёк | списания разрешены, аудит |
| M7 | `ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв ТСП (`POST …/revoke`) или плательщика/банка (событие/оператор) | — | терминал; **немедленный запрет новых списаний**, аудит, вебхук `mandate.revoked` |
| M8 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | таймер `validUntil` | — | терминал, аудит, вебхук `mandate.expired` |
| M9 | `CREATED` | `REVOKED` | ошибка регистрации в ОПКЦ / отзыв до согласия | — | терминал, аудит |

## 9. Рекуррентное списание: переходы в статусной машине платежа

Списание — это платёж части I. Переходы `PAID → CREDITED` (T8) и `CREDITED → COMPLETED` (T10) переиспользуются без изменений; `QR_ISSUED` недостижим.

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| T13 | — | `CREATED` | `POST /v1/mandates/{id}/payments` (новый `paymentId`) | мандат `ACTIVE`; `amount ≤ maxAmountPerDebit`; сумма за период ≤ `maxTotalAmount`; число списаний ≤ `maxDebitsPerPeriod`; `now ≤ validUntil`; валюта совпадает | запись платежа (`initiationType=MANDATE`) + outbox «дебет в ОПКЦ» + учёт расхода лимита; аудит |
| T14 | `CREATED` | `PAID` | подтверждение дебета банком плательщика/НСПК (событие или сверка) | сумма и получатель совпадают | outbox-событие «зачисление в АБС» |
| T15 | `CREATED` | `FAILED` | отказ банка плательщика/НСПК (недостаточно средств, лимит, отзыв) | ошибка не транзиентная | `errorCode` (напр. `DEBIT_DECLINED`), вебхук `payment.failed`, аудит |

## 10. Запрещённые переходы и инварианты (мандат/дебет)

- **Списание невозможно без мандата в состоянии `ACTIVE`** и вне его лимитов (AD-009). Из `PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`DECLINED` — недостижимо; проверяется fitness-тестом.
- **Зачисление по рекуррентному списанию — только из `PAID`** (AD-005, AD-010). Из `CREATED` — недостижимо.
- `QR_ISSUED` для мандатного платежа **недостижим** (QR не создаётся).
- `REVOKED`/`EXPIRED`/`DECLINED` — терминальные: переходов из них нет; повторные триггеры идемпотентны.
- **Гонка «отзыв ∥ списание»:** guard-проверка мандата и создание платежа (расход лимита) выполняются в одной транзакции со сменой статуса мандата; после фиксации `REVOKED` новые списания невозможны.
- **Параметры мандата (лимиты, `validUntil`) иммутабельны после `ACTIVE`;** изменение условий — отзыв старого мандата и регистрация нового (исключает скрытое расширение согласия).
- Отзыв, пришедший от плательщика через НСПК, **приоритетен** над локальным состоянием и переводит мандат в `REVOKED`.

## 11. Идемпотентность (мандат/дебет)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| `POST /v1/mandates/{id}/payments` | `Idempotency-Key` | возврат того же `paymentId`, **второго списания и второго расхода лимита нет** |
| Расход лимита мандата | `paymentId` | повтор не увеличивает счётчик списаний/сумм |
| `POST /v1/mandates/{id}/revoke` | `mandateId` | повтор возвращает текущее состояние, не ошибку |
| События НСПК `mandate.*`/`debit.*` | `eventId` | обработанный `eventId` игнорируется; новый по завершённому переходу — алерт без смены состояния |

## 12. Сверка (мандат/дебет)

- Мандаты — объект сверки с НСПК: статусы и отзывы; целевой регламент — суточная сверка, критические расхождения (`у НСПК REVOKED`, `у нас ACTIVE`) — стоп-сигнал и немедленная приостановка списаний по мандату до выяснения.
- Дебеты — в существующей ежечасной сверке платежей: «у НСПК подтверждён, у нас нет» → дозапрос → T14.
- Расхождение лимитов (шлюз разрешил — НСПК отклонил) — в отчёт незавершённых операций и runbook.

## 13. Согласованность с API ТСП (v0.2)

- Наружу выставляются статусы мандата (`CREATED`, `PENDING_CONSENT`, `ACTIVE`, `SUSPENDED`, `DECLINED`, `REVOKED`, `EXPIRED`) и статусы платежа части I; технических подсостояний нет.
- Мандатный платёж отличается полем `initiationType: MANDATE` и наличием `mandateId`; статусная модель та же, что у QR-платежа.

## Критерии приёмки

- [ ] Зачисление в АБС недостижимо из любого состояния, кроме `PAID` (T4/T14) — fitness-тест.
- [ ] Рекуррентное списание недостижимо без мандата в `ACTIVE` и вне его лимитов (AD-009) — fitness-тест.
- [ ] Для мандатного платежа состояние `QR_ISSUED` недостижимо — тест.
- [ ] Каждый переход — атомарная транзакция «статус + outbox + аудит»; при сбое частичного состояния нет — тест на сбой.
- [ ] Повторные триггеры идемпотентны: тот же `Idempotency-Key`/`eventId` не меняет завершённое состояние — тест.
- [ ] Терминальные состояния (`FAILED`, `EXPIRED`, `REFUNDED`, `DECLINED`, `REVOKED`) не имеют исходящих переходов — тест.
- [ ] Гонка «отзыв ∥ списание» не приводит к списанию после `REVOKED` — тест.
- [ ] Маппинг статусов наружу совпадает с API ТСП (технические подсостояния не выставляются) — contract-тест.

## Риски

- Двойное зачисление при повторе, если атомарность перехода нарушена в коде → блокер-ревью + fitness-тест на каждый переход.
- Гонка «отзыв ∥ списание» → guard мандата и смена статуса в одной транзакции; отдельный тест на гонку.
- Расхождение статусов с НСПК/АБС → ежечасная/суточная сверка и отчёт незавершённых операций.
- «У нас `PAID`, у НСПК нет» → стоп-сигнал и эскалация; зачисление по несуществующему платежу исключено инвариантом AD-005.
- Расширение автомата новыми состояниями без обновления этой спецификации → дрейф модели; изменения — только через ADR/дельту.
