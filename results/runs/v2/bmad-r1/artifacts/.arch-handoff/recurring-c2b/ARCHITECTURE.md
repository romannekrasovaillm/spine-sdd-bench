# Архитектурный контекст инкремента (recurring-c2b)

Собран: 2026-09-28
Источники: `docs/adr/ADR-008-recurring-c2b-mandate.md` (копия — `adr/`), `docs/change/recurring-c2b-change-package.md`, `ARCHITECTURE-SPINE.md`, `docs/spec/state-machine.md` (Часть II), `docs/contracts/tsp-api.md` / `openapi/tsp-api.yaml` v0.2, `docs/contracts/opkc-adapter.md` v0.2, `docs/nfr.md` §7.

## Цель

Добавить рекуррентные C2B-списания по согласию плательщика (подписки СБП), не меняя существующий QR-поток: плательщик один раз даёт согласие (мандат), ТСП инициирует списания без QR. Инкремент к walking skeleton: переиспользовать выделенный шлюз, транзакционный outbox, статусную машину платежа, идемпотентность, сверку и вебхуки. Транспорт НСПК — мок (реальный протокол `[ТРЕБУЕТ ПРОВЕРКИ]`).

## Инварианты (связывающие AD, дословные Rule)

- **AD-001** (изоляция): любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза.
- **AD-002** (единый источник истины): изменение финансового статуса платежа и запись исходящего события (outbox) — в одной локальной транзакции.
- **AD-003** (идемпотентность): повторная доставка любого сообщения не изменяет уже завершённое состояние.
- **AD-004** (единственный адаптер ОПКЦ): протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.
- **AD-005** (зачисление): вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус); из `CREATED`/`QR_ISSUED` зачисление недостижимо.
- **AD-006** (trust-зоны): сеть между зонами — только через межсетевые экраны по белому списку; ключевой материал — в СКЗИ/HSM; доступ операторов — 4-eyes.
- **AD-007** (НПС/КИИ/ПДн): каждый финансовый переход и административное действие — в неизменяемом аудит-логе; каналы к ОПКЦ — на сертифицированных СКЗИ.
- **AD-008** [ADOPTED] (стратегия): ядро шлюза контрактно-независимо от транспорта; реализация транспорта — только после контракта с вендором и документации НСПК.
- **AD-009** (новый): Рекуррентное C2B-списание выполняется только при мандате в состоянии `ACTIVE` и в пределах его лимитов (`maxAmountPerDebit`, `maxTotalAmount` за период, `maxDebitsPerPeriod`, `validUntil`), проверяемых перед вызовом ОПКЦ. Отзыв или приостановка мандата немедленно запрещают новые списания; отзыв, пришедший от плательщика через НСПК, приоритетен. Переходы статуса мандата — атомарные транзакции «статус + outbox + аудит» (AD-002, AD-007).
- **AD-010** (новый): Рекуррентное списание проходит ту же статусную машину (`CREATED → PAID → CREDITED → COMPLETED`, терминальные `FAILED`), состояние `QR_ISSUED` не используется. Зачисление возможно только из `PAID`, где `PAID` — подтверждённый банком плательщика/НСПК дебет (AD-005 не ослабляется). Идемпотентность — по `Idempotency-Key` и `paymentId`.

## Технические решения

- Мандат — first-class агрегат в БД шлюза; состояния `CREATED | PENDING_CONSENT | ACTIVE | SUSPENDED | DECLINED | REVOKED | EXPIRED`; параметры мандата иммутабельны после `ACTIVE` (изменение условий = отзыв + новый мандат).
- Дебет — платёж: переходы T13 (`→CREATED`), T14 (`CREATED→PAID`), T15 (`CREATED→FAILED`); далее T8/T10 без изменений.
- Инициатор списания — ТСП; расписание биллинга хранит ТСП (планировщик шлюза — Deferred).
- Guard-проверки и расход лимита — в одной транзакции с созданием платежа; гонка «отзыв ∥ списание» безопасна.
- Контракт адаптера: `registerMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus`; события `mandate.*`, `debit.confirmed`/`debit.rejected`; идемпотентность по `reference`.

## Изменения контрактов (v0.2, аддитивно)

Новые пути `/v1/mandates*`, новые схемы `Mandate*`/`RecurringPaymentRequest`; в `Payment` — новые опциональные `initiationType`, `mandateId`. `PaymentRequest`, `Payment.required` и перечень значений `Payment.status` **не изменены**. Вебхуки: `mandate.activated|declined|revoked|expired`; дебетовые исходы — `payment.completed`/`payment.failed`. Новые коды ошибок: `MANDATE_NOT_ACTIVE`, `MANDATE_REVOKED`, `MANDATE_EXPIRED`, `AMOUNT_EXCEEDS_MANDATE_LIMIT`, `MANDATE_LIMIT_EXCEEDED`; отказ дебета — `status=FAILED`, `errorCode=DEBIT_DECLINED`.

## Запрещено менять

- Второй автомат состояний для денег / второй источник истины зачисления.
- AD-005 и семантику `PAID` (кроме «подтверждённый статус»); зачисление не из `PAID`.
- Существующий контракт v0.1: удаление/переименование полей, перевод опциональных в обязательные, изменение `Payment.status` enum.
- Вызовы АБС/ОПКЦ вне адаптеров; реализацию транспорта НСПК до условий AD-008.

## Критерии приёмки (проверяемые)

Счастливый путь мандат→согласие→дебет→`COMPLETED`; отказ списания без `ACTIVE`-мандата; отказ сверх лимитов; повтор `Idempotency-Key` → тот же `paymentId` (без второго списания/расхода лимита); повтор события → без второго зачисления; гонка «отзыв ∥ списание»; недостижимость зачисления из `CREATED`; регресс QR-потока; contract-compat test v0.1→v0.2. Полный список — `docs/change/recurring-c2b-change-package.md` §6, NFR — `docs/nfr.md` §7.

## План отката

Фиче-флаг `recurring_c2b` (глобально/по ТСП): выключение останавливает новые мандаты и списания, QR-поток и открытые операции не затронуты; массовый отзыв мандатов — по runbook. Сигналы: списание без согласия, дубль, расхождение статусов мандатов с НСПК, провал испытаний НСПК. Владелец — архитектор + дежурная смена; ручные операции 4-eyes. RTO ≤ 1 ч.
