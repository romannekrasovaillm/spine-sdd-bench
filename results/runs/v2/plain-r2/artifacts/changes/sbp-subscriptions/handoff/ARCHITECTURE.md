# Архитектурный контекст (epic-context): СБП-подписки

**Цель.** Добавить к принятому СБП-шлюзу (C2B-приём) рекуррентные списания по согласию плательщика: плательщик один раз авторизует согласие (мандат), далее шлюз инициирует списания по расписанию без QR и без действия клиента. Изменение — Critical, Proposed; реализация только после A3.

**Стыки (интерфейсы, которые нельзя переизобретать).**
- API ТСП `openapi/tsp-api.yaml` v0.2: `POST /v1/consents`, `GET /v1/consents/{consentId}`, `POST /v1/consents/{consentId}/revoke`, `POST /v1/consents/{consentId}/debits`; платежи/возвраты v0.1 не меняются; `Idempotency-Key` обязателен на POST; суммы — целые копейки; ошибки — RFC 9457 (`CONSENT_NOT_ACTIVE` = 422 и др.).
- Вебхуки ТСП (at-least-once, ретраи, DLQ, HMAC): `consent.activated` / `consent.rejected` / `consent.revoked` / `consent.expired` / `consent.suspended`, плюс существующие `payment.*` / `refund.*`.
- Внутренний контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md` §3.1, §4): `createMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus`; события `mandate.*`, `debit.*`; идемпотентность по `reference`. Протокол НСПК — внутри адаптера; точные поля/тайминги `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Хранилище: БД шлюза — **единственный источник истины** для платежа и согласия; АБС — только через адаптер АБС.

**Связывающие инварианты (Rule — дословно, менять запрещено).**
- AD-002: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции.» Согласие подчиняется той же дисциплине (AD-009).
- AD-003: «Повторная доставка любого сообщения не изменяет уже завершённое состояние.»
- AD-005: «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус).»
- AD-009: «Рекуррентное списание инициируется только при согласии в состоянии `ACTIVE` и идемпотентно по ключу `consentId + billingPeriod`; само списание — платёж в статусной машине ADR-002, и зачисление по нему возможно только из `PAID` (AD-005) — `ACTIVE`-согласие не является основанием зачисления. Отзыв согласия необратим и останавливает новые списания. Согласие — второй источник истины в БД шлюза с атомарными переходами «статус + outbox + аудит» (AD-002).»
- AD-001: любое взаимодействие с АБС и ОПКЦ — только через адаптеры шлюза. AD-004: протокол НСПК знает только адаптер ОПКЦ. AD-008: ядро контрактно-независимо от транспорта. AD-006/AD-007: trust-зоны, ГОСТ/СКЗИ, ПДн, аудит.

**Запрещено менять (вне этой задачи).** Контракт v0.1 (пути/поля/enum платежей и возвратов), семантику `PAID`/зачисления, топологию и trust-зоны, стратегию ADR-007/AD-008, существующие ADR-001..007. Конфликт с любым из них — **остановка и эскалация**, не «тихое» отклонение.

**Ключевые потоки.**
1. Согласие: ТСП `POST /consents` → `PENDING_PAYER` → (подтверждение плательщика по НСПК) → `ACTIVE` (событие `consent.activated`); `revoke` из любого нетерминального → `REVOKED` необратимо.
2. Списание: срок `billingPeriod` (планировщик) или ручной триггер ТСП → guard `ACTIVE` → платёж `CREATED`/`DEBIT_PENDING` → `PAID` (подтверждение НСПК) → зачисление АБС только из `PAID` → `CREDITED` → `COMPLETED` → вебхук.
3. Идемпотентность: повтор тика/запроса не создаёт второе списание; повтор `eventId` игнорируется; отзыв приоритетен, in-flight доводится, корректировка — возвратом.

**Приёмка (на моках).** NFR `docs/nfr.md` §7: дубликаты списаний = 0; списание без `ACTIVE` = 0 (ОПКЦ не вызван); прекращение новых списаний после отзыва ≤ 60 с; инициация по расписанию p95 ≤ 5 мин; АБС недоступна → платёж остаётся `PAID`, сверка дозарабатывает; рестарт планировщика без пропусков/дублей. Негативные сценарии обязательны.

**Откат.** Фиче-флаг `sbp.subscriptions.enabled` (по умолчанию `false`); stop-new (остановка планировщика + отказ `POST /consents`), открытые операции дорабатываются; см. `ROLLBACK.yaml`.
