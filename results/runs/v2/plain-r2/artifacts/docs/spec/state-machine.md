# Статусная машина платежа — спецификация переходов

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002, ADR-005, ADR-008, AD-002, AD-003, AD-005, AD-009

Единый источник истины состояния платежа — БД шлюза (ADR-002). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003). СБП-подписки добавляют вторую машину — согласие (§7–8, ADR-008, AD-009).

## Проблема

Канал к ОПКЦ СБП не даёт доставку «ровно один раз»: нотификации повторяются и опаздывают, ответы приходят после таймаута. Финансовое последствие ошибки — двойное зачисление или потерянный платёж — недопустимо, а регулятор требует доказуемости каждого финансового перехода. Нужна явная модель состояний и переходов, где каждый шаг атомарен, идемпотентен и аудируем; подписки добавляют долгоживущее состояние согласия с теми же гарантиями.

## 1. Состояния

### Финансовые (видны ТСП в API)

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Платёж зарегистрирован в шлюзе, запрос к ОПКЦ в процессе | да |
| `QR_ISSUED` | QR/ссылка получена от ОПКЦ, ожидается оплата | да |
| `PAID` | **Подтверждённый НСПК статус** оплаты (нотификация или сверка) | да |
| `CREDITED` | Зачисление в АБС выполнено (получен `absDocId`) | да (как `creditingStatus`) |
| `COMPLETED` | Доведено до ТСП (вебхук доставлен/в очереди) | да |
| `FAILED` | Регистрация QR не удалась / платёж отклонён НСПК | да |
| `EXPIRED` | TTL истёк, оплата не наступила | да |
| `REFUNDED` | **Полный** возврат завершён | да |

### Технические (внутренние, наружу не выставляются)

| Состояние | Смысл |
|---|---|
| `ABS_PENDING` | Зачисление в АБС инициировано, ждём подтверждения (ретраи) |
| `NOTIFY_PENDING` | Вебхук ТСП поставлен в очередь (доставка — outbox/нотификатор) |

## 2. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| T1 | — | `CREATED` | `POST /v1/payments` (новый `paymentId`) | валидный запрос, ТСП активен | запись платежа + outbox-событие «регистрация в ОПКЦ» |
| T2 | `CREATED` | `QR_ISSUED` | ответ адаптера ОПКЦ: `qrId` получен | `qrId` непустой | сохранить `qrId/qrUrl`, outbox-нотификация «создан» |
| T3 | `CREATED` | `FAILED` | ошибка регистрации в ОПКЦ (исчерпаны ретраи/DLQ) | ошибка не транзиентная | `errorCode`, outbox, вебхук `payment.failed` |
| T4 | `QR_ISSUED` | `PAID` | нотификация НСПК `PAID` (или подтверждение сверкой) | **сумма и получатель совпадают** (иначе → T7) | outbox-событие «зачисление в АБС» |
| T5 | `QR_ISSUED` | `EXPIRED` | таймер TTL | `PAID` не наступил | закрытие/отмена в ОПКЦ (по протоколу), вебхук `payment.expired` |
| T6 | `QR_ISSUED` | `FAILED` | нотификация НСПК об отклонении | — | `errorCode`, вебхук `payment.failed` |
| T7 | `QR_ISSUED` | `FAILED` | расхождение суммы/получателя в нотификации | платёж ещё не `PAID` | **зачисление запрещено** (AD-005), алерт + runbook |
| T8 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`) | вызов АБС идемпотентен по `paymentId` | сохранить `absDocId`, outbox-событие «доставка ТСП» |
| T9 | `PAID` | (остаётся `PAID`) | АБС недоступна / ретраи | — | подсостояние `ABS_PENDING`, ретраи, сверка; **финансовый статус не меняется** |
| T10 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен (или поставлен в очередь `NOTIFY_PENDING`) | — | outbox, аудит; вебхук `payment.completed` |
| T11 | `COMPLETED` | `REFUNDED` | сага возврата завершена (АБС списала + НСПК подтвердила) | **полный** возврат, платёж был зачислен | outbox, вебхук `refund.completed` |
| T12 | `COMPLETED` | (остаётся `COMPLETED`) | **частичный** возврат завершён | сумма возврата < суммы платежа | запись в `refunds[]`, вебхук `refund.completed` |

## 3. Запрещённые переходы (инварианты)

- **Зачисление в АБС невозможно из любого состояния, кроме `PAID`** (AD-005). Из `CREATED`/`QR_ISSUED` — недостижимо; проверяется fitness-тестом.
- `FAILED`/`EXPIRED`/`REFUNDED` — терминальные: из них переходов нет (повторные триггеры идемпотентны, AD-003).
- `REFUNDED` достижим **только** из `COMPLETED` (только после зачисления).
- Сумма и реквизиты платежа иммутабельны после `QR_ISSUED` (T2).
- `PAID` не может «откатиться» в `QR_ISSUED` — подтверждённый НСПК статус необратим; корректировки — только возвратом (сага).

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| API ТСП `POST /payments` | `Idempotency-Key` | возврат того же `paymentId`, состояние не меняется |
| Нотификация НСПК `PAID` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Подтверждение АБС | `paymentId` | повторное подтверждение не создаёт вторую проводку (маппинг `paymentId → absDocId`) |
| Сага возврата | `refundId` | повторная инициация возврата возвращает существующий `refundId` |
| API ТСП `POST /consents` | `Idempotency-Key` | возврат того же `consentId`, состояние согласия не меняется |
| Планировщик списаний | `consentId + billingPeriod` | повторный тик/перезапуск не создаёт второе списание |
| Ручной триггер списания `POST /consents/{id}/debits` | `Idempotency-Key` (+ `consentId + billingPeriod`) | возврат существующего списания (`paymentId`), второго финансового действия нет |
| Отзыв согласия | `consentId` | повторный отзыв идемпотентен, согласие остаётся `REVOKED` |

## 5. Сверка и восстановление

- Открытые состояния (`QR_ISSUED`, `PAID`, `ABS_PENDING`) — кандидаты для сверки с НСПК и АБС (ADR-004, ADR-005): ежечасная сверка с НСПК, суточная с АБС.
- «У НСПК `PAID`, у нас нет» → дозапрос статуса → T4.
- «У нас `PAID`, у НСПК нет» → стоп-сигнал, эскалация.
- Платёж в `PAID` с недоступной АБС — остаётся `PAID`, виден в отчёте незавершённых операций, зачисление гарантируется сверкой (не «забывается»).

## 6. Согласованность с API ТСП

Маппинг статусов наружу (TSP API §3.3): `CREATED`, `QR_ISSUED`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`, `REFUNDED` — без технических подсостояний (`ABS_PENDING`, `NOTIFY_PENDING` наружу не выставляются; `ABS_PENDING` отражается как `PAID` + поле `creditingStatus`).

## 7. Машина согласия (СБП-подписки, ADR-008)

Согласие (мандат) — **второй источник истины** в БД шлюза (AD-009, расширение AD-002). Каждый переход — атомарная транзакция «статус + outbox + аудит»; повторные триггеры идемпотентны (AD-003).

### Состояния согласия

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_PAYER` | Согласие зарегистрировано, ожидает подтверждения плательщика (в приложении его банка) | да |
| `ACTIVE` | Подтверждено плательщиком; единственное основание списаний | да |
| `SUSPENDED` | Приостановлено (лимит, спор, требование банка); новые списания запрещены | да |
| `REVOKED` | Отозвано плательщиком/банком/НСПК; терминальное, новые списания невозможны | да |
| `EXPIRED` | Истёк срок действия согласия; терминальное | да |
| `REJECTED` | Плательщик/НСПК отклонил регистрацию; терминальное | да |

### Переходы согласия

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING_PAYER` | `POST /v1/consents` (новый `consentId`) | ТСП активен, валидные параметры/лимиты | запись согласия + outbox «создание мандата в ОПКЦ» |
| C2 | `PENDING_PAYER` | `ACTIVE` | подтверждение плательщика (нотификация НСПК) | мандат подтверждён | outbox, вебхук `consent.activated` |
| C3 | `PENDING_PAYER` | `REJECTED` | отказ плательщика/НСПК | — | `reasonCode`, вебхук `consent.rejected` |
| C4 | `ACTIVE` | `SUSPENDED` | лимит/спор/требование банка | — | запрет новых списаний, outbox |
| C5 | `SUSPENDED` | `ACTIVE` | снятие ограничения | основание зафиксировано | outbox, вебхук `consent.activated` |
| C6 | `PENDING_PAYER`/`ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв (плательщик, банк плательщика, ТСП, НСПК) | — | **необратимо**, запрет новых списаний, аудит, вебхук `consent.revoked` |
| C7 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | таймер срока согласия | `REVOKED` не наступил | запрет списаний, вебхук `consent.expired` |

### Запрещённые переходы согласия

- `REVOKED`, `EXPIRED`, `REJECTED` — терминальные: переходов из них нет (повторные триггеры идемпотентны).
- Из `REVOKED` **невозврат** в `ACTIVE`; повторное подключение — новое согласие.
- Списание невозможно ни из одного состояния, кроме `ACTIVE` (AD-009).

## 8. Рекуррентное списание как платёж (ADR-008)

Списание не создаёт вторую машину движения денег: это платёж в §1–§2 с дополнительным полем `consentId` и техническим подсостоянием `DEBIT_PENDING` (ожидание подтверждения НСПК по мандату; наружу отражается как `PAID`-ожидание, по аналогии с `ABS_PENDING`).

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| D1 | — | `CREATED` | тик планировщика по `billingPeriod` или `POST /v1/consents/{id}/debits` | согласие `ACTIVE`, лимит не исчерпан, ключ `consentId + billingPeriod` новый | платёж с `consentId`, outbox «списание в ОПКЦ» |
| D2 | `CREATED` | `DEBIT_PENDING` | запрос списания принят ОПКЦ | — | ожидание подтверждения НСПК |
| D3 | `DEBIT_PENDING` | `PAID` | нотификация НСПК о списании (или сверка) | сумма/получатель/согласие совпадают | outbox «зачисление в АБС» (T8 далее) |
| D4 | `DEBIT_PENDING`/`CREATED` | `FAILED` | отказ НСПК (недостаточно средств, отзыв, лимит) | ошибка не транзиентная | `errorCode`, вебхук `payment.failed` |
| D5 | — | отклонение инициации | попытка списания при согласии не `ACTIVE` | — | `CONSENT_NOT_ACTIVE`, вызов ОПКЦ не выполняется, аудит |

- Зачисление по списанию — **только из `PAID`** (AD-005); состояние согласия зачисление не разрешает.
- Отзыв во время in-flight списания: новые инициации прекращаются немедленно; уже подтверждённое НСПК списание доводится, корректировка — только возвратом (сага ADR-005).
- Сверка: согласия и открытые списания — кандидаты (ежечасная с НСПК, суточная с АБС); расхождение «у НСПК списание есть, у нас нет» → дозапрос → D3; «у нас есть, у НСПК нет» — стоп-сигнал.
- Согласие наружу: `PENDING_PAYER`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`, `REJECTED`; технические подсостояния не выставляются.

## Критерии приёмки

- [ ] Каждый переход T1–T12 имеет fitness-тест; зачисление недостижимо из `CREATED`/`QR_ISSUED` (AD-005).
- [ ] Каждый переход согласия C1–C7 и списания D1–D5 имеет тест; состояние согласия — атомарная транзакция (AD-002/AD-009).
- [ ] Признак EARS: When приходит повтор `eventId`, the шлюз shall не менять завершённое состояние (AD-003).
- [ ] Признак EARS: If согласие не в состоянии `ACTIVE`, then the шлюз shall отклонить списание без обращения к ОПКЦ (AD-009).
- [ ] Признак EARS: When приходит отзыв согласия, the шлюз shall прекратить новые списания и перевести согласие в `REVOKED` (AD-009).
- [ ] Негативные сценарии: дубль тика планировщика/ручного триггера; отзыв во время in-flight; рестарт планировщика без пропусков/дублей.

## Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Неполная таблица переходов (пропущенный терминальный/обратный переход) | недоказуемая корректность, дефекты в проде | fitness на каждый переход, ревью против протокола НСПК |
| Расхождение локального согласия и мандата НСПК | списание без подтверждённого мандата | сверка `getMandateStatus`, guard `ACTIVE`, алерт на расхождение |
| Поздние/повторные события при подписках | ложный отказ или двойное списание | дедуп по `eventId`, идемпотентность `consentId + billingPeriod`, сверка |
| Технические подсостояния «протекут» наружу | ломающая совместимость API | маппинг наружу только канонических статусов (§6) |
