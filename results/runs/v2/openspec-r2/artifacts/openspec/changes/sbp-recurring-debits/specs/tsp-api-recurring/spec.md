# tsp-api-recurring

## Purpose

Аддитивное расширение контракта API ТСП (`openapi/tsp-api.yaml`) для согласий и рекуррентных списаний, сохраняющее работоспособность существующих потребителей версии v0.1.

## ADDED Requirements

### Requirement: Аддитивность и обратная совместимость расширения

Расширение контракта SHALL быть аддитивным. Существующие пути, поля, обязательность полей и значения перечислений MUST NOT изменяться, удаляться или переименовываться, а новые значения MUST NOT добавляться в существующие перечисления (включая `Payment.status`).

#### Scenario: Существующий потребитель продолжает работать

- **WHEN** потребитель, использующий только ресурсы и поля версии v0.1, обращается к API после включения расширения
- **THEN** его запросы и ответы не меняются по структуре и семантике, новые поля присутствуют только там, где они опциональны

#### Scenario: Отсутствие новых значений в старых перечислениях

- **WHEN** выполняется ревью расширения контракта
- **THEN** ни одно существующее перечисление (в частности `Payment.status`) не содержит добавленных значений, а новые состояния вынесены в отдельные схемы

### Requirement: Ресурсы согласия в API ТСП

API SHALL предоставлять регистрацию согласия (`POST /v1/mandates`), чтение состояния (`GET /v1/mandates/{mandateId}`) и отзыв (`POST /v1/mandates/{mandateId}/revoke`). Ответы SHALL содержать `mandateId`, состояние, лимиты/период и срок действия, а также средство подтверждения плательщиком при регистрации.

#### Scenario: Чтение состояния согласия

- **WHEN** ТСП запрашивает `GET /v1/mandates/{mandateId}`
- **THEN** ответ `200` содержит `mandateId`, `status`, лимиты, период и `expiresAt`

#### Scenario: Отзыв согласия через API

- **WHEN** ТСП вызывает `POST /v1/mandates/{mandateId}/revoke` с `Idempotency-Key`
- **THEN** ответ подтверждает отзыв, повторный вызов идемпотентен

### Requirement: Ресурсы рекуррентного списания в API ТСП

API SHALL предоставлять инициацию списания (`POST /v1/mandates/{mandateId}/debits`) и чтение состояния списания (`GET /v1/debits/{debitId}`). Состояния списания SHALL быть отдельным перечислением, не смешанным с `Payment.status`.

#### Scenario: Инициация списания

- **WHEN** ТСП вызывает `POST /v1/mandates/{mandateId}/debits` с суммой и `Idempotency-Key`
- **THEN** ответ содержит `debitId` и состояние списания

#### Scenario: Состояния списания изолированы

- **WHEN** потребитель читает состояние списания
- **THEN** оно выражено отдельным перечислением (например, `CREATED`, `CONFIRMED`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`), не расширяющим `Payment.status`

### Requirement: Идемпотентность новых операций

Заголовок `Idempotency-Key` SHALL быть обязателен для всех новых `POST`. Повторный запрос с тем же ключом и тем же телом SHALL возвращать ранее созданный ресурс; повтор с иным телом SHALL завершаться `409 IDEMPOTENCY_CONFLICT`.

#### Scenario: Повтор с другим телом

- **WHEN** ТСП повторяет новый `POST` с тем же `Idempotency-Key`, но другим телом
- **THEN** шлюз отвечает `409 IDEMPOTENCY_CONFLICT` и не создаёт новый ресурс

### Requirement: Ошибки новых операций

Ошибки SHALL соответствовать RFC 9457 (Problem Details) и включать `traceId`. Помимо существующих кодов, контракт SHALL определять новые коды: `MANDATE_NOT_ACTIVE` (422), `MANDATE_EXPIRED` (422), `MANDATE_REVOKED` (422), `MANDATE_LIMIT_EXCEEDED` (422), `DEBIT_NOT_REFUNDABLE` (422).

#### Scenario: Отклонение по недействующему согласию

- **WHEN** ТСП инициирует списание по недействующему согласию
- **THEN** ответ содержит Problem Details с соответствующим кодом и `traceId`, а не `5xx`

### Requirement: Уведомления (вебхуки) для согласий и списаний

Контракт SHALL определять новые типы событий (например, `mandate.activated`, `mandate.revoked`, `debit.completed`, `debit.failed`), доставляемые с существующими гарантиями: HMAC-подпись, `X-SBP-Event-Id` для дедупликации у ТСП, ретраи и DLQ. ТСП SHALL отвечать идемпотентно по `eventId`.

#### Scenario: Уведомление о завершении списания

- **WHEN** списание зачислено и доведено до `COMPLETED`
- **THEN** шлюз доставляет `debit.completed` с `debitId`, суммой и `eventId`, при ошибке доставки применяет ретраи и DLQ

### Requirement: Версионирование и совместимость

Новые пути и опциональные поля SHALL добавляться в рамках `/v1`. Ломающие изменения SHALL выполняться только в новой мажорной версии с периодом поддержки обеих версий не менее 6 месяцев, с заголовками `Deprecation` и `Sunset` для устаревающей версии.

#### Scenario: Планируемое изменение контракта

- **WHEN** команда предлагает изменение, ломающее существующего потребителя
- **THEN** оно оформляется в новой мажорной версии, а не в `/v1`
