# Пакет изменения: Подписки СБП (рекуррентные C2B-списания по согласию плательщика)

- Change: `sbp-subscriptions` · Date: 2026-09-28 · Статус: **предложено (к архитектурному решению)**
- Решение: `docs/adr/ADR-008-podpiski-sbp-soglasie-na-rekurrentnye-c2b-spisaniya.md` (Proposed)
- Дельта: `changes/sbp-subscriptions/DELTA.md` · Передача исполнителям: `changes/sbp-subscriptions/HANDOFF.md`
- Бизнес-задача: ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика; сейчас каждый платёж требует QR и действия клиента.

---

## 1. Оценка значимости и маршрут

**Маршрут: Critical. Architecture Significance Score = 10/15** (порог Critical — 5+ или критический триггер).

Сработавшие триггеры (машинно: `significance_score`; заявлены также `significance_from_diff`):

| Триггер | Почему |
|---|---|
| `api_contract_change` | расширение контракта API ТСП (новые методы/поля/события) |
| `data_contract_change` | новая сущность «мандат» и её данные; новые события |
| `consistency_model_change` | второй конечный автомат (жизненный цикл согласия) поверх платёжного |
| `cross_domain_integration` | рекуррентное списание между банком-эквайером и банком плательщика через ОПКЦ |
| `financial_impact` | рекуррентные списания без действия плательщика — прямая финансовая операция |
| `new_component` | контур подписок (сущность + инициатор/планировщик) в ядре |
| `new_datastore` | хранение мандатов как источник истины о согласии |
| `security_boundary_change` | модель согласия: от «действие плательщика на каждый платёж» к «стоячее согласие» |
| `significant_nfr` | новые измеримые NFR (окно отзыва, точность расписания, лимиты) |
| `criticality_or_exception` | платёжный контур, КИИ |

**Что это значит для процесса.** Критический маршрут исключает прохождение «через дельту на быстром
пути»: требуется полный Solutioning (spine + ADR + NFR), **обязательная человеческая точка A3**,
walking skeleton до массовой генерации и evidence-гейты A4. Поэтому пакет содержит ADR-008, новую
спецификацию жизненного цикла мандата, измеримые NFR, критерии приёмки (EARS) и план отката — этого
делать при Fast/Standard не понадобилось бы.

Машинное свидетельство: `significance_score` → `{"route":"Critical","score":10}`; авто-детектор по
диффу подтверждает `api_contract_change` (openapi/tsp-api.yaml) — см. прогон гейта в `HANDOFF.md`.

> **Оговорка о маршруте (честно).** Гейт с `--route auto` по текущему диффу классифицирует изменение
> как **Fast** (детекторы `significance_from_diff` реагируют на код/манифесты/новые компоненты, а не на
> прозрачный для них пакет документов, даже с изменением `openapi/tsp-api.yaml`). Это **занижение**
> механическим детектором: заявленный маршрут — **Critical** (10/15, включая `security_boundary_change`
> и `financial_impact`), и процесс идёт по Critical (полный Solutioning + A3). Расхождение — дефект
> авто-детектора для чисто документарных диффов; брать надо максимальный из заявленного и машинного
> маршрутов. Отдельно: на маршруте Critical гейт даёт `INCOMPLETE` (exit 3) — обязательные
> составляющие `trace_check`, `nfr`, `model_validate`, `evidence_verify` не имеют входа (в репозитории
> нет каталога `model/` и Evidence Bundle). Это ожидаемо: они закрываются артефактами A4 (после
> реализации), а не пакетом архитектурного изменения. Единственная **проваленная** составляющая,
> найденная на Critical, — `sensors` (`required_sections`) — устранена в этом пакете.

## 2. Влияние на принятую архитектуру

### 2.1 Затронутые инварианты спайна

| Инвариант | Влияние | Что меняется |
|---|---|---|
| AD-001 (изоляция платёжного контура) | **Затронут (усиление)** | Инициатор и мандаты — внутри платёжного контура; списания идут только через шлюз. Прямые списания мимо шлюза запрещены (AD-010). |
| AD-002 (единый источник истины — статусная машина) | **Затронут** | Появляется **второй** конечный автомат (мандат) в БД шлюза; платёж по мандату остаётся в общем автомате (T13–T15). |
| AD-003 (идемпотентность финансовых операций) | **Затронут (расширение)** | Новый ключ идемпотентности `(mandateId, periodKey)` для рекуррентных списаний. |
| AD-004 (единственный адаптер ОПКЦ) | **Затронут (расширение)** | В адаптер добавляются операции мандата и списания по мандату; граница «протокол только в адаптере» сохраняется. |
| AD-005 (зачисление только из `PAID`) | **Не меняется** | Правило действует без изменений для платежей по мандату. |
| AD-006 (trust-зоны и сегментация) | **Не меняется** | Контур подписок размещается в тех же зонах. |
| AD-007 (НПС/КИИ/ПДн) | **Затронут (расширение охвата)** | Согласие и его отзыв — новый объект аудита; ПДн плательщика минимизируются (`payerRef` — токен). |
| AD-008 (гибрид, ядро контрактно-независимо) | **Не меняется** | Ядро по-прежнему зависит только от внутреннего контракта адаптера. |
| **AD-009 (новый)** | Добавлен | Мандат — источник истины о согласии; списание только против `ACTIVE`. |
| **AD-010 (новый)** | Добавлен | Изоляция и идемпотентность рекуррентного инициатора. |

### 2.2 Что НЕ меняется (явно)

- Платёжный конечный автомат остаётся единым источником истины (ADR-002) — мандатный платёж в нём же.
- Правило «зачисление только из `PAID`» (AD-005) и возвраты-сага (ADR-005) не пересматриваются.
- Транспортный слой (mTLS/ГОСТ/СКЗИ), trust-зоны и требования КИИ (ADR-003, ADR-006) не пересматриваются.
- Гибридная стратегия реализации (ADR-007, AD-008) сохраняется: финансовая логика — у банка, транспорт — у вендора.
- Существующий C2B-поток по QR не затрагивается; контракт остаётся обратно совместимым.
- Родительский spine не меняется (влияние внутри feature-уровня).

### 2.3 Радиус поражения (blast radius) и владельцы

| Затрагивается | Владелец | Действие |
|---|---|---|
| Ядро шлюза (новый контур подписок + планировщик) | команда платёжного контура | новая разработка |
| Контракт API ТСП (0.2.0) | solution-architect + ТСП-направление | аддитивное расширение, согласование с ТСП |
| Контракт адаптера ОПКЦ (§10) и RFP | solution-architect + закупки/вендор | расширить требования RFP по подпискам |
| АБС-интеграция | владелец АБС | без изменений контракта; нагрузка +250 TPS, согласовать ёмкость |
| Нотификации/сверка | команда шлюза | новые типы событий и сверка мандатов |
| ИБ/КИИ/юридическое | ИБ, комплаенс | согласие/отзыв, ПДн, аудит (161-ФЗ/152-ФЗ) |

## 3. Архитектурное решение (кратко; полностью — ADR-008)

Выбрано **A: контур подписок в ядре шлюза**; мандат — отдельная сущность и конечный автомат;
рекуррентный инициатор создаёт платёж по расписанию и переиспользует доказанный платёжный контур
(outbox, идемпотентность, зачисление из `PAID`, сверка). Рассмотрены и отвергнуты: мандат как атрибут
платежа (B), отдельный микросервис подписок (C), целиком вендорская «коробка» (D). Последствия
(положительные и отрицательные), обратимость (`reversible` → `costly` после запуска) и A3-пакет
(`choice/rationale/constraints/rejected options/expiry`) — в ADR-008.

Альтернативы и отрицательные последствия приведены намеренно: решение без минусов и без альтернатив
не проходит архитектурное ревью (канон ADR).

## 4. Изменения контрактов без поломки потребителей

**Принцип совместимости:** только аддитивные изменения в рамках `/v1`; `Payment.status` не расширяется
(новые состояния мандата живут в отдельном ресурсе `Mandate`); новые признаки платежа — опциональные
поля.

| Изменение | Тип | Совместимость |
|---|---|---|
| Пути `POST /v1/mandates`, `GET /v1/mandates/{mandateId}`, `POST /v1/mandates/{mandateId}/revoke` | добавление | обратно совместимо |
| `Payment.originationType` (`QR`\|`MANDATE`, default `QR`), `Payment.mandateId` | опциональные поля | обратно совместимо; отсутствие = `QR` |
| Типы вебхуков `mandate.*`, `debit.failed` | добавление | обратно совместимо; потребитель игнорирует неизвестные типы |
| `info.version` 0.1.0 → 0.2.0 | метаданные | в рамках `/v1`, без ломающих диффов |
| Перечисление `Payment.status` | **не меняется** | сохранено 1:1 |

Машинная проверка: `openapi_lint` (`openapi/tsp-api.yaml`) — PASS, 0 находок; сравнение версий
(`contract_diff`) не выявляет ломающих изменений (CD-1..CD-10 чисто). Документирование — `docs/contracts/tsp-api.md` §3.6–3.9, §5, §6.

## 5. Измеримые NFR нового функционала

Полный набор — `docs/nfr.md` §7; ключевое (метрика / цель / метод):

- Лаг активации мандата (нотификация ОПКЦ → `ACTIVE`): p95 < 5 с — метрика лага очереди.
- Окно остановки списаний после отзыва: ≤ 5 мин, 100 % случаев — тест отзыва + метрика инициатора.
- Двойных списаний за период мандата: **0** — тест повторного/параллельного запуска инициатора.
- Точность расписания: ±60 с от `scheduleAnchor` (p99); пропущенные запуски — 0 потерянных без следа.
- Соблюдение лимитов (на списание/период/число): 100 % — property-тест guard-логики.
- Доступность инициатора подписок: ≥ 99,95 %/мес; ёмкость: +200 TPS sustained, календарный пик до 500 TPS.
- Сверка мандатов с ОПКЦ: ежечасная; расхождений по `ACTIVE` — 0.
- Аудит согласия: 100 % переходов мандата в неизменяемом логе.

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (EARS, проверяемые тестом)

1. When рекуррентное списание инициируется, the шлюз shall выполнить его только против мандата `ACTIVE` и в пределах лимитов; иначе — отказать и не создавать платёж (AD-009, property-тест).
2. When инициатор запускается повторно за тот же `(mandateId, periodKey)`, the шлюз shall не создать второе списание (AD-010, тест идемпотентности).
3. When приходит событие ОПКЦ об отзыве согласия, the шлюз shall в течение целевого окна остановить новые списания и зафиксировать отзыв в неизменяемом аудит-логе.
4. When платёж по мандату подтверждён ОПКЦ, the шлюз shall провести зачисление только из состояния `PAID` (AD-005) и доставить ТСП `payment.completed`.
5. When ТСП повторно создаёт согласие с тем же `Idempotency-Key`, the шлюз shall вернуть тот же `mandateId` без повторного действия.
6. While вебхуки доставляются повторно, the ТСП shall дедуплицировать события по `X-SBP-Event-Id` (ADR-004).
7. Негативные сценарии (обязательны): отказ ОПКЦ, недоступность АБС при зачислении (платёж остаётся `PAID`, сверка добирает), гонка «отзыв ↔ инициация», обрыв канала к ОПКЦ (circuit breaker).
8. Совместимость: потребитель API 0.1 продолжает работать без изменений; `openapi_lint` — PASS.
9. Критерий успешного отката: after feature-flag off — новые списания не создаются (0 за окно наблюдения), существующие платежи доводятся до терминального статуса, сверка без расхождений.

### 6.2 План отката

- **Сигналы отката (триггеры):** рост двойных списаний (SLO нарушен: >0); окно остановки после отзыва превышено; расхождения сверки мандатов; инцидент ИБ/регуляторный флаг.
- **До боевой эксплуатации:** откат = не включать фичу (фиче-флаг `subscriptions.enabled=false`); аддитивные изменения безвредны.
- **После включения (обратный откат):**
  1. `stop-new`: запрет регистрации новых мандатов и новых списаний (флаг выключен), обработка уже открытых платежей продолжается.
  2. Отзыв/архивация затронутых мандатов по процедуре (совместно с ИБ/юридическим), уведомление ТСП.
  3. Rolling-откат релиза; данные мандатов не удаляются (архив) — шлюз остаётся источником истины до полной сверки.
  4. Аварийный сценарий: DLQ → дежурная смена по runbook; сверка компенсирует расхождения; RTO ≤ 1 ч.
- **Владелец решения об откате:** solution-architect + владелец платёжного контура (при участии ИБ для регуляторных триггеров).

## 7. Что остаётся на решение человека-архитектора (A3) и почему

Маршрут Critical делает человеческое решение **обязательным** (`choice` в ADR-008). На машине/агенте
остаются: доказательная база, альтернативы и пакет; за человеком — выбор и его последствия.

1. **Выбор модели подписок** (`mandate-context-in-gateway` vs B/C/D) — влияет на стоимость владения, регуляторный контур и сроки; требует бизнес- и юридического мандата, которого у агента нет.
2. **Юридическая модель согласия** (форма согласия, формулировка отзыва, правовое основание 152-ФЗ, соответствие 161-ФЗ) — предмет решения комплаенса, не инженерии.
3. **Политика лимитов и расписаний по категориям ТСП** (какие максимумы допустимы для кинотеатров/ЖКХ/связи) — коммерческое и риск-решение.
4. **Включение подписок в текущий RFP вендора или отдельная закупка** — решение по срокам/бюджету/риску закупки.
5. **Категория объекта КИИ и состав мер** — согласование с ИБ; внешний вход.
6. **Точная семантика протокола НСПК по подпискам** (поля, отзыв, лимиты) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; проект зафиксирует после получения документации.
7. **Порог и владелец решения об откате** (см. §6.2) — ответственность за финансовый/регуляторный риск.

Отдельно: агент **не** принимает решение о выкатке в бой и **не** подписывает A3 — это фиксирует ADR-008
(Status: Proposed → Accepted после человеческого решения).
