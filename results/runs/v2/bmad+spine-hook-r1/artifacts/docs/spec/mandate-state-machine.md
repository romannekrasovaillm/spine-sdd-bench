# Статусная машина мандата (согласия плательщика) — спецификация

- Status: Draft (для ревью на гейте A1, change `sbp-subscriptions`)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, AD-009, AD-010, `docs/spec/state-machine.md` (платёж по мандату)

## Проблема

Рекуррентное C2B-списание выполняется без действия плательщика на каждый платёж, поэтому его законность и безопасность опираются на ранее оформленное согласие. Принятая архитектура (ADR-002) описывает только платёж по QR и не содержит сущности согласия: негде хранить лимиты и расписание, нечем доказать отзыв, нечего сверять с ОПКЦ. Без явного жизненного цикла мандата невозможны ни контроль несанкционированных списаний, ни аудит для 161-ФЗ/152-ФЗ.

## 1. Состояния мандата

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `DRAFT` | Заявка на подписку создана, ещё не отправлена в ОПКЦ | да |
| `PENDING_CONFIRMATION` | Согласие зарегистрировано в ОПКЦ, ожидается подтверждение плательщика в приложении его банка | да |
| `ACTIVE` | Согласие подтверждено; списания в пределах лимитов разрешены | да |
| `SUSPENDED` | Списания приостановлены (ТСП либо по требованию/лимиту); отзыв не выполнен | да |
| `EXPIRED` | Истёк срок действия мандата; списания невозможны | да |
| `REVOKED` | Согласие отозвано (плательщиком или принудительно); терминальное состояние | да |
| `FAILED` | Регистрация согласия отклонена ОПКЦ либо не подтверждена; терминальное | да |

## 2. Атрибуты мандата

| Поле | Назначение |
|---|---|
| `mandateId` | Идентификатор мандата в шлюзе (сквозной для сверки) |
| `tspId` | Владелец подписки (ТСП) |
| `payerRef` | Обезличенная ссылка на плательщика (токен ОПКЦ; без ПДн в шлюзе — AD-007) |
| `amountLimit` | Лимит на одно списание (копейки) |
| `periodLimit` | Лимит накопленной суммы за период (копейки) |
| `periodKind` | Период: `DAY` \| `MONTH` |
| `maxDebitsPerPeriod` | Максимум списаний в периоде |
| `scheduleAnchor` | Дата/день привязки расписания (напр. 5-е число месяца) |
| `purpose` | Назначение (текст для плательщика) |
| `validUntil` | Срок действия согласия |
| `status` | Текущее состояние (см. §1) |
| `revokedAt`, `revocationReason` | Время и причина отзыва (аудит) |

## 3. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| M1 | — | `DRAFT` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен, лимиты в допустимых границах | запись мандата + outbox-событие «регистрация согласия в ОПКЦ» |
| M2 | `DRAFT` | `PENDING_CONFIRMATION` | ответ адаптера ОПКЦ: согласие зарегистрировано | получен `opkcMandateRef` | сохранить ссылку ОПКЦ, outbox-нотификация ТСП |
| M3 | `DRAFT` | `FAILED` | ошибка регистрации (исчерпаны ретраи/DLQ) | ошибка не транзиентная | `errorCode`, вебхук, аудит |
| M4 | `PENDING_CONFIRMATION` | `ACTIVE` | событие ОПКЦ «согласие подтверждено» (или сверка) | `payerRef` и лимиты совпадают с заявкой | outbox-событие, вебхук `mandate.activated`, аудит |
| M5 | `PENDING_CONFIRMATION` | `FAILED` | плательщик не подтвердил / ОПКЦ отклонил | — | `errorCode`, вебхук, аудит |
| M6 | `ACTIVE` | `SUSPENDED` | запрос ТСП на паузу либо достигнут лимит | — | пауза расписания, вебхук, аудит |
| M7 | `SUSPENDED` | `ACTIVE` | снятие паузы (лимит/срок не истёк) | срок действия не истёк | возобновление расписания, аудит |
| M8 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | `validUntil` наступил | новых списаний нет | закрытие расписания, вебхук `mandate.expired`, аудит |
| M9 | `ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв плательщиком (событие ОПКЦ) либо принудительный отзыв | — | немедленный запрет новых списаний, вебхук `mandate.revoked`, аудит |
| M10 | `PENDING_CONFIRMATION` | `REVOKED` | отзыв до подтверждения | — | терминальное, вебхук, аудит |

## 4. Запрещённые переходы (инварианты)

- Списание в АБС/ОПКЦ инициируется **только против `ACTIVE`-мандата** (AD-009); из любого иного состояния — недостижимо, проверяется fitness-тестом.
- `REVOKED`, `EXPIRED`, `FAILED` — терминальные; переходов из них нет (повторные триггеры идемпотентны, AD-003).
- После `REVOKED` новое списание невозможно; уже инициированные платежи доводятся до терминального статуса, но не заменяются новыми.
- Изменение лимитов/расписания оформленного мандата — только через новый мандат или согласованную операцию ОПКЦ (протокол — `[ТРЕБУЕТ ПРОВЕРКИ]`); «на лету» менять лимиты нельзя.
- `payerRef` и реквизиты мандата иммутабельны после `PENDING_CONFIRMATION`.

## 5. Идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| Событие ОПКЦ о подтверждении/отзыве | `eventId` | обработанный `eventId` игнорируется (ADR-004) |
| Инициация списания за период | `(mandateId, periodKey)` | повторный запуск за тот же период не создаёт второе списание (AD-010) |
| `POST /v1/mandates/{mandateId}/revoke` | `Idempotency-Key` | повторный отзыв возвращает текущий ресурс, новых действий нет |

## 6. Интеграция с платёжной статусной машиной

- Платёж по мандату — платёж с `originationType=MANDATE` и ссылкой `mandateId` в том же конечном автомате (ADR-002).
- Дополнительные переходы к `docs/spec/state-machine.md`:
  - **T13**: `CREATED → PAID` — подтверждение списания от ОПКЦ по мандату (состояние `QR_ISSUED` не используется).
  - **T14**: `CREATED → FAILED` — списание отклонено ОПКЦ (лимит, отзыв, недостаток средств) с `errorCode`.
- Правила AD-005 (зачисление только из `PAID`), AD-002 (атомарность «статус + outbox + аудит») и AD-003 (идемпотентность) действуют без изменений.

## 7. Лимиты и расписание

- Перед инициацией списания шлюз проверяет: мандат `ACTIVE`; `amount` ≤ `amountLimit`; сумма за период + `amount` ≤ `periodLimit`; число списаний за период < `maxDebitsPerPeriod`; наступил срок по `scheduleAnchor`.
- Нарушение любого условия — списание не инициируется, фиксируется событие `debit.skipped` с причиной (наблюдаемость), ТСП получает вебхук `debit.failed`.
- Пропущенный запуск планировщика не теряется: фиксируется в отчёте незавершённых операций и, при допустимости окна, довыполняется в пределах периода.

## 8. Сверка и восстановление

- Открытые состояния (`PENDING_CONFIRMATION`, `ACTIVE`) — кандидаты сверки с ОПКЦ (ADR-004): подтверждение/отзыв, потерянные нотификацией, восстанавливаются опросом статуса мандата.
- «У ОПКЦ отозван, у нас `ACTIVE`» → немедленный M9 (стоп-сигнал, эскалация).
- «У нас `ACTIVE`, у ОПКЦ нет» → пауза списаний по мандату, эскалация.

## Критерии приёмки

- When мандат находится в состоянии `REVOKED`/`EXPIRED`/`FAILED`, the инициатор shall не создать ни одного нового платежа по этому мандату (проверяется фикстурой состояния + тестом).
- When запрошенное списание превышает `amountLimit`/`periodLimit`/`maxDebitsPerPeriod`, the шлюз shall отклонить инициацию, зафиксировать `debit.skipped` с причиной и вернуть ТСП `debit.failed`.
- When инициатор запускается повторно за тот же `(mandateId, periodKey)`, the шлюз shall не создать второе списание (идемпотентность, AD-010).
- When приходит событие ОПКЦ об отзыве согласия, the шлюз shall в течение целевого окна остановить новые списания по мандату и зафиксировать отзыв в неизменяемом аудит-логе.
- When платёж по мандату подтверждён ОПКЦ, the шлюз shall провести зачисление только из состояния `PAID` (AD-005) и доставить ТСП `payment.completed`.
- While вебхуки доставляются повторно, the ТСП shall дедуплицировать события по `X-SBP-Event-Id` (ADR-004).

## Риски

- Протокол подписок НСПК не получен: точные поля мандата, семантика отзыва и лимиты помечены `[ТРЕБУЕТ ПРОВЕРКИ]` — риск переработки спецификации после получения документации НСПК.
- Отзыв согласия асинхронен: возможен малый интервал, в котором списание уже инициировано, но отзыв ещё не обработан; митигация — целевое окно остановки (NFR) + компенсация возвратом.
- Календарные пики (начало месяца) могут дать всплеск нагрузки на инициатор, адаптер и АБС; митигация — разнесение якорей расписания и запас ёмкости.
- Ошибка в guard-логике лимитов = несанкционированное списание (финансовый и репутационный риск); митигация — fitness-тесты на все запрещённые переходы и лимиты.

## 9. Согласованность с API ТСП

Маппинг наружу (TSP API v0.2.0): состояния мандата выводятся в ресурсе `Mandate.status`; платёж по мандату виден в существующем `Payment` с `originationType=MANDATE` и `mandateId`. Технические подсостояния инициатора наружу не выставляются.
