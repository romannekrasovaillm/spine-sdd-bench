# Влияние изменения: СБП-подписки (рекуррентные C2B-списания)

Сопровождает `changes/sbp-subscriptions/DELTA.md`. Отвечает на вопросы «насколько глубокое проектирование нужно» (значимость) и «что именно меняется в принятой архитектуре».

## 1. Значимость и маршрут

Инструмент `significance_score` (Spine), заявленные триггеры:

| Триггер | Значение | Почему |
|---|---|---|
| `new_component` | true | контур мандатов и поручений (слоты списаний) |
| `new_datastore` | true | хранилище мандатов, согласий и слотов списаний |
| `cross_domain_integration` | true | новый домен «подписки» стыкуется с платежами, АБС, НСПК |
| `api_contract_change` | true | расширение API ТСП (мандаты, списания) |
| `data_contract_change` | true | новые сущности мандата/слота, связь «списание ↔ платёж» |
| `consistency_model_change` | true | второй автомат (мандат) + семантика слота |
| `significant_nfr` | true | новые бюджетные цели (инициация, отзыв, уведомление) |
| `rto_rpo_targets` | true | RPO=0/RTO для мандатов и слотов, распространение отзыва |
| `financial_impact` | true | списание без участия плательщика в момент операции |
| `criticality_or_exception` | true | СБП — критичный контур; рекуррент меняет профиль риска |

**Вердикт: 10/15 → маршрут Critical.** Порог Critical (≥5 либо критический триггер) пройден с запасом; более того, сработал критический триггер `criticality_or_exception`.

**Что это значит для процесса:**

- Полный Solutioning — дельта-спеки недостаточно (Fast/Standard-маршруты отпадают).
- Обязательная человеческая точка **A3** по развилке «кто инициирует списание» (ADR-009) — это не делегируемое агенту решение.
- Расширение спайна (новые AD) — до реализации; walking skeleton подписок до массовой генерации; evidence-гейты A4/A5.

Примечание для человека-архитектора: два триггера я оцениваю как **пограничные** и намеренно не заявлял их `true` — `security_boundary_change` (мандат хранит идентификаторы плательщика) и `domain_ownership_change` (домен подписок может получить отдельного владельца). Оба не меняют маршрут (Critical уже достигнут), но влияют на состав согласований и должны быть подтверждены на A3 (см. `OPEN-QUESTIONS.md`, п. 2 и 4).

## 2. Что меняется и что не меняется

### 2.1 Не меняется (важно зафиксировать явно)

- **AD-005 «зачисление только из `PAID`»** — сохраняется без изменений. Рекуррентное списание, как и разовый платёж, зачисляется только по подтверждённому ОПКЦ статусу. Меняется лишь способ достижения `PAID` (подтверждение поручения вместо сканирования QR).
- **AD-002 «атомарный переход = статус + outbox + аудит»** — правило то же; распространяется на переходы мандата, но не пересматривается.
- **ADR-007 (гибрид: своё ядро + вендорский транспорт)** — не пересматривается. Ядро остаётся контрактно-независимым от транспорта; расширяется только *скоуп* внутреннего контракта адаптера (мандаты, списания, отзывы).
- **Статусная машина платежа (T1–T12)** — не переписывается. Рекуррентный поток переиспользует подмножество переходов `CREATED → PAID → CREDITED → COMPLETED` и существующую сагу возврата; ветка `QR_ISSUED` остаётся для разового потока.
- **Возвраты** — существующая сага ADR-005 переиспользуется (возврат рекуррентного списания — частный случай возврата по `paymentId`).

### 2.2 Меняется (расширяется)

| Инвариант | Что добавляется |
|---|---|
| AD-001 (изоляция) | новый контур подписок (мандаты, слоты) размещается **внутри** платёжного контура; доступ к ОПКЦ и АБС — только через существующие адаптеры. `Binds` расширяется. |
| AD-002 (атомарность) | вторая статусная машина — мандат — с той же дисциплиной «изменение статуса + outbox + аудит в одной транзакции». |
| AD-003 (идемпотентность) | новый класс ключей: слот списания `mandateId + periodKey` (в дополнение к `Idempotency-Key` ТСП и `eventId` НСПК). |
| AD-004 (единый адаптер ОПКЦ) | новые методы/события протокола (регистрация мандата, поручение на списание, подтверждение/отказ, отзыв) — только через адаптер; `opkc-adapter` получает дельту. |
| AD-006 (trust-зоны) | новая зона **не** появляется; усиливаются меры по ПДн плательщика (идентификаторы, лимиты, хранение мандата). |
| AD-007 (НПС/КИИ/ПДн) | новый регуляторный слой: согласие плательщика как правовое основание повторных списаний, уведомление плательщика о списании, лимиты. |
| AD-008 (гибрид) | ядро не меняется; возможен новый вендорский скоуп (рекуррент в транспорте) → обновление RFP и kill-criteria. |

### 2.3 Новые инварианты (проект, Proposed)

Формально вносятся в `ARCHITECTURE-SPINE.md` как AD-009…AD-012 (см. дельту):

- **AD-009.** Действующий мандат — предусловие любого рекуррентного списания.
- **AD-010.** Сумма и число списаний проверяются против границ мандата на каждом списании.
- **AD-011.** Идемпотентность слота: `mandateId + periodKey` не допускает второго списания.
- **AD-012.** Отзыв мандата немедленно останавливает будущие списания; подтверждённое после отзыва — возвращается.

## 3. Влияние на компоненты (C4 — контейнеры)

К существующему контуру (`docs/solutioning.md` §2) добавляются:

- **Сервис мандатов (согласий)** — CRUD/статусная машина мандата, регистрация в ОПКЦ через адаптер, проекция статуса из ОПКЦ.
- **Сервис поручений (слоты списаний)** — приём поручений ТСП, валидация границ, ключ слота, материализация платежа в автомат платежа.
- *(вариант)* **Банковский добиватель слотов** — ретрай уже авторизованных незавершённых слотов; **не** инициирует новые списания (см. ADR-009).

Существующие компоненты **не перепроектируются**: статусная машина платежа, outbox, нотификатор ТСП, адаптер АБС, сверка, адаптер ОПКЦ — переиспользуются; меняется только состав методов адаптера ОПКЦ и появляются новые источники событий для сверки.

## 4. Границы изменения (anti-scope-creep)

Вне scope этой дельты остаётся: изменение модели разового C2B-приёма; смена стратегии реализации (ADR-007); C2C/B2C-выплаты; изменение «зачисление только из `PAID`»; замена АБС-интеграции. Всё перечисленное — отдельные решения с собственными ADR.
