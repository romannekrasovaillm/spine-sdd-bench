# Дельта контракта адаптера ОПКЦ: мандаты и рекуррентные списания — v0.1 draft

- Status: Draft (для A1; обновляет скоуп RFP, `docs/rfp/vendor-rfp.md`)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, ADR-010, AD-004, AD-008
- Базовый контракт: `docs/contracts/opkc-adapter.md`

Дополняет базовый контракт ядро↔транспорт, не изменяя его существующие методы и события. Точные сообщения протокола НСПК — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]` (адаптер нормализует их в формы ниже).

## 1. Синхронные операции (ядро → адаптер)

| Метод | Смысл | Ключевые поля | Ответ | Таймаут (p99.9) |
|---|---|---|---|---|
| `registerMandate` | регистрация согласия плательщика в ОПКЦ | `reference` (= `mandateId` ядра), плательщик, `tspId`, лимиты, срок | `mandateOpcId`, статус `ACCEPTED` (результат — событием) | 5 c |
| `getMandateStatus` | статус согласия (сверка) | `mandateOpcId` или `reference` | `ACTIVE` / `PENDING` / `REVOKED` / `EXPIRED` / `REJECTED` / `UNKNOWN` | 3 c |
| `revokeMandate` | отзыв согласия по инициативе ТСП/ядра | `reference`, `reason` | `REVOKED` | 3 c |
| `createDebit` | поручение на рекуррентное списание | `reference` (= `debitId` ядра), `mandateOpcId`, `amount`, `periodKey` | `ACCEPTED` (результат — событием) | 5 c |
| `getDebitStatus` | статус списания (сверка) | `reference`/`debitOpcId` | `PAID` / `PENDING` / `REJECTED` / `UNKNOWN`, `paidAt?` | 3 c |
| `getMandateReconciliation` | выписка мандатов/списаний за период | `from`, `to` | список: `mandateOpcId`, `status`, `debitRef`, `amount`, `timestamp` | 10 c |

Статусы ОПКЦ (`ACTIVE`, `REVOKED`, `PAID`, `REJECTED`, `EXPIRED`) — **нормализованные адаптером**; ядро не зависит от конкретных значений НСПК.

## 2. Асинхронные события (адаптер → ядро)

Обязательные поля: `eventId` (дедупликация), `type`, `timestamp`, `correlationRef` (reference ядра).

| Тип | Смысл | Ключевые поля |
|---|---|---|
| `mandate.activated` | согласие подтверждено ОПКЦ | `reference` (= `mandateId`), `mandateOpcId`, `validUntil?` |
| `mandate.rejected` | регистрация согласия отклонена | `reference`, `reasonCode`, `reasonText` |
| `mandate.revoked` | согласие отозвано (банк плательщика/ОПКЦ) | `reference`, `revokedAt`, `reasonCode?` |
| `debit.paid` | списание подтверждено | `reference` (= `debitId`), `mandateOpcId`, `amount`, `paidAt` |
| `debit.rejected` | списание отклонено | `reference`, `reasonCode`, `reasonText` |
| `debit.expired` | поручение не исполнено в срок | `reference` |
| `mandate.limit_exceeded` | попытка списания за границами мандата | `reference`, `limitType` |

Гарантии прежние (базовый контракт §4): at-least-once, повторы возможны → ядро дедуплицирует по `eventId`; строгий порядок не гарантируется, ядро устойчиво к поздним событиям; сверка страхует.

## 3. Идемпотентность и границы

- Ядро передаёт `reference` в каждый мутирующий вызов; **адаптер обязан обеспечить идемпотентность по `reference`** (обязательное требование RFP, базовый контракт §5).
- Для `createDebit` ключ идемпотентности на стороне ядра — слот `mandateId + periodKey` (AD-011); адаптер обязан не создавать дубль списания при повторном `reference`.
- Отзыв идемпотентен: повторный `revokeMandate` возвращает `REVOKED` без побочных действий.

## 4. Требования к вендору (дополнение к RFP)

1. Поддержка методов §1 и событий §2 поверх протокола НСПК; нормализация статусов/ошибок.
2. Идемпотентность `createDebit`/`registerMandate` по `reference` — **обязательно** (демо на POC).
3. Тестовый контур НСПК: сценарии мандата (активация/отказ/отзыв) и списаний (paid/rejected/expired, повторы) — для тестов ядра.
4. Документация: схема мандата, правила лимитов и TTL согласия, семантика отзыва, ротация ключей.
5. Если протокол НСПК не даёт идемпотентности «из коробки» — вендор реализует маппинг `reference → операция ОПКЦ` у себя.

## 5. Сценарии POC (дополнение к базовым P1–P8)

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| S1 | Счастливый путь: `registerMandate` → `mandate.activated` → `createDebit` → `debit.paid` | корректные `mandateOpcId`/события |
| S2 | Повтор `createDebit` с тем же `reference` | одно списание, дубля нет |
| S3 | Отзыв: `revokeMandate` → `mandate.revoked`; повторная попытка `createDebit` | списание отклонено |
| S4 | Попытка списания сверх границ мандата | `mandate.limit_exceeded` / отклонение |
| S5 | Потеря события `debit.paid` | сверка через `getDebitStatus`/`getMandateReconciliation` находит операцию |

## 6. Открытые вопросы

1. Полный перечень сообщений протокола НСПК по рекуррентным списаниям и мандатам — `[ТРЕБУЕТ ПРОВЕРКИ]`.
2. Правила лимитов и TTL согласия (кто задаёт, можно ли менять) — по документации НСПК.
3. Формат уведомления плательщика о списании — канал (уведомление банка плательщика/НСПК) уточняется.
4. Нужен ли отдельный `getMandateReconciliation` или сверка идёт общим отчётом — решить с вендором.
