# ADR-010. Надёжность и идемпотентность инициатора регулярных списаний

- Date: 2026-09-28
- Status: Proposed (требует человеческого решения A3 до реализации)
- Owner: solution-architect (платёжный контур) + SRE/платёжный мониторинг
- Related: ADR-008, ADR-002, ADR-004, AD-002, AD-003, AD-005

## Context

Инициатор регулярных списаний — новый компонент, который по расписанию создаёт платежи без действия клиента. В отличие от API ТСП, триггер здесь **внутренний и плановый**, а это порождает специфические отказы:

- компонент мог быть недоступен в момент наступления периода (`nextChargeAt` в прошлом) — нужен **catch-up**, но не более одного списания на период;
- экземпляров инициатора при горизонтальном масштабировании несколько — нельзя допустить двойной инициации одной и той же подписки;
- рестарт в середине цикла, переобработка события, «дребезг» планировщика — всё это не должно превращаться в двойное списание;
- после сбоя нельзя «потерять» период (пропуск списания), но и нельзя «догнать» его ценой нескольких списаний.

При этом регулярное списание — финансово значимое действие (AD-003, AD-005), значит идемпотентность обязана быть не «на уровне приложения», а на уровне естественного ключа, проверяемого в одной транзакции с состоянием.

## Decision

1. **Один объект списания на период.** Детерминированный `periodKey` (календарный период подписки; формат/календарь фиксируются с требованиями НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`). Объект списания создаётся один раз на пару **`(mandateId, periodKey)`**; уникальный индекс в БД ядра запрещает второй объект за тот же период.
2. **Единственный писатель расписания — инициатор.** ТСП и API расписание только читают. **Инициатор — не источник финансового статуса:** он создаёт объект списания в `CREATED` через **тот же внутренний домен-сервис статусной машины**, что использует API ТСП (не через внешний HTTP), с `paymentType=recurring`, `mandateId`, `periodKey`. Далее — переходы T13 (`CREATED → PAID` по НСПК) и общие (зачисление только из `PAID`, AD-005).
3. **Идемпотентность операций списания:** синхронный вызов адаптера несёт `reference = paymentId` объекта списания (1:1 с `(mandateId, periodKey)`); повтор с тем же `reference` не создаёт дубль в ОПКЦ (обязательное требование RFP). Каждая **попытка** дуннинга имеет собственный `attemptRef`, поэтому её повтор идемпотентен по своему `attemptRef`, но не создаёт новый объект списания.
4. **Catch-up ограничен политикой:** при недоступности инициатора после восстановления — **не более одной попытки за просроченный период**; периоды, когда мандат был не `ACTIVE`, не догоняются. Сколько периодов догонять — бизнес-политика (по умолчанию фиксируется на A2).
5. **Горизонтальное масштабирование без лидер-лока:** корректность обеспечивают уникальность `(mandateId, periodKey)` и транзакционное создание объекта списания, а не единый инстанс-лидер. Гонку двух экземпляров разрешает уникальный индекс/транзакция.
6. **Дуннинг — попытки внутри объекта списания:** конечное число попыток с экспоненциальной задержкой; неуспех не создаёт второй объект списания; **успешным и зачисленным за период может быть не более одной попытки** (частичный уникальный индекс на уровне зачисленного состояния). Исчерпание попыток → объект `FAILED` + мандат `SUSPENDED` (M4).
7. **Commit-time правило отзыва:** объект списания создаётся только если мандат `ACTIVE` в той же транзакции; при отзыве (M6) ещё не подтверждённые НСПК списания отменяются (T14), подтверждённые — доводятся.
8. **Наблюдаемость и сверка:** лаг инициации, число catch-up, дуннинг-ретраи, доля отказов, DLQ; периодическая сверка мандатов с НСПК (ежечасная), расхождения — в отчёт незавершённых операций (ADR-004).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Выбран: детерминированный `(mandateId, periodKey)` + транзакционное создание платежа** | Защита от дублей даже при гонке экземпляров и рестарте; масштабируется без лидер-лока; «ровно одно списание на период» доказуемо | Нужен календарь периодов и уникальный индекс; catch-up-политика требует бизнес-решения |
| Единый инстанс-лидер (leader election), планирует и инициирует один узел | Проще рассуждать, один планировщик | Лидер — single point of failure; при смене лидера возможны пропуск или дубль; сложнее масштабировать |
| «Fire once» best-effort без персистентности расписания | Минимум кода | Потеря периода при рестарте; невозможность catch-up; недопустимо для финансовой операции |
| Идемпотентность «по времени» (не инициировать, если недавно было списание) | Просто | Не детерминировано; не защищает от гонки и от корректного catch-up; расходится с AD-003 |

## Consequences

### Positive

- «Не более одного зачисленного списания на период» обеспечивается на уровне данных, а не соглашений между экземплярами.
- Catch-up делает регулярные списания устойчивыми к простоям без риска двойного списания.
- Повторное использование статусной машины и outbox сохраняет аудит и сверку едиными.

### Negative

- Календарь периодов и политика catch-up — дополнительная бизнес- и тестовая сложность (таймзоны, месячные периоды, DST).
- Дуннинг добавляет операции и события, требующие приоритизации и мониторинга.
- Уникальный индекс на `(mandateId, periodKey)` — жёсткое ограничение, которое нельзя «обойти» ручной операцией без 4-eyes (AD-006).

## Reversibility

**reversible.** Механика инициатора (планировщик, catch-up, дуннинг) заменяема и настраивается без смены статусной модели и контрактов; `periodKey`-модель можно расширять. Отказ от инициатора в пользу charge-on-demand (см. ADR-008 Deferred) возможен поверх того же мандата.
