# ADR-008. Модель подписок СБП: мандат плательщика и инициатор регулярных списаний в ядре шлюза

- Date: 2026-09-28
- Status: Proposed (требует человеческого решения A3 до реализации)
- Owner: solution-architect (платёжный контур) + продукт/бизнес + ИБ/комплаенс
- Related: ADR-002, ADR-004, ADR-005, ADR-007, AD-002, AD-003, AD-005, AD-008

## Context

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** — подписки СБП. Сегодня каждый платёж требует QR и действия клиента, регулярность обеспечивается вне банка (напоминания, повторные ссылки), а не самим шлюзом.

> **Внешнее допущение `[ТРЕБУЕТ ПРОВЕРКИ]`:** наличие и состав mandate-механизма (согласие плательщика + регулярное списание без QR) в протоколе ОПКЦ СБП подтверждается документацией НСПК по договору. До подтверждения архитектура строится на изоляции этого механизма внутри адаптера и на моках; при отсутствии механизма решение пересматривается (эскалация).

Изменение вводит в платёжный контур две новые сущности:

- **мандат (согласие плательщика)** — оформленное по правилам СБП согласие на серию списаний в пользу ТСП;
- **расписание списаний** — параметры регулярности (период, сумма/лимит), по которым шлюз обязан инициировать списания без действия плательщика.

Ключевые силы:

- Списание происходит **без действия клиента** → цена ошибки (двойное списание, списание без действующего согласия, продолжение после отзыва) резко выше, чем у разового платежа.
- Согласие и уведомления — регуляторный контур (161-ФЗ, 152-ФЗ, правила НСПК); точный протокол ОПКЦ по мандатам публично не раскрыт, получается по договору `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Принятое решение — **гибрид** (ADR-007, AD-008 `[ADOPTED]`): ядро шлюза собственное, транспорт ОПКЦ вендорский, ядро контрактно-независимо от транспорта.

Развилка: **где живёт расписание** (кто инициирует каждое списание) и **где живёт мандат**. Затронуты статусная машина и её инварианты (ADR-002, AD-005), идемпотентность (ADR-003), единственный адаптер ОПКЦ (AD-004) и trust-зоны (AD-006).

Решение принято на развилке «инициатор списаний»: **банк (ядро шлюза) владеет расписанием**; модель мандата — **обе: fixed и variable**.

## Decision

1. **Мандат плательщика — отдельная сущность ядра шлюза** с собственной статусной машиной (`PENDING_CONSENT → ACTIVE → SUSPENDED | REVOKED | EXPIRED`), отдельной таблицей и неизменяемым аудитом. Мандат — единственный источник истины о согласии; см. AD-009 (spine) и ADR-009.
2. **Расписание регулярных списаний — в ядре шлюза.** Новый компонент контура — **инициатор регулярных списаний** — хранит расписание (`periodKey`/`nextChargeAt`), по наступлении срока создаёт платёж и запускает его через **существующую статусную машину платежа**. Инициатор не пишет финансовый статус сам.
3. **Регулярное списание — это обычный платёж** с общей статусной моделью и терминальными состояниями; для него `paymentType = recurring` и обязательна ссылка `mandateId`. **Стадия QR отсутствует:** после принятия `createRecurringDebit` платёж переходит `CREATED → PAID` по подтверждению НСПК (явное расширение статусной машины, ADR-002; QR-переходы T2 применяются только к разовым платежам). **Зачисление — только из подтверждённого НСПК `PAID`** (AD-005 сохраняется без изменений и распространяется на регулярные списания).
4. **Идемпотентность создания списания — по натуральному ключу `(mandateId, periodKey)`** (плюс существующие `Idempotency-Key` для API ТСП и `eventId` для нотификаций): за период создаётся **один объект списания**; повторная инициация не создаёт второй. Повторы при неуспехе (дуннинг) выполняются как **попытки внутри того же списания** с отдельными `attemptRef`; успешным (и зачисленным) за период может быть только один (AD-011).
5. **Модель мандата — обе:** `fixed` (фиксированная сумма и период; сумма списания определяется мандатом) и `variable` (сумма каждого списания задаётся ТСП заранее для периода и не превышает `maxAmount` согласия; см. ADR-009).
6. **Протокол ОПКЦ по мандатам — целиком внутри транспортного адаптера** (новые методы и события контракта `docs/contracts/opkc-adapter.md`). Ядро оперирует нормализованными `mandateRef`/`chargeKey` и не знает деталей НСПК (AD-004, AD-008).
7. **Эволюция API ТСП — строго аддитивная** (`docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml` → v0.2): новые пути/схемы и опциональные поля, путь `/v1` сохранён, существующий enum `Payment.status` не расширяется (ADR-008 §4).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Выбран: мандат + инициатор (расписание) в ядре шлюза** | Единый источник истины о согласии и расписании; полный контроль регулярности, аудита и уведомлений; переиспользует статусную машину, outbox и сверку; обратимо фиче-флагом до включения | Новый компонент и новая БД-логика; инициатор требует catch-up, идемпотентности и мониторинга; +RFP-скоуп вендора |
| Мандат и расписание в НСПК/у вендора, ядро проксирует | Меньше кода в ядре; вендор отвечает за регулярность | Расписание и согласие вне источника истины шлюза (нарушает AD-002); финансовая регулярность вне контроля и аудита банка; vendor lock-in; расходится с AD-008 (ядро владеет финансовой логикой) |
| Планировщик — отдельный банковский сервис вне платёжного контура, вызывает API ТСП шлюза | Переиспользование внеконтурного планировщика | Второй путь создания платежа мимо статусной машины; расщепление источника истины (AD-002); внешний сервис получает доступ в платёжный контур (AD-001); идемпотентность расползается между сервисами |
| Charge-on-demand: каждое списание инициирует ТСП по мандату | Минимум нового в шлюзе; расписание остаётся у ТСП | Банк не контролирует, состоялось ли списание и не нарушена ли регулярность; дуннинг и уведомления размазаны по ТСП; слабее гарантии для плательщика (отклонено как основная модель; см. Deferred) |
| Регулярность через повторные разовые QR с действием клиента | Нет новых сущностей | Это не рекуррент: сохраняется текущая боль бизнеса; не является решением задачи |

## Consequences

### Positive

- Единый источник истины о согласии и расписании — проще доказывать корректность регулятору и сверять с НСПК/АБС.
- Регулярное списание переиспользует уже принятые инварианты: атомарные переходы, outbox, «зачисление только из `PAID`», дедупликация по `eventId` — ядро не переписывается.
- Границы адаптера ОПКЦ соблюдены: протокол мандатов не протекает в ядро, вендор остаётся заменяемым.
- Согласие, расписание и уведомления аудируемы и управляемы фиче-флагом.

### Negative

- Новый компонент (инициатор) и новая сущность (мандат) — эксплуатационная и тестовая нагрузка; нужны catch-up, мониторинг лага, DLQ, сверка мандатов.
- Регуляторный контур (согласие, уведомление о списании, отзыв, хранение доказательств) добавляет нетривиальные требования и внешние согласования.
- Расширяется RFP-скоуп вендора (mandate-протокол ОПКЦ); при отсутствии поддержки у вендора изменение AD-008 придётся эскалировать.
- Цена ошибки при списании без действия клиента выше: критичен контроль лимитов, дедупликации и приоритетной обработки отзыва.

## Reversibility

**costly** после включения боевых списаний. До включения — **reversible**: всё скрыто за фиче-флагом, работ по транспорту нет, данные мандатов не накоплены. После боевой эксплуатации упрощённый откат невозможен: действующие мандаты накладывают обязательства (зачисление уже начатых списаний, уведомление и honouring отзыва плательщика), доказательства согласия подлежат регуляторному хранению. Полный отказ от функции = прекращение новых мандатов и новых списаний при сохранении обязательств по действующим; данные мандатов не удаляются.
