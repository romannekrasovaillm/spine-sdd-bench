# 06. Критерии приёмки и план отката

## 1. Критерии приёмки (проверяемые)

Каждый критерий проверяется тестом или fitness-проверкой на гейте A4; негативные сценарии обязательны.

### Позитивные и функциональные

| ID | Критерий | Проверка |
|---|---|---|
| AC-01 | Мандат после `POST /v1/mandates` — `PENDING_CONSENT`; после события НСПК — `ACTIVE` | Интеграционный тест на моке НСПК |
| AC-02 | По `ACTIVE`-мандату `fixed` регулярное списание создаётся ровно за каждый период с суммой, равной объявленной | Тест расписания на моке |
| AC-03 | По `ACTIVE`-мандату `variable` списание ≤ `maxAmount`; сумма задана ТСП заранее (`POST …/charges`), без суммы списание не инициируется | Граничные тест-кейсы + тест fail-closed |
| AC-04 | Регулярное списание проходит путь `CREATED → PAID → CREDITED → COMPLETED` (без QR-стадии) и видно в `GET /v1/payments/{paymentId}` с `paymentType=recurring`, `mandateId`, `periodKey` | Интеграционный тест |
| AC-05 | ТСП получает вебхук `payment.completed` по списанию и `mandate.activated`/`mandate.revoked` по мандату (дедуп по `eventId`) | Тест вебхуков |
| AC-06 | Отзыв мандата (`POST …/revoke` или событие НСПК) блокирует новые списания | Интеграционный тест |

### Негативные (обязательны)

| ID | Критерий | Проверка |
|---|---|---|
| AC-07 | Списание по мандату не в `ACTIVE` (`PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`EXPIRED`) — отказ (`MANDATE_NOT_ACTIVE`/`MANDATE_REVOKED`), **финансового движения нет** | Негативный тест |
| AC-08 | Повторная инициация за тот же `(mandateId, periodKey)` (рестарт, гонка двух экземпляров, повтор события) → **один** объект списания; **более одной зачисленной попытки за период быть не может** | Тест идемпотентности + fitness AD-011 |
| AC-09 | Отзыв мандата в окне инициации: новые списания не создаются; уже подтверждённые НСПК доводятся, спорные — через возврат | Тест гонки «отзыв ↔ инициация» |
| AC-10 | Списание выше `maxAmount` (`variable`) — отказ (`MANDATE_LIMIT_EXCEEDED`), финансового движения нет | Граничный негативный тест |
| AC-11 | Недоступность АБС/ОПКЦ при списании: платёж остаётся в согласованном состоянии; после восстановления сверка гарантирует исход; двойных зачислений 0 | Chaos-тест + сверка |
| AC-12 | Зачисление по регулярному списанию невозможно из `CREATED`/`QR_ISSUED` — только из `PAID` | Fitness AD-005 (расширение существующего теста) |
| AC-13 | Catch-up после простоя инициатора: пропущенных активных периодов 0, не более одного списания на просроченный период | Chaos-тест (остановка на N периодов) |
| AC-14 | **Обратная совместимость:** регресс-набор потребителя v0.1 проходит против схемы v0.2; в `Payment.status` новых значений нет | Contract-test + schema diff |
| AC-15 | Каждый переход мандата и каждое списание — в неизменяемом аудите; доказательство согласия восстановимо | ИБ-аудит |

### Восстановление и эксплуатация

| ID | Критерий | Проверка |
|---|---|---|
| AC-16 | RPO = 0 по мандатам и списаниям; RTO ≤ 1 ч | Тест отключения ноды, DR-учения |
| AC-17 | Сверка мандатов с НСПК находит и разрешает расхождение «у нас `ACTIVE`, у НСПК отозван» | Тест сверки на моке |
| AC-18 | Алерты инициатора (лаг, DLQ, дуннинг) срабатывают по порогам | Проверка мониторинга |
| AC-19 | **Совместимость:** contract-test прогоняется против зафиксированного артефакта-эталона v0.1 (сохранённый `openapi/tsp-api.yaml`@v0.1.0) и проходит; строгие потребители (`additionalProperties:false`) не ломаются | Contract-test с pinned baseline |
| AC-20 | Ручные операции по мандатам (снятие `SUSPENDED`, ручные переключения) — только через привилегированный контур с 4-eyes; прямой «обход» уникального ключа невозможен | RBAC-проверка + негативный тест |
| AC-21 | ПДн плательщика: инвентаризация состава, правовое основание, шифрование, маскирование в логах; операции по подпискам передаются в AML по порогам | ИБ/DPO-ревью + тест-кейсы AML |

## 2. Критерий успешной приёмки

Изменение считается принятым, когда на гейте A4 **все AC-01..AC-21 зелёные**, негативные сценарии AC-07..AC-13 воспроизведены и пройдены, contract-test AC-14/AC-19 подтверждает совместимость, а ИБ-аудит AC-15/AC-17/AC-21 не выявил блокеров. NFR-цели §7 `docs/nfr.md` подтверждены нагрузочными/chaos-тестами на моках (реальная проверка — на тестовом контуре НСПК после получения доступа).

## 3. План отката

### 3.1 До боевой эксплуатации — откат = не включать

Функция скрыта за **фиче-флагом**; транспорт mandate-протокола не реализуется (до контракта с вендором и документации НСПК). Откат бесплатен, миграции данных нет, все работы обратимы (согласуется с ADR-008: `reversible` до включения).

### 3.2 После включения — stop-new и деградация

Принцип: **остановить новое, довести начатое, не потерять обязательства.**

| Шаг | Действие |
|---|---|
| 1. Остановить новое | Запретить создание новых мандатов и новых регулярных списаний (пауза инициатора; `stop-new` на `POST /v1/mandates`) |
| 2. Довести начатое | Продолжить обработку уже открытых списаний (зачисление по `PAID`, вебхуки, сверка) — «открытые» деньги не бросаются |
| 3. Honouring обязательств | Продолжить обработку отзывов плательщика и уведомлений по действующим мандатам (регуляторно обязательно) |
| 4. Откат релиза | Rolling-откат версии ядра; **данные мандатов и доказательства согласия из шлюза не удаляются** в рамках отката (удаление не входит в процедуру; срок регуляторного хранения — `[ТРЕБУЕТ ПРОВЕРКИ]`) |
| 5. Общение | Уведомить ТСП о приостановке; зафиксировать инцидент и решение в аудите |

### 3.3 Сигналы-триггеры отката

- Двойные списания за период **> 0** (нарушение AD-011).
- Списание по не-`ACTIVE` мандату или списание выше лимита (нарушение AD-009).
- Массовые жалобы плательщиков / регуляторный запрос по подпискам.
- Расхождения сверки мандатов (в т.ч. продолжение списаний после отзыва) **> 0**.
- Отказ АБС/НСПК, из-за которого регулярные зачисления выходят за SLA, не компенсируясь сверкой.

### 3.4 Владелец решения об откате

Решение об **остановке новых списаний** — **совместное решение** **дежурного SRE/платёжного мониторинга** (немедленно при критичном сигнале) с информированием **человека-архитектора и продукта**; решение о **свёртывании функции** (прекращение новых мандатов) — **архитектор + продукт + ИБ/комплаенс** (при регуляторном сигнале — с обязательным участием комплаенса).

### 3.5 Критерий успешного отката

Откат считается успешным, если: (1) новые списания прекращены и подтверждены метрикой «инициаций = 0»; (2) все начатые списания доведены до терминального состояния либо переведены в отчёт незавершённых операций; (3) обязательства по действующим мандатам (отзыв, уведомления) продолжают исполняться; (4) отчёт сверки показывает 0 расхождений по завершённым операциям; (5) инцидент и решение задокументированы в аудите.

### 3.6 Обратимость и её границы

Откат **функции** (новых списаний) технически прост; откат **обязательств** — невозможен: согласия плательщиков и движения средств регуляторно значимы. Поэтому дешёвый откат = не включить функцию; аварийный режим = stop-new с сохранением обязательств (см. ADR-008, Reversibility).
