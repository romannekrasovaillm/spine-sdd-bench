# 03. Архитектурное решение: альтернативы, последствия, обратимость

Формулировка решения для A3. Канонические записи — `docs/adr/ADR-008..010`; инварианты — `ARCHITECTURE-SPINE.md` (`AD-009..AD-012`).

## 1. Решение

**Подписки СБП реализуются в ядре шлюза как «мандат плательщика + инициатор регулярных списаний», при этом регулярное списание — обычный платёж в уже принятой статусной машине.**

1. **Мандат плательщика** — отдельная сущность ядра со своей статусной машиной (`PENDING_CONSENT → ACTIVE → SUSPENDED | REVOKED | EXPIRED`), лимитами, неизменяемым аудитом согласия. Регулярное списание возможно только при `ACTIVE`.
2. **Расписание и инициация — в ядре шлюза** (компонент «инициатор регулярных списаний»): банк владеет расписанием подписки и сам инициирует каждое списание.
3. **Инициатор не пишет финансовый статус** — он создаёт платёж `CREATED` через ту же статусную машину, что и API ТСП; зачисление — **только из подтверждённого НСПК `PAID`** (AD-005 без исключений).
4. **Не более одного успешного списания на период** — один объект списания на `(mandateId, periodKey)` с уникальным индексом; дуннинг — попытки внутри объекта (`attemptRef`), зачисленной может быть не более одной; catch-up после простоя не создаёт дублей.
5. **Протокол мандатов ОПКЦ — целиком в вендорском адаптере** (AD-004, AD-008); ядро оперирует нормализованными `mandateId`/`periodKey`.
6. **Модель мандата — обе:** `fixed` (сумма+период) и `variable` (сумма каждого списания задаётся ТСП заранее для периода и ≤ `maxAmount`; без суммы списание не инициируется).
7. **Контракт ТСП эволюционирует v0.1 → v0.2 строго аддитивно** (путь `/v1`, только новые пути/схемы и опциональные поля).

## 2. Ключевые развилки и рассмотренные альтернативы

### 2.1 Где живёт расписание (кто инициирует списание)

| Вариант | Вердикт | Почему |
|---|---|---|
| **Инициатор в ядре шлюза (расписание у банка)** | **Выбран** | Единый источник истины (AD-002), контроль регулярности/аудита/уведомлений, переиспользование машины и outbox |
| Расписание в НСПК/у вендора | Отклонён | Согласие и расписание вне источника истины шлюза; финансовая регулярность вне контроля банка; vendor lock-in; расходится с AD-008 |
| Планировщик — отдельный банковский сервис вне контура | Отклонён | Второй путь создания платежа мимо статусной машины; внешний сервис входит в платёжный контур (AD-001); идемпотентность расползается |
| Charge-on-demand (ТСП инициирует каждое списание) | Отклонён как основная модель; **в Deferred** | Банк не контролирует регулярность и дуннинг; слабее гарантии плательщику. Остаётся возможным расширением поверх того же мандата |
| Регулярность через повторные QR с действием клиента | Отклонён | Не решает задачу (остаётся текущая боль) |

### 2.2 Модель мандата

| Вариант | Вердикт | Почему |
|---|---|---|
| **Обе: `fixed` и `variable`** | **Выбран** | Покрывает и подписки (кинотеатр, связь), и автоплатежи (ЖКХ) одной моделью согласия и одним контрактом |
| Только `fixed` | Отклонён | Не покрывает переменные платежи (ЖКХ) — потребует второго пересмотра контракта |
| Только `variable` | Отклонён | Избыточен и рискован для классических подписок с фиксированной суммой |

### 2.3 Где живёт состояние мандата

| Вариант | Вердикт | Почему |
|---|---|---|
| **Агрегат «мандат» в ядре со своей статусной машиной** | **Выбран** | Доказуемое согласие, приоритетный отзыв, контроль лимитов, единая сверка |
| Флаг в записи платежа | Отклонён | Нет аудита и истории согласия; невозможно доказать отзыв; расхождение с НСПК не детектируется |
| Всегда спрашивать статус у НСПК | Отклонён | Зависимость каждого списания от синхронного вызова; отзыв с задержкой; при недоступности НСПК — списание вслепую |

### 2.4 Модель идемпотентности регулярного списания

| Вариант | Вердикт | Почему |
|---|---|---|
| **Детерминированный `(mandateId, periodKey)` + транзакция** | **Выбран** | Защита от дублей при гонке/рестарте; масштабирование без лидер-лока; «ровно одно списание на период» доказуемо |
| Единый инстанс-лидер инициатора | Отклонён | Single point of failure; при смене лидера возможны пропуск/дубль |
| Best-effort без persisted расписания | Отклонён | Потеря периода при рестарте — недопустимо для финансовой операции |

## 3. Последствия

### Положительные

- **Минимальное расширение ядра.** Регулярное списание переиспользует статусную машину, outbox, сверку и правило «зачисление только из `PAID`» — принятые инварианты работают без изменений.
- **Единый источник истины** о согласии и расписании — проще доказывать корректность регулятору и сверять с НСПК/АБС.
- **Защита плательщика** встроена: списание только при `ACTIVE`, контроль лимита, приоритетный отзыв, аудит согласия.
- **Адаптер остаётся заменяемым** (AD-004/AD-008); протокол мандатов не протекает в ядро.
- **Обратимо до включения** — фиче-флаг, отсутствие миграции данных.

### Отрицательные

- **Новый компонент и новый агрегат** — эксплуатационная и тестовая нагрузка (catch-up, мониторинг лага, DLQ, сверка мандатов).
- **Регуляторный контур** (согласие, уведомление, отзыв, retention доказательств) добавляет внешние согласования и требования к ПДн.
- **Расширение RFP** вендора под mandate-протокол — внешняя зависимость по срокам; при отсутствии поддержки — эскалация AD-008.
- **Цена ошибки выше**: списание без действия клиента требует особенно строгого контроля дедупликации, лимитов и отзыва.
- **Бизнес-политики** (дуннинг, catch-up, лимиты) должны быть приняты до реализации — иначе поведение определяется «по умолчанию».

## 4. Обратимость

| Аспект | Обратимость | Комментарий |
|---|---|---|
| Изменение в целом (ADR-008) | **costly** после включения, **reversible** до | До боевых списаний всё за фиче-флагом; после — действующие мандаты накладывают обязательства (honouring отзыва, зачисление начатых списаний), доказательства согласия хранятся регуляторно |
| Мандат (ADR-009, AD-009) | **reversible** (механика) / **irreversible** (регуляторный контур) | Каналы/очереди/retention заменяемы; права плательщика и хранение доказательств обязательны |
| Инициатор (ADR-010, AD-010/AD-011) | **reversible** | Планировщик, catch-up, дуннинг настраиваемы; отказ в пользу charge-on-demand возможен поверх того же мандата |
| Интеграция с АБС (ADR-005) | **costly** (наследуется) | Не меняется этим изменением |
| AD-005 «зачисление только из `PAID`» | **costly/unknown** (наследуется) | Не пересматривается; распространяется на подписки |

**Минимальный откат** — не включать функцию (до боевой эксплуатации). **Аварийный stop-new** — запрет новых мандатов и новых списаний при сохранении обработки уже открытых операций; детали и сигналы-триггеры — [`06-acceptance-and-rollback.md`](06-acceptance-and-rollback.md).

## 5. Что решено этим пакетом и что отложено

**Решено (в рамках A3):** модель подписок и владелец расписания; разделение «мандат / платёж»; правило «списание только при `ACTIVE`»; ключ идемпотентности `(mandateId, periodKey)`; аддитивная эволюция контракта; границы транспорта.

**Отложено (обосновано):**
- **charge-on-demand** (ТСП инициирует списание) — Deferred spine; расширяемо поверх мандата.
- **уведомление плательщика силами шлюза** — если это не функция НСПК/банка плательщика; ждёт документации НСПК.
- **бизнес-политики дуннинга/catch-up/лимитов** — решения человека, см. `07-human-decisions.md`.
