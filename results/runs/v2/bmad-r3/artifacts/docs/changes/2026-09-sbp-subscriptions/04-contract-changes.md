# 04. Изменения контрактов без поломки существующих потребителей

## 1. Принцип

**Строго аддитивная эволюция в существующей мажорной версии `/v1`.** Ничего не удаляется, не переименовывается и не становится обязательным; существующие типы и значения enum не расширяются. Потребитель v0.1 продолжает работать без изменений.

## 2. `openapi/tsp-api.yaml` (v0.1.0 → v0.2.0)

### 2.1 Добавлено (новое)

| Элемент | Тип | Назначение |
|---|---|---|
| `POST /v1/mandates` | новый путь | регистрация мандата (согласия) |
| `GET /v1/mandates/{mandateId}` | новый путь | статус мандата |
| `POST /v1/mandates/{mandateId}/revoke` | новый путь | отзыв мандата по инициативе ТСП |
| `GET /v1/mandates/{mandateId}/charges` | новый путь | список регулярных списаний по мандату |
| `MandateRequest`, `Mandate`, `ChargeRef` | новые схемы | модель мандата и ссылки на списание |
| `Payment.paymentType` | новое **опциональное** поле (`oneoff` \| `recurring`) | тип платежа; отсутствие = `oneoff` |
| `Payment.mandateId`, `Payment.periodKey` | новые **опциональные** поля | привязка регулярного списания к мандату и периоду |

### 2.2 Не изменено (гарантия совместимости v0.1)

| Элемент | Статус |
|---|---|
| `POST /v1/payments`, `GET /v1/payments/{paymentId}` | без изменений |
| `PaymentRequest`, обязательные поля | без изменений |
| `Payment.status` и его enum `[…]` | **значения не добавлены и не удалены** — терминальные/промежуточные статусы подписок те же, что у платежа |
| Обязательность любых существующих полей | без изменений |
| Заголовок `Idempotency-Key` | без изменений (добавлен как обязательный на новых `POST`) |
| Коды ошибок v0.1 | без изменений (только добавлены новые коды контура подписок) |

### 2.3 Влияние на существующих потребителей

| Потребитель | Влияние |
|---|---|
| ТСП, использующий только платежи/возвраты | **Нулевое.** Новые пути не вызываются; новые поля `Payment.*` — опциональные и по умолчанию означают прежнее поведение (`oneoff`) |
| Клиентские SDK, генерируемые по схеме | **Обратимо совместимо**: новые опциональные поля и новые пути/Schemas; регенерация не ломает вызовы |
| Подписчики вебхуков | **Обратимо совместимо**: новые типы событий `mandate.*`; существующие `payment.*` не меняются по структуре |
| Внутренние потребители (отчётность/аудит) | Читают БД ядра, не OpenAPI; изменение аддитивно |

## 3. Доказательство совместимости (что проверяется)

- **Contract-test v0.1:** прогон существующего набора запросов/ответов v0.1 против схемы v0.2 проходит без расхождений; эталон — **зафиксированный артефакт** `openapi/tsp-api.yaml`@v0.1.0 (хранится как baseline, AC-19), а не «текущая» схема.
- **Schema diff:** автоматический diff `openapi` не показывает `removed`/`modified` у существующих путей/полей/enum; только `added`.
- **Enum guard:** тест, запрещающий добавление значений в `Payment.status` (расширение подписок идёт через `paymentType`, а не через новые статусы).
- **Idempotency regression:** повторные `POST` v0.1 по-прежнему возвращают тот же ресурс 200/201 (`IDEMPOTENCY_CONFLICT` на другое тело) — поведение §2 не изменено.

## 4. Человекочитаемый контракт `docs/contracts/tsp-api.md` (v0.2)

Добавлено: §2 (натуральный ключ регулярного списания), §3.6 (мандаты и подписки), коды ошибок контура подписок в §4, события `mandate.*` в §5, явное утверждение аддитивности v0.1 → v0.2 в §6, новые открытые вопросы в §7. Существующие §1, §3.1–3.5, §4 (базовые коды) — без изменения семантики.

## 5. Внутренний контракт адаптера ОПКЦ `docs/contracts/opkc-adapter.md`

**Семантическая версия не поднимается отдельным мажором** (это внутренняя граница ядро ↔ вендор), изменения — аддитивные, но **расширяют требования RFP**:

- Синхронные операции: `registerMandate`, `getMandateStatus`, `revokeMandate`, `createRecurringDebit` (§3).
- События: `mandate.activated`, `mandate.revoked`, `mandate.suspended`, `mandate.expired` (§4).
- Идемпотентность `createRecurringDebit` по `reference = paymentId`, где `paymentId` детерминирован из `(mandateId, periodKey)` (§5).
- Требования к вендору/RFP: поддержка mandate-контура, нормализация статусов мандата, приоритетный отзыв (§8).
- Все протокольные детали НСПК по мандатам — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации; контракт описывает **нормализованный** вид и не фиксирует поля НСПК.

## 6. Совместимость и деприкейшн

- Политика §6 контракта не меняется: ломающие изменения — только `/v2` с поддержкой ≥ 6 мес.; добавление опциональных полей — совместимо.
- v0.2 не требует `/v2`: потребители v0.1 не затронуты.
- Если впоследствии понадобится charge-on-demand или изменение семантики статусов (не планируется) — это отдельная мажорная эволюция, вне этого изменения.

## 7. Гигиена обязательных полей новых схем

- `MandateRequest`: `tspId`, `mandateType`, `merchantOrderId` обязательны; `amount` обязателен при `fixed`, `maxAmount` — при `variable`. Валидация — на A1 (JSON Schema `if/then` или серверная проверка).
- `Mandate.status`: `PENDING_CONSENT | ACTIVE | SUSPENDED | REVOKED | EXPIRED`.
- `ChargeRef.status` повторяет `Payment.status` — единый источник статусов, без нового enum.
