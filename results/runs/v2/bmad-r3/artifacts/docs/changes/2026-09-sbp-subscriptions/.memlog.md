- (event) Запуск: Update-прогон bmad-architecture поверх принятого feature-spine (задача: рекуррентные C2B-списания по согласию плательщика — подписки СБП)
- (constraint) Наследуемые инварианты (binding, read-only): AD-001 изоляция платёжного контура; AD-002 единый источник истины (статусная машина + outbox в одной транзакции); AD-003 идемпотентность финансовых операций; AD-004 единственный адаптер ОПКЦ; AD-005 зачисление только из подтверждённого PAID; AD-006 trust-зоны; AD-007 НПС/КИИ/ПДн; AD-008 [ADOPTED] гибрид (ядро собственное, транспорт вендорский)
- (constraint) ADR-007/AD-008: транспортный адаптер вендорский, ядро контрактно-независимо; новые методы протокола НСПК (мандаты) обязаны уйти в адаптер, RFP-скоуп расширяется
- (direction) Изменение не пересматривает ядро (AD-001..008) и не переоткрывает ADR-001..007; проектируем новый домен (мандат) + новый компонент (инициатор) внутри существующего контура
- (decision) Выбор Roman: инициатор регулярных списаний — ядро шлюза по расписанию (банк владеет расписанием подписки); charge-on-demand ТСП отклонён как основная модель
- (decision) Выбор Roman: тип мандата — обе модели, fixed (фиксированная сумма+период) и variable (переменная сумма в пределах лимита согласия)
- (decision) AD-009: мандат плательщика — отдельная сущность/источник истины в ядре, своя статусная машина (PENDING_CONSENT→ACTIVE→SUSPENDED|REVOKED|EXPIRED), атомарные переходы + outbox + аудит; списание только при ACTIVE
- (decision) AD-010: регулярное списание создаётся только через существующую статусную машину платежа (инициатор не пишет финансовый статус сам); тип recurring, ссылка на mandateId; зачисление по-прежнему только из PAID (AD-005)
- (decision) AD-011: ровно одно списание на период — детерминированный periodKey + идемпотентность (mandateId, periodKey); catch-up после простоя в пределах политики; горизонтальное масштабирование без лидер-лока
- (decision) AD-012: согласие, уведомление и отзыв — доказательство согласия в неизменяемом аудите; каждое списание уведомляет плательщика по требованиям НПС/НСПК; отзыв обрабатывается приоритетно и блокирует новые списания
- (decision) Контракт ТСП: эволюция v0.1→v0.2 строго аддитивно (/v1 сохранён), только новые пути/схемы и опциональные поля; существующий enum Payment.status не расширяется
- (assumption) Точный протокол НСПК по мандатам/рекуррентным списаниям (поля, тайминги, требования к согласию и уведомлению) недоступен — все протокольные детали помечены [ТРЕБУЕТ ПРОВЕРКИ] и реализуются на моках
- (assumption) Уведомление плательщика о каждом списании может выполняться НСПК/банком плательщика, а не шлюзом эквайера — требует подтверждения у НСПК/комплаенса
- (question) Регуляторные сроки/период предварительного уведомления плательщика о списании и порядок отзыва (161-ФЗ/Положение ЦБ, правила НСПК) — ИБ/комплаенс/юристы
- (question) Бизнес-политики dunning: число ретраев и интервалы при неуспешном списании, грация/приостановка мандата, политика catch-up при простое, лимиты maxAmount
- (question) Расширение RFP/контракта вендора под mandate-протокол НСПК и подтверждение идемпотентности по reference — обязательное условие AD-008
- (event) Черновики решений зафиксированы; далее — ADR-008..010, правка spine (AD-009..012) и контрактов, изменение кода не выполняется
