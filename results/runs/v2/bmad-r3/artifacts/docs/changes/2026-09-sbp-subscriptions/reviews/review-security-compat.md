# Ревью: безопасность, ПДн/комплаенс и обратная совместимость API

- Линза: regulated-industry (банк / 161-ФЗ / 152-ФЗ / НСПК), compliance + backward-compatible API evolution.
- Дата: 2026-09-28. Ревизия состояния рабочего дерева (не коммит), относительно `HEAD`.
- Проверяемые артефакты: `ARCHITECTURE-SPINE.md` (AD-005, AD-007, AD-012), `docs/changes/2026-09-sbp-subscriptions/02,04,05,06,07`, `docs/adr/ADR-008..010`, `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`, `docs/spec/state-machine.md`, `docs/nfr.md`, `openapi/tsp-api.yaml`.

## Вердикт

**Условно пригодно: обратная совместимость API подтверждена и действительно аддитивна (Critical по BC нет), но пакет не готов к A1/A3 без устранения 1 Critical (противоречие «дуннинг ↔ ключ `(mandateId, periodKey)`») и блокирующих комплаенс-контролей (4-eyes для ручных операций по мандату, владелец уведомления плательщика, инвентарь/шифрование ПДн, покрытие AML регулярных списаний).**

### Доказательство аддитивности OpenAPI (п.1)

Сравнение `openapi/tsp-api.yaml` с `HEAD` (`git diff HEAD` / `git show HEAD:openapi/tsp-api.yaml`):

- Пути `POST /v1/payments` и `GET /v1/payments/{paymentId}` — **байт-в-байт без изменений**; удалённых/переименованных путей нет. Добавлены только `/v1/mandates`, `/v1/mandates/{mandateId}`, `/v1/mandates/{mandateId}/revoke`, `/v1/mandates/{mandateId}/charges`.
- `PaymentRequest.required: [amount, merchantOrderId]` и `Payment.required: [paymentId, amount, status]` — **не изменены**.
- `Payment.status.enum: [CREATED, QR_ISSUED, PAID, CREDITED, COMPLETED, FAILED, EXPIRED, REFUNDED]` — **идентичен** HEAD; новых значений нет. Новые enum (`Mandate.status`, `Payment.paymentType`, `mandateType`) — только на новых сущностях/полях.
- Новые поля `Payment.paymentType|mandateId|periodKey` — **опциональны** (отсутствуют в `required`). Новые схемы `MandateRequest`/`Mandate`/`ChargeRef` v0.1-потребителя не затрагивают.
- Итог: **non-additive изменений не обнаружено → Critical по BC отсутствует.**

## Findings

### Critical

#### C-1. Дуннинг-ретраи несовместимы с детерминированным ключом `(mandateId, periodKey)` и AD-011

- **Файлы/секции:**
  - `docs/adr/ADR-010-…-iniciatora-regulyarnyh-spisanij.md` §Decision 1 (уникальный индекс `(mandateId, periodKey)` «запрещает вторую запись за тот же период»), §Decision 3 (`reference = paymentId` либо `chargeKey`), §Decision 6 (дуннинг: «каждая попытка — **отдельная операция** с собственной идемпотентностью, но в рамках того же `periodKey`»).
  - `docs/contracts/opkc-adapter.md` §5 (`createRecurringDebit` идемпотентен по `reference = paymentId`; `paymentId` **детерминированно выводится из `(mandateId, periodKey)`**).
  - `docs/spec/state-machine.md` §8 (guard: «за `(mandateId, periodKey)` нет **начатого**/успешного списания»).
  - `ARCHITECTURE-SPINE.md` AD-011 («натуральный ключ идемпотентности списания — `(mandateId, periodKey)`»).
- **Сценарий отказа:** списание за период отклонено (например, недостаток средств → `REJECTED`). Дуннинг требует новой попытки, но: (а) `reference` детерминирован из периода, значит повтор вернёт **тот же** `REJECTED` и не создаст новую операцию в ОПКЦ; (б) уникальный индекс и guard «нет начатого списания» **запрещают** вторую запись за период. Либо дуннинг нереализуем в описанном виде, либо его реализуют с новым `reference`, что **ломает инвариант «ровно одно списание на период» (AD-011)** и открывает путь ко второму списанию и **второму зачислению без действия клиента** — ровно тот класс инцидента, который 161-ФЗ/защита плательщика и должен исключать.
- **Конкретный фикс:** ввести единую сущность `chargeKey = (mandateId, periodKey)`; явно зафиксировать, что неуспешная попытка **не освобождает** ключ периода; ввести идемпотентность уровня попытки `(chargeKey, attemptNo)`; определить, как из попытки выводится `reference` для ОПКЦ (тот же `reference` при retry-совместимой семантике НСПК **или** `reference = f(chargeKey, attemptNo)` с уникальностью шлюза по **успешно** зачисленному списанию); переформулировать ADR-010 §6 и opkc-adapter §5 согласованно; добавить AC: «N неуспешных попыток дуннинга в периоде → ровно одна строка `chargeKey`, ровно одно успешное зачисление, второе зачисление недостижимо».

### High

#### H-1. AC-14 не доказывает «non-breaking» и не автоматизируется

- **Файлы/секции:** `04-contract-changes.md` §3; `06-acceptance-and-rollback.md` AC-14.
- **Проблема:** критерий текстом проверяет только «в `Payment.status` новых значений нет» и не перечисляет остальные BC-инварианты (нет удалённых/переименованных путей; не изменены существующие `required`; все новые **request**-поля опциональны; нет добавлений в **любой** ранее существовавший enum). Baseline v0.1 не пиннится (доступен только через историю git, а не как опубликованный артефакт), а «регресс-набор потребителя v0.1» не имеет владельца/происхождения. Дополнительно: добавление **опциональных полей в ответ** ломает строгих потребителей с `additionalProperties: false` — критерий этого не покрывает. Сегодняшний diff аддитивен, но критерий не способен это сертифицировать в общем случае.
- **Конкретный фикс:** заменить AC-14 на единый автоматический гейт: (1) закоммитить frozen v0.1 (`openapi/baseline/tsp-api-v0.1.0.yaml`); (2) прогонять breaking-change-линтер OpenAPI (oasdiff/oasdiff-совместимый), падающий на: удалённых путях/операциях, изменении `required`, добавлении значений в ранее существовавшие enum, новых обязательных request-полях; (3) собрать strict-SDK по v0.1 и прогнать фикстуры запросов/ответов v0.1 против v0.2.

#### H-2. Для ручных операций по мандату не задан контроль 4-eyes

- **Файлы/секции:** `ARCHITECTURE-SPINE.md` AD-006 («4-eyes для ручных операций»); `docs/nfr.md` §5; `ADR-010` §Negative («нельзя обойти ручной операцией без 4-eyes»); `docs/spec/state-machine.md` §7.2 M4/M5 (`SUSPENDED→ACTIVE` — «бизнес-решение/восстановление»).
- **Проблема:** ручная реактивация (M5), ручная приостановка (M4) и ручное переопределение уникального ключа — это «включающие списания» операции. AD-006 требует 4-eyes, но ни статусная машина, ни список AC не задают субъекта, двухстороннее согласование или проверяемый критерий; AC-15 покрывает только аудит.
- **Конкретный фикс:** добавить в `state-machine.md` §7.2 guard для M4/M5 («требуется 4-eyes, аудит с двумя субъектами») и новый AC: ручные suspend/reactivate без двух согласований отклоняются; каждая ручная операция пишет аудит с двумя субъектами. Комплаенс не примет инвариант, заявленный только прозой.

#### H-3. Владелец уведомления плательщика не определён, тогда как AD-012/NFR заявляют обязательный контроль «100 %»

- **Файлы/секции:** `ARCHITECTURE-SPINE.md` AD-012 и `Deferred`; `02-impact-on-architecture.md` §2.1 (AD-007 «усилен»); `05-nfr.md` §3/§4 («100 % списаний в регламентный срок `[ТРЕБУЕТ ПРОВЕРКИ]`»); `07-human-decisions.md` §2.
- **Проблема:** AD-012 объявляет уведомление о каждом списании обязательным, NFR делает его измеримым (100 %), но **исполнитель (шлюз vs НСПК/банк плательщика) не выбран**, AC-заглушки нет. Отложено корректно, но формулировка «AD-007 усилен» опережает решение.
- **Конкретный фикс:** пометить требование AD-012 как **блокирующее/условное** до разъяснения НСПК; завести AC-заглушку (доказательство уведомления по каждому списанию **либо** подтверждённый источник, что уведомляет НСПК/банк плательщика) и владельца комплаенс-подписи; не заявлять «усилен» до фиксации исполнителя.

#### H-4. ПДн плательщика: нет инвентаря, правового основания и проверяемого контроля минимизации/шифрования

- **Файлы/секции:** `ADR-009` §Decision 7 («ПДн плательщика (идентификаторы для сверки) минимизируются и шифруются; в логах — маскирование»); `02 §4` (ADR-006 «расширяется на ПДн плательщика»); `docs/nfr.md` §5/§7; `07-human-decisions.md` §3.
- **Проблема:** **состав** ПДн плательщика не назван; нет правового основания/срока хранения (152-ФЗ), нет упоминания DPIA/уведомления РКН; нет AC на шифрование в покое и маскирование (AC-15 — только аудит). Хранилище доказательств согласия само является ПДн и подлежит классификации. Передача вопроса ИБ/DPO корректна, но пробел не оформлен как пункт A4-гейта с конкретной проверкой.
- **Конкретный фикс:** добавить раздел «инвентарь данных» (поля: хэш идентификатора плательщика, ссылка на согласие, контакты и т.п.), правовое основание и retention; добавить AC: ПДн маскируются в логах, шифруются в покое (проверяемо), в API/вебхуках нет сырых ПДн. Решение оставить в `07 §3`, но вынести конкретную проверку на гейт.

#### H-5. Покрытие регулярных списаний контролем AML/антифрод не заявлено

- **Файлы/секции:** `ARCHITECTURE-SPINE.md` AD-007 (binds «интеграция с антифрод/AML»); `02 §4`; `docs/nfr.md` §5 («AML — передача операций по порогам — 100 %»).
- **Проблема:** нигде не сказано, что регулярное списание наследует те же AML/антифрод-контроли, что и разовый платёж (поперечно и/или по мандату). Для списаний без действия клиента, особенно `variable`, комплаенс потребует явного подтверждения.
- **Конкретный фикс:** явно указать, что каждое регулярное списание подлежит тем же порогам AML/антифрод, что и разовое (плюс агрегатная проверка по мандату для `variable`), и добавить AC.

### Medium

#### M-1. Несогласованность `qrType=recurring` (ADR/state-machine) vs `paymentType=recurring` (контракт/OpenAPI)

- **Файлы/секции:** `ADR-008` §Decision 3; `docs/spec/state-machine.md` §8 («с `qrType=recurring`»); `docs/contracts/tsp-api.md` §3.6 и `openapi` (`Payment.paymentType`); `docs/contracts/tsp-api.md` §3.2 (`qrType = dynamic|static|link`).
- **Проблема:** одно понятие названо двумя разными полями. На BC v0.1 не влияет, но создаёт риск, что реализатор добавит `recurring` в существующий request-enum `qrType` либо смоделирует два поля.
- **Фикс:** выбрать одно имя; в ADR-008/state-machine заменить на `paymentType=recurring`; если `paymentType` — только read-модель, указать, как инициатор его проставляет.

#### M-2. OpenAPI не кодирует условную обязательность `amount` (fixed) / `maxAmount` (variable) и не требует `period`

- **Файлы/секции:** `openapi/tsp-api.yaml` `MandateRequest`; `04-contract-changes.md` §7.
- **Проблема:** `period` — не required, хотя определяет подписку; контроль лимита `variable` (комплаенс-значимый guard) описан только серверно и не выражен в схеме. Допустимо, если закрывается на A1, но пакет подаёт схему как финальную.
- **Фикс:** выразить через `oneOf`/`if-then` (минимум — сделать `period` required); добавить AC на матрицу обязательных полей fixed/variable.

#### M-3. Триггеры отката частично не измеримы; нет учений по откату

- **Файлы/секции:** `06-acceptance-and-rollback.md` §3.3 («массовые жалобы», «регуляторный запрос»), §3.4, §3.5.
- **Проблема:** часть триггеров не количественная; критерий успеха измерим, но не тестируется; владелец — коллегиальный орган без единого ответственного и SLA эскалации.
- **Фикс:** квантифицировать частоту жалоб и порог расхождений сверки; назначить одного ответственного + SLA; добавить AC на учение stop-new (инициатор останавливается, открытые списания доводятся, отзывы/уведомления продолжаются).

#### M-4. Неизменяемость аудита заявлена, механизм не задан

- **Файлы/секции:** AD-007; `06` AC-15; `05-nfr.md` §4.
- **Проблема:** «неизменяемый аудит» без указания WORM/append-only/hash-chain, ролей чтения и управления ключами. Комплаенс запросит механизм и доказательство.
- **Фикс:** задать способ хранения (append-only/WORM, цепочка хэшей), роли доступа и процедуру выгрузки аудита как deliverable A4.

### Low

#### L-1. Формулировка о вебхуках неточна

- **Файлы/секции:** `04-contract-changes.md` §2.3 («существующие `payment.*` не меняются по структуре»); `docs/contracts/tsp-api.md` §5.
- **Проблема:** регулярные списания переиспользуют `payment.*` с добавленными `paymentType/mandateId/periodKey`, т.е. тело для recurring получает новые опциональные поля.
- **Фикс:** уточнить: «новые поля только для recurring-платежей; v0.1-потребитель их не видит, т.к. не имеет мандатов».

#### L-2. Происхождение baseline и semver

- Baseline v0.1 доступен только через git HEAD; version `0.1.0 → 0.2.0` без опубликованного тега контракта. Для партнёрского (ТСП) API baseline следует публиковать как версионированный артефакт. **Фикс:** опубликовать v0.1-артефакт и привязать semver к нему.

#### L-3. `consentUrl`, возвращаемый ТСП, может содержать токен/ПДн

- **Файлы/секции:** `openapi` `Mandate.consentUrl`; `docs/contracts/tsp-api.md` §3.6.
- **Проблема:** риск 152-ФЗ (минимизация), если URL встраивает ПДн/долгоживущий токен и передаётся ТСП. **Фикс:** зафиксировать требование «непрозрачный/короткоживущий URL без ПДн» и проверить тестом.

## Соответствие AD-005 (п.4) — детали

Проверены все вхождения формулировок о зачислении. Зачисление «только из `PAID`» повторено без исключений в: `ARCHITECTURE-SPINE.md` AD-005/AD-010; `ADR-008` §Decision 3; `docs/spec/state-machine.md` §3 и §8 («AD-005, без исключений»); `docs/contracts/tsp-api.md` §3.6; `02 §3`; `03 §1.3`; `README.md` изменения. **Формулировок, допускающих иное зачисление для подписок, не найдено.** Оговорка: контракт дуннинга (ADR-010 §6) противоречит AD-011 (см. C-1) и косвенно создаёт теоретический путь ко второму зачислению за период — это дефект AD-011/дуннинга, а не ослабление AD-005, но устранить следует до A1.

## Согласованность отката с ADR (п.5) — детали

`06 §3.3–3.6` даёт триггеры, владельца (SRE + архитектор/продукт/ИБ) и измеримый критерий («инициаций = 0», 0 расхождений, доведение до терминальных состояний, сохранение обязательств). Это согласуется с заявленной обратимостью (`ADR-008` costly после включения / reversible до; `ADR-009` reversible-механика / irreversible-регуляторный контур; `ADR-010` reversible; `03 §4`). Пробелы — в M-3 (неизмеримые триггеры, отсутствие учений), не в противоречии с ADR.
