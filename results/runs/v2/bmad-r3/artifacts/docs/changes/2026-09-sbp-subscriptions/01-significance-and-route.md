# 01. Оценка значимости изменения и маршрута

## 1. Что именно меняется

Добавляется **новый бизнес-сценарий**: рекуррентные C2B-списания по согласию плательщика (подписки СБП). Сегодня каждый платёж требует QR и действия клиента; после изменения шлюз сам инициирует списания по расписанию против оформленного мандата. Наличие mandate-механизма в протоколе ОПКЦ — внешнее допущение `[ТРЕБУЕТ ПРОВЕРКИ]` (см. ADR-008, Context).

Архитектурно это:
- новый **домен** (мандат плательщика — согласие, лимиты, отзыв);
- новый **компонент** в платёжном контуре (инициатор регулярных списаний);
- новые **методы и события** внешнего протокола (мандаты ОПКЦ) — внутрь вендорского транспортного адаптера;
- аддитивное **расширение контракта ТСП** (v0.1 → v0.2).

## 2. Оценка значимости (изменение, 0–3 по каждому критерию)

Методика: те же оси значимости, что зафиксированы для принятого решения в контексте ADR-007 (новый компонент, внешняя интеграция, финансовое влияние, КИИ/регуляторика), плюс ось «пересмотр принятой архитектуры». Банковскую официальную рубрику следует подтвердить у владельца метода; здесь — прозрачная и воспроизводимая оценка.

| # | Критерий | Оценка | Обоснование |
|---|---|---|---|
| 1 | Денежное влияние и необратимость | **3** | Списание идёт **без действия клиента** и повторяется; ошибка = массовые неверные списания и возвраты, обязанности перед плательщиком сохраняются после сбоя |
| 2 | Новый внешний интерфейс / протокол | **2** | Новые методы протокола НСПК (мандаты, регулярные списания), но **в рамках уже согласованного канала и адаптера** — не новый транспорт и не новый контрагент |
| 3 | Регуляторика / ПДн / НПС | **3** | Согласие плательщика (152-ФЗ, 161-ФЗ), уведомление о каждом списании, право и порядок отзыва, хранение доказательств согласия |
| 4 | Новый компонент / сущность / данные | **2** | Новый агрегат «мандат» и новый компонент «инициатор» — внутри существующего контура, переиспользуют БД/outbox/сверку |
| 5 | Пересмотр принятой архитектуры / инвариантов | **1** | Инварианты AD-001..008 и ADR-001..007 **не пересматриваются**; добавляются новые AD-009..012, ядро переиспользуется |
| | **Итого** | **11 / 15** | |

**Маршрут: Critical.** Изменение само по себе набирает порог критичности (доминируют денежное влияние и регуляторика). Понижение маршрута (Standard/Light) отклонено: списание без действия клиента и внешний протокол мандатов исключают «лёгкое» проектирование.

## 3. Насколько глубокое проектирование нужно и почему

**Нужно полное проектирование нового домена — но не перепроектирование ядра.**

Почему глубина обязательна:
- **Финансовая необратимость.** Один корректный инвариант («ровно одно списание на период», «списание только при `ACTIVE`») нельзя «дописать потом» — цена ошибки измеряется реальными списаниями плательщиков и регуляторными последствиями.
- **Регуляторный контур.** Согласие, уведомление, отзыв — обязательные свойства, а не улучшения; их нельзя отложить.
- **Внешняя неопределённость.** Протокол мандатов НСПК — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; архитектура обязана изолировать его (адаптер), иначе изменение нельзя начать безопасно.

Почему глубина ограничена:
- **Ядро переиспользуется.** Регулярное списание — обычный платёж; AD-002/AD-003/AD-005 действуют без изменений. Это снижает риск и объём.
- **Нет новых trust-зон, каналов и систем-контрагентов.** Trust-зоны, СКЗИ, АБС-интеграция, сверка не меняются.
- **Нет миграции существующих данных** — изменение аддитивное.

**Уровень проектирования:** расширение feature-spine (новые инварианты) + 3 ADR + контракты v0.2 + NFR + приёмка/откат. Это ровно тот объём, который нужен, чтобы (а) вынести на A3 и (б) передать исполнителям без архитектурных изобретений.

## 4. Маршрут и гейты

| Гейт | Применимость и содержание |
|---|---|
| **A0 (readiness)** | Пакет изменения готов: новые ADR заполнены, spine дополнен `AD-009..012`, gaps зафиксированы. |
| **A1 (Spec)** | Контракт ТСП **v0.2** и статусная машина мандата финализируются; контракт адаптера ОПКЦ дополняется методами мандатов; RFP-скоуп расширяется. |
| **A2 (Plan)** | Разбивка на задачи; walking skeleton расширяется сквозным сценарием: ТСП → мандат → мок НСПК (активация) → мок АБС → регулярное списание → вебхук. |
| **A3 (решение человека)** | **Обязателен до реализации**: утверждение ADR-008..010 и `AD-009..012`; маршрут Critical. Точка принятия — см. [`07-human-decisions.md`](07-human-decisions.md). |
| **A4 (conformance)** | Fitness-тесты новых инвариантов (`AD-009..012`), негативные сценарии (дубль периода, отзыв в окне списания, лимит `variable`), нагрузочные тесты NFR §7, ИБ-аудит (ПДн/аудит согласия). |
| **A5 (post-deploy drift)** | Сверка мандатов с НСПК, SLO-отчёт, контроль дрейфа от spine через 30 дней после включения. |

Дополнительно к плану гейтов исходного решения: **расширение RFP/POC** вендора под mandate-протокол (обязательное условие AD-008) — см. [`07-human-decisions.md`](07-human-decisions.md).

## 5. Вывод

- Значимость изменения — **Critical (11/15)**; маршрут не понижается.
- Проектирование — **полное для нового домена, без пересмотра ядра**.
- Реализация не начинается до **A3** и до подтверждённого доступа к протоколу мандатов НСПК (иначе — только моки).
