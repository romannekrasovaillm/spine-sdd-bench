# Adversarial review — подписки СБП: единицы, совместимые с инвариантами, но несовместимые друг с другом

- Reviewer: adversarial architecture reviewer (lens «две единицы уровня ниже»)
- Date: 2026-09-28
- Область: `ARCHITECTURE-SPINE.md` (AD-009..AD-012 + AD-001..AD-008), `docs/adr/ADR-008..010`, `docs/spec/state-machine.md` (§7, §8), `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`, `docs/changes/2026-09-sbp-subscriptions/*`
- Метод: для каждой дыры построены две единицы, каждая из которых выполняет **букву** перечисленных инвариантов, но принимает другое решение по неспецифицированному вопросу; показана наблюдаемая дивергенция в деньгах/состоянии.

## Verdict

**Не готово к A3 как «достаточно однозначное для двух команд».** AD-009..AD-012 фиксируют «кто владеет» (мандат, инициатор, ядро), но не фиксируют **разделяемые формы данных** (переходы, поля, ключи, время отсечения) и **разрешение конфликтов инвариантов**. Найдено 5 пар, расходящихся в деньгах (C1–C5), и 7 пар, расходящихся в состоянии/аудируемости (H1–H7). Три из них — прямые противоречия между документами пакета (C1, C2, M1), а не пробелы. Дополнительно: два инварианта (AD-009 «блокировать при отзыве» и AD-011/NFR «пропущенных периодов 0») не имеют заданного приоритета — на `UNKNOWN`/`SUSPENDED` они прямо подталкивают единицы в противоположные стороны (H2, H3).

## Critical

### C1. Для `recurring`-платежа нет легального пути в статусной машине (`CREATED → PAID` отсутствует)

**Единица A** (статусная машина/ядро) соблюдает `state-machine.md` §8 буквально: «инициатор создаёт его в `CREATED`, далее действуют переходы T2–T12 без изменений». Но `opkc-adapter.md` §3: `createRecurringDebit` возвращает `ACCEPTED`, **не `qrId`** → T2 (`CREATED → QR_ISSUED`, guard `qrId` непустой) недостижим; T4 (`QR_ISSUED → PAID`) недостижим; T5 (TTL) неприменим. Единственной идемпотентной реакцией на событие `payment.paid` для такого платежа нет правил → платёж остаётся в `CREATED`, зачисления нет, `payment.completed` не отправляется.

**Единица B** (тот же контракт + AD-005 «зачисление только из `PAID`») вынуждена ввести неявный переход `CREATED → PAID` по `payment.paid`, иначе регулярное зачисление физически недостижимо; это модификация таблицы §2, тогда как `02-impact-on-architecture.md` §3 декларирует «статусная машина §1–6 и переходы T1–T12 — **не** меняются», а `04-contract-changes.md` §2.2 — что `Payment.status` не расширяется.

**Дивергенция:** один и тот же сценарий даёт либо залипшие `CREATED`-платежи (ноль зачислений, AC-04 не проходит), либо неспецифицированный переход, который вторая единица не реализует (несовместимые consumer/state reads, разный результат fitness AD-005).

**Ужесточение (AD-010, одну строку в Rule + строку в §2/§4 status-machine):** явно объявить новый переход `T13: CREATED → PAID` по нормализованной нотификации `payment.paid` для `paymentType=recurring`, зафиксировать, что `QR_ISSUED` и T5 (`EXPIRED`) для `recurring` недостижимы, и добавить строку идемпотентности «`payment.paid` по `paymentId`/`eventId`». Без этого «T2–T12 без изменений» невыполнимо, и формулировка обязана быть изменена явно, а не «по умолчанию».

### C2. Уникальность `(mandateId, periodKey)` физически запрещает дуннинг (ADR-010 §6)

**Единица A** читает ADR-010 §1/§5 буквально: «уникальный индекс в БД ядра запрещает вторую запись за тот же период», «корректность обеспечивается уникальностью `(mandateId, periodKey)` и транзакционным созданием платежа» → в таблице платежей не может быть второй строки за период; а `FAILED` терминален (§3: «из них переходов нет») → после первой неуспешной попытки повтор невозможен, период «сгорает» под ключом, который уже занят.

**Единица B** реализует ADR-010 §6: «каждая попытка — отдельная операция с собственной идемпотентностью, но в рамках того же `periodKey`» → создаёт по платежу на попытку (естественно ключ `(mandateId, periodKey, attemptNo)`), что **нарушает AD-011** и AC-08 («ровно один платёж»).

**Дивергенция:** один и тот же мандат либо не имеет дуннинга вообще (нарушение ADR-010 §6 и бизнес-политики, падение сборов), либо имеет >1 платёж за период (нарушение AD-011, прямой триггер откатa по `06-acceptance-and-rollback.md` §3.3 «двойные списания > 0»). Обе единицы сослались на инвариант. Дополнительно: `ChargeRef` не имеет представления для неуспешной попытки, и `GET .../charges` не сможет её показать (AC «видимость неуспешных попыток» из `07-human-decisions.md` §7.5 нереализуем).

**Ужесточение (AD-011 + ADR-010 §1/§6):** развести два разных ключа явными словами: «уникальность `(mandateId, periodKey)` защищает от второго **успешного** списания; попытки (включая неуспешные) — отдельная сущность `chargeAttempt` с ключом `(mandateId, periodKey, attemptNo)`; переход в `PAID` возможен только из попытки, чей `attemptNo` минимален среди незавершённых, и не более одного `PAID` на период». Альтернатива — прямо запретить дуннинг в первой волне (тогда §6 ADR-010 удаляется, а не остаётся противоречием).

### C3. Источник суммы для `variable`-мандата не определён нигде

**Единица A** (инициатор): единственное известное ядру число — `maxAmount` (`tsp-api.md` §3.6, `openapi` `MandateRequest`); ADR-009 §3 требует лишь `amount ≤ maxAmount` → A списывает по `maxAmount` за каждый период.

**Единица B** (инициатор + контракт): читает «лимит `variable`-мандата нужно контролировать на стороне шлюза» (ADR-009 Context) как «сумму сообщает ТСП перед списанием» — и ждёт внешний сигнал суммы. Но в v0.2 нет ни пути, ни поля для этого: `MandateRequest` знает только `amount`/`maxAmount`, charge-on-demand вынесен в Deferred (ADR-008, spine Deferred), а `POST /v1/mandates` — единственный вход по мандату. B не инициирует списания по `variable` вовсе.

**Дивергенция:** для одного и того же ЖКХ-мандата — либо списание по потолку согласия (нарушение прав плательщика, регуляторный риск, жалобы), либо 0 списаний (функция не работает). AC-03 («списание ≤ `maxAmount`») **зелёный у обеих единиц**, AC-02 сформулирован только для `fixed` — набор приёмки эту дыру не ловит.

**Ужесточение (AD-009/AD-011 + `tsp-api.md`):** зафиксировать, что сумма списания `variable` — **входной факт** от ТСП: новый аддитивный путь `POST /v1/mandates/{mandateId}/charge-requests` (или поле `Charge.amount` в предзаявке) с `Idempotency-Key`, привязанный к `periodKey`; «нет суммы к моменту периода → отказ без финансового движения, период не закрывается успехом». Если это признано нежелательным — прямо вынести `variable` из первой волны в Deferred с указанием причины. Оставлять «лимит есть, суммы нет» нельзя: два compliant-инициатора дадут разные деньги.

### C4. Отзыв vs уже созданное, но не подтверждённое списание: disposition не определён и нет времени отсечения

**Единица A**: AD-009 «отзыв… немедленно блокирует **новые** списания»; ADR-009 §4 и `state-machine.md` §8: «уже **подтверждённые НСПК** списания доводятся, спорные — через возврат». Платёж в `CREATED`, не получивший `PAID`, — не «подтверждённый» → A обязан его остановить. Но легального способа нет: в §2/§3 нет перехода `CREATED → FAILED` по отзыву (T3 — ошибка ОПКЦ, T5 требует `QR_ISSUED`), отсутствует состояние «отменён», а `cancelPaymentLink` в контракте адаптера не отражён ни одним переходом. A вынуждена либо изобрести переход, либо **довести** списание.

**Единица B**: читает AD-010/AD-005 строго: платёж создан → идёт общим путём → любой подтверждённый НСПК `PAID` зачисляется (AD-005 не имеет исключений) → списание после отзыва состоится и будет зачислено; компенсация — отдельное решение ТСП через сагу. Это «соответствует» AD-005 и не нарушает ни одного AD.

**Дивергенция:** одна и та же последовательность «отзыв ↔ окно списания» даёт либо «списания нет», либо «деньги у ТСП». Ни AD, ни AC-09 не задают (i) что такое «уже подтверждённое» и (ii) по каким часам сравнивать: commit-время M6 в ядре или `revokedAt` от НСПК (при at-least-once доставке они расходятся на минуты, а именно в этом окне и происходит гонка). Дополнительно конфликт AD-005 (зачислить всё подтверждённое) vs AD-012 (списаний после отзыва нет) не разрешён: приоритет инвариантов не указан.

**Ужесточение (AD-009 + AD-012, по одной фразе в Rule):** (i) хранить на мандате `revokeCutoff = min(commitTime(M6), revokedAt из события)` — единственное сравнимое значение, доступное всем единицам; (ii) любой `recurring`-платёж, не достигший `PAID` до `revokeCutoff`, переводится в `FAILED` новым явным переходом `T14: CREATED|QR_ISSUED → FAILED (reason=mandate_revoked)` с вызовом `cancelPaymentLink`; (iii) доводятся только платежи с `paidAt < revokeCutoff`; (iv) если НСПК подтвердил списание после `revokeCutoff` — обязательное возмещение (сага T11/T12) по инициативе шлюза, а не по решению ТСП. Это же снимает конфликт AD-005/AD-012.

### C5. `paymentId`, «детерминированно выводимый из `(mandateId, periodKey)`»: не специфицирован и противоречит AD-010

**Единица A** (ядро/статусная машина): AD-010 §2 и T1 — «создаёт платёж… с новым `paymentId`»; `Idempotency-Key`/T1 порождают непрозрачный id; A генерирует случайный `paymentId` и хранит отображение «ключ `(mandateId, periodKey)` → `paymentId`».

**Единица B** (адаптер/контракт): `opkc-adapter.md` §5 и `04-contract-changes.md` §5 требуют обратного: «`paymentId` детерминированно выводится из `(mandateId, periodKey)`… повторная инициация гарантированно возвращает тот же результат». B закладывает конкретную деривацию (например, `pay_` + усечённый хэш) и требует её от ядра — иначе её собственный тест идемпотентности не воспроизводим.

**Дивергенция:** (1) **формат деривации не задан ни в одном AD** — вторая команда не может воспроизвести результат, требование неверифицируемо; (2) появляется **второй генератор одного и того же идентификатора** (T1 и деривация) — владелец `paymentId` не назначен, что нарушает саму идею AD-011 «естественный ключ проверяется в одной транзакции с созданием»; (3) деривированный `paymentId` становится вычислимым из `mandateId`+`periodKey`, которые ТСП видит в `GET /v1/mandates/{id}/charges` и `?periodKey=` → предсказуемый идентификатор в `GET /v1/payments/{paymentId}` (расширение IDOR-поверхности; проверка владения ТСП в AD не фигурирует); (4) гарантия «не создаёт второе списание в ОПКЦ» неверна как формулировка: её обеспечивает **стабильность `reference` при повторах одного и того же платежа**, а не выводимость id из календарного ключа.

**Ужесточение (AD-010 + правка opkc-adapter §5 и 04-contract-changes §5):** «`paymentId` — единственный генератор: сервис статусной машины; идентификатор непрозрачен, не выводится из ключей и не переиспользуется; идемпотентность `createRecurringDebit` гарантируется тем, что повтор/ретрай использует **тот же** `paymentId`; повторная инициация за период возвращает существующую запись по уникальному ключу `(mandateId, periodKey)`, а не пересчитывает id». Убрать слово «детерминированно выводится» из обоих документов.

## High

### H1. `periodKey`: календарь, таймзона, якорь и кламп конца месяца не определены

ADR-010 §1: «формат и календарь фиксируются с требованиями НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`»; `tsp-api.md` §7.6 — открытый вопрос. Единица A: якорь = дата активации мандата в Europe/Moscow, `periodKey = "2026-03-01"` (день месяца). Единица B (сверка/отчётность/фильтр `charges?periodKey=`): `periodKey = "2026-02"` (UTC-месяц).
**Дивергенция:** для мандата, активированного 31-го числа, списание 2026-02-28T21:30Z (= 2026-03-01 00:30 MSK) получает у A ключ марта, у B — февраля → уникальный индекс **не дедуплицирует** (двойное списание в одном реальном периоде) либо, при обратном сдвиге, **душит** новый период (пропуск, при этом AC-13/NFR требуют «пропущенных периодов 0»). ТСП, задавая `?periodKey=`, не может воспроизвести значение → фильтр списка списаний недетерминирован. `period: "P1M"` — ISO-duration **без якоря**: день месяца не задан, месячный период с 31-го в феврале не определён, DST/таймзона вообще не упомянуты (упомянуты только как «сложность» в ADR-010 Negative).
**Ужесточение (AD-011 Rule, 5 пунктов + golden-вектора):** (i) грамматика `periodKey` (например `YYYY-MM-<anchor>` либо `YYYY-MM`); (ii) фиксированная IANA-зона, не «локальная»; (iii) формула `periodIndex = floor((instant − activatedAt)/period)` в этой зоне; (iv) правило клампа конца месяца (31 → 28/29/30) и правила для активации в 23:30–00:30; (v) `periodKey` производит **исключительно** ядро, наружу — только строка; (vi) таблица тест-векторов в приёмку (граница месяца, активация 31-го, DST, повтор нотификации через границу). Пока этого нет — «ровно одно списание на период» недоказуемо, а `(mandateId, periodKey)` — не ключ, а договорённость.

### H2. Catch-up vs периоды, прошедшие в `SUSPENDED`: два «compliant» числа списаний

Единица A: `nextChargeAt` не двигается, пока мандат не `ACTIVE`; после M5 (восстановление) A видит N просроченных периодов и по AD-011/ADR-010 §4 («не более одного списания на просроченный период») делает **до N** списаний.
Единица B: читает ADR-009 Alternatives (вариант «Разрешить `SUSPENDED`-списания с догоном» **отклонён**) и AD-012 → периоды, прошедшие в `SUSPENDED`, считает «сгоревшими», расписание сдвигает.
**Дивергенция:** после одной и той же паузы дуннинга мандат получает 1 списание или «пачку» N — при этом A ссылается на AD-011, B — на отклонённую альтернативу ADR-009; приоритет не задан. Плюс AD-011 формулирует catch-up только «после простоя инициатора» (ADR-010 §4), а не после паузы по состоянию мандата — область применения правила не определена.
**Ужесточение (AD-011, одна фраза):** «catch-up применяется только к периодам, просроченным из-за недоступности инициатора; периоды, в которых мандат был не-`ACTIVE` (кроме краткого окна fail-closed по H3), не догоняются и не восстанавливаются; расписание сдвигается на первый период, начинающийся после восстановления». Правило — константа ядра, а не конфиг (иначе дивергенция по конфигурации двух сред).

### H3. Расхождение «наше состояние мандата vs НСПК»: кто авторитет и что делает единица (AD-009 vs AC-17)

Единица A (сверка): AD-009 «мандат — источник истины в ядре» + аналогия `state-machine §5` («у нас `PAID`, у НСПК нет → стоп-сигнал, эскалация») → на «у нас `ACTIVE`, у НСПК `REVOKED`» **только алертит**, состояние ядра не меняет; списания продолжаются до решения человека.
Единица B (сверка/мандат): AC-17 «сверка… **находит и разрешает** расхождение» → применяет внешний факт: M6 → `REVOKED` с аудитом/outbox.
**Дивергенция:** на одном и том же расхождении A продолжает списывать по отозванному согласию (регуляторное нарушение, прямо названное в `AD-009 Prevents`), B отзывает мандат «по данным сверки» — нарушая «ядро — источник истины» и требование M6-триггера. Ни один AD не даёт **fail-closed** правила на период неопределённости, хотя именно оно здесь критично. Сопутствующее: `getMandateStatus` возвращает `UNKNOWN`, а в статусной машине мандата такого состояния нет (Low→L-M5), и **AD-011/NFR («пропущенных периодов 0») прямо подталкивают продолжать списание, а AD-009 — блокировать**; приоритет инвариантов не указан.
**Ужесточение (AD-009, 3 пункта):** (i) **fail-closed**: «неизвестный/устаревший статус мандата (`UNKNOWN`, нет ответа, незавершённая сверка) блокирует создание новых платежей по мандату до подтверждения»; (ii) «период, пропущенный из-за fail-closed, подлежит догону по правилу одного списания (H2) — `UNKNOWN` не создаёт потерю периода» (снимает конфликт с AD-011); (iii) «подтверждённый внешний факт отзыва (событие или сверка) — единственный источник перехода M6; иных выводов `REVOKED` ядро не делает, но обязано исполнить M6 немедленно»; (iv) в AC-17 раскрыть «разрешает» = M6 + аудит + алерт, а не ручной разбор.

### H4. Дублирование мандатов: нет уникальности `(tspId, merchantOrderId)`

Единица A: `Idempotency-Key` хранится 24 часа (`tsp-api.md` §2) → повторный `POST /v1/mandates` с тем же `merchantOrderId` **после истечения ключа** (или с новым ключом) создаёт второй мандат; `merchantOrderId` обязателен в `MandateRequest`, но ключом не объявлен.
Единица B: считает `merchantOrderId` естественным ключом подписки и возвращает существующий мандат (200, не 201).
**Дивергенция:** две записи об одной подписке → **два списания за период на одном плательщике**, и AD-011 это не ловит, потому что ключ ограничен `mandateId`; AC-08 остаётся зелёным (внутри каждого мандата ровно один платёж). Обе единицы не нарушают ни одного AD.
**Ужесточение (AD-009 Rule + уникальный индекс БД мандатов + AC):** «мандат уникален в пределах (`tspId`, ключ подписки `merchantOrderId`); повторный `POST` с тем же ключом возвращает существующий мандат; смена ключа при действующем мандате — ошибка (`MANDATE_ALREADY_EXISTS`), а не второй мандат». Добавить fitness/AC «двойной мандат по одному ключу подписки = 0».

### H5. Владение расписанием: два писателя `nextChargeAt`

Единица A: расписание — часть агрегата мандата (ADR-009 знает `period`, лимиты, аудит; M-переходы двигают расписание).
Единица B: расписание — в компоненте инициатора (ADR-008 §2: «инициатор хранит расписание (`periodKey`/`nextChargeAt`)») и двигает его сам при инициации/дуннинге.
**Дивергенция:** две записи об одном факте расходятся после M4/M5/M6; при восстановлении один писатель считает период начатым, другой — нет (композиция с H2 даёт разное число списаний). Кто владелец — не сказано; `AD-002` («единый источник истины») формально соблюдён обеими единицами, потому что каждая владеет **своей** таблицей. Единица B не может гарантировать, что расписание не «отстало» от изменившегося периода мандата.
**Ужесточение (AD-009/AD-010, одна фраза):** «расписание — часть агрегата мандата (единственный писатель — переходы мандата и фиксация факта списания); инициатор — читатель расписания и писатель только `chargeAttempt`/платежа; `nextChargeAt` не хранится в двух таблицах и не вычисляется двумя формулами».

### H6. Уведомление плательщика (AD-012): и оба, и ни один; разделяемой формы нет

Единица A (нотификатор): AD-012 «каждое списание сопровождается уведомлением плательщика» + NFR §3 «100 % списаний уведомлены» → строит отправку уведомления по каждому списанию со своим учётом статуса уведомления.
Единица B (мандат/инициатор): spine `Deferred` + `[ТРЕБУЕТ ПРОВЕРКИ]` → уведомляет НСПК/банк плательщика, ядро не делает ничего.
**Дивергенция:** либо двойное уведомление плательщика (регуляторный шум, жалобы), либо пропуск уведомления при формально обязательной метрике. Метрику NFR §3 **не может измерить ни одна единица**: нет владельца, нет сущности/поля статуса уведомления. Единица A пишет `notifiedAt` в мандат, единица B — в платёж → AC-15 (ИБ-аудит) и сверка расходятся по составу; более того, сохранённое «доказательство согласия» (AD-012) и «доказательство уведомления» окажутся в разных агрегатах.
**Ужесточение (AD-012 — решение, а не Deferred):** выбрать и записать в AD: (i) «уведомление о каждом списании — обязанность шлюза; форма: `notificationState`/`notifiedAt` на попытке списания + outbox-событие `payer.notified`», либо (ii) «уведомление вне периметра шлюза» — и тогда **удалить метрику NFR §3** и указать владельца метрики у НСПК/банка плательщика. В обоих случаях: одно поле владения, один владелец метрики, одна сущность для аудита уведомления.

### H7. «Тем же сервисным путём, что и API ТСП» (AD-010): два пути создания платежа

Единица A: инициатор вызывает **публичный** сервис `POST /v1/payments` (HTTP), сам подставляя `Idempotency-Key` (ТСП его не выдаёт) и проходя ТСП-валидацию/авторизацию; при catch-up позже 24 ч (срок хранения ключа, `tsp-api.md` §2) пересчитанный ключ = новый запрос → второй платёж, если защита опирается на `Idempotency-Key`, а не на ключ БД.
Единица B: инициатор вызывает **внутренний доменный сервис** (тот же transaction boundary, что и T1), `Idempotency-Key` не участвует; переменная сумма/лимит проверяются внутренней валидацией.
**Дивергенция:** два пути создания платежа с разной семантикой идемпотентности, разной валидацией суммы/лимита и разным автором в аудите (см. M4); «единственный сервисный путь» AD-010 выполняется только у B, а AC-08 у A хрупок (зависит от чужого TTL-а).
**Ужесточение (AD-010 Rule, одна фраза):** «инициатор вызывает **внутренний** доменный сервис создания платежа, который является тем же сервисом, что обслуживает `POST /v1/payments`; публичный HTTP-путь и его `Idempotency-Key` не задействуются; идемпотентность — исключительно `(mandateId, periodKey)`; валидация суммы/лимита — общая функция для обоих входов».

## Medium

### M1. `qrType = recurring` (ADR-008 §3, state-machine §8) vs закрытый enum `qrType: dynamic|static|link` и «PaymentRequest без изменений»

Единица A расширяет `qrType` в **запросе** значением `recurring` (буква ADR-008 §3) → ломает аддитивность и `enum guard` (`04-contract-changes.md` §3, AC-14). Единица B вводит только `paymentType` в **ответе** (как описано в `04-contract-changes.md` §2.1) и внутренний тип → ADR-008 §3 не выполняется буквально.
**Дивергенция:** два разных признака «регулярности»; отчёты, фильтры и сверка используют разные поля; AC-14 проходит у B и падает у A (или наоборот, если A расширит другой enum). Противоречие внутри пакета.
**Ужесточение (AD-010 + правка ADR-008 §3 и status-machine §8):** «`paymentType=recurring` — единственный признак регулярного списания; `qrType` не расширяется и для `recurring` не используется».

### M2. TTL и `EXPIRED` для `recurring` не определены (T5 требует `QR_ISSUED`)

Единица A ставит таймер и переводит списание в `EXPIRED` (терминальное) → период закрыт успешно-неуспехом, повтор невозможен (уникальный ключ занят) → AC-13/NFR «пропущенных периодов 0» нарушено. Единица B TTL не ставит (QR нет) → платёж может залипнуть в `CREATED` неограниченно, что противоречит духу «залипших подписок нет» (`AD-011 Prevents`) и наблюдаемости (AC-18).
**Ужесточение (AD-011/AD-010):** «для `recurring` TTL и T5 не применяются; незавершённое списание разрешается только протокольным исходом (нотификация/сверка) с конечным SLA эскалации в отчёт незавершённых операций; `EXPIRED` для `recurring` недостижим».

### M3. Дуннинг и `SUSPENDED`: область счётчика попыток и отсутствие протокольного аналога `SUSPENDED`

Единица A считает исчерпание попыток внутри периода; единица B — накопленные неуспехи по мандату → разные моменты перехода M4. Дополнительно: M4 меняет состояние **локально**, а в контракте адаптера есть событие `mandate.suspended`, но **нет метода** `suspendMandate`/`updateMandate` → НСПК и ядро расходятся по `SUSPENDED` навсегда, при этом ADR-010 §7 и AC-17 требуют «расхождений 0» — цель недостижима по построению.
**Ужесточение (AD-009 + AD-004/opkc-adapter):** либо объявить `SUSPENDED` локальным состоянием ядра (и явно исключить его из сравнения в сверке/AC-17), либо добавить `suspendMandate` в контракт адаптера и RFP. Плюс определить scope счётчика попыток (мандат или период) в AD-010 §6.

### M4. Автор перехода в аудите (AD-007) для внутренних триггеров не определён

Единица A пишет `actor = "SYSTEM"`; единица B — `tspId` владельца мандата или `mandateId`. **Дивергенция:** два аудит-лога об одном финансовом переходе несовместимы по составу → ИБ-аудит (AC-15) не сходится, и невозможно доказать, что списание инициировано банком, а не ТСП (регуляторно значимо при разборе жалобы).
**Ужесточение (AD-007/AD-010):** закрепить поля аудита внутренних триггеров: `actorType: SYSTEM|TSP`, `actorId` (=`initiator`), `mandateId`, `periodKey`, `chargeAttemptNo`, `paymentId`.

### M5. Словарь идентификаторов и `UNKNOWN`: `mandateId` vs `mandateRef` vs `chargeKey`

ADR-008 §6: «ядро оперирует нормализованными **`mandateRef`/`chargeKey`**»; `02-impact-on-architecture.md` §2.2, AD-011 и `opkc-adapter.md` — «`mandateId`/`periodKey`», при этом в адаптере `mandateRef` — это **id ОПКЦ**, а `reference` — id ядра. Единица A делает ключом уникального индекса `mandateId` ядра (и хранит `mandateRef` атрибутом), единица B — читает ADR-008 §6 и делает ключом `mandateRef`.
**Дивергенция:** уникальность и сверка join’ятся по разным полям; при перерегистрации мандата в ОПКЦ (смена вендора, восстановление) ключи перестают совпадать. Плюс `UNKNOWN` из `getMandateStatus` отсутствует в статусной машине мандата → поведение на него не определено (усиливает H3).
**Ужесточение (AD-009, словарь):** `mandateId` — первичный ключ ядра; `mandateRef` — идентификатор ОПКЦ (атрибут, не ключ); `periodKey` — ключ периода; термин `chargeKey` запрещён/удалён. Плюс строка «`UNKNOWN` → fail-closed (H3)».

## Low

### L1. `period: "P1M"` — ISO-duration без якоря и без допустимых границ

Единица A принимает любые `P*` (включая `P0D`, `P30D`, `P1Y`), единица B — только `P1M|P1W|P1Y` и нормализует `P30D→P1M`. **Дивергенция:** один и тот же запрос ТСП валиден у одной и невалиден у другой; `P30D` vs `P1M` дают разные `periodKey` (композиция с H1). **Ужесточение:** зафиксировать закрытый набор и нормализацию в `MandateRequest` и в AD-011; убрать `[ТРЕБУЕТ ПРОВЕРКИ]` из «бизнес-решения» в «контрактную константу».

### L2. `ChargeRef` не описывает будущее и неуспех

`GET /v1/mandates/{id}/charges?periodKey=` не определяет: что отдаётся для ещё не наступившего периода, как выглядит неуспешная попытка (следствие C2), чем `scheduledAt` отличается от `paidAt` при catch-up. Две реализации дадут несовместимые ответы при одинаковой схеме. **Ужесточение:** дополнить `ChargeRef` (попытки/`attemptNo`/`failureReason`) и описать семантику фильтра в `tsp-api.md`.

### L3. Позднее событие мандата после терминального отзыва

Для платежа §3 фиксирует «`PAID` не может откатиться», для мандата аналогичного правила нет: поздний `mandate.activated` (at-least-once, «строгий порядок не гарантируется») после `mandate.revoked` формально применим к M2. Единица A игнорирует (REVOKED терминален), единица B применяет (M2 из `PENDING_CONSENT`; но если состояние уже `REVOKED` — переход не определён, поведение «на усмотрение»). **Ужесточение:** добавить инвариант мандата: «терминальный отзыв не отменяется никаким последующим событием, включая `mandate.activated`; такое событие → алерт, состояние не меняется».

### L4. `correlationRef` vs `reference` в одном контракте адаптера

§4 требует обязательное поле события `correlationRef`, далее таблица событий использует `reference` (= id ядра). Две единицы десериализуют по-разному; события мандата могут быть отброшены как невалидные. **Ужесточение:** одно имя (`reference`) во всём `opkc-adapter.md`; при необходимости различать — `reference (ядро)` и `mandateRef/операция (ОПКЦ)` явно разными именами.
