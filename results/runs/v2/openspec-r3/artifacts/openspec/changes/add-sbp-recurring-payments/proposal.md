# Proposal

## Why

ТСП из сегментов «онлайн-кинотеатры, ЖКХ, связь» не могут проводить повторные платежи без участия клиента: каждая оплата требует нового QR и подтверждения в приложении банка плательщика. Это рвёт подписочные сценарии (продления, регулярные взносы) и снижает удержание. Бизнес просит рекуррентные C2B-списания по согласию плательщика («подписки СБП») поверх уже принятого решения.

Изменение носит архитектурный характер, а не является локальной доработкой: оно расширяет **финансовую модель** (автоматические списания без действия клиента), требует новых операции протокола НСПК («автоплатёж» — внешний вход, `[ТРЕБУЕТ ПРОВЕРКИ]`) и новых мер по **согласию плательщика** (161-ФЗ/152-ФЗ). Поэтому оно требует ревью инвариантов spine, отдельного архитектурного решения и человеческого решения A3 до начала реализации транспортной части (в развитие ADR-007/AD-008).

## What Changes

- Вводится первоклассная сущность **«согласие плательщика» (mandate)** со своим жизненным циклом (`PENDING_CONSENT → ACTIVE → SUSPENDED/REVOKED/EXPIRED`), лимитами и сроком действия; НСПК — авторитетный источник подтверждения, шлюз хранит локальную проекцию и сверяет её.
- Добавляется **инициация рекуррентного списания** по активному согласию: списание исполняется **существующей** статусной машиной платежа (новый триггер + связь `mandateId`), зачисление — только из подтверждённого `PAID` (AD-005 не пересматривается).
- Добавляется **guard-политика согласия** в ядре: списание запрещено вне `ACTIVE`, сверх лимитов и после отзыва; отзыв согласия из НСПК немедленно блокирует последующие списания.
- **Контракт API ТСП расширяется аддитивно (не BREAKING)**: новые пути `/v1/mandates*`, опциональные поля в `Payment`, новые события вебхуков `mandate.*`, новые коды ошибок. Существующие поля, статусы и потребители не меняются.
- Расширяется **внутренний контракт адаптера ОПКЦ** (регистрация/отзыв согласия, инициирование списания) — в пределах AD-004/AD-008; протокольные детали получаются от НСПК.
- Добавляются **нотификации, сверка, аудит и наблюдаемость** для согласий и списаний.
- Предлагается новый spine-инвариант **AD-009** (списание только по активному согласию; отзыв необратим) и явная ревизия затронутых AD (AD-003, AD-005, AD-008).
- **BREAKING**: нет. Изменение только аддитивное; потребители версии `/v1` продолжают работать без доработок.

## Capabilities

### New Capabilities
- `sbp-recurring-payments`: согласие плательщика и рекуррентные C2B-списания по нему — жизненный цикл согласия, guard-политика (лимиты, отзыв), инициация и исполнение списаний, идемпотентность, уведомления, сверка и аддитивное (не BREAKING) расширение контракта ТСП.

## Impact

- **API ТСП** (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`): аддитивное расширение до v1.1 — новые пути, схемы, события, коды ошибок; ломающих изменений нет.
- **Контракт адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`): новые синхронные операции и события; требования к вендору и RFP.
- **Ядро шлюза**: модель данных `mandate`, политика лимитов/отзыва, новый триггер статусной машины, новые outbox-события и аудит.
- **АБС-интеграция**: контракт не меняется — рекуррентное списание переиспользует идемпотентное зачисление по `paymentId` (ADR-005).
- **НСПК / вендор транспорта**: новый протокол автоплатежей — внешний вход; возможна ревизия контракта с вендором (границы AD-008).
- **Принятые артефакты решения** (`ARCHITECTURE-SPINE.md`, `docs/adr/`, `docs/nfr.md`, `docs/spec/state-machine.md`): обновление только на этапе ратификации (A1/A3), в рамках настоящего planning-пакета не изменяются.
- **Регуляторика/ИБ**: правовое основание и хранение согласия, минимизация ПДн плательщика, неизменяемый аудит.
