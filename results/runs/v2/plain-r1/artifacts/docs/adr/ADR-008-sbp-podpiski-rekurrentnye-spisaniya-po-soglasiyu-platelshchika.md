# ADR-008. СБП-подписки: рекуррентные C2B-списания по согласию плательщика

- Date: 2026-09-28
- Status: Proposed (выносится на человеческое решение; пакет — `docs/changes/change-001-sbp-podpiski/`)
- Owner: solution-architect (платёжный контур) + владелец продукта
- Related: ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-007, AD-002, AD-003, AD-004, AD-005, AD-009 (новый), AD-010 (новый)

## Context

Бизнес-задача. ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** — «подписки СБП». Сейчас в принятом решении (ADR-001..007) каждый платёж инициируется плательщиком: ТСП регистрирует QR/ссылку, клиент сканирует и подтверждает оплату в своём банке. Для регулярных платежей это неприемлемо: клиент не должен совершать действие при каждом списании.

Что требуется от механизма:
- плательщик однократно оформляет **согласие** (mandate) на списания в пользу конкретного ТСП в приложении своего банка;
- ТСП **инициирует списания** по расписанию/по требованию в пределах согласия — без QR и без действия клиента;
- плательщик получает **обязательные уведомления** и может **отозвать согласие**; отзыв немедленно блокирует новые списания;
- сохраняются финансовые гарантии принятого решения: зачисление только по подтверждённому статусу, идемпотентность, отсутствие двойных списаний/зачислений, аудируемость.

Регуляторный и внешний контекст. Порядок работы рекуррентных списаний (регистрация согласия, расписание, обязательные нотификации плательщику, сроки отзыва, лимиты) определяется регламентом НСПК/Правилами ОПКЦ СБП. Точный протокол — **внешний вход**, публично не раскрыт; все протокольные и регламентные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации НСПК (аналогично ADR-003). Согласие и связанные данные плательщика попадают под 152-ФЗ; обязательность уведомлений и право отзыва — под требования НПС и правила ОПКЦ СБП (AD-007).

Силы: новый клиентский путь (доверие, отзыв согласия); финансовое последствие ошибки — **списание без действующего согласия** или двойное списание; внешний оператор не даёт «ровно один раз»; согласие — юридически значимое состояние, которое должно иметь локальный источник истины; ядро шлюза по ADR-007 — собственная разработка, транспорт — сертифицированный вендорский модуль.

## Decision

1. **Новый агрегат «Согласие плательщика» (Mandate) в БД шлюза** — первоклассная сущность со своей статусной машиной (`CREATED → PENDING_PAYER → ACTIVE → EXPIRED/REVOKED/REJECTED`; см. `docs/spec/mandate-debit-lifecycle.md`). Как и платёж (AD-002), Mandate — единственный источник истины для своего состояния; каждый переход — атомарная транзакция «смена статуса + outbox + аудит».
2. **Списание по подписке — это Платёж.** Рекуррентное списание моделируется как существующий платёж (ADR-002) с атрибутом `mandateId` и источником инициации «ТСП по согласию». Списание переиспользует жизненный цикл платежа `CREATED → PAID → CREDITED → COMPLETED` и терминальные состояния; шаг `QR_ISSUED` на пути списания отсутствует (вместо него — инициация списания в ОПКЦ). **AD-005 не ослабляется: зачисление в АБС по списанию возможно только из подтверждённого `PAID`.**
3. **Единственный адаптер ОПКЦ (AD-004) расширяется, а не дублируется.** Регистрация/активация/отзыв согласия и инициация/статус списания выполняются через тот же транспортный адаптер; внутренний контракт `docs/contracts/opkc-adapter.md` расширяется аддитивно (новые операции и события, помечены `[ТРЕБУЕТ ПРОВЕРКИ]`). Другие компоненты протокола НСПК не знают.
4. **Идемпотентность (AD-003) распространяется на новые ключи**: регистрация/отзыв согласия — по `Idempotency-Key`; инициация списания — по `Idempotency-Key` и бизнес-ключу периода (`mandateId` + `merchantOrderId`/`billingPeriod`); обработка нотификаций ОПКЦ по списанию — по `eventId`. Повтор любого триггера не создаёт второе списание/зачисление.
5. **Оркестратор списаний — durable, из outbox.** Планируемые списания планируются durable-планировщиком (не in-memory таймером) и запускаются из очереди; обработка «по требованию» инициируется API-вызовом ТСП. Оба пути ведут к одному и тому же переходу статусной машины.
6. **Обязательные нотификации плательщику.** Перед списанием плательщику направляется уведомление в срок по регламенту НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`; политика при недоставке уведомления — блокировать списание и алертить. Отзыв согласия обрабатывается и подтверждается; после отзыва новые списания невозможны.
7. **Ограничения согласия проверяются на ядре.** Сумма каждого списания и суммарный лимит за период проверяются против условий Mandate в состоянии `ACTIVE`; списание при `REVOKED`/`EXPIRED`/превышении лимита — недостижимо (AD-009).
8. **Раскатка — фиче-флагом на ТСП.** Функционал включается по ТСП (и/или сегменту) независимо; выключение флага запрещает новые списания, не затрагивая уже открытые операции (см. план отката).
9. **Комплаенс.** Согласие — юридически значимое состояние с аудируемой историей; персональные данные плательщика минимизируются (ADR-006); интеграция с антифрод/AML — по порогам, как для C2B (AD-007).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Вердикт |
|---------|-------|--------|---------|
| **A. Расширение ядра шлюза** (агрегат Mandate + оркестратор списаний + новые методы API, переиспользование платёжной статусной машины) | Единый источник истины для согласия и списания; переиспользование outbox/идемпотентности/сверки/АБС-интеграции; гарантия AD-005 сохраняется без нового механизма; нет второго контура | Расширяется самая нагруженная часть; планировщик и нотификации плательщика — новая сложность | **выбран** |
| **B. Отдельный сервис «Подписки»** с собственной БД и интеграцией с шлюзом через внутренний API/сагу | Изоляция; независимый релизный цикл | Второй источник истины по списаниям → ослабление AD-002/AD-005; кросс-сервисная сага «согласие↔списание↔АБС»; дублирование сверки и идемпотентности; сложнее аудит | отклонён |
| **C. Аутсорс подписок вендору/внешнему биллингу** | Быстрый старт для бизнеса | Финансовая логика и согласие вне платёжного контура банка → нарушение AD-001; фрагментация аудита для ЦБ; vendor lock-in; ТСП-данные у третьей стороны | отклонён |
| **D. Списание как обычный платёж без агрегата Mandate** (согласие хранится только на стороне НСПК) | Меньше изменений в БД | Нет локального источника истины о согласии → невозможно гарантировать проверку лимита/срока и мгновенный отзыв; нарушение AD-002; риск списания без действующего согласия | отклонён |

## Consequences

### Positive

- Новый источник регулярной выручки для банка-эквайера и ТСП; закрывает запрос онлайн-кинотеатров, ЖКХ, связи без ручного действия клиента на каждом платеже.
- Гарантии принятого решения сохраняются: списание проходит тот же контролируемый путь «подтверждённый статус → зачисление», идемпотентность и сверка переиспользуются.
- Согласие и его отзыв аудируемы; отзыв немедленно блокирует списания — управляемый регуляторный риск.
- Расширение аддитивно: путь разовых QR-платежей не меняется.

### Negative

- Новый агрегат, планировщик и логика обязательных нотификаций — рост сложности ядра и эксплуатационной нагрузки.
- Гонки и краевые случаи: отзыв согласия в момент списания, расхождение «списание подтверждено НСПК, но согласие уже отозвано», поздние нотификации — нужны саговые компенсации и runbook (возврат списанного).
- Новый внешний вход: протокол НСПК по подпискам `[ТРЕБУЕТ ПРОВЕРКИ]`; задержка до получения документации.
- Зависимость от вендора транспорта (ADR-007): вендор обязан реализовать новые операции/события — возможна доработка контракта/бюджета.
- Повышенное внимание регулятора и бизнеса: обязательные уведомления, право отзыва, возможные претензии плательщиков (диспуты — см. Deferred в spine).

## Reversibility

**reversible.** Изменение аддитивно: новые сущности/методы/события не изменяют путь разового C2B-платежа. Функционал включается фиче-флагом на ТСП; отключение флага прекращает новые списания без обратной миграции данных. Уже оформленные согласия и история списаний сохраняются для аудита и сверки. Единственная внешняя зависимость — поддержка подписок вендорским адаптером ОПКЦ (расширение контракта, а не смена ядра).
