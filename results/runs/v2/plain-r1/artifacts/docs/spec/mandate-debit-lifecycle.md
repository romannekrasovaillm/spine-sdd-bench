# Статусная модель согласия и списания по подписке — спецификация переходов

- Status: Draft (для ревью на гейте решения CHANGE-001)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-004, ADR-005, AD-002, AD-003, AD-005, AD-009, AD-010

Дополняет `docs/spec/state-machine.md` (разовые платежи). Правила неизменны: **каждый переход — атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002); повторные триггеры идемпотентны (AD-003); **зачисление в АБС — только из подтверждённого `PAID`** (AD-005).

Протокольные значения (тайминги, типы статусов НСПК, сроки нотификаций и отзыва) — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения регламента НСПК; ниже — нормализованная модель.

## 1. Агрегат «Согласие плательщика» (Mandate)

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Согласие зарегистрировано в шлюзе, запрос в ОПКЦ в процессе | да |
| `PENDING_PAYER` | Ожидается подтверждение/оформление согласия плательщиком (в приложении банка плательщика) | да |
| `ACTIVE` | Согласие действует: списания разрешены в пределах срока и лимита | да |
| `REJECTED` | Плательщик/ОПКЦ отклонил согласие | да |
| `EXPIRED` | Истёк срок действия согласия | да |
| `REVOKED` | Согласие отозвано (плательщиком/ТСП/банком); списания невозможны | да |

Терминальные: `REJECTED`, `EXPIRED`, `REVOKED`.

### 1.1 Переходы Mandate

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` (Idempotency-Key) | ТСП активен, условия валидны | запись Mandate + outbox «регистрация согласия в ОПКЦ» |
| M2 | `CREATED` | `PENDING_PAYER` | ОПКЦ принял регистрацию (ссылка/сценарий согласия передана плательщику) | ответ ОПКЦ успешен | сохранить ссылку/идентификатор ОПКЦ, outbox-вебхук ТСП |
| M3 | `CREATED` | `REJECTED` | ошибка регистрации в ОПКЦ | нетранзиентная ошибка | `errorCode`, вебхук ТСП |
| M4 | `PENDING_PAYER` | `ACTIVE` | событие ОПКЦ: согласие оформлено плательщиком | плательщик подтвердил | outbox-вебхук ТСП, разрешение списаний (AD-009) |
| M5 | `PENDING_PAYER` | `REJECTED` | плательщик отказался / ОПКЦ отклонил | — | `errorCode`, вебхук ТСП |
| M6 | `ACTIVE` | `EXPIRED` | истечение срока согласия | срок истёк | прекращение списаний, вебхук ТСП |
| M7 | `ACTIVE`/`PENDING_PAYER` | `REVOKED` | отзыв согласия (плательщик/ТСП/банк) | — | **немедленная блокировка новых списаний**, outbox, аудит, вебхук ТСП |
| M8 | `REVOKED`/`EXPIRED` | (остаётся) | повторный отзыв/истечение | — | идемпотентно, состояние не меняется |

Инварианты Mandate:
- Списание возможно **только** из `ACTIVE` (AD-009).
- `REVOKED`/`EXPIRED`/`REJECTED` — терминальные; перехода назад в `ACTIVE` нет (возобновление — только новое согласие).
- Условия согласия (лимит, период, получатель) иммутабельны после `ACTIVE`; изменение — новое согласие.
- Отзыв обрабатывается независимо от текущих списаний; списания «в полёте» — по компенсационному сценарию (§3).

## 2. Списание по подписке (Payment)

Списание — это Платёж (ADR-008). Использует состояния из `docs/spec/state-machine.md` (`CREATED → PAID → CREDITED → COMPLETED`, терминальные `FAILED`/`EXPIRED`/`REFUNDED`), **без шага `QR_ISSUED`**.

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| D1 | — | `CREATED` | `POST /v1/mandates/{mandateId}/debits` (Idempotency-Key) **или** durable-планировщик | Mandate=`ACTIVE`; сумма ≤ лимита; срок ок; обязательное уведомление плательщику доставлено | запись Payment(`mandateId`) + outbox «инициация списания в ОПКЦ» |
| D2 | `CREATED` | `PAID` | событие ОПКЦ `debit.paid` (или подтверждение сверкой) | **сумма/получатель совпадают**, Mandate был `ACTIVE` на момент списания | идемпотентно по `eventId`, outbox «зачисление в АБС» |
| D3 | `CREATED` | `FAILED` | ОПКЦ отклонил списание / исчерпаны ретраи | нетранзиентная ошибка | `errorCode`, вебхук ТСП |
| D4 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`) | вызов АБС идемпотентен по `paymentId` | сохранить `absDocId`, outbox |
| D5 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен/в очереди | — | outbox, аудит |
| D6 | `COMPLETED` | `REFUNDED` | сага возврата (ADR-005) завершена | полный возврат | outbox (в т.ч. случай отказа в списании/спора) |
| D7 | `CREATED` | `FAILED` | Mandate отозван/истёк **до** подтверждения ОПКЦ | — | списание не завершается; при необходимости — компенсация |
| D8 | `PAID`/`CREDITED`/`COMPLETED` | (не меняется без саги) | Mandate отозван **после** подтверждения списания | списание уже подтверждено | запись в отчёт расхождений; при требовании плательщика — возврат (D6) |

## 3. Краевые случаи и компенсации

| Сценарий | Поведение |
|---|---|
| Отзыв согласия в момент списания (гонка) | Проверка Mandate — в той же транзакции, что и переход D1; если отзыв зафиксирован раньше — D1 не выполняется. Если списание уже подтверждено ОПКЦ — фиксируется расхождение, инициируется возврат (D6) по требованию |
| Поздняя/повторная нотификация `debit.paid` | Дедупликация по `eventId`; повтор не меняет завершённое состояние (AD-003) |
| Двойной триггер списания (повтор API/планировщика) | Идемпотентность по `Idempotency-Key` и бизнес-ключу (`mandateId`+период): одно списание/одно зачисление |
| Списание сверх лимита/срока | D1 отклоняется до вызова ОПКЦ (AD-009); алерт при попытке |
| АБС недоступна при `PAID` | Payment остаётся `PAID`, ретраи, отчёт незавершённых операций; зачисление гарантируется сверкой (ADR-005) |
| Обязательное уведомление не доставлено | Списание блокируется/ретраится по политике (H7); алерт |

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | тот же `mandateId`, состояние не меняется |
| `POST /v1/mandates/{id}/revoke` | `Idempotency-Key` | идемпотентно; повторный отзыв — тот же результат |
| `POST /v1/mandates/{id}/debits` / планировщик | `Idempotency-Key` + `mandateId`+период | то же списание, повтор не создаёт второй Payment/зачисление |
| Нотификация ОПКЦ по списанию | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Подтверждение АБС | `paymentId` | повторное подтверждение не создаёт вторую проводку |

## 5. Сверка и восстановление

- Открытые Mandate (`PENDING_PAYER`) и открытые списания (`CREATED`, `PAID`, `ABS_PENDING`) — кандидаты сверки с ОПКЦ (ежечасная) и АБС (суточная).
- «У ОПКЦ согласие активно, у нас нет» / «у ОПКЦ списание подтверждено, у нас нет» → дозапрос статуса → соответствующий переход.
- «У нас `PAID`/`COMPLETED`, у ОПКЦ нет» → стоп-сигнал, эскалация.
- `REVOKED` Mandate со «зависшим» списанием → отчёт расхождений, компенсация/возврат.

## 6. Согласованность с API ТСП

Маппинг наружу: `Mandate.status` — значения из §1 (`CREATED`, `PENDING_PAYER`, `ACTIVE`, `REJECTED`, `EXPIRED`, `REVOKED`); `Payment.status` — без изменений (см. `openapi/tsp-api.yaml`). Технические подсостояния (`ABS_PENDING`, `NOTIFY_PENDING`) наружу не выставляются. Новые значения **не добавляются** в существующий enum `Payment.status` — списание использует уже существующие состояния.
