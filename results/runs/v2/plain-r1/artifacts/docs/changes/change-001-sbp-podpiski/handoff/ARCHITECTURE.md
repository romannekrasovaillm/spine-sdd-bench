# Архитектурный контекст (epic-context) — CHANGE-001 «СБП-подписки»

Собран: 2026-09-28. Источники: `docs/adr/ADR-008-...md`, `ARCHITECTURE-SPINE.md`, `docs/contracts/tsp-api.md`, `docs/contracts/opkc-adapter.md`, `docs/spec/mandate-debit-lifecycle.md`, `docs/nfr.md` §7, `docs/changes/change-001-sbp-podpiski/acceptance-and-rollback.md`.

> Статус: пакет активируется после ратификации ADR-008 (гейт H1) и получения регламента НСПК (H2). До этого — не передавать в реализацию.

## Цель

Добавить к принятому СБП-шлюзу (C2B-приём) механизм **рекуррентных списаний по согласию плательщика** («подписки СБП»): плательщик однократно оформляет согласие (Mandate) в пользу ТСП, ТСП инициирует списания без QR и без действия клиента — в пределах согласия. Изменение — **аддитивное**: путь разового QR-платежа не меняется.

## Что строим (границы)

- Агрегат **Mandate** в БД ядра с собственной статусной машиной (`CREATED → PENDING_PAYER → ACTIVE → EXPIRED/REVOKED/REJECTED`).
- **Списание — это Платёж**: переиспользует существующую статусную машину (`CREATED → PAID → CREDITED → COMPLETED`), без шага `QR_ISSUED`; связь с согласием через `mandateId`.
- **Durable-планировщик** списаний (не in-memory таймер) + инициация «по требованию» через API.
- **Обязательные нотификации плательщику** до списания и **обработка отзыва** согласия.
- Расширение **единственного** адаптера ОПКЦ (AD-004) новыми операциями/событиями; ядро остаётся контрактно-независимым от транспорта.

## Стыки (внутренний контракт) — единственная зависимость ядра от транспорта (AD-008)

- Синхронные операции адаптера: `createMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus` (идемпотентны по `reference` = `mandateId`/`paymentId` ядра).
- Асинхронные события адаптера: `mandate.activated`, `mandate.rejected`, `mandate.revoked`, `debit.paid`, `debit.rejected` (at-least-once, дедуп по `eventId`).
- API ТСП (аддитивно, `/v1`): `POST /v1/mandates`, `GET /v1/mandates/{id}`, `POST /v1/mandates/{id}/revoke`, `POST /v1/mandates/{id}/debits` → возвращает `Payment`. Новые состояния в `Payment.status` **не добавляются**. Новые вебхуки: `mandate.activated/rejected/revoked`.
- АБС: без изменений контракта — зачисление по `paymentId` (как для разового платежа).

## Связывающие инварианты spine (Rule — дословно)

- **AD-002** (Proposed): «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера (ревью + fitness-тест на каждый переход).»
- **AD-003** (Proposed): «Повторная доставка любого сообщения не изменяет уже завершённое состояние. Fitness: тест "повторная нотификация/повторный запрос → состояние не меняется, результат идемпотентен".»
- **AD-004** (Proposed): «Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.»
- **AD-005** (Proposed): «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Fitness: проверка недостижимости зачисления из `CREATED`/`QR_ISSUED`.»
- **AD-009** (Proposed, новый): «Вызов ОПКЦ на списание и зачисление по списанию в АБС возможны только при Mandate в состоянии `ACTIVE` (действующий срок, непревышенный лимит). Отзыв согласия немедленно блокирует новые списания. Fitness: списание при `REVOKED`/`EXPIRED`/`REJECTED`/превышенном лимите — недостижимо (ревью + fitness-тест на каждый переход). Согласие не является основанием для зачисления в обход AD-005.»
- **AD-010** (Proposed, новый): «Перед каждым списанием по согласию плательщику направляется уведомление в срок, установленный регламентом НСПК [ТРЕБУЕТ ПРОВЕРКИ]. Отзыв согласия обрабатывается и подтверждается, после чего новые списания невозможны. Каждая нотификация и каждый отзыв — в неизменяемом аудит-логе. Проверка — ИБ-аудит и fitness.»

Также действуют AD-001, AD-006, AD-007, AD-008 (без изменений; см. `ARCHITECTURE-SPINE.md`).

## Запрещено менять

- Существующий путь и контракт разового C2B-платежа (ломающие изменения — только `/v2`).
- Enum `Payment.status` — не добавлять/не удалять значения.
- Инвариант AD-005 — не ослаблять; согласие **не** является основанием для зачисления.
- Правило AD-004/AD-008 — протокол НСПК только в адаптере; реализация транспорта — только после договора и документации НСПК.
- Правило AD-002 — никаких «обновить статус, потом отправить событие».

## Внешние входы и допущения

- Регламент/протокол НСПК по подпискам (состояния, тайминги нотификаций, сроки отзыва, лимиты) — `[ТРЕБУЕТ ПРОВЕРКИ]`; до получения часть дизайна не финализируется.
- Поддержка операций подписок вендорским адаптером — требуется аддендум контракта (ADR-007/H4).
- Правовая модель согласия (152-ФЗ) и канал обязательных уведомлений — по согласованию с юристами/ИБ (H3).

## NFR, определяющие приёмку

Доступность ≥ 99,95 %; RPO=0; RTO ≤ 1 ч; списаний после отзыва/сверх лимита — 0; дублей списаний/зачислений — 0; обязательное уведомление доставлено в 100 % списаний; массовые списания ≥ 200 TPS sustained / 500 TPS пик; сверка согласий/списаний с НСПК ежечасная, с АБС суточная, расхождений — 0 (полностью — `docs/nfr.md` §7).

## Критерии приёмки и откат

Полный набор (включая негативные сценарии и rollback-критерий) — `acceptance-and-rollback.md`. Ключевое: дубль триггера → одно списание; списание при `REVOKED` → недостижимо; отказ АБС → без двойного зачисления; отключение фиче-флага → новые списания не создаются, открытые завершаются, данные сохраняются.
