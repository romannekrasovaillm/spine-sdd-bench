# Задача для исполнителей — CHANGE-001 «СБП-подписки»

> Активируется после ратификации ADR-008 (гейт H1) и получения регламента НСПК (H2). До этого — не начинать транспортные и протокольные работы.

Реализовать поверх walking skeleton платёжного шлюза СБП механизм рекуррентных списаний по согласию плательщика (ADR-008, `docs/spec/mandate-debit-lifecycle.md`):

1. **REST API ТСП** (аддитивно к v0.1): `POST /v1/mandates`, `GET /v1/mandates/{mandateId}`, `POST /v1/mandates/{mandateId}/revoke`, `POST /v1/mandates/{mandateId}/debits` (возвращает `Payment`) с идемпотентностью (`Idempotency-Key`); обновить `openapi/tsp-api.yaml` без ломающих изменений.
2. **Статусная машина Mandate** (`CREATED → PENDING_PAYER → ACTIVE → EXPIRED/REVOKED/REJECTED`) с транзакционным outbox и аудит-логом; списание — Payment без шага `QR_ISSUED`.
3. **Проверки AD-009** перед каждым списанием: Mandate=`ACTIVE`, срок, лимит; отзыв немедленно блокирует новые списания.
4. **Обязательные нотификации плательщику** (AD-010) и обработка отзыва; триггер недоставки — по политике H7.
5. **Durable-планировщик** списаний (не in-memory) + инициация «по требованию» через API.
6. **Расширение мок-адаптера ОПКЦ** новыми операциями/событиями подписок (`createMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus`, `mandate.*`, `debit.*`) — ядро контрактно-независимо; реальный протокол НСПК НЕ реализуется (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`).
7. **Зачисление по списанию** — только из подтверждённого `PAID` (AD-005, без изменений), идемпотентно по `paymentId` (мок-АБС).
8. **Фиче-флаг** на ТСП/сегмент: отключение запрещает новые списания, не затрагивая открытые.

Spine-инварианты AD-001..AD-010 обязательны, в первую очередь AD-002 (атомарные переходы), AD-003 (идемпотентность), AD-004 (единственный адаптер), AD-005 (зачисление только из PAID), AD-009 (только при действующем согласии), AD-010 (нотификации/отзыв). Критерии приёмки — `../acceptance-and-rollback.md` и NFR §7 (выполнимыми на моках): латентности, массовые списания, идемпотентность, отсутствие дублей, списания после отзыва = 0. Приоритет — доказать архитектуру сквозным сценарием, а не полнотой продукта. Код — на усмотрение команды с обоснованием в ADR.

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine) — **обязаны останавливать работу и эскалироваться**.
- При `blocked` — перечислить недостающие входы (в т.ч. регламент НСПК, аддендум вендора).

Архитектурный контекст — `ARCHITECTURE.md`, ограничения — `CONSTRAINTS.yaml`, рубрика приёмки — `RUBRIC.yaml`. Полное решение — `docs/adr/ADR-008-...md`.
