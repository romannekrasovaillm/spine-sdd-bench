# CHANGE-001 — изменения контрактов (совместимость)

- Status: Draft (вместе с ADR-008 на решение)
- Связано: ADR-008, ADR-004, `docs/contracts/tsp-api.md` §6, `docs/contracts/opkc-adapter.md`, `openapi/tsp-api.yaml`

Цель — добавить функциональность подписок **без поломки существующих потребителей**. Правило версионирования из `docs/contracts/tsp-api.md` §6: аддитивные опциональные поля — обратно совместимы и не требуют новой major-версии; ломающие изменения — только в `/v2`.

## 1. API ТСП (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`)

Версия: **0.1.0 → 0.2.0** (minor, аддитивно). Путь `/v1` сохраняется.

### 1.1 Добавлено (аддитивно)

| Элемент | Тип | Назначение |
|---|---|---|
| `POST /v1/mandates` | путь | Регистрация согласия плательщика (Idempotency-Key) → `Mandate` |
| `GET /v1/mandates/{mandateId}` | путь | Статус согласия → `Mandate` |
| `POST /v1/mandates/{mandateId}/revoke` | путь | Отзыв согласия (Idempotency-Key) → `Mandate` |
| `POST /v1/mandates/{mandateId}/debits` | путь | Инициация списания по согласию (Idempotency-Key) → `Payment` |
| `MandateRequest`, `Mandate`, `DebitRequest` | схемы | Новые объекты |
| `MandateStatus` | enum (новый) | `CREATED`, `PENDING_PAYER`, `ACTIVE`, `REJECTED`, `EXPIRED`, `REVOKED` |
| `Payment.mandateId` | поле, **опциональное** | Связь списания с согласием |
| `Payment.paymentType` | поле, **опциональное** | `one_off` (по умолчанию) \| `subscription` |

Ключевое решение совместимости: **списание возвращает существующую схему `Payment`**, а его статус — уже существующий enum. Новые значения в `Payment.status` **не добавляются**; статус согласия вынесен в отдельный ресурс/`MandateStatus`.

### 1.2 Не изменено (гарантии совместимости)

- `POST /v1/payments`, `GET /v1/payments/{paymentId}`, `POST /v1/payments/{paymentId}/refunds`, `GET .../refunds/{refundId}` — без изменений.
- `PaymentRequest` и обязательные поля `Payment` — без изменений.
- Enum `Payment.status` — значения не удаляются, не переименовываются, не добавляются.
- Существующие коды ошибок — без изменений.

### 1.3 Матрица совместимости

| Изменение | Влияние на существующего потребителя | Вердикт |
|---|---|---|
| Новые пути `/v1/mandates*` | Не вызывает (потребитель их не использует) | совместимо |
| Новые схемы/`MandateStatus` | Не вызывает (отдельные объекты) | совместимо |
| Новое опциональное поле `Payment.mandateId` | Не вызывает: поле отсутствует в старых ответах? — присутствует как `null`/отсутствует только для разовых платежей; потребители, игнорирующие неизвестные поля, не затронуты | совместимо (аддитивно) |
| Новое опциональное поле `Payment.paymentType` | То же; значение по умолчанию `one_off` сохраняет семантику | совместимо |
| Отдельный канал обязательных нотификаций плательщику | Не является частью контракта ТСП; вебхуки ТСП (ADR-004) не меняются | совместимо |

Замечание по строгим потребителям: формальная проверка ответов по фиксированной схеме без `additionalProperties: false` новых полей не отклонит; удалений и смены типов нет. В случае строгой валидации у ТСП — новые поля опциональны и не влияют на разбор существующих.

### 1.4 Вебхуки ТСП

События `payment.completed`/`payment.failed`/`payment.expired` и `refund.*` (ADR-004) переиспользуются для списаний без изменения формата. События жизненного цикла согласия (`mandate.activated`, `mandate.rejected`, `mandate.revoked`) — **новые типы**, добавляются аддитивно; ТСП, не подписанные на подписки, их не получают.

## 2. Контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md`)

Версия: **0.1 → 0.2 (draft)**. Расширяется аддитивно; **других точек знания протокола НСПК не появляется** (AD-004).

Новые синхронные операции (ядро → адаптер): `createMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus`.
Новые события (адаптер → ядро, at-least-once, дедуп по `eventId`): `mandate.activated`, `mandate.rejected`, `mandate.revoked`, `debit.paid`, `debit.rejected`.

Идемпотентность — по `reference` (`mandateId`/`paymentId` ядра), как в §5 контракта; это остаётся обязательным критерием RFP (G3). Все протокольные детали (поля, тайминги, статусы, сроки нотификаций/отзыва) — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации НСПК.

## 3. Влияние на вендора транспорта (ADR-007/AD-008)

Вендорский адаптер обязан реализовать новые операции/события — это расширение объёма контракта и критериев RFP (требуется аддендум, см. H4 в `README.md`). Правило AD-008 сохраняется: реализация транспорта — после подписания и получения документации НСПК.
