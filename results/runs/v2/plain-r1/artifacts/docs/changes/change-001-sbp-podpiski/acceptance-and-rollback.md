# CHANGE-001 — критерии приёмки и план отката

- Status: Draft (вместе с ADR-008 на решение)
- Связано: ADR-008, `docs/spec/mandate-debit-lifecycle.md`, `docs/nfr.md` §7, RUBRIC handoff-пакета (негативные сценарии + критерий отката)

## 1. Критерии приёмки

Каждый критерий проверяем тестом/командой. Обязательны негативные сценарии (дубль, отказ соседа, гонка) и критерий успешного отката.

### 1.1 Позитивные сценарии

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-01 | Happy path: согласие → `ACTIVE` → списание → `COMPLETED`, зачисление ровно один раз | E2E-тест на мок-адаптере ОПКЦ и мок-АБС |
| AC-02 | Списание по расписанию (durable-планировщик) выполняется в окне | Тест планировщика: отклонение от запланированного времени ≤ NFR §7 |
| AC-03 | Обязательное уведомление плательщику доставлено до списания (в срок регламента) | Тест контура нотификаций + аудит |
| AC-04 | Отзыв согласия обрабатывается и подтверждается (`REVOKED`) | Тест `POST /revoke` + вебхук `mandate.revoked` |
| AC-05 | Возврат по списанию (сага) приводит к `REFUNDED`, деньги возвращены корректно | Тест саги, включая сбой на шаге |
| AC-06 | Каждый переход Mandate/списания — в неизменяемом аудит-логе | Проверка аудита/SIEM (100 %) |

### 1.2 Негативные сценарии (обязательны)

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-N1 | Повторная инициация списания (тот же `Idempotency-Key` / тот же период) → **одно** списание и **одно** зачисление | Тест повторной доставки |
| AC-N2 | Повторная нотификация ОПКЦ `debit.paid` (тот же `eventId`) → состояние не меняется | Тест дедупликации |
| AC-N3 | Списание при Mandate `REVOKED`/`EXPIRED`/`REJECTED` → отклонено, вызова АБС нет (fitness AD-009) | Fitness-тест недостижимости |
| AC-N4 | Списание сверх лимита согласия / вне срока → отклонено до вызова ОПКЦ | Тест guard-условий D1 |
| AC-N5 | Зачисление по списанию невозможно из `CREATED` (не `PAID`) — недостижимо (fitness AD-005) | Fitness-тест переходов |
| AC-N6 | Отказ АБС: платёж остаётся `PAID`, ретраи, сверка гарантирует зачисление, дублей нет | Chaos-тест + сверка |
| AC-N7 | Потеря нотификации ОПКЦ: сверка находит и достраивает списание | Тест сверки |
| AC-N8 | Гонка «отзыв vs списание»: списание не выполняется, если отзыв зафиксирован раньше; при подтверждённом списании — расхождение и компенсация | Тест конкурентного сценария |
| AC-N9 | Обязательное уведомление не доставлено → списание блокируется/ретраится по политике (H7), алерт | Тест негативного пути нотификации |
| AC-N10 | Позднее событие после отзыва согласия не приводит к зачислению без подтверждённого статуса | Тест поздних событий |

### 1.3 Нефункциональные

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-P1 | Латентности и пропускная способность в норме (NFR §7) | Нагрузочный тест (sustained/пик/массовые списания) |
| AC-P2 | Сверка с ОПКЦ/АБС по подпискам: расхождений по завершённым операциям — 0 | Reconciliation-отчёт |
| AC-P3 | Существующий контракт не сломан: разовые платежи работают как раньше | Регресс базовых сценариев C2B |

### 1.4 Rollback-критерий (успех отката)

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-R1 | После выключения фиче-флага **новые** списания не создаются, открытые операции завершаются, данные сохранены | Тест отката в среде, близкой к боевой |

## 2. План отката

Согласован с оценкой обратимости в ADR-008 (**reversible**): изменение аддитивно и управляется фиче-флагом.

### 2.1 До боевой эксплуатации

Откат = **не включать** функционал подписок. Все работы обратимы; путь разовых платежей не затронут (AC-P3).

### 2.2 После включения (по ТСП/сегменту)

| Шаг | Действие | Эффект |
|---|---|---|
| R1 | Выключить фиче-флаг подписок для ТСП/сегмента | Новые списания не создаются; API возвращает `403 TSP_NOT_ACTIVE`/политику «выключено» |
| R2 | Не прерывать открытые операции | Списания «в полёте» доводятся до `COMPLETED`/терминального состояния; обязательства не теряются |
| R3 | Остановить планировщик новых списаний (только новые окна) | Расписание новых списаний не запускается |
| R4 | Сохранить данные согласий и аудит | Нужны для сверки, аудита и возможного возврата средств |
| R5 | Уведомить ТСП и (при необходимости) плательщиков об остановке списаний | Снижение клиентского/регуляторного риска |
| R6 | При подтверждённом дефекте финансового характера — компенсация (возвраты) по runbook | Устранение последствий |

Данные **не мигрируются обратно**: согласия и история списаний остаются в БД шлюза (единый источник истины, AD-002).

### 2.3 Сигналы-триггеры отката

- Любое двойное списание/зачисление (> 0) — немедленный стоп-новых.
- Зафиксировано списание при `REVOKED`/превышении лимита.
- Нарушение SLA обязательных нотификаций плательщику.
- Непрохождение сверки: расхождения по завершённым операциям > 0 (устойчиво).
- Несоответствие поведения регламенту НСПК; рост обращений/жалоб на списания.

### 2.4 Владелец решения об откате

- **Архитектор платёжного контура** — технический откат (R1–R3).
- **Владелец продукта** — коммуникация с ТСП и бизнес-решение (R5).
- **Риск/ИБ/комплаенс** — эскалация при регуляторном сигнале; решение об остановке при инциденте.

Совместное решение фиксируется в журнале инцидентов; RTO процесса отката — ≤ 1 ч (согласовано с NFR §3).
