# Согласие плательщика и списания по подписке — спецификация

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, AD-009, AD-010, AD-011, AD-005

Единый источник истины состояния согласия — БД шлюза (AD-002, ADR-009). Каждый
переход согласия — **атомарная транзакция** «смена статуса + запись в outbox +
аудит-лог» (AD-002, распространённый на согласие: AD-010). Повторные триггеры
идемпотентны (AD-003, AD-011).

## Проблема

Разовый C2B-платёж по QR требует действия плательщика в момент оплаты, поэтому
подписка (рекуррентное списание) невозможна. Нужна сущность **согласия
плательщика** (мандата) с параметрами и лимитами, списание против действующего
согласия без QR, и механически защищённый отзыв: списание по отозванному согласию
недопустимо. Протокол согласий ОПКЦ — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; локальная
модель ниже от него не зависит (AD-008, ADR-009).

## 1. Состояния согласия

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_PAYER` | Зарегистрировано, ожидается подтверждение плательщика в его банке | да |
| `ACTIVE` | Подтверждено плательщиком; списания разрешены в пределах лимитов | да |
| `REVOKED` | Отозвано плательщиком (или его банком) — **необратимо** | да |
| `EXPIRED` | Истёк срок действия (`validUntil`) | да |
| `CANCELLED` | Прекращено ТСП до/после активации | да |
| `REJECTED` | Плательщик отказал при подтверждении | да |

Терминальные: `REVOKED`, `EXPIRED`, `CANCELLED`, `REJECTED`. Из терминального
состояния списание невозможно ни при каких условиях (AD-009).

## 2. Таблица переходов согласия

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| C1 | — | `PENDING_PAYER` | `POST /v1/consents` (новый `consentId`) | ТСП активен; `maxAmountPerDebit` > 0 | запись согласия + outbox «регистрация в ОПКЦ» |
| C2 | `PENDING_PAYER` | `ACTIVE` | нотификация ОПКЦ о подтверждении плательщиком | согласие не отозвано/не истекло | outbox `consent.activated`; списания разрешены |
| C3 | `PENDING_PAYER` | `REJECTED` | нотификация ОПКЦ об отказе | — | outbox `consent.rejected` |
| C4 | `PENDING_PAYER` | `EXPIRED` | таймер срока подтверждения | не подтверждено | outbox `consent.expired` |
| C5 | `ACTIVE` | `REVOKED` | нотификация ОПКЦ об отзыве | — | **блокировка новых дебетов** + outbox `consent.revoked` + аудит |
| C6 | `ACTIVE` | `CANCELLED` | `DELETE /v1/consents/{consentId}` (ТСП) | — | блокировка новых дебетов; уведомление ОПКЦ |
| C7 | `ACTIVE` | `EXPIRED` | `validUntil` пройден | — | блокировка новых дебетов; outbox `consent.expired` |

## 3. Запрещённые переходы (инварианты)

- **Списание возможно только из состояния `ACTIVE`** (AD-009). Из `PENDING_PAYER`,
  `REVOKED`, `EXPIRED`, `CANCELLED`, `REJECTED` — недостижимо; проверяется
  fitness-тестом.
- `REVOKED` необратим: отозванное согласие не может вернуться в `ACTIVE`; замена —
  только новое согласие с новым подтверждением плательщика.
- Переход в `REVOKED` (C5, C6, C7) **атомарно** блокирует инициирование новых
  дебетов (AD-010): после фиксации перехода дебет невозможен.
- Сумма и параметры согласия не изменяются в одностороннем порядке ТСП после
  активации: изменение лимитов = новое согласие (ADR-008).

## 4. Лимиты согласия (guard дебета)

Лимиты задаются при регистрации; отсутствие необязательного лимита означает «без
ограничения по этому измерению»:

| Параметр | Обяз. | Смысл | Guard |
|---|---|---|---|
| `maxAmountPerDebit` | да | максимальная разовая сумма списания | `amount ≤ maxAmountPerDebit` |
| `maxAmountTotal` | нет | суммарный лимит по согласию | `списано + amount ≤ maxAmountTotal` |
| `period` + `maxDebitsPerPeriod` | нет | период и число списаний за период | `число успешных дебетов в периоде < maxDebitsPerPeriod` |
| `validUntil` | нет | срок действия согласия | `now ≤ validUntil` |
| `currency` | да | валюта согласия | совпадает с валютой дебета |

Проверка лимитов и запись дебета — в одной локальной транзакции (AD-009): гонка
двух одновременных дебетов не должна провести оба сверх лимита. Учёт списанного —
в БД шлюза (AD-011).

## 5. Списание по согласию (дебет)

- Запрос: `POST /v1/payments` с `consentId` (обязателен для подписки) и
  `debitPeriodId` (идентификатор периода подписки, например `2026-09`).
- `qrType` при наличии `consentId` не допускается — QR не выпускается.
- Статусная машина платежа: `CREATED → DEBIT_SENT → PAID → CREDITED → COMPLETED`
  (терминальные `FAILED`/`EXPIRED`/`REFUNDED`). `DEBIT_SENT` — «запрос списания
  отправлен в ОПКЦ, ожидается подтверждение»; `PAID` — подтверждённый ОПКЦ дебет,
  зачисление только из него (AD-005).
- Идемпотентность: пара (`consentId`, `debitPeriodId`) уникальна. Повтор запроса
  с тем же периодом возвращает существующий платёж, второго списания нет (AD-011).
  Повтор с тем же `Idempotency-Key` и другим телом — `409 IDEMPOTENCY_CONFLICT`.
- Отказ ОПКЦ по дебету → `FAILED`, вебхук `payment.failed`, лимит периода не
  расходуется.

## 6. Отзыв и гонки

- Отзыв приходит нотификацией ОПКЦ; применяется атомарно (C5), приоритет отзыва
  выше любых локальных решений (AD-010, ADR-009).
- **Гонка «отзыв ↔ отправленный дебет»**: если дебет был отправлен до фиксации
  отзыва и подтверждён ОПКЦ после — платёж завершается, затем компенсируется
  возвратом (сага ADR-005) по runbook. Устранить гонку полностью нельзя; окно
  сужается (AD-010) и фиксируется в отчёте инцидента.
- Сверка согласий с ОПКЦ — ежечасная (контур сверки ADR-004); при расхождении
  трактовка — в пользу плательщика.

## 7. Согласованность с API ТСП

Маппинг статусов согласия наружу (см. `docs/contracts/tsp-api.md` §3.6):
`PENDING_PAYER`, `ACTIVE`, `REVOKED`, `EXPIRED`, `CANCELLED`, `REJECTED` — без
технических подсостояний. Статусы платежа-дебета — те же, что у разового платежа,
плюс техническое `DEBIT_SENT` (наружу не выставляется отдельно: `PAID` появляется
только после подтверждения ОПКЦ).

## Критерии приёмки

Проверяемые критерии (EARS), выполнимые на моках (гейт A4):

- [ ] When ТСП регистрирует согласие, the шлюз shall вернуть `201 {consentId,
      consentUrl}` ≤ 500 мс p95 (без учёта времени ОПКЦ).
- [ ] When плательщик подтверждает согласие, the шлюз shall перевести его в `ACTIVE`
      и доставить `consent.activated` ≤ 5 с p95.
- [ ] When приходит дебет по `ACTIVE`-согласию в пределах лимитов, the шлюз shall
      провести его и зачислить в АБС только из подтверждённого статуса (AD-005).
- [ ] When сумма дебета превышает `maxAmountPerDebit` или остаток суммарного лимита,
      the шлюз shall отклонить дебет `422` **без обращения к ОПКЦ**.
- [ ] When число списаний за период достигает `maxDebitsPerPeriod`, the шлюз shall
      отклонить следующий дебет `422`.
- [ ] When повторно приходит запрос дебета с тем же (`consentId`, `debitPeriodId`),
      the шлюз shall вернуть существующий платёж и не создать второго списания.
- [ ] When приходит отзыв согласия, the шлюз shall за ≤ 5 с p95 перевести согласие
      в `REVOKED` и заблокировать новые дебеты; дебетов после отзыва — 0.
- [ ] When приходит дебет по согласию в состоянии `PENDING_PAYER`/`REVOKED`/
      `EXPIRED`/`CANCELLED`/`REJECTED`, the шлюз shall отклонить его (`409`/`422`).
- [ ] When ОПКЦ недоступен, the шлюз shall не активировать согласие и не проводить
      дебет; ТСП получает retryable-ошибку, состояние не искажается.
- [ ] When нотификация ОПКЦ дублируется, the шлюз shall обработать её идемпотентно
      (состояние не меняется).

## Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Точный протокол согласий ОПКЦ неизвестен | Модель лимитов/отзыва может потребовать уточнения | Изоляция в адаптере ОПКЦ (AD-004); протокольные детали — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; ядро контрактно-независимо |
| Гонка «отзыв ↔ отправленный дебет» | Списание после отзыва (P0) | Атомарный отзыв (AD-010), компенсация возвратом, runbook, метрика «дебетов после отзыва = 0» |
| Ошибка в учёте лимитов/периодов | Превышение лимитов, двойные списания | Проверка и запись в одной транзакции (AD-009), идемпотентность периода (AD-011), property-тесты |
| Утечка/избыточное хранение идентификатора плательщика | ПДн, регуляторный риск | Минимизация, шифрование, маскирование в логах (AD-006, AD-007); сроки хранения — комплаенс |
| Вендорский транспорт не поддержит подписки | Блокировка сценария | Расширение constraints RFP (ADR-007); проверка на этапе выбора вендора |
| Рост библиотеки правил без исполняемых проверок | Иллюзия контроля | На A4 — шаблоны исполняемых правил (`arch-be rules template`) для AD-009/AD-010/AD-011 |
