# Контракт API ТСП (мерчант-API) — v0.2 draft

- Status: Draft (для ревью на гейте A1)
- Версия контракта: 0.2 (аддитивно поверх 0.1; машиночитаемая форма — `openapi/tsp-api.yaml`, `info.version` 0.2.0)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002 (идемпотентность), ADR-004 (нотификации), ADR-008 (подписки), ADR-009 (согласия), AD-003, AD-009, AD-011

Назначение: контракт между **ТСП/мерчантом** и **СБП-шлюзом банка** (ядро, собственная разработка). Контракт **не зависит** от протокола ОПКЦ СБП (AD-008): адаптер НСПК скрыт за внутренним интерфейсом шлюза.

> Версия 0.2 добавляет подписки СБП: согласие плательщика и списания по согласию.
> Все изменения **аддитивны**: методы, поля и события v0.1 сохраняют смысл; ломающих
> изменений нет (проверка — `contract_diff` v0.1 → v0.2). Потребители v0.1
> продолжают работать без миграции.

## 1. Общие положения

- Транспорт: **HTTPS, REST/JSON**, версия пути `/v1`.
- Кодировка: UTF-8. Числа сумм — **целые, в копейках** (minor units), валюта — `RUB` (ISO 4217: 643).
- Временные метки — ISO 8601 (UTC), формат `YYYY-MM-DDTHH:MM:SS.sssZ`.
- Авторизация ТСП: **mTLS** (сертификат ТСП, выпущенный УЦ банка) + `X-API-Key`. Детали финализирует ИБ на A4; для v0.2 — mTLS обязателен.
- Rate limiting: по умолчанию 50 req/s на ТСП (конфигурируемо); превышение — `429` + заголовок `Retry-After`.
- Корреляция: каждый ответ содержит `X-Trace-Id` (генерируется шлюзом, прокидывается в логи/SIEM).

## 2. Идемпотентность

- Заголовок `Idempotency-Key` **обязателен** для всех `POST`.
- Ключ генерирует ТСП (UUID); шлюз хранит маппинг ключ → ресурс **24 часа**.
- Повторный `POST` с тем же ключом и тем же телом → возвращается **тот же ресурс** (тот же `paymentId`/`consentId`/`refundId`), статус 200/201 без повторного действия.
- Повторный `POST` с тем же ключом, но **другим телом** → `409 IDEMPOTENCY_CONFLICT`.
- GET-запросы идемпотентны по своей природе, ключ не требуется. `DELETE` идемпотентен: повторный вызов не меняет результат.
- Дополнительно для дебетов по согласию: пара (`consentId`, `debitPeriodId`) уникальна — повтор запроса за тот же период не создаёт второго списания (AD-011).

## 3. Методы

### 3.1 Регистрация ТСП (онбординг)

`POST /v1/tsp`

Запрос:
```json
{
  "inn": "7701234567",
  "ogrn": "1027700132195",
  "name": "ООО «Ромашка»",
  "merchantType": "LE",            // LE | IE | SELF_EMPLOYED
  "mcc": "5411",
  "settlementAccount": "40702810900000000001",
  "pointsOfSale": [
    { "name": "Магазин на Тверской", "address": "Москва, ул. Тверская, 1", "phone": "+74950000000" }
  ],
  "webhookUrl": "https://merchant.example.com/hooks/sbp",
  "webhookSecret": "…"             // секрет для HMAC-подписи вебхуков (см. §5)
}
```

Ответ `201`:
```json
{
  "tspId": "tsp_9f3c2a1b",
  "status": "ACTIVE"
}
```

Примечания: регистрация ТСП в ОПКЦ выполняется асинхронно через адаптер; если ОПКЦ не подтвердил — ТСП получает статус `PENDING_OPKC`, приём платежей недоступен до подтверждения. Критерии отказа (ПОД/ФТ) — на этапе A4. Для приёма подписок ТСП должен быть активен и допущен к сценарию подписок (флаг допуска — на этапе A4).

### 3.2 Создание платежа (динамический QR / ссылка / дебет по согласию)

`POST /v1/payments`

Запрос (разовый платёж по QR):
```json
{
  "tspId": "tsp_9f3c2a1b",
  "amount": 149990,                // копейки, int
  "currency": "RUB",
  "qrType": "dynamic",             // dynamic | static | link
  "paymentPurpose": "Заказ № 12345",
  "ttlSeconds": 900,               // опц.; лимит — по НСПК [ТРЕБУЕТ ПРОВЕРКИ]
  "redirectUrl": "https://merchant.example.com/order/12345/return",
  "merchantOrderId": "order-12345" // опц., сквозной для ТСП
}
```

Запрос (дебет по согласию — **новое в v0.2**):
```json
{
  "tspId": "tsp_9f3c2a1b",
  "amount": 39900,
  "currency": "RUB",
  "consentId": "cns_7a1b2c3d",     // новое, обязательно для подписки
  "debitPeriodId": "2026-09",      // новое, идентификатор периода подписки
  "paymentPurpose": "Подписка «Кинопоиск+» за сентябрь 2026",
  "merchantOrderId": "sub-12345-2026-09"
}
```

Ответ `201`:
```json
{
  "paymentId": "pay_8d1e4f5a",
  "qrId": "QR-…",                  // id в ОПКЦ (сквозной для сверки); при дебете по согласию отсутствует
  "qrUrl": "https://qr.nspk.ru/AS100001ORTF4GAF80KPJ53K186D9A3G?type=02&bank=…&crc=…",
  "qrImage": "data:image/png;base64,…", // опц., если ТСП не рендерит сам
  "status": "QR_ISSUED",           // при дебете по согласию — DEBIT_SENT не выставляется: см. §3.3
  "amount": 149990,
  "expiresAt": "2026-08-15T18:00:00.000Z"
}
```

Правила:
- `amount` > 0; для `qrType=static` сумма может отсутствовать (`amount` опц.); после создания **сумма и реквизиты иммутабельны** (ADR-002). Максимальная сумма — по лимитам НСПК [ТРЕБУЕТ ПРОВЕРКИ].
- **Новое в v0.2**: если указан `consentId`, поле `qrType` **не допускается** (QR не выпускается), платёж проходит как дебет по согласию; обязателен `debitPeriodId`. Шлюз проверяет статус согласия (`ACTIVE`) и лимиты **до** обращения к ОПКЦ; нарушение — `409 CONSENT_NOT_ACTIVE` или `422` (см. §4). Значения `status` в ответе — из общего перечня §3.3 (`DEBIT_SENT` — техническое, наружу не выставляется).

### 3.3 Запрос статуса платежа

`GET /v1/payments/{paymentId}`

Ответ `200`:
```json
{
  "paymentId": "pay_8d1e4f5a",
  "status": "COMPLETED",           // CREATED | QR_ISSUED | PAID | CREDITED | COMPLETED | FAILED | EXPIRED | REFUNDED
  "amount": 149990,
  "paidAt": "2026-08-15T17:31:02.000Z",
  "creditingStatus": "CREDITED",   // технический статус зачисления (для ТСП)
  "consentId": "cns_7a1b2c3d",     // новое, присутствует для дебетов по согласию
  "debitPeriodId": "2026-09",      // новое, присутствует для дебетов по согласию
  "refunds": [
    { "refundId": "ref_1a2b3c", "amount": 149990, "status": "COMPLETED" }
  ],
  "errorCode": null,               // код отклонения НСПК, если статус FAILED
  "merchantOrderId": "order-12345"
}
```

Статусы платежа: разовый платёж — `CREATED → QR_ISSUED → PAID → CREDITED → COMPLETED`; дебет по согласию — `CREATED → (DEBIT_SENT) → PAID → CREDITED → COMPLETED`. Терминальные: `FAILED`, `EXPIRED`, `REFUNDED`. Технические подсостояния наружу не выставляются.

### 3.4 Возврат (полный/частичный)

`POST /v1/payments/{paymentId}/refunds`

Запрос:
```json
{
  "amount": 149990,                // <= оплаченная сумма; опц. (по умолчанию — полный)
  "reason": "Возврат по заявлению клиента"
}
```

Ответ `201`:
```json
{ "refundId": "ref_1a2b3c", "paymentId": "pay_8d1e4f5a", "amount": 149990, "status": "PENDING" }
```

Правила: возврат возможен только если платёж в состоянии `CREDITED`/`COMPLETED` (ADR-005, сага). Полный возврат переводит платёж в `REFUNDED`; частичные — платёж остаётся `COMPLETED`, возврат виден в `refunds[]`. Статус возврата: `PENDING → COMPLETED | FAILED`. Возврат дебета по согласию не восстанавливает израсходованный лимит периода автоматически — возврат лимита — отдельное решение (см. §7).

### 3.5 Статус возврата

`GET /v1/payments/{paymentId}/refunds/{refundId}` → `200 { refundId, paymentId, amount, status, completedAt }`

### 3.6 Согласия (подписки СБП) — **новое в v0.2**

Ресурс «согласие» (в терминах бизнеса — **подписка СБП**) описывает мандат
плательщика на рекуррентные списания. Подтверждение и отзыв выполняет **плательщик
в своём банке**; шлюз получает о них нотификации ОПКЦ и сообщает ТСП вебхуками.

#### 3.6.1 Регистрация согласия

`POST /v1/consents`

```json
{
  "tspId": "tsp_9f3c2a1b",
  "payerId": "+79*********",       // идентификатор плательщика; формат — по протоколу ОПКЦ [ТРЕБУЕТ ПРОВЕРКИ]
  "paymentPurpose": "Подписка «Кинопоиск+», ежемесячно",
  "limits": {
    "currency": "RUB",
    "maxAmountPerDebit": 39900,    // обязательно
    "maxAmountTotal": 478800,      // опц.
    "period": "MONTHLY",           // DAILY | WEEKLY | MONTHLY [ТРЕБУЕТ ПРОВЕРКИ]
    "maxDebitsPerPeriod": 1        // опц.
  },
  "validUntil": "2027-09-28T00:00:00.000Z",  // опц.
  "redirectUrl": "https://merchant.example.com/subscription/return",
  "merchantOrderId": "sub-12345"
}
```

Ответ `201`:
```json
{
  "consentId": "cns_7a1b2c3d",
  "status": "PENDING_PAYER",
  "consentUrl": "https://qr.nspk.ru/…",   // ссылка для подтверждения плательщиком
  "limits": { "currency": "RUB", "maxAmountPerDebit": 39900, "maxAmountTotal": 478800, "period": "MONTHLY", "maxDebitsPerPeriod": 1 },
  "validUntil": "2027-09-28T00:00:00.000Z",
  "createdAt": "2026-09-28T10:00:00.000Z"
}
```

Правила: `maxAmountPerDebit` > 0 обязателен (списание без разового лимита не допускается — AD-009). Одностороннее изменение лимитов ТСП после активации не поддерживается (ADR-008): новые условия — новое согласие.

#### 3.6.2 Статус согласия

`GET /v1/consents/{consentId}` → `200`

```json
{
  "consentId": "cns_7a1b2c3d",
  "status": "ACTIVE",                  // PENDING_PAYER | ACTIVE | REVOKED | EXPIRED | CANCELLED | REJECTED
  "limits": { "currency": "RUB", "maxAmountPerDebit": 39900, "maxAmountTotal": 478800, "period": "MONTHLY", "maxDebitsPerPeriod": 1 },
  "amountDebitedTotal": 119700,
  "debitsInCurrentPeriod": 1,
  "validUntil": "2027-09-28T00:00:00.000Z",
  "lastDebitAt": "2026-09-28T10:05:00.000Z",
  "activatedAt": "2026-09-28T10:01:00.000Z",
  "revokedAt": null
}
```

#### 3.6.3 Прекращение согласия ТСП

`DELETE /v1/consents/{consentId}` → `200 { consentId, status: "CANCELLED", cancelledAt }`

Идемпотентно. Новые списания блокируются немедленно (AD-010). Если согласие уже
`REVOKED`/`EXPIRED` — `409 CONSENT_NOT_ACTIVE` (отзыв плательщика отменять нельзя:
он необратим, AD-010). Отзыв плательщиком через этот метод **не выполняется** —
он приходит нотификацией ОПКЦ и отражается событием `consent.revoked`.

## 4. Ошибки (RFC 9457, Problem Details)

```json
{
  "type": "https://api.bank.ru/sbp/errors/amount-exceeds-paid",
  "title": "Сумма возврата превышает оплаченную",
  "status": 422,
  "detail": "Доступная к возврату сумма: 149990",
  "code": "AMOUNT_EXCEEDS_PAID",
  "traceId": "…",
  "idempotencyKey": "…"
}
```

Канонические коды v0.1: `INVALID_REQUEST` (400), `UNAUTHORIZED` (401), `TSP_NOT_ACTIVE` (403), `NOT_FOUND` (404), `IDEMPOTENCY_CONFLICT` (409), `PAYMENT_NOT_REFUNDABLE` (422), `AMOUNT_EXCEEDS_PAID` (422), `RATE_LIMITED` (429), `INTERNAL` (500).

**Новые коды v0.2 (согласия и дебеты):**

| Код | HTTP | Когда |
|---|---|---|
| `CONSENT_NOT_FOUND` | 404 | `consentId` неизвестен |
| `CONSENT_NOT_ACTIVE` | 409 | дебет/прекращение при статусе не `ACTIVE` |
| `CONSENT_EXPIRED` | 422 | истёк `validUntil` |
| `CONSENT_LIMIT_EXCEEDED` | 422 | превышен `maxAmountPerDebit` или остаток `maxAmountTotal` |
| `CONSENT_FREQUENCY_EXCEEDED` | 422 | превышено `maxDebitsPerPeriod` за период |
| `DEBIT_PERIOD_ALREADY_PAID` | 409 | период уже оплачен другим запросом |
| `CONSENT_SCENARIO_NOT_ALLOWED` | 403 | ТСП не допущен к сценарию подписок |

Идемпотентный повтор успешного запроса возвращает ресурс со статусом 200, а не ошибку.

## 5. Вебхуки (нотификации ТСП)

Шлюз доставляет события на `webhookUrl` ТСП (ADR-004: at-least-once, ретраи, DLQ).

Заголовки: `X-SBP-Event-Id` (uuid события — для дедупликации у ТСП), `X-SBP-Signature` (HMAC-SHA256 тела, ключ — `webhookSecret`), `Content-Type: application/json`.

События v0.1:
- `payment.completed` — платёж зачислен (`status: COMPLETED`)
- `payment.failed` — платёж отклонён/ошибка
- `payment.expired` — истёк TTL
- `refund.completed` / `refund.failed`

**События v0.2 (согласия):**
- `consent.activated` — плательщик подтвердил согласие
- `consent.revoked` — согласие отозвано плательщиком (необратимо)
- `consent.expired` — истёк срок согласия
- `consent.rejected` — плательщик отказал при подтверждении

Тело (`consent.revoked`):
```json
{
  "eventId": "evt_…",
  "type": "consent.revoked",
  "consentId": "cns_7a1b2c3d",
  "status": "REVOKED",
  "timestamp": "2026-09-28T12:00:00.000Z"
}
```

Доставка: ответ ТСП `2xx` = успех; иначе ретрай (экспоненциальная задержка + джиттер), после исчерпания — DLQ. ТСП обязан отвечать идемпотентно по `eventId`. Получив `consent.revoked`, ТСП обязан прекратить инициирование списаний по согласию.

## 6. Версионирование и совместимость

- Путь `/v1`; изменения, ломающие контракт, — только в `/v2` с периодом поддержки обеих версий ≥ 6 мес.
- Добавление опциональных полей и новых методов, новых событий и новых кодов ошибок — обратно совместимо, не требует новой версии (в том числе `consentId`/`debitPeriodId` в v0.2).
- Deprecation: заголовок `Deprecation` + `Sunset` в ответах старой версии.

**История изменений:**

| Версия | Что | Совместимость |
|---|---|---|
| 0.1 | Базовый C2B-приём: платежи, статусы, возвраты, вебхуки | — |
| 0.2 | Согласия (`/v1/consents`), дебет по согласию (`consentId`/`debitPeriodId` в `POST /v1/payments`), события `consent.*`, коды ошибок согласия | аддитивно, ломающих изменений нет |

## 7. Открытые вопросы (для A1)

1. Необходимость отдельного метода «отмена QR до оплаты» (`POST /v1/payments/{paymentId}/cancel`) — roadmap, ждёт подтверждения от бизнеса.
2. Лимиты сумм и TTL — по документации НСПК [ТРЕБУЕТ ПРОВЕРКИ]. Для подписок — регламент согласий ОПКЦ (период, частота, срок действия) [ТРЕБУЕТ ПРОВЕРКИ].
3. Модель подписи запросов ТСП (mTLS + подпись тела) — финализирует ИБ на A4.
4. Формат `qrImage` (PNG base64) и необходимость — на усмотрение продукта.
5. Восстанавливается ли израсходованный лимит периода при возврате дебета — решение бизнеса/ОПКЦ.
6. Нотификация плательщика о списании (обязательность и канал) — правовой вопрос, комплаенс.
