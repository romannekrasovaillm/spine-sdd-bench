## Epic-context (цель, стыки, ограничения)

**Цель.** Дать ТСП (кинотеатры, ЖКХ, связь) возможность повторяющихся C2B-списаний
по согласию плательщика, не ломая принятый контур C2B-приёма. Плательщик один раз
подтверждает согласие (mandate) в приложении своего банка; далее шлюз инициирует
списания по расписанию без участия плательщика. Каждое списание — обычный платёж
существующей статусной машины: то же зачисление в АБС, те же возвраты.

**Компоненты (новое — модули внутри существующего контейнера «СБП-шлюз»).**
Реестр согласий (жизненный цикл согласия, источник истины) и планировщик подписок
(расчёт сроков, инициация списаний). Расширяются: статусная машина платежа (новый
вход в `PAID` — подтверждение ОПКЦ по инициативе планировщика), нотификатор ТСП
(события `subscription.*`), сверка (согласия наравне с платежами), адаптеры
ОПКЦ/АБС (новые операции без смены границ). Новых сервисов, хранилищ и trust-зон
**не создаётся**.

**Стыки.**
- API ТСП v0.2 (`openapi/tsp-api.yaml`): `POST /v1/subscriptions`,
  `GET /v1/subscriptions/{id}`, `POST /v1/subscriptions/{id}/cancel`; поля
  `subscriptionId`, `paymentType` у платежа; вебхуки `subscription.*`.
- Адаптер ОПКЦ v0.2 (внутренний контракт ядро↔транспорт):
  `createMandate`/`getMandateStatus`/`cancelMandate`/`createDebit` +
  события `mandate.activated/rejected/revoked/expired`. Протокол НСПК в ядро не
  протекает: его знает только адаптер.
- АБС: без изменений — зачисление по `paymentId`, возврат сагой по `refundId`.
- Сверка: часовой опрос согласий/открытых попыток у ОПКЦ, суточная с АБС.

**Ограничения.** Точная семантика рекуррентного продукта НСПК — внешний вход
`[ТРЕБУЕТ ПРОВЕРКИ]` (объект согласия, подтверждение, момент «списания
инициировано», обработка отзыва); до получения документации протокольные детали
не реализуются, ядро работает по внутреннему контракту. Реализация начинается
только после A3 и (для реального транспорта) после документации НСПК.

## Инварианты (дословно; менять нельзя)

- **AD-001**: Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза.
- **AD-002**: Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции.
- **AD-003**: Повторная доставка любого сообщения не изменяет уже завершённое состояние.
- **AD-004**: Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.
- **AD-005**: Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус).
- **AD-008**: Ядро шлюза проектируется контрактно-независимым от транспорта.
- **AD-009**: Инициация рекуррентного списания возможна только из согласия в состоянии `ACTIVE` и только при `amount ≤ mandate.maxAmount` и совпадении получателя с согласием; иного пути зачисления, кроме `PAID`, не существует. Повтор с тем же ключом попытки `(mandateId, periodStart)` второго списания не создаёт.
- **AD-010**: Смена состояния согласия и запись события/аудита — одна транзакция; обработанный отзыв блокирует инициацию новых списаний; инициированные разрешаются по подтверждённому статусу ОПКЦ (не отменяются); состояния согласий сверяются с ОПКЦ.

**Запрещено менять:** `ARCHITECTURE-SPINE.md`, `docs/adr/**`, `.arch-handoff/CONSTRAINTS.yaml`
(прямые правки — только через активную дельту `changes/sbp-recurring-consent/DELTA.md`);
зачисление из любого состояния, кроме `PAID`; доверять «единственному лидеру»
планировщика; хранить ПДн плательщика сверх `payerRef`; «отменять» уже инициированное
списание деньгами. Конфликт с инвариантом — **остановка и эскалация**, не молчаливое
решение.

## Критерии приёмки

Позитивные и негативные критерии — в `changes/sbp-recurring-consent/DELTA.md`
(раздел «Критерии приёмки») и `docs/spec/consent-state-machine.md` (раздел
«Критерии приёмки»); измеримые цели — `docs/nfr.md` §7. Обязательно покрыть:
отсутствие согласия, отозванное согласие, превышение лимита, повтор `attemptId`
(рестарт планировщика), недоступность ОПКЦ (попытка `FAILED`, в АБС пусто),
гонку «отзыв ↔ списание», 100 % аудит переходов. Контрактный контроль:
`openapi_lint` (0 error), `contract_diff` против v0.1 — **0 ломающих**.

## Контракт результата (headless JSON)

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

`conflicts_with_prior_decisions` — **сигнал остановки и эскалации архитектору**, а
не повод продолжить с иным решением. При `blocked` перечислить недостающие входы
(например, отсутствующая документация НСПК).

## План отката (для исполнителя)

- До боевой эксплуатации: не включать (фича-флаг `recurring-enabled` по ТСП).
- После включения: kill-switch планировщика → новые списания не инициируются;
  массовое завершение активных согласий по runbook; подтверждённые платежи
  доводятся до терминального состояния, при необходимости возврат сагой.
- **Сигналы отката**: любое двойное списание за период; списание после
  обработанного отзыва; расхождение согласий с ОПКЦ выше порога сверки.
- **Владелец решения об откате**: владелец платёжного контура (дежурный архитектор
  + продукт). **Признак успешного отката**: 0 новых списаний и 0 незавершённых
  операций по подпискам.
