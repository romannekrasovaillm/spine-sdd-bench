# Оценка значимости и маршрут — изменение «подписки СБП»

- Изменение: `sbp-recurring-consent` (рекуррентные C2B-списания по согласию плательщика)
- Дата: 2026-09-28
- Метод: Architecture Significance Score (15 триггеров), инструмент `significance_score`
- **Результат: score 9/15 → маршрут Critical**

## 1. Сработавшие триггеры (9)

| Триггер | Почему сработал |
|---|---|
| `financial_impact` | Списание денег со счёта плательщика без его участия — прямое финансовое последствие |
| `criticality_or_exception` | Платёжный контур КИИ; ручное исключение: рекуррентность по умолчанию запрещена (нужно согласие) |
| `security_boundary_change` | Новый входной объект (согласие) и новый внешний сценарий (отзыв от банка плательщика) — меняется модель авторизации списания |
| `consistency_model_change` | Новый агрегат (согласие) со своим жизненным циклом, гонка «отзыв ↔ списание», новый класс попыток |
| `api_contract_change` | Новые пути/поля API ТСП (`/v1/subscriptions*`, `subscriptionId`, `paymentType`) |
| `data_contract_change` | Новый контракт данных: согласие, попытки списания, события `subscription.*`/`mandate.*` |
| `cross_domain_integration` | Плательщик (банк плательщика/ОПКЦ) ↔ платёжный контур ↔ ТСП; отзыв приходит из внешнего домена |
| `new_component` | Новые модули контура: реестр согласий и планировщик подписок (внутри существующего контейнера) |
| `significant_nfr` | Новые измеримые NFR (лаг планировщика, блокировка после отзыва, 0 двойных списаний) |

## 2. Не сработавшие триггеры (6) — почему

| Триггер | Почему не сработал |
|---|---|
| `new_datastore` | Новых хранилищ нет: согласия и попытки — расширение схемы существующей БД шлюза (ADR-008) |
| `new_vendor` | Вендор транспорта ОПКЦ уже выбран/выбирается по RFP (ADR-007); рекуррентность — расширение того же контракта адаптера |
| `trust_zone_change` | Новых trust-зон нет: модули подписок живут в существующем платёжном контуре (AD-006, ADR-008) |
| `irreversible_migration` | Изменение аддитивно, миграции существующих данных нет; откат — фича-флаг и остановка планировщика |
| `rto_rpo_targets` | Целевые RPO=0/RTO≤1 ч принятого решения не меняются; наследуются |
| `domain_ownership_change` | Домен остаётся платёжным; пересечение с доменом клиентских согласий — вопрос владения, вынесен на A3 (см. `README.md`) |

## 3. Что означает маршрут Critical

- **Полный Solutioning** (не дельта-спека): подход и альтернативы — ADR-008…ADR-010,
  инварианты — AD-009/AD-010, NFR — раздел 7 `docs/nfr.md`.
- **Обязательная человеческая точка A3**: без неё реализация не начинается
  (ADR-008…ADR-010 остаются `Proposed`, блоки AD-009/AD-010 — `Proposed`).
- **Walking skeleton до массовой генерации**: сквозной сценарий «подписка →
  подтверждение → списание (мок НСПК) → зачисление (мок АБС) → отзыв → блокировка»
  на моках адаптеров.
- **Evidence-гейты**: fitness-правила (`CONSTRAINTS.yaml`), негативные тесты
  (нет согласия / отозвано / дубль / отказ ОПКЦ), репетиция отката.

## 4. Декларированный маршрут и «авто»-маршрут гейта — не одно и то же

`arch-be gate --route auto` вычисляет маршрут механически из git-диффа. Детекторы
видят в этом изменении только `api_contract_change` (изменены `openapi/tsp-api.yaml`
и `docs/contracts/**`), поэтому авто-маршрут гейта — **Fast**, и он **не запускает**
сенсоры спецификаций, количественные NFR (нет `model/`) и evidence-бандлы.

Это ограничение детекторов, а не оценка риска: триггеры `financial_impact`,
`security_boundary_change`, `consistency_model_change` и др. по git-диффу не
выводятся и объявляются архитектором (см. §1). **Истинный маршрут — Critical**, и
реализация идёт по Critical-процессу; при желании гейт можно прогнать явно:
`arch-be gate --route critical` (потребует секции сенсоров в `docs/spec/*.md` и
evidence-бандл — появляются на этапе реализации, см. `HANDOFF.md`).

## 5. Контрольные точки для этого изменения

| Точка | Содержание | Кто |
|---|---|---|
| A0 Architecture Fit | Укладывается в принятый паттерн (модуль в контуре, AD-001…AD-008) — да | авто + архитектор |
| A1 Impact Assessment | `IMPACT.md`, контракты v0.2, NFR раздела 7 | агент (готово в пакете) |
| A2 Solutioning trigger | Порог определён: Critical | архитектор |
| **A3 Human Architecture Decision** | Рекомендация `hybrid-recurring-in-contour`; ратификация ADR-008…ADR-010 и AD-009/AD-010 | **человек-архитектор** |
| A4 Conformance Evidence | fitness-правила, негативные тесты, 0 ломающих контрактных диффов, репетиция отката | исполнители + контроль |
| A5 Post-deploy Drift | Сверка согласий с ОПКЦ, SLO-отчёт, отсутствие дрейфа от spine | эксплуатация |

## 6. A3-рекомендация (машинно-читаемая форма)

- **choice**: `hybrid-recurring-in-contour` — согласие как новый агрегат и модуль
  подписок внутри существующего платёжного контура; рекуррентные операции
  добавляются в контракт адаптера ОПКЦ и входят в текущий RFP.
- **rationale**: переиспользует статусную машину, outbox, идемпотентность, сверку
  и сагу возвратов; не создаёт второго источника истины по деньгам и новых
  trust-зон; расширение контракта адаптера попадает в закупку до подписания.
- **constraints**: (1) зачисление только из `PAID` (AD-005) — без исключений;
  (2) списание только при `ACTIVE` согласии и в пределах лимитов (AD-009);
  (3) отзыв атомарен и приоритетен; уже инициированное не отменяется деньгами
  (AD-010); (4) протокольные детали — только в адаптере ОПКЦ (AD-008), до
  документации НСПК — `[ТРЕБУЕТ ПРОВЕРКИ]`; (5) реализация — после A3.
- **rejected options**: отдельный сервис подписок с собственной БД; поля согласия
  внутри платежа; истина о согласии только у НСПК (см. ADR-008, Alternatives).
- **expiry**: пересмотр при расхождении модели с протоколом НСПК или при росте
  числа согласий, делающем совместный деплой ограничением.
