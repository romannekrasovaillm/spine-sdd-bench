# ADR-010. Идемпотентность и неопределённый исход рекуррентного списания: запрет повторной отправки без проверки статуса

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур)
- Related: ADR-008, ADR-002, ADR-004, ADR-005; AD-002, AD-003, AD-005, AD-010

## Context

Рекуррентное списание инициирует ТСП по расписанию; вызовы могут повторяться (ретраи ТСП, сбои сети, перезапуски), а канал к ОПКЦ не даёт «ровно один раз»: ответ может прийти позже таймаута, нотификации дублируются. Финансовое последствие ошибки здесь **дороже**, чем у разового платежа: двойное списание означает повторное списание денег у плательщика без его участия, а потерянное списание — неоплаченную подписку и спор с ТСП. ТСП технически может пересоздать ключ идемпотентности и повторить списание за тот же период.

Силы: at-least-once доставка от внешнего оператора; неопределённый исход (таймаут) нельзя трактовать ни как успех, ни как отказ; идемпотентность обеспечена контрактом адаптера по `reference` (AD-004), но ядро обязано не превратить ретрай в новое списание; отзыв мандата (ADR-009) может произойти в момент списания — гонка должна разрешаться в пользу запрета.

## Decision

1. **Каждое списание идемпотентно по ключу ТСП.** `POST /v1/payments` со `subscriptionId` требует `Idempotency-Key`; повтор с тем же ключом и телом возвращает **тот же** `paymentId`, состояние не меняется (расширение AD-003 на списания). Повтор с тем же ключом и другим телом — `409 IDEMPOTENCY_CONFLICT`.
2. **Дополнительный бизнес-ключ периода.** Для защиты от повторного списания за один и тот же период при новом `Idempotency-Key` шлюз поддерживает уникальность в пределах мандата по ключу периода (`subscriptionId` + период/`billId`, формат — по сервису СБП `[ТРЕБУЕТ ПРОВЕРКИ]`). Повтор за уже закрытый период — отклонение, если иное не разрешено параметрами мандата (например, явно разрешённые повторные попытки после отказа).
3. **Неопределённый исход — не повод повторять.** Если вызов регистрации списания в ОПКЦ завершился таймаутом/ошибкой без ответа, списание остаётся в состоянии неопределённого исхода (`CREATED`/техническое подсостояние `OPKC_UNKNOWN`) — **не** `PAID` и **не** `FAILED`. Новых отправок нет до разрешения: сначала запрос статуса у ОПКЦ (`getPaymentStatus`) и/или сверка; повторный вызов возможен только с тем же `reference` и только если подтверждено, что операция в СБП не создана (шаблон правила `unknown-outcome-no-resend`).
4. **Зачисление — только из `PAID`.** Состояние неопределённого исхода не даёт зачисления; AD-005 не ослабляется.
5. **Гонка «отзыв ↔ списание» разрешается в пользу отзыва.** Если мандат отозван до подтверждения списания, новое списание не создаётся; уже отправленное — доводится до терминального состояния и, при завершении списания, компенсируется возвратом (сага ADR-005). Проверка мандата выполняется и перед отправкой, и перед зачислением.
6. **Дедупликация нотификаций** — по `eventId` (AD-003, ADR-004); повторная нотификация `PAID` по завершённому списанию состояние не меняет и алертит.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Ключ + бизнес-ключ периода + UNKNOWN без повторной отправки (выбран)** | Исключает двойное списание даже при пересоздании ключа ТСП; неопределённость не превращается в деньги | Нужны состояние `OPKC_UNKNOWN`, опрос статуса и сверка; больше кода и тестов |
| Полагаться только на `Idempotency-Key` ТСП | Просто, переиспользует существующее | ТСП, пересоздавший ключ за тот же период, спишет дважды — финансовый инцидент |
| Слепой ретрай при таймауте | Не теряет списание при кратком сбое | При «ответе, который не дошёл» даёт второе списание; недопустимо |
| At-most-once: при таймауте сразу `FAILED`, без опроса | Просто | Теряются успешные списания — неоплаченные подписки, споры, ручной разбор |
| Возложить защиту целиком на адаптер/ОПКЦ | Меньше логики в ядре | Протокол НСПК может не давать идемпотентности по периоду; ядро всё равно обязано владеть инвариантом |

## Consequences

### Positive

- Двойное списание у плательщика исключается на уровне ядра, а не только на уровне протокола.
- Неопределённый исход перестаёт быть источником финансовых ошибок: операция не «забывается» (опрос статуса + сверка) и не создаётся дважды.
- Инвариант AD-005 (зачисление только из `PAID`) сохраняется без ослабления.

### Negative

- Добавляется техническое состояние неопределённого исхода и логика опроса статуса — сложность модели и тестов (гонки, поздние события).
- Бизнес-ключ периода требует согласования формата с сервисом СБП и ТСП; при несовпадении семантики периода возможны ложные отказы (митигируется параметрами мандата).
- Отклонение повторного списания за период может быть воспринято ТСП как ошибка интеграции — нужна внятная модель ошибок и документация.

## Reversibility

**reversible.** Правила идемпотентности и обработки неопределённости — логика ядра поверх существующих механизмов; их можно уточнять, не меняя статусную модель и контракт транспорта. Ослабление инварианта «без повторной отправки при неопределённости» недопустимо и потребовало бы отдельного решения с пересмотром финансовой модели.
