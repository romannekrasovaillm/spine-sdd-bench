# Дельта: sbp-subscriptions

- Route: Critical (полный Solutioning + человеческое решение A3 — см. `docs/solutioning-sbp-subscriptions.md`)
- Created: 2026-09-28
- Основание: ADR-008, ADR-009, ADR-010 (Proposed); значимость 10/15 (`arch control score`; с `criticality_or_exception` — 11/15)
- Затрагивает защищённые файлы: `ARCHITECTURE-SPINE.md`, `.arch-handoff/CONSTRAINTS.yaml`

## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика — подписки СБП. Сегодня каждый платёж требует QR и действия клиента; для подписок согласие подтверждается один раз, далее списания инициирует ТСП, а отзыв согласия прекращает списания. Автоплатежи ранее были вне scope принятого решения, поэтому изменение проводится дельтой поверх него: ядро, trust-зоны и транспорт не переписываются.

## ADDED

- When ТСП создаёт подписку (`POST /v1/subscriptions`), the СБП-шлюз shall создать мандат в состоянии `PENDING_CONSENT` и запустить регистрацию согласия через ОПКЦ (ADR-008).
- When плательщик подтверждает согласие в банке плательщика, the СБП-шлюз shall записать неизменяемое доказательство согласия и перевести мандат в `ACTIVE` (ADR-009, AD-011 spine).
- When ТСП инициирует списание по мандату (`POST /v1/payments` с `subscriptionId`), the СБП-шлюз shall допустить списание только при мандате `ACTIVE` и в пределах его лимитов, иначе отказать без обращения в ОПКЦ (AD-009 spine).
- When получен отзыв согласия, the СБП-шлюз shall немедленно перевести мандат в `REVOKED` и запретить новые списания (ADR-009).
- When вызов ОПКЦ по списанию завершается таймаутом, the СБП-шлюз shall оставить списание в состоянии неопределённого исхода (`OPKC_UNKNOWN`) и не повторять отправку до разрешения исхода опросом статуса/сверкой (AD-010 spine).
- When приходит повтор нотификации или запроса, the СБП-шлюз shall не изменять завершённое состояние и не создавать второй эффект (AD-003).
- When ТСП запрашивает состояние подписки или список списаний, the СБП-шлюз shall вернуть состояние мандата и списания через существующий контракт (аддитивные пути и события, §8 `docs/contracts/tsp-api.md`).
- When списание отклонено по мандату или лимиту, the СБП-шлюз shall вернуть канонический код ошибки и не создавать операцию в ОПКЦ.
- NFR подписок (доля успешных списаний, лаг отзыва, latency, нулевые негативные исходы) — `docs/nfr.md` §7.

## MODIFIED

- **Roadmap базового решения (`docs/solutioning.md` §1):** автоплатежи перенесены из «вне scope» в scope — причина: запрос бизнеса; реализация оформлена новым изменением, базовое решение не переписывается.
- **Контракт API ТСП (`docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`):** было v0.1 → стало v0.2 — добавлены пути `/v1/subscriptions*`, опциональные поля `subscriptionId`/`periodKey` в платеже, новые события и коды ошибок. Изменение аддитивное, breaking = 0 (проверено `arch contract-diff`).
- **Контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md`):** было v0.1 → стало v0.2 — добавлены операции `registerMandate`/`getMandateStatus`/`cancelMandate`/`createCharge`/`getChargeStatus` и события `mandate.*`; протокольные детали `[ТРЕБУЕТ ПРОВЕРКИ]` (документация НСПК). Граница «ядро ↔ адаптер» не меняется (AD-004/AD-008).
- **Статусная машина платежа (`docs/spec/state-machine.md` §6.1):** для платежей по подписке путь `CREATED → PAID → CREDITED → COMPLETED` без `QR_ISSUED`; добавлено техническое подсостояние `OPKC_UNKNOWN`. Переходы базового QR-платежа не меняются; зачисление — по-прежнему только из `PAID` (AD-005).
- **NFR (`docs/nfr.md`):** добавлен §7 с измеримыми целями подписок и негативными критериями (0 списаний без мандата, 0 двойных списаний, 0 повторных отправок при неопределённости).

- **Spine (`ARCHITECTURE-SPINE.md`):** добавлены Proposed-блоки AD-009, AD-010, AD-011; обновлены раздел Deferred (подписки возвращены в scope; календарь списаний оставлен вне scope — отвергнутый `gateway-scheduler`) и раздел «Контракты и версии» (v0.2). Существующие AD-001..AD-008 не переписываются.

## План отката

1. **Сигналы отката:** доля успешных списаний ниже порога; списание без действующего согласия; рост жалоб/споров; расхождение мандатов со СБП; инцидент вендора транспорта.
2. **Мгновенный стоп:** feature-флаг `subscriptions.charges=off` — новые списания не создаются; мандаты остаются читаемыми; списания в полёте доводятся или компенсируются возвратом.
3. **Пошагово:** отключить создание мандатов → отключить списания → вернуть ТСП на разовые QR (базовая способность не изменялась). Обновления БД — аддитивные (новые сущности/таблицы), деструктивной миграции нет.
4. **Данные не удаляются:** записи согласий и операций хранятся (регуляторно и для аудита) даже после выключения функциональности.
5. **Владелец решения об отказе:** владелец продукта «СБП-приём» + ИБ (при риске для ПДн).
6. **Критерий успешного отката:** после выключения новых списаний нет; незавершённых списаний нет; сверка чистая; разовые платежи работают штатно; записи согласий читаемы.

## Критерии приёмки

Позитивные:

- [ ] Сквозной сценарий: создание подписки → подтверждение согласия → списание → `PAID` → `CREDITED` → `COMPLETED`; вебхуки `subscription.activated`, `charge.completed` доставлены (идемпотентно по `eventId`).
- [ ] Возврат списания проходит существующую сагу; полный возврат → `REFUNDED`; мандат при этом не меняется.
- [ ] Контракт v0.2 обратно совместим: `arch contract-diff` между v0.1 и v0.2 — PASS, breaking = 0; клиент v0.1 продолжает работать.

Негативные:

- [ ] Списание при мандате `PENDING_CONSENT`/`PAUSED`/`REVOKED`/`EXPIRED` отклоняется (`SUBSCRIPTION_NOT_ACTIVE`/`CONSENT_REVOKED`), обращения в ОПКЦ нет (тест-шпион на адаптер).
- [ ] Списание сверх лимита разового/периода отклоняется (`SUBSCRIPTION_LIMIT_EXCEEDED`).
- [ ] Повтор списания с тем же `Idempotency-Key` → тот же `paymentId`, второй проводки нет; повтор за закрытый период → `CHARGE_PERIOD_CLOSED` (правило `idempotency-key`).
- [ ] Таймаут ОПКЦ → `OPKC_UNKNOWN`, повторной отправки нет, исход разрешается `getChargeStatus`/сверкой (правило `unknown-outcome-no-resend`).
- [ ] Отзыв мандата в момент списания: зачисление не выполняется; повторный отзыв идемпотентен (гонка разрешается в пользу запрета).
- [ ] Повторная нотификация СБП по завершённому списанию состояние не меняет (дедуп по `eventId`).
- [ ] ПДн плательщика отсутствуют в логах и метках метрик (правило `no-pii-in-logs`); запись доказательства согласия неизменяема (правило `append-only-journal`).
