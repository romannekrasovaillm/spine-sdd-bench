# Handoff: эпик «Подписки СБП» (рекуррентные C2B-списания)

Epic-context для кодового харнесса. Реализуется поверх уже принятого решения C2B-приёма. Канонический пакет `.arch-handoff/` относится к базовому эпику; этот файл — пакет изменения (обнови/пересобери `arch handoff` на A2). Полные источники: `docs/solutioning-sbp-subscriptions.md`, ADR-008..ADR-010, `docs/spec/subscriptions.md`, `docs/contracts/tsp-api.md` §8, `docs/nfr.md` §7.

## 1. Цель и гипотеза результата

Дать ТСП (кино, ЖКХ, связь) рекуррентные списания по согласию плательщика: плательщик подтверждает согласие один раз в своём банке, далее ТСП инициирует списания без его участия, отзыв согласия немедленно прекращает списания. Успех: списания проходят сквозным путём, двойных и несанкционированных списаний нет, отзыв действует. Базовая способность (разовые QR) не деградирует.

## 2. Связывающие инварианты (Rule — дословно)

- AD-002: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера (ревью + fitness-тест на каждый переход).»
- AD-003: «Повторная доставка любого сообщения не изменяет уже завершённое состояние. Fitness: тест „повторная нотификация/повторный запрос → состояние не меняется, результат идемпотентен“.»
- AD-005: «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Fitness: проверка недостижимости зачисления из `CREATED`/`QR_ISSUED`.»
- AD-008 [ADOPTED]: ядро контрактно-независимо от транспорта; единственная зависимость — внутренний контракт адаптера ОПКЦ.
- AD-009: «Рекуррентное списание создаётся только при мандате в состоянии `ACTIVE` и в пределах его лимитов; при отсутствии, отзыве (`REVOKED`), истечении (`EXPIRED`) или приостановке (`PAUSED`) мандата обращение в ОПКЦ за списанием не выполняется.»
- AD-010: «При таймауте/отсутствии ответа ОПКЦ списание остаётся в состоянии неопределённого исхода — не `PAID` и не `FAILED`; повторная отправка запрещена до разрешения исхода запросом статуса/сверкой; зачисление возможно только из `PAID`.»
- AD-011: состояние мандата хранится и изменяется только в реестре мандатов шлюза; другие компоненты читают его только через API шлюза; расхождение со СБП разрешается в пользу запрета списаний.

## 3. Запрещено менять

- Существующие контракты v0.1 и поведение разовых QR-платежей (только аддитивные расширения; breaking = 0).
- AD-001, AD-004, AD-005, AD-006, AD-008 и ADR-001, ADR-003, ADR-005, ADR-006, ADR-007.
- Прямые правки `ARCHITECTURE-SPINE.md` вне активной дельты (`arch delta guard`).
- Протокол НСПК вне адаптера ОПКЦ; локальное переопределение spine запрещено — конфликт останавливает работу и эскалируется.

## 4. Контракты стыков

- **API ТСП (v0.2, `/v1`)**: `POST /v1/subscriptions` (+`Idempotency-Key`), `GET /v1/subscriptions/{id}`, `.../pause|resume|cancel`, `GET /v1/subscriptions/{id}/payments`, списание — `POST /v1/payments` с `subscriptionId`+`periodKey`. Статусы мандата: `PENDING_CONSENT|ACTIVE|PAUSED|REVOKED|EXPIRED`. Статусы платежа — существующие. Ошибки: `SUBSCRIPTION_NOT_ACTIVE`, `SUBSCRIPTION_LIMIT_EXCEEDED`, `CHARGE_PERIOD_CLOSED`, `CONSENT_REVOKED` (Problem Details, RFC 9457).
- **Внутренний контракт адаптера ОПКЦ (v0.2)**: `registerMandate`, `getMandateStatus`, `cancelMandate`, `createCharge`, `getChargeStatus`; события `mandate.registered|revoked|expired`; списание — события `payment.*` с `mandateRef`. Идемпотентность мутаций — по `reference` (+ `periodKey` для списания); неопределённость — явный `UNKNOWN`.
- **Сквозные идентификаторы**: `subscriptionId` (= reference мандата), `paymentId` (= reference списания), `eventId` для дедупликации событий, `periodKey` для защиты от повтора за период.
- **Идемпотентность**: все POST — `Idempotency-Key`; повтор с тем же ключом/телом → тот же ресурс; другое тело → `409`.

## 5. Критерии приёмки (проверяемые)

Позитивные: создание подписки → подтверждение согласия → списание → `PAID` → `CREDITED` → `COMPLETED`; вебхуки `subscription.activated`/`charge.completed` идемпотентны по `eventId`; возврат списания — сага, мандат не меняется; `arch contract-diff` v0.1→v0.2 — breaking = 0.

Негативные (обязательны): списание без `ACTIVE`-мандата и сверх лимита отклоняется без обращения в ОПКЦ (тест-шпион); повтор `Idempotency-Key` → один `paymentId`, одна проводка; повтор за закрытый период → `CHARGE_PERIOD_CLOSED`; таймаут ОПКЦ → `OPKC_UNKNOWN`, отправка ровно одна, исход решается опросом; отказ АБС → платёж остаётся `PAID` (не `CREDITED`); гонка «отзыв ↔ списание» → зачисления нет; повтор нотификации состояние не меняет; ПДн нет в логах/метриках; запись согласия append-only.

Fitness-шаблоны: `consent-before-auto-action`, `idempotency-key`, `unknown-outcome-no-resend`, `no-pii-in-logs`, `append-only-journal`, `single-source-of-truth`.

## 6. План отката

Триггеры: списание без согласия; доля успешных списаний ниже порога; расхождение мандатов со СБП. Откат: `subscriptions.charges=off` (мгновенный стоп) → доведение/компенсация списаний в полёте → `subscriptions.create=off` → ТСП на разовые QR. Данные согласий и операций не удаляются (регуляторно). Владелец решения: продукт + ИБ. Успех: новых списаний нет, сверка чистая, разовые платежи штатны.

## 7. Финализация

Работа завершается git-коммитом в рабочем репозитории; результат забирается из `git log`. Тесты и fitness-проверки — по `.arch-handoff/CONSTRAINTS.yaml` (правила `mandate-*`, `unknown-outcome-*`, `spine-subscription-*`).

## 8. Контракт результата (headless)

Прогон обязан завершиться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

При непустом `conflicts_with_prior_decisions` реализация останавливается и эскалирует, а не «чинит» решение молча. При `blocked` — перечислить недостающий вход (например, документация НСПК по сервису мандатов).
