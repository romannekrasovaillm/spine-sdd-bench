## Находки

1. [blocker] **Протокол рекуррентных платежей НСПК не получен** — поля мандата, статусы, тайминги уведомлений и наличие `revokedAt` неизвестны. REQ-REC-1..3, REQ-REC-8 и вся машина согласия опираются на непроверенные предположения.
   Свидетельство: `docs/solutioning.md` §9 (gap «Точный протокол НСПК»); `docs/spec/consent-state-machine.md` (шапка `[ТРЕБУЕТ ПРОВЕРКИ]`); `DELTA.md` REQ-REC-1.
   Чинить: получить документацию НСПК (внешний вход), уточнить адаптерный контракт.

2. [blocker] **ADR-011 не имеет человеческого решения A3** — правило «отзыв ↔ списание в полёте» меняет права плательщика и финансовую семантику; без A3 реализация выберет произвольное поведение.
   Свидетельство: `docs/adr/ADR-011-...md` — Status «Proposed (требует человеческого решения A3)»; `DELTA.md` — запрет новых списаний после `revokedAt`.
   Чинить: A3 с участием юристов/комплаенса.

3. [major] **Правило «запрет по `revokedAt`» нереализуемо, если ОПКЦ не даёт время отзыва** (даёт только факт). Тогда граница «до/после отзыва» неопределима, и часть списаний станет спорной.
   Свидетельство: ADR-011, решение «запрет по времени отзыва `revokedAt`, полученному от ОПКЦ».
   Чинить: подтвердить наличие `revokedAt` в протоколе; иначе определить fallback (например, запрет с момента получения нотификации + расширенная сверка).

4. [major] **`maxTotalAmount` не обеспечен поведением**: не определено, что происходит при исчерпании суммарного лимита (авто-стоп? перевод в `SUSPENDED`? отказ следующего списания?).
   Свидетельство: `openapi/tsp-api.yaml` `ConsentRequest.maxTotalAmount` (optional); `docs/spec/consent-state-machine.md` — переходы по исчерпанию не описаны.
   Чинить: добавить переход/правило в спецификацию согласия.

5. [major] **Требование к ТСП формировать `billingId`** может не выполняться для ТСП с плавающей периодичностью (ЖКХ: начисления не равны календарному месяцу); при неверном `billingId` дедуп даст ложные конфликты или пропуски.
   Свидетельство: ADR-009, раздел Negative; `docs/contracts/tsp-api.md` §3.9.
   Чинить: регламент формирования `billingId` для пилотных ТСП; валидация.

6. [major] **Инвариант AD-009 пока текст-единственный**: шаблон `consent_before_auto_action` в CONSTRAINTS.yaml задаётся как требование, но исполняемая проверка появится только после кода; сейчас инвариант держится ревью.
   Свидетельство: `ARCHITECTURE-SPINE.md` AD-009 Rule; `CONSTRAINTS.yaml`.
   Чинить: применить `arch-be rules template apply consent-before-auto-action --ad AD-009` на этапе A2 (walking skeleton).

7. [minor] **Метрика «доля успешных продлений ≥ 95 %»** не имеет знаменателя и источника данных.
   Свидетельство: `PROBLEM.md`, «Гипотеза результата».
   Чинить: согласовать с бизнесом.

8. [minor] **Код `CONSENT_NOT_REVOCABLE` объявлен, но сценарий не описан** (когда согласие нельзя отозвать?).
   Свидетельство: `docs/contracts/tsp-api.md` §4.
   Чинить: либо описать, либо убрать из списка.

9. [minor] **`currency` в `ChargeRequest`/`ConsentRequest` имеет default RUB, но валюта не валидируется на несоответствие согласию** (например, списание в иной валюте).
   Свидетельство: `openapi/tsp-api.yaml` схема `ChargeRequest`.
   Чинить: guard «валюта списания = валюта согласия».

## Линза «стыки» (кратко)

- Адаптер ОПКЦ: идемпотентность мутирующих операций по `reference` (уже требование RFP) — рекуррентные операции обязаны её наследовать, иначе ретраи charge дают двойной мандат/списание. Свидетельство: `docs/contracts/opkc-adapter.md` §5; ADR-009.
- АБС: изменений нет; зачисление по `paymentId` — тот же идемпотентный путь (AD-005). Риск не обнаружен.
- Вебхуки: новые `consent.*` события обязаны быть идемпотентны у ТСП по `eventId` — требование уже зафиксировано (`docs/contracts/tsp-api.md` §5).

## Линза «данные/ПДн» (кратко)

- Мандат расширяет состав ПДн (данные плательщика, ссылка на банк). Требуется пересмотр модели угроз и сроков хранения согласий — см. `PROBLEM.md`, ADR-008 (Negative), `docs/nfr.md` §5. Не блокер архитектуры, но блокер A4 для ИБ.

## Что остаётся человеку-архитектору

1. **A3 по ADR-011** — правило отзыва и списания в полёте (юридическая семантика).
2. Утвердить лимиты/периодичность/TTL по документации НСПК (после получения).
3. Юридическое заключение: хранение доказательств согласия, сроки, соответствие 161-ФЗ/НПС.
4. Согласовать метрику успеха подписки с бизнесом.
5. Решить объём первой волны (только приём рекуррентных + отзыв, без ЛК банка).
6. Назначить независимое ревью пакета (судья ≠ автор) и владельца пилотных ТСП.
