# Epic-context: рекуррентные C2B-списания (подписки СБП)

## Цель

Расширить принятый СБП-шлюз (C2B-приём) рекуррентными списаниями по согласию плательщика — **аддитивно**: одноразовые QR-платежи и их потребители не меняются. ТСП (кинотеатры, ЖКХ, связь) оформляют согласие, плательщик активирует его в своём банке, ТСП инициирует списания за расчётные периоды. Код не реализует протокол НСПК (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`) — только мок-адаптер и ядро.

## Что строим

1. Агрегат **Согласие** (`Consent`) со статусной машиной `PENDING_PAYER → ACTIVE → REVOKED | EXPIRED` (+ `SUSPENDED`, `REJECTED`) — `docs/spec/consent-state-machine.md`.
2. **Списание** (`Charge`): `POST /v1/consents/{consentId}/charges` создаёт обычный платёж (`initiation=CONSENT`) в существующей статусной машине: `CREATED → PAID → CREDITED → COMPLETED`.
3. Расширение **мок-адаптера ОПКЦ**: `registerConsent`, `getConsentStatus`, `revokeConsent`, `createCharge`, `getChargeStatus`; события `consent.activated`, `consent.revoked`, `consent.rejected`, `payment.paid`.
4. **Отзыв** (ТСП и плательщик), дедуп нотификаций по `eventId`, правило «отзыв ↔ списание в полёте» (ADR-011).
5. **Сверка** согласий с ОПКЦ и дублей списаний по `(consentId, billingId)`.

## Стыки (контракты)

- **ТСП ↔ шлюз**: `openapi/tsp-api.yaml` v0.2 (аддитивно к v0.1); `docs/contracts/tsp-api.md` §3.6–3.10; события `consent.*`; результат списания — события `payment.*` с `consentId`. Все mutation — с `Idempotency-Key`; списание дополнительно с `billingId`.
- **Ядро ↔ адаптер ОПКЦ**: `docs/contracts/opkc-adapter.md` — новые операции мандата/списания, `reference` = `consentId`/`paymentId`, идемпотентность по `reference` обязательна.
- **Шлюз ↔ АБС**: без изменений — зачисление по `paymentId`, идемпотентно.

## Инварианты (Rule — дословно из `ARCHITECTURE-SPINE.md`)

- **AD-005**: «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Fitness: проверка недостижимости зачисления из `CREATED`/`QR_ISSUED`.»
- **AD-002**: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции.»
- **AD-003**: «Повторная доставка любого сообщения не изменяет уже завершённое состояние.»
- **AD-004**: «Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.»
- **AD-009**: «Рекуррентное списание создаётся только при согласии в статусе `ACTIVE` с совпадающими ТСП/счётом и в пределах `maxAmountPerCharge` и срока действия. Уникальность списания — пара `(consentId, billingId)` поверх обязательного `Idempotency-Key`. После `revokedAt` новые списания запрещены; списание в полёте обрабатывается по ADR-011.»

**Запрещено менять**: существующие пути/поля/события `/v1` одноразовых платежей; размещение протокольной логики НСПК вне адаптера ОПКЦ; зачисление из состояния, отличного от `PAID`.

## Критерии приёмки (обязательные негативные)

`ACCEPTANCE.md`: повтор с той же `(consentId, billingId)` → одно списание; отказ без `ACTIVE` без вызова ОПКЦ; отказ сверх лимита; после `revokedAt` новых списаний нет; `IN_FLIGHT` без `PAID` отменяется; недоступность ОПКЦ/АБС не теряет операцию; `contract_diff` breaking = 0.

## NFR (измеримые)

Активация согласия p95 < 30 с; отзыв p95 < 30 с и **0** списаний после `revokedAt`; двойных списаний — 0; окно биллинга выравнивается очередью (burst +300 TPS, лаг p95 < 5 мин, пик ≤ 1000 TPS); RPO=0, RTO ≤ 1 ч, доступность ≥ 99,95 % без изменений.

## Границы

В scope: создание/активация/отзыв согласия, списание, лимиты, дедуп, отзыв vs полёт, контракт, NFR. Вне scope: управление подписками из ЛК банка, изменение параметров согласия, C2C, диспуты.

## Откат

Фича-флаг `recurring_consents_enabled`; выключение останавливает новые согласия/списания, одноразовый контур продолжает работать; очередь дренируется, незавершённые компенсируются по ADR-011; обратной миграции нет (`ROLLBACK.md`).

## Блокеры до реализации

1. Протокол НСПК по рекуррентным платежам не получен (`[ТРЕБУЕТ ПРОВЕРКИ]`).
2. A3 по ADR-011 (правило «отзыв ↔ списание в полёте») не принято — ветку «в полёте» не кодировать до решения.

## Контракт результата

Завершать прогон JSON: `{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}`. `blocked` — корректный исход до A3/протокола; `conflicts_with_prior_decisions` — эскалация архитектору, не молчаливое отклонение.
