# ADR-010. Рекуррентные платежи — аддитивное расширение API ТСП `/v1` без ломающих изменений

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + владелец API ТСП
- Related: ADR-008, ADR-009, AD-001, `docs/contracts/tsp-api.md` §6

## Context

Контракт API ТСП v0.1 (`docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`) описывает мерчант-API одноразовых платежей. Он помечен как draft, но на него уже ориентируются интеграции, и в нём зафиксирована политика совместимости: ломающие изменения — только в `/v2` с окном поддержки обеих версий ≥ 6 месяцев; добавление опциональных полей — обратно совместимо (`docs/contracts/tsp-api.md` §6).

Добавление рекуррентных платежей — новая функциональность. Существующие одноразовые платежи (динамический/статический QR, кассовые ссылки) должны продолжать работать у потребителей **без изменения кода**.

## Decision

Расширять действующий `/v1` **только аддитивно**:

- новые ресурсы: `POST /v1/consents`, `GET /v1/consents/{consentId}`, `POST /v1/consents/{consentId}/revoke`, `POST /v1/consents/{consentId}/charges`, `GET /v1/payments/{paymentId}/charges/{chargeId}`;
- новые опциональные поля в существующих схемах (`Payment.consentId?`, `Payment.initiation?`) и новые события вебхуков (`consent.activated`, `consent.revoked`, `consent.rejected`) — существующий набор событий не меняется;
- результат рекуррентного списания — обычный платёж, доступный через существующий `GET /v1/payments/{paymentId}` (ТСП, уже опрашивающие статус, не меняют интеграцию).

Версия контракта `0.1.0 → 0.2.0` (minor; до 1.0 — совместимое расширение). Отдельная `/v2` не вводится. Любое **ломающее** изменение в будущем (переименование статусов, удаление поля) — только через `/v2` и deprecation-окно. Перед каждым релизом контракта — контрактный гейт: `openapi_lint` (обе версии) + `contract_diff` (должен показать только не-ломающие изменения).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| A. Новый `/v2` для рекуррентных платежей | Чистая граница версий | Удвоение поддержки; ТСП интегрируют два API; выигрыша нет, расширение аддитивно | Избыточно |
| B. Отдельный микросервис подписок со своим API | Изоляция домена | Дублирование аутентификации ТСП, вебхуков, статусов; расщепление истины о платеже (нарушает AD-002) | Противоречит единому источнику истины |
| C. Ломающее изменение `/v1` (переработать `PaymentRequest`) | Меньше сущностей | Ломает существующих потребителей; нарушает политику §6 | Недопустимо |
| D. Аддитивное расширение `/v1` | Существующие ТСП не меняют код; минимум поддержки; единая истина о платеже | `/v1` растёт; нужна дисциплина «только добавление» | **Выбран** |

## Consequences

### Positive

- Нулевая миграция существующих потребителей: одноразовые платежи не затронуты.
- Рекуррентные списания видны в общей модели платежа и в общем контуре вебхуков.
- Контрактный гейт (`openapi_lint` + `contract_diff`) делает сохранение совместимости проверяемым, а не обещанным.

### Negative

- Контракт `/v1` усложняется: больше сущностей и полей, выше цена чтения и валидации.
- Обязательное для новых вызовов поле `billingId` требует дисциплины интеграции ТСП (см. ADR-009).
- Риск «расползания» `/v1` — требует постоянного контрактного гейта.

## Reversibility

**reversible.** Аддитивные ресурсы и поля можно вывести через deprecation (`Deprecation`/`Sunset`); существующие потребители при этом не страдают.

**Expiry:** при накоплении ломающего требования или > 2 неподдерживаемых «слоёв» расширений — пересмотр с выпуском `/v2`.
