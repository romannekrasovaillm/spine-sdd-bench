## 1. Оценка значимости изменения и маршрута

**Маршрут: Critical.** Инструмент `significance_score` (Spine) по 15 каноническим триггерам дал
**score 8**; сработали триггеры:

| Триггер | Почему сработал |
|---|---|
| `security_boundary_change` | Списание без активного действия клиента: авторизацией становится согласие, а не операция. Это смена модели авторизации (критический триггер → маршрут Critical вне зависимости от score) |
| `financial_impact` | Новый класс финансовых операций (рекуррентные списания со счетов плательщиков) |
| `consistency_model_change` | Появляется сущность, живущая дольше платежа (согласие) и порождающая много списаний; добавляется сверка согласий |
| `api_contract_change` | Новые методы API ТСП и новые поля (аддитивно) |
| `data_contract_change` | Новая модель данных «согласие» (в т.ч. ПДн-минимум плательщика) |
| `new_component` | Реестр согласий + расширение модели/сверки/нотификаций в ядре |
| `new_datastore` | Персистентное состояние согласий в БД шлюза |
| `significant_nfr` | Новые измеримые NFR: действенность отзыва, отсутствие двойных списаний, предуведомление |

**Что это значит для процесса.** Fast/Standard-маршрут недостаточен: это платежи, КИИ и необратимая
после запуска модель авторизации. Требуется полный Solutioning (спайн + ADR + NFR), **обязательная
человеческая точка A3**, walking skeleton до массовой генерации и evidence-гейты A4/A5. Дельта-спека
(`delta-spec`) применяется как форма описания изменения, но **не заменяет** полное решение.

**Почему не «просто критический».** Значимость не в объёме кода (его немного: аддитивные методы +
новая сущность), а в цене ошибки и обратимости: неверная семантика отзыва или двойное списание —
финансовый и регуляторный инцидент. Поэтому глубина проектирования — по риску, а не по размеру диффа.

## 2. Влияние на принятую архитектуру

### 2.1 Затронутые инварианты спайна

| Инвариант | Влияние | Что именно |
|---|---|---|
| AD-001 Изоляция платёжного контура | **не изменяется** | Логика согласий — внутри шлюза; внешние каналы — через адаптеры |
| AD-002 Единый источник истины | **расширяется** | Согласие — новая сущность БД шлюза; переходы согласия атомарны (статус + outbox + аудит), как у платежа |
| AD-003 Идемпотентность | **расширяется** | `Idempotency-Key` на оформление/отзыв согласия и на каждое списание; повтор не меняет состояние |
| AD-004 Единственный адаптер ОПКЦ | **расширяется** | В контракт адаптера добавляются mandate-операции и события; протокол НСПК по-прежнему знает только адаптер |
| AD-005 Зачисление только из `PAID` | **не изменяется** | Списание по согласию зачисляется по тому же правилу: только из подтверждённого `PAID` |
| AD-006 Trust-зоны | **не изменяется** | Новых trust-зон нет; ПДн плательщика — в существующем платёжном контуре |
| AD-007 НПС/КИИ/ПДн | **расширяется** | Согласие хранит ПДн-минимум; добавляются предуведомление плательщика и аудит отзывов |
| AD-008 Стратегия (гибрид) | **расширяется** | Вендор транспорта обязан поддержать mandate-операции; ядро остаётся контрактно-независимым |
| **AD-009 (новый, Proposed)** | **добавляется** | Списание только при `mandate.status = ACTIVE` и в пределах лимитов; отзыв немедленно блокирует новые списания |

Новый инвариант AD-009 добавлен в `ARCHITECTURE-SPINE.md` в статусе `Proposed` (действует после
ратификации ADR-008).

### 2.2 Что меняется

- **Модель данных:** новая сущность «согласие» (`mandateId`, `tspId`, `payerRef`, лимиты, срок, статус,
  ссылки на ОПКЦ), журнал согласий в аудите.
- **Статусная машина:** добавляется отдельная модель согласия; **модель платежа не меняется** — списание
  проходит те же переходы, что и платёж по QR.
- **Сверка (ADR-004):** ежечасная сверка расширяется на согласия; новое расхождение-триггер.
- **Нотификации (ADR-004):** новые события ТСП по согласиям, механика доставки прежняя.
- **Контракт API ТСП:** аддитивные методы/поля (см. §4).
- **Контракт адаптера ОПКЦ:** новые методы/события (ядро ↔ транспорт).

### 2.3 Что не меняется

- QR-сценарии (динамический/статический QR, кассовые ссылки), возвраты-сага, зачисление из `PAID`,
  trust-зоны и сегментация, стратегия гибрида (ADR-007), выбранный транспортный слой.
- Существующие потребители API ТСП: новых обязательных полей и удалённых методов нет.
- Ограничения родительского спайна: C2C/выплаты остаются `Deferred`.

## 3. Архитектурное решение

Полная запись решения — **ADR-008** (альтернативы, последствия, обратимость). Кратко:

1. **Согласие плательщика — первоклассная сущность ядра** со статусной моделью
   `PENDING → ACTIVE → (SUSPENDED) → REVOKED | EXPIRED | FAILED`. Хранится зеркало состояния ОПКЦ для
   предпроверок, аудита и сверки.
2. **Списание переиспользует существующую статусную машину платежа**; предпроверка «`ACTIVE` + лимиты»
   выполняется до обращения к ОПКЦ. Зачисление — по AD-005.
3. **Отзыв действует немедленно** и блокирует новые списания; отзыв идемпотентен и аудируется.
4. **Сверка согласий** — расширение ADR-004; расхождение → `SUSPENDED` + эскалация.
5. **Граница транспорта не меняется**: mandate-операции — во внутреннем контракте адаптера (AD-004/AD-008).

### 3.1 Рассмотренные альтернативы (сводно; детали — в ADR-008)

| Вариант | Итог |
|---|---|
| A. Отдельная сущность согласия + переиспользование статусной машины платежа | **выбран** |
| B. Состояния согласия внутри статусной машины платежа | отвергнут: смешение двух жизненных циклов, потеря ясности аудита |
| C. Без локального состояния согласия (каждый раз ОПКЦ) | отвергнут: нет предпроверок/лимитов, критическая зависимость от ОПКЦ (против AD-002, ADR-004) |
| D. Отдельный микросервис «Подписки» со своей БД | отвергнут: второй источник истины и распределённая транзакция внутри контура (против AD-001/AD-002) |
| E. Списания по расписанию инициирует ОПКЦ/вендор | отвергнут: утрата контроля над таймингом/лимитами; не подтверждён протоколом `[ТРЕБУЕТ ПРОВЕРКИ]` |

### 3.2 Решение, запрашиваемое у человека-архитектора (A3, machine-readable)

- **choice**: `mandate-as-core-entity + reuse-payment-state-machine` (вариант A)
- **rationale**: сохраняет единую финансово-аудируемую машину и доказанные идемпотентность/зачисление;
  локализует новое состояние (согласие) рядом с платежом; не трогает границы транспорта и QR-потоки.
- **constraints**: (1) списание только при `ACTIVE` и в пределах лимитов (AD-009, AD-005);
  (2) отзыв немедленно блокирует новые списания; (3) mandate-операции — только через адаптер ОПКЦ
  (AD-004); (4) ПДн плательщика — минимизация и защита (AD-007); (5) транспорт — после протокола НСПК
  и подтверждения поддержки вендором (ADR-007).
- **rejected options**: `inline-mandate-states`, `stateless-gateway`, `separate-subscriptions-service`,
  `operator-scheduled-pull` (см. §3.1).
- **expiry (пересмотр)**: протокол НСПК не поддерживает семантику отзыва/лимитов; вендор не реализует
  mandate-операции; регулятор ужесточает предуведомление. Плановая ревизия — 12 мес. эксплуатации.

Дополняют `docs/nfr.md` (раздел «Подписки»); проверяются на A4/A5. Регламентные значения уточняются по

| NFR | Цель | Метод проверки |
|---|---|---|

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (EARS)

- When плательщик отозвал согласие (событие `mandate.revoked`), the СБП-шлюз shall перевести согласие
  в `REVOKED` и отклонить любое последующее списание по нему.
- When поступает запрос списания по согласию в статусе, отличном от `ACTIVE`, the СБП-шлюз shall
  отказать (`422 MANDATE_NOT_ACTIVE`) и не создавать платёж.
- When запрошено списание, превышающее лимит согласия, the СБП-шлюз shall отказать
  (`422 MANDATE_LIMIT_EXCEEDED`) до обращения к ОПКЦ.
- When повторно доставлен запрос списания с тем же `Idempotency-Key`, the СБП-шлюз shall вернуть тот же
  `paymentId` без второго списания.
- When получено подтверждение оплаты по списанию, the СБП-шлюз shall зачислить средства только из
  состояния `PAID` и идемпотентно (AD-005).
- While согласие `ACTIVE`, the СБП-шлюз shall участвовать в ежечасной сверке согласий с ОПКЦ.
- If сверка выявила «ОПКЦ `REVOKED`, у нас `ACTIVE`», then СБП-шлюз shall перевести согласие в
  `SUSPENDED`, запретить новые списания и эскалировать.
- When оформляется согласие, the СБП-шлюз shall вернуть `mandateId` и не создавать платёж.
- Существующие сценарии: When ТСП использует QR-сценарий, the СБП-шлюз shall работать без изменений
  (регресс-набор C2B-приёма остаётся зелёным).

### 6.2 План отката

- **До боевых согласий:** откат = выключить фиче-флаг `subscriptions`; новые методы перестают
  приниматься, QR-поток и уже принятые платежи не затрагиваются. Данные не мигрируются.
- **После появления согласий:** «просто выключить» нельзя — требуется (1) остановить новые списания,
  (2) провести финальную сверку согласий с ОПКЦ, (3) закрыть/отозвать незавершённые согласия,
  (4) сохранить аудит. Окно и порядок — по runbook дежурной смены.
- **Сигналы отката (триггеры):** любое списание после подтверждённого отзыва; рост расхождений сверки
  согласий; деградация QR-потока после включения; предписание комплаенса по предуведомлению.
- **Владелец решения об откате:** архитектор платёжного контура + дежурная смена SRE/платёжный
  мониторинг; при регуляторном сигнале — комплаенс с эскалацией на A3.
- **Обратимость:** `reversible` на старте, `costly` после боевых согласий (см. ADR-008, Reversibility).

## 7. Что остаётся на решение человека-архитектора и почему

Агент подготовил и обосновал решение, но следующие пункты **не могут быть закрыты автоматически**:

1. **A3 по ADR-008 (Proposed → Accepted).** Маршрут Critical требует обязательной человеческой точки.
   Причина: смена модели авторизации финансовых операций.
2. **Регуляторная политика предуведомления плательщика** (срок, канал, содержание, необходимость
   повторного подтверждения) — комплаенс/ИБ + 161-ФЗ; требует юридической трактовки, не выводится из кода.
3. **Семантика и SLA отзыва согласия** (мгновенная блокировка vs регуляторное окно) — юристы + НСПК
   `[ТРЕБУЕТ ПРОВЕРКИ]`: зависит от регламента оператора.
4. **Модель авторизации списаний** (достаточно ли mTLS + `X-API-Key` + `Idempotency-Key`, или требуется
   подпись запроса списания/дополнительный фактор) — решение ИБ; влияет на контракт.
5. **Лимиты согласий** (макс. разовое/период/срок, декларируемые и контролируемые) — бизнес + регламент
   НСПК; влияет на модель данных и проверки.
6. **Расширение scope вендора транспорта** (обязан ли вендорский адаптер поддержать подписки; как это
   отразится на RFP и SLA) — закупки + проектный офис; внешний вход.
7. **Границы «подписки» как продукта** (хранит ли шлюз расписание/план или только согласие, а расписание
   остаётся у ТСП) — продукт/ТСП; влияет на объём модели.
8. **Приёмка пакета** — подтверждение, что дельта влита после A3 и AD-009 переведён из `Proposed`.

## 8. Готовность к handoff (следующий шаг после A3)

Пакет спроектирован как источник для будущего `.arch-handoff/` (навык `handoff-packaging`): после A3
необходимо скомпилировать epic-context 800–1500 токенов (цель, стыки, инварианты AD-009/AD-005/AD-003
**дословно**, запреты), приложить ADR-008, дельта-спеку, расширенные контракты и NFR, а критерии приёмки
из §6.1 передать как проверяемые (негативные сценарии: отзыв, лимит, повтор, расхождение сверки).
Обязательный headless-контракт результата: `{"status": complete|partial|blocked, ...}`; конфликт с
инвариантами — остановка и эскалация.

|---|---|---|
| Протокол НСПК по подпискам (операции, лимиты, тайминги, отзыв) | точный контракт адаптера ОПКЦ | Проектный офис / НСПК |
| Регламент предуведомления плательщика | политика REQ-SUB-6 | Комплаенс/ИБ |
| Поддержка mandate-операций вендором транспорта | scope RFP, SLA | Закупки + архитектор |
| Лимиты согласий | REQ-SUB-4 | Бизнес + НСПК |
| Доступность АБС в ночные окна списаний | SLA зачисления | Архитектор + владелец АБС |
