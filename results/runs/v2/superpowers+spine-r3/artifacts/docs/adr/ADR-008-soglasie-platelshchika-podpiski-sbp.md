# ADR-008. СБП-подписки: согласие плательщика как первоклассная сущность ядра, списание по согласию через существующую статусную машину

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + бизнес
- Модель-автор: qwen-code (agent)
- Related: ADR-001, ADR-002, ADR-004, ADR-005, AD-003, AD-005, AD-009 (new)

## Context

ТСП (онлайн-кинотеатры, ЖКХ, операторы связи) просят **рекуррентные C2B-списания по согласию
плательщика** — «подписки СБП». Сегодня каждый платёж требует активного действия клиента (сканирование
QR/переход по ссылке), что неприемлемо для регулярных списаний (месячная подписка, платёж по счётчику,
связь).

Силы и ограничения:

- **Внешний протокол.** Механизм согласий/автоплатежей определяется протоколом ОПКЦ СБП; точные
  операции, тайминги и требования к предуведомлению плательщика публично не раскрыты и получаются по
  договору — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]` (как в ADR-003, ADR-007).
- **Существующее решение.** Уже приняты: выделенный шлюз с outbox (ADR-001), статусная машина платежа с
  идемпотентностью (ADR-002), at-least-once нотификации + DLQ + сверка (ADR-004), зачисление только из
  `PAID` и возвраты-сага (ADR-005), изолированный адаптер ОПКЦ (ADR-003, ADR-007). Согласие — новая
  сущность, живущая **дольше** одного платежа и порождающая много списаний.
- **Регуляторика.** 161-ФЗ (защита при переводах), 152-ФЗ (ПДн плательщика), 115-ФЗ (ПОД/ФТ),
  требования КИИ (187-ФЗ). Рекуррентное списание **без активного действия клиента в момент списания**
  смещает границу авторизации: авторизация — это само согласие, а не операция.
- **Гибрид (ADR-007).** Транспорт — вендорский; ядро (в т.ч. модель согласий) — собственная разработка;
  вендор обязан поддержать mandate-операции (`[ТРЕБУЕТ ПРОВЕРКИ]`).

## Decision

1. **Согласие плательщика (mandate) — первоклассная сущность ядра** в БД шлюза, со своей статусной
   моделью: `PENDING → ACTIVE → (SUSPENDED) → REVOKED | EXPIRED | FAILED`. Согласие связывает ТСП,
   псевдоним плательщика (`payerRef`, минимизация ПДн), лимиты и срок. Хранится зеркало состояния ОПКЦ
   для локальных предпроверок, аудита и сверки.
2. **Списание по согласию переиспользует существующую статусную машину платежа** (ADR-002):
   платёж создаётся со ссылкой `mandateId` и `Idempotency-Key`; предпроверка «согласие `ACTIVE` и в
   пределах лимитов» выполняется **до** вызова ОПКЦ; дальнейшие переходы и зачисление — без изменений
   (`PAID → CREDITED → COMPLETED`, зачисление только из `PAID`, AD-005).
3. **Отзыв согласия действует немедленно**: переход в `REVOKED` блокирует любые новые списания
   (инвариант AD-009). Отзыв принимается из двух источников (ОПКЦ-событие, ТСП-запрос) и идемпотентен.
4. **Сверка согласий** расширяет сверку ADR-004: ежечасно по открытым согласиям; расхождение
   «ОПКЦ `REVOKED`, у нас `ACTIVE`» → `SUSPENDED` + эскалация (списания запрещены до разрешения).
5. **Авторизация и контроль списаний** (в границах существующей модели ADR-006): mTLS + `X-API-Key`
   ТСП, `Idempotency-Key` на списание, серверная проверка лимитов согласия, неизменяемый аудит отзыва.
   Предуведомление плательщика — по регламенту ОПКЦ/161-ФЗ; **точная политика (срок/канал/содержание и
   необходимость доп. подписи запроса списания) — предмет человеческого решения A3** (см. Consequences).
6. **Граница с транспортом не меняется** (AD-004, AD-008): mandate-операции добавляются во внутренний
   контракт адаптера ОПКЦ; ядро по-прежнему не знает протокола НСПК.

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Согласие — отдельная сущность + переиспользование статусной машины платежа** (выбран) | Одна финансово-аудируемая машина на все списания; согласие живёт независимо; идемпотентность и зачисление уже доказаны | Нужны новые состояния согласия и расширение сверки | — |
| B. Встроить состояния согласия прямо в статусную машину платежа | Меньше сущностей | Смешиваются два жизненных цикла (согласие ≫ платежа), «размножение» платежа плодит состояния согласия; сложнее аудит и отчётность | Две разные сущности с разным временем жизни нельзя свести в один автомат без потери ясности |
| C. Шлюз без собственного состояния согласия (каждый раз спрашивать ОПКЦ) | Нет дублирования, нет сверки согласий | Нет локальных предпроверок и лимитов; доступность ОПКЦ становится критической зависимостью на каждое списание; слабая аудируемость | Противоречит AD-002 (локальный источник истины) и ADR-004 (устойчивость к деградации ОПКЦ) |
| D. Отдельный микросервис «Подписки» со своей БД | Изоляция | Второй источник истины внутри платёжного контура; предпроверка согласия и создание платежа становятся распределённой транзакцией; нарушает связность AD-001/AD-002 | Дробление внутри одного платёжного контура даёт распределённую консистентность там, где сейчас есть локальная |
| E. Списания по расписанию инициирует ОПКЦ/вендор (pull), банк только принимает нотификации | Банку не нужен планировщик | Расписание/бизнес-логика — зона ТСП/банка; утрата контроля над таймингом, ретраями и лимитами; зависимость от roadmap оператора | Убирает контроль банка над ключевым процессом, не подтверждён протоколом `[ТРЕБУЕТ ПРОВЕРКИ]` |

## Consequences

### Positive

- Бизнес получает рекуррентные списания без QR; существующие QR-потоки не затрагиваются (аддитивно).
- Единая финансовая машина: зачисление по списанию проходит уже доказанный путь (AD-005) — ниже риск
  двойных зачислений и расхождений.
- Локальное зеркало согласия даёт предпроверки лимитов до внешнего вызова и доказуемый аудит отзывов.
- Границы транспорта сохранены — замена вендора по-прежнему не трогает ядро (ADR-007).

### Negative

- **Смещение границы авторизации:** списание без действия клиента требует усиленного контроля
  (лимиты, предуведомление, немедленный отзыв) и пристального внимания ИБ/комплаенса — это цена модели.
- Новая сущность + расширение сверки: рост объёма состояния и эксплуатационной нагрузки (согласия в
  сверке наравне с платежами).
- Зависимость от протокола НСПК по подпискам — внешний вход; без него контракт адаптера остаётся
  `[ТРЕБУЕТ ПРОВЕРКИ]` и реализация транспорта не начинается (как в ADR-003/ADR-007).
- Вендор транспорта должен поддержать mandate-операции; иначе вариант реализации меняется (эскалация).
- Предуведомление плательщика добавляет обязательный шаг, который может задерживать списание.

## Reversibility

**reversible на старте, costly после боевых согласий.** До эксплуатации изменение аддитивно и
отключается фиче-флагом (QR-поток не затронут). После появления действующих согласий «просто отключить»
нельзя: требуется отзыв/закрытие согласий, финальная сверка с ОПКЦ и сохранение аудита — это costly.
Триггеры пересмотра (expiry): (а) протокол НСПК не поддерживает требуемую семантику отзыва/лимитов;
(б) вендор транспорта не может реализовать mandate-операции; (в) регулятор ужесточает требования к
предуведомлению, делая модель неприменимой без пересмотра. Плановая ревизия — через 12 месяцев
эксплуатации.
