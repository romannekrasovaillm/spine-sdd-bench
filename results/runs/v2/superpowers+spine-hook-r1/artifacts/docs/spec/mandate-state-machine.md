# Согласие на рекуррентные списания (мандат) — спецификация переходов

- Status: Draft (для ревью на гейте A1 эпика СБП-подписок)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, AD-002, AD-003, AD-004, AD-005, AD-009, AD-010, AD-011, AD-012

Единый источник истины по праву списания — БД шлюза (расширение AD-002). Каждый переход согласия — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог». Рекуррентное списание — платёж принятой статусной машины (`docs/spec/state-machine.md`), отличающийся триггером и наличием основания `mandateId`.

## 1. Состояния согласия

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING` | Согласие создано, ожидает подтверждения плательщика (регистрация в ОПКЦ в процессе) | да |
| `ACTIVE` | Плательщик подтвердил согласие; списания в пределах лимитов разрешены | да |
| `SUSPENDED` | Согласие приостановлено банком/антифродом (списания запрещены) | да |
| `REVOKED` | Согласие отозвано плательщиком, ТСП или оператором; будущие списания запрещены | да |
| `EXPIRED` | Истёк срок действия согласия; будущие списания запрещены | да |

Терминальные: `REVOKED`, `EXPIRED`. Согласие — юридически значимая запись: терминальные состояния **не удаляются**, а хранятся (срок — по 152-ФЗ/правилам НСПК).

## 2. Модель инициатора

Согласие даётся **ТСП** (получателю средств); ТСП — законный инициатор каждого списания в пределах согласия. Планировщик шлюза — не самостоятельный субъект, а **исполнитель постоянного поручения ТСП** по расписанию согласия: инициатором в аудите указывается `TSP(SCHEDULER)` либо `TSP(API)`. Иных инициаторов нет. Это снимает развилку «кто вправе списать»: любой запуск (планировщик или вызов ТСП) — действие в рамках одного согласия одного ТСП.

## 3. Таблица переходов

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `PENDING` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен | запись согласия + outbox-событие «регистрация согласия в ОПКЦ»; аудит |
| M2 | `PENDING` | `ACTIVE` | подтверждение плательщика (событие ОПКЦ) | реквизиты совпадают с заявленными | сохранение `mandateRef`, `stateSyncedAt=now`, outbox `mandate.activated`, аудит |
| M3 | `PENDING` | `REVOKED` | отказ плательщика / ошибка регистрации (исчерпаны ретраи) | — | `reasonCode`, outbox-событие, аудит |
| M4 | `PENDING` | `EXPIRED` | таймер ожидания подтверждения | подтверждение не наступило | закрытие запроса в ОПКЦ, аудит |
| M5 | `ACTIVE` | `SUSPENDED` | стоп банка/антифрода (операторская операция, 4-eyes) | — | outbox `mandate.suspended`, аудит (кто, причина) |
| M6 | `SUSPENDED` | `ACTIVE` | снятие стопа + повторное подтверждение статуса в ОПКЦ | согласие не отозвано и не истекло; `stateSyncedAt=now` | outbox `mandate.activated`, аудит |
| M7 | `ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв плательщиком или ТСП (`POST …/revoke`) | — | idempotent; остановка будущих списаний, распространение отзыва в ОПКЦ, outbox `mandate.revoked`, аудит |
| M8 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | наступила `untilDate` (по расписанию) | — | outbox `mandate.expired`, аудит |
| M9 | `ACTIVE` | `ACTIVE` (без смены) | **списание** (планировщик или ТСП) | см. §4 | создание платежа с `mandateId`, `periodKey` |
| M10 | `PENDING`/`ACTIVE`/`SUSPENDED` | `REVOKED` | сверка/событие ОПКЦ: согласие отозвано (в т. ч. плательщиком в своём банке) | — | `stateSyncedAt=now`, остановка будущих списаний, алерт, аудит |
| M11 | `PENDING` | `ACTIVE` | сверка/событие ОПКЦ: согласие подтверждено | реквизиты совпадают | `stateSyncedAt=now`, outbox `mandate.activated`, аудит |
| M12 | `ACTIVE`/`SUSPENDED` | `SUSPENDED` | **остановка обслуживания подписок** (откат фиче-флага, инцидент): операторская операция, 4-eyes | — | запрет новых списаний, `stateSyncedAt=now`, аудит |
| M13 | `ACTIVE`/`SUSPENDED` | `REVOKED` | **массовый отзыв** при откате: операторская операция, 4-eyes | — | остановка списаний, `revokeMandate` в ОПКЦ по каждому согласию, outbox `mandate.revoked`, аудит |

`stateSyncedAt` обновляется на M2/M6/M10/M11 и при каждой периодической сверке.

## 4. Guard списания (M9)

Списание разрешено, только если выполнены **все** условия:

1. статус согласия — `ACTIVE`;
2. сумма ≤ `amountLimitPerCharge`; для автосписания планировщика сумма = `amountPerCharge`;
3. `periodKey` не списан ранее (уникальность `(mandateId, periodKey)`, §5);
4. **свежесть статуса**: `now − stateSyncedAt ≤ 15 мин` (baseline; срок — по регламенту НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`). Если свежесть не подтверждена — ядро запрашивает `getMandateStatus` у ОПКЦ **до** списания; при недоступности ОПКЦ или подтверждённом отзыве списание не выполняется (`MANDATE_STATE_STALE`), алерт;
5. факт предварительного уведомления плательщика зафиксирован (AD-012, §6).

## 5. Запрещённые переходы и идемпотентность

- **Списание невозможно при согласии не в `ACTIVE`** (AD-009). Из `PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED` — недостижимо; проверяется fitness/тестом.
- **После фиксации отзыва в шлюзе** (переход в `REVOKED`) — 0 будущих списаний (AD-010). Завершённые списания не откатываются автоматически (возврат — отдельная сага, ADR-005).
- **Один период — одно списание.** Ключ идемпотентности — `(mandateId, periodKey)`, где `periodKey` детерминированно выводится из расписания согласия (например `2026-10`), а не задаётся ТСП произвольно. Повторная инициация того же периода (тем же или другим инициатором) не создаёт второе списание; попытка провести тот же период с другой суммой → `409 IDEMPOTENCY_CONFLICT` (AD-011).
- **Зачисление — только из `PAID`** (AD-005) — распространяется без изменений.
- Параметры согласия (`amountPerCharge`, `amountLimitPerCharge`, `period`, `untilDate`, назначение) **иммутабельны** после `ACTIVE`. Изменение лимита/суммы/срока требует нового согласия плательщика.
- `REVOKED`/`EXPIRED` необратимы: повторное использование согласия невозможно, нужно новое.

## 6. Уведомление плательщика

- Предварительное уведомление — **внешнее звено** (банк плательщика / ОПКЦ): шлюз инициирует/ожидает его и получает подтверждение событием `charge.notification.sent` от адаптера ОПКЦ (ADR-012).
- В аудите фиксируются: инициатор, `mandateId`, `periodKey`, `amount`, факт и время уведомления.
- Вебхук ТСП `mandate.charge.scheduled` — **информационный для ТСП**, а не уведомление плательщика (см. `docs/contracts/tsp-api.md` §5).

## 7. Поток рекуррентного списания

```
Планировщик (исполнитель поручения ТСП) / вызов ТСП
   → guard §4 (ACTIVE, лимит, период не списан, свежесть ≤ 15 мин, уведомление отправлено)
   → создать платёж {mandateId, periodKey, amount} — та же машина: CREATED → PAID → CREDITED → COMPLETED
       (QR_ISSUED для рекуррентного списания НЕ используется: QR не выпускается)
   → зачисление только из PAID (AD-005)
   → outbox-нотификация ТСП (payment.completed), аудит с основанием mandateId
```

- Сбой на любом шаге — ретраи с идемпотентностью; при исчерпании — DLQ + runbook (ADR-004). Платёж не «теряется»: виден в сверке и отчёте незавершённых операций.
- Новых статусов платежа не вводится; `QR_ISSUED` рекуррентным списанием не используется.

## 8. Сверка и восстановление

- Кандидаты сверки с ОПКЦ: согласия в `PENDING`, `ACTIVE`, `SUSPENDED` (ежечасная сверка, ADR-004) **и опрос `getMandateStatus` перед списанием** при устаревшем `stateSyncedAt` (§4). Расхождение «у НСПК отозвано, у нас `ACTIVE`» → M10, стоп будущих списаний, алерт.
- Кандидаты сверки с АБС: рекуррентные платежи в `PAID`/`CREDITED` (суточная сверка, ADR-005).
- Расписание списаний хранится долговечно (RPO=0): после простоя планировщика — catch-up без потерь и дублей.
- **Остаточное окно отзыва.** Отзыв, данный плательщиком в своём банке, доходит до шлюза через ОПКЦ; между отзывом и получением шлюзом окно ограничено свежестью §4 (≤ 15 мин). Списание внутри этого окна при уже отозванном на стороне НСПК согласии невозможно после ответа `getMandateStatus`; при недоступности ОПКЦ списание не выполняется. Остаточный риск (отзыв между подтверждением свежести и проводкой) закрывается сверкой и возвратом по заявлению; фиксируется как принятый риск в ADR-008.

## 9. Согласованность с API ТСП

Маппинг статусов согласия наружу (TSP API §3.6): `PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`. Рекуррентное списание отражается как обычный платёж с полями `mandateId` и `periodKey`.
