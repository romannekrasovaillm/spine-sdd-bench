# Статусная машина платежа — спецификация переходов

- Status: Draft (база — для ревью на гейте A1; раздел согласий §7 — для A1′)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-002, ADR-005, ADR-008, AD-002, AD-003, AD-005, AD-009, AD-010

Единый источник истины состояния платежа — БД шлюза (ADR-002). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003).

## 1. Состояния

### Финансовые (видны ТСП в API)

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Платёж зарегистрирован в шлюзе, запрос к ОПКЦ в процессе | да |
| `QR_ISSUED` | QR/ссылка получена от ОПКЦ, ожидается оплата | да |
| `PAID` | **Подтверждённый НСПК статус** оплаты (нотификация или сверка) | да |
| `CREDITED` | Зачисление в АБС выполнено (получен `absDocId`) | да (как `creditingStatus`) |
| `COMPLETED` | Доведено до ТСП (вебхук доставлен/в очереди) | да |
| `FAILED` | Регистрация QR не удалась / платёж отклонён НСПК | да |
| `EXPIRED` | TTL истёк, оплата не наступила | да |
| `REFUNDED` | **Полный** возврат завершён | да |

### Технические (внутренние, наружу не выставляются)

| Состояние | Смысл |
|---|---|
| `ABS_PENDING` | Зачисление в АБС инициировано, ждём подтверждения (ретраи) |
| `NOTIFY_PENDING` | Вебхук ТСП поставлен в очередь (доставка — outbox/нотификатор) |

## 2. Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| T1 | — | `CREATED` | `POST /v1/payments` (новый `paymentId`) | валидный запрос, ТСП активен | запись платежа + outbox-событие «регистрация в ОПКЦ» |
| T2 | `CREATED` | `QR_ISSUED` | ответ адаптера ОПКЦ: `qrId` получен | `qrId` непустой | сохранить `qrId/qrUrl`, outbox-нотификация «создан» |
| T3 | `CREATED` | `FAILED` | ошибка регистрации в ОПКЦ (исчерпаны ретраи/DLQ) | ошибка не транзиентная | `errorCode`, outbox, вебхук `payment.failed` |
| T4 | `QR_ISSUED` | `PAID` | нотификация НСПК `PAID` (или подтверждение сверкой) | **сумма и получатель совпадают** (иначе → T7) | outbox-событие «зачисление в АБС» |
| T5 | `QR_ISSUED` | `EXPIRED` | таймер TTL | `PAID` не наступил | закрытие/отмена в ОПКЦ (по протоколу), вебхук `payment.expired` |
| T6 | `QR_ISSUED` | `FAILED` | нотификация НСПК об отклонении | — | `errorCode`, вебхук `payment.failed` |
| T7 | `QR_ISSUED` | `FAILED` | расхождение суммы/получателя в нотификации | платёж ещё не `PAID` | **зачисление запрещено** (AD-005), алерт + runbook |
| T8 | `PAID` | `CREDITED` | подтверждение АБС (`absDocId`) | вызов АБС идемпотентен по `paymentId` | сохранить `absDocId`, outbox-событие «доставка ТСП» |
| T9 | `PAID` | (остаётся `PAID`) | АБС недоступна / ретраи | — | подсостояние `ABS_PENDING`, ретраи, сверка; **финансовый статус не меняется** |
| T10 | `CREDITED` | `COMPLETED` | вебхук ТСП доставлен (или поставлен в очередь `NOTIFY_PENDING`) | — | outbox, аудит; вебхук `payment.completed` |
| T11 | `COMPLETED` | `REFUNDED` | сага возврата завершена (АБС списала + НСПК подтвердила) | **полный** возврат, платёж был зачислен | outbox, вебхук `refund.completed` |
| T12 | `COMPLETED` | (остаётся `COMPLETED`) | **частичный** возврат завершён | сумма возврата < суммы платежа | запись в `refunds[]`, вебхук `refund.completed` |
| T13 | `CREATED` | `PAID` | рекуррентное списание (`initiation=RECURRENT`), подтверждение НСПК (или сверкой) | согласие в `ACTIVE` того же ТСП/валюты/плательщика, сумма ≤ лимитов согласия | QR-шаг пропущен (нет `QR_ISSUED`); outbox-событие «зачисление в АБС» |
| T14 | `CREATED` | `FAILED` | рекуррентное списание отклонено (согласие не `ACTIVE` / превышен лимит / отказ НСПК) | `initiation=RECURRENT` | `errorCode` (`MANDATE_NOT_ACTIVE`/`MANDATE_REVOKED`/`MANDATE_LIMIT_EXCEEDED`…), вебхук `payment.failed`; **деньги не двигаются** |

## 3. Запрещённые переходы (инварианты)

- **Зачисление в АБС невозможно из любого состояния, кроме `PAID`** (AD-005). Из `CREATED`/`QR_ISSUED` — недостижимо; проверяется fitness-тестом.
- **Рекуррентное списание невозможно при согласии не в `ACTIVE`** (AD-009). Из `CREATED`/`PENDING_PAYER`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`FAILED`-согласия — недостижимо (уходит в T14); проверяется fitness-тестом.
- **Списание после фиксации `REVOKED` недостижимо** (AD-010). Гонка «списание ↔ отзыв» разрешается в одной транзакции (AD-002): если списание успело стать `PAID` до фиксации отзыва — оно доводится до `CREDITED`; иначе отклоняется (T14). Проверяется тестом гонки.
- Для `initiation=RECURRENT` состояние `QR_ISSUED` недостижимо (QR не выдаётся); короткий путь — T13/T14.
- `FAILED`/`EXPIRED`/`REFUNDED` — терминальные: из них переходов нет (повторные триггеры идемпотентны, AD-003).
- `REFUNDED` достижим **только** из `COMPLETED` (только после зачисления).
- Сумма и реквизиты платежа иммутабельны после `QR_ISSUED` (T2).
- `PAID` не может «откатиться» в `QR_ISSUED` — подтверждённый НСПК статус необратим; корректировки — только возвратом (сага).

## 4. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| API ТСП `POST /payments` | `Idempotency-Key` | возврат того же `paymentId`, состояние не меняется |
| Нотификация НСПК `PAID` | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Подтверждение АБС | `paymentId` | повторное подтверждение не создаёт вторую проводку (маппинг `paymentId → absDocId`) |
| Сага возврата | `refundId` | повторная инициация возврата возвращает существующий `refundId` |
| API ТСП `POST /mandates` | `Idempotency-Key` | возврат того же `mandateId`, повторной регистрации в ОПКЦ нет |
| API ТСП `POST /mandates/{id}/revoke` | `Idempotency-Key` + `mandateId` | повторный отзыв идемпотентен: состояние уже `REVOKED` |
| Рекуррентное списание `POST /payments` (RECURRENT) | `Idempotency-Key` | возврат того же `paymentId`, второе списание не создаётся |
| События согласия (`mandate.activated`/`revoked`/`expired`) | `eventId` | обработанный `eventId` игнорируется; поздний/повторный не меняет завершённое состояние |

## 5. Сверка и восстановление

- Открытые состояния (`QR_ISSUED`, `PAID`, `ABS_PENDING`) — кандидаты для сверки с НСПК и АБС (ADR-004, ADR-005): ежечасная сверка с НСПК, суточная с АБС.
- «У НСПК `PAID`, у нас нет» → дозапрос статуса → T4.
- «У нас `PAID`, у НСПК нет» → стоп-сигнал, эскалация.
- Платёж в `PAID` с недоступной АБС — остаётся `PAID`, виден в отчёте незавершённых операций, зачисление гарантируется сверкой (не «забывается»).
- Открытые согласия (`PENDING_PAYER`, `ACTIVE`) и «висящие» рекуррентные списания — кандидаты для сверки с НСПК. «У НСПК согласие активно, у нас нет» → дозапрос `getMandateStatus` → активация; «у нас `ACTIVE`, у НСПК нет» → стоп-сигнал, эскалация; «у нас `ACTIVE`, у НСПК `REVOKED`» → немедленный переход в `REVOKED` (AD-010).

## 6. Согласованность с API ТСП

Маппинг статусов наружу (TSP API §3.3): `CREATED`, `QR_ISSUED`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`, `REFUNDED` — без технических подсостояний (`ABS_PENDING`, `NOTIFY_PENDING` наружу не выставляются; `ABS_PENDING` отражается как `PAID` + поле `creditingStatus`).

Для рекуррентного платежа набор статусов тот же; `QR_ISSUED` не достигается, `initiation: RECURRENT` виден в `Payment` (v0.2). Статусы согласия — **отдельное** перечисление `MandateStatus` (TSP API §3.6), не смешивается со статусами платежа.

## 7. Согласие (mandate) — статусная машина

Единый источник истины состояния согласия — БД шлюза (расширение AD-002). Каждый переход — атомарная транзакция «состояние согласия + outbox + аудит»; повторные триггеры идемпотентны (AD-003). Согласие — обязательное условие рекуррентного списания (AD-009), его отзыв блокирует будущие списания (AD-010).

### 7.1 Состояния

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Согласие зарегистрировано в шлюзе, запрос к ОПКЦ в процессе | да |
| `PENDING_PAYER` | QR/ссылка выдана, ожидается подтверждение плательщика | да |
| `ACTIVE` | Плательщик подтвердил согласие; разрешены списания | да |
| `SUSPENDED` | Списания приостановлены (ТСП/ядром), согласие не отозвано | да |
| `REVOKED` | Согласие отозвано (плательщиком/его банком через НСПК или ТСП) | да |
| `EXPIRED` | Истёк срок согласия | да |
| `FAILED` | Регистрация/подтверждение не удались | да |

Терминальные: `REVOKED`, `EXPIRED`, `FAILED`.

### 7.2 Таблица переходов

| № | From | To | Триггер | Guard (условие) | Действие при переходе |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен | запись согласия + outbox «регистрация в ОПКЦ» |
| M2 | `CREATED` | `PENDING_PAYER` | ответ адаптера ОПКЦ: `mandateRef`+`qrId` получены | идентификаторы непустые | сохранить `mandateRef/qrId/qrUrl`, outbox-нотификация |
| M3 | `CREATED`/`PENDING_PAYER` | `FAILED` | ошибка регистрации/подтверждения (исчерпаны ретраи/DLQ, отклонение) | ошибка не транзиентная | `errorCode`, outbox, вебхук `mandate.failed` |
| M4 | `PENDING_PAYER` | `ACTIVE` | событие НСПК `mandate.activated` (или сверка) | дедупликация по `eventId` | фиксация реквизитов (иммутабельны), outbox, вебхук `mandate.activated` |
| M5 | `PENDING_PAYER` | `EXPIRED` | таймер срока подтверждения | подтверждение не наступило | закрытие в ОПКЦ, outbox |
| M6 | `ACTIVE` | `SUSPENDED` | приостановка (ТСП/ядро) | согласие не отозвано | outbox; новые списания запрещены |
| M7 | `SUSPENDED` | `ACTIVE` | возобновление | согласие не отозвано/не истекло | outbox; списания снова разрешены |
| M8 | `ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв: событие НСПК `mandate.revoked` или `POST /mandates/{id}/revoke` | — | outbox, вебхук `mandate.revoked`; **новые списания запрещены** (AD-010) |
| M9 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | истёк `validUntil` | — | outbox, вебхук `mandate.expired` |

### 7.3 Запрещённые переходы (инварианты)

- Рекуррентное списание невозможно, пока согласие не в `ACTIVE` (AD-009); из `REVOKED`/`EXPIRED`/`FAILED` — переходов нет (терминальные).
- Ключевые реквизиты (`tspId`, плательщик, `currency`, лимиты, срок) иммутабельны после `ACTIVE` (AD-009); изменение — только новое согласие.
- После фиксации `REVOKED` новые инициации списаний недостижимы (AD-010).
- `REVOKED` недостижим из `REVOKED` повторно (идемпотентность отзыва).

### 7.4 Идемпотентность и сверка

- Ключи: `Idempotency-Key` (регистрация, отзыв), `mandateId`/`mandateRef` (сквозной), `eventId` (события НСПК).
- Сверка с НСПК: открытые `PENDING_PAYER`/`ACTIVE` — периодический `getMandateStatus`; расхождения — по §5.
