# Solutioning — Платёжный шлюз СБП (C2B-приём)

Маршрут: **Critical** (значимость 11/15). Настоящий документ — полный Solutioning: контекст, компоненты, потоки, разбиение на ADR, NFR, план гейтов A0–A5, план отката, gaps.

## 1. Контекст и границы

Банк — участник СБП (эквайер/агент ТСП) принимает C2B-платежи от ТСП. Внешние системы: **ОПКЦ СБП (АО «НСПК»)** — операционный/клиринговый центр, **Банк России** — расчёты по корсчетам. Внутренние: **АБС** (счета ТСП), **антифрод/AML**, **SIEM**, **отчётность** (ЦБ/НСПК).

Подключение банка — по порядку ЦБ РФ (cbr.ru/PSystem/payment_system/actions/): договор с ПБР + СКЗИ → присоединение к Правилам ОПКЦ СБП → доработка ПО по документации Портала поддержки НСПК → тестовые испытания → активация. **Документация НСПК — внешний вход**: точный протокол получается по договору, публично не раскрыт (все протокольные детали помечены `[ТРЕБУЕТ ПРОВЕРКИ]` до получения).

Сценарии C2B в scope: динамический QR, статический QR/наклейка, кассовые ссылки, оплата по ссылке в e-commerce, возвраты. **Изменение 2026-09-28 (ADR-008): в scope добавлены подписки СБП** — рекуррентные C2B-списания по согласию плательщика (mandate); оценка изменения — маршрут Critical 12/15, гейт A3′ (`docs/changes/sbp-subscriptions/IMPACT.md`). Roadmap (вне scope): C2C, выплаты B2C/B2B, диспуты. (Автоплатежи/подписки выведены из roadmap в scope решением ADR-008.)

## 3. Статусная модель платежа

```
CREATED ──► QR_ISSUED ──► PAID ──► CREDITED ──► COMPLETED
   │            │          │            │
   ▼            ▼          ▼            ▼
 FAILED      EXPIRED    FAILED      REFUNDED (через сагу возврата)
```

- `PAID` — подтверждённый НСПК статус; **только из него** разрешено зачисление (AD-005).
- Переходы — атомарные транзакции «статус + outbox + аудит» (AD-002).
- Повторные нотификации идемпотентны (AD-003).
- **Рекуррентное списание (ADR-008)** — тот же автомат без шага `QR_ISSUED`: `CREATED → PAID` только при `ACTIVE`-согласии (AD-009); отзыв согласия блокирует будущие списания (AD-010). Согласие имеет отдельную статусную машину (`docs/spec/state-machine.md` §7).

## 4. Ключевые потоки

### 4.1 Оплата динамическим QR (счастливый путь)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant N as ОПКЦ СБП (НСПК)
    participant A as АБС

    T->>G: POST /payments (Idempotency-Key, сумма, реквизиты ТСП)
    G->>G: создать CREATED, outbox
    G->>N: регистрация QR (адаптер ОПКЦ)
    N-->>G: qrId + ссылка qr.nspk.ru/...
    G->>G: статус QR_ISSUED, outbox
    G-->>T: 201 {paymentId, qrId, qrUrl, qrImage}
    Note over N: плательщик сканирует QR и платит в своём банке
    N-->>G: нотификация PAID (eventId)
    G->>G: дедупликация по eventId, статус PAID, outbox
    G->>A: зачисление (paymentId, сумма, счёт ТСП)
    A-->>G: absDocId / подтверждение
    G->>G: статус CREDITED → COMPLETED, outbox
    G-->>T: вебхук COMPLETED
```

### 4.2 Возврат (сага)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз
    participant A as АБС
    participant N as ОПКЦ СБП (НСПК)

    T->>G: POST /refunds (refundId, paymentId, сумма)
    G->>G: проверка: платёж CREDITED/COMPLETED
    G->>A: списание со счёта ТСП (refundId)
    A-->>G: подтверждение
    G->>N: регистрация возврата (refundId)
    N-->>G: подтверждение возврата
    G->>G: статус REFUNDED, outbox
    G-->>T: вебхук REFUNDED
    Note over G: сбой на шаге → компенсация (отмена АБС-списания / повтор регистрации в НСПК / DLQ + runbook)
```

### 4.3 Подписка: регистрация согласия и рекуррентное списание (ADR-008)

```mermaid
sequenceDiagram
    participant T as ТСП
    participant G as СБП-шлюз (ядро + mandate SM)
    participant N as ОПКЦ СБП (НСПК)
    participant A as АБС

    T->>G: POST /v1/mandates (Idempotency-Key, реквизиты подписки)
    G->>G: создать согласие CREATED, outbox
    G->>N: registerMandate (адаптер ОПКЦ)
    N-->>G: mandateRef + qrId/qrUrl
    G->>G: PENDING_PAYER, outbox
    G-->>T: 201 {mandateId, qrUrl}
    Note over N: плательщик подтверждает согласие в приложении банка
    N-->>G: событие mandate.activated (eventId)
    G->>G: дедуп по eventId, ACTIVE, outbox
    G-->>T: вебхук mandate.activated
    Note over T,N: позже — списание без действия клиента
    T->>G: POST /v1/payments (mandateId, initiation=RECURRENT, Idempotency-Key)
    G->>G: guard: согласие ACTIVE, тот же ТСП/валюта, лимит — иначе отказ (деньги не двигаются)
    G->>N: createSubscriptionCharge (reference=paymentId)
    N-->>G: подтверждение списания (или событие)
    G->>G: CREATED→PAID (без QR), outbox
    G->>A: зачисление (paymentId, счёт ТСП)
    A-->>G: absDocId
    G->>G: CREDITED→COMPLETED, outbox
    G-->>T: вебхук payment.completed
    Note over G: отзыв согласия (событие НСПК или POST /mandates/{id}/revoke) → REVOKED; новые списания запрещены (AD-010); уже PAID — зачисляются
```

## 5. Разбиение на решения (ADR)

| Решение | ADR | Spine |
|---|---|---|
| Топология: выделенный компонент + outbox | ADR-001 | AD-001, AD-002 |
| Статусная машина + идемпотентность | ADR-002 | AD-002, AD-003 |
| Транспорт к ОПКЦ: изолированный адаптер, mTLS/ГОСТ, СКЗИ | ADR-003 | AD-004 |
| Нотификации: at-least-once, дедуп, DLQ, сверка | ADR-004 | AD-003 |
| АБС: зачисление из PAID, возвраты-сага | ADR-005 | AD-005 |
| НПС/КИИ/ПДн: trust-зоны, ГОСТ | ADR-006 | AD-006, AD-007 |
| Стратегия реализации (гибрид) — **A3 принято 2026-08-15** | ADR-007 (Accepted) | AD-008 [ADOPTED] |
| Подписки: согласие плательщика (mandate), рекуррентные списания — Proposed, ожидает A3′ | ADR-008 | AD-009, AD-010 |

## 6. NFR

Полный набор с измеримыми целями — `docs/nfr.md`. Ключевое: доступность ≥ 99,95 %; RPO=0; RTO ≤ 1 ч; регистрация QR p95 < 500 мс; sustained 200 TPS / пик 500 TPS; сверка с НСПК ежечасная, с АБС суточная; двойных зачислений — 0. Для подписок — `docs/nfr.md` §7: 0 списаний вне `ACTIVE`-согласия, блокировка после отзыва ≤ 5 с, throughput рекуррентных списаний ≥ 50 TPS.

## 7. Гейты и критерии приёмки

- **A0 (readiness)**: ADR-001..007 заполнены, spine пролинтован, gaps зафиксированы. Критерий: PASS.
- **A1 (Spec)**: контракт API ТСП (v0.1 — `docs/contracts/tsp-api.md`), таблица переходов статусной машины (`docs/spec/state-machine.md`), контракт адаптера ОПКЦ (`docs/contracts/opkc-adapter.md` — ядро↔транспорт, основа RFP), RFP-пакет по вендору (`docs/rfp/vendor-rfp.md`), NFR финализированы.
- **A2 (Plan)**: разбивка на задачи, walking skeleton определён (сквозной путь: ТСП → шлюз → мок НСПК → АБС-мок → нотификация).
- **A3 (человеческое решение)**: стратегия реализации (ADR-007) — **обязательно до реализации транспорта**.
- **A4 (conformance)**: fitness-проверки spine-инвариантов, нагрузочные тесты (NFR), тесты идемпотентности, ИБ-аудит.
- **A5 (post-deploy drift)**: сверка с НСПК/АБС в проде, SLO-отчёт через 30 дней, проверка отсутствия дрейфа от spine.

Гейты изменения (подписки СБП, ADR-008):

- **A3′ (человеческое решение, изменение)**: ратификация ADR-008 и scope (H-1/H-2 в `docs/changes/sbp-subscriptions/IMPACT.md` §7) — **обязательно до реализации** ядра/транспорта подписок.
- **A1′ (Spec, изменение)**: дельта контрактов (TSP-API v0.2, opkc-adapter v0.2), статусная машина согласия (`docs/spec/state-machine.md` §7), NFR §7, расширение RFP — после A3′.
- **A4′ (conformance, изменение)**: fitness AD-009/AD-010, тесты гонки «отзыв ↔ списание», идемпотентности, лимитов; нагрузочные тесты NFR §7; ИБ-аудит согласий/ПДн.

## 8. План отката

- **До боевой эксплуатации**: откат = не включать. Все работы обратимы (ADR-007 reversible).
- **После включения**: фиче-флаг на приём новых ТСП; мгновенный stop-new (запрет регистрации новых QR) без остановки обработки уже открытых операций; откат релиза — rolling; данные не мигрируются обратно (шлюз остаётся источником истины до полной сверки с АБС).
- **Аварийный сценарий**: DLQ → дежурная смена по runbook; сверка компенсирует потерянные нотификации; RTO ≤ 1 ч.
- **Подписки (ADR-008, изменение)**: до боевой — reversible (фиче-флаг, ядро/данные базового C2B не меняются). После включения — фиче-флаг «подписки»: выключить приём новых согласий и новых рекуррентных инициаций, дождаться завершения/компенсации открытых, довести подтверждённые `PAID` до зачисления, при необходимости — управляемое сворачивание действующих согласий; данные согласий не мигрируются обратно. Критерии и владелец решения — `docs/changes/sbp-subscriptions/IMPACT.md` §6.2.

## 9. Gaps и внешние входы

| Gap | Что закроет | Владелец |
|---|---|---|
| Точный протокол НСПК (поля, тайминги, TLS-профили) | Документация НСПК по договору (Портал поддержки) | Проектный офис / НСПК |
| Регламенты НСПК (таймауты, сроки уведомлений, доступность) | Документация НСПК, правила ОПКЦ СБП | Проектный офис |
| Номер/редакция Положения ЦБ о защите информации при переводах | ИБ/комплаенс банка | ИБ |
| Контракт АБС на зачисление/списание (идемпотентность, SLA) | Интервью с владельцем АБС | Архитектор + АБС |
| Категория объекта КИИ, состав мер ФСТЭК | ИБ/КИИ банка | ИБ |
| Выбор конкретного вендора транспорта ОПКЦ | RFP по критериям ADR-007 (сертификаты ФСТЭК, тестовый контур, SLA, референсы) | Проектный офис / закупки |
| Протокол сервиса подписок НСПК (поля согласия, уведомление/подтверждение списаний, распространение отзыва, лимиты) | Документация НСПК по договору | Проектный офис / НСПК |
| Контрактное требование к вендору по согласиям (методы, идемпотентность, тестовый контур) | Расширение RFP (`docs/rfp/vendor-rfp.md`) | Проектный офис / архитектор |
| Сроки хранения согласий/аудита и минимизация ПДн | Юридическая позиция + ИБ | ИБ/комплаенс |

## 10. Открытые вопросы

1. Объём первой волны: только C2B-приём или сразу C2C/выплаты? (влияет на состав адаптеров, но не на ядро).
2. Требования бизнеса к комиссиям и тарифам ТСП (влияет на модель отчётности).
3. Лимиты/пороги для AML-интеграции.
4. Доступность АБС в ночные окна (влияет на SLA зачисления).
5. Подписки: подтверждение каждого списания клиентом или только предварительное уведомление? (влияет на UX, SLA, риск; требует протокола НСПК).
6. Подписки: лимиты по умолчанию (на списание/период/срок согласия) и пороги антифрода.
7. Подписки: ёмкость по числу активных согласий (бизнес-прогноз) и приоритеты очередей списаний.
8. Подписки: scope — расширение текущего initiative или отдельный initiative (родительский spine).
