# ADR-008. Подписки СБП: рекуррентные C2B-списания по согласию плательщика

- Date: 2026-09-28
- Status: Proposed (выносится на A3 — человеческое архитектурное решение)
- Owner: solution-architect (платёжный контур) + продукт/бизнес (сегменты ТСП)
- Related: ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-006, ADR-007, AD-001..AD-013, `docs/solutioning-subscriptions.md`, `docs/spec/subscriptions.md`
- Author-model: qwen-code

## Context

Бизнес (онлайн-кинотеатры, ЖКХ, связь) просит рекуррентные C2B-списания по подписке: плательщик один раз даёт согласие, далее списания инициируются ТСП/шлюзом без QR на каждый платёж. Принятое решение (ADR-001..007, AD-001..008) проектировалось под разовый платёж «QR → оплата»; сейчас каждый платёж требует QR и активного действия клиента.

Силы и ограничения:
- **Финансовая значимость и at-least-once**: списание инициирует сам шлюз (впервые появляется «исходящая» инициатива массово), повторы планировщика/ретраи не должны давать двойных проводок (AD-003).
- **Регуляторика и ПДн**: согласие плательщика — персональные данные; отзыв согласия обязан немедленно прекращать списания; аудит каждого финансового и административного действия (AD-006, AD-007).
- **Внешний вход**: точный протокол подписок СБП (поля согласия, тайминги предварительного уведомления, коды отказов, лимиты) публично не раскрыт — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации НСПК; это тот же внешний вход, что у базового решения.
- **Принятые инварианты**: единый доверенный контур и единственный адаптер ОПКЦ (AD-001, AD-004), зачисление только из подтверждённого `PAID` (AD-005), стратегия гибрида «ядро — своё, транспорт — вендорский» (AD-008, ADR-007).
- **Новый профиль нагрузки**: планировщик создаёт концентрированные пики (календарные даты списаний), не похожие на поток «оплата по QR».

## Decision

Подписки реализуются **расширением существующего СБП-шлюза**, без выхода из его доверенного контура:

1. **Подписочный контур внутри периметра шлюза** (AD-001, AD-006): жизненный цикл согласия плательщика и подписки ТСП + планировщик списаний; собственная БД-модель, но тот же контур, что и статусная машина платежа.
2. **Рекуррентное списание — обычный платёж со ссылкой на подписку**: проходит **ту же** статусную машину и **тот же** шлюз зачисления, зачисляется только из `PAID` (AD-002, AD-005 не переопределяются). Ветвь без QR: `CREATED → PAID` по подтверждённой нотификации о списании (переход `T4a`), вместо `qrId` — `debitId`; статусы наружу не меняются.
3. **Идемпотентность списания — детерминированный ключ** `(subscriptionId, billingPeriod, attempt)`: не более одного **зачисленного** списания на период; транзиентный ретрай возвращает существующий `paymentId` и не создаёт вторую проводку; новая попытка после явного отказа — только по политике ретраев (AD-003, AD-010).
4. **Списание только по действующему согласию и в его пределах** (статус `ACTIVE`, `amount ≤ maxAmount`, `period` совпадает, `scheduledAt < validUntil`), проверяемых в одной транзакции с инициацией; подписка привязывается только к мандату того же ТСП. Отзыв согласия (подтверждённый переход в `REVOKING`/`REVOKED`) имеет приоритет над расписанием и исключает согласие из планировщика (AD-009, AD-011).
5. **Протокол подписок инкапсулируется в единственном адаптере ОПКЦ** как расширение внутреннего контракта адаптера (AD-004, AD-008): ядро по-прежнему не знает протокола НСПК; вендор обязан поддержать подписочный транспорт (расширение RFP).
6. **Контракт API ТСП расширяется аддитивно** (v0.2.0): новые пути/схемы, ни одно существующее поле/путь/enum не изменяется — существующие потребители v0.1 не ломаются.

Сущности разделяются: **согласие ≠ подписка ≠ платёж**; финансовый эффект существует только у платежа (AD-013).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **Расширение шлюза подписочным контуром (выбран)** | Единый источник истины, переиспользование статусной машины/идемпотентности/сверки, соответствие AD-001/004/005/008 | Рост периметра шлюза, новая БД-модель и планировщик, выше цена сопровождения | — |
| Отдельный сервис подписок вне шлюза (своя БД, свой канал к НСПК) | Независимое развитие, изоляция нагрузки | Второй источник истины и второй канал к НСПК → нарушение AD-001/AD-004; дублирование идемпотентности и статусной модели; риск двойного зачисления; два адаптера к оператору | Противоречит принятым инвариантам, удваивает регуляторную поверхность |
| Полностью вендорский подписочный модуль (включая логику списаний) | Быстрый старт, вендор отвечает за протокол | Финансовая логика вне контроля банка, vendor lock-in, ограниченный аудит для ЦБ | Противоречит ADR-007: ядро — собственная разработка |
| Встроить подписки в существующий платёжный движок без выделенного контура (только новые состояния) | Минимум компонентов | Смешение жизненных циклов согласия/подписки/платежа, нет явного владельца мандатов, планировщик размазан по платежам, труднее аудит и отзыв | Нет субъекта ответственности за согласие; нарушает AD-013 и усложняет отзыв |

## Consequences

### Positive

- Переиспользование доказанных механизмов: статусная машина, outbox, идемпотентность, сверка — подписки не создают параллельной финансовой логики.
- Зачисление по-прежнему только из подтверждённого `PAID` — «платежи из воздуха» невозможны.
- Тот же адаптер ОПКЦ остаётся единственной точкой знания протокола; замена вендора не затрагивает ядро.
- Явный владелец согласия и приоритет отзыва — управляемый регуляторный и клиентский риск.
- Аддитивное расширение API не ломает существующих ТСП.

### Negative

- Периметр шлюза расширяется: новый подписочный контур, планировщик, БД-модель согласий — рост стоимости владения и эксплуатационной нагрузки (пики списаний).
- Внешняя зависимость: вендор транспорта обязан поддержать протокол подписок НСПК — иначе фича блокируется (расширение RFP/контракта).
- Отзыв согласия во время «списания в полёте» требует компенсации (возврат/runbook) — сложная логика, тесты на сценарии гонки.
- Планировщик — новый источник массовых инициирующих операций; ошибка конфигурации расписания даёт массовые отказы и обращения плательщиков.
- Точный протокол — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; часть контракта адаптера и API не может быть финализирована до документации НСПК.

## Reversibility

**costly.** До боевой эксплуатации — `reversible` (фича за флагом, подписочный контур можно не включать). После появления действующих согласий и истории списаний простой откат невозможен: обязательства перед плательщиками и ТСП сохраняются, отзывы должны продолжать обрабатываться, а отключение планировщика означает невыполнение подписок.

Откат = «stop-new» (запрет новых согласий/подписок) + продолжение обслуживания существующих. **Подписочный контур не откатывается вместе с релизом ядра**: он разворачивается как отдельный модуль/фича-флаг и при откате релиза остаётся на предыдущей совместимой версии (blue-green), иначе исчезает компонент, обязанный обслуживать отзывы (см. `docs/solutioning-subscriptions.md` §6.2).

Kill/expiry-условие пересмотра: (а) документация НСПК не подтверждает протокол подписок как предполагалось; (б) вендор транспорта не может поддержать подписочную часть контракта; (в) изменяются требования к предварительному уведомлению плательщика, делающие модель несоответствующей; плановая ревизия — через 12 месяцев эксплуатации.
