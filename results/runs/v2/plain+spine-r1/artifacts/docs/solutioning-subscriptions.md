- Owner: solution-architect (платёжный контур)
- База решения: `ARCHITECTURE-SPINE.md` (AD-001..AD-008), `docs/solutioning.md`, `docs/adr/ADR-001..007`

**Маршрут — Critical** (≥5 триггеров + `criticality_or_exception` + `financial_impact`). Следствие: полный Solutioning (spine + ADR + NFR), обязательная человеческая точка **A3** до реализации, walking skeleton и evidence-гейты; дельты недостаточно (дельта — лишь механизм авторизации правок защищённых файлов).

> Anti-bypass floor: скоринг дополнительно проверяется из git-диффа (`arch-be control score --from-diff`) — детектор только добавляет триггеры, занизить вручную нельзя.

## 2. Влияние на принятую архитектуру

### 2.1 Затронутые инварианты

| Инвариант | Что происходит | Как |
|---|---|---|
| AD-001 (изоляция платёжного контура) | **Сохраняется**, периметр расширяется | подписочный контур — внутри того же доверенного контура; внешние вызовы только через адаптеры |
| AD-002 (единый источник истины — статусная машина) | **Расширяется** | те же атомарные переходы «статус + outbox + аудит» для согласия/подписки/списания |
| AD-003 (идемпотентность финансовых операций) | **Расширяется** | новый детерминированный ключ инициации `(subscriptionId, billingPeriod, attempt)`; не более одного зачисленного списания на период (AD-010) |
| AD-004 (единственный адаптер ОПКЦ) | **Сохраняется**, контракт адаптера расширяется | протокол подписок знает только адаптер (AD-008) |
| AD-005 (зачисление только из `PAID`) | **Сохраняется без изменения текста** | рекуррентный платёж зачисляется только из `PAID`; отдельного пути нет (AD-012) |
| AD-006 (trust-зоны/сегментация) | **Сохраняется** | новых зон нет; канал к НСПК по-прежнему в DMZ-адаптере |
| AD-007 (НПС/КИИ/ПДн) | **Усиливается** | согласие — ПДн плательщика; аудит отзыва и уведомлений |
| AD-008 (гибрид «ядро — своё, транспорт — вендорский») | **Сохраняется**, scope вендора расширяется | вендор обязан поддержать подписочный протокол; ядро контрактно-независимо |

**Новые инварианты** (спайн расширяется блоками AD-009..AD-013, обоснование — в `changes/sbp-subscriptions/DELTA.md`):

- **AD-009.** Списание возможно только по действующему согласию плательщика.
- **AD-010.** Не более одного зачисленного списания на `(subscriptionId, billingPeriod)`; ключ инициации — `(subscriptionId, billingPeriod, attempt)`.
- **AD-011.** Приоритет отзыва согласия: подтверждённый отзыв немедленно исключает мандат из планировщика.
- **AD-012.** Единая статусная машина и единственный шлюз зачисления для подписок.
- **AD-013.** Разделение сущностей «согласие ≠ подписка ≠ платёж».

### 2.2 Что меняется

- **Компоненты (C4):** внутри платёжного контура добавляется подписочный контур — сервис жизненного цикла согласий и подписок + планировщик списаний; новых trust-зон и внешних каналов нет.
- **Модель данных:** новые сущности `mandate`, `subscription`, `billing_schedule`, `debit_attempt`; связь с платежом через `paymentId`; ПДн плательщика минимизируются.
- **Статусные машины:** добавлены автоматы согласия и подписки; рекуррентное списание переиспользует существующий автомат платежа с **ветвью без QR** (`CREATED → PAID`, переход `T4a`; в ветви QR `qrId` обязателен и для подписки неприменим) (`docs/spec/state-machine.md`).
- **Эксплуатационный артефакт:** runbook урегулирования «списания в полёте» при отзыве согласия (владелец — дежурная смена платежей) — обязателен к A4 (AD-011).
- **Контракты:** API ТСП v0.1.0 → v0.2.0 (аддитивно); контракт адаптера ОПКЦ — новые методы/события; RFP — расширение scope и критериев допуска.
- **NFR:** новый раздел (планировщик, уведомления, отзыв, сверка согласий).
- **Реестр правил:** новые fitness-правила в `.arch-handoff/CONSTRAINTS.yaml`.

### 2.3 Что НЕ меняется

- Принцип изоляции и единственный адаптер ОПКЦ (AD-001, AD-004) — не пересматриваются.
- Правило зачисления «только из `PAID`» (AD-005) — текст не меняется; подписки подчиняются ему.
- Стратегия реализации (ADR-007, ADOPTED) — не пересматривается; расширяется только scope вендора.
- Возвраты (сага, ADR-005) и базовая сверка (ADR-004) — переиспользуются; добавляются объекты сверки.
- Существующие статусы платежа наружу — без изменений (совместимость API).

## 3. Архитектурное решение

Решение зафиксировано в **`docs/adr/ADR-008-podpiski-sbp-rekurrentnye-c2b-spisaniya-po-soglasiyu-platelschika.md`** (Status: Proposed): расширение существующего шлюза подписочным контуром, переиспользование статусной машины и шлюза зачисления, инкапсуляция протокола подписок в единственном адаптере ОПКЦ, аддитивное расширение API ТСП. Рассмотрены и отвергнуты: отдельный сервис вне шлюза, вендорская «коробка», встраивание без выделенного контура. Обратимость: **costly** (после появления действующих согласий). Условие/срок пересмотра указаны в ADR-008.

Детализация автоматов — `docs/spec/subscriptions.md`.

## 4. Изменения контрактов без поломки существующих потребителей

**Принцип: только аддитивность.** Ни один существующий путь, поле, тип или значение enum не изменяется и не удаляется. Версия `openapi/tsp-api.yaml`: `0.1.0 → 0.2.0` (аддитивное минорное расширение; мажорный путь `/v1` сохраняется).

### 4.1 API ТСП — новые возможности (аддитивно)

| Метод | Назначение | Ломает v0.1? |
|---|---|---|
| `POST /v1/mandates` | инициировать оформление согласия плательщика | нет (новый путь) |
| `GET /v1/mandates/{mandateId}` | статус согласия | нет |
| `DELETE /v1/mandates/{mandateId}` | отмена согласия со стороны ТСП (отражается как `REVOKING`) | нет |
| `POST /v1/subscriptions` | создать подписку (с указанием `mandateId`) | нет |
| `GET /v1/subscriptions/{subscriptionId}` | статус подписки | нет |
| `POST /v1/subscriptions/{subscriptionId}/cancel` | отменить подписку | нет |
| `GET /v1/payments?subscriptionId={id}` | список списаний по подписке | нет (расширение фильтра) |
| Поле `subscriptionId` в `Payment` | связь платежа с подпиской | нет (опциональное поле только в ответах) |

`Idempotency-Key` остаётся обязательным для всех `POST`, включая новые.

### 4.2 Вебхуки (аддитивно)

Новые типы событий: `mandate.activated`, `mandate.revoked`, `mandate.rejected`, `subscription.activated`, `subscription.suspended`, `subscription.cancelled`; результаты списаний используют существующие `payment.*`. **Требование к ТСП:** игнорировать неизвестные типы событий (forward-compatibility) — добавляется в контракт как явное правило.

### 4.3 Контракт адаптера ОПКЦ (расширение)

Новые методы: `registerConsent`, `getConsentStatus`, `revokeConsent`, `createSubscriptionDebit`, `getSubscriptionDebitStatus`; новые события: `consent.registered`, `consent.rejected`, `consent.revoked`, `subscription.debit.rejected`; те же гарантии at-least-once и идемпотентность по `reference`.

### 4.4 Машинная проверка неразрушаемости

Ломающие изменения проверяются механически — `arch-be contract-diff <v0.1> <v0.2>` (OpenAPI 3.x, CD-001..CD-007; ломающее изменение = exit 1). Результат прогона зафиксирован в этом пакете (см. §8 «Проверки»). Ломающих изменений нет.

## 5. Измеримые NFR для нового функционала

Полный раздел — `docs/nfr.md` §7 «Подписки СБП». Ключевое:

| NFR | Цель | Метод проверки |
|---|---|---|
| Точность запуска планировщика | p99 отклонение от `scheduledAt` ≤ 60 с | метрика планировщика |
| Двойные (зачисленные) списания на период | 0 (не более одного на `(subscriptionId, billingPeriod)`, ключ инициации с `attempt`) | тест повторного запуска/ретрая |
| Инициация списания без действующего мандата | 0 | fitness/тест, алерт |
| Списанный платёж подтверждён `PAID` | 100 % | сверка, аудит |
| Остановка списаний после подтверждённого отзыва | 0 новых инициаций (в-полёте ≤ 1 на согласие, по runbook) | тест + метрика |
| Предварительное уведомление плательщика | 100 % списаний: инициация уведомления через ОПКЦ в срок `[ТРЕБУЕТ ПРОВЕРКИ]`; доставка — банк плательщика/НСПК (R5) | метрика инициации уведомлений |
| Актуализация статуса согласия из ОПКЦ | p95 ≤ 60 с | лаг очереди |
| Доступность подписочного контура/планировщика | ≥ 99,95 % | SLO-отчёт |
| RPO/RTO подписочного хранилища | RPO = 0; RTO ≤ 1 ч | учения/chaos |
| Сверка согласий и списаний с НСПК | ежечасная; расхождений по завершённым списаниям — 0 | reconciliation-отчёт |
| Пиковая нагрузка списаний | sustained 200 TPS, пик 500 TPS (как у платежей) | нагрузочный тест на расписании-пике |
| Пропускная способность планировщика | ≥ 720 000 списаний/час (= sustained 200 TPS), запас ×2 | нагрузочный тест |

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (EARS; позитивные и негативные)

1. When планировщик запущен повторно на тот же `billingPeriod`, the шлюз shall вернуть существующий `paymentId` и не инициировать второе списание (AD-010).
2. If статус мандата ≠ `ACTIVE`, then инициация списания shall быть невозможна и зафиксирована алертом (AD-009).
3. When получен подтверждённый отзыв согласия, the подписочный контур shall немедленно исключить мандат из планировщика; списание из состояния «в полёте» shall быть урегулировано по runbook (AD-011).
4. Where платёж создан по подписке, the зачисление shall происходить только из `PAID` через общий шлюз (AD-005/AD-012).
5. When ТСП отменяет подписку, the согласие shall остаться в текущем статусе (AD-013).
6. When приходит повторная нотификация НСПК с тем же `eventId`, the состояние shall не измениться (AD-003).
7. If вендорский транспорт недоступен, then шлюз shall не терять списания: инициации в очереди/DLQ, видимость в отчёте незавершённых операций, сверка добирает результат.
8. When ТСП вызывает любой метод v0.1 после релиза v0.2, the поведение shall не измениться (обратная совместимость; проверяется контрактным диффом и regression-тестом).
9. Критерий успешного отката: после `stop-new` существующие согласия/подписки продолжают обслуживаться (отзывы обрабатываются, «в полёте» операции завершаются/компенсируются), расхождений сверки — 0.

### 6.2 План отката

- **До боевой эксплуатации:** откат = не включать фичу (feature-flag по ТСП/окружению). Изменения аддитивны, данные не мигрируются.
- **Триггеры отката (сигналы):** массовые двойные списания; списания по отозванным мандатам; деградация планировщика (пропуск расписаний); нарушение уведомлений; расхождения сверки по согласиям.
- **Порядок:** (1) `stop-new` — запрет новых согласий/подписок; (2) остановка планировщика по новым периодам (существующие «в полёте» доводятся); (3) отключение подписочной фичи фича-флагом; откат релиза ядра возможен только для компонентов, **не** входящих в подписочный контур (сам контур остаётся на предыдущей совместимой версии — blue-green), иначе исчезает компонент, обязанный обслуживать отзывы; (4) компенсации/возвраты по затронутым операциям (сага ADR-005); (5) эскалация вендору при отказе транспорта; (6) сверка и отчёт.
- **Что НЕ откатывается:** данные согласий/подписок и обязательства перед плательщиками; отзывы обязаны обрабатываться и после отката — поэтому подписочный контур разворачивается отдельно от релиза ядра и не «сворачивается» вместе с ним.
- **Владелец решения об откате:** архитектор платёжного контура совместно с владельцем продукта и дежурной сменой платежей (4-eyes для ручных компенсаций). RTO ≤ 1 ч.

## 7. Что остаётся на решение человека-архитектора (A3)

1. **Готовность и scope фичи**: запускать ли подписки сейчас (до получения документации НСПК) и для каких сегментов ТСП (кинотеатры/ЖКХ/связь); какова первая волна.
2. **Модель согласия и уведомлений**: юридическая/регуляторная трактовка предварительного уведомления и отзыва (совместно с ИБ/комплаенс) — контрактные тайминги `[ТРЕБУЕТ ПРОВЕРКИ]`.
3. **Расширение scope вендора транспорта**: переговоры с вендором ADR-007 о поддержке подписочного протокола; при отказе — эскалация/пересмотр (kill-условие ADR-008).
4. **Политика ретраев при отказе списания** (число попыток, интервалы, авто-приостановка подписки) и её соответствие требованиям НСПК.
5. **Лимиты** (максимальная сумма списания, период) — по документации НСПК и продукту.
6. **Введение типизированной модели `model/`**: гейт маршрута Critical ожидает `trace_check`/`nfr`/`model_validate` (сейчас SKIP — в базовом репозитории нет каталога `model/`). Это отдельная инициатива, не часть данного изменения; решение за архитектором.
7. **Судьба отложенного `disputes`** при росте доли отказов/претензий по подпискам (в базовом решении диспуты в Deferred).
8. **Семантика `maxAmount`** (лимит на одно списание) и наличие агрегатного лимита за период согласия — требует регламента НСПК/продукта; от этого зависит enforcement в §2.1 спеки.
9. **Политика пропущенного периода** при простое транспорта (догнать/пропустить, окно уведомления) — решение A2 + регламент НСПК (R7).
10. **Runbook «списание в полёте»** (AD-011): владелец — дежурная смена платежей; содержимое (компенсация возвратом vs подтверждение, 4-eyes) — обязательный артефакт к A4.
11. **Ретенция и удаление ПДн плательщика при отзыве** (152-ФЗ): срок хранения, анонимизация — владелец ИБ.
12. **Аутентификация вызывающего ТСП**: `tspId` берётся из mTLS/`X-API-Key`, а не из тела запроса (влияет на проверку владения мандатом, §2.1) — ИБ, A4.

| Сенсоры спецификаций | `arch-be gate …` (sensors) | PASS (обязательные секции спек на месте) |
| Delta validate / delta guard | `arch-be delta validate sbp-subscriptions` / `arch-be delta guard` | нарушений нет; правки спайна покрыты активной дельтой |

Регистрация правил в `.arch-handoff/CONSTRAINTS.yaml` (текстовый слой трассировки) на этапе решения; **поведенческие** правила (`command_succeeds`) добавляются при передаче в реализацию (`--refresh-constraints`), как и предусмотрено шапкой CONSTRAINTS.yaml. Отчёт `arch-be control rules-report`: 0 из 19 правил проверяют поведение — это ожидаемо **до** появления кода; при handoff поведенческие проверки обязательны.

## 9. Передача исполнителям (после A3)

Handoff-пакет собирается **после** подписания A3 (маршрут Critical: реализация до A3 не начинается). Команда:

```
arch-be handoff qwen-code --repo . \
  --task "<задача подписок>" \
  --spec ARCHITECTURE-SPINE.md docs/solutioning-subscriptions.md docs/adr/ADR-008-*.md docs/spec/subscriptions.md docs/nfr.md \
  --route critical \
  --rollback "stop-new + остановка планировщика по новым периодам + отключение подписочной фичи (контур вне отката релиза ядра, blue-green) + компенсации по саге (ADR-005)"
```

Пакет унаследует инварианты AD-009..AD-013 и текст задачи; существующий `.arch-handoff` перегенерируется на этапе передачи (не раньше A3), правки архитектора в CONSTRAINTS.yaml сохраняются (без `--refresh-constraints`).

## 10. Готовность и статус гейта (readiness)

**Вердикт readiness-гейта: CONCERNS** — изменение можно выносить на A3, но не начинать реализацию до закрытия условий. Это не FAIL: незакрытые пункты — внешние входы и человеческое решение, а не отсутствующие in-scope артефакты.

- Трассируемость: требования REQ-SUB-1..8 (DELTA) ↔ критерии приёмки (EARS) ↔ инварианты AD-009..AD-013 ↔ правила CONSTRAINTS.yaml — двусторонняя.
- NFR: бюджеты заданы числами и методом проверки (`docs/nfr.md` §7).
- Условия (чинятся вне пакета): документация НСПК (внешний вход); A3-решение; расширение scope вендора транспорта; поведенческие fitness-правила — при handoff.

**Статус единого гейта репозитория** (`arch-be gate --repo . --route critical`): **FAIL (exit 1) — «выпуск заблокирован»**, и это корректно для стадии propose: единственная провалившаяся составляющая — `evidence_verify`, и только из-за отсутствия четырёх **пост-A3/пост-реализационных** артефактов (содержательных находок в bundle — 0). Всё, что проверяемо на стадии решения, — зелёное:

| Составляющая Critical | Статус | Причина |
|---|---|---|
| fitness (19 правил), delta_guard, rule_weakened, spine_lint, sensors | **PASS** | проверено этим изменением |
| `evidence_verify` | FAIL | bundle 9/13; отсутствуют `decision_a3`, `walking_skeleton`, `rollback_rehearsal`, `validation` — пост-A3/пост-реализация; содержательных находок нет (ревью READY, fitness PASS) |
| `trace_check`, `nfr`, `model_validate` | SKIP | в репозитории нет каталога `model/` — **отдельная инициатива**, решение архитектора (§7 п.6) |

**Честная граница:** пакет не фабрикует пост-A3 evidence (решение A3, walking skeleton, репетиция отката, validation) — гейт осознанно заблокирован, пока эти шаги не выполнены человеком и реализацией. Зелёный здесь был бы признаком approval theater. После A3 и walking skeleton bundle дозаполняется, и гейт закрывается без изменения решения.
