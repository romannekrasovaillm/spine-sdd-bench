# Подписки СБП: согласие, подписка, рекуррентное списание — спецификация

- Status: Draft (для ревью на гейте A1; выносится вместе с ADR-008)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-005, AD-001, AD-003, AD-005, AD-009..AD-013
- Внешний вход: протокол подписок НСПК (поля согласия, тайминги уведомления, коды отказа, лимиты) — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации.

## Проблема

Сейчас каждый C2B-платёж требует QR и действия плательщика; ТСП (кинотеатры, ЖКХ, связь) просят рекуррентные списания по подписке. Нужны три раздельных жизненных цикла — согласие плательщика, подписка ТСП и рекуррентный платёж — так, чтобы списание было невозможно без действующего согласия, повтор запуска планировщика не давал двойной проводки, а отзыв согласия немедленно останавливал будущие списания (ADR-008, AD-009..AD-013).

## 1. Сущности и разделение (AD-013)

| Сущность | ID | Смысл | Финансовый эффект |
|---|---|---|---|
| **Согласие плательщика** (mandate/consent) | `mandateId` | Разрешение плательщика списывать в пользу ТСП в рамках условий (лимит, период, срок) | нет |
| **Подписка ТСП** (subscription) | `subscriptionId` | Договорённость с ТСП: план, сумма, расписание; ссылается на `mandateId` | нет |
| **Рекуррентный платёж** | `paymentId` | Конкретное списание за период; проходит общую статусную машину платежа | **да** |

Согласие ≠ подписка ≠ платёж: отзыв согласия, отмена подписки и возврат платежа — независимые операции с разными последствиями. Финансовый эффект существует только у платежа (AD-013).

## 2. Статусная машина согласия плательщика

```
CREATED ──► PENDING_PAYER ──► ACTIVE ──► REVOKING ──► REVOKED
   │             │              │
   ▼             ▼              ▼
 FAILED      REJECTED        EXPIRED
```

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` (ТСП инициирует оформление) | ТСП активен, реквизиты валидны | запись мандата + outbox «регистрация согласия в ОПКЦ» |
| M2 | `CREATED` | `PENDING_PAYER` | адаптер ОПКЦ: согласие принято к оформлению | получен внешний `consentId` | сохранить `consentId`, ссылка/QR для подтверждения плательщиком |
| M3 | `PENDING_PAYER` | `ACTIVE` | подтверждение плательщика (нотификация/сверка ОПКЦ) | условия (лимит/период/срок) зафиксированы | мандат доступен планировщику; outbox `mandate.activated` |
| M4 | `CREATED`/`PENDING_PAYER` | `FAILED`/`REJECTED` | отказ ОПКЦ или плательщика | не транзиентный | `errorCode`, outbox |
| M5 | `ACTIVE` | `REVOKING` | отзыв согласия плательщиком (ОПКЦ) или ТСП/банком по регламенту | — | мандат исключается из планировщика **немедленно** (AD-011) |
| M6 | `REVOKING` | `REVOKED` | подтверждение отзыва из ОПКЦ | в-полёте списания урегулированы по runbook | outbox `mandate.revoked`; новые списания невозможны |
| M7 | `ACTIVE` | `EXPIRED` | истёк срок действия (`validUntil`); при введённом агрегатном лимите — дополнительно при его исчерпании | — | мандат исключается из планировщика |
| M8 | `ACTIVE` | `ACTIVE` | обновление условий (лимит/срок) по регламенту | требует подтверждения плательщика, если так требует НСПК | аудит, outbox |

**Запрещено:** инициация списания при статусе согласия, отличном от `ACTIVE` (AD-009). `REVOKED`/`EXPIRED`/`REJECTED`/`FAILED` — терминальные для списаний.

### 2.1 Ограничения согласия и их обязательная проверка (AD-009)

Условия согласия — суть волеизъявления плательщика; их нарушение = спорное списание. Guard'ы обязательны **в одной транзакции с созданием списания** (а не «на этапе оформления»):

| Ограничение согласия | Где проверяется | Что запрещено |
|---|---|---|
| статус = `ACTIVE` | перед каждой инициацией (R1) | инициация при `PENDING_PAYER`/`REVOKING`/`REVOKED`/`EXPIRED`/`REJECTED`/`FAILED` |
| `subscription.amount ≤ mandate.maxAmount` | при создании подписки (S1/S7) и при каждой инициации (R1) | подписка/списание выше лимита согласия |
| `period` списания совпадает с `mandate.period` | при создании подписки (S1) | несовпадение периодичности |
| `scheduledAt < mandate.validUntil` | перед каждой инициацией (R1) | списание после истечения срока согласия |
| `subscription.tspId == mandate.tspId == вызывающий ТСП` | при создании подписки (S2) и в API-аутентификации | привязка подписки к чужому мандату (межтенантная утечка) |
| кардинальность: **один мандат — одна активная подписка** на данного ТСП | при создании подписки (S1) | обход лимита несколькими подписками на один мандат |

**Механизм истечения `ACTIVE → EXPIRED` (M7):** планировщик при каждом запуске (и регламентная задача) переводит мандаты с `validUntil ≤ now` в `EXPIRED`. Агрегатный лимит за период (если будет введён по внешнему решению, см. `docs/solutioning-subscriptions.md` §7) добавит второй триггер исчерпания; до этого решения M7 срабатывает только по сроку. Владелец механизма — подписочный контур (планировщик); истечение фиксируется аудитом и событием.

`maxAmount` трактуется как лимит **на одно списание**; агрегатный лимит за период — предмет согласования с НСПК/продуктом `[ТРЕБУЕТ ПРОВЕРКИ]` (см. `docs/contracts/tsp-api.md` §7 и `docs/solutioning-subscriptions.md` §7).

## 3. Статусная машина подписки ТСП

```
DRAFT ──► PENDING_MANDATE ──► ACTIVE ──► SUSPENDED ──► CANCELLED
```

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| S1 | — | `DRAFT` | `POST /v1/subscriptions` | ТСП активен, план валиден; `amount ≤ mandate.maxAmount`; `period` совпадает с `mandate.period`; нет другой активной подписки на этот мандат (§2.1) | запись подписки |
| S2 | `DRAFT` | `PENDING_MANDATE` | указан `mandateId` (или создаётся согласие) | мандат существует **и принадлежит тому же ТСП**, что вызывающий (§2.1) | связывание |
| S3 | `PENDING_MANDATE` | `ACTIVE` | мандат перешёл в `ACTIVE` | — | подписка попадает в расписание планировщика |
| S4 | `ACTIVE` | `SUSPENDED` | приостановка (ТСП/банк; серия отказов списаний) | — | списания не инициируются, мандат сохраняется |
| S5 | `SUSPENDED` | `ACTIVE` | возобновление | мандат `ACTIVE`; на мандат нет другой активной подписки (иначе обход кардинальности через S4→S1→S5) | возврат в расписание |
| S6 | `ACTIVE`/`SUSPENDED`/`PENDING_MANDATE` | `CANCELLED` | отмена подписки ТСП | — | новые списания не инициируются; согласие не отзывается автоматически |
| S7 | `ACTIVE` | `ACTIVE` | изменение плана/суммы | при необходимости — переоформление согласия | аудит, outbox |
| S8 | — | `SUSPENDED` | мандат отозван/истёк (`REVOKED`/`EXPIRED`) | — | авто-приостановка подписки; outbox ТСП |

## 4. Рекуррентное списание (использует общую статусную машину платежа)

Списание — обычный платёж (`docs/spec/state-machine.md`) со ссылкой на подписку; отдельной финансовой модели нет (AD-012).

| № | Шаг | Условие | Действие | Идемпотентность |
|---|---|---|---|---|
| R1 | Планировщик выбирает наступление `billingPeriod` | подписка `ACTIVE`; мандат `ACTIVE`, `scheduledAt < validUntil`, `amount ≤ maxAmount` — **в одной транзакции** (§2.1); нет зачисленного платежа на этот период; **нет незавершённой («в полёте») инициации по этому мандату** (иначе нарушалось бы «≤1 в полёте на согласие», AD-011) | создать `CREATED` + outbox «инициация списания в ОПКЦ» | ключ `(subscriptionId, billingPeriod, attempt)` (AD-010) |
| R2 | Инициация в ОПКЦ | — | вызов `createSubscriptionDebit`, ожидание нотификации | повтор (транзиентный) возвращает тот же `paymentId`, `attempt` не меняется |
| R3 | Подтверждение | нотификация `PAID` (или сверка) | `CREATED → PAID` (**T4a**, без QR) → зачисление (AD-005/AD-012) | дедуп по `eventId` (ADR-004) |
| R4 | Отказ (недостаток средств и т.п.) | нотификация об отклонении | `FAILED`; новая попытка — только по политике ретраев, `attempt+1` | ключ `(subscriptionId, billingPeriod, attempt)`; зачисление возможно не более одного раза на период (AD-010) |
| R5 | Предварительное уведомление плательщика | до списания | шлюз обеспечивает **инициацию** уведомления через ОПКЦ; доставку физлицу выполняет банк плательщика/НСПК (вне контура эквайера) `[ТРЕБУЕТ ПРОВЕРКИ]` | ключ уведомления |
| R6 | Отзыв согласия | подтверждён переход мандата в `REVOKING`/`REVOKED` | для будущих списаний — запрет (AD-011); для «в полёте» — runbook (компенсация возвратом, см. §6) | по `paymentId` |
| R7 | Восстановление транспорта после простоя | период наступил, но `createSubscriptionDebit` не выполнен | политика пропущенного периода (догнать/пропустить) — по регламенту НСПК и решению A2; списание не инициируется, если прошло окно уведомления или истёк `validUntil` | по `(subscriptionId, billingPeriod, attempt)` |

Политика ретраев при отказе (число попыток, интервалы) согласуется с НСПК/бизнесом `[ТРЕБУЕТ ПРОВЕРКИ]`.

## 5. Запрещённые переходы и инварианты

- Списание при мандате ≠ `ACTIVE` — недостижимо (AD-009); статус и лимит/срок согласия проверяются в одной транзакции с созданием списания (§2.1).
- **Не более одного зачисленного списания** на пару `(subscriptionId, billingPeriod)` (AD-010). Повторный запуск планировщика и транзиентные ретраи идемпотентны (тот же `paymentId`, `attempt` не меняется). Новая попытка после явного отказа (`attempt+1`) допустима только по политике ретраев и не даёт второго зачисления за период.
- Инициация новых списаний после **подтверждённого** отзыва — недостижимо (AD-011); момент отзыва = подтверждённый переход мандата в `REVOKING`/`REVOKED` из ОПКЦ, а не действие плательщика в банке плательщика. До подтверждения действует окно актуализации (NFR §7: p95 ≤ 60 с); «в полёте» — runbook (§6).
- Зачисление по рекуррентному платежу — только из `PAID` (T4a), через общий шлюз зачисления (AD-005/AD-012); отдельного пути зачисления нет.
- Согласие, подписка и платёж не смешивают статусы (AD-013); финансовый эффект только у платежа.
- Подписка привязывается только к мандату того же ТСП; один мандат — одна активная подписка на ТСП (§2.1).

**Формат `billingPeriod` (компонент ключа идемпотентности):** строка идентификатора периода начала списания; для `period = MONTHLY` — `YYYY-MM`; для прочих периодов — `YYYY-MM-DD` начала периода. Таймзона расписания фиксирована (МСК). Формат нормализуется шлюзом до записи ключа — иначе одна и та же логическая пара даёт разные строки и детерминированность ключа теряется.

**Срок жизни ключа идемпотентности:** запись `(subscriptionId, billingPeriod, attempt) → paymentId` не удаляется быстрее, чем `период + окно ретраев` (по регламенту НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`), и переживает рестарты планировщика и смену календарного периода.

**ПДн и ретенция:** шлюз хранит минимум (идентификатор мандата, реквизиты согласия без избыточных ПДн); срок хранения и порядок удаления/анонимизации при `REVOKED` — по 152-ФЗ и политике банка; владелец — ИБ совместно с владельцем подписочного контура `[ТРЕБУЕТ ПРОВЕРКИ]`.

## 6. Сверка и восстановление

- Согласия и подписки включаются в регламентную сверку с НСПК (ADR-004): «у НСПК согласие `ACTIVE`, у нас нет» → дозапрос; «у нас `ACTIVE`, у НСПК нет» → стоп-сигнал.
- **Runbook «списание в полёте» (AD-011):** для каждого согласия допускается не более одного списания, уже отправленного в ОПКЦ на момент отзыва; урегулирование — компенсация возвратом (сага ADR-005) или подтверждение списания, по решению 4-eyes. Владелец runbook — дежурная смена платежей; runbook — обязательный артефакт изменения (см. `docs/solutioning-subscriptions.md` §7).
- Плановые списания, не нашедшие подтверждения, попадают в отчёт незавершённых операций и добираются сверкой.
- Планировщик восстанавливается после сбоя без двойных списаний (детерминированный ключ, AD-010).

## Критерии приёмки

- [ ] Когда планировщик запущен повторно на тот же `billingPeriod` (и при транзиентном ретрае), the шлюз shall не создавать второе зачисление и вернуть существующий `paymentId` (`attempt` не меняется) (AD-010).
- [ ] If мандат не `ACTIVE`, или `amount > maxAmount`, или `scheduledAt ≥ validUntil`, then инициация списания shall быть недостижима и фиксироваться алертом (AD-009, §2.1).
- [ ] If вызывающий ТСП не владеет `mandateId`, then создание подписки shall быть отклонено (изоляция ТСП, §2.1).
- [ ] If на мандат уже есть активная подписка, then создание второй shall быть отклонено (обход лимита, §2.1).
- [ ] If на мандат есть активная подписка, then возобновление другой подписки по этому мандату shall быть отклонено (S5; закрытие обхода S4→S1→S5).
- [ ] When приходит нотификация об отклонении списания, the платёж shall перейти в `FAILED` (переход `T4b`), повтор — только `attempt+1` (AD-010; `docs/spec/state-machine.md`).
- [ ] When получен подтверждённый отзыв согласия (`REVOKING`/`REVOKED`), the подписочный контур shall не инициировать новые списания; «в полёте» — не более одного на согласие и урегулирование по runbook (AD-011).
- [ ] Where платёж создан по подписке, the зачисление shall происходить только из `PAID` (T4a) через общий шлюз зачисления; путь через `QR_ISSUED` для подписки недостижим (AD-005/AD-012).
- [ ] When ТСП отменяет подписку, the согласие shall остаться в своём статусе (отмена подписки ≠ отзыв согласия) (AD-013).
- [ ] When наступает `billingPeriod`, the шлюз shall обеспечить инициацию предварительного уведомления плательщика через ОПКЦ (доставку выполняет банк плательщика/НСПК; владелец — R5) (AD-009, NFR §7).
- [ ] Каждый переход согласия/подписки/списания shall быть записан атомарно со статусом, outbox и аудит-логом (AD-002).

## Риски

- **Гонка «отзыв ↔ списание в полёте»**: списание уже отправлено в ОПКЦ — риск списания после волеизъявления; митигация: приоритет отзыва (AD-011), компенсация возвратом, runbook, 4-eyes для ручных операций.
- **Пики планировщика**: концентрация списаний на календарные даты → нагрузка и массовые отказы; митигация: разнесение расписаний, queue load leveling, приоритеты.
- **Внешний вход (протокол НСПК)**: UX подтверждения согласия, тайминги уведомления и коды отказа неизвестны — риск переделки контракта адаптера; митигация: `[ТРЕБУЕТ ПРОВЕРКИ]`, контракт адаптера финализируется после документации.
- **Доставка предварительного уведомления плательщику вне контура эквайера**: у эквайера нет канала и контакта плательщика (клиент другого банка); ответственность за доставку — на банке плательщика/НСПК. Митигация: явные границы ответственности в контракте адаптера, метрика только по инициации уведомления, открытый вопрос к НСПК.
- **ПДн плательщика**: согласие содержит идентифицирующие данные — риск нарушения 152-ФЗ; митигация: минимизация, шифрование, маскирование в логах, ретенция и удаление при `REVOKED` (AD-007, §5).
- **Пропущенный период при простое транспорта**: отложенная инициация может выйти за окно уведомления/`validUntil`; митигация: политика пропущенного периода (R7), решение A2, сверка.
- **Поведение при серии отказов**: агрессивные ретраи могут восприниматься как недобросовестные списания; митигация: политика ретраев, авто-приостановка подписки, уведомления.
