# Дельта: sbp-subscriptions (Подписки СБП — рекуррентные C2B-списания)

- Route: **Critical** (полный Solutioning — `docs/solutioning-subscriptions.md`; дельта — механизм авторизации правок защищённых файлов, не замена Solutioning)
- Created: 2026-09-28
- Решение: `docs/adr/ADR-008-podpiski-sbp-rekurrentnye-c2b-spisaniya-po-soglasiyu-platelschika.md` (Proposed)
- Статус дельты: propose (apply/archive — после A3)

## Проблема

ТСП (кинотеатры, ЖКХ, связь) просят рекуррентные списания по подписке; сейчас каждый C2B-платёж требует QR и действия плательщика. Нужно добавить согласие плательщика, подписку ТСП и планируемое списание так, чтобы: списание было невозможно без действующего согласия, повтор планировщика не давал двойной проводки, отзыв согласия немедленно останавливал будущие списания, а зачисление по-прежнему происходило только из подтверждённого `PAID`.

## ADDED

- **REQ-SUB-1.** When планировщик запущен повторно на тот же `billingPeriod` (или происходит транзиентный ретрай), the шлюз shall вернуть существующий `paymentId` и не создать второе **зачисленное** списание (ключ `(subscriptionId, billingPeriod, attempt)`; AD-010).
- **REQ-SUB-2.** If статус согласия ≠ `ACTIVE`, или `amount > maxAmount`, или `scheduledAt ≥ validUntil`, then инициация списания shall быть недостижима и фиксироваться алертом (AD-009).
- **REQ-SUB-2a.** If вызывающий ТСП не владеет `mandateId` или на мандат уже есть активная подписка, then создание подписки shall быть отклонено (`MANDATE_NOT_OWNED`/`SUBSCRIPTION_EXISTS`) (AD-009/AD-013).
- **REQ-SUB-2b.** When платёж создан по подписке, the его путь до `PAID` shall идти без QR (`CREATED → PAID`, `debitId`) и не требовать `qrId` (AD-012).
- **REQ-SUB-3.** When получен подтверждённый отзыв согласия, the подписочный контур shall немедленно исключить мандат из планировщика и не инициировать новые списания (AD-011).
- **REQ-SUB-4.** Where платёж создан по подписке, the зачисление shall происходить только из `PAID` через общий шлюз зачисления (AD-005/AD-012).
- **REQ-SUB-5.** When ТСП отменяет подписку, the согласие плательщика shall остаться в текущем статусе (AD-013).
- **REQ-SUB-6.** When наступает `scheduledAt`, the шлюз shall обеспечить инициацию предварительного уведомления плательщика через ОПКЦ в срок по регламенту НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` (доставку физлицу выполняет банк плательщика/НСПК — R5).
- **REQ-SUB-7.** When вендорский транспорт недоступен, the шлюз shall не терять списания (очередь/DLQ, отчёт незавершённых операций, сверка добирает результат).
- **REQ-SUB-8.** When ТСП вызывает любой метод v0.1 после релиза v0.2, the поведение shall не измениться (аддитивность контракта).
- **ADDED (артефакты):** сущности `mandate`/`subscription`/`billing_schedule`/`debit_attempt`; автоматы согласия и подписки (`docs/spec/subscriptions.md`); новые методы API ТСП (`/v1/mandates*`, `/v1/subscriptions*`); новые методы/события контракта адаптера ОПКЦ; раздел NFR «Подписки СБП» (`docs/nfr.md` §7).

## План отката

См. `docs/solutioning-subscriptions.md` §6.2. Кратко: до боёвки — не включать (feature-flag); после — `stop-new` (запрет новых согласий/подписок) + остановка планировщика по новым периодам + отключение подписочной фичи; откат релиза ядра — только для компонентов **вне** подписочного контура (контур остаётся на предыдущей совместимой версии, blue-green); компенсации по саге возвратов (ADR-005); данные согласий не удаляются, отзывы обслуживаются; владелец решения — архитектор + продукт + дежурная смена; RTO ≤ 1 ч.

## Критерии приёмки

- [ ] Повторный запуск планировщика/транзиентный ретрай на тот же период не создаёт второе зачисление (REQ-SUB-1/AD-010).
- [ ] Списание при мандате ≠ `ACTIVE`, сверх лимита или после `validUntil` недостижимо и алертит (REQ-SUB-2/AD-009).
- [ ] Подписка на чужой мандат или вторая подписка на мандат отклоняется (REQ-SUB-2a/AD-009,AD-013).
- [ ] Рекуррентный платёж достигает `PAID` без `qrId` (T4a) (REQ-SUB-2b/AD-012).
- [ ] После подтверждённого отзыва нет новых инициаций; «в полёте» — по runbook (REQ-SUB-3/AD-011).
- [ ] Зачисление по подписке только из `PAID` (REQ-SUB-4/AD-005,AD-012).
- [ ] Отмена подписки не отзывает согласие (REQ-SUB-5/AD-013).
- [ ] Уведомление плательщика до списания — 100 % в срок `[ТРЕБУЕТ ПРОВЕРКИ]` (REQ-SUB-6).
- [ ] Вендорский транспорт недоступен — списания не теряются, виден отчёт (REQ-SUB-7).
- [ ] API v0.1 остаётся рабочим после v0.2 (`contract-diff` — без ломающих; regression-тест) (REQ-SUB-8).
- [ ] Критерий успешного отката: существующие согласия/подписки обслуживаются, расхождений сверки — 0.
