# Архитектурный контекст (epic-context) — рекуррентные C2B-списания (подписки СБП)

Собрано: 2026-09-28. Источники: `ARCHITECTURE-SPINE.md` (AD-001..AD-009), `docs/adr/ADR-008-*.md`, `docs/nfr.md` §7, `openapi/tsp-api.yaml` v0.2, `docs/contracts/opkc-adapter.md` §10, `openspec/changes/add-sbp-recurring-subscriptions/`.

## Цель эпика

Дать ТСП (кинотеатры, ЖКХ, связь) **рекуррентные C2B-списания по однократному согласию плательщика** без QR и без действия клиента на каждое списание. Инициатор финансовой операции — ТСП, а не плательщик. Все финансовые инварианты принятого решения сохраняются без ослабления.

## Что построить (стыки)

1. **Согласие (consent)**: регистрация/подтверждение/отзыв мандата плательщика в ОПКЦ; локальная сущность со статусом `PENDING/ACTIVE/REVOKED/EXPIRED`; сквозная ссылка на мандат ОПКЦ.
2. **Подписка (subscription)**: план списаний, привязанный к одному согласию; статусы `ACTIVE/SUSPENDED/REVOKED/EXPIRED`; параметры иммутабельны после активации.
3. **Списание (charge)**: платёж в существующей статусной машине БЕЗ стадии `QR_ISSUED`: `CREATED → PAID → CREDITED → COMPLETED`. Зачисление в АБС — только из `PAID`.
4. **Идемпотентность периода**: уникальный ключ `(subscriptionId, billingPeriod)` + уникальный индекс в БД + идемпотентность `reference` в адаптере.
5. **Планировщик** плановых списаний (идемпотентный запуск) и **сервис уведомлений** плательщику (идемпотентный по `(chargeId, notificationType)`).
6. **Контракты**: API ТСП — аддитивно до v0.2.0 (`/v1/consents*`, `/v1/subscriptions*`, `/v1/charges*`, опциональные поля `Payment`, новые вебхуки); внутренний контракт адаптера ОПКЦ — §10 (методы/события мандатов и списаний), реализует вендор.
7. **Возвраты** по списаниям — существующая сага (ADR-005), без новой модели.

## Связывающие инварианты (Rule — дословно, менять нельзя)

- **AD-001**: Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза (проверка: сетевые правила и код — единая точка вызова; fitness: отсутствие исходящих вызовов НСПК/АБС вне адаптеров).
- **AD-002**: Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера (ревью + fitness-тест на каждый переход).
- **AD-003**: Повторная доставка любого сообщения не изменяет уже завершённое состояние. Fitness: тест «повторная нотификация/повторный запрос → состояние не меняется, результат идемпотентен».
- **AD-005**: Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Fitness: проверка недостижимости зачисления из `CREATED`/`QR_ISSUED`.
- **AD-008**: Ядро шлюза проектируется контрактно-независимым от транспорта (внутренний контракт адаптера ОПКЦ — единственная зависимость). Реализация транспортного слоя начинается только после подписания контракта и получения документации НСПК.
- **AD-009 (новый, Proposed → после ратификации)**: Списание SHALL быть невозможным без подтверждённого ОПКЦ согласия и активной подписки; каждое списание MUST иметь уникальный ключ `(subscriptionId, billingPeriod)`; отзыв согласия MUST прекращать все будущие списания; уведомление плательщику о предстоящем списании MUST быть отправлено не позднее регламентного срока.

## Явные запреты

- НЕ менять модель зачисления (только из `PAID`), модель идемпотентности, trust-зоны, стратегию «гибрид» (AD-008).
- НЕ реализовывать протокол НСПК в ядре — только через адаптер (детали протокола — у вендора; `[ТРЕБУЕТ ПРОВЕРКИ]`).
- НЕ создавать второй источник истины по финансовым операциям (никакого отдельного сервиса «подписок» со своей БД статусов).
- НЕ реализовывать реальный транспорт НСПК: тестовый контур — мок-адаптер; реальный транспорт — после контракта с вендором.
- Конфликт с любым AD-001..AD-009 обязан **останавливать работу** и эскалироваться, а не решаться на усмотрение исполнителя.

## Не в scope

C2C, выплаты B2C/B2B, диспуты/претензии, мультивалютность; реализация кода протокола НСПК. Решения §7 design (владелец расписания, канал/срок уведомления, политика при недоступности канала, политика ретраев, scope первой волны) — принимаются человеком-архитектором до реализации соответствующих частей.
