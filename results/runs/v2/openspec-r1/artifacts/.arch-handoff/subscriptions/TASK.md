# Задача для кодового харнесса — рекуррентные C2B-списания (подписки СБП)

Реализовать расширение СБП-шлюза (C2B-приём) рекуррентными списаниями по согласию плательщика по решению `docs/adr/ADR-008-*.md`, блоку `AD-009` (`ARCHITECTURE-SPINE.md`), спецификации и дизайну change `openspec/changes/add-sbp-recurring-subscriptions/`. Детальный чек-лист работ — `tasks.md` того же change.

**Предпосылки (без них работа не начинается):** ратификация ADR-008/AD-009 человеком-архитектором и ответы на решения §7 design. Если предпосылки не закрыты — статус `blocked` с перечислением недостающих входов, без изобретения решений.

## Объём

1. Агрегаты `Consent`, `Subscription`, `Charge` в БД шлюза; уникальный индекс `(subscriptionId, billingPeriod)`.
2. Расширение статусной машины: списание без стадии `QR_ISSUED` (`CREATED → PAID → CREDITED → COMPLETED`); атомарность «статус + outbox + аудит»; зачисление только из `PAID`.
3. REST API ТСП аддитивно (`openapi/tsp-api.yaml` v0.2): согласия/подписки/списания + вебхуки; `openapi-diff` — 0 breaking changes; старый потребитель не затронут.
4. Расширение контракта адаптера ОПКЦ (`docs/contracts/opkc-adapter.md` §10) и **мок-адаптер** (регистрация/отзыв мандата, списание, события, идемпотентность по `reference`). Реальный протокол НСПК НЕ реализуется (внешний вход).
5. Планировщик плановых списаний (идемпотентный запуск) и обработка неуспеха (ограниченные ретраи, DLQ).
6. Сервис уведомлений плательщику (предстоящее + состоявшееся списание), идемпотентный, с политикой при недоступности канала.
7. Возвраты по списаниям — существующей сагой; расширение сверки и отчёта незавершённых операций.
8. Аудит, метрики/алерты, дополнение `docs/nfr.md` §7.

## Критерии приёмки (проверяемы тестом)

**Позитивные:** сквозной путь `consent → subscription → списание → COMPLETED` (AC-1); возврат по списанию (AC-2); доставка вебхуков с ретраями/DLQ и дедупом по `eventId` (AC-3); `openapi-diff` breaking = 0 (AC-4).

**Негативные (обязательны):** повторный/параллельный триггер списания за период → одно списание (AC-5); повторная нотификация не меняет завершённое состояние, новый `eventId` → алерт (AC-6); списание по отозванному/неподтверждённому согласию отклонено, АБС не вызывается (AC-7); зачисление из `CREATED` недостижимо (AC-8); недостаток средств → `FAILED`, успешных списаний за период ≤ 1 (AC-9); недоступность АБС после `PAID` → операция не теряется (AC-10); гонка «`PAID` + отзыв» → списание доведено, будущие прекращены (AC-11); недоступность канала уведомления → применена политика, инцидент зафиксирован (AC-12); нагрузка/идемпотентность — двойных списаний 0, RPO=0 (AC-13).

**Критерий успешного отката:** `stop-new` (запрет новых согласий/подписок и плановых списаний) выключает приём нового, открытые списания доведены/видны в отчёте незавершённых, уведомления не потеряны, двойных списаний 0, разовые платежи деградировали.

## План отката (кратко)

До боевой эксплуатации — фиче-флаг off (полностью обратимо). После — `stop-new` per-ТСП + rolling-откат релиза; данные согласий не удаляются (уведомления/аудит/регуляторные сроки); сверка закрывает расхождения. Владелец решения об откате — владелец продукта/CIO + ИБ (не один инженер).

## Контракт результата

Финальный ответ обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `status`: `complete` — выполнено полностью; `partial` — частично; `blocked` — заблокировано.
- `assumptions`: допущения, принятые при реализации.
- `open_questions`: вопросы к архитектору.
- `conflicts_with_prior_decisions`: расхождения с принятыми ранее решениями (ADR, spine); при расхождении — остановиться и эскалировать.

Инварианты — `.arch-handoff/subscriptions/ARCHITECTURE.md` (Rule дословно), ограничения — `.arch-handoff/subscriptions/CONSTRAINTS.yaml`, рубрика — `.arch-handoff/RUBRIC.yaml`.
