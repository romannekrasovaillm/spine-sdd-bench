# Proposal

## Why

Ключевые ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** («подписки СБП»). Принятое решение `ARCHITECTURE-SPINE.md` и контракт `openapi/tsp-api.yaml` v0.1 покрывают только разовые платежи: каждый платёж требует динамического QR/ссылки и подтверждающего действия клиента в приложении банка. Для подписок это экономически и операционно неприемлемо — нужен механизм однократного согласия плательщика и последующих списаний, инициируемых ТСП, при сохранении всех действующих финансовых инвариантов (зачисление только из `PAID`, идемпотентность, RPO=0, изоляция платёжного контура).

## What Changes

- Новый доменный объект **«Согласие плательщика» (consent, мандат)** — регистрация однократного согласия на рекуррентные списания в пользу ТСП через ОПКЦ СБП, хранение ссылки на мандат, отзыв согласия плательщиком или ТСП.
- Новый доменный объект **«Подписка» (subscription)** — план списаний ТСП (сумма, период/расписание, лимиты), привязанный к consent; собственный конечный автомат со статусами `ACTIVE`/`SUSPENDED`/`REVOKED`/`EXPIRED`.
- **Инициируемое ТСП списание по подписке (charge)** без QR и без действия клиента на каждое списание: платёж-списание проходит `CREATED → PAID → CREDITED → COMPLETED` (стадия `QR_ISSUED` отсутствует), зачисление по-прежнему **только из подтверждённого `PAID`**.
- **Обязательные уведомления плательщика** о каждом списании и о предстоящем списании — в объёме и сроках, требуемых 161-ФЗ и правилами ОПКЦ СБП (точный регламент — внешний вход).
- **Идемпотентность списаний на уровне ключа периода** `(subscriptionId, billingPeriod)` / `chargeId`: повторные и параллельные триггеры не создают второе списание.
- **Расширение контракта API ТСП** (`openapi/tsp-api.yaml`) обратно совместимо: новые ресурсы `consents` и `subscriptions`, новые типы вебхуков, новые **опциональные** поля в `Payment`. Существующие потребители (разовые платежи, возвраты, статусы) не меняются.
- **Расширение внутреннего контракта адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`) новыми методами и событиями (регистрация/отзыв согласия, списание, статус списания) — граница ядро↔транспорт `AD-008` сохраняется, ядро по-прежнему контрактно-независимо от протокола НСПК.
- Возвраты по рекуррентным списаниям — существующая **сага возврата** (`ADR-005`) без изменения модели.
- Новые измеримые NFR для подписок (доля успешных списаний, время регистрации согласия, лаг уведомлений, отсутствие двойных списаний, поведение при недостатке средств).

Не меняется: топология шлюза (`AD-001`), единый источник истины — статусная машина платежа (`AD-002`), модель идемпотентности (`AD-003`), единственный адаптер ОПКЦ (`AD-004`), правило «зачисление только из `PAID`» (`AD-005`), trust-зоны (`AD-006`), соответствие НПС/КИИ/ПДн (`AD-007`), стратегия «гибрид» (`AD-008`).

## Capabilities

### New Capabilities

- `sbp-subscriptions`: жизненный цикл согласия плательщика и подписки, инициируемые ТСП рекуррентные списания, уведомления плательщику, отзыв согласия, устойчивость к повторным/параллельным триггерам, расширение контрактов (API ТСП и адаптер ОПКЦ) обратно совместимым способом.

### Modified Capabilities

Нет. Спецификации `openspec/specs/` пусты — принятое решение хранится в `ARCHITECTURE-SPINE.md`/`docs/` и вводится в OpenSpec настоящим change как новая capability. Изменения принятых файлов решения оформляются отдельными ADR (см. design.md §«Влияние на принятую архитектуру»).

## Impact

- **Контракт API ТСП** `openapi/tsp-api.yaml`: минорный рост версии `0.1.0 → 0.2.0`, только аддитивные изменения (`/v1/consents*`, `/v1/subscriptions*`, опциональные поля `Payment`, новые вебхуки). Ломающих изменений нет.
- **Документы решения**: новый `docs/adr/ADR-008-*.md` (Status: Proposed, требуется ратификация человеком-архитектором), новый блок `AD-009` в `ARCHITECTURE-SPINE.md` (Status: Proposed, ADR-008), дополнение `docs/nfr.md`, дополнение `docs/contracts/opkc-adapter.md`.
- **Ядро шлюза**: новые агрегаты `Consent`, `Subscription`, `Charge`; расширение статусной машины; планировщик списаний; обработчик уведомлений плательщику; расширение outbox/аудита.
- **Адаптер ОПКЦ (вендорский)**: новые методы/события — вне scope ядра, попадают в RFP-пакет (`docs/rfp/vendor-rfp.md`).
- **АБС**: без изменения контракта — списание по-прежнему идемпотентное зачисление по `paymentId` (рекуррентный платёж — обычный платёж для АБС).
- **ИБ/ПДн**: согласие плательщика и идентификаторы для уведомлений — персональные данные; требуется согласование с ИБ (152-ФЗ) и правилами 161-ФЗ.
- **Эксплуатация**: новые метрики (успешность списаний, лаг уведомлений, отказы по недостатку средств), новые runbook-сценарии.

## Non-goals

- C2C-переводы, выплаты B2C/B2B, диспуты — остаются в `Deferred` spine.
- Реализация протокола НСПК для согласий/списаний — за вендором транспорта (`AD-008`); точные поля и тайминги — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Изменение модели зачисления, идемпотентности и trust-зон — эти инварианты переиспользуются как есть.
