# Design

## Context

См. `proposal.md` — Why. Проектный контекст, который определяет подход:

- Принятое решение (`ARCHITECTURE-SPINE.md`, `ADR-001..007`, `docs/solutioning.md`) покрывает **разовые** C2B-платежи: инициатор — плательщик (через QR), каждый платёж требует действия клиента.
- Ядро шлюза — собственная разработка, транспорт к ОПКЦ — вендорский (AD-008, ADR-007). Граница «ядро ↔ адаптер» (`docs/contracts/opkc-adapter.md`) — единственная зависимость ядра от протокола НСПК.
- Модель консистентности: конечный автомат платежа в БД шлюза как единый источник истины, транзакционный outbox, идемпотентность по `eventId`/`reference`/`Idempotency-Key` (ADR-001, ADR-002, ADR-004).
- Зачисление в АБС — только из подтверждённого `PAID`; возвраты — сага (ADR-005).
- Точный протокол НСПК (в частности, по мандатам на рекуррентные списания и уведомлениям плательщика) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`: получается по договору/документации НСПК. Настоящий дизайн фиксирует внутреннюю модель и границы, а не протокольные детали.

Новое требование бизнеса меняет **инициатора** финансовой операции: списание запускает ТСП (по расписанию/подписке), а не плательщик. Это новый класс операций, который нагружает существующие инварианты иначе, чем разовый платёж.

## Goals / Non-Goals

**Goals:**

- Рекуррентные списания по однократному согласию плательщика без QR и без действия клиента на каждое списание.
- Сохранить все финансовые инварианты принятого решения без ослабления: `AD-002` (атомарные переходы), `AD-003` (идемпотентность), `AD-005` (зачисление только из `PAID`), `AD-001`/`AD-004` (изоляция, единственный адаптер), `AD-006`/`AD-007` (trust, аудит).
- Обратно совместимое расширение контракта API ТСП и внутреннего контракта адаптера ОПКЦ.
- Готовый к вынесению на архитектурное решение и передаче исполнителям пакет: ADR-008, дельта spine, контракты, NFR, критерии приёмки, откат.

**Non-Goals:**

- Реализация протокола НСПК по мандатам/списаниям (вендор, AD-008).
- C2C, выплаты, диспуты (остаются `Deferred`).
- Изменение модели зачисления, идемпотентности и trust-зон — переиспользуются как есть.
- Реализация кода — пакет планирующий; далее `/opsx-apply`.

## 1. Оценка значимости и маршрут

Оценка по пяти факторам, шкала 1–3 (3 — максимальное влияние):

| Фактор | Оценка | Обоснование |
|---|---|---|
| Финансовый риск и характер операций | 3 | Новый класс операций: списание инициирует ТСП без действия клиента — цена ошибки (двойное списание, списание без согласия) выше, чем у разового платежа |
| Внешние зависимости и регуляторика | 3 | Новые взаимодействия с ОПКЦ (мандат), обязательные уведомления плательщику (161-ФЗ/правила ОПКЦ), рост объёма ПДн |
| Изменение границ и инвариантов | 3 | Новые агрегаты, расширение статусной машины и обоих контрактов; затрагивает AD-002/003/004/005 |
| Обратимость / стоимость отката | 2 | До боевой эксплуатации полностью обратимо фиче-флагом; после — costly (данные согласий, обязательные уведомления, регуляторный след) |
| Операционная сложность и эксплуатация | 1 | Переиспользует существующую очередь/outbox/сверку/мониторинг; добавляет планировщик и уведомления (runbook), без новой инфраструктуры |

**Итог: 12/15 (высокая значимость). Маршрут — Critical.** Обоснование маршрута: изменение является **дельта-изменением поверх уже принятого Critical-решения** (11/15), вводит новый класс финансовых операций и регуляторно обязательные уведомления. Поэтому требуется:

- полное проектирование (design + новый ADR + дельта spine + изменение контрактов) — **сделано в этом пакете**;
- **человеческое решение** (аналог гейта A3) по ADR-008 и по списку §7 — до реализации транспорта и до боевой эксплуатации;
- гейты A1/A2/A4/A5 из `docs/solutioning.md` применяются к расширенному scope (контракты, NFR, fitness, сверка).

Глубина проектирования оправдана: недостаточно «добавить эндпоинт», потому что меняется инициатор операции, добавляется сущность согласия (регуляторно значимая) и обязательные уведомления; при этом подход намеренно **минимально инвазивен** — расширяет существующие механизмы, а не строит параллельную подсистему.

## 2. Влияние на принятую архитектуру

| Инвариант (spine) | Статус | Что меняется / что нет |
|---|---|---|
| `AD-001` Изоляция платёжного контура | Не меняется | Новые взаимодействия с ОПКЦ идут через тот же адаптер; «приём продолжается при сбое» сохраняется |
| `AD-002` Единый источник истины — статусная машина | **Затронут (расширение)** | Добавляются агрегаты `Consent` и `Subscription` со своими автоматами; платёж-списание проходит `CREATED → PAID → CREDITED → COMPLETED` (пропуск `QR_ISSUED`). Правило «переход = одна транзакция + outbox + аудит» сохраняется без изменений |
| `AD-003` Идемпотентность | **Затронут (расширение)** | Новые ключи: `consentId`, `subscriptionId`, и главное — `(subscriptionId, billingPeriod)`; сохраняется требование «повторная доставка не меняет завершённое состояние» |
| `AD-004` Единственный адаптер ОПКЦ | **Затронут (расширение)** | Внутренний контракт адаптера получает новые методы/события (мандат, списание). Граница «протокол НСПК знает только адаптер» не меняется |
| `AD-005` Зачисление только из подтверждённого `PAID` | Не меняется | Рекуррентное списание зачисляется только из `PAID`; недостижимость зачисления из `CREATED` — по-прежнему fitness-тест |
| `AD-006` Trust-зоны и сегментация | Не меняется | Новые данные (согласия) размещаются в том же платёжном контуре; ключи — в СКЗИ/HSM |
| `AD-007` НПС/КИИ/ПДн | **Затронут (объём данных)** | Согласие и идентификаторы для уведомлений — ПДн; расширяется аудит (переходы списаний, отзывы) и интеграция с антифрод/AML |
| `AD-008` Стратегия «гибрид» | Не меняется | Ядро остаётся контрактно-независимым; новые протокольные методы реализует вендор |

**Что меняется:** доменная модель (новые агрегаты), статусная машина (платёж без QR; автоматы согласия/подписки), API ТСП (аддитивно), внутренний контракт адаптера (аддитивно), NFR (новый раздел), RFP (новые критерии/сценарии POC).

**Что не меняется:** топология и состав компонентов, модель консистентности и идемпотентности, правило зачисления, trust-зоны, криптография, стратегия реализации, сага возврата, сверка.

**Предлагаемая дельта spine (новый инвариант, оформить как `AD-009`, Status: Proposed, ADR-008):**

> **AD-009. Рекуррентные списания только по действующему подтверждённому согласию.**
> **Binds:** агрегаты `Consent`/`Subscription`, статусная машина списания, уведомления плательщику, адаптер ОПКЦ.
> **Prevents:** списание без подтверждённого согласия; двойное списание за период; списание после отзыва согласия; уведомление плательщика после факта (нарушение 161-ФЗ).
> **Rule:** Списание SHALL быть невозможным без подтверждённого ОПКЦ согласия и активной подписки; каждое списание MUST иметь уникальный ключ `(subscriptionId, billingPeriod)`; отзыв согласия MUST прекращать все будущие списания; уведомление плательщику о предстоящем списании MUST быть отправлено не позднее регламентного срока.

## Decisions

### D1. Расширять существующий шлюз, а не строить отдельную подсистему подписок

- **Выбрано:** новые агрегаты и эндпоинты живут в **том же** СБП-шлюзе и той же БД, переиспользуют статусную машину, outbox, идемпотентность, сверку, аудит и сагу возврата.
- **Альтернативы:**
  | Вариант | Плюсы | Минусы |
  |---|---|---|
  | Отдельный сервис «подписки» рядом со шлюзом | Изоляция, свои релизы | Второй источник истины по финансовым операциям → нарушает AD-002; дублирование идемпотентности/сверки; сквозной аудит и сверка усложняются |
  | Полностью на стороне ТСП, без мандата в ОПКЦ | Нулевые изменения банка | Невозможно: рекуррентное списание через СБП требует мандата в ОПКЦ; вне регулирования |
  | Вендорская «коробка» подписок | Быстрый старт | Противоречит AD-008 (ядро — собственная разработка), закрывает финансовую логику, vendor lock-in |

### D2. Согласие (consent) — хранимая сущность шлюза, мандат — в ОПКЦ

- **Выбрано:** шлюз хранит согласие как сущность со статусом (подтверждено/отозвано/истекло) и сквозной ссылкой на мандат ОПКЦ; регистрация/отзыв идут через адаптер; списание невозможно без подтверждённого согласия.
- **Альтернативы:** хранить состояние только в ОПКЦ и опрашивать при каждом списании (нет локальной истины, ломает RPO=0 и AD-002, лишняя зависимость в горячем пути); хранить «согласие» в АБС (АБС не знает СБП-согласий, нарушает AD-005/границы).

### D3. Списание — платёж в существующей статусной машине (без `QR_ISSUED`)

- **Выбрано:** списание (charge) — платёж с тем же автоматом и теми же гарантиями; стадия `QR_ISSUED` для него недостижима, платёж создаётся сразу в `CREATED` и переходит в `PAID` по подтверждению ОПКЦ. Зачисление — только из `PAID` (AD-005) без изменений.
- **Альтернативы:** отдельная статусная машина для подписок (дублирование финансовой логики, риск расхождения с AD-002/AD-005, два аудита); «особый» платёж без статусной модели (неприемлемо — нет SSOT).

### D4. Идемпотентность по ключу периода `(subscriptionId, billingPeriod)`

- **Выбрано:** уникальный ключ списания = `(subscriptionId, billingPeriod)`; API дополнительно требует `Idempotency-Key`/`chargeId` от ТСП. Повторный или параллельный триггер за тот же период возвращает существующее списание и не создаёт второе обращение к ОПКЦ/АБС. Дублирующая защита: уникальный индекс в БД + идемпотентность `reference` в адаптере.
- **Альтернативы:** только `Idempotency-Key` от ТСП (не защищает от параллельных триггеров разными ключами за один период); только по времени расписания (хрупко при сдвигах/повторных запусках планировщика).

### D5. Владелец расписания списаний — развилка (см. §7)

- **Дизайн:** модель подписки допускает оба режима: (а) расписание хранит шлюз и сам инициирует списание («pull»); (б) ТСП триггерит списание через API («push»), шлюз обеспечивает идемпотентность периода. В обоих режимах ключ идемпотентности один и тот же.
- **Рекомендация архитектора:** режим (а) как основной (детерминизм, своевременность, единый контроль), с опциональным on-demand списанием. **Финальный выбор — за человеком-архитектором** (влияет на контракт и NFR).

### D6. Канал и срок уведомления плательщику — развилка (см. §7)

- **Дизайн:** уведомления выносятся как отдельный сервис ядра с идемпотентной отправкой и аудитом; состав/срок/канал — конфигурируемы; при недоступности канала применяется утверждённая политика (по умолчанию — списание задерживается до уведомления).
- **Развилка:** уведомляет банк-эквайер, банк плательщика (через ОПКЦ) или ТСП — распределение ответственности и точный срок требуют решения человека (регуляторная трактовка).

### D7. Расширение контракта API ТСП — аддитивное, минорная версия

- **Выбрано:** только новые ресурсы и опциональные поля; `/v1` сохраняется; версия `0.1.0 → 0.2.0`. Ломающие изменения — только `/v2` с поддержкой ≥ 6 мес (см. §4).

### D8. Расширение адаптера ОПКЦ — в контракте адаптера, не в ядре

- **Выбрано:** новые протокольные операции (регистрация/отзыв мандата, списание, статус списания) добавляются в `docs/contracts/opkc-adapter.md` и реализуются вендором. Ядро работает с нормализованными статусами; требования идемпотентности по `reference`, тестовый контур, СКЗИ распространяются на новые методы (ADR-007, AD-008).

## 4. Изменения контрактов

### 4.1 `openapi/tsp-api.yaml` (v0.1.0 → v0.2.0, только аддитивно)

Новые пути (все в `/v1`):

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/v1/consents` | Регистрация согласия плательщика (идемпотентно по `Idempotency-Key`) |
| `GET` | `/v1/consents/{consentId}` | Статус согласия (подтверждено/отозвано/истекло) |
| `POST` | `/v1/consents/{consentId}/revoke` | Отзыв согласия |
| `POST` | `/v1/subscriptions` | Создание подписки по действующему согласию |
| `GET` | `/v1/subscriptions/{subscriptionId}` | Статус/параметры подписки |
| `POST` | `/v1/subscriptions/{subscriptionId}/suspend` | Приостановка |
| `POST` | `/v1/subscriptions/{subscriptionId}/resume` | Возобновление |
| `GET` | `/v1/subscriptions/{subscriptionId}/charges` | История списаний |
| `POST` | `/v1/subscriptions/{subscriptionId}/charges` | On-demand списание (ключ периода) |
| `GET` | `/v1/charges/{chargeId}` | Статус списания (совместим по смыслу с `Payment`) |

Новые схемы: `Consent`, `Subscription`, `ChargeRequest`, `Charge` (расширение `Payment`). Расширение существующей `Payment` — **только опциональные** поля: `subscriptionId?`, `consentId?`, `initiator` (`PAYER` | `MERCHANT`, default `PAYER`). Существующие обязательные поля и перечисления не меняются (перечисление `status` сохраняется).

Новые вебхуки (аддитивно, в дополнение к `payment.*`/`refund.*`): `consent.registered`, `consent.revoked`, `subscription.activated`, `subscription.suspended`, `subscription.revoked`, `charge.completed`, `charge.failed` (списание также отражается существующим `payment.completed`/`payment.failed` с `initiator: MERCHANT` — для потребителей, уже слушающих `payment.*`).

**Гарантия совместимости:** удалённых/переименованных путей, полей и значений нет; ранее обязательные поля не меняют обязательность/тип; старые потребители продолжают работать без изменений. Это проверяется тестом на `openapi-diff` (breaking changes = 0).

### 4.2 `docs/contracts/opkc-adapter.md` (v0.1 → v0.2, аддитивно)

- Новые синхронные методы: `registerConsent`, `revokeConsent`, `getConsentStatus`, `createCharge` (списание по мандату), `getChargeStatus`.
- Новые асинхронные события: `consent.registered`, `consent.revoked`, `charge.paid`, `charge.rejected`, `charge.expired` (или подтверждение списания в терминах `payment.*` — нормализация за адаптером).
- Все мутирующие вызовы — идемпотентны по `reference` (`consentId`/`chargeId` шлюза); дедупликация событий — по `eventId` на стороне ядра (без изменений AD-004).
- В RFP (`docs/rfp/vendor-rfp.md`) добавляются критерии: поддержка мандатов/списаний, сценарии POC (регистрация/отзыв мандата, повторный `createCharge` с тем же `reference` → одно списание, отвоб/отказ, повтор события).

### 4.3 Внутренняя модель (не контракт, для исполнителей)

- `Consent`: `consentId`, `tspId`, ссылка на мандат ОПКЦ, статус (`PENDING`/`ACTIVE`/`REVOKED`/`EXPIRED`), срок действия, аудит.
- `Subscription`: `subscriptionId`, `consentId`, `tspId`, сумма, расписание/период, лимиты, статус (`ACTIVE`/`SUSPENDED`/`REVOKED`/`EXPIRED`), иммутабельность параметров.
- `Charge`: расширение сущности платежа — `chargeId`, `subscriptionId`, `billingPeriod`, уникальный индекс `(subscriptionId, billingPeriod)`, `initiator=MERCHANT`.
- Планировщик списаний: триггер по расписанию → создание `Charge` (идемпотентно) → существующий пайплайн (ОПКЦ → `PAID` → АБС → `COMPLETED`).
- Сервис уведомлений плательщику: идемпотентная отправка (ключ `(chargeId, notificationType)`), аудит, политика при недоступности канала.

## 5. NFR

Измеримые цели; полное закрепление — в `docs/nfr.md` (раздел «NFR подписок»). Значения — baseline, уточняются регламентами НСПК и бизнесом.

| Метрика | Цель | Метод проверки |
|---|---|---|
| Регистрация согласия (API → ответ, без времени ОПКЦ) | p95 < 500 мс | Нагрузочный тест, APM |
| Подтверждение согласия ОПКЦ (асинхронно) | p95 < 5 с при доступном ОПКЦ `[ТРЕБУЕТ ПРОВЕРКИ — регламент НСПК]` | Метрика процесса |
| Запуск планового списания (от планового момента до запроса в ОПКЦ) | p95 < 2 с; p99 отклонения от расписания < 30 с | Метрика планировщика |
| Завершение списания (`PAID → CREDITED → COMPLETED`) | p95 < 60 с от `PAID` (SLA АБС) | Метрика процесса |
| Доля успешных списаний (с ретраями) | ≥ 98 % | Отчётность |
| Уведомление о предстоящем списании | 100 % списаний, не позднее регламентного срока `[ТРЕБУЕТ ПРОВЕРКИ]` | Отчёт, тест |
| Лаг уведомления о состоявшемся списании | p95 < 60 с | Метрика |
| Двойные списания | 0 | Тест на повторные/параллельные триггеры |
| Отзыв согласия → прекращение будущих списаний | 100 % отклоняются; применено ≤ 5 с от получения отзыва | Тест |
| Throughput рекуррентных списаний | sustained 200 TPS, пик 500 TPS, биллинговое окно burst 1000 TPS/1 мин | Нагрузочный тест |
| RPO / RTO | RPO=0; RTO ≤ 1 ч | Chaos/DR |
| Аудит финансовых переходов списаний | 100 %, неизменяемый | Аудит, SIEM |
| Отказы по недостатку средств | классифицированы; ретраи ≤ политики | Тест, отчётность |

## Risks / Trade-offs

- **[Двойное списание при ретраях/параллельных триггерах]** → уникальный ключ `(subscriptionId, billingPeriod)`, уникальный индекс в БД, идемпотентность `reference` в адаптере, fitness-тест на дубль (обязательный критерий приёмки).
- **[Списание без действующего согласия]** → guard во всех точках инициации; `CONSENT_NOT_ACTIVE`; тест «списание по отозванному согласию».
- **[Нарушение 161-ФЗ по срокам уведомлений]** → уведомление как обязательный шаг до списания; политика при недоступности канала; согласование с ИБ/комплаенсом (§7).
- **[Рост объёма ПДн]** → минимизация, шифрование в покое, маскирование в логах, журналирование доступа (AD-007), ИБ-ревью.
- **[Пиковые биллинговые окна]** → burst-профиль в NFR, приоритеты очередей, capacity plan; деградация без потери операций (RPO=0).
- **[Гонка отзыва согласия и списания]** → подтверждённое `PAID` доводится до завершения, будущие списания прекращаются; явный сценарий теста.
- **[Внешний вход: протокол НСПК по мандатам]** → `[ТРЕБУЕТ ПРОВЕРКИ]`; контракт адаптера и RFP фиксируют требования, детали закрываются вендором/документацией; до этого реализуется на моках.
- **[Расширение статусной машины усложняет модель]** → переиспользование существующего автомата вместо новой модели; fitness-тесты продолжают охранять AD-005.

## Migration Plan

Поэтапное включение за фиче-флагом per-ТСП; каждый этап обратим до следующего:

1. **Гейт-0 (человеческий):** ратификация ADR-008/AD-009, решения §7; согласование с ИБ/комплаенсом сроков и канала уведомлений; согласование расширенного контракта адаптера и критериев POC с вендором.
2. **Этап 1 (моки):** реализация агрегатов, расширения статусной машины, планировщика, уведомлений и адаптер-мока; fitness и негативные тесты; `openapi-diff` (0 breaking).
3. **Этап 2 (тестовый контур НСПК):** интеграция через вендора, сценарии POC (мандат, повтор списания, отказ, отзыв, повтор события, нагрузка).
4. **Этап 3 (pilot):** 1–2 ТСП за фиче-флагом; сверка согласий/списаний; SLO-отчёт; расширение.

Откат — в §6.

## Open Questions

Отложенные неизвестные, не меняющие спецификацию/подход:

1. Формат `openapi`-выражения для `charge` — отдельная схема или reuse `Payment` (влияет только на генерацию клиентов).
2. Нумерация вебхуков списаний: дублировать ли `charge.*` рядом с `payment.*` или только `payment.*` с `initiator` (влияет на эргономику ТСП, не на поведение).
3. Срок хранения согласий после отзыва (регуляторный минимум) — уточняется ИБ/юристами.

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки

**Позитивные (проверяемы тестом/командой):**

- AC-1: сквозной сценарий на моках `POST /v1/consents → POST /v1/subscriptions → списание → COMPLETED` проходит; платёж виден в `GET /v1/charges/{chargeId}`.
- AC-2: частичный и полный возврат по рекуррентному списанию проходят существующей сагой.
- AC-3: вебхуки `charge.completed`/`consent.revoked`/`subscription.*` доставляются с ретраями и DLQ; дедуп у ТСП по `eventId`.
- AC-4: `openapi-diff` ТСП-контракта: breaking changes = 0; старый потребитель проходит регрессионный тест без изменений.

**Негативные (обязательны, по рубрике handoff):**

- AC-5: повторный/параллельный триггер списания за один `billingPeriod` → одно списание; второе обращение к ОПКЦ/АБС отсутствует.
- AC-6: повторная нотификация ОПКЦ (`eventId`) не меняет завершённое состояние; новый `eventId` по завершённой операции даёт алерт.
- AC-7: списание по отозванному/неподтверждённому согласию отклонено (`CONSENT_NOT_ACTIVE`), АБС не вызывается.
- AC-8: зачисление из `CREATED` недостижимо (fitness AD-005).
- AC-9: недостаток средств → `FAILED` с кодом, ретраи ≤ политики, успешных списаний за период ≤ 1.
- AC-10: недоступность АБС после `PAID` → списание остаётся `PAID`, видно в отчёте незавершённых, зачисляется после восстановления (RPO=0).
- AC-11: гонка «подтверждено `PAID` + пришёл отзыв» → списание доведено, будущие прекращены.
- AC-12: недоступность канала уведомления → применена утверждённая политика, инцидент в отчёте.
- AC-13: нагрузочный тест — профиль NFR выдержан, двойных списаний 0.

**Критерий успешного отката:** фиче-флаг выключен для всех ТСП; новые согласия/подписки не создаются; открытые списания доведены до терминального состояния или видны в отчёте незавершённых; уведомления по уже начатым списаниям не потеряны; двойных списаний 0.

### 6.2 План отката

- **До боевой эксплуатации:** откат = «не включать» (фиче-флаг off); все изменения обратимы.
- **После включения:**
  1. **Stop-new:** запрет создания новых согласий/подписок и плановых списаний (фиче-флаг per-ТСП), без остановки обработки уже открытых списаний, отзывов, возвратов и уведомлений.
  2. **Rolling-откат релиза** до предыдущей версии; обработка открытых операций — существующим пайплайном.
  3. **Данные не удаляются:** согласия/списания хранятся для уведомлений, аудита и регуляторных сроков; при необходимости — перевод подписок в `SUSPENDED`.
  4. **Сверка и компенсация:** сверка с НСПК/АБС по открытым списаниям; расхождения — по runbook.
- **Сигналы-триггеры отката:** доля успешных списаний ниже порога NFR; двойное списание > 0; регуляторное замечание по уведомлениям; инцидент ИБ/ПДн; деградация базового приёма разовых платежей.
- **Владелец решения об откате:** владелец продукта/CIO совместно с ИБ (не принимается одним инженером); до боевой эксплуатации — solution-архитектор.

## 7. Решения, остающиеся человеку-архитектору

1. **Ратифицировать ADR-008 и блок `AD-009`** (статус `Proposed` → `Adopted`), включая формулировку Rule и перечень затронутых AD.
2. **Владелец расписания списаний** (D5): шлюз-планировщик («pull», рекомендовано) или ТСП-триггер («push») — влияет на контракт, NFR и эксплуатацию.
3. **Канал и срок уведомления плательщику** (D6): банк-эквайер, банк плательщика через ОПКЦ или ТСП; точный срок «T−N» — регуляторная трактовка 161-ФЗ/правил ОПКЦ.
4. **Политика при недоступности канала уведомления:** задержать списание или выполнить с пост-уведомлением (по умолчанию дизайн — задержать).
5. **Политика ретраев при недостатке средств:** число попыток и окно (влияет на клиентский опыт и обработку жалоб).
6. **Scope первой волны:** только подписки с фиксированной суммой/периодом или сразу «плавающие» суммы/лимиты (usage-based) — влияет на модель подписки и контракт.
7. **Регуляторные внешние входы:** подтвердить регламент НСПК по мандатам/списаниям/уведомлениям и снять метки `[ТРЕБУЕТ ПРОВЕРКИ]`; подтвердить Положение ЦБ по защите информации (владелец — ИБ).
8. **Претензионный процесс/диспуты по рекуррентным списаниям** — остаются `Deferred`; подтвердить, что возврата через сагу достаточно для первой волны.

Эти решения не разблокируются «сами»: без пункта 1 и 7 не начинается реализация транспорта; без 2–5 не финализируются контракт и NFR.
