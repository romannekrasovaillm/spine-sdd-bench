# Влияние на принятую архитектуру

Оценка влияния изменения «Подписки СБП» на принятое решение (AD-001…AD-008, ADR-001…007). Формат: затронутый инвариант → характер влияния → что именно меняется.

## 1. Влияние на инварианты spine

| Инвариант | Влияние | Что меняется |
|---|---|---|
| **AD-001** Изоляция платёжного контура | Не затронут | Новые компоненты (реестр согласий, планировщик) остаются в контуре шлюза; обращения к АБС/ОПКЦ — по-прежнему только через адаптеры |
| **AD-002** Единый источник истины (статусная машина) | **Затронут (расширение)** | Область действия расширена на согласие/подписку и рекуррентное списание: каждый переход согласия и списания — атомарно «состояние + outbox + аудит». Формулировка блока не изменяется |
| **AD-003** Идемпотентность финансовых операций | **Затронут (расширение)** | Новый ключ идемпотентности `(subscriptionId, billingPeriod)` для рекуррентного списания; дедупликация событий `subscription.*`/`debit.*` по `eventId` |
| **AD-004** Единственный адаптер ОПКЦ | **Затронут (расширение)** | Контракт адаптера получает новые методы/события подписок (v0.2); принцип «протокол НСПК знает только адаптер» сохраняется |
| **AD-005** Зачисление из подтверждённого статуса | **Не изменяется, распространяется** | Рекуррентное списание зачисляется только из `PAID`; новых исключений нет |
| **AD-006** Trust-зоны и сегментация | Не затронут по существу | Новые компоненты — в платёжном контуре; зоны доверия не меняются. Требуется подтверждение при размещении планировщика/хранилища согласий |
| **AD-007** НПС/КИИ/ПДн | **Затронут (расширение)** | Новый класс ПДн (данные согласия плательщика) → минимизация, шифрование, аудит жизненного цикла согласия; новая граница безопасности требует согласования ИБ/юристов |
| **AD-008** Гибрид (контрактная изоляция транспорта) | Не затронут | Ядро остаётся независимым от транспорта; поддержка подписок инкапсулируется в вендорском адаптере (расширение RFP) |
| **AD-009 (новый)** Согласие — источник истины для рекуррентного списания | Добавлен | Списание только при `ACTIVE` и в пределах лимитов; отзыв транзакционно запрещает новые списания |
| **AD-010 (новый)** Один период — одно списание | Добавлен | Идемпотентность по `(subscriptionId, billingPeriod)`; `reference = debitId` на НСПК |

## 2. Изменения компонентов и данных

- **Новые компоненты** (в контуре шлюза): реестр согласий/подписок; планировщик рекуррентных списаний (HA).
- **Новые данные**: согласие (идентификатор ОПКЦ, плательщик-минимум, лимиты, срок, статус, история); подписка (ТСП ↔ согласие ↔ условия); попытка списания (ключ периода, статус, `absDocId`).
- **Переиспользуется без изменений**: статусная машина платежа, outbox, нотификатор, сверка, интеграция с АБС, адаптер ОПКЦ (расширяется аддитивно).
- **АБС**: изменения не требуются — рекуррентное списание оформляется тем же идемпотентным документом по `paymentId`/`debitId`.

## 3. Контракты

- **API ТСП** (`openapi/tsp-api.yaml`, v0.2): добавлены `/v1/subscriptions…` (аддитивно; `contract_diff` 0.1.0→0.2.0 — breaking: 0). Существующие потребители не затронуты.
- **Контракт адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`, v0.2): +5 методов, +4 события; идемпотентность рекуррентного списания — обязательный критерий RFP.
- **RFP вендора**: расширен (scope, G3, POC P9–P11).

## 5. Что НЕ меняется (проверка границ)

- Разовый приём C2B, возвраты, статусы платежа, их контракты и семантика — без изменений.
- Trust-зоны, СКЗИ/ГОСТ, интеграция с АБС, антифрод/AML — без изменения подхода (только рост объёма и новый аудит согласий).
- Родительский (initiative) spine — не переопределяется локально; при выделении подписок в отдельный домен изменение эскалируется наверх (см. `DECISION.md`, вопрос владения доменом).
