# ADR-010. Эволюция контрактов для подписок: аддитивные расширения API ТСП и внутреннего контракта адаптера ОПКЦ

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + ИБ (для аутентификации ТСП)
- Author-model: qwen-code (agent)
- Related: ADR-003, ADR-007, ADR-008, ADR-009, AD-004, AD-008

## Context

Подписки требуют новых операций у двух границ: **API ТСП** (создание/опрос/отмена подписки, инициация списания) и **внутренний контракт адаптера ОПКЦ** (регистрация согласия, рекуррентное списание, отзыв) — последний является основой RFP вендора (AD-008). Оба контракта сейчас в статусе draft v0.1. Уже существуют потребители разового C2B-приёма (регистрация QR, статус, возврат), и их нельзя ломать: изменение финансового контракта без версии — регуляторный и операционный риск.

Силы: ADR-003 (единственный адаптер, граница транспорта), AD-008 (ядро контрактно-независимо от транспорта), AD-003 (идемпотентность мутирующих операций), контрактный гейт Spine (`openapi_lint`, `contract_diff`), период поддержки версий.

## Decision

1. **Расширять оба контракта аддитивно**: только добавление новых методов, полей и событий; существующие пути, поля, типы и семантика не удаляются и не переименовываются.
2. **API ТСП остаётся в `/v1`**: `info.version` повышается 0.1.0 → 0.2.0 (minor; контракт ещё draft, стабилизация — на A1). Новые POST-методы обязаны принимать `Idempotency-Key`; ошибки — RFC 9457 `application/problem+json` (единый стиль с существующим контрактом).
3. **Новые эндпоинты** (детали — `openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`): `POST /v1/subscriptions`, `GET /v1/subscriptions/{subscriptionId}`, `POST /v1/subscriptions/{subscriptionId}/cancel`, `POST /v1/subscriptions/{subscriptionId}/debits`, `GET /v1/subscriptions/{subscriptionId}/debits/{debitId}`.
4. **Новые события вебхуков** добавляются в перечень (без изменения формата существующих): `subscription.activated`, `subscription.revoked`, `debit.completed`, `debit.failed`.
5. **Контракт адаптера ОПКЦ расширяется** новыми методами (`registerSubscription`, `getSubscriptionStatus`, `cancelSubscription`, `createDebit`, `getDebitStatus`) и событиями (`subscription.activated`, `subscription.revoked`, `debit.paid`, `debit.rejected`) с обязательной идемпотентностью по `reference`; изменения вносятся в `docs/contracts/opkc-adapter.md` и в требования RFP.
6. **Ломающие изменения — только через новую major-версию**: API ТСП — `/v2` с периодом поддержки обеих версий ≥ 6 мес.; контракт адаптера — major-версия контракта. Подтверждение неразрушающего характера: `openapi_lint` PASS и `contract_diff old=0.1.0 new=0.2.0` без breaking changes.

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| **A. Сразу поднять API до `/v2`** | Формальная чистота версии | Дублирование версий без выгоды (контракт ещё draft, потребителей v2 нет), лишняя поддержка | Отвергнут: преждевременно и дороже |
| **B. Отдельный сервис/API для подписок** | Изоляция | Фрагментация домена ТСП, вторая аутентификация/онбординг, разрыв модели с платежами | Отвергнут |
| **C. Изменить существующие схемы `Payment`/`PaymentRequest` под подписки** | Нет новых путей | Ломает существующих потребителей | Отвергнут: нарушает совместимость |
| **D. Аддитивные расширения обоих контрактов в текущих версиях (выбран)** | Совместимость; единый стиль; минимальная цена; подтверждаемо гейтом | Некоторый рост «ширины» API; нужна дисциплина версионирования | Выбран |

## Consequences

### Positive

- Существующие потребители (разовый приём) не затрагиваются — нулевой риск регресса контракта.
- Единый стиль идемпотентности и ошибок для старых и новых методов.
- Расширение RFP прозрачно: вендор получает новые методы/события как явные требования с критерием идемпотентности.
- Неразрушающий характер проверяется механически (`contract_diff`), а не «на глаз».

### Negative

- Рост числа методов и событий — нужна дисциплина документации и тестов контракта.
- Контракт адаптера расширяется до подтверждения поддержки подписок вендором — риск, что вендор не реализует часть (митигация: обязательный критерий RFP + POC, ADR-007).
- Часть семантики (лимиты, сроки, поля согласия) остаётся `[ТРЕБУЕТ ПРОВЕРКИ]` до получения протокола НСПК — контракт draft, возможны уточнения без смены major.

## Reversibility

**reversible.** Новые методы и события можно исключить из публикации, не задевая существующих потребителей (они продолжат работать на прежнем подмножестве контракта). Смена схемы версионирования (например, `/v2`) возможна позже, при появлении реальных ломающих изменений.

**Condition/expiry (пересмотр при):** получении протокола НСПК с иной моделью согласия/списания; необходимости ломающего изменения; выделении подписок в отдельный API.
