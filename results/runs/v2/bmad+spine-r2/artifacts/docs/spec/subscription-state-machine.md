# Статусная машина подписки и рекуррентного списания — спецификация

- Status: Draft (для ревью на гейте A1)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, ADR-010, AD-002, AD-003, AD-005, AD-009, AD-010

Расширение к `docs/spec/state-machine.md` (разовый платёж). Рекуррентное списание — платёжный переход, переиспользующий канонические состояния платежа; подписка/согласие — отдельный автомат (ADR-008).

## Проблема

Подписки СБП позволяют списывать средства **без действия плательщика** по ранее выданному согласию. Это меняет модель авторизации: поручение существует до и независимо от конкретного списания. Без явного автомата состояний согласия невозможно доказать регулятору и обеспечить механически, что (а) списание возможно только по действующему согласию, (б) отзыв согласия немедленно останавливает будущие списания, (в) за один расчётный период создаётся не более одного списания. Спецификация фиксирует состояния, переходы и запреты, из которых выводятся fitness-проверки (AD-009, AD-010).

## 1. Состояния согласия/подписки

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `PENDING_CONSENT` | Регистрация согласия в ОПКЦ инициирована, плательщик ещё не подтвердил | да |
| `ACTIVE` | Согласие подтверждено НСПК; списания разрешены в пределах лимитов/срока | да |
| `SUSPENDED` | Приостановлена (по решению ТСП/банка/плательщика); новые списания запрещены, возобновление возможно | да |
| `REVOKED` | Согласие отозвано плательщиком/СБП; терминальное, новые списания запрещены навсегда | да |
| `EXPIRED` | Истёк срок (`endAt`) или исчерпан `maxDebits`; терминальное | да |

Технические подсостояния (наружу не выставляются): `CONSENT_RETRY` (ожидание подтверждения/повтор запроса), `DEBITS_DRAINING` (в обработке есть подтверждённые списания при отзыве).

## 2. Таблица переходов подписки

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| S1 | — | `PENDING_CONSENT` | `POST /v1/subscriptions` | ТСП активен, условия валидны | запись подписки + outbox `registerSubscription` |
| S2 | `PENDING_CONSENT` | `ACTIVE` | событие `subscription.activated` (или сверка) | `consentId` непустой | сохранить `consentId`, `nextDebitAt`, outbox-нотификация |
| S3 | `PENDING_CONSENT` | `REVOKED` | плательщик не подтвердил / отказ ОПКЦ | — | терминал, нотификация |
| S4 | `ACTIVE` | `SUSPENDED` | запрос ТСП/банка | — | запрет новых списаний, нотификация |
| S5 | `SUSPENDED` | `ACTIVE` | возобновление | согласие не отозвано/не истекло | разрешение списаний |
| S6 | `ACTIVE` | `REVOKED` | событие `subscription.revoked` (плательщик/СБП) | — | **в одной транзакции**: запрет новых списаний + событие + аудит (AD-009) |
| S7 | `SUSPENDED` | `REVOKED` | событие `subscription.revoked` | — | как S6 |
| S8 | `ACTIVE` | `EXPIRED` | `endAt` или `maxDebits` исчерпан | — | терминал, нотификация |
| S9 | `ACTIVE` | `REVOKED` | `POST …/cancel` (ТСП) | — | как S6 (компенсаций нет; уже подтверждённые списания — возвратом) |

## 3. Состояния попытки списания (`Debit`)

Попытка списания — платёж типа «рекуррентный»: канонические состояния платежа (`CREATED`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`) плюс планировочные (`SCHEDULED`, `SKIPPED`). Терминальные: `COMPLETED`, `FAILED`, `SKIPPED`.

| Состояние | Смысл |
|---|---|
| `SCHEDULED` | Плановое списание создано планировщиком, инициация ОПКЦ не выполнена |
| `CREATED` | Запрос списания в ОПКЦ зарегистрирован (ретраи возможны) |
| `PAID` | Подтверждено НСПК (нотификация/сверка) — только отсюда разрешено зачисление (AD-005) |
| `CREDITED` | Зачислено в АБС (`absDocId`) |
| `COMPLETED` | Доведено до ТСП (вебхук доставлен/в очереди) |
| `FAILED` | Отклонено НСПК или исчерпаны повторы (период не оплачен) |
| `SKIPPED` | Пропущено по политике (согласие неактивно/истекло/отозвано, лимит) — без обращения к НСПК |

## 4. Таблица переходов списания

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| D1 | — | `SCHEDULED` | наступление планового времени | согласие `ACTIVE`, период не обработан | запись попытки с ключом `(subscriptionId, billingPeriod)` |
| D2 | `SCHEDULED` | `CREATED` | инициация в ОПКЦ | лимит/срок соблюдены | outbox `createDebit(reference=debitId)` |
| D3 | `SCHEDULED` | `SKIPPED` | инициация отклонена политикой | согласие не `ACTIVE` / лимит / срок | терминал, нотификация |
| D4 | `CREATED` | `PAID` | `debit.paid` (или сверка) | сумма и период совпадают | outbox-зачисление в АБС |
| D5 | `CREATED` | `FAILED` | `debit.rejected` (исчерпаны повторы) | отказ не транзиентный | `errorCode`, вебхук `debit.failed` |
| D6 | `PAID` | `CREDITED` | подтверждение АБС | идемпотентно по `debitId` | `absDocId`, outbox-доставка |
| D7 | `PAID` | (остаётся `PAID`) | АБС недоступна | — | подсостояние ожидания, повторы, сверка |
| D8 | `CREDITED` | `COMPLETED` | вебхук доставлен/в очереди | — | вебхук `debit.completed` |
| D9 | `COMPLETED` | `REFUNDED`-эффект | возврат (сага, ADR-005) | платёж был зачислен | возврат по `debitId` (ADR-005) |

## 5. Запрещённые переходы (инварианты)

- **Списание невозможно при отсутствии согласия или состоянии ≠ `ACTIVE`** (AD-009). Из `PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`EXPIRED` — недостижимо; проверяется fitness-тестом.
- **Зачисление — только из `PAID`** (AD-005), включая рекуррентные списания.
- **После `REVOKED` новое списание невозможно** (AD-009); допускается завершение уже подтверждённых (`DEBITS_DRAINING`), автоматический откат не выполняется.
- **Один `(subscriptionId, billingPeriod)` — одна попытка** (AD-010): повторная обработка периода идемпотентна, второе списание не создаётся.
- **Сумма списания ≤ `amountLimit` согласия**; период и число списаний — в пределах условий.
- `REVOKED`/`EXPIRED` — терминальные состояния согласия.

## 6. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ | Поведение при повторе |
|---|---|---|
| `POST /v1/subscriptions` | `Idempotency-Key` | возврат той же подписки |
| `POST …/debits` | `Idempotency-Key` + `(subscriptionId, billingPeriod)` | возврат той же попытки, второе списание не создаётся |
| Событие `subscription.activated`/`revoked` | `eventId` | повтор игнорируется; новый `eventId` по завершённому переходу — алерт |
| Событие `debit.paid`/`rejected` | `eventId` (+ `reference`) | повтор не меняет завершённое состояние |
| Подтверждение АБС | `debitId` | повтор не создаёт вторую проводку |

## Критерии приёмки

1. Создание списания при согласии в состоянии ≠ `ACTIVE` — отклонено (`CONSENT_NOT_ACTIVE`), списание не создано (тест недостижимости, AD-009).
2. Повторная обработка периода `(subscriptionId, billingPeriod)` → одна попытка, одна проводка (AD-010).
3. После `subscription.revoked` новые списания не создаются; число списаний с временем после отзыва — 0.
4. Зачисление рекуррентного списания невозможно из `SCHEDULED`/`CREATED` (наследование AD-005).
5. Превышение `amountLimit`/срока/`maxDebits` — отклонение без обращения к НСПК.
6. Дубли нотификаций НСПК и подтверждений АБС не меняют завершённое состояние (AD-003).
7. Все переходы согласия и списания отражены в аудит-логе (AD-007).

## Риски

- Двойное списание при ошибке распределённого выбора ответственного планировщика — митигируется ключом `(subscriptionId, billingPeriod)` и тестом повтора.
- Рассинхрон статуса согласия между шлюзом и НСПК (позднее/потерянное событие отзыва) — митигируется сверкой и опросом `getSubscriptionStatus`.
- Пиковые массовые списания деградируют разовый приём — митигируется управлением темпом и приоритетами (NFR §7).
- Неполнота протокола НСПК по подпискам (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`) — митигируется контрактной изоляцией адаптера (AD-008) и обновлением ADR по факту.
