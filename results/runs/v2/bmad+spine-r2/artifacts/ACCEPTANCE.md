# Критерии приёмки — Подписки СБП

Критерии проверяемы тестом/командой и выведены из требований дельты (`changes/subscriptions-c2b/DELTA.md`) и новых инвариантов (AD-009, AD-010). Каждый — с указанием метода проверки. Формулировки — EARS (When/If/While…the system shall…).

## Функциональные (позитивные)

- **AC-1.** When ТСП создаёт подписку, the шлюз shall зарегистрировать согласие через адаптер ОПКЦ и вернуть `subscriptionId`; состояние — `PENDING_CONSENT`, списания невозможны. *(Тест: POST /v1/subscriptions; проверка state machine.)*
- **AC-2.** When приходит подтверждение согласия (`subscription.activated`), the шлюз shall перевести подписку в `ACTIVE` и сохранить `consentId`. *(Тест: событие→состояние; сверка.)*
- **AC-3.** When согласие `ACTIVE` и сумма в пределах лимита, the шлюз shall создать попытку списания и провести её по циклу `CREATED→PAID→CREDITED→COMPLETED`. *(Тест: сквозной сценарий подписки.)*
- **AC-4.** When приходит подтверждение НСПК по рекуррентному списанию, the шлюз shall зачислить средства только из `PAID` (наследование AD-005). *(Тест: недостижимость зачисления из `CREATED`/`SCHEDULED`.)*
- **AC-5.** When ТСП отменяет подписку, the шлюз shall прекратить будущие списания и вернуть состояние `REVOKED`. *(Тест: POST …/cancel.)*

## Негативные и граничные (обязательны)

- **AC-6 (нет согласия → нет списания).** If состояние согласия ≠ `ACTIVE` (нет/`PENDING_CONSENT`/`SUSPENDED`/`REVOKED`/`EXPIRED`), then the шлюз shall отклонить списание (`CONSENT_NOT_ACTIVE`) и **не** обращаться к НСПК. *(Тест недостижимости, AD-009; счётчик вызовов адаптера = 0.)*
- **AC-7 (дубль периода).** When повторно обрабатывается `(subscriptionId, billingPeriod)`, the шлюз shall вернуть ту же попытку и не создать второе списание/проводку. *(Тест повтора; число списаний за период = 1.)*
- **AC-8 (дубль нотификации).** When повторно доставляется событие с тем же `eventId`, the шлюз shall не изменить завершённое состояние. *(Тест дубля.)*
- **AC-9 (отзыв во время обработки).** When согласие отозвано, the шлюз shall прекратить новые списания; подтверждённые до отзыва — не откатываются автоматически. *(Тест: число списаний с временем после отзыва = 0.)*
- **AC-10 (превышение лимита/срока/числа).** If сумма/период/срок/`maxDebits` выходят за условия, then the шлюз shall отклонить без обращения к НСПК. *(Тест-кейсы границ.)*
- **AC-11 (отказ зависимостей).** While АБС недоступна, the шлюз shall не терять плановое списание (остаётся `PAID`, видно в отчёте незавершённых; сверка компенсирует). *(Chaos-тест.)*
- **AC-12 (гонка повторов).** When две попытки за один период приходят конкурентно, the шлюз shall создать ровно одну (idempotency + unique-ключ). *(Тест гонки.)*

## Контрактные (неразрушающее расширение)

- **AC-13.** `openapi_lint` по `openapi/tsp-api.yaml` — PASS; все новые POST принимают `Idempotency-Key`; ошибки — RFC 9457.
- **AC-14.** `contract_diff` версий 0.1.0 → 0.2.0 — **breaking: 0** (только добавления). Существующие методы §3.1–3.5 не изменены. *(Команда: contract_diff; результат: 0 breaking.)*

## NFR (измеримо, `docs/nfr.md` §7)

- **AC-15.** Своевременность ≥ 99,5 % в окне ±30 мин; p95 задержки инициации ≤ 5 мин.
- **AC-16.** Применение отзыва: 100 % ≤ 5 мин (p95 ≤ 1 мин).
- **AC-17.** Двойных списаний за период — 0; списаний после отзыва — 0; расхождений сверки — 0.
- **AC-18.** Массовые списания: sustained 200 TPS / пик 500 TPS с управлением темпом; разовый приём не деградирует ниже SLO.

## Соответствие и аудит

- **AC-19.** 100 % переходов согласия и списания — в неизменяемом аудит-логе (AD-007).
- **AC-20.** Критерий успешного отката: фиче-флаг `stop-new` останавливает новые подписки/списания; разовый приём и подтверждённые операции продолжают работу; состояние восстанавливается без изменения кода (см. `ROLLBACK.md`).
