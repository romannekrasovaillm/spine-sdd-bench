# Walking skeleton — Подписки СБП

Цель — **доказать архитектуру сквозным сценарием на моках**, а не полноту продукта (как и для базового решения, `.arch-handoff/TASK.md`). Реальный протокол НСПК **не реализуется** (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`); транспорт — мок-адаптер.

## Сквозной путь (обязательный минимум)

```
ТСП → API шлюза → реестр согласий/подписок → планировщик списаний
      → мок-адаптер ОПКЦ (registerSubscription, createDebit, события)
      → статусная машина + outbox → мок-адаптер АБС (идемпотентное зачисление по debitId)
      → нотификатор ТСП (вебхуки, ретраи, DLQ)
```

## Что входит в skeleton

1. `POST /v1/subscriptions` — создание подписки (`PENDING_CONSENT`), идемпотентность по `Idempotency-Key`.
2. Мок-ОПКЦ: событие `subscription.activated` → подписка `ACTIVE`, сохранён `consentId`.
3. Планировщик: формирование плановой попытки с ключом `(subscriptionId, billingPeriod)`.
4. `POST /v1/subscriptions/{id}/debits` (или плановая инициация) → мок-ОПКЦ `createDebit` → событие `debit.paid`.
5. Статусная машина: `CREATED → PAID → CREDITED → COMPLETED`; зачисление мок-АБС идемпотентно по `debitId`.
6. Нотификатор: вебхуки `debit.completed`, `subscription.*`.
7. Отзыв: событие `subscription.revoked` → запрет новых списаний; `POST …/cancel` (ТСП).

## Обязательно доказать (негативные сценарии)

- Нет согласия / не `ACTIVE` → списание отклонено, **0 обращений** к адаптеру ОПКЦ (AD-009).
- Повтор за тот же `billingPeriod` → **одно** списание и **одна** проводка (AD-010).
- Дубль события `debit.paid` (тот же `eventId`) → состояние не меняется.
- Отзыв во время обработки → новых списаний нет; подтверждённые не откатываются.
- АБС недоступна → плановое списание не теряется (остаётся `PAID`, видно в отчёте).

## Границы skeleton

- Протокол НСПК, СКЗИ/ГОСТ, реальный транспорт — вне skeleton (моки; вендорский адаптер, ADR-007/ADR-008).
- Биллинг ТСП, тарифы, комиссии — вне skeleton.
- Полнота UI/ЛК, отчётность ЦБ — вне skeleton (последующие этапы).

## Приоритет и критерий готовности skeleton

Приоритет — сквозной сценарий подписки с негативными проверками; критерий — сценарии выше проходят на моках, а критерии `ACCEPTANCE.md` AC-1…AC-12 воспроизводимы автоматическими тестами (см. `VALIDATION.md`).
