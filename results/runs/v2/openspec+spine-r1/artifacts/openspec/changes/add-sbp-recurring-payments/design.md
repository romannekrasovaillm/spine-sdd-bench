# Design

## Context

Принятое решение (ADR-001..007, `ARCHITECTURE-SPINE.md` AD-001..AD-008) обслуживает **разовый** C2B-приём: платёж `CREATED → QR_ISSUED → PAID → CREDITED → COMPLETED`, инициатива у плательщика, зачисление только из `PAID`. Публичный контракт — `openapi/tsp-api.yaml` v0.1.0 (`/v1/payments`, `/v1/payments/{paymentId}`); мерчант-контракт v0.1 в `docs/contracts/tsp-api.md`.

Ограничения, формирующие подход:

- маршрут изменения — **Critical** (10/15, см. `proposal.md`); родительский spine — read-only, локальное переопределение запрещено;
- протокол подписок НСПК — **внешний вход** `[ТРЕБУЕТ ПРОВЕРКИ]`; транспорт реализуется только после контракта и документации (AD-008);
- транспорт — за границей внутреннего контракта адаптера ОПКЦ (ADR-003/ADR-007): ядро не знает протокола;
- изменение затрагивает Accepted-решение ADR-007 → область транспорта подписок выносится отдельным ADR-009 на A3.

Мотивация и объём — в `proposal.md`; внешнее поведение — в `specs/sbp-recurring-payments/spec.md`.

## Goals / Non-Goals

**Goals:**

- Рекуррентные списания по согласию плательщика, зарегистрированному в СБП, без его участия в каждом списании.
- Ноль несанкционированных списаний (без действующего согласия или сверх лимитов) и ноль двойных списаний.
- Корректная семантика отзыва согласия, включая гонку «списание в полёте / отзыв».
- Обратно совместимое расширение контракта ТСП и переиспользование существующих контуров (статусная машина, outbox, АБС-зачисление, сага возвратов, сверка).
- Измеримые NFR на новый класс операций.

**Non-Goals:**

- Карточный рекуррент, C2C, выплаты B2C/B2B, диспуты — вне scope.
- Юридическая модель взыскания задолженности (dunning/collection) — только технические повторы списаний в рамках согласия.
- Личный кабинет/UI плательщика — согласие подтверждает и отзывает банк плательщика (СБП), не наш шлюз.
- Изменение существующих инвариантов AD-001..AD-008 и ломающие изменения контракта.

## Decisions

| # | Решение | Обоснование / альтернативы | ADR |
|---|---|---|---|
| D-1 | Согласие — самостоятельная сущность; источник истины — реестр СБП, в шлюзе зеркало | Единственный межбанковский вариант; альтернативы B–E отвергнуты (см. ADR-008) | ADR-008 |
| D-2 | Списание — платёж существующей статусной машины с `consentId` (QR-шаг заменён инициацией списания) | Переиспользует AD-002/AD-005/сагу возвратов; альтернатива «свой конечный автомат для списаний» отвергнута как дублирование финансовой логики | ADR-008 |
| D-3 | Предусловие списания (ACTIVE + лимиты) проверяется в одной транзакции с созданием попытки | Исключает «списание из воздуха»; новый инвариант AD-009 | ADR-008 |
| D-4 | Отзыв согласия приоритетен; неподтверждённые попытки блокируются, подтверждённые компенсируются возвратом | Единственная семантика, совместимая с «деньги уже ушли»; инвариант AD-010 | ADR-008 |
| D-5 | Детерминированный ключ попытки `(consentId, billingPeriod, attemptSeq)` → `reference` адаптера и внешний ключ АБС | Делает ретраи/повторы планировщика безопасными; инвариант AD-011 | ADR-008 |
| D-6 | Планировщик списаний — в ядре, по outbox/очереди; ретраи с экспоненциальной задержкой и джиттером | Сохраняет атомарность «состояние + outbox» (AD-002); альтернатива «внешний планировщик дёргает API» отвергнута (обход инвариантов) | ADR-008 |
| D-7 | Транспорт подписок — область существующего вендорского адаптера (рекомендация) либо отдельный адаптер | Затрагивает Accepted ADR-007 → отдельное решение A3 | ADR-009 |
| D-8 | Сглаживание пиков границ периода очередью и per-ТСП честностью | Пиковый профиль подписок взрывной; защита от «шумного соседа» | ADR-008 |

### Impact on the accepted architecture (spine)

| Инвариант | Влияние | Вердикт |
|---|---|---|
| AD-001 (изоляция контура) | Новые компоненты (согласия, планировщик) — внутри платёжного контура; к АБС/ОПКЦ только через адаптеры | **не изменяется**, распространяется на новые компоненты |
| AD-002 (единый источник истины, атомарные переходы) | Появляется вторая сущность с жизненным циклом; правило «смена состояния + outbox в одной транзакции» распространяется на согласие | **расширяется** (без изменения текста блока) |
| AD-003 (идемпотентность) | Ключи идемпотентности распространяются на попытки списания и нотификации о согласиях | **расширяется** |
| AD-004 (единственный адаптер ОПКЦ) | Новые операции подписок обязаны жить в единственном адаптере; кто именно — решает ADR-009 | **не изменяется**; область поставки — ADR-009 |
| AD-005 (зачисление только из PAID) | Сохраняется полностью; добавляется предусловие списания (AD-009) | **не изменяется** |
| AD-006 (trust-зоны) | Новая зона не появляется; согласие обрабатывается в платёжном контуре; вход плательщика — в его банке | **не изменяется** |
| AD-007 (НПС/КИИ/ПДн) | Согласие — правовое основание; аудит и минимизация ПДн распространяются на новый класс | **расширяется** |
| AD-008 (гибрид, ADOPTED) | Ядро остаётся контрактно-независимым; ограничение «транспорт только после контракта и документации НСПК» действует и для подписок | **не изменяется** |
| — | Новые инварианты | **добавляются AD-009, AD-010, AD-011** (Proposed, ADR-008) |

### Contract delta (`openapi/tsp-api.yaml`)

Аддитивное расширение, версия **0.1.0 → 0.2.0**, путь API остаётся `/v1`:

- новые пути: `POST|GET /v1/consents`, `GET /v1/consents/{consentId}`, `POST /v1/consents/{consentId}/cancel`, `GET|POST /v1/consents/{consentId}/charges`;
- новые схемы: `Consent`, `ConsentRequest`, `ConsentLimits`, `ConsentStatus`, `ChargeAttempt`, `ChargeRequest`, `Problem`;
- у `Payment` добавлено **опциональное** поле `consentId`;
- новые события вебхуков (`consent.activated/revoked/expired`, `charge.completed/failed`) и коды ошибок (`CONSENT_*`, `CHARGE_ALREADY_EXISTS`) — описаны в спеке;
- **не изменяются**: существующие пути, обязательные поля, значения `Payment.status`, коды ответов. Ломающих изменений нет → миграция потребителей не требуется.

### NFR budgets (measurable)

| Метрика | Цель | Метод проверки | Почему так |
|---|---|---|---|
| Старт планового списания от срока | p95 ≤ 5 мин | метрика планировщика, нагрузочный тест | границы периода группируют списания |
| Лаг отзыва → блокировка новых попыток | p95 ≤ 60 с | тест отзыва + мониторинг | отзыв — юридически значимое действие |
| Обработка пика границ периода | sustained 500 TPS, burst 2000 TPS / 5 мин | нагрузочный тест | профиль подписок взрывной (1-е число) |
| Несанкционированные списания | 0 | негативные тесты (AD-009) | регуляторный риск |
| Двойные списания/зачисления | 0 | тест повторной доставки (AD-011) | финансовый инцидент |
| RPO / RTO по согласиям и попыткам | RPO=0, RTO ≤ 1 ч | chaos-тест, сверка | согласие — невосстановимое внешнее состояние |
| Доступность исполнения списаний | ≥ 99,95 % | SLO-отчёт | наследует NFR шлюза |
| Сверка согласий/списаний с НСПК | ежедневно, расхождений 0 | reconciliation-отчёт | «у НСПК есть — у нас нет» недопустимо |
| Аудит переходов согласия и списания | 100 % | аудит/SIEM | AD-007 |
| Частичные/полные возвраты по списаниям | существующая сага | тесты саги | переиспользование ADR-005 |

Точные лимиты/периоды/сроки уведомлений — из регламентов НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` (могут быть строже).

### Acceptance criteria (A4)

Позитивные и негативные, каждая — проверяема тестом/командой:

1. Согласие `PENDING_PAYER → ACTIVE` по подтверждению; `REJECTED` по отказу — тест на моке ОПКЦ.
2. Списание при `ACTIVE` и в пределах лимитов — исполняется; при `REVOKED`/`EXPIRED`/`SUSPENDED`/`PENDING_PAYER` — отказ без вызовов ОПКЦ/АБС.
3. Превышение лимита (на операцию / период / суммарный) — отказ `CONSENT_LIMIT_EXCEEDED`, списания нет.
4. Гонка «попытка в полёте / отзыв»: до подтверждения ОПКЦ — блокировка; после подтверждения — зачисление + компенсирующий возврат.
5. Повтор планировщика и повторная нотификация ОПКЦ по одной попытке → ровно одно списание и одно зачисление.
6. Пик 2000 TPS / 5 мин → p95 старта ≤ 5 мин, потерь нет.
7. Отзыв → новые попытки блокируются ≤ 60 с (p95).
8. Существующий потребитель `/v1/payments` не затронут; `arch-be contract-diff` 0.1.0→0.2.0 — без ломающих.
9. Аудит: 100 % переходов согласия и списаний в неизменяемом логе; ПДн маскированы.
10. Сверка с НСПК: расхождений по завершённым операциям — 0.
11. Fitness-проверки AD-009..AD-011 зелёные (`arch-be gate`).

## Risks / Trade-offs

- [Протокол подписок НСПК неизвестен] → contract-first: не начинать транспорт до документации; помечать протокольные поля `[ТРЕБУЕТ ПРОВЕРКИ]`; пилот на тестовом контуре.
- [Гонка «списание в полёте / отзыв»] → явная семантика AD-010, компенсация возвратом, выделенный негативный тест и runbook.
- [Взрывной пик границ периода] → очередь-сглаживание, per-ТСП честность, запас мощности, прогрев; иначе деградация всех ТСП одновременно.
- [Согласие — правовое основание; ПДн] → минимизация, шифрование, аудит, юридическое ревью семантики отзыва (A3).
- [Расширение scope вендора/сроки] → ADR-009 (A3) с явным fallback на отдельный адаптер; не делать «тихий» обход.
- [Откат дорог потому, что согласия живут во внешнем реестре] → costly-обратимость, фиче-флаг + обязательство honor/revoke существующих согласий.
- [Повторы списаний давят на плательщика] → лимиты и окно повторов — политика бизнеса/юристов (A3), а не дефолт разработчика.
- [Дрейф зеркала согласия от реестра НСПК] → ежедневная сверка + дозапрос статуса, как в ADR-004.

## Migration Plan

1. **A3**: ратификация новых спайн-блоков AD-009..AD-011 и ADR-008; решение по ADR-009 (область транспорта).
2. **Contract-first**: получение документации НСПК по подпискам; расширение RFP/контракта вендора; финализация `docs/contracts/opkc-adapter.md`.
3. **Walking skeleton** на моках: согласие → списание → зачисление → отзыв → компенсация (сквозной сценарий, включая гонку).
4. **Пилот** с 1–2 ТСП под фиче-флагом; расширение по мере зелёных NFR/сверки.
5. **Данные**: миграция не требуется — сущности новые; контракт обратно совместим, потребители не мигрируют.

### Rollback

- **До боевой эксплуатации**: откат = не включать фиче-флаг; все работы обратимы.
- **После включения**: (1) остановить регистрацию новых согласий; (2) продолжать обслуживание/исполнение существующих согласий либо согласованно отзывать их с НСПК — «молча бросить» выданные согласия нельзя; (3) данные не удаляются (RPO=0), `ARCHITECTURE-SPINE.md` и ADR не откатываются — при отмене решения оформляется `Superseded by`.
- **Сигналы отката (триггеры)**: несанкционированное списание; двойное списание; отзыв не заблокировал попытку; несоответствие протоколу НСПК на испытаниях; расхождение сверки, не устранимое по runbook.
- **Владелец решения об откате**: архитектор + владелец продукта + ИБ (4-eyes для операций с согласиями).

## Open Questions

- Период хранения согласий и аудита (юридическое требование) — уточнить у ИБ/юристов; не влияет на архитектуру, влияет на retention-конфигурацию.
- Нужен ли ТСП внеочередной (`off-cycle`) запуск списания в первой волне — влияет только на включение уже описанного эндпоинта.
- Формат передачи согласия плательщику (`consentUrl`/диплинк/QR) — продукт + протокол НСПК.
- Уровни лимитов по умолчанию для сегментов ТСП (кино/ЖКХ/связь) — бизнес; архитектуру не меняют.

## Decisions reserved for the human architect (A3)

1. **ADR-009 — область транспорта подписок**: расширить существующий вендорский адаптер (рекомендация) или отдельный адаптер/вендор. Затрагивает Accepted ADR-007, RFP и сроки.
2. **Ратификация AD-009, AD-010, AD-011** и ADR-008 (перевод Proposed → Accepted).
3. **Политика повторов (dunning)**: число и окно попыток, реакция на «недостаточно средств», уведомления плательщику — бизнес + юристы.
4. **Юридическое подтверждение семантики отзыва** (что считается «не подтверждённым» и когда возникает обязанность возврата) — юристы + ИБ.
5. **Модель лимитов** (набор и дефолты) — бизнес + протокол НСПК.
6. **Границы пилота**: состав ТСП и сегментов первой волны.
7. **Организационная форма**: остаётся ли это feature-дельтой текущего initiative или выделяется в отдельную инициативу (со сменой родительского spine).
