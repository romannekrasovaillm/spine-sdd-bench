# Proposal

## Why

ТСП — онлайн-кинотеатры, ЖКХ, связь — просят **рекуррентные C2B-списания по согласию плательщика** (подписки СБП). Принятое решение обслуживает только разовый приём: каждый платёж требует QR и действия клиента, поэтому подписочные сценарии невозможны. Без этого банк теряет подписочный сегмент эквайринга СБП.

## Significance and Route (A1)

**Score: 10/15 → маршрут Critical** (`arch-be control score --trigger ... --from-diff`).

| Триггер | Значение | Почему |
|---|---|---|
| financial_impact | true | появляется новый класс инициативы списания денег со счёта плательщика |
| security_boundary_change | true | согласие — юридическое основание списания; новая долгоживущая авторизация и её отзыв |
| consistency_model_change | true | новая долгоживущая сущность (согласие) и её жизненный цикл рядом со статусной машиной платежа |
| api_contract_change | true | новые ресурсы контракта ТСП (согласия, списания) |
| data_contract_change | true | новые данные (согласие, лимиты, попытки списания) и новые события нотификаций |
| cross_domain_integration | true | ТСП ↔ шлюз ↔ ОПКЦ (реестр согласий) ↔ АБС ↔ банк плательщика |
| new_component | true | сервис согласий и планировщик списаний — новые рантайм-компоненты контура |
| significant_nfr | true | новые измеримые бюджеты: старт списания, лаг отзыва, пиковая нагрузка границ периода |
| rto_rpo_targets | true | RPO=0 распространяется на согласия и попытки списания |
| criticality_or_exception | true | платёжный контур, КИИ, регуляторные последствия |

Не сработали: `new_datastore` (расширение существующей БД шлюза), `new_vendor` (тот же вендорский транспорт; область поставки — предмет ADR-009, не новый вендор), `domain_ownership_change`, `trust_zone_change`, `irreversible_migration`.

Почему Critical: ≥5 триггеров и явные `security_boundary_change` + `criticality_or_exception`. По правилам маршрутизации дельта-спеки недостаточно — требуется полный Solutioning: спайн-инварианты, ADR, NFR, **обязательная человеческая точка A3**, walking skeleton и evidence-гейты. При этом изменение — **feature-уровня**: родительский spine (initiative) остаётся read-only связывающим ограничением, локальное переопределение запрещено.

Примечание: `arch-be gate --route auto` на пустом диффе даёт Fast (score 0) — это не оценка значимости, а отсутствие изменений; заявленный маршрут (Critical) является входом гейта после появления артефактов и фиксируется в `changes/add-sbp-recurring-payments/DELTA.md`.

## What Changes

- **Новая сущность «согласие плательщика» (mandate)** с жизненным циклом `PENDING_PAYER → ACTIVE → SUSPENDED → REVOKED | EXPIRED | REJECTED`; источник истины — реестр СБП, в шлюзе — зеркало с синхронизацией и сверкой.
- **Рекуррентное списание** как платёж существующей статусной машины с атрибутом `consentId`; зачисление — по-прежнему **только из `PAID`** (AD-005).
- **Предусловие списания**: действующее согласие и лимиты проверяются в одной транзакции с созданием попытки (новый инвариант AD-009).
- **Приоритет отзыва согласия**: отзыв блокирует неподтверждённые попытки и компенсирует подтверждённые возвратом (новый инвариант AD-010).
- **Идемпотентность попытки списания** с детерминированным ключом `(consentId, billingPeriod, attemptSeq)` (новый инвариант AD-011).
- **Планировщик списаний в ядре** (outbox/очередь), сглаживание пиков границ периода, per-ТСП честность, ретраи с джиттером.
- **Контракт ТСП расширяется обратно совместимо** (`openapi/tsp-api.yaml` 0.1.0 → 0.2.0): новые пути `/v1/consents*`, опциональное поле `consentId`, новые события/коды ошибок. Ломающих изменений нет.
- Не **BREAKING**: существующие потребители, поля и значения перечислений не изменяются; версия API остаётся `/v1`.

## Capabilities

### New Capabilities
- `sbp-recurring-payments`: согласие плательщика (регистрация, статусы, отзыв, лимиты) и исполнение рекуррентных списаний в рамках согласия — поведение, контракт ТСП, нотификации, NFR и аудит.

### Modified Capabilities
- Нет. `openspec/specs/` пуст — существующие возможности ещё не описаны как OpenSpec-спеки; изменения принятой архитектуры (спайн, контракт, ADR) зафиксированы дельтой `changes/add-sbp-recurring-payments/DELTA.md`, ADR-008/ADR-009 и расширением `openapi/tsp-api.yaml`.

## Impact

- **Код/компоненты**: новый сервис согласий и планировщик списаний в платёжном контуре; расширение ядра (статусная машина → согласие как источник предусловия), нотификатора, сверки; расширение внутреннего контракта адаптера ОПКЦ (`docs/contracts/opkc-adapter.md`) — новые операции `registerConsent`/`getConsentStatus`/`cancelConsent`/`createDebit`.
- **API/контракты**: `openapi/tsp-api.yaml` 0.2.0 (аддитивно); новые события вебхуков `consent.*`, `charge.*`; новые коды ошибок.
- **Данные**: новые сущности (согласие, лимиты, попытки списания) в БД шлюза; расширение outbox и аудит-лога; ПДн плательщика — минимизированы.
- **Спайн**: добавляются блоки AD-009, AD-010, AD-011 (Proposed, ADR-008); AD-001..AD-008 не переопределяются.
- **Внешние зависимости/владельцы**: НСПК (протокол подписок — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`), вендор транспорта (расширение области — ADR-009/A3), владелец АБС, ИБ/КИИ, юристы (природа согласия и отзыва).
- **Решения, требующие человека (A3)**: ADR-009 (область транспорта подписок) и параметры политики dunning; перечень — в `design.md`.
