# CHG-001 — Оценка значимости и маршрут

- Изменение: рекуррентные C2B-списания (подписки СБП) по мандату плательщика
- Дата: 2026-09-28
- Инструмент: `significance_score` (15 триггеров)

## 1. Результат

**Score: 11/15 → маршрут Critical** (порог: 5+ либо критический триггер). Сработали 11 триггеров, включая критический `security_boundary_change`. Маршрут совпадает с исходным решением (Critical, 11/15): изменение не снижает класс процесса.

## 2. Сработавшие триггеры и почему

| Триггер | Сработал | Обоснование |
|---|---|---|
| new_component | да | Выделенный сервис подписок + планировщик списаний в платёжном контуре. |
| new_datastore | да | Реестр мандатов (согласий) — новое хранилище персонально значимых данных. |
| security_boundary_change (критический) | да | Списание без интерактивного действия клиента: основание — хранимый мандат; отзыв и уведомления становятся границей безопасности. |
| cross_domain_integration | да | Домены ТСП↔шлюз↔НСПК↔банк плательщика↔АБС; новый домен согласий. |
| domain_ownership_change | да | Появляется владелец домена «согласия/подписки», которого ранее не было. |
| api_contract_change | да | Новые пути/схемы контракта API ТСП (`openapi/tsp-api.yaml`). |
| data_contract_change | да | Новая сущность мандата, реестр `charges`, новые события подписок. |
| consistency_model_change | да | Согласованность согласия и исполнения периодов; гонка «отзыв ↔ списание в полёте». |
| significant_nfr | да | Новые измеримые бюджеты (точность расписания, немедленность блокировки, пакетные пики). |
| financial_impact | да | Автоматические списания с счетов плательщиков. |
| criticality_or_exception | да | Платёжный контур, КИИ, регуляторика (161-ФЗ, 152-ФЗ). |
| new_vendor | нет | Транспорт к ОПКЦ уже вендорский (ADR-007); рекуррентный протокол расширяет тот же адаптер. |
| trust_zone_change | нет | Новые trust-зоны не вводятся; контур сохраняется (AD-006). |
| rto_rpo_targets | нет | Целевые RPO=0 / RTO ≤ 1 ч сохраняются, новых целей нет. |
| irreversible_migration | нет | Изменение аддитивно, отключается фиче-флагом; миграции данных «в обратную сторону» нет. |

## 3. Почему нужна глубина именно Critical

- **Критический триггер (security_boundary_change)** сам по себе фиксирует маршрут Critical: рекуррентное списание меняет модель авторизации платежа — основанием становится хранимое согласие, а не действие клиента в момент оплаты. Ошибка необратима финансово.
- **Новый источник персонально значимых данных** (мандат) под 152-ФЗ требует ИБ-ревью и режима хранения.
- **Human-in-the-loop обязателен (A3)**: продуктово-регуляторные развилки (тип подписки, политика неоплаченных периодов, уведомления) не могут быть решены агентом.

## 4. План гейтов A0–A5 для этого изменения

| Гейт | Что делаем | Статус после пакета |
|---|---|---|
| A0 Architecture Fit | Укладывается ли в существующий контур (FSM/outbox/адаптер)? | PASS — переиспользование ядра |
| A1 Impact Assessment | Blast radius, затронутые владельцы, контракты | `IMPACT.md`, `CONTRACT-DELTA.md` — PASS |
| A2 Solutioning trigger | Полное solutioning (Critical) | Этот пакет + `ADR-008` |
| A3 Human Architecture Decision | Утверждение развилок (см. `OPEN-QUESTIONS.md`) | **ОЖИДАЕТ человека** |
| A4 Conformance Evidence | Fitness-правила, тесты идемпотентности/отзыва, ИБ-аудит, нагрузка | не начат (после A3) |
| A5 Post-deploy Drift Check | SLO-отчёт, отсутствие двойных списаний, сверка мандатов | не начат (после запуска) |

## 5. Approval theater — контроль

Риск «резинового штампа» на A3 высок из-за бизнес-давления ТСП. Поэтому в пакет вынесены **явные развилки с rejected-вариантами** (`OPEN-QUESTIONS.md`) и черновик machine-readable A3-решения в `ADR-008`: человек утверждает развилки, а не «пакет целиком».
