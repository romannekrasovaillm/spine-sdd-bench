# Статусная машина согласия плательщика и расписание списаний — спецификация

- Status: Draft (для ревью на гейте A1; дополняет `docs/spec/state-machine.md`, не заменяет его)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-009, ADR-011, AD-009, AD-010, AD-011

Единый источник истины состояния согласия — реестр согласий в БД шлюза (ADR-009, по образцу AD-002). Каждый переход — **атомарная транзакция** «смена состояния согласия + запись в outbox + аудит-лог». Повторные триггеры идемпотентны.

Предметная граница: согласие **не является платежом**. Каждое списание по согласию — обычный платёж (`docs/spec/state-machine.md`), проходящий `CREATED → QR_ISSUED → PAID → CREDITED → COMPLETED` с зачислением только из `PAID` (AD-005).

## Проблема

ТСП нужны повторяющиеся списания без участия плательщика в момент каждой оплаты. Это требует носителя авторизации (мандата), который живёт дольше отдельного платежа и может быть отозван. Необходимо однозначно описать состояния согласия, правила переходов и запрет дебета без действующего согласия, чтобы независимые исполнители (ядро, планировщик, адаптер, API ТСП) не разошлись в семантике.

## 1. Состояния согласия

| Состояние | Смысл | Дебеты разрешены | Терминальное |
|---|---|---|---|
| `PENDING` | Согласие зарегистрировано в шлюзе, ожидает подтверждения НСПК | нет | нет |
| `ACTIVE` | Действует: плательщик авторизовал списания в границах согласия | да | нет |
| `SUSPENDED` | Приостановлено (по запросу ТСП/плательщика или политикой), не отозвано | нет | нет |
| `REVOKED` | Отозвано плательщиком (или его банком) | нет | да |
| `EXPIRED` | Истёк срок действия согласия | нет | да |
| `REJECTED` | Отклонено НСПК / не подтверждено плательщиком | нет | да |

Границы согласия (фиксируются при создании, иммутабельны): получатель (ТСП и счёт), `amountType` (`FIXED` | `VARIABLE_WITH_LIMIT`), `maxAmount`, периодичность, срок действия.

## 2. Таблица переходов

| № | From | To | Триггер | Guard | Действие при переходе |
|---|---|---|---|---|---|
| CS1 | — | `PENDING` | `POST /v1/consents` (новый `consentId`) | валидный запрос, ТСП активен | запись согласия + outbox «регистрация у ОПКЦ» |
| CS2 | `PENDING` | `ACTIVE` | подтверждение НСПК (`consent.registered`) | реквизиты/лимиты совпадают с заявкой | outbox, вебхук `consent.activated`; согласие готово к расписанию |
| CS3 | `PENDING` | `REJECTED` | отказ НСПК (`consent.rejected`) или не подтверждено в срок | — | `errorCode`, вебхук `consent.rejected`; дебетов нет |
| CS4 | `ACTIVE` | `SUSPENDED` | запрос приостановки (ТСП/плательщик/политика) | — | outbox; планировщик не создаёт дебетов |
| CS5 | `SUSPENDED` | `ACTIVE` | возобновление | согласие не отозвано и не истекло | outbox; расписание продолжается со следующего периода |
| CS6 | `PENDING`/`ACTIVE`/`SUSPENDED` | `REVOKED` | отзыв плательщика/ТСП (`POST /v1/consents/{id}/revoke` или событие НСПК) | — | **локально немедленно**: дебеты запрещены; outbox «регистрация отзыва у ОПКЦ»; вебхук `consent.revoked`. Необратимо |
| CS7 | `ACTIVE`/`SUSPENDED` | `EXPIRED` | наступление `validUntil` | — | outbox, вебхук `consent.expired`; дебеты запрещены |
| CS8 | `ACTIVE` | `ACTIVE` | сверка подтвердила расхождение «у НСПК отозвано» | — | **стоп-сигнал**: списания остановлены, эскалация, ручной разбор (состояние переводится в `REVOKED` только после подтверждения) |

## 3. Запрещённые переходы (инварианты)

- **Дебет невозможен без `ACTIVE`** (AD-009): из `PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED`/`REJECTED` автосписание недостижимо. Проверяется правилом `consent_before_auto_action`.
- **`REVOKED` необратимо**: переходов из него нет; повторный отзыв идемпотентен.
- Границы согласия (`maxAmount`, получатель, периодичность) иммутабельны после `ACTIVE`; изменение границ — только новое согласие.
- Дебет не может превышать `maxAmount` и выходить за период; нарушение → дебет не создаётся, находка в аудите (REQ-SUB-7).
- Отзыв не «откатывается» возобновлением: `REVOKED → ACTIVE` запрещён (только новое согласие).

## 4. Дебеты по расписанию и идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| Плановый дебет планировщика | `consentId + periodNumber` | второй финансовый эффект не создаётся; возвращается существующий дебет (AD-011) |
| Повторная нотификация НСПК о дебете | `eventId` (как ADR-004) | обработанный `eventId` игнорируется |
| Повторная инициация после `UNKNOWN` | `consentId + periodNumber` | сначала запрос статуса, повтор только если дебет не создан |
| `POST /v1/consents` | `Idempotency-Key` | тот же `consentId`, состояние не меняется |
| `POST /v1/consents/{id}/revoke` | идемпотентно по `consentId` | повтор возвращает `REVOKED` без побочных эффектов |

## 5. Сверка и восстановление

- Согласия — отдельный контур сверки (ADR-009): ежечасный запрос статусов согласий у НСПК (целевой регламент) и сверка с реестром.
- «У нас `ACTIVE`, у НСПК отозвано» → немедленная остановка списаний, эскалация (CS8).
- «У нас нет / `PENDING`, у НСПК `ACTIVE`» → дозапрос и восстановление состояния.
- Согласие в `ACTIVE` с недоступным НСПК: локальные проверки и запрет новых дебетов при неопределённости; дебеты видны в отчёте незавершённых операций (по образцу ADR-004/ADR-005).

## 6. Согласованность с API ТСП

Наружу выставляются состояния `PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`, `REJECTED` — без технических подсостояний. Вебхуки `consent.activated`, `consent.rejected`, `consent.revoked`, `consent.expired`. Дебеты видны ТСП как обычные платежи с полем `consentId` и `periodNumber`.

## Критерии приёмки

- [ ] Дебет невозможен вне состояния `ACTIVE` (тест `consent_before_auto_action`; REQ-SUB-2).
- [ ] Отзыв согласия → 0 последующих списаний (REQ-SUB-5).
- [ ] Повторный триггер периода `consentId + periodNumber` → ровно один финансовый эффект (REQ-SUB-4).
- [ ] `REVOKED`/`EXPIRED`/`REJECTED` — терминальные: переходов нет, повтор идемпотентен.
- [ ] Каждый переход «состояние + outbox + аудит» атомарен; сверка согласий с НСПК находит расхождения.

## Риски

- Расхождение состояния согласия в шлюзе и у НСПК (окно асинхронной регистрации отзыва) → ежечасная сверка, стоп-сигнал CS8.
- Гонка отзыва и уже запущенного списания → проверка согласия в момент создания дебета + сверка.
- Рост числа согласий и совпадение периодов → нагрузка на планировщик и НСПК на границе периода → джиттер, допуск окна, нагрузочные тесты.
