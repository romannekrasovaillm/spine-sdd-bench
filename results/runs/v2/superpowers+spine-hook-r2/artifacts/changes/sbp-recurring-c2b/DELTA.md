## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по однажды полученному согласию плательщика — «подписки СБП». Сейчас каждый платёж требует нового QR и действия клиента, поэтому подписки невозможны. Нужно добавить автосписания (мандат плательщика + расписание + отзыв), не меняя ядро приёма (AD-002, AD-003, AD-005) и не ломая существующих потребителей API ТСП v0.1.

## ADDED

Инварианты spine (полные формулировки — в `ARCHITECTURE-SPINE.md`):

- `AD-009` — согласие плательщика обязательно до автоматического списания. Binds: реестр согласий, планировщик списаний, статусная машина, API ТСП, адаптер ОПКЦ. Rule: автосписание создаётся только при записи о согласии в состоянии `ACTIVE`, покрывающей сумму и период; проверка — исполняемое правило `consent-before-auto-action`.
- `AD-010` — согласие: единственный источник истины, RPO=0, отзыв необратим и останавливает следующее списание. Binds: реестр согласий, БД шлюза, планировщик, адаптер ОПКЦ, аудит-лог. Rule: изменение состояния согласия и outbox — одна локальная транзакция; после подтверждённого отзыва — 0 будущих списаний; сверка согласий с НСПК.
- `AD-011` — периодическое списание идемпотентно по ключу периода. Binds: планировщик, статусная машина, адаптеры АБС/ОПКЦ. Rule: ключ дебета = `consentId + periodNumber`; повторный триггер периода не создаёт второго финансового эффекта; проверка — исполняемое правило `debit-period-idempotency`.

Требования с критериями EARS (проверяемые; полный список — `docs/solutioning-subscriptions.md` §6):

- **REQ-SUB-1.** When ТСП регистрирует согласие плательщика, the СБП-шлюз shall создать согласие и вернуть `consentId` со статусом `PENDING`, не создавая ни одного списания до подтверждения согласия.
- **REQ-SUB-2.** While для подписки нет согласия в состоянии `ACTIVE`, the СБП-шлюз shall не создавать автоматических списаний.
- **REQ-SUB-3.** When наступает плановый период по действующему согласию, the планировщик shall инициировать ровно одно списание за период в пределах допуска расписания.
- **REQ-SUB-4.** If тот же период (`consentId + periodNumber`) инициируется повторно (ретрай, дубль нотификации, перезапуск планировщика), then the СБП-шлюз shall обеспечить ровно один финансовый эффект.
- **REQ-SUB-5.** When ТСП отзывает согласие, the СБП-шлюз shall прекратить все будущие списания по этому согласию (0 списаний после подтверждённого отзыва).
- **REQ-SUB-6.** If НСПК отклоняет согласие либо дебет, then the СБП-шлюз shall перевести согласие/дебет в терминальный отказ и не создавать финансового эффекта.
- **REQ-SUB-7.** When сумма или период списания выходит за границы согласия, the СБП-шлюз shall не создавать списание и зафиксировать находку в аудите.

Контрактные элементы (аддитивно, `openapi/tsp-api.yaml` v0.2.0):

- Новые пути: `POST /v1/consents`, `GET /v1/consents/{consentId}`, `POST /v1/consents/{consentId}/revoke`.
- Новые схемы: `ConsentRequest`, `Consent`, `ConsentStatus`, `Periodicity`, `AmountType`.
- Расширение `Payment`/`PaymentRequest` необязательными полями `consentId`, `paymentType` (`SINGLE|RECURRING`), `periodNumber`.
- Новые ошибки: `CONSENT_NOT_ACTIVE` (409), `CONSENT_LIMIT_EXCEEDED` (422), `CONSENT_EXPIRED` (422).
- Новые вебхуки: `consent.activated`, `consent.rejected`, `consent.revoked`.

Контракт адаптера ОПКЦ (аддитивно, `docs/contracts/opkc-adapter-recurring.md` v0.2-draft): методы `registerConsent`, `getConsentStatus`, `revokeConsent`, `createDebit`, `getDebitStatus`, `getConsentReconciliationReport`; события `consent.registered`, `consent.rejected`, `consent.revoked`, `debit.paid`, `debit.rejected`; идемпотентность по `reference` (для дебета — `consentId + periodNumber`).

## Влияние на принятую архитектуру (кратко; полный разбор — §2 solutioning)

- **Расширяются, не ломаются:** AD-002 (единый источник истины) — тем же правилом «статус + outbox + аудит в одной транзакции» теперь покрывается и реестр согласий; AD-003 (идемпотентность) — добавляется ключ периода; AD-004 (единственный адаптер) — контракт адаптера расширяется, адаптер остаётся один; AD-005 (зачисление только из `PAID`) — каждый дебет остаётся обычным платежом и проходит `PAID → CREDITED`.
- **Не меняются:** AD-001 (изоляция), AD-006 (trust-зоны), AD-007 (НПС/КИИ/ПДн), AD-008 (гибрид «ядро + вендорский транспорт») — расширяется состав ядра (планировщик, реестр согласий) и объём контракта с вендором.
- **Новое:** реестр согласий и планировщик списаний как часть платёжного контура (ядро, собственная разработка — по ADR-007); новый внешний вход НСПК — сервис подписок/автоплатежей `[ТРЕБУЕТ ПРОВЕРКИ]`.

## План отката

- **До боевой эксплуатации:** откат = не включать функционал; все работы обратимы (ADR-008…011 на старте reversible/costly).
- **После включения:** фиче-флаг; немедленно — запрет регистрации **новых** согласий; запросы на отзыв согласий и исполнение уже действующих обязательств НЕ отключаются (потребительское право на отзыв и финансовые обязательства сохраняются). Синхронная сверка согласий с НСПК перед любым решением о заморозке.
- **Сигналы отката:** нарушение «0 списаний после отзыва», дубли списаний за период > 0, расхождения согласий с НСПК, недоступность контура согласий, каскадные ошибки протокола НСПК.
- **Владелец решения об откате:** solution-архитектор совместно с бизнесом (остановка биллинга затрагивает выручку ТСП и обязательства) — закрепляется на A3. Исполнитель откат не выполняет и не маскирует проблему обходным редизайном.
- **Данные:** согласия не мигрируются обратно; шлюз остаётся источником истины по согласиям до полной сверки с НСПК; детали — `changes/sbp-recurring-c2b/handoff/ROLLBACK.yaml`.
