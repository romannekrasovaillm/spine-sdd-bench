# Проблема и гипотеза результата — sbp-recurring-c2b

## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) не могут принимать рекуррентные C2B-платежи: принятое решение «СБП-шлюз (C2B-приём)» описывает только разовый платёж, требующий нового QR и действия клиента при каждой оплате. Подписки (по однажды выданному согласию плательщика) невозможны, ТСП уходят к конкурентам с сервисом подписок СБП.

## Гипотеза результата

Добавление сущности «согласие плательщика» (мандат) и планировщика списаний в ядро СБП-шлюза позволит исполнять периодические списания **без изменения** принятой модели платежа (AD-002/AD-003/AD-005) и **без поломки** существующих потребителей API ТСП v0.1:
- каждое списание — обычный платёж, проходящий `PAID → CREDITED`;
- автосписание невозможно без действующего согласия (AD-009);
- согласие — источник истины с RPO=0, отзыв необратим и останавливает будущие списания (AD-010);
- повтор периода `consentId+periodNumber` не создаёт второго финансового эффекта (AD-011).

Гипотеза проверяема: см. `ACCEPTANCE.md` и правила `consent_before_auto_action`, `debit_period_idempotency`.

Полное решение — `docs/solutioning-subscriptions.md`; дельта — `DELTA.md`.
