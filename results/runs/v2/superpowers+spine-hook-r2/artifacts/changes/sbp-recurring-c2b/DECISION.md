# Запись решения A3 — подписки СБП (sbp-recurring-c2b)

**Решение принимает человек-архитектор (A3). Агент оставляет `decided_by` пустым — гейт обязан поймать `a3_not_signed`.**

## Машиночитаемая запись

Значения ниже заполняет человек-архитектор на A3. Смысл полей: `choice` — принято/принято с условиями/отклонено; `rationale` — обоснование; `rejected` — отвергнутые варианты из ADR-008…011; `conditions` — условия принятия; `expiry` — срок/условие пересмотра (дата ГГГГ-ММ-ДД); `decided_by` — имя человека; `decided_at` — дата.

```yaml
choice:
rationale:
rejected: []
conditions: []
expiry:
decided_by:
decided_at:
```

## Что выносится на решение

Ратификация ADR-008…011 (статус Proposed → Accepted / Superseded):
- **ADR-008** — модель подписок: согласие плательщика как мандат в ядре шлюза (альтернативы: у ТСП, вендорская «коробка», «повтор платежа»).
- **ADR-009** — жизненный цикл согласия: локально немедленный отзыв + асинхронная регистрация у НСПК; RPO=0; единственный источник истины.
- **ADR-010** — транспорт: расширение контракта единственного адаптера ОПКЦ (не второй адаптер).
- **ADR-011** — идемпотентность и расписание: планировщик шлюза + ключ периода `consentId+periodNumber`.

После ратификации: спайн-блоки AD-009…011 переводятся в Accepted/[ADOPTED], handoff-пакет перегенерируется (`handoff/README.md`).

## Условия, требующие решения человека/бизнеса (не закрываются машиной)

1. Объём первой волны: фиксированная сумма / переменная с лимитом / гибкая без уведомления; расписание шлюза vs ad-hoc дебет ТСП.
2. Регуляторика: юридическая форма согласия, обязанности уведомления плательщика, 161-ФЗ/152-ФЗ, срок хранения доказательств согласия (ИБ/комплаенс).
3. Протокол НСПК по подпискам — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.
4. Вендор и закупка: расширение RFP/контракта, proof идемпотентности дебета, SLA, стоимость/сроки.
5. Бизнес-модель: тарифы, политика пропущенного периода, пороги AML/антифрода, уведомления ТСП.
6. Находки состязательного ревью (`docs/REVIEW.md`, blocker 1–2) — закрыть до старта реализации.
