- ID изменения: CHG-SBP-RECURRING-001
- Дата: 2026-09-28
- Автор: solution-architect (платёжный контур)
- Базовое решение: `docs/solutioning.md`, ADR-001…007, `ARCHITECTURE-SPINE.md` (AD-001…AD-008)
- Статус пакета: **Proposed** — выносится на человеческое решение (гейт A3-типа) до реализации
- Решение изменения: `docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-podpiski-sbp.md`

## 1. Оценка значимости и маршрута

### 1.1 Оценка значимости (рабочая модель 5 осей, 0–3)

| Ось | Балл | Обоснование |
|---|---:|---|
| Новизна и внешние интеграции | 3 | Новый класс операций к ОПКЦ (согласия и инициируемые банком-получателем списания), новый участник действия — банк плательщика; протокол не раскрыт `[ТРЕБУЕТ ПРОВЕРКИ]` |
| Финансовое влияние | 3 | Рекуррентное списание со счёта физлица: ошибка = двойное списание/несанкционированное списание; прямой материальный и репутационный ущерб |
| Данные и ПДн | 2 | Идентификатор плательщика и параметры согласия — ПДн-чувствительные данные; требуется минимизация/токенизация (AD-006) |
| Регуляторные требования / КИИ | 3 | Действие допустимо только по действующему согласию и в его пределах; аудит, уведомление плательщика, отзыв (161-ФЗ, 152-ФЗ, ПОД/ФТ, КИИ) |
| Необратимость (стоимость отката) | 1 | Изменение аддитивно и включается флагом; технический откат дешёв, организационный — дороже после появления действующих согласий |
| **Итого** | **12/15** | Сопоставимо с базовой значимостью решения (11/15) |

**Маршрут: Critical.** Изменение сопоставимой значимости с базовым решением.

### 1.2 Почему нужен полный цикл, а не bounded-правка

- Меняются **интерфейсы, от которых зависят другие** (API ТСП, контракт адаптера ОПКЦ, статусная модель) — по классификации это архитектурная работа.
- Затрагивается **смысл финансового инварианта** (AD-005): «подтверждение» для рекуррентного списания приходит от другого источника, чем нотификация оплаты QR.
- Появляется **новое регуляторное основание** (согласие плательщика) и новый класс ПДн.
- Решение **необратимо на уровне обязательств** после запуска действующих согласий (закон требует их обслуживать/отзывать).

### 1.3 Требуемые гейты

Полный ADR (ADR-008) → человеческое решение (A3-типа, ратификация AD-008 и блока spine AD-009) → A1 (финализация контрактов/NFR) → A2 (walking skeleton подписок) → A4 (conformance: fitness-инварианты, нагрузка, ИБ) → A5 (post-deploy drift). Реализация транспорта — только после подтверждения поддержки mandate-протокола вендором (ADR-007).

### 2.2 Что не меняется

- Топология и изоляция (AD-001), транзакционный outbox и единая точка записи (ADR-001).
- Механика нотификаций ТСП: at-least-once, дедуп по `eventId`, DLQ, сверка (ADR-004) — переиспользуется для `debit.*`/`mandate.*`.
- Транспорт к ОПКЦ: mTLS/ГОСТ, СКЗИ/HSM, circuit breaker (ADR-003) — только новые операции внутри того же адаптера.
- Интеграция с АБС: зачисление идемпотентно по `paymentId`, возвраты-сага, сверка (ADR-005) — для рекуррентного списания те же правила.
- **Существующий разовый приём по QR** — переходы T1–T12 и контракт v0.1 не изменяются.
- Стратегия реализации (ADR-007 hybrid) — сохраняется; расширяется только объём контракта адаптера (риск — см. §7).

## 3. Архитектурное решение (резюме ADR-008)

Полный текст — `docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-podpiski-sbp.md`.

- **Выбор:** расширение ядра существующего шлюза новым агрегатом `Mandate` и рекуррентным списанием `origin=MANDATE`; переиспользование outbox, статусной машины, адаптера ОПКЦ, нотификатора, сверки и интеграции с АБС.
- **Альтернативы:** (B) отдельный микросервис «Подписки»; (C) хранение согласий в АБС/системе длинных поручений; (D) вендорский модуль «подписки» целиком. Отклонены по причинам: второй источник истины и распределённая согласованность (B), разрыв изоляции и семантики СБП (C), lock-in финансовой логики и сложный аудит (D).
- **Ключевые последствия (positive):** единая доказанная модель консистентности; симметричная защита от двойного списания и двойного зачисления; аддитивность и обратная совместимость; управляемый отзыв согласия.
- **Ключевые последствия (negative):** рост сложности ядра; новый периметр ПДн/регуляторики; зависимость от протокола НСПК и вендорского адаптера; двойная проверка лимитов.
- **Обратимость:** **reversible** технически (аддитивно, флаг) / **costly** организационно после появления действующих согласий.

## 4. Изменения контрактов без поломки существующих потребителей

### 4.1 Принцип

Изменения **только аддитивные** в пространстве имён `/v1`: новые ресурсы и опциональные поля; существующие пути, обязательные поля и `enum` `Payment.status` **не изменяются**. Разрушающие изменения — только в `/v2` с периодом поддержки ≥ 6 мес (`docs/contracts/tsp-api.md` §6). Версия контракта: 0.1.0 → **0.2.0-draft**.

Осознанное решение по статусам: статусы рекуррентного списания (`DEBIT_PENDING` и т.п.) отдаются в **отдельном ресурсе `Debit`**, а не добавлением значений в `Payment.status`, чтобы не ломать строгих потребителей, исчерпывающе разбирающих enum v0.1. В `Payment` добавляются только опциональные поля `origin`, `mandateId`.

### 4.2 API ТСП — новые методы (аддитивно)

| Метод | Назначение |
|---|---|
| `POST /v1/mandates` | Регистрация согласия плательщика (`Idempotency-Key` обязателен) |
| `GET /v1/mandates/{mandateId}` | Статус и параметры согласия |
| `POST /v1/mandates/{mandateId}/debits` | Инициировать рекуррентное списание (`Idempotency-Key` + `(mandateId, period)`) |
| `GET /v1/debits/{debitId}` | Статус списания |
| `POST /v1/mandates/{mandateId}/suspend` / `…/resume` | Приостановка/возобновление (опционально, по решению бизнеса) |
| `POST /v1/mandates/{mandateId}/revoke` | Отзыв согласия со стороны ТСП (отзыв плательщиком приходит событием) |

Новые коды ошибок: `MANDATE_NOT_ACTIVE` (422), `MANDATE_EXPIRED` (422), `AMOUNT_EXCEEDS_MANDATE_LIMIT` (422), `PERIOD_ALREADY_DEBITED` (409), `MANDATE_ALREADY_REVOKED` (409), `MANDATE_NOT_FOUND` (404).

`openapi/tsp-api.yaml` покрывает обязательный поднабор (регистрация/статус согласия, инициирование/статус списания). Опциональные методы `suspend`/`resume`/`revoke` описаны в `docs/contracts/tsp-api.md` §3.10 и вносятся в машиночитаемый контракт после решения бизнеса об их включении (см. §7).

### 4.3 Вебхуки — новые события (аддитивно)

`mandate.activated`, `mandate.pending`, `mandate.rejected`, `mandate.suspended`, `mandate.revoked`, `mandate.expired`, `debit.completed` / `debit.failed` (с `errorCode`). Механика доставки, заголовки `X-SBP-Event-Id`/`X-SBP-Signature` и дедупликация — без изменений (ADR-004).

### 4.4 Контракт адаптера ОПКЦ — новые операции/события (аддитивно)

Синхронные: `registerMandate`, `getMandateStatus`, `revokeMandate`, `createDebit`, `getDebitStatus`. Асинхронные: `mandate.activated|rejected|revoked|expired`, `debit.paid|rejected|expired`. Идемпотентность по `reference` (`mandateId`/`debitId`) — обязательное требование RFP (без него ретраи дают двойные списания).

### 4.5 OpenAPI

`openapi/tsp-api.yaml` дополняется новыми путями и схемами (`Mandate`, `MandateRequest`, `Debit`, `DebitRequest`, `DebitStatus`); существующие пути/схемы сохраняются побайтово, меняется только `info.version` → `0.2.0-draft`. Проверка совместимости — diff-инструментом (oasdiff): только additive (AC9, §6).

### 4.6 Совместимость и миграция потребителей

- Существующие интеграции ТСП продолжают работать без изменений (v0.1-сценарий).
- Новые возможности — опциональны и включаются по согласованию с ТСП.
- Contract-тесты v0.1 обязательны в CI (AC8); релиз-ноуты фиксируют `DEBIT_PENDING` в ресурсе `Debit` и новые опциональные поля `Payment`.

## 6. Критерии приёмки и план отката

### 6.1 Критерии приёмки (проверяемые)

| ID | Критерий | Проверка |
|---|---|---|
| AC1 | Повторный `POST /v1/mandates` с тем же `Idempotency-Key` → тот же `mandateId`, второго согласия нет | Тест идемпотентности |
| AC2 | Списание возможно только при `Mandate.status = ACTIVE`; из `PENDING_PAYER`/`REVOKED`/`EXPIRED` → 422 `MANDATE_NOT_ACTIVE`/`MANDATE_EXPIRED`, вызова НСПК нет | Негативный тест + fitness |
| AC3 | Списание сверх `maxAmountPerPeriod`/остатка `maxTotalAmount` → 422 `AMOUNT_EXCEEDS_MANDATE_LIMIT` **до** вызова НСПК | Негативный тест |
| AC4 | Повторное событие НСПК `debit.paid` с тем же `eventId` не меняет состояние и не создаёт второе зачисление | Тест дедупликации |
| AC5 | Зачисление в АБС недостижимо из `CREATED`/`DEBIT_PENDING` (только из `PAID`) | Fitness-тест (AD-005/AD-009) |
| AC6 | Второе успешное списание за один `(mandateId, period)` недостижимо: один 201, повтор → идемпотентный ресурс или `409 PERIOD_ALREADY_DEBITED` | Тест гонки/конкурентного сабмита |
| AC7 | Отзыв согласия (плательщиком или ТСП) → новые списания отклоняются, незавершённые → `FAILED(MANDATE_REVOKED)`, ТСП получает `mandate.revoked` | Тест сквозного отзыва |
| AC8 | Регрессия v0.1: все contract-тесты существующего API ТСП (QR-приём, статусы, возвраты, вебхуки) проходят без изменений | CI contract-тесты |
| AC9 | Diff OpenAPI v0.1→v0.2 (oasdiff) — только аддитивные изменения; удалённых/переименованных полей и значений enum нет | CI-проверка совместимости |
| AC10 | Недоступность АБС: списание остаётся `PAID`, ретраи, двойной проводки нет, расхождение ловится сверкой | Chaos-тест |
| AC11 | Сбой функции подписок не влияет на доступность разового QR-приёма | Fault-isolation тест |
| AC12 | `payerRef` токенизирован и маскирован в логах; аудит содержит все переходы мандата и списания | ИБ-ревью, проверка лога |

### 6.2 План отката

- **Сигналы-триггеры:** любое двойное списание; несанкционированное списание без `ACTIVE`-согласия; инцидент ПДн; доля расхождений сверки выше порога; невозможность выполнить отзыв согласия; рост отказов списаний сверх порога.
- **До прода:** флаг выключен по умолчанию — откат = не включать.
- **В проде — уровни:**
  1. Запрет регистрации новых согласий (`POST /v1/mandates` off) — действующие не затрагиваются.
  2. «Stop-new-debits» — новые списания не инициируются; обслуживание отзывов и возвратов продолжается.
  3. Аварийный revoke-all по runbook с координацией с НСПК и 4-eyes.
  4. Данные не мигрируются обратно: мандаты остаются источником истины до планового завершения.
- **Владелец решения об откате:** solution-architect + владелец продукта + ИБ; при регуляторном инциденте — эскалация на профильный комитет.
- **Критерий успешного отката:** разовый QR-приём работает; новые согласия недоступны; действующие согласия корректно завершены (отозваны/истекли); 0 необработанных списаний и расхождений сверки.

## 8. Handoff-бриф для исполнителей (активируется после ратификации ADR-008)

Дистиллят для передачи исполнителям; до решения человека-архитектора не является основанием для реализации. Полные тексты — в файлах-источниках (см. §2.3).

**Цель изменения.** Дать ТСП возможность рекуррентных C2B-списаний по согласию плательщика (подписки СБП) поверх существующего шлюза: однократное оформление согласия, далее списания без QR и без действия клиента на каждый период.

**Что строим.** (1) API ТСП для мандатов и списаний (аддитивно к v0.1); (2) агрегат `Mandate` с жизненным циклом и RPO=0; (3) рекуррентное списание `origin=MANDATE` с предсостоянием `DEBIT_PENDING`; (4) mandate-операции и события в контракте адаптера ОПКЦ; (5) новые вебхуки `mandate.*`/`debit.*`; (6) расширение сверки на мандаты и списания.

**Инварианты (обязательны, дословно из spine).**
- AD-005: «Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус)».
- AD-009 (новый): «Рекуррентное списание инициируется только при `Mandate.status = ACTIVE`, в пределах лимитов согласия, идемпотентно по `(mandateId, period)`; зачисление — только из подтверждённого статуса (расширение AD-005); отзыв/приостановка согласия прекращает новые списания немедленно и фиксируется в аудит-логе».
- AD-002: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции».
- AD-003: «Повторная доставка любого сообщения не изменяет уже завершённое состояние».
- AD-004: «Протокол НСПК знает только адаптер ОПКЦ».
- AD-001: «Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза».

**Запрещено менять:** переходы T1–T12 разового приёма; существующие поля и enum `Payment.status` v0.1; правила outbox/идемпотентности AD-002/AD-003; границу адаптера AD-004. Любой конфликт с этими ограничениями обязан останавливать работу и эскалироваться архитектору.

**Критерии приёмки:** AC1–AC12 (§6.1). **NFR:** §5. **Откат:** §6.2. **Открытые внешние входы:** §7 п.2–4.
