# Статусная модель подписок СБП — мандат и рекуррентное списание

- Status: Draft (для ревью на гейте A1 изменения; вводится ADR-008)
- Owner: solution-architect (платёжный контур)
- Связано: ADR-008, ADR-002, ADR-003, ADR-005, AD-002, AD-003, AD-005, AD-009

Настоящая спецификация **дополняет** `docs/spec/state-machine.md` (разовый C2B по QR) и не изменяет существующие переходы T1–T12. Единый источник истины — БД шлюза (ADR-002). Каждый переход — **атомарная транзакция** «смена статуса + запись в outbox + аудит-лог» (AD-002). Повторные триггеры идемпотентны (AD-003).

Протокольные детали НСПК (названия операций, тайминги авторизации, лимиты, тексты уведомлений плательщику) — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации по договору.

## 1. Агрегат «согласие плательщика» (Mandate)

Параметры согласия (иммутабельны после `ACTIVE`; изменение = новое согласие):

| Поле | Смысл |
|---|---|
| `mandateId` | Идентификатор согласия в шлюзе (сквозной для сверки) |
| `tspId` | Получатель списаний |
| `payerRef` | Непрозрачная токенизированная ссылка на плательщика (не открытые ПДн, AD-006) |
| `maxAmountPerPeriod` | Максимальная сумма одного списания за период (копейки) |
| `period` | Период списаний (например, календарный месяц) `[ТРЕБУЕТ ПРОВЕРКИ]` |
| `maxTotalAmount` | Общий лимит по согласию (опционально) |
| `validUntil` | Срок действия согласия |
| `purpose` | Назначение (для плательщика) |

### 1.1 Состояния мандата

| Состояние | Смысл | Виден ТСП |
|---|---|---|
| `CREATED` | Согласие зарегистрировано в шлюзе, запрос к ОПКЦ в процессе | да |
| `PENDING_PAYER` | Запрос согласия передан в НСПК; плательщик подтверждает в своём банке | да |
| `ACTIVE` | Согласие действует; списания разрешены в пределах лимитов | да |
| `SUSPENDED` | Приостановлено (ТСП/шлюзом/банком); новые списания запрещены, возобновляемо | да |
| `REVOKED` | Отозвано плательщиком или банком; терминальное | да |
| `REJECTED` | Плательщик отказал / банк отклонил; терминальное | да |
| `EXPIRED` | Истёк `validUntil`; терминальное | да |

### 1.2 Переходы мандата

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` (новый `mandateId`) | валидный запрос, ТСП активен | запись мандата + outbox «регистрация согласия в ОПКЦ» |
| M2 | `CREATED` | `PENDING_PAYER` | ответ адаптера: запрос согласия принят | `opkcRequestId` получен | outbox-нотификация ТСП `mandate.pending` |
| M3 | `PENDING_PAYER` | `ACTIVE` | событие НСПК `mandate.activated` | параметры согласия совпадают с запрошенными | outbox, вебхук `mandate.activated` |
| M4 | `PENDING_PAYER` | `REJECTED` | событие НСПК `mandate.rejected` / таймаут подтверждения | — | `reasonCode`, вебхук `mandate.rejected` |
| M5 | `CREATED` | `REJECTED` | ошибка регистрации в ОПКЦ (не транзиентная / DLQ) | — | `errorCode`, вебхук `mandate.rejected` |
| M6 | `ACTIVE` | `SUSPENDED` | `POST /v1/mandates/{id}/suspend` (ТСП) или решение банка | — | outbox, вебхук `mandate.suspended` |
| M7 | `SUSPENDED` | `ACTIVE` | `POST /v1/mandates/{id}/resume` (ТСП) | подтверждение банка плательщика | outbox, вебхук `mandate.activated` |
| M8 | `ACTIVE`/`SUSPENDED`/`PENDING_PAYER` | `REVOKED` | отзыв плательщиком (событие НСПК) или `POST /v1/mandates/{id}/revoke` | — | outbox, аудит, вебхук `mandate.revoked` |
| M9 | `ACTIVE` | `EXPIRED` | достигнут `validUntil` | — | outbox, вебхук `mandate.expired` |

### 1.3 Инварианты мандата

- **Списание инициируется только при `Mandate.status = ACTIVE`.** Из `CREATED`, `PENDING_PAYER`, `SUSPENDED`, `REVOKED`, `REJECTED`, `EXPIRED` — недостижимо (AD-009).
- `REVOKED`, `REJECTED`, `EXPIRED` — терминальные. Отзыв необратим (повторный отзыв идемпотентен, состояние не меняется).
- Параметры согласия (`maxAmountPerPeriod`, `period`, `maxTotalAmount`, `validUntil`, `payerRef`) иммутабельны после `ACTIVE`.
- Отзыв/приостановка прекращают **новые** списания немедленно; уже подтверждённые списания не откатываются (корректировка — только возвратом, сага ADR-005).

## 2. Рекуррентное списание (Payment с `origin = MANDATE`)

Рекуррентное списание — это **тот же агрегат «платёж»** (`docs/spec/state-machine.md`), но с другим входом и добавленным авторизационным предсостоянием. Терминальные состояния и сага возврата — как в базовой спецификации.

### 2.1 Дополнительные состояния/признаки

| Состояние/признак | Смысл | Виден ТСП |
|---|---|---|
| `origin` (поле) | `QR` \| `MANDATE` — происхождение платежа | да (новое опциональное поле) |
| `DEBIT_PENDING` | Списание зарегистрировано, ожидается подтверждение банка плательщика | да |
| `mandateId` (поле) | Согласие, по которому инициировано списание | да (новое опциональное поле) |

Далее состояния совпадают с базовыми: `PAID` (подтверждено), `CREDITED`, `COMPLETED`; терминальные `FAILED`, `EXPIRED`, `REFUNDED`.

### 2.2 Переходы рекуррентного списания

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| D1 | — | `CREATED` | `POST /v1/mandates/{mandateId}/debits` (новый `paymentId`) | мандат `ACTIVE`; `amount ≤ maxAmountPerPeriod` и в остатке `maxTotalAmount`; `now < validUntil`; период не списан | запись платежа (`origin=MANDATE`) + outbox «регистрация списания в ОПКЦ» |
| D2 | `CREATED` | `DEBIT_PENDING` | ответ адаптера: списание принято | `opkcDebitId` получен | outbox-нотификация ТСП `debit.pending` |
| D3 | `DEBIT_PENDING` | `PAID` | событие НСПК `debit.paid` (подтверждение банка плательщика) | сумма и `mandateId` совпадают с инициированным списанием | outbox-событие «зачисление в АБС» (переход базового T4) |
| D4 | `DEBIT_PENDING` | `FAILED` | событие НСПК `debit.rejected` (отказ плательщика, недостаток средств, превышение лимита, отсутствие согласия) | — | `errorCode`, вебхук `debit.failed`; **зачисление запрещено** |
| D5 | `CREATED`/`DEBIT_PENDING` | `FAILED` | ошибка регистрации в ОПКЦ (не транзиентная / DLQ) | — | `errorCode`, вебхук `debit.failed` |
| D6 | `DEBIT_PENDING` | `EXPIRED` | таймаут авторизации списания | подтверждение не наступило | вебхук `debit.failed` (код `DEBIT_TIMEOUT`) |
| D7 | `PAID` | `CREDITED` → `COMPLETED` | подтверждение АБС → вебхук ТСП | как в базовых T8/T10 | как в базовой спецификации |
| D8 | `COMPLETED` | `REFUNDED` (или остаётся `COMPLETED` при частичном) | сага возврата | как в базовых T11/T12 | возврат средств плательщику |

### 2.3 Инварианты рекуррентного списания

- **Зачисление в АБС невозможно, кроме как из `PAID`** (расширение AD-005 на `origin=MANDATE`): из `CREATED`/`DEBIT_PENDING` зачисление недостижимо; проверяется fitness-тестом (AD-009).
- **Не более одного успешного списания на (`mandateId`, `period`)** (AD-009). Повторный запрос списания за тот же период → идемпотентный ответ существующего ресурса или `409 PERIOD_ALREADY_DEBITED`, но **не** новое списание.
- **Лимиты согласия соблюдаются до отправки в ОПКЦ** (guard D1) и повторно сверяются в `debit.paid`; расхождение суммы → `FAILED` + алерт, зачисление запрещено.
- **Отзыв согласия** (M8) переводит не завершённые списания по этому мандату в `FAILED` (`MANDATE_REVOKED`); новые списания (D1) отклоняются.
- Повторная доставка событий НСПК идемпотентна по `eventId` (AD-003, ADR-004).
- Сумма и реквизиты списания иммутабельны после `DEBIT_PENDING`.

## 3. Обработка повторных триггеров (идемпотентность)

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| `POST /v1/mandates/{id}/debits` | `Idempotency-Key` + `(mandateId, period)` | тот же `paymentId`; повтор за уже успешно списанный период → `409 PERIOD_ALREADY_DEBITED`, новое списание не создаётся |
| Событие НСПК `mandate.*` / `debit.*` | `eventId` (+ корреляция `mandateId`/`qrId`) | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу → алерт, состояние не меняется |
| Подтверждение АБС | `paymentId` | без второй проводки (маппинг `paymentId → absDocId`) |
| Сага возврата | `refundId` | без повторного списания/зачисления |

## 4. Сверка и восстановление

- Сверка с НСПК (ежечасная, ADR-004) расширяется на мандаты и списания: сверяются `ACTIVE`/`SUSPENDED` согласия и открытые списания (`CREATED`, `DEBIT_PENDING`, `PAID`).
- Расхождение «у НСПК согласие отозвано, у нас `ACTIVE`» → немедленный перевод в `REVOKED`, алерт, остановка списаний (AD-009).
- Расхождение «у НСПК подтверждено списание, у нас нет» → дозапрос статуса → D3; «у нас `PAID`, у НСПК нет» → стоп-сигнал, эскалация.
- Сверка с АБС (суточная, ADR-005) — без изменений.
- Мандат в `ACTIVE` с недоступным ОПКЦ — списания не инициируются (guard D1), мандат виден в отчёте незавершённых операций.

## 5. Согласованность с API ТСП

- Статусы мандата наружу: `CREATED`, `PENDING_PAYER`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `REJECTED`, `EXPIRED`.
- Статусы списания наружу: через ресурс `Debit` (`DEBIT_PENDING`, `PAID`, `CREDITED`, `COMPLETED`, `FAILED`, `EXPIRED`, `REFUNDED`) + существующие вебхуки `debit.*`.
- В `Payment` добавляются **опциональные** поля `origin` и `mandateId`; существующий enum `Payment.status` (v0.1) не изменяется — статусы `DEBIT_PENDING` отдаются в ресурсе `Debit` (см. `docs/contracts/tsp-api.md` §6, совместимость).
