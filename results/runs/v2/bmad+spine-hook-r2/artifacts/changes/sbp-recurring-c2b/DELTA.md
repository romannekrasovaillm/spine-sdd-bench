# Дельта: sbp-recurring-c2b

- Route: **Critical** (значимость 7/15; дельты недостаточно — полный Solutioning в `docs/solutioning-recurring-c2b.md`)
- Created: 2026-09-28
- Пакет: ADR-008, ADR-009, `docs/solutioning-recurring-c2b.md`, `docs/nfr-recurring-c2b.md`, `docs/spec/subscription-lifecycle.md`, `docs/contracts/tsp-api-recurring-c2b.md`, `openapi/tsp-api.yaml` (v0.2.0)

## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика (подписки СБП): сейчас каждый платёж требует QR и действия клиента. Нужны длящееся согласие плательщика (мандат), планировщик периодических списаний и защита от списания без согласия и двойного списания за период — поверх принятого решения о разовом C2B-приёме, не ломая его.

## ADDED

- When ТСП отправляет `POST /v1/mandates` с валидным `Idempotency-Key`, the шлюз shall создать заявку на мандат в статусе `PENDING_CONSENT` и вернуть `mandateId` (p95 < 500 мс).
- When ОПКЦ принимает заявку на мандат, the шлюз shall перевести мандат в `PENDING_OPKC` до получения подтверждения (списания запрещены).
- When банк плательщика подтверждает согласие (событие `mandate.activated`), the шлюз shall перевести мандат в `ACTIVE` в одной локальной транзакции с записью outbox и аудита (AD-002).
- When шлюз инициирует плановое списание, the шлюз shall проверить статус мандата (локально и, в целевом режиме, live-запросом `getMandateStatus`) и не создавать списание вне `ACTIVE`/лимитов.
- When наступает `scheduledAt` для мандата `ACTIVE`, the планировщик shall создать плановое списание с ключом идемпотентности (`mandateId`, `periodKey`) с лагом p95 ≤ 5 мин.
- When планировщик повторно обрабатывает период, для которого списание уже создано (в т.ч. второй нодой), the шлюз shall не создавать второй платёж и вернуть существующий (расширение AD-003).
- When плановое списание подтверждено НСПК, the шлюз shall зачислить средства только из состояния `PAID` (AD-005).
- When приходит событие `mandate.revoked`, the шлюз shall перевести мандат в `REVOKED` и заблокировать новые списания за ≤ 60 с (AD-009).
- When списание инициируется при мандате не в `ACTIVE`, истёкшем или с превышением `maxAmountPerCharge`/`maxAmountPerPeriod`, the шлюз shall отклонить списание без движения денег (AD-009).
- When ТСП запрашивает `GET /v1/mandates/{mandateId}`, the шлюз shall вернуть статус и параметры мандата (p95 < 300 мс).
- When шлюз доставляет событие `mandate.*`, the шлюз shall подписать его HMAC и обеспечить дедупликацию по `X-SBP-Event-Id` (at-least-once, ADR-004).
- When ядро вызывает рекуррентные методы адаптера ОПКЦ, the адаптер shall обеспечить идемпотентность по `reference` (без дублей мандата/списания в ОПКЦ, AD-008).

## MODIFIED

- **AD-002 (spine)** — единый источник истины расширен: было «статус платежа», стало «статус платежа + мандат + плановое списание» (ADR-008). Причина: мандат — длящееся состояние, списания обязаны меняться согласованно с ним.
- **AD-003 (spine)** — идемпотентность расширена: добавлен ключ планового списания (`mandateId`, `periodKey`) и `consentRef` для согласия. Причина: защита от двойного списания за период.
- **Семантика `QR_ISSUED`** (`docs/spec/state-machine.md`) — было «QR получен, ожидается оплата», стало также «предъявлено банку плательщика» для `origin=recurring`. Набор состояний не изменён; обратная совместимость сохраняется.
- **API ТСП** (`docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`) — было v0.1.0, стало v0.2.0: добавлены опциональные поля `origin`/`mandateId`/`periodKey` и пути `/v1/mandates*`. Аддитивно; `contract_diff` v0.1→v0.2: breaking 0.
- **Контракт адаптера ОПКЦ** (`docs/contracts/opkc-adapter.md`) — добавлены методы `registerMandate`/`getMandateStatus`/`createRecurringDebit`/`cancelMandate`/`getMandateReconciliationReport` и события `mandate.*`.
- **`docs/spec/state-machine.md`** — добавлены обязательные секции «Проблема», «Критерии приёмки», «Риски» (сенсор `required_sections`) и ссылка на рекуррентный поток.
- **Deferred (spine)** — диспуты/претензии: для рекуррентных списаний периметр должен быть определён до боевого включения (причина: рост риска несанкционированных списаний).
- **`docs/nfr.md`** — не изменяется; новые цели вынесены в `docs/nfr-recurring-c2b.md`.

## План отката

1. **До боевой эксплуатации**: откат = не включать; рекуррентный поток за фиче-флагом, по умолчанию выключен для всех ТСП.
2. **После включения**: административная операция **stop-new** (глобальный фиче-флаг приёма списаний + флаг на ТСП) немедленно прекращает новые списания — **массово, без поштучных `revoke`**; начатые операции доводятся существующим контуром; разовый C2B-приём не затрагивается. Массовая заморозка мандатов — той же административной операцией (владелец — дежурный платёжный SRE); поштучный `POST /v1/mandates/{mandateId}/revoke` — для отдельных ТСП.
3. **Сигналы отката**: любое несанкционированное списание; двойное списание за период; отзыв, не заблокировавший списание.
4. **Владелец решения**: дежурный платёжный SRE совместно с архитектором; решение фиксируется в аудит-логе.
5. **Критерий успешного отката**: новых списаний — ноль; мандаты в терминальном/замороженном статусе; сверка с банком плательщика без расхождений; разовый приём работает.
6. Данные обратно не мигрируются: мандаты и история списаний остаются в БД шлюза для аудита (ADR-009 — юридические факты).

## Критерии приёмки

- [ ] Мандат не становится `ACTIVE` без подтверждения ОПКЦ; из `PENDING_CONSENT` списание невозможно.
- [ ] Списание **не инициируется** при `SUSPENDED`/`REVOKED`/`EXPIRED`/истёкшем `validTo` или превышении лимита; отклонение до `PAID` денег не двигает.
- [ ] Отзыв после инициации, но до `PAID` → предъявление закрыто, денег не двинуто; отзыв после `PAID` → списание доведено до `COMPLETED`, возврат (если выбран политикой) — существующей сагой.
- [ ] Превышение `maxAmountPerCharge`/`maxAmountPerPeriod` отклонено без движения денег; параллельные ручные списания не превышают лимит периода (тест на гонку).
- [ ] Повтор списания за тот же `(mandateId, periodKey)` (включая вторую ноду) → ровно один платёж и одно зачисление.
- [ ] Повторная нотификация ОПКЦ с тем же `eventId` не меняет состояние.
- [ ] После `mandate.revoked` — ноль новых списаний.
- [ ] Зачисление по плановому списанию недостижимо из состояний до `PAID` (AD-005).
- [ ] Существующий потребитель API v0.1 работает: `contract_diff` v0.1→v0.2 без breaking changes.
- [ ] Каждый переход мандата и каждое списание — в неизменяемом аудит-логе.
- [ ] NFR `docs/nfr-recurring-c2b.md` достигнуты на нагрузочном стенде (лаг планировщика, throughput, латентности).
