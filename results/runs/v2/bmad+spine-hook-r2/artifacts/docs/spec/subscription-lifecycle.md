# Подписки СБП — жизненный цикл мандата и планового списания

- Status: Draft (для ревью на гейте A1 изменения `sbp-recurring-c2b`)
- Owner: solution-architect (платёжный контур)
- Related: ADR-002, ADR-008, ADR-009, AD-002, AD-003, AD-005, AD-009
- Дополняет: `docs/spec/state-machine.md` (статусная машина платежа не изменяется; плановое списание — платёж с `origin=recurring`).

Единый источник истины — БД шлюза (AD-002). Каждый переход мандата — атомарная транзакция «смена статуса + запись в outbox + аудит-лог». Повторные триггеры идемпотентны (AD-003).

## Проблема

Рекуррентное C2B-списание требует длящегося согласия плательщика (мандата), которое живёт годами и может быть отозвано в любой момент в банке плательщика. Без явной модели мандата и правил его проверки возникают списания без согласия, двойные списания за период и списания после отзыва. Спецификация фиксирует состояния мандата и планового списания, разрешённые переходы и запреты, чтобы исполнители не переизобрели правила согласованности.

## 1. Сущности

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| **Мандат** | Подтверждённое согласие плательщика на рекуррентные списания в пользу ТСП | `mandateId`, `tspId`, `payerRef` (токен), `consentRef` (подтверждение ОПКЦ), `currency`, `maxAmountPerCharge`, `maxAmountPerPeriod`, `period` (`MONTH`/`WEEK`/`CUSTOM`), `validFrom`, `validTo`, `status` |
| **Плановое списание** | Одно списание в рамках мандата; является платежом статусной машины | `chargeId`, `mandateId`, `periodKey`, `amount`, `paymentId`, `scheduledAt`, `origin=recurring` |

Формат `periodKey` (однозначно задаёт период и ключ идемпотентности):

- `period=MONTH` → `YYYY-MM` (напр. `2026-09`);
- `period=WEEK` → `YYYY-Www` (ISO-неделя, напр. `2026-W40`);
- `period=CUSTOM` → `periodKey` задаёт ТСП явно (строка ≤ 64 символов), окно периода определяется мандатом (`periodLengthDays`).

Для любого планового **и** ручного списания `periodKey` обязателен: он одновременно ключ идемпотентности и знаменатель лимита `maxAmountPerPeriod`.

## 2. Статусная модель мандата

| Состояние | Смысл | Списания разрешены |
|---|---|---|
| `PENDING_CONSENT` | Заявка создана, ждём подтверждения банка плательщика | нет |
| `PENDING_OPKC` | ОПКЦ принял заявку, регистрация в процессе | нет |
| `ACTIVE` | Согласие подтверждено и действует | **да** (в пределах лимитов и срока) |
| `SUSPENDED` | Приостановлен **внутренней административной операцией** (антифрод/оператор, 4-eyes); в API ТСП v0.2 не выставляется | нет |
| `REVOKED` | Отозван плательщиком | нет |
| `EXPIRED` | Истёк `validTo` | нет |
| `REJECTED` | Отклонён банком плательщика/ОПКЦ | нет |

Переходы: `PENDING_CONSENT → PENDING_OPKC → ACTIVE`; `PENDING_* → REJECTED`; `ACTIVE → SUSPENDED ⇄ ACTIVE`; `ACTIVE → REVOKED | EXPIRED`; `SUSPENDED → REVOKED | EXPIRED`. Терминальные: `REVOKED`, `EXPIRED`, `REJECTED` — переходов из них нет.

## 3. Статусная модель планового списания

Плановое списание использует канонические состояния платежа (ADR-002) с признаком `origin=recurring`:

```
CREATED ──► QR_ISSUED ──► PAID ──► CREDITED ──► COMPLETED
   │            │            │
   ▼            ▼            ▼
 FAILED      EXPIRED      FAILED
```

Для `origin=recurring` состояние `QR_ISSUED` означает «списание предъявлено банку плательщика, ожидается подтверждение» (QR не создаётся). Техническое подсостояние `ABS_PENDING` (см. `state-machine.md`) применяется без изменений.

## 4. Запрещённые переходы (инварианты)

- **Списание не инициируется, если мандат не в `ACTIVE`,** истёк `validTo` или превышены лимиты (AD-009). Проверка выполняется **на инициации** списания по актуальному статусу мандата (см. §6 о live-проверке).
- **Сумма списания не превышает `maxAmountPerCharge`**; сумма списаний за период не превышает `maxAmountPerPeriod` (AD-009) — проверяется атомарно с созданием списания (§5).
- **Одно плановое списание на `(mandateId, periodKey)`**: повтор не создаёт второй платёж (расширение AD-003).
- Зачисление по списанию возможно **только из `PAID`** (AD-005 не изменяется).
- **Поведение при отзыве, гонящемся со списанием** (граница необратимости — момент `PAID`, а не момент отзыва):
  - отзыв до инициации → списание не создаётся (новых нет);
  - отзыв **после инициации, но до `PAID`** → предъявление закрывается (`FAILED`/`EXPIRED`); банк плательщика списание не подтвердил, деньги не двинуты;
  - отзыв **после `PAID`** → `PAID` необратим, деньги двинуты; списание доводится до `CREDITED`/`COMPLETED` (AD-005), а возврат при необходимости выполняется существующей сагой возврата из `COMPLETED` (ADR-005; переходы T11/T12 в `state-machine.md`), не «откатом» статуса.
- После `REVOKED`/`EXPIRED`/`SUSPENDED` новые списания недостижимы.

## 5. Идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| Создание заявки на мандат (API ТСП) | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| Подтверждение/отзыв мандата (ОПКЦ) | `eventId` + `mandateId` | обработанный `eventId` игнорируется; повтор по завершённому переходу — алерт, состояние не меняется |
| Инициация планового списания | `(mandateId, periodKey)` | возврат существующего `paymentId`, второй платёж не создаётся |
| Ручное списание ТСП под мандатом | `Idempotency-Key` ТСП + обязательный `periodKey` | возврат того же `paymentId`; лимит периода проверяется атомарно с созданием |

Лимит `maxAmountPerPeriod` проверяется **атомарно** с созданием списания (единая транзакция с учётом уже созданных за тот же `mandateId`+`periodKey`), поэтому параллельные ручные списания не могут суммарно превысить лимит; уникальный индекс `(mandateId, periodKey)` дополнительно исключает дубль планового списания.

## 6. Сверка и восстановление

- **Перед инициацией списания** шлюз использует актуальный локальный статус мандата; чтобы гарантировать «ноль списаний после отзыва» при потере события, целевой режим — live-проверка статуса мандата у ОПКЦ (`getMandateStatus`) в рамках регламента сверки `[ТРЕБУЕТ ПРОВЕРКИ]` (стоимость/частота согласуются с регламентом НСПК).
- Открытые мандаты (`ACTIVE`) сверяются с ОПКЦ периодически (целевой регламент — ежедневно, при инциденте — по запросу): расхождение «отозван у плательщика, у нас `ACTIVE`» — стоп-сигнал, немедленная блокировка списаний по мандату, эскалация.
- Открытые плановые списания (`QR_ISSUED`, `PAID`, `ABS_PENDING`) — в общей сверке платежей (ADR-004).
- Пропущенное плановое списание (мандат `ACTIVE`, списания за период нет) — видно в отчёте незавершённых операций планировщика; восстановление — догоняющий прогон (catch-up) в пределах окна `catch_up_horizon` (по умолчанию — один период). В пределах окна точность восстановления — 100 %; простой дольше окна фиксируется как инцидент с ручным разбором (см. `docs/nfr-recurring-c2b.md`).

## 7. Согласованность с API ТСП

Маппинг наружу: статусы мандата выставляются в `Mandate.status` без технических подсостояний; статус списания — через `GET /v1/payments/{paymentId}` с полями `origin`, `mandateId`, `periodKey`. Имена существующих состояний платежа не меняются — обратная совместимость потребителей v0.1 сохраняется.

## Критерии приёмки

- Мандат не становится `ACTIVE` без подтверждения ОПКЦ; из `PENDING_CONSENT` списание невозможно (негативный тест).
- Списание **не инициируется** при `SUSPENDED`/`REVOKED`/`EXPIRED`/истёкшем `validTo` или превышении лимита (негативный тест на каждый случай); отклонение до `PAID` денег не двигает.
- Отзыв после инициации, но до `PAID` → предъявление закрыто (`FAILED`/`EXPIRED`), денег не двинуто; отзыв после `PAID` → списание доводится до `COMPLETED`, возврат — существующей сагой (тест на оба случая).
- Повторная инициация списания с тем же `(mandateId, periodKey)` (в т.ч. на второй ноде планировщика) даёт ровно один платёж и одно зачисление.
- Сумма параллельных ручных списаний за период не превышает `maxAmountPerPeriod` (тест на гонку).
- После `mandate.revoked` число новых списаний равно нулю.
- Зачисление по плановому списанию невозможно из состояний до `PAID` (наследуется от AD-005).
- Все события жизненного цикла мандата и списаний присутствуют в аудит-логе; события ОПКЦ дедуплицированы по `eventId`.

## Риски

- **Протокольная неопределённость НСПК**: механизм рекуррентного C2B может отличаться от принятой модели мандата → пересмотр ADR-008/009 после получения документации НСПК (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`).
- **Задержка/потеря отзыва**: расхождение локального статуса с банком плательщика → периодическая сверка мандатов и стоп-сигнал (п. 6).
- **Долгоживущее состояние и ПДн**: рост объёма и срока хранения мандатов → ретенция, токенизация, аудит (ADR-009).
- **Споры/претензии**: периметр диспутов по рекуррентным списаниям в принятом решении отложен → требуется отдельное решение до боевого включения (см. `docs/solutioning-recurring-c2b.md`, §«На решение человека»).
- **Планировщик как точка отказа**: остановка/дубли при отказе ноды → идемпотентность по `(mandateId, periodKey)` и catch-up.
