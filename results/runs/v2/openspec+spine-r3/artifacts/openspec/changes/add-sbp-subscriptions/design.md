# Design

## Context

Мотивация — в `proposal.md`. Принятая архитектура — `ARCHITECTURE-SPINE.md` (AD-001…AD-008), `docs/solutioning.md`, статусная машина `docs/spec/state-machine.md`, контракт ТСП `docs/contracts/tsp-api.md` + `openapi/tsp-api.yaml` v0.1.0, внутренний контракт адаптера ОПКЦ `docs/contracts/opkc-adapter.md`, NFR `docs/nfr.md`.

Что формирует подход:
- **At-least-once** на канале НСПК: повторные нотификации/события — норма (ADR-002, ADR-004).
- **AD-005**: зачисление только из подтверждённого статуса — распространяется и на списания по согласию.
- **AD-008**: ядро контрактно-независимо от транспорта; реальный протокол НСПК по подпискам — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Рекуррентное списание — финансово значимая операция без действия плательщика в момент списания, поэтому требования к идемпотентности и отзыву жёстче, чем у разового платежа.
- Маршрут изменения — **Critical** (score 8), наследует критичность initiative.

## Goals / Non-Goals

**Goals:**
- Ввести согласие на рекуррентные списания как отдельный агрегат с единым источником истины и предсказуемым жизненным циклом.
- Переиспользовать существующую статусную машину, outbox и дисциплину идемпотентности — не вводить второй финансовый контур.
- Гарантировать отсутствие двойных списаний и своевременную остановку списаний при отзыве.
- Расширить контракт ТСП аддитивно, без ломки существующих потребителей.
- Дать измеримые NFR, критерии приёмки и план отката.

**Non-Goals:**
- Не перепроектируется приём по QR/ссылке и статусная модель разового платежа.
- Не реализуется реальный протокол НСПК по подпискам (внешний вход; адаптер нормализует).
- Не вводятся C2C, выплаты B2C/B2B, диспуты (вне scope по-прежнему).
- Не выбираются коммерческие параметры (тарифы, лимиты) — за бизнесом.
- Не строится отдельное BI/отчётность по подпискам (используем существующую отчётность + выписки ОПКЦ).

## Влияние на принятую архитектуру (инварианты)

| Инвариант | Статус | Что происходит |
|---|---|---|
| AD-001 Изоляция платёжного контура | **Без изменений** | Рекуррентный модуль и реестр согласий — внутри платёжного контура; прямые вызовы АБС/ОПКЦ мимо адаптеров запрещены как и раньше. |
| AD-002 Единый источник истины | **Расширяется** | Дисциплина «статус + outbox + аудит в одной транзакции» распространяется на второй агрегат — согласие. `Binds` дополняется: реестр согласий, таблица списаний. |
| AD-003 Идемпотентность | **Расширяется** | Добавляется ключ `(subscriptionId, periodKey)` для списаний; `Binds` дополняется согласиями и периодными списаниями. |
| AD-004 Единственный адаптер ОПКЦ | **Расширяется аддитивно** | Новые операции и события согласия/списания проходят через тот же адаптер; протокол НСПК по-прежнему знает только адаптер. |
| AD-005 Зачисление только из подтверждённого статуса | **Без изменений (усилено)** | Рекуррентное списание зачисляется только из `PAID`. Вводится явный запрет зачисления при отзыве без подтверждения. |
| AD-006 Trust-зоны и сегментация | **Без изменений** | Новые потоки остаются в существующих зонах; ключевой материал — СКЗИ/HSM. |
| AD-007 НПС/КИИ/ПДн | **Без изменений (расширяется объект аудита)** | Аудит распространяется на жизненный цикл согласия; согласие содержит ссылку на плательщика — минимизация ПДн. |
| AD-008 Стратегия реализации (гибрид) | **Без изменений** | Контрактная независимость ядра сохраняется; подписки — на стороне ядра, транспорт — у вендора. |
| **AD-009 (новый, Proposed)** | **Добавляется** | Согласие — второй агрегат с единым источником истины и той же дисциплиной атомарности/идемпотентности. |
| **AD-010 (новый, Proposed)** | **Добавляется** | Рекуррентное списание не ослабляет AD-005 и проходит антифрод на каждое списание; отзыв согласия блокирует новые списания. |

**Что НЕ меняется:** приём по QR/ссылке, статусная модель разового платежа, характер отказа АБС/ОПКЦ, trust-зоны, СКЗИ-требования, стратегия «гибрид».

**Оговорка о маршруте.** Триггер `security_boundary_change` заявлен как `false`: границы trust-зон не меняются. Если рассматривать снятие обязательного действия плательщика как изменение *границы авторизации*, триггер может быть поднят — это осознанное решение человека-архитектора (см. ADR-008, A3).

## Decisions

### D1. Топология: согласие и планировщик — модуль внутри платёжного контура

**Решение.** Реестр согласий и планировщик списаний — модуль внутри платёжного контура шлюза, использующий ту же БД шлюза и ту же дисциплину outbox/аудита. Инициация списания (пометка периода `periodKey` + создание платежа + outbox-событие) атомарна в одной локальной транзакции.

**Почему.** Инициация списания — финансово значимая операция; пометка периода (дедупликация) и создание платежа обязаны быть атомарны, иначе сбой между двумя хранилищами даёт двойное списание или потерянное списание. Единая БД устраняет эту вилку и сохраняет AD-001/AD-002. Альтернатива «отдельный сервис подписок» добавляет сагу для операции, где нужна атомарность.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Модуль в контуре (выбран)** | Атомарность дедуп+платёж; переиспользование outbox/статусной машины; нет cross-service саги | Ядро растёт; планировщик делить ресурсы с API |
| Отдельный сервис подписок со своей БД | Независимое масштабирование планировщика | Сага на финансовую операцию; окно двойного списания; два источника истины |
| Вендорский модуль подписок | Готовый функционал | Vendor lock-in на финансовую логику; сложнее аудит ЦБ |

**Обратимость.** `costly`: модуль можно выделить в сервис позже, когда нагрузка планировщика потребует отдельного масштабирования; границей выделения служит таблица списаний и её транзакционная семантика. Не `irreversible`.

### D2. Жизненный цикл согласия и семантика отзыва

**Решение.** Состояния: `PENDING → ACTIVE → {SUSPENDED, REVOKED, EXPIRED}`, терминальные `REJECTED`, `EXPIRED`, `REVOKED`. Отзыв: **немедленный stop-new** (новые списания блокируются в пределах целевого лага); для списаний «в полёте» — политика *cancel-if-possible*: списание, ещё не подтверждённое ОПКЦ, отменяется, если это допускает протокол; уже подтверждённое — завершается, а возврат выполняется по запросу ТСП. `SUSPENDED` обратим, `REVOKED`/`EXPIRED` — нет.

**Почему.** Право потребителя на отзыв и защита от нежелательных списаний требуют остановки новых списаний без задержки; при этом нельзя нарушать уже подтверждённые расчёты. Альтернатива «drain-in-flight» (дать всем списаниям «в полёте» завершиться) хуже защищает плательщика.

**Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.** Точная семантика отзыва и in-flight — по регламентам НСПК; политика утверждается на A3.

### D3. Идемпотентность списания: периодный ключ

**Решение.** Ключ идемпотентности списания — детерминированная пара `(subscriptionId, periodKey)` с уникальным ограничением на уровне хранилища; дополнительно действует `Idempotency-Key` API (ADR-003). Повторная инициация за тот же период возвращает существующее списание.

**Почему.** `Idempotency-Key` защищает от ретрая *одного и того же* запроса, но не от повторной инициации с новым ключом тем же периодом. Уникальность периода закрывает этот класс двойных списаний.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`(subscriptionId, periodKey)` + `Idempotency-Key` (выбран)** | Закрывает и ретраи, и повторную инициацию за период | Требует соглашения о формате периода |
| Только `Idempotency-Key` | Просто | Повторная инициация с новым ключом создаёт дубль |
| Суррогатный `debitId` от планировщика | Годится для автосписаний | Не защищает ручную инициацию ТСП |

**Формат `periodKey`** — `[ТРЕБУЕТ ПРОВЕРКИ]`, финализируется с протоколом НСПК на A1.

### D4. Переиспользование статусной машины и AD-005

**Решение.** Каждое списание материализуется как платёж в существующей статусной машине; «статус списания» — проекция статуса платежа (`debit.status` синхронизирован с `payment.status`), отдельной статусной машины списаний не вводим.

**Почему.** Один финансовый контур и один источник истины; AD-005 сохраняется без изменений. Альтернатива (своя машина списаний) создаёт второй источник истины и рассинхрон.

### D5. Наблюдаемость планировщика и периодные пики

**Решение.** Планировщик — один или несколько воркеров поверх той же БД; запуск по расписанию с нагрузочным сглаживанием (queue-based load leveling), конкурирующие потребители, bulkhead от общего пула (чтобы пик подписок не топил разовые платежи). Дедуп по `periodKey` — на уровне хранилища.

**Почему.** Периодные пики (начало расчётного периода) концентрируют нагрузку; без сглаживания — шторм на ОПКЦ/АБС. Альтернатива «cron на каждую подписку» даёт шторм и не масштабируется.

### D6. Антифрод на каждое списание

**Решение.** Каждое списание проходит антифрод/AML-проверку **до** регистрации в ОПКЦ; лимиты согласия (`maxAmount`, период, срок) — жёсткие проверки на входе. Отклонение антифрода не создаёт списание.

**Почему.** Плательщик не совершает действие в момент списания — контроль переносится на параметры согласия и на проверку каждого списания. Альтернатива (пост-проверка с возвратом) — поздно и дорого.

### D7. Контракт: аддитивное расширение

**Решение.** `openapi/tsp-api.yaml` → `0.2.0`: новые пути подписок/списаний, опциональные поля в `Payment` (`initiationType`, `subscriptionId`, `debitId`), новые вебхуки и коды ошибок. Обязательные поля существующих схем не меняются, ничего не удаляется.

**Проверка.** `contract_diff` (old = baseline v0.1.0, new = v0.2.0) — не должен показать ломающих изменений; `openapi_lint` — PASS.

**Внутренний контракт адаптера ОПКЦ** (аддитивно): `registerConsent`, `revokeConsent`, `createDebit`, `getDebitStatus`; события `consent.activated/revoked/expired`, `debit.confirmed/rejected`; идемпотентность по `reference` — обязательное требование RFP (как и для платежей).

## NFR (измеримые цели нового функционала)

Значения — **baseline**; финальные согласуются с бизнесом и регламентами НСПК. Проверка — на гейте A4/A5.

| # | Метрика | Цель (baseline) | Метод проверки |
|---|---|---|---|
| N1 | Активация согласия (подтверждение → `ACTIVE`) | p95 < 3 с (без учёта канала НСПК) | APM, процессная метрика |
| N2 | Инициация списания, приём API | p95 < 500 мс, p99 < 1 с | нагрузочный тест |
| N3 | Регистрация списания в ОПКЦ (`createDebit`) | p95 < 2 с | нагрузочный тест |
| N4 | Своевременность списания по расписанию (on-time) | ≥ 99,9 % в окне ±60 с | метрика планировщика |
| N5 | Пропускная способность (рекуррентные списания) | sustained 150 TPS | нагрузочный тест |
| N6 | Периодный пик (burst) | 1500 TPS в течение 5 мин без потерь и дублей | нагрузочный тест пика |
| N7 | Масштабируемость | ×2 без перепроектирования | load-test на удвоенной нагрузке |
| N8 | Лаг блокировки новых списаний при отзыве | p99 ≤ 5 с | интеграционный тест (отзыв → попытка списания) |
| N9 | Двойные списания (повторы, ретраи, гонка) | 0 | тест на повтор и на конкурентную инициацию |
| N10 | Доступность подписочного API | ≥ 99,95 % | SLO-отчёт |
| N11 | RPO / RTO | наследуются: RPO = 0, RTO ≤ 1 ч | DR-учения, сверка |
| N12 | Уведомление плательщика о предстоящем списании (если требуется) | 100 %, lead time ≥ 24 ч `[ТРЕБУЕТ ПРОВЕРКИ]` | сверка/тест |
| N13 | Антифрод-покрытие списаний | 100 % списаний | тест-кейсы |
| N14 | Аудит переходов согласия и списаний | 100 %, лог неизменяем | аудит, SIEM |

## Risks / Trade-offs

- **[Двойное списание из-за ошибки `periodKey`]** → уникальный индекс `(subscriptionId, periodKey)` + property-тест «повтор/гонка → одно списание»; алерт на дубли.
- **[Отзыв не гасит списание «в полёте»]** → политика cancel-if-possible + возврат подтверждённого; тест N8; runbook для ручного разбора.
- **[Периодный пик перегружает ОПКЦ/АБС]** → load leveling, конкурирующие потребители, bulkhead, дедуп; нагрузочный тест N6.
- **[Неизвестный протокол НСПК по подпискам]** → адаптер нормализует статусы; реализация транспорта — после получения документации (условие AD-008); `[ТРЕБУЕТ ПРОВЕРКИ]` — блокирующий внешний вход.
- **[ПДн плательщика в согласии]** → минимизация, шифрование в покое, маскирование в логах; ИБ-ревью на A4.
- **[Ослабление AD-005 «оптимизацией»]** → frozen-тест: зачисление недостижимо вне `PAID`, в т.ч. для списаний; fitness-правило.
- **[Рост ядра и связность модуля согласий]** → модульная граница (согласие/списания), readiness-гейт на выделение в сервис при N7-триггере.

## Migration Plan

1. **Walking skeleton на моках** (в русле `.arch-handoff/TASK.md`): согласие → активация → списание → зачисление → вебхук, плюс негативные сценарии (дубль периода, отзыв, лимит).
2. **Фиче-флаг**: глобальный и по-ТСП; по умолчанию выключено.
3. **Волны ТСП**: пилот (1–2 ТСП) → расширение; критерии входа волны — зелёные N1–N14 и отсутствие инцидентов двойных списаний.
4. **Rollback** — см. `tasks.md` и раздел ниже; обратимость ADR-008 `costly`, ADR-009 `reversible`.
5. **A4 evidence**: fitness-правила, тесты идемпотентности/отзыва, нагрузочные N5/N6, ИБ-аудит; A5 — SLO-отчёт и дрейф-проверка.

### План отката (сводно)

- **До боевой эксплуатации** — откат = не включать: всё обратимо, данные не мигрируются.
- **Kill-switch**: фиче-флаг «stop-new» (запрет создания согласий и новых списаний) без остановки обработки уже открытых операций.
- **Откат релиза** — rolling; БД шлюза остаётся источником истины; согласия сохраняются.
- **Сигналы отката**: N9 > 0 (двойное списание), лаг отзыва > целевого (N8), burn error budget, обход антифрода, инцидент ИБ — немедленный stop-new и разбор по runbook.
- **Владелец решения об откате**: дежурный + архитектор платёжного контура (эскалация на A3-владельца при отзыве функционала).
