# Spec Delta

## Purpose

Фиксирует внешний контракт СБП-шлюза для ТСП (мерчант-API) в части расширения под рекуррентные списания и инвариант обратной совместимости для уже подключённых потребителей.

## ADDED Requirements

### Requirement: Операции управления подписками

API SHALL предоставлять в версии `/v1` операции: создание подписки, запрос статуса подписки, отмену подписки со стороны ТСП, список списаний и инициацию списания. Все мутирующие операции SHALL требовать `Idempotency-Key`.

#### Scenario: Создание и запрос подписки

- **WHEN** ТСП вызывает `POST /v1/subscriptions` с `Idempotency-Key`, затем `GET /v1/subscriptions/{subscriptionId}`
- **THEN** API SHALL вернуть подписку с её статусом, согласованным с моделью согласия (`PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED`, `REJECTED`)

#### Scenario: Инициация списания

- **WHEN** ТСП вызывает `POST /v1/subscriptions/{subscriptionId}/debits` с `Idempotency-Key` и `periodKey`
- **THEN** API SHALL вернуть списание, связанное с платежом, и SHALL быть идемпотентным по паре `(subscriptionId, periodKey)`

#### Scenario: Отмена подписки ТСП

- **WHEN** ТСП вызывает `POST /v1/subscriptions/{subscriptionId}/cancel`
- **THEN** API SHALL прекратить новые списания по подписке и SHALL NOT удалять историю согласия и списаний

### Requirement: Обратная совместимость API

Расширение под подписки SHALL быть аддитивным. Существующие эндпоинты `/v1/payments`, их схемы и обязательные поля SHALL NOT изменяться ломающим образом; новые поля в существующих схемах SHALL быть опциональными.

#### Scenario: Существующий потребитель без изменений

- **WHEN** потребитель контракта v0.1 продолжает вызывать `POST /v1/payments` и `GET /v1/payments/{paymentId}`
- **THEN** семантика и обязательные поля ответа SHALL остаться совместимыми, а новые поля SHALL быть опциональными и безопасными для игнорирования

#### Scenario: Ломающее изменение запрещено в минорной версии

- **WHEN** требуется удалить или переименовать поле либо сделать новое поле обязательным в существующей схеме
- **THEN** изменение SHALL выполняться только в новой мажорной версии пути с периодом поддержки обеих версий не менее 6 месяцев

### Requirement: Единая модель ошибок и идемпотентность

API SHALL использовать `application/problem+json` (RFC 9457) с каноническими кодами. Повторный `POST` с тем же `Idempotency-Key` и телом SHALL возвращать существующий ресурс, а не ошибку.

#### Scenario: Идемпотентный повтор

- **WHEN** повторяется успешный `POST` с тем же `Idempotency-Key` и тем же телом
- **THEN** API SHALL вернуть тот же ресурс со статусом `200` или `201` без повторного действия

#### Scenario: Конфликт ключа идемпотентности

- **WHEN** тот же `Idempotency-Key` приходит с другим телом
- **THEN** API SHALL вернуть `409 IDEMPOTENCY_CONFLICT`

#### Scenario: Новые канонические коды ошибок

- **WHEN** списание невозможно по состоянию согласия или лимиту
- **THEN** API SHALL вернуть problem+json с одним из кодов `CONSENT_NOT_ACTIVE`, `CONSENT_LIMIT_EXCEEDED`, `SUBSCRIPTION_NOT_FOUND`, `DEBIT_NOT_ALLOWED`

### Requirement: Вебхуки жизненного цикла подписки

API SHALL доставлять события жизненного цикла подписки и списаний at-least-once, с подписью HMAC-SHA256 и идентификатором события для дедупликации (в соответствии с ADR-004).

#### Scenario: Доставка события подписки

- **WHEN** согласие активируется, отзывается или истекает либо списание завершается или отклоняется
- **THEN** шлюз SHALL доставить вебхук `subscription.activated` / `subscription.revoked` / `subscription.expired` / `debit.completed` / `debit.failed` с заголовками `X-SBP-Event-Id` и `X-SBP-Signature`, с ретраями и DLQ

#### Scenario: Идемпотентность потребителя вебхука

- **WHEN** ТСП получает повтор того же события (`X-SBP-Event-Id` уже обработан)
- **THEN** повторная обработка SHALL NOT приводить к двойному эффекту на стороне ТСП
