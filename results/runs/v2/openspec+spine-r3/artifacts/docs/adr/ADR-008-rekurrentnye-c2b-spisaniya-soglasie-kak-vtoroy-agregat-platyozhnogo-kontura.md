# ADR-008. Рекуррентные C2B-списания: согласие как второй агрегат платёжного контура

- Date: 2026-09-28
- Status: Proposed (ожидает человеческого решения A3)
- Owner: solution-architect (платёжный контур) + бизнес/CIO
- Модель-автор: qwen-code
- Related: ADR-001, ADR-002, ADR-003, ADR-005, ADR-007, ADR-009, AD-001, AD-002, AD-008

## Context

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят регулярные C2B-списания по согласию плательщика; в принятом решении (`docs/solutioning.md`, ADR-001…ADR-007) каждый платёж требует динамического QR и действия плательщика, что делает подписочные модели неприемлемыми. Рекуррентное списание — финансовая операция **без действия плательщика в момент списания**, поэтому требования к идемпотентности и остановке списаний жёстче, чем у разового платежа.

Силы и ограничения:
- Канал НСПК — at-least-once: повторные события и ретраи нормальны (ADR-002, ADR-004).
- AD-005: зачисление только из подтверждённого статуса — распространяется и на списания.
- AD-008: ядро контрактно-независимо от транспорта; реальный протокол НСПК по подпискам не раскрыт публично `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Маршрут изменения — Critical (score 8): новый компонент, новое хранилище данных, изменение контракта и модели согласованности, финансовое влияние, наследование критичности initiative.
- Ранее зафиксированное решение по стратегии реализации (ADR-007, A3 от 2026-08-15): ядро — собственная разработка, транспорт — сертифицированный вендорский адаптер.

Требуется решить, где живёт рекуррентный контур (согласие + списания) и какова модель согласия.

## A3 Decision (черновик — подписывает человек)

- **choice**: `in-core-module` — реестр согласий и списания — отдельный агрегат **внутри** платёжного контура шлюза, на БД шлюза, с той же дисциплиной outbox/аудита/идемпотентности; каждое списание материализуется как платёж существующей статусной машины.
- **rationale**: инициация списания требует атомарности «пометка периода (дедупликация) + создание платежа + outbox»; единая БД и транзакция устраняют окно двойного/потерянного списания, которое неизбежно при разделении на два сервиса. Решение сохраняет AD-001/AD-002/AD-005 и контрактную независимость ядра (AD-008), переиспользует уже принятые механизмы (outbox, дедупликация, сверка).
- **constraints**: (1) протокол НСПК по подпискам знает только адаптер ОПКЦ (AD-004); (2) зачисление списания — только из подтверждённого статуса (AD-005, усилено AD-010); (3) идемпотентность списания по `(subscriptionId, periodKey)` — см. ADR-009; (4) выделение модуля в отдельный сервис допускается только по триггеру нагрузки (см. Reversibility) и через отдельное ADR.
- **rejected options**: `separate-service` (сага на финансовую операцию, окно двойного списания, два источника истины) — отклонено; `vendor-module` (vendor lock-in на финансовую логику, усложнение аудита для ЦБ) — отклонено.
- **expiry**: пересмотр при (а) недостижимости целей N4/N7 без выделения планировщика в отдельный сервис; (б) изменении требований НСПК, делающих согласие неотделимым от транспорта. Плановая ревизия — через 12 месяцев боевой эксплуатации.
- **decided_by**: (пусто — подписывает человек-архитектор на гейте A3)

## Decision

1. **Согласие — отдельный агрегат** («второй агрегат» рядом с платежом) в БД шлюза: единый источник истины, жизненный цикл `PENDING → ACTIVE → {SUSPENDED, REVOKED, EXPIRED}` + терминальные `REJECTED`; переходы атомарны по дисциплине AD-002 (статус + outbox + аудит).
2. **Списание — платёж**, проведённый через существующую статусную машину (`docs/spec/state-machine.md`); отдельной статусной машины списаний не вводится. Формируется только из действующего согласия.
3. **Планировщик списаний** — один или несколько воркеров поверх той же БД, с нагрузочным сглаживанием и дедупликацией по `periodKey`.
4. **Транспорт** — новые операции согласия/списания проходят через единственный адаптер ОПКЦ (AD-004); внутренний контракт адаптера расширяется аддитивно.
5. **Внешний контракт** API ТСП расширяется аддитивно (v0.2): см. ADR-009 и `openapi/tsp-api.yaml`.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Модуль в платёжном контуре (выбран)** | Атомарность дедуп+платёж; переиспользование outbox/статусной машины/сверки; один источник истины; нет cross-service саги | Ядро растёт; планировщик делит ресурсы с API (снимается bulkhead/масштабированием воркеров) |
| Отдельный сервис подписок со своей БД | Независимое масштабирование планировщика; изоляция ресурсов | Сага на финансовую операцию; окно двойного списания при сбое между сервисами; два источника истины → сверка сложнее; дублирование outbox |
| Вендорский модуль подписок (в транспорте) | Готовый функционал, меньше разработки | Vendor lock-in на финансовую логику; согласие уходит из-под контроля банка; усложняется аудит ЦБ и кастомизация под АБС |

## Consequences

### Positive

- Один финансовый контур и один источник истины: списание и согласие консистентны без распределённой транзакции.
- Переиспользование проверенных механизмов (outbox, дедупликация, сверка, аудит) снижает риск и стоимость.
- Контрактная независимость ядра (AD-008) сохраняется: подписки не привязывают ядро к транспорту.
- Отзыв согласия реализуем как быстрое локальное решение (стоп новых списаний), а не как межсервисная координация.

### Negative

- Ядро усложняется: появляется второй агрегат и планировщик; нужны модульные границы и дисциплина, чтобы «подписки» не размыли платёжный код.
- Планировщик делит ресурсы БД с API — при росте будет нужен bulkhead и, возможно, выделение в отдельный сервис (дорогая, но не необратимая эволюция).
- Нагрузка на ОПКЦ/АБС становится неравномерной (периодные пики) — требуются сглаживание и лимиты.
- Согласие содержит ссылку на плательщика (ПДн) — расширяется периметр защиты персональных данных.

## Reversibility

**costly.** Модуль обратим: его можно выделить в отдельный сервис, не меняя внешние контракты (API ТСП и контракт адаптера), но потребуется перенос таблиц согласий/списаний и сохранение транзакционной семантики дедупликации. Не `irreversible`: данные и контракты сохраняются, обратной миграции финансовых данных не требуется.

Триггер пересмотра: недостижимость N4 (on-time) или N7 (×2) в границах модуля; решение о выделении — отдельным ADR с A3.
