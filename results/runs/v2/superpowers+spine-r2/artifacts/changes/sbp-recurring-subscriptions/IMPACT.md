## 2. Влияние на принятую архитектуру

### 2.1 Инварианты spine

| AD | Влияние | Что именно |
|---|---|---|
| AD-001 Изоляция контура | Сохраняется, расширяется Binds | Логика согласия и рекуррентных списаний — внутри шлюза |
| AD-002 Статусная машина + outbox | **Модифицируется** | Дисциплина «статус + outbox + аудит» распространяется на согласие |
| AD-003 Идемпотентность | **Модифицируется (усиливается)** | Ключ `(consentId, billingPeriod)`; окно хранения = срок жизни согласия |
| AD-004 Единственный адаптер ОПКЦ | Инвариант сохраняется, контракт расширяется | +операции/события согласий и рекуррентных списаний |
| AD-005 Зачисление только из PAID | **Сохраняется без изменений** | Рекуррентный платёж идёт тем же путём `PAID→CREDITED→COMPLETED` |
| AD-006 Trust-зоны/сегментация | Сохраняется | Новых зон и каналов нет; ПДн — в защищённой зоне |
| AD-007 НПС/КИИ/ПДн | **Усиливается** | Новый класс ПДн (согласие), новое право плательщика (отзыв), аудит согласий |
| AD-008 Гибрид [ADOPTED] | Сохраняется | Транспорт согласий — та же вендорская граница; протокол НСПК `[ТРЕБУЕТ ПРОВЕРКИ]` |
| **AD-009 (новый)** | Добавляется | Согласие — first-class; списание только по `ACTIVE` и в пределах лимитов |
| **AD-010 (новый)** | Добавляется | Отзыв fail-closed; идемпотентность цикла `(consentId, billingPeriod)` |

### 2.2 Что меняется

- **Данные**: +согласие (Consent) и его проекция; +связь Payment↔Consent; +ключи идемпотентности периода (уникальный индекс).
- **Статусная модель**: +автомат согласия `PENDING→ACTIVE→SUSPENDED→REVOKED`/`EXPIRED`; рекуррентный платёж — в существующем автомате, **без новых финансовых состояний** платежа.
- **API ТСП**: +`/v1/consents`, `/v1/consents/{consentId}`, `/v1/consents/{consentId}/revoke`; +опциональные `type`, `consentId`, `billingPeriod` (обратно совместимо, см. §4).
- **Контракт адаптера ОПКЦ**: +`registerConsent`, `getConsentStatus`, `revokeConsent`, `createRecurringDebit`, `getDebitStatus`; +события `consent.granted`, `consent.revoked`, `debit.paid`, `debit.rejected`.
- **NFR**: +бюджеты залпового биллинга, распространения отзыва, нулевых дублей (`NFR-DELTA.md`).
- **Сверка**: +сверка проекции согласий; +сверка рекуррентных списаний.
- **Эксплуатация/RFP**: +требования к вендору по согласиям и залповой нагрузке.

### 2.3 Что НЕ меняется (защита от расползания)

- Зачисление на счёт ТСП — только из `PAID` (AD-005); сага возвратов (ADR-005) остаётся прежней.
- Топология (ADR-001), trust-зоны (ADR-006), единственный адаптер ОПКЦ (AD-004), гибридная стратегия (ADR-007/AD-008) — без изменений.
- Разовые платежи (QR/ссылка): путь, контракт и поведение не меняются — версия 0.1.0 совместима.
- Идемпотентное зачисление в АБС по `paymentId` — без изменений.
- Никаких новых вызовов АБС «на списание» в контуре эквайера: списание инициируется в НСПК/банке плательщика, эквайер получает подтверждение `PAID` и по-прежнему только зачисляет.

## 3. Что выносится на человеческое решение (A3)

Полный машинно-читаемый пакет — `A3-DECISION.yaml`. Кратко:

1. **Инициатор цикла**: ТСП-драйвер (выбрано, ADR-009) против планировщика в шлюзе (отложено).
2. **Где авторитетный реестр согласий** (НСПК / банк плательщика / шлюз) — зависит от протокола НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`.
3. **Регуляторная модель прав плательщика**: обязательность предварительного уведомления перед списанием, форма согласия, лимиты по умолчанию, статус паузы.
4. **Коммерческая модель** подписок (тарифы/комиссии ТСП).
5. **Порог свежести проекции согласия** (предлагается 5 мин) и политика компенсации in-flight при отзыве.

Ни один из этих пунктов агент не вправе закрыть самостоятельно: это регуляторные/бизнес/внешне-протокольные вопросы.
