# DELTA — Подписки СБП (рекуррентные C2B-списания по согласию плательщика)

- Изменение: `sbp-recurring-subscriptions`
- База: принятое решение «Платёжный шлюз СБП (C2B-приём)» (коммит `9f7abb5`)
- Маршрут: **Critical** (`significance_score`: score 8)
- Статус: **proposed** (до ратификации A3)
- Защищённые файлы, изменяемые ТОЛЬКО этой дельтой (`delta guard`): `ARCHITECTURE-SPINE.md`, `.arch-handoff/CONSTRAINTS.yaml`.
  Прямая правка этих файлов вне дельты запрещена (модель 5.2).

## Why

ТСП просят рекуррентные списания по согласию плательщика. Решение оформлено тремя ADR: ADR-008 (модель согласия), ADR-009 (инициатор цикла), ADR-010 (идемпотентность/отзыв). Дельта фиксирует минимальные изменения инвариантов и контрактов; всё остальное (AD-001, AD-005…AD-008) сохраняется.

## ADDED — новые инварианты spine

### AD-009. Согласие плательщика — сущность с лимитами; списание только по `ACTIVE`

- Status: Proposed (ADR-008)
- **Binds**: БД шлюза (согласия), API ТСП, статусная машина платежа, адаптер ОПКЦ.
- **Prevents**: списание без действующего согласия или сверх лимитов; хранение лимитов и срока только «в договоре», а не в системе; расхождение представления согласия между ТСП и шлюзом.
- **Rule**: Рекуррентное списание создаётся только при согласии в статусе `ACTIVE` и в пределах `maxAmountPerDebit` / `maxAmountPerPeriod` / `maxDebitsPerPeriod`; изменение статуса согласия — атомарно (статус + outbox + аудит). Проверка (fitness): тест «списание по `REVOKED`/`EXPIRED`/`SUSPENDED` или сверх лимита отклоняется кодом `CONSENT_*`».

### AD-010. Отзыв согласия fail-closed; идемпотентность цикла списания

- Status: Proposed (ADR-010)
- **Binds**: вход ТСП (`Idempotency-Key` + `billingPeriod`), нотификации НСПК по согласиям (`eventId`), БД шлюза (ключи идемпотентности), статусная машина согласия.
- **Prevents**: двойное списание за один период; списание после отзыва согласия; потеря отзыва при сбое.
- **Rule**: на пару `(consentId, billingPeriod)` — не более одного списания (уникальный индекс; окно хранения ключа ≥ срока жизни согласия); после перехода согласия в `REVOKED` новые списания отклоняются (`CONSENT_REVOKED`), отзыв применяется fail-closed. Проверка (fitness): тесты «повтор запроса за период → один `paymentId`» и «списание после отзыва → отказ».

## MODIFIED — существующие блоки spine

### AD-002 — распространить дисциплину на согласие

- **Binds** (было): БД шлюза (состояние платежа), outbox, аудит-лог.
  **Binds** (станет): БД шлюза (состояние платежа **и состояние согласия**), outbox, аудит-лог.
- **Prevents** (было): расхождение «шлюз думает `PAID`, АБС не знает» без сверки; неатомарные обновления статуса.
  **Prevents** (станет): расхождение «шлюз думает `PAID`, АБС не знает» без сверки; неатомарные обновления статуса **платежа или согласия**.
- **Rule** (станет): Изменение финансового статуса платежа **или юридически значимого статуса согласия плательщика** и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера (ревью + fitness-тест на каждый переход).

### AD-003 — усилить идемпотентность циклом списания

- **Binds** (станет): вход ТСП (`Idempotency-Key` **и `(consentId, billingPeriod)` для рекуррентных списаний**), нотификации НСПК (`eventId`), вызовы АБС (`paymentId`/`refundId`).
- **Rule** (станет): Повторная доставка любого сообщения не изменяет уже завершённое состояние. **Рекуррентное списание идемпотентно по паре `(consentId, billingPeriod)`: повтор за тот же период не создаёт второго списания; окно хранения ключа — не менее срока жизни согласия.** Fitness: тесты «повторная нотификация/повторный запрос → состояние не меняется» и «повтор списания за период → один платёж».

### AD-004 — контракт расширяется, инвариант неизменен

- Инвариант AD-004 (протокол НСПК знает только адаптер ОПКЦ) **не меняется**.
- **MODIFIED** документ `docs/contracts/opkc-adapter.md`: +методы `registerConsent`, `getConsentStatus`, `revokeConsent`, `createRecurringDebit`, `getDebitStatus`; +события `consent.granted`, `consent.revoked`, `debit.paid`, `debit.rejected`. Идемпотентность по `reference`, как в §5 контракта, обязательна и для новых операций.
