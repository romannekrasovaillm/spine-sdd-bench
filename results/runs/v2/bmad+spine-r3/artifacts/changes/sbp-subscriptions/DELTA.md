# Дельта: sbp-subscriptions

- Route: Critical
- Created: 2026-09-28
- Owner: solution-architect (платёжный контур)
- Status: Proposed (действует после A3 — человеческого решения по ADR-008)

## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика («подписки СБП») — серию списаний по расписанию без QR и без действия клиента в момент каждого платежа. Принятое решение описывает только разовые C2B-платежи, инициируемые действием плательщика. Дельта расширяет ядро шлюза доменом согласий/подписок, не меняя финансовую модель, статусную машину и границы контура.

Точный протокол рекуррентных операций НСПК (регистрация согласия, инициирование списания, предуведомление, отзыв) — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации по договору; дельта протокол-независима (AD-004, AD-008).

## Значимость и маршрут

Маршрут: **Critical**, значимость **10/15** (`significance_score`). Сработавшие триггеры: `security_boundary_change` (новая граница авторизации — списание без действия плательщика в момент операции), `criticality_or_exception` (платёжный контур), `financial_impact`, `api_contract_change`, `data_contract_change`, `cross_domain_integration`, `new_component`, `new_datastore`, `consistency_model_change`, `significant_nfr`.

Следствие: дельты недостаточно — требуется полный Solutioning (spine + ADR + измеримые NFR), обязательная человеческая точка A3, walking skeleton сквозного сценария на моках до массовой реализации, evidence-гейты A4/A5. Обоснование и детали — `changes/sbp-subscriptions/IMPACT.md`.

## ADDED

- **Инвариант AD-009 (spine, proposed). Рекуррентное списание — только по действующему согласию.** Binds: сервис согласий, планировщик списаний, адаптер ОПКЦ, аудит-лог. Prevents: списание без согласия; списание после отзыва/истечения; списание сверх лимита согласия. Rule: ни одно списание (`Payment` с `initiationType` = `SCHEDULED`/`MERCHANT`) не создаётся, если `consent.status != ACTIVE` в момент списания, сумма превышает лимит согласия либо `now` вне `[validFrom, validTo]`. Проверка: шаблон `consent-before-auto-action` + проверка лимита/срока.
- **Инвариант AD-010 (spine, proposed). Рекуррентное списание — это платёж.** Binds: статусная машина, планировщик, АБС-адаптер, нотификатор. Prevents: обход `PAID` при зачислении; отдельная «облегчённая» финансовая логика; двойное списание за один период. Rule: каждое списание создаёт `Payment` с уникальным ключом occurrence `subscriptionId + scheduledFor`; зачисление — только из `PAID`; повторный тик планировщика не создаёт второй платёж за тот же occurrence. Проверка: шаблон `idempotency-key` + property-тест «зачисление только из PAID».
- **Инвариант AD-011 (spine, proposed). Отзыв согласия блокирует будущее, не отменяет завершённое.** Binds: сервис согласий, планировщик, сага возврата, аудит. Prevents: списание после отзыва; «откат» уже зачисленного платежа вместо возврата. Rule: после `consent.revoked` новые списания по согласию не создаются (≤ 5 с); незавершённое списание обрабатывается по утверждённой политике (завершить/отклонить) с аудитом; зачисленное отменяется только сагой возврата (ADR-005). Проверка: шаблон `consent-before-auto-action` (свойство «отзыв останавливает следующее срабатывание»).
- **Требование SUB-1.** When ТСП вызывает `POST /v1/consents`, the шлюз shall зарегистрировать согласие (статус `PENDING`) и передать операцию в ОПКЦ через адаптер в пределах таймаута контракта.
- **Требование SUB-2.** When плательщик подтверждает согласие в своём банке (событие ОПКЦ), the шлюз shall перевести согласие в `ACTIVE` и уведомить ТСП событием `consent.activated`.
- **Требование SUB-3.** When ТСП вызывает `POST /v1/subscriptions` с действующим согласием, the шлюз shall создать подписку `ACTIVE` и назначить первое списание на `firstDebitAt`.
- **Требование SUB-4.** When наступает `scheduledFor` подписки, the планировщик shall создать не более одного списания с ключом occurrence `subscriptionId + scheduledFor`.
- **Требование SUB-5.** If сумма списания превышает лимит согласия или `now` вне срока действия согласия, then the шлюз shall отклонить списание без отправки в ОПКЦ и вернуть код `CONSENT_LIMIT_EXCEEDED`/`CONSENT_NOT_ACTIVE`.
- **Требование SUB-6.** When плательщик отзывает согласие (событие ОПКЦ `consent.revoked`), the шлюз shall за ≤ 5 с заблокировать все будущие списания по согласию и перевести зависимые подписки в `CANCELLED`.
- **Требование SUB-7.** When приходит подтверждение ОПКЦ об успешном списании, the шлюз shall выполнить зачисление только из статуса `PAID` и уведомить ТСП событием `subscription.debit.completed`.
- **Требование SUB-8 (аддитивность контракта).** When ТСП использует только существующие методы, the шлюз shall отвечать по неизменной схеме — новые поля, пути и типы событий необязательны и не влияют на разовые платежи.

## MODIFIED

- **AD-002 (spine):** Binds расширяется сущностями `Consent` и `Subscription`; те же правила атомарных переходов (статус + outbox + аудит) распространяются на согласия и подписки. Исходный Rule не меняется, добавляются новые сущности в область действия.
- **AD-003 (spine):** Binds расширяется ключами идемпотентности `consentId`, `subscriptionId`, `occurrenceKey` (тик планировщика). Rule дополняется: повторная доставка/повторный тик не изменяет завершённое состояние.
- **AD-004 (spine):** Rule дополняется: рекуррентные операции к ОПКЦ (регистрация согласия, инициирование списания, отзыв) выполняются только через единственный адаптер; ядро не обращается к НСПК напрямую.
- **AD-005 (spine):** Binds/Prevents дополняются явным указанием, что зачисление по рекуррентному списанию подчиняется тому же правилу «только из состояния `PAID`»; исходный Rule сохраняется дословно.
- **AD-007 (spine):** Rule дополняется: жизненный цикл согласия (выдача, изменение лимитов, отзыв) — в неизменяемом аудит-логе; ПДн плательщика минимизируются; правовое основание рекуррентного списания — согласие плательщика (161-ФЗ, 152-ФЗ).
- **`docs/spec/state-machine.md`:** добавляются автоматы `Consent` (`PENDING → ACTIVE → REVOKED | EXPIRED | REJECTED`) и `Subscription` (`ACTIVE → PAUSED → ACTIVE`, `ACTIVE/PAUSED → CANCELLED | EXPIRED`) и переход `CREATED → PAID` для рекуррентного платежа (guard «действующее согласие»); публичный enum статусов платежа не меняется.
- **`docs/contracts/tsp-api.md` и `openapi/tsp-api.yaml`:** аддитивно добавляются ресурсы `/v1/consents`, `/v1/subscriptions` (+ `pause`/`resume`/`cancel`/`debits`), схемы `Consent`/`Subscription`, опциональные поля платежа `subscriptionId`/`initiationType` и типы вебхук-событий `consent.*`, `subscription.debit.*`; версия контракта `0.1.0 → 0.2.0`. Ломающих изменений нет (проверено `contract_diff`).
- **`docs/nfr.md`:** добавляется раздел измеримых NFR рекуррентных списаний (точность планировщика, дедупликация occurrence, реакция на отзыв, масштаб, сверка согласий, аудит).
- **`.arch-handoff/CONSTRAINTS.yaml` (при apply, защищённый файл):** добавляются исполняемые правила `consent_before_autodebit` и `recurring_debit_idempotent` (шаблоны `consent-before-auto-action`, `idempotency-key`) и правило трассировки EARS-критериев. Фрагмент — `changes/sbp-subscriptions/CONSTRAINTS.delta.yaml`, вносится архитектором на этапе apply после применения шаблонов (сейчас в реестр не вносится, чтобы не ломать гейт отсутствующими файлами тестов).

## Предлагаемые fitness-правила (фрагмент для CONSTRAINTS.yaml)

Полный фрагмент — `changes/sbp-subscriptions/CONSTRAINTS.delta.yaml`. Ключевые:

- `consent_before_autodebit` — `command_succeeds`, error: повторная/автоматическая операция не создаётся без действующего согласия, отзыв блокирует следующее срабатывание (шаблон `consent-before-auto-action`).
- `recurring_debit_idempotent` — `command_succeeds`, error: два тика/доставки с одним `occurrenceKey` дают ровно один эффект (шаблон `idempotency-key`).
- `ears_acceptance_criteria` — `must_contain`, warn: критерии приёмки рекуррентного контура в EARS-форме.

## План отката

1. **До боевого включения** — откат = не включать: изменения аддитивны (новые ресурсы/поля/события), разовые платежи не затронуты; фиче-флаг `sbp_subscriptions_enabled` (глобально/по ТСП) выключен.
2. **После включения** — сигналы отката: двойные списания > 0; списание после отзыва > 0; пропущенные списания по расписанию; превышение SLA задержки дебетов; рост DLQ по рекуррентным событиям; отказы ОПКЦ по consent-операциям.
3. **Действия отката:** запрет новых согласий/подписок (stop-new) → приостановка автодебетов по флагу (подписки `PAUSED`, in-flight списания доводятся по политике) → rolling-откат релиза. Данные согласий не удаляются (правовые последствия 152-ФЗ/161-ФЗ); повторное включение — без миграции.
4. **Владелец решения об откате:** дежурная смена + архитектор платёжного контура; бизнес-риск прекращения подписок — владелец продукта. RTO обработки — в пределах NFR шлюза (≤ 1 ч).

## Критерии приёмки

- [ ] When план выполняется повторно с тем же `occurrenceKey`, the шлюз shall не создать второе списание (0 двойных списаний; тест на повторный тик/рестарт/повторную доставку).
- [ ] When согласие в статусе `REVOKED`/`EXPIRED`, the шлюз shall не создавать списания (негативный тест; 0 списаний по недействующему согласию).
- [ ] When сумма списания превышает лимит согласия, the шлюз shall отклонить операцию до отправки в ОПКЦ (`CONSENT_LIMIT_EXCEEDED`).
- [ ] When приходит подтверждение ОПКЦ, the шлюз shall зачислить средства только из статуса `PAID` (property-тест недостижимости зачисления из `CREATED`).
- [ ] When повторно доставлено событие ОПКЦ с тем же `eventId`, the шлюз shall не изменить завершённое состояние.
- [ ] Точность планировщика: отклонение старта списания от расписания ≤ 60 с для ≥ 99,9 % списаний; пропущенных списаний — 0.
- [ ] Реакция на отзыв: все будущие списания заблокированы ≤ 5 с; зачисленные не «откатываются» (только сага возврата).
- [ ] Совместимость: существующие методы `/v1/payments` отвечают по неизменной схеме (`contract_diff` — 0 ломающих изменений).
- [ ] Рекуррентные финансовые переходы и операции с согласием — 100 % в неизменяемом аудит-логе.
- [ ] Откат: выключение флага прекращает новые списания и не влияет на разовые платежи (критерий успешного отката).
