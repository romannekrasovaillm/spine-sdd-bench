## 1. Задача (statement)

Расширить ядро СБП-шлюза рекуррентными C2B-списаниями по согласию плательщика («СБП-подписки»): (1) ресурсы `/v1/consents` и `/v1/subscriptions` с идемпотентностью; (2) автоматы `Consent` (`PENDING→ACTIVE→REVOKED|EXPIRED|REJECTED`) и `Subscription` (`ACTIVE⇄PAUSED→CANCELLED|EXPIRED`) с транзакционным outbox и аудитом; (3) планировщик, создающий не более одного списания на `occurrenceKey = subscriptionId + scheduledFor`; (4) списание как `Payment` в существующей статусной машине (`CREATED→PAID→CREDITED→COMPLETED`, состояние `QR_ISSUED` не применяется); (5) аддитивное расширение контракта адаптера ОПКЦ рекуррентными операциями (регистрация согласия, инициирование списания, отзыв) — на моке, реальный протокол НСПК не реализуется (внешний вход); (6) зачисление по списанию — только из `PAID` (через существующий АБС-адаптер). Приоритет — доказать архитектуру сквозным сценарием на моках, а не полнотой продукта.

## 2. Epic-context (смысловое ядро, 800–1500 токенов)

**Цель.** ТСП (кино/ЖКХ/связь) получают серию списаний по расписанию без QR и без действия клиента в момент платежа. Новое — только *авторизация списания* (согласие) и *расписание*; финансовая машина (статусы, outbox, АБС-зачисление, возвраты, сверка, идемпотентность) уже есть и переиспользуется без изменений.

**Границы.** Согласия/подписки/планировщик живут в платёжном контуре шлюза. К ОПКЦ — только через единственный адаптер (внутренний контракт, AD-008). К АБС — только через адаптер АБС. Реальный протокол НСПК и его поля/тайминги — `[ТРЕБУЕТ ПРОВЕРКИ]`; реализация — против мока, контракт адаптера расширяется аддитивно.

**Стыки (что с чем не разойтись).**
- *Согласие → списание*: списание создаётся только при `consent.status == ACTIVE`, сумма ≤ `amountLimit`, `now ∈ [validFrom, validTo]`. Иначе — отказ до вызова ОПКЦ (`CONSENT_NOT_ACTIVE`/`CONSENT_LIMIT_EXCEEDED`).
- *Планировщик → платёж*: один период → максимум один `Payment` (уникальный `occurrenceKey`). Повторный тик/рестарт/повторная доставка не создают второй платёж.
- *Списание → зачисление*: `Payment` проходит `CREATED → PAID → CREDITED → COMPLETED`; зачисление в АБС — **только из `PAID`**; сага возврата — без изменений.
- *Отзыв → будущее/завершённое*: отзыв блокирует будущие списания (≤ 5 с) и переводит подписки в `CANCELLED`; уже зачисленное не «откатывается», а возвращается сагой.
- *Контракт ТСП*: только аддитивные изменения (новые пути/поля/события); существующие `/v1/payments` неизменны.

**Запреты.** Не менять публичный enum статуса платежа. Не обращаться к НСПК/АБС мимо адаптеров. Не зачислять вне `PAID`. Не удалять и не переименовывать поля/пути контракта. Не хранить ПДн плательщика сверх необходимого минимума. Любой конфликт с `ARCHITECTURE-SPINE.md`/ADR — остановка и эскалация, а не локальное решение.

**Критерий успеха.** Сквозной сценарий на моках (consent → subscription → плановое списание → PAID → зачисление → COMPLETED) плюс негативные сценарии: повтор тика/события (нет дубля), отзыв (нет будущих списаний), превышение лимита (отказ до ОПКЦ), попытка зачисления не из `PAID` (недостижимо).

## 3. Инварианты (передаются дословно; нарушение — блокер)

Наследуются из `ARCHITECTURE-SPINE.md` (Rule — дословно):

- **AD-001**: «Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза».
- **AD-002**: «Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции» (распространяется на `Consent`/`Subscription`).
- **AD-003**: «Повторная доставка любого сообщения не изменяет уже завершённое состояние» (ключи: `consentId`, `subscriptionId`, `occurrenceKey`).
- **AD-004**: «Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов».
- **AD-005**: «Вызов АБС на зачисление возможен только из состояния `PAID`».
- **AD-006**: trust-зоны и сегментация — без изменений.
- **AD-007**: «Каждый финансовый переход и административное действие — в неизменяемом аудит-логе» (+ жизненный цикл согласия).
- **AD-008**: «Ядро шлюза проектируется контрактно-независимым от транспорта».

Предлагаются дельтой (действуют после A3): **AD-009** (списание только по действующему согласию), **AD-010** (списание — это платёж; уникальный occurrence; зачисление из `PAID`), **AD-011** (отзыв блокирует будущее, не отменяет завершённое).

## 7. Контракт результата (headless JSON)

Финальный ответ исполнителя обязан завершаться JSON-объектом (после него — ни символа):

```json
{"status": "complete|partial|blocked", "assumptions": [], "open_questions": [], "conflicts_with_prior_decisions": []}
```

- `conflicts_with_prior_decisions` — расхождения с AD-* / ADR-008; сигнал эскалации к архитектору, не молчаливое отклонение.
- `blocked` — перечислить недостающие внешние входы (протокол НСПК, ответ вендора, правовая позиция).

## 8. Ограничения готовности
