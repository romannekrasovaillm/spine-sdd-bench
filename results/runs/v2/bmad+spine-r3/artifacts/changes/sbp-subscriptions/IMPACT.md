# Влияние изменения `sbp-subscriptions` на принятую архитектуру

- Route: **Critical** (значимость **10/15**)
- Owner: solution-architect (платёжный контур)
- Связано: `changes/sbp-subscriptions/DELTA.md`, `docs/adr/ADR-008-rekurrentnye-c2b-spisaniya-soglasie-platelshchika.md`, `ARCHITECTURE-SPINE.md`

## 1. Оценка значимости и маршрута

`significance_score` (10 сработавших триггеров из 15) → маршрут **Critical**:

| Триггер | Почему сработал |
|---|---|
| `security_boundary_change` | Новая граница авторизации: списание инициируется шлюзом/ТСП без действия плательщика в момент операции. Требует доказуемого согласия, лимитов и отзыва. |
| `criticality_or_exception` | Платёжный контур банка — критичный объект; регуляторные исключения (161-ФЗ/КИИ). |
| `financial_impact` | Ошибка ведёт к двойному списанию, списанию после отзыва — прямое финансовое последствие. |
| `api_contract_change` | Расширение контракта ТСП (новые ресурсы/поля/события). |
| `data_contract_change` | Новые сущности и события (согласие, подписка, списания). |
| `cross_domain_integration` | ТСП ↔ шлюз ↔ ОПКЦ ↔ банк плательщика ↔ АБС. |
| `new_component` | Сервис согласий/подписок и планировщик списаний. |
| `new_datastore` | Хранилище согласий/подписок. |
| `consistency_model_change` | Жизненный цикл согласия vs in-flight списание; отзыв во время списания. |
| `significant_nfr` | Новые измеримые NFR (точность планировщика, реакция на отзыв, масштаб). |

Вывод по маршруту: **дельты недостаточно**; требуется полный Solutioning (spine + ADR + NFR), обязательная человеческая точка **A3**, walking skeleton сквозного сценария (`consent → subscription → debit → credit`) на моках до массовой реализации и evidence-гейты A4/A5. Дельтой оформляется propose, живая истина (spine, CONSTRAINTS) обновляется на apply/archive после A3.

Контрольные точки для этого изменения:
- **A0 (fit)**: укладывается в существующий паттерн (выделенный шлюз, outbox, статусная машина) — да; нового паттерна не вводится.
- **A1 (impact)**: см. §2–§4.
- **A2 (solutioning trigger)**: порог задан (Critical) заранее, не «на глаз».
- **A3 (человеческое решение)**: см. §5 — обязательна до реализации транспорта рекуррентных операций.
- **A4 (conformance)**: fitness-правила (§4) + негативные тесты (дубль, отзыв, лимит, обход PAID).
- **A5 (drift)**: сверка согласий/списаний с ОПКЦ в проде, SLO через 30 дней.

## 2. Влияние на инварианты spine

| Инвариант | Что происходит | Характер |
|---|---|---|
| **AD-001** Изоляция платёжного контура | Согласия/подписки и планировщик живут в платёжном контуре; АБС и ОПКЦ — только через адаптеры. | **Усиливается** (новые сущности не расширяют путь к АБС/ОПКЦ) |
| **AD-002** Единый источник истины | Добавляются сущности `Consent` и `Subscription` с атомарными переходами (статус + outbox + аудит). | **Расширяется** (Binds += Consent, Subscription) |
| **AD-003** Идемпотентность | Новые ключи: `consentId`, `subscriptionId`, `occurrenceKey` (тик планировщика). | **Расширяется** (Binds += новые ключи) |
| **AD-004** Единственный адаптер ОПКЦ | Рекуррентные операции (регистрация согласия, списание, отзыв) — только через адаптер; планировщик не ходит в НСПК. | **Расширяется** (Rule += рекуррентные операции) |
| **AD-005** Зачисление только из `PAID` | Рекуррентное списание моделируется как платёж и подчиняется тому же правилу; обход невозможен. | **Не меняется по сути**, область действия явно расширена |
| **AD-006** Trust-зоны и сегментация | Новые сетевые зоны не появляются; ПДн плательщика — внутри платёжного контура. | **Не меняется** |
| **AD-007** НПС/КИИ/ПДн | Согласие — правовое основание списания; его жизненный цикл в неизменяемом аудите; минимизация ПДн. | **Расширяется** (Rule += согласие/аудит) |
| **AD-008** Стратегия гибрид [ADOPTED] | Транспорт рекуррентных операций — в вендорском адаптере; контрактная независимость ядра сохраняется. | **Не меняется**, но создаёт constraint на ADR-007 (см. §4) |
| **AD-009 (new)** Согласие до автодействия | Нет действующего согласия — нет списания (статус/лимит/срок). | **Добавляется** |
| **AD-010 (new)** Списание — это платёж | Уникальный `occurrenceKey`; зачисление только из `PAID`; повторный тик не создаёт второй платёж. | **Добавляется** |
| **AD-011 (new)** Отзыв блокирует будущее | Отзыв не отменяет завершённое; зачисленное — только сагой возврата. | **Добавляется** |

## 3. Что НЕ меняется

- Статусная машина **разовых** платежей и её публичный enum (`CREATED…REFUNDED`) — без изменений; `QR_ISSUED` не удаляется и не переиспользуется.
- Инвариант зачисления **только из `PAID`** (AD-005) и сага возвратов (ADR-005) — без изменений.
- Границы и trust-зоны (AD-006), требования к СКЗИ/ГОСТ (ADR-003/ADR-006) — без изменений.
- Контракт адаптера ОПКЦ как **единственная** зависимость ядра от транспорта (AD-008) — сохраняется; расширяется аддитивно новыми операциями/событиями.
- Механика outbox/дедупликации/сверки/DLQ (ADR-001/ADR-004) — переиспользуется без перепроектирования.
- Существующие потребители ТСП: разовые методы и поля — без изменений (совместимость доказана `contract_diff`).

## 4. Пробелы, риски и предлагаемые проверки

| # | Что | Тип | Митигация / проверка |
|---|---|---|---|
| R1 | Протокол рекуррентных операций НСПК неизвестен | внешний вход | Проектирование протокол-независимо (AD-004/AD-008); детали — `[ТРЕБУЕТ ПРОВЕРКИ]` до документации. |
| R2 | Вендор транспорта может не поддерживать рекуррентные операции | constraint ADR-007 | Подтвердить на RFI/RFP; при отсутствии — расширить scope RFP/пересмотреть вендора (решение A3, §5). |
| R3 | Двойное списание за период | финансы | AD-010 + правило `recurring_debit_idempotent` (шаблон `idempotency-key`). |
| R4 | Списание после отзыва | финансы | AD-009/AD-011 + правило `consent_before_autodebit` (шаблон `consent-before-auto-action`). |
| R5 | Пропуск/задержка плановых списаний | SLA/клиент | Мониторинг точности планировщика; NFR-порог ≤ 60 с / 0 пропусков; сверка. |
| R6 | Рост ПДн (реквизиты плательщика) | 152-ФЗ | Минимизация; шифрование; маскирование в логах (существующее правило + шаблон `no-pii-in-logs`); сроки хранения. |
| R7 | Регуляторный статус рекуррентных списаний | НПС/КИИ | Внешний вход (юр./ИБ); решение A3. |

Предлагаемые исполняемые правила (фрагмент — `CONSTRAINTS.delta.yaml`): `consent_before_autodebit`, `recurring_debit_idempotent`, `ears_acceptance_criteria`. Базовая линия реестра: **0 из 7** правил проверяют поведение — новые правила добавляют поведенческие проверки на AD-009/AD-010.

## 5. Что остаётся на решение человека-архитектора (A3)

Ни один из пунктов ниже не может быть решён агентом: нужны бизнес, юрист/ИБ и владелец внешнего контракта.

1. **Scope и приоритет первой волны.** Какие сегменты ТСП подключаем первыми (кино/ЖКХ/связь), и допускаются ли **внеплановые** списания по согласию помимо расписания (влияет на модель `Subscription` и лимиты).
2. **Вендор транспорта (ADR-007).** Подтверждает ли вендор поддержку рекуррентных операций НСПК; если нет — расширение scope RFP или пересмотр выбора вендора. Это меняет `constraints` принятого ADR-007, а не только реализацию.
3. **Предуведомление плательщика.** Обязательно ли оно по правилам НСПК, за какой срок, кто инициирует (банк плательщика/шлюз/ТСП). Внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`; влияет на UX, NFR и юридическую модель.
4. **Политика in-flight при отзыве.** Списание, уже отправленное в ОПКЦ до отзыва: доводить до конца или отклонять; кто несёт риск. Требует продукта и юриста.
5. **Лимиты и тарифы.** Максимум на одно списание, суммарный/периодический лимит, комиссия ТСП, дефолтное расписание. Бизнес-решение.
6. **Правовое основание и ПДн.** Формулировка согласия, состав хранимых данных плательщика, сроки хранения, порядок отзыва (161-ФЗ, 152-ФЗ). Юрист/ИБ.
7. **Гранулярность согласия.** Согласие на ТСП, на конкретный план/услугу или на связку ТСП+назначение; может ли плательщик приостановить подписку из приложения своего банка (возможности НСПК).
8. **Регуляторная классификация.** Меняет ли рекуррентность категорию объекта КИИ и состав мер ФСТЭК; нужны ли отдельные тестовые испытания НСПК. ИБ/КИИ.
9. **Бизнес-риск отката.** При откате согласия/подписки прекращаются — кто и как уведомляет плательщиков и ТСП, кто владелец решения (владелец продукта).

## 6. Внешние входы (блокируют финализацию, не блокируют A3-проектирование)

- Документация НСПК по рекуррентным операциям (поля, тайминги, статусы, предуведомление, отзыв) — по договору.
- Ответ вендора транспорта о поддержке рекуррентных операций.
- Правовая позиция юристов и ИБ по согласию/ПДн.
- Регламенты НСПК по лимитам и срокам.
