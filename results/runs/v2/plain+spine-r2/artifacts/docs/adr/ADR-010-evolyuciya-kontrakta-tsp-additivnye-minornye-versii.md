# ADR-010. Эволюция контракта API ТСП: аддитивные минорные версии без поломки потребителей

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + владелец API ТСП
- Модель-автор: qwen-code
- Related: ADR-008, AD-010, ADR-002

## Context

Контракт API ТСП (`docs/contracts/tsp-api.md`, `openapi/tsp-api.yaml`) уже опубликован как v0.1 draft, но на нём будут строиться интеграции ТСП (кассы, e-commerce, ЖКХ, связь). Подписки добавляют новые сущности (мандат, списание) и события вебхуков.

Существующий контракт §6 уже фиксирует правило: ломающие изменения — только в `/v2` с периодом поддержки ≥ 6 мес; добавление опциональных полей — обратно совместимо. Нужно решить, как именно встроить подписки: ломать ли v1, заводить ли v2, или наращивать v1.

Силы: (а) нельзя ломать существующих потребителей разового C2B-приёма — у них нет подписок и они не должны даже заметить изменение; (б) мандат и списание — это новые ресурсы, а не изменение старых; (в) списание — вид платежа, значит его статус можно читать существующим `GET /v1/payments/{paymentId}`; (г) нужна простая и доказуемая стратегия версионирования для аудита и CI.

## Decision

1. **Аддитивная эволюция v1**: подписки встраиваются в `/v1` **новыми путями и новыми опциональными полями**; `info.version` повышается минорно (0.1.0 → 0.2.0).
2. **Ничего существующего не удаляется и не сужается**: пути `/v1/payments`, `/v1/payments/{paymentId}` и семантика полей сохраняются; **enum `Payment.status` не расширяется и не меняется**; новые обязательные поля в существующие запросы не добавляются.
3. **Новые ресурсы**: `POST /v1/mandates`, `GET /v1/mandates/{mandateId}`, `POST /v1/mandates/{mandateId}/revoke`, `POST /v1/mandates/{mandateId}/suspend`, `POST /v1/mandates/{mandateId}/resume`, `POST|GET /v1/mandates/{mandateId}/debits`. Новые схемы: `Mandate`, `MandateRequest`, `DebitRequest`, `Problem`.
4. **Списание читается существующим статусным методом**: `GET /v1/payments/{paymentId}` (списание — вид платежа, ADR-008); `Payment` расширяется **опциональными** полями `paymentType`, `mandateId`, `billingPeriod`. Новые события вебхуков **только мандатные** (`mandate.pending/activated/rejected/suspended/resumed/revoked/expired`); по списаниям ТСП получает **существующие** `payment.completed`/`payment.failed` — типы событий по платежам не добавляются и не переименовываются. Транспортные события ОПКЦ `debit.paid`/`debit.rejected` — внутренние (ядро↔адаптер) и наружу ТСП не выставляются.
5. **Доказательство неразрушаемости — механическое**: `contract_diff` v0.1→v0.2 не должен находить breaking changes; fitness-правила (`changes/sbp-subscriptions/DELTA.md` §Fitness) сторожат сохранность существующих путей и enum.
6. **Внутренний контракт с вендором** (`opkc-adapter.md`) расширяется так же аддитивно: новые методы (`registerMandate`, `getMandateStatus`, `revokeMandate`, `suspendMandate`, `resumeMandate`, `createRecurringDebit`, `getDebitStatus`, возврат по `debitRef`) и события (`mandate.*`, `debit.*`); существующие сигнатуры не меняются. Для вендора это обязательное требование RFP (дельта к `docs/rfp/vendor-rfp.md`).

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| A. Аддитивные минорные версии в `/v1` (выбран) | Существующие ТСП не меняют ничего; нет дублирования кода и версий; списание читается старым методом | `/v1` растёт; нужна дисциплина «только добавление» | — |
| B. Новый `/v2` для подписок | Чистая граница версий | Дублирование контракта и маршрутов; существующие ТСП должны мигрировать ради чужих подписок; поддержка двух версий ≥6 мес; нет выгоды, т.к. изменений старой семантики нет | Ломать нечего — v2 не оправдан |
| C. Отдельный API/сервис «подписки» | Изоляция домена | Второй контракт, второе версионирование, кросс-доменная согласованность; противоречит ADR-008 (списание — вид платежа) | Дороже без выгоды |
| D. Расширить `Payment.status` новыми статусами (`MANDATE_BOUND`, `DEBIT_*`) | Прозрачность для ТСП | Расширение enum ломает строгих потребителей; технические подсостояния не должны выходить наружу | Нарушает AD-010 и родительский ADR-002 |

## Consequences

### Positive

- Ноль изменений для существующих ТСП — подтверждается `contract_diff`, а не обещанием.
- Одна версия контракта — меньше кода, тестов и документации в поддержке.
- Списание автоматически доступно существующим механизмам статуса/возврата/вебхуков.
- Стратегия доказуема в CI: breaking-дифф становится красным гейтом.

### Negative

- `/v1` со временем накапливает опциональные поля — нужна ревизия «не пора ли v2» (условие пересмотра ниже).
- «Только добавление» — ограничение на рефакторинг контракта: неудачно названное поле нельзя переименовать, только депрецировать.
- Смешение разовых и рекуррентных полей в `Payment` требует дисциплины документации (какие поля применимы к какому `paymentType`).
- Потребители, валидирующие ответы строго по схеме (`additionalProperties: false`), должны допускать новые опциональные поля — это стандартное требование Tolerant Reader, но его надо явно донести до ТСП.

## Reversibility

**reversible.** Контракт можно заморозить и ввести `/v2` позже, если накопятся ломающие изменения; добавленные опциональные поля и новые пути можно депрецировать. Необратимых последствий нет.

**Условие пересмотра (expiry):** пересмотр при (а) необходимости первого ломающего изменения (тогда v2); (б) накоплении «неиспользуемых/депрецированных» полей ≥ порога; (в) изменении протокола НСПК, требующего иной формы ресурсов.
