# ADR-012. Внедрение, обратимость и откат подписок: поэтапный запуск с kill-switch

- Date: 2026-09-28
- Status: Proposed (требует человеческого решения A3)
- Owner: solution-architect (платёжный контур) + продукт + SRE
- Модель-автор: qwen-code
- Related: ADR-007, ADR-008, ADR-009, ADR-010, ADR-011, AD-008

## Context

Подписки затрагивают живые финансы клиентов и строятся **поверх** уже принятого решения (ADR-001…ADR-007), которое сейчас проходит путь до боевой эксплуатации. Нужно встроить подписки так, чтобы:

- существующий разовый C2B-приём не зависел от нового функционала и не деградировал при его проблемах;
- откат был возможен **после** включения (а не только «до»);
- решение о запуске принимал человек (маршрут Critical, обязательная точка A3), с явными сигналами и владельцем отката;
- обратимость была согласована с оценками в ADR (ADR-008 costly, ADR-009 costly, ADR-010 reversible, ADR-011 reversible).

Принятая стратегия реализации транспорта (ADR-007, AD-008) уже требует: реализация транспорта начинается только после контракта с вендором и документации НСПК. Подписки добавляют к транспорту мандатные операции — то же ограничение распространяется на них.

## Decision

1. **Поэтапный запуск за фиче-флагом `recurring-debits`** (по умолчанию выключен, отдельно от разового приёма):
   - этап 0 — walking skeleton на моках (мандат + списание + вебхуки) без боевого транспорта;
   - этап 1 — пилот с 1–2 ТСП и ограниченным набором мандатов, малые лимиты;
   - этап 2 — расширение на ТСП по волнам, с мониторингом метрик §7 `docs/nfr.md`;
   - этап 3 — общий запуск.
2. **Kill-switch на новые списания** — мгновенная остановка **инициации новых** списаний без остановки уже открытых операций, обработки мандатных событий и отзыва. Существующий разовый приём продолжает работать независимо. Судьба **уже принятых** (`201`) но ещё не отправленных списаний: они **удерживаются**, а не теряются, — видны в отчёте незавершённых операций; при возобновлении отправляются с **повторной проверкой guard** (ADR-009); при удержании дольше согласованного окна (по умолчанию 24 ч — параметр A3) освобождаются и ТСП получает явный статус/вебхук (без молчаливой потери).
3. **Сигналы отката (триггеры)** — измеримые, а не «на глаз»:
   - **нарушение AD-009** (любое списание без `ACTIVE`-мандата или дубль за период) — **стоп-сигнал: немедленный kill-switch**, не «снижение метрики»;
   - распространение отзыва: p95 > 5 мин или p99 > 15 мин на ≥ 3 событиях из 5 за час → эскалация; p99 > 30 мин → kill-switch;
   - расхождения сверки по **завершённым** списаниям > 0 → разбор; доля расхождений > 0,1 % от операций окна → kill-switch;
   - лаг очереди списаний p95 > 5 мин, либо возраст первого необработанного > 15 мин, либо DLQ > 0 → эскалация; устойчиво (> 30 мин подряд) → kill-switch.
4. **Владелец решения об откате** — дежурный SRE/платёжный мониторинг для немедленного kill-switch (по runbook), архитектор + продукт — для отката этапа/запуска. Kill-switch — не архитектурное решение, а эксплуатационное действие по заранее утверждённому триггеру.
5. **Данные при откате не мигрируются назад**: мандаты и списания остаются в БД и в сверке; обслуживание уже выданных согласий (отзыв, возвраты) продолжается даже при выключенной инициации. Это согласуется с родительским планом отката (`docs/solutioning.md` §8).
6. **Реализация мандатного транспорта — только после выполнения условий ADR-007** (контракт с вендором, документация НСПК); до этого — мок-адаптер (расширение внутреннего контракта `opkc-adapter.md` §3–4 мандатными операциями).
7. **Человеческое решение A3 обязательно** и фиксируется машинно-читаемым пакетом (`changes/sbp-subscriptions/PROPOSAL.md` §8: `choice`, `rationale`, `constraints`, `rejected`, `expiry`, `decided_by`). Агент оставляет `decided_by` пустым — подписывает человек.

## Alternatives Considered

| Вариант | Плюсы | Минусы | Почему отвергнут |
|---|---|---|---|
| A. Фиче-флаг + поэтапный пилот + kill-switch (выбран) | Откат после включения без остановки разового приёма; ограниченный blast radius; измеримые сигналы | Нужны флаги, поэтапная эксплуатация, отдельные runbook и мониторинг | — |
| B. Big-bang запуск всем ТСП сразу | Быстро до эффекта | Нет отката после включения кроме остановки всего; дубль/списание без согласия сразу у многих клиентов | Недопустимо на маршруте Critical с финансовым влиянием |
| C. Параллельный пилотный сервис подписок вне основного контура | Изоляция пилота | Второй источник истины, расхождение с ADR-001/ADR-008; после пилота — миграция | Противоречит единому источнику истины |
| D. Только «до боевой эксплуатации» откат (как в родительском решении) | Проще | После включения подписок отката нет — а именно он нужен для нового функционала | Не закрывает риск |

## Consequences

### Positive

- Откат возможен на любом этапе без остановки разового C2B-приёма.
- Ограниченный радиус поражения при пилоте; сигналы отката привязаны к инвариантам, а не к настроению.
- Обслуживание уже выданных согласий сохраняется — клиент не «подвешен» при откате инициации.
- A3-пакет фиксирует выбор и его условия пересмотра — аудиторский след.

### Negative

- Поэтапный запуск удлиняет время до полного эффекта; нужна координация с продуктом и ТСП.
- Фиче-флаг и kill-switch — дополнительный код и тесты (переключения, «отзыв при выключенной инициации»).
- Постоянное обслуживание мандатов даже в «выключенном» состоянии — эксплуатационная нагрузка.
- Пилот на реальных клиентах требует юридического оформления согласий и уведомлений (комплаенс).

## Reversibility

**reversible** для механизма внедрения (флаг/этапы/пороги меняются без смены архитектуры). **costly** для самого функционала после боевого запуска: активные мандаты — обязательства перед плательщиками (согласовано с ADR-008/ADR-009).

**Условие пересмотра (expiry):** пересмотр при выходе из пилота и при изменении регуляторных требований к порядку запуска; плановая ревизия — через 12 месяцев.
