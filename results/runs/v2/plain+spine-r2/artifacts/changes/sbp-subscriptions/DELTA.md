## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика (подписки СБП). Сейчас каждый платёж требует нового QR и действия клиента, что неприменимо к массовым подпискам. Принятое решение (C2B-приём, ADR-001…ADR-007) описывает только разовые платежи: нет долгоживущего согласия, нет защиты от дубля списания за период и нет обработки пиковой нагрузки биллинговых дат. Изменение добавляет мандат и рекуррентное списание, не отменяя принятое решение и не ломая существующих потребителей.

## ADDED (требования с критериями EARS)

- **REQ-SUB-1**: When ТСП регистрирует согласие плательщика (`POST /v1/mandates`), the СБП-шлюз shall создать мандат и, при доступном ОПКЦ, вернуть `consentUrl` за ≤ 5 с (p95); при недоступности ОПКЦ — вернуть `201` с `CREATED` (без `5xx` и потери операции) и выдать `consentUrl` позже вебхуком `mandate.pending`. Повтор с тем же `Idempotency-Key` дубль не создаёт.
- **REQ-SUB-2**: When плательщик подтверждает согласие (событие ОПКЦ `mandate.activated`), the СБП-шлюз shall перевести мандат в `ACTIVE` и записать неизменяемую аудит-запись согласия за ≤ 5 с (p95) от события.
- **REQ-SUB-3**: If мандат не в статусе `ACTIVE` (или вне срока/сверх лимита), then the СБП-шлюз shall отклонить инициацию списания (`422`) и не создавать списание.
- **REQ-SUB-4**: When ТСП инициирует списание с `billingPeriod`, the СБП-шлюз shall **зарезервировать период** (уникальный ключ на (`mandateId`, `billingPeriod`) для всех списаний, кроме отменённых до отправки) в одной транзакции с guard и вернуть `409` при повторе периода (в т.ч. с другим `Idempotency-Key`).
- **REQ-SUB-5**: When поступает событие отзыва согласия, the СБП-шлюз shall запретить новые инициации списаний по мандату; while мандат `REVOKED`, the СБП-шлюз shall не создавать ни одной новой инициации (уже отправленные в ОПКЦ — в отчёте незавершённых, политика A3); запрет вступает в силу ≤ 60 с (p95).
- **REQ-SUB-6**: When списание подтверждено ОПКЦ (`debit.paid`), the СБП-шлюз shall зачислить средства в АБС только из состояния `PAID` и не более одного раза (AD-005, ADR-009).
- **REQ-SUB-7**: While биллинговое окно перегружено, the СБП-шлюз shall выравнивать списания очередью с приоритетом мандатных событий/отзыва и притормаживать приём (`429`/`503`), не создавая неограниченный бэклог.
- **REQ-SUB-8**: If ТСП-клиент знает только v0.1 (без мандатов), then the СБП-шлюз shall обслуживать его без изменений — существующие пути, поля и enum `Payment.status` не меняются.
- **REQ-SUB-9**: The СБП-шлюз shall не выполнять автоматический fallback списания на другой способ оплаты при неуспехе (неуспех возвращается явным статусом).

## MODIFIED (было → стало, причина)

- **AD-002**: правило атомарности «статус + outbox + аудит» → **распространено** на мандат и рекуррентное списание (было только «финансовый статус платежа»). Причина: мандат — тоже источник истины (ADR-008).
- **AD-003**: ключи идемпотентности (`Idempotency-Key`, `eventId`, `paymentId`/`refundId`) → **добавлены** (`mandateId`, `billingPeriod`) и `reference` для мандата/списания, с **безусловной резервацией периода** при инициации (не «по успешным»). Причина: защита от дубля списания за период при конкуренции (ADR-009).
- **AD-005**: «зачисление только из `PAID`» → **усилено** guard'ом входа «списание только по `ACTIVE`-мандату» (на инициации **и при отправке**); инвариант зачисления не ослаблен. Причина: списание без согласия недопустимо (ADR-008/ADR-009).
- **AD-007**: распространено на ПДн согласия (неизменяемая запись согласия, маскирование, аудит). Правило не меняется.
- **Границы scope** (`docs/solutioning.md` §1): «автоплатежи» были в roadmap (вне scope) → **выведены в scope** как расширение (ADR-008…ADR-012).
- **Контракт API ТСП** v0.1 → **v0.2** (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`): аддитивно — новые пути `/v1/mandates*`, новые схемы, опциональные поля `Payment`; enum `Payment.status` неизменен (`contract_diff`: 0 breaking, 6 non-breaking).
- **Контракт адаптера ОПКЦ** v0.1 → **v0.2** (`docs/contracts/opkc-adapter.md`): аддитивно добавлены мандатные операции (`registerMandate`, `getMandateStatus`, `revokeMandate`, `suspendMandate`, `resumeMandate`), списания (`createRecurringDebit`, `getDebitStatus`), возврат по списанию через `debitRef` (`createRefund`/`refund.confirmed`), события `mandate.*`/`debit.*`; ёмкость повышена до ≥ 300 sustained / 1500 burst.
- **NFR** (`docs/nfr.md`): добавлен §7 — измеримые цели рекуррентных списаний (распространение отзыва, дубли за период = 0, пиковый профиль).
- **RFP** (`docs/rfp/vendor-rfp.md`): добавлены критерий допуска G8, POC-сценарии P9–P13 и повышенная ёмкость (≥300 sustained / 1500 burst).
- **Спецификация** (`docs/spec/state-machine.md`): добавлен §7 «Изменения дельтой»; новая `docs/spec/mandate-state-machine.md` — статусная машина мандата и вход рекуррентного списания.

## REMOVED

- **Нет.** Ничего не удаляется и не сужается (AD-010, ADR-010). Технические подсостояния (`MANDATE_BOUND`, `DEBIT_SUBMITTED`) наружу не выставлялись и не выставляются.

## План отката

См. `changes/sbp-subscriptions/PROPOSAL.md` §7 и ADR-012. Кратко:

- Фиче-флаг `recurring-debits` выключен по умолчанию; разовый C2B-приём от него не зависит.
- **Kill-switch**: остановка инициации **новых** списаний; отзыв, приём мандатных событий и обслуживание выданных согласий продолжаются.
- Данные мандатов/списаний сохраняются и остаются в сверке (обратной миграции нет).
- Сигналы отката: нарушение AD-009 (дубль/без согласия) — немедленный стоп-сигнал; превышение целевого распространения отзыва; рост DLQ/лага при биллинговом окне.
- Владелец: дежурный SRE — kill-switch по runbook; архитектор + продукт — откат этапа.

## Критерии приёмки

- [ ] Мандат: `POST /v1/mandates` идемпотентен; `ACTIVE` по событию; условия иммутабельны после активации; при недоступности ОПКЦ — `CREATED` + вебхук, без потери.
- [ ] Списание без `ACTIVE`-мандата невозможно на инициации **и при отправке** (тест guard'а; 0 случаев).
- [ ] Дубль списания за (`mandateId`, `billingPeriod`) невозможен даже при конкурентных запросах (0 случаев; резервация периода + `409`).
- [ ] Лимит периода и `frequency` не могут быть превышены конкурирующими списаниями (тест счётчика).
- [ ] После обработанного отзыва — 0 **новых инициаций**; запрет ≤ 60 с (p95) от события; уже отправленные — в отчёте незавершённых.
- [ ] Зачисление по списанию — только из `PAID`, однократно (тест повторной доставки `debit.paid`; второй `PAID` по занятому периоду → алерт, без второго зачисления).
- [ ] Возврат по списанию проходит сагу без `qrId` (адресация `debitRef`).
- [ ] Приостановка/возобновление (`suspend`/`resume`) работают; из `REVOKED`/`EXPIRED` возобновление невозможно (`422`).
- [ ] Автоматический fallback при неуспехе списания отсутствует.
- [ ] `contract_diff` v0.1→v0.2: 0 breaking; `openapi_lint` нового контракта — PASS.
- [ ] Разовый C2B-приём не деградирует при выключенном флаге `recurring-debits` (регресс-тест).
- [ ] Нагрузочный тест биллингового пика (burst 1500 TPS ≥ 10 мин, суммарно с разовым потоком): потерянных — 0, деградация управляема.
- [ ] Откат отрепетирован: kill-switch запрещает новые инициации, уже принятые удерживаются (не теряются), отзыв и сверка продолжают работать.
- [ ] A3 подписан человеком (`decided_by` заполнен) — без подписи реализация не начинается.

## Fitness (вносится в `.arch-handoff/CONSTRAINTS.yaml`)

Формулировки — в `CONSTRAINTS.yaml` (внесены этой дельтой).

**Граница проверки (честно):** C-101…C-104, C-107 — правила **трассируемости** (инвариант записан в тексте), а не проверки поведения; C-105/C-106/C-108/C-109 — защита контракта от удаления/сужения. Поведенческие проверки (guard, уникальность периода, отзыв, идемпотентность зачисления) ставятся на гейте A4 шаблонами исполняемых правил (`arch-be rules template`, `command_succeeds`) — на этапе решения кода ещё нет.
