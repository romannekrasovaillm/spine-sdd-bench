## 1. Оценка значимости и маршрута

**Маршрут: Critical.** Инструмент `significance_score` (MCP Spine) на заявленных триггерах даёт **10/15 → Critical** (`criticality_or_exception` — критический триггер).

| Триггер | Значение | Почему |
|---|---|---|
| `financial_impact` | **true** | Рекуррентные списания — финансовые операции клиентов |
| `criticality_or_exception` | **true** | Платёжный контур СБП (КИИ, НПС) |
| `consistency_model_change` | **true** | Согласие живёт дольше платежа; гонка «отзыв ↔ списание» |
| `api_contract_change` | **true** | Новые ресурсы/поля в API ТСП |
| `data_contract_change` | **true** | Новые сущности и ключи идемпотентности |
| `domain_ownership_change` | **true** | Новый агрегат «мандат» с владельцем |
| `cross_domain_integration` | **true** | ТСП ↔ шлюз ↔ ОПКЦ ↔ банк плательщика ↔ АБС |
| `significant_nfr` | **true** | Распространение отзыва, пиковый профиль биллинга |
| `rto_rpo_targets` | **true** | RPO=0 распространяется на мандаты/списания |
| `new_component` | **true** | Новый модуль (мандат) + планировщик/очередь списаний внутри платёжного контура (новая единица владения в коде и эксплуатации) |
| `new_datastore` | false | Новые таблицы в существующей БД шлюза |
| `new_vendor` | false | Тот же вендор транспорта (расширение контракта), не новый поставщик |
| `security_boundary_change` | false | Новых trust-зон и внешних каналов нет (AD-006 не меняется) |
| `trust_zone_change` | false | То же |
| `irreversible_migration` | false | Миграции данных назад нет; откат через kill-switch |

**Следствие маршрута (почему нужен именно такой объём):** Critical требует полного Solutioning (spine + ADR + NFR), **обязательной человеческой точки A3**, walking skeleton до массовой генерации и evidence-гейтов A4/A5. Дельта-спека как самостоятельный артефакт недостаточна — она здесь работает как механизм аудиторского следа для защищённых файлов (spine, CONSTRAINTS), а не как замена Solutioning.

> Оговорка: маршрут — функция **заявленных** триггеров. Если появятся новые вводные (например, требование обрабатывать карточные рекуррентные списания в том же контуре), оценку нужно пересмотреть.

## 2. Влияние на принятую архитектуру

### 2.1 Что **не** меняется

- Топология и изоляция контура (AD-001, ADR-001): мандат и списания — в существующем шлюзе и его БД.
- Единственный адаптер ОПКЦ (AD-004, ADR-003): протокол НСПК по-прежнему знает только он; транспорт подписок — его расширение.
- Trust-зоны и сегментация (AD-006, ADR-006): новых зон и каналов нет.
- Соответствие НПС/КИИ/ПДн (AD-007, ADR-006): требования те же, распространяются на данные согласия.
- Стратегия реализации «гибрид» (AD-008, ADR-007, ADOPTED): ядро — собственное, транспорт — вендорский; мандатная логика — в ядре.
- АБС-интеграция (ADR-005): контракт с АБС не меняется — списание зачисляется тем же идемпотентным механизмом по `paymentId`.
- Сага возвратов (ADR-005): возврат по списанию — существующая сага без изменений.
- Enum `Payment.status` и пути `/v1/payments*` — неизменны (AD-010).

### 2.2 Что меняется

| Инвариант | Характер | Суть изменения |
|---|---|---|
| AD-002 | **расширение** | Атомарность «статус + outbox + аудит» распространяется на мандат и списание |
| AD-003 | **расширение** | Идемпотентность: (`mandateId`, `billingPeriod`) + `reference` мандата/списания |
| AD-005 | **усиление** | Guard «списание только по `ACTIVE`-мандату»; зачисление по-прежнему только из `PAID` |
| AD-007 | **распространение** | ПДн/аудит согласия (неизменяемая запись, маскирование) |
| **AD-009 (new)** | **новый** | Рекуррентное списание — только по действующему согласию |
| **AD-010 (new)** | **новый** | Аддитивная эволюция контракта API ТСП |
| **AD-011 (new)** | **новый** | Пиковые нагрузки биллинга выравниваются очередью |
| Deferred | **изменение** | Автоплатежи/подписки выведены из Deferred в scope |

Новые сущности: `Mandate` (согласие) и рекуррентное списание как вид платежа (`paymentType=recurring`). Новые единицы: мандатный модуль, планировщик/очередь списаний и резервация периода (внутри платёжного контура). Новых trust-зон и внешних интеграций нет.

## 3. Архитектурное решение: рассмотренные альтернативы, последствия, обратимость

Решение разбито на пять ADR (канон `adr-authoring`: одна запись — одно решение; обязательны альтернативы, отрицательные последствия, обратимость).

| ADR | Решение | Ключевая альтернатива и почему отвергнута | Обратимость |
|---|---|---|---|
| [ADR-008](../docs/adr/ADR-008-mandat-soglasie-platelshchika-i-rekurrentnoe-spisanie.md) | Мандат — сущность ядра; списание — вид платежа | Мандат у ТСП (нет единого источника истины); выделенный микросервис (второй источник истины) | **costly** |
| [ADR-009](../docs/adr/ADR-009-konsistentnost-i-idempotentnost-rekurrentnyh-spisanij.md) | Guard + уникальность периода + отзыв-приоритет + ограниченные ретраи; без fallback | Полагаться на банк плательщика (нет гарантий); распределённый лок (избыточно, добавляет отказов); авто-fallback на QR (расширяет аварию) | **costly** |
| [ADR-010](../docs/adr/ADR-010-evolyuciya-kontrakta-tsp-additivnye-minornye-versii.md) | Аддитивные минорные версии в `/v1` | Новый `/v2` (нечего ломать, лишняя миграция); отдельный API подписок (второй контракт) | **reversible** |
| [ADR-011](../docs/adr/ADR-011-pikovaya-nagruzka-billingovyh-dat-vyravnivanie-i-dopusch.md) | Очередь выравнивания + допуск + приоритеты + джиттер | Синхронный вызов (каскадный отказ); только пакетная обработка (теряется событийность); организационное разнесение окон (не архитектура) | **reversible** |
| [ADR-012](../docs/adr/ADR-012-vnedrenie-otkat-i-kill-switch-podpisok.md) | Поэтапный запуск за фиче-флагом + kill-switch; A3 обязателен | Big-bang (нет отката); параллельный пилотный сервис (второй источник истины) | **reversible** (механизм) / **costly** (функционал) |

Каждый ADR содержит секции Context / Decision / Alternatives Considered / Consequences (Positive + Negative) / Reversibility / References. Сводные отрицательные последствия (честно): новый агрегат и вторая машина состояний; отложенная обработка списаний из-за очереди; остаточная неопределённость по «осевшему» после отзыва списанию; долгоживущие ПДн согласия; рост эксплуатационной нагрузки (мандаты обслуживаются и при выключенной инициации).

## 4. Изменения контрактов без поломки потребителей

**Правило (AD-010, ADR-010):** только новыми путями, новыми ресурсами и опциональными полями; существующие пути/поля/enum не удаляются и не сужаются.

Изменения `openapi/tsp-api.yaml` (v0.1.0 → v0.2.0):

- **Новые пути**: `POST /v1/mandates`, `GET /v1/mandates/{mandateId}`, `POST /v1/mandates/{mandateId}/revoke`, `POST /v1/mandates/{mandateId}/suspend`, `POST /v1/mandates/{mandateId}/resume`, `POST|GET /v1/mandates/{mandateId}/debits`.
- **Новые схемы**: `Mandate`, `MandateRequest`, `DebitRequest`, `Problem`.
- **`Payment`**: добавлены **опциональные** `paymentType`, `mandateId`, `billingPeriod`. Существующие обязательные поля и **enum `Payment.status` не изменены**.
- **Списание читается существующим методом** `GET /v1/payments/{paymentId}` — не нужен новый статусный ресурс; возврат по списанию — существующая сага `POST /v1/payments/{paymentId}/refunds`.
- **Новые события вебхуков** — только мандатные; по списаниям ТСП получает существующие `payment.completed`/`payment.failed` (типы не добавляются и не переименовываются).

**Доказательство (механическое, не «на словах»):**

- `openapi_lint openapi/tsp-api.yaml` → **PASS** (0 error, 0 warn).
- `contract_diff` v0.1 → v0.2 → **0 breaking, 6 non-breaking** (только новые пути; CD-007 «ломающий дифф без смены major» не сработал).
- Fitness-правила C-105/C-108 (пути `/v1/payments`, `/v1/payments/{paymentId}`), C-106 (enum `Payment.status`) и C-109 (`PaymentRequest.required`) сторожат неразрушаемость в CI. Граница честно: это правила **сохранности контракта и трассируемости**, а не проверки поведения — поведенческие проверки ставятся на A4 (`command_succeeds`/шаблоны правил).

Внутренний контракт `docs/contracts/opkc-adapter.md` (v0.1 → v0.2) расширен аддитивно: мандатные операции (`registerMandate`, `getMandateStatus`, `revokeMandate`, `suspendMandate`, `resumeMandate`), списания (`createRecurringDebit`, `getDebitStatus`), возврат по списанию через `debitRef` (без `qrId`), события `mandate.*`/`debit.*`. Для вендора добавлен критерий допуска **G8**, POC-сценарии **P9–P13** и повышенная ёмкость (≥ 300 sustained / 1500 burst) (`docs/rfp/vendor-rfp.md`).

## 5. Измеримые NFR нового функционала

Полностью — `docs/nfr.md` §7. Ключевое:

| Метрика | Цель |
|---|---|
| Распространение отзыва: от события до запрета новых списаний | p95 ≤ 60 с, p99 ≤ 5 мин; после обработки — **0** новых списаний |
| Дублей списания за (`mandateId`, `billingPeriod`) | **0** |
| Списаний без `ACTIVE`-мандата | **0** |
| Списаний после обработанного отзыва | **0** |
| Инициация списания (`POST …/debits`) | p95 ≤ 300 мс, p99 ≤ 1 с |
| Активация мандата (подтверждение → `ACTIVE`) | p95 ≤ 5 с |
| Пиковая пропускная способность биллинга | sustained 300 TPS, burst 1500 TPS ≥ 10 мин |
| Лаг очереди списаний | p95 ≤ 60 с; метрика «возраст первого необработанного» + алерт |
| Доступность потоков мандатов/списаний | ≥ 99,95 % |
| RPO / RTO (мандаты и списания) | RPO = 0; RTO ≤ 1 ч |

Каждая цель — с методом проверки; «ноль» для дублей и списаний без согласия выбран потому, что это финансовый/регуляторный инцидент, а не деградация метрики.

## 6. Критерии приёмки

Полный список — `changes/sbp-subscriptions/DELTA.md` §Критерии приёмки (14 пунктов, проверяемые). Обязательные негативные сценарии:

- дубль списания за период (повтор `Idempotency-Key` и повтор с другим ключом);
- списание по мандату не в `ACTIVE` (отзыв обработан, срок истёк, лимит превышен);
- гонка «отзыв ↔ списание» (отзыв при активном биллинге, в т.ч. при списании в очереди и уже отправленном);
- недоступность вендорского адаптера в пик биллинга (бэклог, никакой лавины ретраев, нет дублей после восстановления);
- повторная доставка `debit.paid` (идемпотентность зачисления);
- регресс разового C2B-приёма при выключенном `recurring-debits`.

## 8. Что остаётся на решение человека-архитектора (A3) и почему

Агент подготовил варианты, последствия и рекомендации, но решения ниже — **за человеком**: они затрагивают бизнес-модель, право, регуляторику и деньги клиентов, где у агента нет полномочий и полного контекста. Машинно-читаемый пакет (по канону `significance-routing`):

```yaml
choice: null              # ожидает человека
rationale: null
constraints: []
rejected: []
expiry: null
decided_by: null          # подпись человека обязательна; агент оставляет пустым
```

Вопросы, требующие решения человека:

1. **Модель согласия.** Полная модель «мандат в ядре» (рекомендация ADR-008) vs упрощённая (расписание у ТСП с проверкой на стороне ОПКЦ). Зависит от фактического протокола подписок НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`.
2. **Версия контракта.** Аддитивные минорные версии `/v1` (рекомендация ADR-010) vs `/v2`. Рекомендация основана на `contract_diff` (0 breaking), но выбор публичной политики версионирования — за архитектором/владельцем API.
3. **Политика dunning.** Число попыток, интервалы, порог `SUSPENDED` (ADR-009). Бизнес + комплаенс: влияет на клиентский опыт и на риск недобора.
4. **Политика «осевшего» списания.** Что делать со списанием, прошедшим после отзыва (возврат / зачисление / ручной разбор) — юридическая политика по правилам НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`.
5. **Пиковые цели.** Значения sustained/burst (ADR-011, NFR §7) зависят от реального числа ТСП и списаний в окне — от бизнеса.
6. **Расширение вендора.** Мандатный транспорт у текущего вендора vs отдельный RFP (ADR-007/ADR-012); влияет на сроки и стоимость.
7. **Правовая модель согласия и уведомлений** (161-ФЗ / Положение ЦБ, обязанность уведомления плательщика) — юристы + ИБ `[ТРЕБУЕТ ПРОВЕРКИ]`.
8. **ПДн и срок хранения согласия** — ДПО/ИБ (AD-007).
9. **Объём первой волны** пилота (какие ТСП, какие лимиты) — продукт (ADR-012).

## 9. Что дальше (после A3)

1. Человек подписывает A3-пакет (заполняет `choice`, `rationale`, `constraints`, `rejected`, `expiry`, `decided_by`).
2. Рекомендации ADR переводятся из `Proposed` в `Accepted`; блоки spine AD-009…AD-011 — в `Accepted`.
3. Обновляется handoff-пакет `.arch-handoff/` (TASK.md/ARCHITECTURE.md) под новые требования; `recurring-debits` уходит в реализацию walking skeleton.
4. Гейт A4: fitness-правила C-101…C-110 + нагрузочный тест биллингового пика + ИБ-ревью ПДн согласия; репетиция отката.
