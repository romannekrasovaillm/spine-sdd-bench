# Дельта: add-recurring-payments
- Route: **Critical** — полный Solutioning (спайн + ADR + NFR + A3). Дельта фиксирует изменения живой истины; полный пакет решения — `openspec/changes/add-recurring-payments/` (proposal/specs/design/tasks) и `docs/adr/ADR-008`, `docs/adr/ADR-009`.
- Created: 2026-09-28

## Проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят рекуррентные C2B-списания по согласию плательщика (подписки СБП). Сейчас каждый платёж требует QR и действия клиента. Дельтой вливаются изменения принятого решения: новые инварианты в `ARCHITECTURE-SPINE.md` (AD-009, AD-010), fitness-правила в `.arch-handoff/CONSTRAINTS.yaml`, измеримые NFR в `docs/nfr.md` и аддитивное расширение контракта `openapi/tsp-api.yaml` / `docs/contracts/tsp-api.md`.

## ADDED

- **Инвариант AD-009** (`ARCHITECTURE-SPINE.md`): рекуррентное списание только по действующему согласию и в пределах его лимитов. Критерий (EARS): While согласие в состоянии, отличном от `ACTIVE`, the шлюз shall отклонять инициацию рекуррентного списания; When согласие отозвано, the шлюз shall немедленно запретить новые списания, доведя уже подтверждённые НСПК списания до завершения.
- **Инвариант AD-010** (`ARCHITECTURE-SPINE.md`): однократность списания за расчётный период. Критерий (EARS): When поступает повторная инициация списания по той же подписке за тот же расчётный период, the шлюз shall вернуть существующее списание и shall not создать новое.
- **NFR рекуррентного потока** (`docs/nfr.md`, раздел 7): latency инициации списания, latency активации согласия, срок блокировки после отзыва, нулевая доля двойных списаний, throughput, доступность, аудит.
- **Согласие и подписка в контракте** (`openapi/tsp-api.yaml`, `docs/contracts/tsp-api.md`): пути `POST/GET /v1/consents`, `POST /v1/consents/{consentId}/revoke`, `POST/GET /v1/subscriptions`, `POST /v1/subscriptions/{subscriptionId}/debits`; тип инициации `debit`, состояние `DEBIT_PENDING`, события `consent.*`.
- **Fitness-правила** (`.arch-handoff/CONSTRAINTS.yaml`): `recurring-only-active-consent`, `recurring-no-double-period`, `spine-ad-009-present`, `spine-ad-010-present`, `nfr-recurring-measurable`.

## MODIFIED

- **`ARCHITECTURE-SPINE.md` — контракты и версии**: добавить ссылки на ADR-008/ADR-009 и отметку о расширении статусной машины платежа состоянием `DEBIT_PENDING` (ADR-002, AD-005 — без ослабления инвариантов).
- **`docs/nfr.md` — статус NFR**: цели рекуррентного потока согласуются с регламентами НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`; новые метрики помечены baseline.

## REMOVED

- Нет. Существующие требования, инварианты и поля контракта сохраняются.

## План отката

До боевого включения — обратимо: функционал за фиче-флагом по ТСП, откат = не включать; QR-поток и существующие потребители не затронуты. После включения: флаг off (новые эндпоинты недоступны), отзыв выданных согласий по runbook (≤ 4 ч), релиз rolling; данные не мигрируются обратно — шлюз остаётся источником истины до сверки с АБС/НСПК. Сигналы отката и владелец решения — в `openspec/changes/add-recurring-payments/ROLLBACK.md`.

## Критерии приёмки

- [ ] Списание по неактивному согласию (`PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED`) отклоняется, платёж не создаётся (AD-009).
- [ ] Списание сверх лимита согласия отклоняется с `LIMIT_EXCEEDED` (AD-009).
- [ ] Повторная инициация за тот же расчётный период возвращает существующее списание (AD-010).
- [ ] Зачисление возможно только из `PAID`; из `DEBIT_PENDING`/`CREATED` недостижимо (AD-005).
- [ ] После отзыва согласия новые списания запрещены; подтверждённые доводятся до `COMPLETED`; неподтверждённые → `FAILED` с `CONSENT_REVOKED`.
- [ ] Повторная доставка событий согласия не меняет состояние (AD-003).
- [ ] QR-поток проходит регрессию без изменений поведения (AC-09).
- [ ] `contract_diff` v0.1→v0.2 не показывает ломающих изменений.
