# Proposal

## Why

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** (подписки СБП). Сегодня каждый платёж в шлюзе требует QR и действия клиента, из-за чего модель подписки не работает и повторные платежи теряются. Изменение расширяет принятое решение (ADR-001…007) рекуррентным потоком, не затрагивая существующий QR-поток и его инварианты.

## What Changes

- Новая сущность — **согласие плательщика (consent)**: мандат на будущие списания, подтверждаемый плательщиком в СБП (НСПК); жизненный цикл `PENDING → ACTIVE → (SUSPENDED) → REVOKED | EXPIRED`.
- Новая сущность — **подписка ТСП (subscription)**: коммерческий план, привязанный к действующему согласию.
- Платежи получают тип инициации `initiationType = debit` и состояние `DEBIT_PENDING`; QR-поток не меняется.
- Новые эндпоинты ТСП API (аддитивно, без поломки потребителей): `POST/GET /v1/consents`, `POST /v1/consents/{id}/revoke`, `POST/GET /v1/subscriptions`, `POST /v1/subscriptions/{id}/debits`.
- Новые события вебхуков: `consent.activated`, `consent.revoked`, `consent.expired`.
- Новые spine-инварианты AD-009 (списание только по действующему согласию, в пределах лимитов) и AD-010 (однократность списания за расчётный период).
- Новые измеримые NFR рекуррентного потока и fitness-правила.
- **BREAKING**: нет. Только добавление опциональных полей, новых путей и новых значений enum; существующие потребители `/v1/payments` не затрагиваются.

## Capabilities

### New Capabilities

- `recurring-payments`: согласие плательщика (мандат СБП), подписка ТСП и инициация рекуррентных списаний с их жизненным циклом, лимитами и политикой отзыва.

## Impact

- **API ТСП**: `openapi/tsp-api.yaml` (аддитивно, v0.1.0 → v0.2.0), `docs/contracts/tsp-api.md`.
- **Статусная машина**: `docs/spec/state-machine.md` — новые состояния/переходы (платёж и согласие).
- **Spine**: `ARCHITECTURE-SPINE.md` — AD-009, AD-010 (через дельту).
- **NFR**: `docs/nfr.md` — раздел рекуррентного потока.
- **Решения**: `docs/adr/ADR-008`, `docs/adr/ADR-009`.
- **Fitness**: `.arch-handoff/CONSTRAINTS.yaml` — правила новых инвариантов.
- **Компоненты шлюза**: новая подсистема согласий/подписок, расширение адаптера ОПКЦ (операции согласий), нотификатор, сверка.
- **Внешний вход**: протокол «подписки СБП» НСПК — `[ТРЕБУЕТ ПРОВЕРКИ]` до получения документации.
- **Данные**: новые таблицы согласий/подписок; класс ПДн не расширяется (реквизиты плательщика не хранятся).
