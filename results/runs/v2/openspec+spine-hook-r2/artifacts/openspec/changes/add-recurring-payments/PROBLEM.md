# Problem — add-recurring-payments

## Бизнес-проблема

ТСП (онлайн-кинотеатры, ЖКХ, связь) просят **рекуррентные C2B-списания по согласию плательщика** (подписки СБП). В принятом решении шлюза (ADR-001…007) каждая оплата инициируется плательщиком через QR/ссылку и требует его действия; мандата «списывать впредь» в модели нет. Как следствие — подписки невозможны, повторные платежи теряются, ТСП уходят в альтернативные способы рекуррента.

## Почему сейчас

- Бизнес-запрос от ключевых ТСП (кинотеатры/ЖКХ/связь) сформирован, ожидание — первая волна после стабилизации базового C2B-приёма.
- В СБП существует продукт согласия плательщика (мандат), подтверждаемый банком плательщика — это позволяет построить рекуррент без хранения платёжных реквизитов в шлюзе (ADR-008).

## Что ломается без изменения

- Финансовый риск: если рекуррент реализовать вне мандата СБП — несанкционированные списания, регуляторный риск, возвраты.
- Архитектурный риск: если не зафиксировать инварианты заранее, независимые исполнители разойдутся в семантике (списание без согласия, двойное списание за период).

## Границы проблемы

- В scope: согласие плательщика, подписка ТСП, инициация рекуррентного списания, отзыв, лимиты, нотификации, сверка.
- Вне scope: реальный протокол НСПК по подпискам (внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`), планировщик периодов в шлюзе, карточный рекуррент, диспуты.
