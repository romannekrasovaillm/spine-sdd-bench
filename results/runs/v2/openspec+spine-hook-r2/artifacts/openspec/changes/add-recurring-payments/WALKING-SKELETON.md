# Walking Skeleton — add-recurring-payments

Итог: NOT-RUN — скелет определён на этапе решения; прогон выполняется на A4/walking-skeleton (отчёт о прогоне прикладывается отдельно). Входные файлы задачи — `tasks.md` (группа 7), критерии — `ACCEPTANCE.md`.

Цель скелета — доказать сквозной рекуррентный поток на моках, не реализуя реальный протокол НСПК. Соответствует `design.md` и `tasks.md` (группа 7).

## Сквозной сценарий (счастливый путь)

1. `POST /v1/consents` → согласие `PENDING` + `confirmationUrl`.
2. Мок НСПК: событие подтверждения → согласие `ACTIVE`; ТСП получает `consent.activated`.
3. `POST /v1/subscriptions` → `ACTIVE`-подписка на согласии.
4. `POST /v1/subscriptions/{id}/debits` (`billingPeriod=2026-10`) → платёж `DEBIT_PENDING`.
5. Мок НСПК: нотификация `PAID` → зачисление через мок АБС (идемпотентно по `paymentId`) → `CREDITED → COMPLETED`; ТСП получает `payment.completed`.

## Негативные сценарии скелета

- Списание по `PENDING`-согласию → `CONSENT_NOT_ACTIVE`, платежа нет.
- Повторная инициация за `2026-10` → существующее списание, второго нет.
- Превышение лимита → `LIMIT_EXCEEDED`.
- Отзыв согласия, затем инициация → отказ; подтверждённое ранее списание доходит до `COMPLETED`.
- Повторная доставка события `PAID`/`consent.confirmed` → состояние не меняется.
- Отказ транспорта (мок `503`) → `DLQ`/ретраи, алерт, состояние согласовано сверкой.

## Что НЕ входит в скелет

- Реальный транспорт НСПК (сертификаты, ГОСТ, СКЗИ) — вне scope (AD-008, `[ТРЕБУЕТ ПРОВЕРКИ]`).
- Планировщик периодов (периоды задаёт ТСП-инициатор).
- Нагрузочные и ИБ-проверки полного профиля — на A4.
