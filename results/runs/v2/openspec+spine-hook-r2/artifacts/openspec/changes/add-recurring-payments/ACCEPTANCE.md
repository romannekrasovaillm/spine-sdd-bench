# Критерии приёмки — add-recurring-payments

Каждый критерий проверяем тестом/командой на walking skeleton (моки НСПК/АБС) и затем на тестовом контуре НСПК.

## Функциональные

- [ ] **AC-01** `POST /v1/consents` создаёт согласие `PENDING` с `confirmationUrl`; повтор с тем же `Idempotency-Key` возвращает тот же `consentId`.
- [ ] **AC-02** По `ACTIVE`-согласию инициация списания создаёт платёж `DEBIT_PENDING`, далее `PAID → CREDITED → COMPLETED` (мок НСПК/АБС).
- [ ] **AC-03** Списание по согласию в состоянии `PENDING`/`SUSPENDED`/`REVOKED`/`EXPIRED` → `CONSENT_NOT_ACTIVE`, платёж не создаётся (AD-009).
- [ ] **AC-04** Повторная инициация за тот же `billingPeriod` (в т.ч. с другим `Idempotency-Key`) возвращает существующее списание; второго обращения к НСПК нет (AD-010).
- [ ] **AC-05** Списание сверх лимита (на списание/за период) → `LIMIT_EXCEEDED`, платёж не создаётся (AD-009).
- [ ] **AC-06** После события отзыва новые списания отклоняются ≤ 5 с; подтверждённые (`PAID`) доводятся до `COMPLETED`; неподтверждённые → `FAILED/CONSENT_REVOKED` (ADR-009).
- [ ] **AC-07** Повторная доставка события согласия (тот же `eventId`) не меняет состояние и не порождает повторных вебхуков/аудита (AD-003).
- [ ] **AC-08** Зачисление рекуррентного списания недостижимо из `CREATED`/`DEBIT_PENDING`; возможно только из `PAID` (AD-005).
- [ ] **AC-09** Регрессия QR-потока: существующие сценарии оплаты по динамическому QR проходят без изменения поведения и контракта.
- [ ] **AC-12** Каждый переход согласия и каждое списание присутствуют в неизменяемом аудит-логе с `traceId`.

## Контрактные и негативные

- [ ] **AC-10** `contract_diff` v0.1→v0.2 — breaking 0; `openapi_lint` — 0 error.
- [ ] **AC-11** Откат: фиче-флаг off → новые эндпоинты недоступны, QR-поток работает; runbook отзыва согласий исполняется ≤ 4 ч.
- [ ] **AC-13** Гонка «отзыв ↔ списание»: конкурентный/property-тест не допускает ни списания после отзыва, ни отката подтверждённой оплаты.
- [ ] **AC-14** Неопределённый исход (таймаут НСПК) при отзыве уходит в сверку/runbook; инцидент не «маскируется» (ADR-009).

## Уточнения по итогам состязательного ревью

- [ ] **AC-15** Повтор после терминального `FAILED` за тот же период создаёт новую попытку; при этом успешных списаний за период остаётся не более одного (AD-010).
- [ ] **AC-16** Ключ периода нормализуется шлюзом: две разные строки `billingPeriod`, нормализуемые к одному периоду, дают одно успешное списание (AD-010).
- [ ] **AC-17** Возврат по завершённому списанию разрешён после отзыва согласия (возврат — не новое списание) (AD-009).
- [ ] **AC-18** Рекуррентное списание проходит те же антифрод/AML-контроли, что и обычный платёж; отклонение → `FAILED`, зачисления нет.
- [ ] **AC-19** Отсутствие ложноположительного блокирования: при `ACTIVE`-согласии и валидном периоде списание проходит (антифрод не блокирует штатный поток).

## Критерий успешного отката

Откат считается успешным, если: фиче-флаг off снимает доступ к рекуррентным эндпоинтам; все выданные согласия отозваны или переведены в не-`ACTIVE` по runbook; ни одно новое списание невозможно; QR-поток проходит регрессию; открытые операции закрыты или переданы в сверку (см. `ROLLBACK.md`).
