# Мандат (согласие плательщика) — спецификация рекуррентных C2B-списаний

- Статус: Draft — на ревью (A1)
- Владелец: solution-architect (платёжный контур)
- Связано: ADR-008, AD-002, AD-003, AD-005, AD-009 (spine), `docs/spec/state-machine.md`, `docs/contracts/opkc-adapter.md`

Рекуррентное списание — обычный платёж (см. `docs/spec/state-machine.md`), инициируемый не по QR, а по **действующему мандату**. Настоящая спецификация — про мандат: состояния, переходы, guard-условия, идемпотентность и связь с платежом. Точный протокол НСПК по мандатам — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.

## Проблема

Разовое списание C2B требует QR и действия клиента в момент оплаты, поэтому непригодно для подписок (онлайн-кинотеатры, ЖКХ, связь). Нужен правомерный рекуррентный контур: согласие плательщика выдаётся один раз, списания проходят без его участия, а отзыв согласия немедленно останавливает списания. Без отдельного объекта «согласие» невозможно ни доказать правомерность списания, ни гарантировать ровно одно списание за период, ни корректно обработать отзыв — при том что канал к НСПК не даёт доставку «ровно один раз». Спецификация фиксирует модель состояния мандата и правила, делающие эти гарантии машинно-проверяемыми.

## 1. Термины

- **Мандат (согласие плательщика)** — зарегистрированное в ОПКЦ и подтверждённое плательщиком право ТСП инициировать списания в заданных границах (сумма, период, назначение, срок).
- **Списание (debit)** — платёж, инициируемый шлюзом по мандату; в платёжной FSM — обычный платёж с `paymentType = mandate_debit`.
- **`periodKey`** — идентификатор периода подписки (например, `2026-10` или порядковый номер), в границах которого допускается ровно одно списание.

## 2. Состояния мандата

| Состояние | Смысл | Терминальное |
|---|---|---|
| `CREATED` | мандат зарегистрирован в шлюзе, запрос на регистрацию согласия в ОПКЦ в процессе | нет |
| `PENDING_CONSENT` | ссылка/QR подтверждения согласия выдана; ждём подтверждения плательщика | нет |
| `ACTIVE` | согласие подтверждено ОПКЦ; списания разрешены | нет |
| `SUSPENDED` | списания временно приостановлены (пауза ТСП или техника ОПКЦ); обратимо в `ACTIVE` | нет |
| `REJECTED` | плательщик отказал или ОПКЦ отклонил регистрацию | да |
| `EXPIRED` | истёк срок действия согласия | да |
| `REVOKED` | согласие отозвано (плательщиком или ТСП) | да |

Списание инициируется **только** из `ACTIVE` (AD-009).

## 3. Таблица переходов мандата

| № | From | To | Триггер | Guard | Действие |
|---|---|---|---|---|---|
| M1 | — | `CREATED` | `POST /v1/mandates` | валидный запрос, ТСП активен | запись мандата + outbox «регистрация согласия в ОПКЦ» |
| M2 | `CREATED` | `PENDING_CONSENT` | ОПКЦ вернул ссылку подтверждения | ссылка непустая | сохранить `consentUrl`, outbox, ответ ТСП 201 |
| M3 | `CREATED` | `REJECTED` | ошибка регистрации в ОПКЦ (не транзиентная) | — | `errorCode`, outbox, вебхук `mandate.rejected` |
| M4 | `PENDING_CONSENT` | `ACTIVE` | событие ОПКЦ `mandate.activated` (или подтверждение сверкой) | дедуп по `eventId` | сохранить границы согласия, расписание `nextDebitAt`, outbox, вебхук `mandate.activated` |
| M5 | `PENDING_CONSENT` | `REJECTED` | отказ плательщика/ОПКЦ | — | outbox, вебхук `mandate.rejected` |
| M6 | `PENDING_CONSENT` | `EXPIRED` | истёк срок подтверждения согласия | подтверждение не наступило | outbox, вебхук `mandate.expired` |
| M7 | `ACTIVE` | `SUSPENDED` | пауза со стороны ТСП или техника ОПКЦ | — | остановить планирование; outbox |
| M8 | `SUSPENDED` | `ACTIVE` | снятие паузы/восстановление ОПКЦ | согласие не отозвано | восстановить планирование; outbox |
| M9 | `ACTIVE`/`SUSPENDED` | `REVOKED` | событие ОПКЦ `mandate.revoked` или отзыв ТСП | — | снять расписание; отменить не подтверждённые списания; outbox, вебхук `mandate.revoked` |
| M10 | `ACTIVE` | `EXPIRED` | наступил срок окончания согласия | — | снять расписание; outbox, вебхук `mandate.expired` |

Терминальные `REJECTED`/`EXPIRED`/`REVOKED` — переходов из них нет; повторные триггеры идемпотентны (AD-003).

## 4. Связь мандата и платежа (списание)

- Инициация списания — `POST /v1/payments` с `mandateId` (и `periodKey`/`merchantOrderId`), `Idempotency-Key` обязателен.
- Guard инициации: мандат `ACTIVE`; сумма ≤ лимита согласия; `periodKey` не имеет успешного/идущего списания; назначение соответствует согласию; ТСП активен.
- Платёжная FSM для списания: `CREATED → PAID → CREDITED → COMPLETED` (стадия `QR_ISSUED` пропускается — QR не выпускается). Переход `CREATED → PAID` допустим **только** для `paymentType = mandate_debit` и только по подтверждённому ОПКЦ событию.
- Зачисление — по общему правилу **только из `PAID`** (AD-005), неизменно.
- Отказ ОПКЦ → `FAILED` у списания; **мандат остаётся `ACTIVE`**, следующий период планируется.
- Возврат списания — существующая сага возвратов (ADR-005), без изменений.

## 5. Идемпотентность

| Триггер | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `POST /v1/mandates` | `Idempotency-Key` | возврат того же `mandateId`, состояние не меняется |
| Событие ОПКЦ о мандате | `eventId` | обработанный `eventId` игнорируется; новый `eventId` по завершённому переходу — алерт, состояние не меняется |
| Инициация списания | `(mandateId, periodKey)` + `Idempotency-Key` | возврат существующего списания; повторный вызов ОПКЦ **не** выполняется |
| Гонка воркеров планировщика | уникальный индекс по `(mandateId, periodKey)` | создаётся ровно одно списание |
| Возврат | `refundId` | повтор возвращает существующий возврат |

## 6. Сверка и восстановление

- Открытые состояния мандата (`CREATED`, `PENDING_CONSENT`, `ACTIVE`, `SUSPENDED`) — кандидаты для ежечасной сверки с ОПКЦ.
- «У ОПКЦ подтверждён, у нас нет» → дозапрос статуса → M4.
- «У нас активен, у ОПКЦ нет» → стоп-сигнал: остановить списания по мандату, эскалация.
- Пропущенные списания (планировщик был недоступен) — догон по расписанию без дублей (идемпотентность по периоду); отчёт просроченных списаний доступен всегда.
- Отзыв, пришедший позже инициированного, но ещё не подтверждённого списания → списание отменяется; уже подтверждённое ОПКЦ — завершается (деньги вернуть можно только возвратом).

## Критерии приёмки

Проверяемые (EARS; негативные — обязательны):

- **When** мандат в `ACTIVE`, the шлюз shall инициировать списание по `(mandateId, periodKey)` и довести платёж до `COMPLETED`.
- **When** ТСП повторно инициирует списание за тот же период, the шлюз shall вернуть существующее списание и не вызвать ОПКЦ повторно.
- **When** два воркера планировщика берут одно задание, the шлюз shall создать ровно одно списание.
- **When** мандат не в `ACTIVE`, the шлюз shall не инициировать списание в ОПКЦ.
- **When** плательщик отзывает согласие, the шлюз shall заблокировать новые списания и отменить не подтверждённые ОПКЦ.
- **When** ОПКЦ отклоняет списание, the мандат shall остаться `ACTIVE`, следующий период shall планироваться.
- **When** ОПКЦ недоступен, the шлюз shall ретраить по политике, не помечая списание `FAILED` преждевременно, и не создавать дубль после восстановления.
- **If** сумма или период выходят за границы мандата, the шлюз shall отклонить инициацию без вызова ОПКЦ.

Машинные проверки (fitness): тест «недействующий мандат → списание недостижимо» (AD-009); тест «повтор/гонка за период → одно списание»; тест «отзыв → следующая инициатива отклонена»; тест «догон после простоя без дублей».

## Риски

- **Двойное списание за период** при гонке воркеров или ретрае инициации — финансовый инцидент и жалоба плательщика. Митигация: уникальный индекс `(mandateId, periodKey)` + идемпотентность ОПКЦ по `reference` (обязательный критерий RFP).
- **Списание по отозванному мандату** из-за задержки события отзыва. Митигация: блокировка планирования по событию + сверка + freshness-check перед каждым вызовом ОПКЦ.
- **Пропуск списания** (планировщик недоступен, пропущен тик) — недополучение выручки ТСП. Митигация: catch-up при старте, отчёт просроченных списаний, алерт.
- **Протокол мандатов НСПК неизвестен** `[ТРЕБУЕТ ПРОВЕРКИ]` — модель может измениться по факту документации. Митигация: контракт адаптера изолирует ядро (AD-008), протокольные детали локализованы.
- **ПДн плательщика** (идентификатор, история согласий) расширяет периметр 152-ФЗ. Митигация: минимизация, шифрование, маскирование, правовое основание (A3).
- **Ретраи неудачных списаний** («дюннинг») конфликтуют с плательщиком. Митигация: политика повторов по регламенту НСПК, уведомления (A3).

## Согласованность с API ТСП

Маппинг наружу (см. `docs/contracts/tsp-api.md`): статусы мандата отдаются как есть; технические подсостояния списания наружу не выставляются. `paymentType = mandate_debit` отличает списание от разового платежа; поле `mandateId` связывает платёж с согласием.
