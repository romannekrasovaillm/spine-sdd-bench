# Epic-context — СБП-подписки (рекуррентные C2B-списания)

Собран из: `ARCHITECTURE-SPINE.md` (AD-001…AD-008), `docs/adr/ADR-002/005/007`, `docs/adr/ADR-008`, `docs/adr/ADR-009`, `docs/contracts/tsp-api.md` v0.2, `openapi/tsp-api.yaml` v0.2, `docs/solutioning.md`, `docs/nfr.md`, `changes/recurring-c2b-mandates/IMPACT.md`, `NFR.md`, `ACCEPTANCE.md`. Статус: пакет готов; публикация — **после человеческого решения A3**.

## Цель изменения

Дать ТСП (онлайн-кинотеатры, ЖКХ, связь) рекуррентные C2B-списания по согласию плательщика («подписки СБП»): плательщик однократно даёт согласие, далее списания инициируются без его участия; согласие можно отозвать. Существующие C2B-платежи и контракт v0.1 должны продолжать работать без изменений.

## Что переиспользуется (не изобретать заново)

- **Денежный путь**: списание — это обычный `Payment` (`source=SUBSCRIPTION`, поля `mandateId`, `billingPeriod`), проходящий существующую статусную машину `CREATED → QR_ISSUED → PAID → CREDITED → COMPLETED`; зачисление в АБС и возвраты — по ADR-005.
- **Идемпотентность и outbox**: те же механизмы AD-002/AD-003 (атомарно «статус + outbox + аудит»).
- **Адаптер ОПКЦ**: только через вендорский адаптер (граница AD-008); новые операции подписок добавляются в его внутренний контракт, протокол НСПК остаётся внутри адаптера.
- **Нотификатор, сверка, DLQ, аудит, SIEM** — существующие.

## Связывающие инварианты (Rule — дословно)

**AD-001.** Rule: Любое взаимодействие с АБС и ОПКЦ СБП — только через адаптеры СБП-шлюза (единая точка вызова; fitness: отсутствие исходящих вызовов НСПК/АБС вне адаптеров).

**AD-002.** Rule: Изменение финансового статуса платежа и запись исходящего события (outbox) выполняются в одной локальной транзакции. Нарушение — дефект блокера.

**AD-003.** Rule: Повторная доставка любого сообщения не изменяет уже завершённое состояние (тест «повтор → состояние не меняется, результат идемпотентен»).

**AD-004.** Rule: Протокол НСПК знает только адаптер ОПКЦ; внутренний контракт шлюза — единственный интерфейс для остальных компонентов.

**AD-005.** Rule: Вызов АБС на зачисление возможен только из состояния `PAID` (подтверждённый НСПК статус). Зачисление из `CREATED`/`QR_ISSUED` недостижимо.

**AD-006.** Rule: Сеть между зонами — только через межсетевые экраны по белому списку; ключевой материал — в сертифицированном СКЗИ/HSM; доступ операторов — привилегированный контур с 4-eyes для ручных операций.

**AD-007.** Rule: Каждый финансовый переход и административное действие — в неизменяемом аудит-логе; все каналы к ОПКЦ — на сертифицированных СКЗИ.

**AD-008 `[ADOPTED]`.** Rule: Ядро шлюза проектируется контрактно-независимым от транспорта (внутренний контракт адаптера ОПКЦ — единственная зависимость). Вендор транспорта обязан предоставить сертификаты ФСТЭК/соответствие требованиям НСПК, тестовый контур, SLA.

**AD-009 (предлагаемый, вступает после ратификации A3).** Rule: рекуррентное списание создаётся только при мандате в состоянии `ACTIVE` на момент инициации; отзыв согласия останавливает следующее списание.

**AD-010 (предлагаемый).** Rule: ключ идемпотентности списания — `(mandateId, billingPeriod)`; уникальность обеспечивает БД; повторный триггер возвращает существующее списание; неопределённый исход (`UNKNOWN`) разрешается сверкой, а не повторной отправкой.

**AD-011 (предлагаемый).** Rule: расписание (`nextChargeAt`, периодичность, `endAt`) хранится в БД шлюза; планировщик пересчитывает due-мандаты из БД и не хранит расписание в памяти или очереди.

## Запреты (менять нельзя)

- Не создавать второй денежный путь и второй источник истины (запрещено проектировать отдельное хранилище/сервис подписок).
- Не вызывать ОПКЦ/АБС вне адаптеров; не реализовывать протокол НСПК в ядре.
- Не зачислять в АБС вне `PAID`; не создавать списание без `ACTIVE`-мандата; не создавать второе списание за период.
- Не ломать контракт v0.1 (только аддитивные изменения; `contract_diff` breaking = 0).
- Не менять файлы решений (`ARCHITECTURE-SPINE.md`, `CONSTRAINTS.yaml`) вне дельты; конфликт со спайном обязан остановить работу.

## Стыки (контракты для реализации)

- **API ТСП v0.2** (`openapi/tsp-api.yaml`): `POST /v1/mandates`, `GET /v1/mandates/{id}`, `GET /v1/mandates/{id}/charges`, `POST /v1/mandates/{id}/revoke`; схемы `Mandate`, `Charge`, `Periodicity`, `MandateStatus`, `ErrorCode`; события `mandate.activated|revoked|expired|rejected`; коды ошибок `MANDATE_*`, `PERIOD_ALREADY_CHARGED`, `CONSENT_*`.
- **Адаптер ОПКЦ**: операции регистрации/отзыва согласия и списания по мандату; идемпотентность по `reference`; `UNKNOWN` — не повторять. Точный протокол НСПК — внешний вход `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **АБС**: без изменений по существу (тот же идемпотентный путь `paymentId`); меняется пиковый профиль.

## Критерии приёмки и откат

- Критерии — EARS `AC-1…AC-13` в `ACCEPTANCE.md` (включая негативные: дубль периода, гонка «отзыв ‖ инициация», `UNKNOWN`, недоступность АБС/ОПКЦ, рестарт планировщика).
- Откат — фиче-флаги `subscriptions.enroll=off`, `subscriptions.charge=off`; начатые операции доводятся; владелец решения — solution-архитектор. Подробно — `ACCEPTANCE.md` §4 и `ROLLBACK.yaml`.

## Внешние входы (блокируют точную спецификацию)

1. Протокол ОПКЦ по подпискам (согласие, списание по мандату, уведомления, лимиты, тайминги) — `[ТРЕБУЕТ ПРОВЕРКИ]`.
2. Подтверждение поддержки операций подписок вендорским адаптером (RFP-дополнение).
3. Политика повторных попыток при недостатке средств и окно «догона» (бизнес, A3).
