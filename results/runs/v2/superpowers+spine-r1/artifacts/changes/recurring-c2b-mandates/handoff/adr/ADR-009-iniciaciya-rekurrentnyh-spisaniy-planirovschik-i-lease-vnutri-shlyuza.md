# ADR-009. Инициация рекуррентных списаний: планировщик и lease внутри шлюза

- Date: 2026-09-28
- Status: Proposed
- Owner: solution-architect (платёжный контур) + эксплуатация платёжного контура
- Related: ADR-002, ADR-004, ADR-005, ADR-008, AD-002, AD-003
- Модель-автор: qwen-code

## Context

СБП-подписки (ADR-008) требуют «часов»: регулярно определять, по каким мандатам наступил срок списания, и инициировать списание. Планировщик инициации — компонент, который **создаёт финансовые операции без действия клиента**, поэтому к нему предъявляются требования сильнее, чем к обычному фоновому заданию:

- **не терять списания** при перезапуске/сбое (RPO=0 распространяется на расписание);
- **не создавать дублей**: второе списание за период — двойное списание средств плательщика, недопустимо;
- **не быть источником истины расписания**: если расписание «знает» планировщик, а не шлюз, состояние расходится (нарушение AD-002);
- выдерживать **пиковые дни** (массовые списания в начале месяца: кинотеатры, ЖКХ, связь платят «в один день») без неограниченного роста очереди;
- быть устойчивым к **неопределённому исходу** вызова ОПКЦ (таймаут): повтор «вслепую» опаснее паузы и сверки (AD-003, `docs/contracts/opkc-adapter.md` §5–6).

## Decision

1. **Расписание хранится в БД шлюза** как атрибуты мандата (`nextChargeAt`, периодичность, `endAt`) — единственный источник истины (AD-002). Планировщик расписание не хранит.
2. **Планировщик — внутренний компонент платёжного контура шлюза.** Он периодически выбирает мандаты `status=ACTIVE` с `nextChargeAt <= now` и в **одной локальной транзакции** создаёт `Charge` + запись в outbox («инициировать списание»). Дальнейший путь — существующий: адаптер ОПКЦ → `PAID` → зачисление в АБС → `COMPLETED` (ADR-005). Планировщик не вызывает ОПКЦ/АБС напрямую (AD-001, AD-004).
3. **Идемпотентность периода — в БД, не в памяти.** Уникальный ключ `(mandateId, billingPeriod)` гарантирует не более одного списания за период; повторный проход планировщика, перезапуск или переезд аренды не создают вторую операцию (AD-010 спайна; шаблон правила `idempotency-key`).
4. **Аренда лидера (lease) — защита в глубину.** Активный планировщик удерживает lease; «почти один» планировщик снижает шум повторных срабатываний, но корректность обеспечивает уникальный ключ периода, а не выборы: единственность недостижима, достижима идемпотентность.
5. **Неопределённый исход не повторяется вслепую.** Таймаут/неизвестный ответ адаптера фиксируется как `UNKNOWN` по `reference` (= `paymentId`); исход разрешается сверкой статуса, а не повторной инициацией (AD-003, шаблон `unknown-outcome-no-resend`).
6. **Восстановление — пересчёт, а не «память планировщика».** При старте/после сбоя планировщик пересчитывает due-мандаты из БД. «Догон» ограничен окном назад и политикой отсечения устаревших периодов; превышение лага — алерт. Backlog разбирается с приоритетом, без бесконечного накопления.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Внутренний планировщик шлюза: расписание в БД + outbox + lease (выбран)** | Единый источник истины (AD-002); идемпотентность периода; списания не теряются при рестарте; вписывается в AD-001 (нет нового внешнего стыка) | Новый компонент и его эксплуатация; нужна аренда/лидер-выбор; нужно следить за лагом и backlog |
| B. Внешний планировщик (enterprise cron/платформа) вызывает идемпотентный внутренний API | Переиспользование платформы планирования | Расписание и состояние «снаружи» → два владельца истины; двойные триггеры; лишний security-стык; сложнее согласованность при сбоях |
| C. Отложенные сообщения в очереди на каждое списание (delayed messages) | Распределённость «из коробки» | Очередь становится источником истины расписания (нарушение AD-002); потеря сообщения = потерянное списание; изменение расписания требует перепланирования |
| D. Регулярность в АБС (периодические документы) | АБС умеет плановые документы | АБС не знает статус СБП и согласие; рассинхрон (см. ADR-008, вариант D) |

## Consequences

### Positive

- Списания не теряются при сбое планировщика: расписание восстанавливается из БД.
- Дублей списаний за период нет даже при нескольких планировщиках — уникальный ключ в БД, а не «договорённость процессов».
- Неопределённый исход не превращается в двойное списание или «фантомный» отказ.
- Периметр безопасности не расширяется: планировщик внутри платёжного контура и не ходит во внешние системы.

### Negative

- Новый фоновый компонент: нужно мониторить лаг и backlog (особенно в пиковые дни), обновлять и эксплуатировать.
- Аренда/лидер-выбор добавляет нетривиальную логику; её отказ не должен ломать корректность (её обеспечивает ключ периода) — нужна дисциплина тестов.
- Политика «догона» и отсечения устаревших периодов — компромисс между «не потерять» и «не списать неожиданно много»; параметры утверждаются бизнесом.
- Нагрузка на НСПК/АБС в пиковые дни концентрируется: нужны лимиты и сглаживание (rate limiting, bulkhead).

## Reversibility

**reversible** для механизма инициации: замена внутреннего планировщика на внешний (вариант B) не меняет модель мандата и денежный путь — меняется только «кто держит часы». При этом идемпотентность периода (`mandateId`, `billingPeriod`) — связывающее решение с финансовой семантикой и при отказе оценивается как `costly` (вместе с ADR-008).

**Условие пересмотра (expiry):** изменения регламента ОПКЦ по срокам/уведомлениям; появление в банке корпоративной платформы планирования с гарантиями идемпотентности, делающей вариант B предпочтительнее; устойчивый рост backlog в пиковые дни.
